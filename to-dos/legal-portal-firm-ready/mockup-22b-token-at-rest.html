The firm's key, kept locked

The portal link is the firm's key: whoever has it acts as the firm. The table kept it in plain text and four office roles could read it. The catch: every email to the firm carries the live link, so the server still needs the key. The answer is Vault, not a plain hash.

Where the key lives

Before
legal_portal_links
  token       a1b2…(64 hex)   ← office roles can SELECT
  token_hash  9f3c…
mint_legal_portal_link(rotate => false)
  → { token: "a1b2…" }  ← any office role, any time
legal-notify-dispatch
  → reads token from the table
After
legal_portal_links
  token            NULL, CHECK (token IS NULL)
  token_hash       9f3c…   (the functions look up by it)
  token_secret_id  → Vault, encrypted
office grant: every column but token
mint_legal_portal_link(rotate => false)
  → { token: null, exists: true }
mint on create / rotate → the raw token, once
legal-notify-dispatch
  → legal_portal_link_token(firm)  service role only

Is this the best we can do?

  • Why not a plain hash, as asked? The first draft did exactly that, then traced legal-notify-dispatch: every notice and digest builds the firm's link from the raw token. Hash-only would have emailed a dead link. Vault keeps the key for the server alone.
  • How does the office preview without the key? By firm id, signed in. The function checks the caller's own session against legal_office_can_read(), the same rule that already lets those roles read every legal table.
  • Can the push break anything? The dialog, the page and the journey work before and after it, and the dispatcher reads the raw column until the Vault read exists. Deploy the two functions, then push. The Lien desk share's "copy the firm's link" line goes quiet after the push.
  • What if Vault refuses? The backfill aborts the whole file before anything is emptied. A refused cleanup on rotate is noted and skipped; a revoked link's key opens nothing anyway.
