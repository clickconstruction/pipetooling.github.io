Is this the best we can do?

  • Will the demo show the new sample tomorrow? Not if it waits on a legal-portal redeploy. Refined: the page builds the sample itself from the same shared fixture the function answers with (sampleLegalPortalResponse), so it shows the moment the page ships, makes no network call, and the function's answer stays identical for anyone calling it.
  • Is "one promise kept" honest? Only once the function agrees. The office's desk measures a promise against what was billed when it was made; legal-portal summed every bill on the job, so on a real matter like this one the first promise would read as broken on the firm's page and kept on the desk. Fixed in the same PR: billedAtPromise, the desk RPC's rule, in a shared kernel with a test.
  • Does it hold on every day? The test builds the packet and the grid on eight days (month ends, a leap day, a year turn, weekends) and checks the same story each time: the notice in time, the affidavit still open, nothing marked missed. The sample's statutory 15th is held to the client's own lien clock by a test.
  • Is the grid empty on its default view? It was on the first draft (every job "later"). Refined: the repipe's affidavit was filed two days ago, so its service copy is always due; the dental job's next notice is chosen to be the first one not yet passed.
  • Anything left? The payment still prints as $-4,000.00: that is item 5's one formatter. The Lien grid's paid-out and 10 % columns stay "?" even though the owner answered: the grid kernel does not read the owner's call yet (worth a later item).
