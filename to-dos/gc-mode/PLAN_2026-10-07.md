# GC mode: the plan from 2026-10-07

The prototype is the spec (`HANDOFF.md`, `BUILD_MAP.md`). This page says who does what over the
next few days so real people are using GC mode on prod while the rest is built. `BUILD_MAP.md`
section 3 holds each lane's PR list; `HELPERS.md` holds the five steps and the rules. Where this
page and `BUILD_MAP.md` disagree, this page is newer.

## The shape

- **Two tracks, one rule.** Every lane writes its plan on the spike first, then builds on `main`
  in small PRs behind the dev door. A separate *door* PR opens each surface to real roles once a
  person can try it. Nothing from the spike ever merges.
- **The user-testing path is the office's own loop.** A real project goes in through New project,
  its plans and questions follow, the schedule draws from its scope lines, then the office moves
  bars. That needs no trade on the other side, so it is testable within two days. The trade-side
  path (company record, then portal, then a friendly trade) is the second wave, around day four.
- **Owner Billing and Building's draws stay dev-only** until the trade side is real: neither can
  be tested without a trade's pay application.

## How a helper works here

- **Read first**, in this order: `HANDOFF.md`; this page; `BUILD_MAP.md`; your lane's plan if it
  exists; `README.md` → *The model, in one paragraph*, *What the prototype has*, *Where it plugs
  into the app that exists*; `HELPERS.md` → *The rules that do not bend*. The plan docs live only
  on the spike: read them with `git show origin/spike/gc-mode:to-dos/gc-mode/<file>` from any
  checkout, or check the spike out.
- **Your plan goes on a spike branch**, `spike/<lane>-plan`, cut from `origin/spike/gc-mode`.
  Message the lead (*GC spike*) with the branch and a five-line summary. Nobody but the lead
  pushes to `spike/gc-mode`.
- **Your code goes on `main`**, one PR at a time, cut from `origin/main`, behind the dev door, with
  its release note, fragment, guide and migration doc (`CLAUDE.md`). Claim the version at the cut
  (`npm run claim -- --branch <branch>`) and the stamp (`npm run claim -- --migration <file>`),
  past `main`'s newest and past every claim not merged. Drop a session card in the main checkout's
  `.claude/sessions/active/` when a PR starts.
- **Helpers never apply DDL and never deploy.** Open the PR with `gh pr merge <n> --auto`, then
  message the lead that a migration or a function is waiting. New RPC names fail `npm run
  typecheck` until the types PR lands; the next PR on your lane waits for it.
- **One migration per lane per day.** The lead's push and Helper 7's types PR are the bottleneck.
  Stack your code PRs behind the types PR.
- **Your environment** (this machine): `node_modules` and `.env.local` come from the main
  checkout, `/Users/Grace/Documents/GitHub/pipetooling.github.io/` (`ln -s …/node_modules
  node_modules`; `cp …/.env.local .env.local`; never print or commit it). A dev server runs on your
  own port, `npm run dev -- --port 53<N> --strictPort` (Helper 1 → 5301 … Helper 7 → 5307); sign in
  at `/dev-login?as=1&to=/gc` (main) or `/dev-login?as=1&to=/bids/gc` (the spike).
- **Tests**: `VITE_SUPABASE_URL=http://x VITE_SUPABASE_ANON_KEY=x npx vitest run src/lib/gc
  src/components/gc` on main; add `src/lib/gcMode` on the spike. Typecheck in the background, 10 to
  25 minutes. Theme check: `node scripts/theme-tokenize.mjs --check src/components/gc`.
- **Report back** with: what it does, the commands you ran and their results, anything left out, and
  the owner's calls your plan raises.
