# G-136: export the schedule, as a spreadsheet and as the file Project and Primavera read

Helper 2, branch `spike/g136`, 2026-10-06. The row in `GANTT_FEATURES.md`: *Export to a spreadsheet,
and to the file Microsoft Project and Primavera read, for a customer who asks* (Tell, Later; round
three). The mockup and the plan, for the lead's go before any code.

## What it is for

A customer who is a GC or an owner's rep keeps a master schedule of its own, in Microsoft Project or
Primavera P6, and asks for ours in it. An owner asks for "the schedule in Excel". Today the only ways
out are the printed page (G-21) and their portal. Each file is one press, from the same chart, with
the same rule for what a customer may see.

## Where it sits

The chart's toolbar, beside **Print or PDF**: a quiet button **Export**. It opens a window of its
own, **Export the schedule**, with the same **Who it is for** switch and the same line under it as
*Print the chart*, read from the same words.

**Why its own window, not inside Print the chart.** The paper is the chart *as you see it*: the
filters and the folds carry over. A schedule file is the logic of the job, and a bar left out would
cut the waits the rest hang on, so a file always carries the whole schedule. One window saying both
"It shows 5 of 30" and a button that writes 30 would be a trap. The switch is the same switch; the
promise is different.

The window's words, exactly: the count (*The whole schedule: 30 activities in 8 trades, 3 things the
work waits on and 4 dates to meet.*), *The filters and folds do not change a file.*, the switch and
its line (the print kernel's own `forWords`), and the two buttons with one line each. A press saves
the file through the browser (a link with `download`, as the pay application's Excel does) and the
window stays open for the other.

## What a file carries, by who it is for

- **Our team**: every activity of the schedule, grouped by the chart's grouping (by trade as it
  opens), each with its trade, company, dates, days, percent done, the chart's words for where it
  stands, what it waits on with the gap, *not before* and *must finish by*, and the days it really
  ran. Then the things the work waits on from outside (a delivery, a decision, a permit, the
  utility), each as a milestone on its expected day that the work it holds waits on. Then the dates
  the job must meet.
- **The customer**: what their picture carries, from `customerSchedulePicture`, and nothing else. An
  owner gets the stages of the job with their dates and percent, and the dates to meet. A GC or an
  owner's rep gets every bar by stage as their list shows it, in their words (*on plan*, *not
  started*). No company, no spare days, no waits between bars, no notes, nothing from outside the
  trades. The lead's rule from G-21 again: what the customer may see is decided in
  `gcCustomerSchedule.ts`, once.
- **Never the rough or the what-if copy.** A file reads the chart's bars, which read
  `project.schedule`. The rough lives in `project.rough` (G-45) and the what-if copy in its own place
  (G-81, still building), so neither can reach a file. A test pins the rough; G-81's own test can pin
  its copy when it lands.

## The project file

One `.xml` in Microsoft Project's own XML schema (MSPDI,
`http://schemas.microsoft.com/project`), which Project opens and Primavera P6 imports. Only the
elements both read, in the schema's order:

- **The project**: `Name`, `Title` (the job), `ScheduleFromStart`, `StartDate`, `FinishDate`,
  `CalendarUID`, `MinutesPerDay` 480, `MinutesPerWeek` 3360, `DaysPerMonth` 30.
- **One calendar, every day worked** (the owner's 365-day rule): seven working days, 8:00 to 12:00 and
  13:00 to 17:00. So a bar of 12 calendar days is 12 working days in both programs, and nothing
  moves on import.
- **Groups as summary tasks** (outline level 1) and the work under them (level 2). Each task: `UID`,
  `ID`, `Name`, `OutlineNumber`, `OutlineLevel`, `Start` (8:00), `Finish` (17:00), `Duration`
  (`PT96H0M0S` for 12 days), `DurationFormat` 7 (days), `Milestone`, `Summary`, `PercentComplete`,
  `ActualStart` and `ActualFinish` where the days it really ran are known, a constraint, and its
  waits.
- **Waits as links**: `PredecessorLink` with `Type` 1 (finish to start, the only kind the app has),
  `LinkLag` in tenths of a minute (4800 a day) and `LagFormat` 7. A thing the work waits on from
  outside is a milestone on its expected day that the held work waits on, the way a scheduler draws
  a delivery.
- **Constraints**: *not before* is "start no earlier than" (`ConstraintType` 4); *must finish by* is
  "finish no later than" (7). A date the job must meet is a milestone held on its day (4). Project
  holds one constraint a task, so an activity with both carries *not before* in the file and keeps
  *must finish by* in its spreadsheet row.
- **The company** (our team's copy only) in the first text field, named *Company*
  (`ExtendedAttribute`, `Text1`).

**What Primavera needs that Project does not**, and how the file meets both:

1. Primavera turns summary tasks into its WBS and only the tasks under them into activities, so every
   activity must sit under a group. The file always groups; nothing sits at the top level alone.
2. Primavera makes its activity IDs from the file and wants them short and unique. The file numbers
   tasks 1, 2, 3…, never the app's long line ids.
3. A link whose other end is not in the file is dropped on import. A link is written only when both
   tasks are in it, and a file is always the whole schedule, so none is lost.
4. Primavera has no elapsed days and no manually scheduled tasks. Durations are working days on the
   every-day calendar, and every task is scheduled automatically.
5. Left out: baselines and deadlines, which Primavera does not take from this file (the plan at Start
   stays in the app and on the paper), and resources and notes, which would put our companies in
   the customer's own lists; the company rides in a text field instead.

## The kernel and the writers

`src/lib/gcMode/gcScheduleExport.ts`, pure, tested, out of the barrel:

```ts
export interface ExportRow {
  uid: number                       // 1, 2, 3… in file order: a group, then its work
  level: 1 | 2                      // 1: a group (a summary task); 2: an activity, a wait, a date to meet
  kind: 'group' | 'activity' | 'inspection' | 'added' | 'wait' | 'milestone' | 'stage'
  group: string
  name: string
  trade: string | null
  company: string | null            // our team's copy only
  start: string
  finish: string
  days: number | null
  done: number | null               // percent
  stands: string                    // the chart's words, or the customer's
  waitsOn: { uid: number; name: string; gap: number }[]   // our team's copy only
  notBefore: string | null
  mustFinishBy: string | null
  actualStart: string | null
  actualFinish: string | null
}

/** The schedule as rows, the chart's bars for our team, the customer's picture for them. Never filtered or folded. */
export function scheduleExport(input: GanttExportInput): { rows: ExportRow[]; counts: { activities: number; groups: number; waits: number; dates: number }; title: string }
/** The spreadsheet: a header and one row a line. */
export function scheduleCsv(rows: ExportRow[], forWhom: 'team' | 'customer', copy: 'team' | 'stages' | 'everyBar'): string
/** The project file both programs read: the common part of MSPDI. */
export function scheduleMspdi(rows: ExportRow[], meta: { title: string; company: string; withCompany: boolean }): string
/** "Fair-Oaks-Shops-Building-D-schedule-2026-10-02.csv", and "-for-Cibolo-Creek-Partners" on the customer's. */
export function exportFileName(job: string, today: string, ext: 'csv' | 'xml', customer: string | null): string
```

`GanttExportInput` is the print's input without the paper's own fields: the chart's bars, its
grouping, the milestones, the outside waits, today, building, who it is for, and the job's words with
the customer's picture (`GanttPrintJob`). The window builds it from the chart's state the way *Print
the chart* does.

## Left out, and why

- **Opening the file in Project and in P6 for real.** The prototype has neither; the file is checked
  against the schema's names and order, and the first real import is the owner's, with a scheduler's
  copy of each.
- **Excel's own `.xlsx`.** A `.csv` opens in every spreadsheet; an `.xlsx` would need the Excel library
  the pay application loads, for no column a `.csv` cannot carry.
- **Primavera's own XER file.** P6 reads the Project file; XER is its native format, a second writer
  for one program.
- **Import** (G-137), next in my order.

## Is this the best we can do?

Three ways to make it better, by the chart's jobs:

1. **Tell: the file carries what changed since it last went.** A customer who loads our file into
   their master every week wants to know what moved. A *What changed since the last file* list (the
   moves since the last export, with their reasons in the customer's words) would ride with it.
   **Not picked**: it needs a record of each file sent, which is G-94's *Send* ground; the owner's
   call, worth its own row.
2. **See: the plan at Start in the project file.** Project would draw our plan at Start against the
   bars right away. **Not picked**: Primavera does not take baselines from this file, and the lead
   asked for the common part; one file would show different things in the two programs.
3. **See and Chase: a Spare days column, a number to sort by.** On our team's spreadsheet the words
   *37 spare days* cannot be sorted; a number can. One sort and the work that sets the finish rises
   to the top, which is what a superintendent wants when the file is open in Excel. **Picked**: one
   column from the read the chart already makes (`GanttBar.spare`); the customer's copies never have
   it, since a customer never sees spare days.
