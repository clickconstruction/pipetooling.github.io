# Messages — hand-off, 2026-10-11 (prototype v1.31)

For the next agent or person picking this up. Everything named here is on branch `spike/gc-mode`
in `to-dos/gc-mode/messages/`; none of it is on `main` and nothing is built in the app yet.

## 1. What this is, in three lines

- One place for every call, text, email and team note with a customer, trade partner or architect.
- A **contact owns the messages**; jobs hang off the contact; a message **may** be tied to one job.
- It is built in the **GC board first** (`/gc` → Follow up and Messages), later for plumbing.

## 4. The owner's decisions on 2026-10-11, in his words where we have them

- "All of these messages are really stored with a contact, and then we associate jobs with that contact. And sometimes particular messages with particular jobs."
- Build it in the GC board first, not a separate chat.
- The note-for-the-team button is the same yellow as a note on the page.
- A preview of the email / text, as a window; then: "instead of send instantly sending something, I would like for what you made to be the confirmation screen before it goes out."
- The Tie-to menu shows the job name and, at the right, a button that opens the bid or job as a window.
- No Reopen button: posting a note for the team closes the row; a new message reopens it.
- Quick replies: a two-row strip that scrolls, in a gray section; an Edit button; each line shows who added it and when, who edited it and when.
- Write it down was too general: say exactly what is written down (one short line with tags by kind).
- Long emails: the first four lines; a click opens the full message as a window, with highlights, attachments, print to PDF and the Apple share menu; Show all text per thread.
- A click anywhere on a Follow up row opens the thread at that message.
- The who-has-it control, taking hints from Intercom; the pill in the top right corner.
- Hover on any control says what it does and how it affects things.
- Header layout **A**; the label before the company ("Customer: Helotes Dental Office"); the email stays on the facts line.
- Where "waiting 6 days" was: show whose court it is in, when they last wrote, when we last wrote.
- A way to keep it in our court after we send: the tick above Send, at the right; *We owe them…* on the toolbar; Settled.
- The left bar collapses; a right bar, collapsed by default, shows the customer's or vendor's flow as a chart; the flow is edited in Settings.
- Every header line after the first two starts at the left edge.
- The toolbar: what is redundant goes (Text, Email, the hint sentence); state beside the pill; the rest behind More ▾.
- Settled opens an internal note at the bottom saying how or why it was settled, for the team.
- The stamps stacked and aligned from the right; the flow is as important as the messages, so a collapsed icon rail like the left one.

## 7. How to work on it

- **Edit**: it is one HTML file with the script at the bottom. Keep every control's `data-tip="Name|what it does|what it changes"`. After a change, parse-check the script: pull the text between `<script>` and `</script>` into a `.mjs` and run `node --check` on it.
- **Look**: open the file in a real browser (the app's file pane shows a static snapshot and can render in print mode). For a fixed-width proof use headless Playwright from inside a repo worktree (it has `node_modules/playwright`): open the file URL, `openThread('priya')`, `setFlow(true)`, `screenshot`. `window.__landing` guards the first render's scroll.
- **Demo state you can drive from the console**: `openThread(id)`, `setFlow(bool, stepId)`, `setCollapsed(bool)`, `settle(id)`, `theyReply(id)`, `showAll[id]=true; render()`. Ids: `priya`, `greg`, `elena`, `jonah`, `bill`, `tom`, `unknown1`.
- **Log every change** as one line under "Prototype log" in `MESSAGES_PLAN.md` (`v1.NN, date: what and why`), and amend the sentence in the plan that holds the fact. Commit to `spike/gc-mode` and push; never to main.
- **Rules that apply** (from `CLAUDE.md` and `../HELPERS.md`): finances stay owner-only; a relayed yes is no yes for anything that writes prod or sends mail; never hand-edit `database.ts`; no agent emails Taunya or Malachi.
