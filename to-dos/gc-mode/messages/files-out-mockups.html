What the handler keeps to

  1. Size and kind decide, never a person. outgoing.ts already holds the rule: an email takes the file up to 10 MB, the files together up to 20 MB, and a plan set or a file of unknown size always goes as our link. A text carries everything as our link.
  2. Our link, not Drive's. A trade partner's file with a portal page goes as their portal link at that page. A customer's goes the same way only where their portal has the page. An architect's, or any file with no page, goes as a file's own link, clicktooling.com/f/<link>, which names one file and nothing else.
  3. Team only stays team only. The function reads a Team only file with the service account and hands its bytes to the person holding the link. It never changes a share. A Plans file opens in Drive's viewer, since that half is open to anyone with the link already.
  4. Every open is counted, and any link can be cut off. An open is a public_page_views row. A cut-off link answers the turned-off page at once, and the file stays where it was.
  5. Nothing goes out that Documents does not hold. A file from this computer goes into Team only, under Sent by us, before the email leaves. A photo goes into the job's photos. A send that cannot put the file there stops and says so, and nothing goes.
  6. Drive stays the one copy. The one list reads the folder each time it is asked and copies nothing into the database. The rows hold only what the database already holds: our links, their opens, and how each file went.

What I need the lead to settle

  1. A Team only file through our link. The function hands over the bytes, so nothing is ever shared. My pick is a cap of 50 MB for that path, with a bigger Team only file going only as a portal link or not at all. Or is a Team only file never sent outside, and the picker says so?
  2. How long a file's own link lives. The plan says a week fits a plan set. Most files on a message are read in the first days. My pick is 30 days, then the turned-off words, and any send of the file makes a fresh link. A portal link lives as long as the portal does, as now.
  3. A customer's link. outgoing.ts sends a customer their portal at the page only where their portal has it, and else the file's own link. Is that the plan's open item settled, or does a customer always get the file?
  4. The papers the app draws on demand. Only our contract is stored. A statement of work and the schedule have no file, and a pay application is made in the browser. My pick: a statement of work and the schedule go as their portal page only, and on an email to someone without that page they are not offered. The pay application is made at send time, as Bill the customer makes it. A PDF writer for the statement of work is its own later piece.
  5. The opens. Counting in public_page_views under a new surface, with no new table. Yes?
  6. The address. clicktooling.com/f/<link>, an app page beside /t/. Or straight to the function's address, which is longer and names Supabase?
  7. Save to Drive's default. Team only for a quote or a photo, Plans for anything else, with the person's pick in the sheet. Or Team only always, with Plans picked on purpose?
  8. One function or two. The plan names one, drive-link. I keep its open door and the office's four actions in it, each checked in code, so there is one Drive client to deploy. Or split the office's actions into their own function, so the open door has nothing else in it?

Is this the best we can do? Three ways it could be better, and the pick

  1. Read the Drive folder once a day into the database. The picker would open with every row at once. But Drive would stop being the one copy, a file added this morning would be missing, and the plan says copy nothing. Not this.
  2. Make every file's own link a portal page. Each person would have one place to read everything we sent them. But an architect has no portal, and a customer's pages are not all there yet. The kernel already prefers the page wherever one exists, so this comes on its own as the portals grow.
  3. Show the opens in the thread as they happen. A line like Greg opened the plans, 2:10 PM would tell Rosa her email landed. But a link cannot know who opened it, an open is a fact about a file rather than a move between us, and a plan set opened in bursts on a bid day would push the real lines out of view. Helper 1, whose thread it is, said no (2026-10-12). Not this.

The pick: the eight screens and six rules above, with the opens on the chip and each open's time in the window, never in the thread.
