Is this the best we can do? Three things the letter still gets wrong

The letter is a good record. It is not a good ask. A GC reads a schedule by stage, not by tag; the decisions we need are buried in a column; and a PDF is a photograph — the day after it is sent it is wrong, while the same rows already live on the GC's room card (the plan's PR 2). So: group by stage with the stage date once, put What we need from you above the table, and make the paper a door back to the live log.

  • Grouped by stageRough In · needed Oct 20 as a band; the rows under it are the rows that make or break that date. "Needed on site" stops repeating.
  • What we need from you, firstThe three rows that are waiting on the recipient, each with the date it must come by. The estimator's typed line becomes the first bullet. The table is the evidence; the ask is the document.
  • A door, not a photograph"This log lives at …" with a QR (the pay-QR mark, already in the repo) to the room card. Approving a row there records a typed name and email (owner decision 6).
  • An update marks change, a print does notOn Record, print and copy the changed rows carry an amber dot and a "since Sep 22" note; Print the log carries neither.

The calls this drawing makes, and why

  1. The letterhead is the submittal cover's, not a new one. Same company block, same To/Re, same brand image — the GC gets one family of paper from one bid. The panel needs the tab to pass what the cover already has (tagline, phone, project address, GC name).
  2. Print the log and the update are two documents from one builder. Today they are one sheet with the counter left on. A print says as of; an update says update N · changes since and marks them. Same rows, same columns.
  3. "Order by" turns into the recipient's deadline. Our internal last-safe-order date is, for a row they have not approved, the date their approval has to come by. That is the one number a GC acts on, so it heads the document.
  4. Notes print the row's note; changes get a mark. A bug today: the column named Notes prints the diff text, so a plain print loses every note the estimator typed for the GC.
  5. The paper points at the room card. The GC's room card is already the plan's next PR (v2.4083). A print that links to it stops being the only copy — the SpaceX problem the whole train was built to end.
  6. The preparer signs; the recipient does not. Owner, 2026-09-29: no acceptance signature — a signature and a date for the person verifying it is real. That is the test report's certifier block, so the settings row already holds the name; the estimator's own name comes from the session.
  7. Who it goes to is left open. The log was asked for by a GC and the code addresses the GC. If the owner's "vendor" is the supply house, the same sheet works with the house in To and "Expected on site" as the date they are confirming — a different ask than the GC's (approve rows), so the What-we-need block would read differently. One question for the owner.
