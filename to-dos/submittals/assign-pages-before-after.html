Before Per row: pick the file, type the pages

Every row asks which file, which pages? To answer, the user scans 75 thumbnails the size of a stamp, reads page numbers off them, remembers "23 to 24", and types it. The hunt is the work; the typing is the tax on top. 27 rows × a hunt each.

  • The question is asked from the wrong sideThe user knows the PDF's order (it follows the schedule); the UI makes them find pages for a row instead of naming the row for a page.
  • Thumbnails are unreadableAt 75 across five rows, a model number is two pixels. Every decision needs a zoom nobody offers.
  • Typed page ranges"3-4" is a transcription of something the user just saw — a second step that can be wrong.
  • No map of what is doneWhich pages are already on a row? Which rows still need one? Only by reading every row's Sheet column.

After Assign pages: one page big, one question, the answer pre-filled

A full-screen modal from the file's strip: Assign pages. Left: the page, large enough to read its header. Right: the fixture rows in schedule order, the expected one lit. The page's model number was read (pdfjs text, already in the repo) and matched to the row's submitted model, so the question comes answered — Space says yes and moves on. A pick marks where a fixture starts; the pages after it inherit until the next pick. The strip along the bottom colors every page by its fixture: the map.

  • Runs, not pagesSpace = same fixture as the last page. 75 pages become ~25 picks, most of them already right.
  • Read for you"Looks like WHA-500 — Z1700-500-OV is on the page." Green when the model matched; amber when it's only the next row in order; grey when nothing was read.
  • Keys over dragsSpace · Enter/click · ← → · Backspace · X · type a tag to filter. Drag a thumbnail onto a row still works, but nobody needs it.
  • The mapColored runs with tag labels; grey = unread, hatched = not a cut sheet. Click any page to jump. Wrong runs are visible before Done.

The owner's call · 2026-09-29 Every page gets eyes on it — the summary is a progress card, not an exit

The first draft opened on a summary with "Looks right — Done" for files the reader had mostly placed. The owner said no: this package goes to the customer, so the estimator reviews every page. The reader still pre-fills the answer, so most pages are one Space — but Done stays locked until all 75 have been seen and each is on a row or marked not a cut sheet. What survives from the draft: the counts as a progress card, Find for a row with nothing (it jumps the walk to the candidate page — still reviewed there), and the robot's guesses landing in the same walk.

  • Every page seenDone unlocks at 75 of 75 seen and 0 undecided. The count is on the button, so "how much is left" never needs asking.
  • Pre-filled, still reviewedA read page arrives answered in green; Space confirms it and moves on. The estimator's eyes are on every page for the same reason a proof-reader reads what the spell-checker passed.
  • Find for a rowA row with nothing gets Find: pages whose text mentions its model. Clicking one jumps the walk there; the page is decided in the walk like any other.

The calls this drawing makes, and why

  1. Page-driven, not row-driven. The owner's instinct is right: walk the pages, name the row. The page is the thing you have to look at; the row list is short and known. Row-driven means hunting through 75 thumbnails per row.
  2. The page is always big; Space is "yes", not "preview". Quick-look-on-spacebar costs two actions per page (select, peek) before the decision. With the page always shown at reading size, the decision is the only action.
  3. Picks are starts; pages inherit. Cut sheets come in runs. Marking where a product starts is ~25 acts on a 75-page file; marking every page is 75. Same result, a third of the work — and the strip shows the runs so a wrong start is obvious.
  4. Read the model number before asking. pdfjs text extraction is already in the repo (the quote-reply reader); the row already holds the submitted model. When they match, the question arrives answered and the human is a checker. This is the single biggest load cut, and it needs no robot.
  5. Every page is reviewed; the summary only reports. Owner, 2026-09-29: the package is submitted to the customer, so the estimator sees every page. The first draft's "check only the 9 unread pages" exit is gone; the counts stay as a progress card and Done carries "N of 75 seen".
  6. Nothing writes until Done. The owner's rule for this surface: the dropped PDF is a working file, the record is the pages on rows (decision 2026-09-15). Done writes sheet_file + sheet_pages per row in one pass; Cancel discards; Undo is free until then.
  7. Keys first, drag second. Typing "W" and pressing Enter is faster and more accurate than dragging a 40-pixel thumbnail across the screen; drag stays as a discoverable extra.
  8. One page can serve two rows. WC-1 and WC-2 split from one count (v2.4110) share a sheet; Shift+click adds the second row instead of forcing a copy.
  9. The robot lands in the same seat. "Ask the robot to split this file" already exists; its output should be suggestions in this modal, not a separate result to reconcile.
