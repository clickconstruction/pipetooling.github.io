## What stage 5 adds — the conversation, in one thread on the room

The review room (`/submittal?t=…`, `src/pages/SubmittalRoom.tsx`) is where the customer's architect already decides on rows. Stage 5 gives it a thread, so a question about a product is one conversation on the submittal itself — not a portal card, not an email chain we lose.

**5a · the conversation.** A card on the room, **On this submittal**, where a reviewer or a watcher can ask. Nobody's question is a decision. Decisions post into the thread as system entries, so the thread is the record and the rows are the summary. The board draws the timeline: *Wendi · Click · Sep 16 — Rev 2 is up. Three rows differ from the plans; each says why* → *Dana W. · Sep 16 · decided 22 rows · 2 revise 1 reject* → *Dana W. · Sep 17 — Is the 1.28 valve the same body? Our water budget is by fixture* → *Logan P. · Sep 17 · watching — Dana, the 1.0 is fine with Structura if TOTO can ship it* → *Wendi · Click · Sep 17 — Same body, different cartridge. Rev 3 will carry TET2UB31 at 1.0, three weeks from NWS* → *Wendi · Click · Sep 17 · shared Rev 3*. The office answers from the inbox it already works: the question lands as a customer-waiting request at high priority, the card gains **Reply**, and Reply writes the message, closes the request and emails the person their link. That is the one email the room ever sends. The GC's portal shows none of it (decision 10).

**5b · the drop zone.** A reviewer who marks up the PDF instead of using the room: drop their redlined PDF or forwarded email onto the revision. Until the stage 6 robot lifts the marks, the estimator types the decisions onto the rows, and the record reads *from Dana's PDF, entered by Wendi*. The per-person trail on the tab (*opened Sep 17 · decided 22 · asked 1*) was planned here but shipped early in 4a-ii (`personTrail` / `describeTrail` in `src/lib/submittals/submittalRoom.ts`), so 5b is smaller than drawn: the drop zone and the *entered by* provenance.

## What stage 6 adds — the robots confirm-first, and Drive

Every robot verb lands on a surface that now exists. A person confirms every row; a robot never sends and never decides.

**6b · three verbs on twin-mcp.** `put_specified_products` reads the fixture schedule off the plan substrate into `bid_specified_products` with `source='robot'`, unconfirmed until a person taps Save in the same *Plug in the fixture schedule* modal (stage 1) — the board reads *Robot read P002 · 18 tags · 15 sure · 3 want a look*. `file_cut_sheets` splits a house's whole PDF by tag into pre-tapped pages on the sheet strip (stage 3) as dashed guess chips; **Confirm 14 · pick 2** turns them into the green chips the strip already draws, then *Done with this file* as today. `read_redlines` reads a redlined PDF's annotations into proposed decisions on the older revision — *10 annotations · 6 read as decisions · 2 unsure · 2 are questions for the thread* — each landing on the room's thread as *read from Dana's PDF, confirmed by Wendi*, never as Dana's typed decision; the questions post as thread entries for the office to answer.

**6c · Drive.** Every shared package is filed in the bid's job folder beside the plans — *Jobs / SpaceX BA-02N / Architectural / Submittals / Rev 3 · 2026-09-17.pdf* — the folder `drive-intake` already makes. Shared revisions only, never a draft.

## The conventions that bit us in stage 4 (read before the first commit)

- **Migrations** only via `bash scripts/db-push.sh` from a checkout at `main` after the PR merges (the throwaway checkout in the scratchpad works: `git checkout -q -- src/types/database.ts` first, because db-push regenerates the types). Number from `origin/main`'s newest file (`git ls-tree --name-only origin/main supabase/migrations/ | tail -1`) and register with `npm run claim -- --migration <file>`. Hand-add the new columns to `src/types/database.ts` so typecheck passes before the regen; open a `chore(types)` PR from the regenerated file after the push.
- **PostgREST `on_conflict` cannot name an expression index** — `bid_submittal_people`'s uniqueness is `(room_id, lower(email))`, so an upsert on `room_id,email` 400s. Read then insert (`SubmittalShareModal.tsx` does this now).
- **Render smokes without a Router**: `BidWonJobActions.render.test.tsx` mounts bare. Anything you put under the won bid's Job block must not call `useNavigate` unguarded (`BidSubmittalChip.tsx` checks `useInRouterContext()`).
- **The live build's `VITE_SUPABASE_URL` ends in a slash**; strip it before concatenating `/functions/v1/…` (`SubmittalRoom.tsx` line 21).
- **`/bids?tab=submittals&bidId=…`** works since v2.3488 (the tab is in `bidTabs` in `src/pages/Bids.tsx`); use it for every door.
- **Version races**: `npm run claim` lagged `origin/main` twice in one morning. After claiming, compare with main's newest `src/content/releaseNotes/v2.*.ts` and take max + 1; push the docs commit promptly. On a conflict, merge main in, `git checkout --theirs` the two contested files, reclaim and rename.
- **Stacked PRs**: after each merge, `git rebase --onto origin/main <old-base-sha>` (a plain rebase trips over the squash), `git push --force-with-lease`, `gh pr edit N --base main`, `gh pr merge N --auto` (no `--squash`). A branch in the merge queue rejects pushes — park late fixes on a new branch.
- **Edge functions**: `bash scripts/deploy-functions.sh <name>` from a checkout at `main` after the merge; `npm run check:edge-drift` (needs `SUPABASE_ACCESS_TOKEN=$SUPABASE_MGMT_TOKEN`, which the script exports from `.env.local`). Twin kernels live in `_shared/*.ts` and are tested from `src/lib/...` by importing `../../supabase/functions/_shared/...`.
- **Public pages**: `staffAwarePublicHeaders()` + `publicViewDecision` mean a staff session on the same origin never counts as a view; to see the outsider's view in the pane, stash the auth token out of `localStorage`, load, restore. The pane blocks `window.open`, so verify downloads with a `fetch` of the link.
- **Timezone**: `'America/Chicago'` literals fail CI — import `APP_CALENDAR_TZ`. **Theme**: `node scripts/theme-tokenize.mjs --check src`. **Guides**: button tokens are `blue · green · amber · red · purple · gray · outline · outline-blue · outline-amber`; the guide test rejects others.
- **The to-do system**: `to-dos/submittals/README.md` owns front matter; after editing it run `npm run check:todo-drift -- --fix` to re-render `to-dos/README.md` and `punch-list.html`, and commit all three.
