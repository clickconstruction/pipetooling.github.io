# Submittals — the product decision, one row per fixture tag, from the schedule to the GC's approval

Status: **not started** · planned 2026-09-14 · mock-up approved for v1 by the owner ("good enough for version one, build it all in stages, testing along the way") · seven decisions open, defaults named below so work can start · design canvas: https://claude.ai/artifact/2tUmSFQPqNaedEhQbeJVaX (nine artboards; `mockup.html` here is the static copy)

## The ask, in the owner's words

> An estimator takes a page off of plans and sends them to a supply house who gives them quotes back, and then we bid the job and send in our cover letter, and if we win the job then we ask the business we got those quotes from for submittals that we share with the client. This is less than ideal and can put us in tough situations sometimes. … Maybe we should create infrastructure that could make the capture and presentation of submittals easier for all parties, and in a way robots could back fill, and maybe we could even show in a portal for our customers to come see and leave feedback.

The case that prompted it: SpaceX BA-02N (B375 → J1007), September 2026. The first submittal was built from Moore Supply's quote and sent Aug 28; Structura redlined ten substitutions inside the PDF on Sep 1; a revised set built from National Wholesale's quote went out Sep 10 by iCloud Mail Drop with no copy in the office; on Sep 14 the GC asked for a list of everything not on the schedule and why alternates were submitted at all. The table Wendi needed (specified · submitted · reason · lead time) was rebuilt by hand from the plans and the NWS quote: eight alternates, a superseded model, an "equal", one design change (a 1.28 gpf flush valve against a 1.0 gpf spec), one valve missing from the quote, and four accessories the schedule leaves to the contractor.

## The decision

**A submittal is not a document; it is the state of the product decisions.** One row per fixture tag lives from the plan's fixture schedule to the purchase order: specified → quoted → picked → priced → sent (in lieu of) → won → submitted → approved → ordered. The new **Submittals** tab (after Cover Letter, as sketched) is a lens on those rows at one moment; the package PDF is a render of the lens; the customer portal shows the same rows to the GC and takes decisions back.

Draft A (a desk after Cover Letter, a house cut-sheet page, a GC review page) was drawn first and kept; the critique moved the *start* of the story onto the Pricing compare (a **Specified** column, a status chip the moment a pick differs from spec, the reason asked at the pick, lead time on the quote line) and the house's page lost its "why yours instead?" question — the house knows availability and lead time, not our reasons. Draft C put the review inside the portal the GC already opens, added a **We need you** strip (the customer's Needs You), one **conversation per job**, and a **push** when a revision lands. Rejected: a job-side tab as the home (the products were chosen on the bid); a separate submittal link when the customer has a portal (the portal is the home, the token page is the fallback for a GC without one); verified identity for reviewers (typed name and email, like the bid room's signer — right for a submittal, not for a lien waiver).

### Owner decisions still open (defaults in bold so work can start)

1. Home: **the Submittals tab on the bid, read by the job and the portal** — or a job-side tab.
2. Name the alternates on the cover letter: **off by default, one toggle** — or on by default. Disclosure moves the risk: alternates accepted with the price are the GC's to reject at their cost.
3. Cut sheets: **the house through a link first**, Wendi by drop second — both drawn.
4. **Ask every house for lead time on every quote from now on** (a new control on the quote page).
5. Push: **email or text the moment a revision is shared**, with opened stamps — or wait for them to open the portal.
6. Reviewer identity: **a typed name and email on the decisions** — or a scoped link per person.
7. The We need you strip: **every portal, drawn only when something waits** — or GCs only.

**New (v1)**

Tables (all RLS'd on the bid's access — `can_access_bid_for_pricing(bid_id)` for staff reads/writes; token-credentialed edge functions for outsiders; every CREATE TABLE ends with both appliers):

- `bid_quote_lines` + `alternate_reason_kind` (`lead_time · discontinued · in_stock · equal · cost · other`), `alternate_reason_note`, `lead_time_days`, `availability` (`in_stock · lead_time · discontinued · unknown`). (`pick_reason` / `pick_source` stay the robot's *why this house* — different fact.)
- `bid_submittals` — `bid_id`, `job_ledger_id` (nullable; set when the job is opened from the bid), `title`, `rev_number`, `status` (`draft · shared · reviewed · superseded`), `note`, `package_path`, `shared_at`, `created_by`. UNIQUE (bid_id, rev_number).
- `bid_submittal_items` — `submittal_id`, `tag`, `sequence_order`, specified (`manufacturer · model · description`), submitted (`manufacturer · model · label`), `supply_house_id`, `source_quote_line_id`, `status` (`as_specified · superseded · equal · alternate · design_change · missing · accessory`), `reason_kind`, `reason_note`, `lead_time_days`, `sheet_path`, `sheet_pages int[]`, `sheet_source` (`house · estimator · robot`), `carried_from_item_id`, `review_decision` (`approved · revise · rejected`, nullable), `review_note`, `reviewed_by_name`, `reviewed_by_email`, `reviewed_at`.
- `bid_submittal_requests` — the cut-sheet ask per house: `submittal_id`, `supply_house_id`, `contact_id`, `sent_email`, `token`, `status` (`sent · viewed · received · closed`), `resend_email_id`, `viewed_at`, `received_at`, `needed_by`, `last_reminded_at`, `reminder_count`.
- `bid_submittal_shares` — the GC's link: `submittal_id`, `customer_id`, `recipient_name`, `recipient_email`, `token`, `via` (`portal · link`), `sent_at`, `resend_email_id`, `opened_at`, `open_count`, `decided_at`, `closed_at`; `bid_submittal_events` (`share_id`, `event_type` `view · link_sent · decided · reply`, `metadata`, `occurred_at`).

## The plan — six stages, sixteen PRs, a live gate at the end of every stage

Every PR ships alone (branch → PR → auto-merge): `npm run claim` for the version, one release note + one `docs/recent-features/` fragment, the help guide with the surface, a `docs/migrations/` fragment per migration, an `EDGE_FUNCTIONS.md` section per function, `npm run typecheck && npm run lint && npm test && npm run build` and the theme check green before the PR. Migrations start with `SET lock_timeout = '3s';`, number from `origin/main`, push only after merge with `bash scripts/db-push.sh`, then `npm run gen-types:linked` as its own chore PR. Functions deploy before the push when a deployed function would select a column the push adds (`bash scripts/deploy-functions.sh <name>`), and the client goes first when an old client would misread. After every push: `npm run check:migration-drift`; after every deploy: `npm run check:edge-drift`.

**Stage gate:** no stage starts until the previous one has been used on a real bid by Wendi and the owner has seen it. The gate for each stage is written under it.
