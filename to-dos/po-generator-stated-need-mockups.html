Today Notes is already the field. Nothing reads it back.

Every minted code is one row in material_po_generator_entries, and the row has a notes column. Both doors write it. The desktop form calls it "Notes" and says nothing about what goes there; the phone form's placeholder already hints at material. Then the ledger is the only place the note is ever shown again: the invoice form checks that the code exists and stops there, and the text to the tech leaves the note out.

Keep it optional. The placeholder does the asking; the invoice reader does the rewarding.

To decide

  1. A, B or C? A if the goal is "write down what they said". C if the goal is "catch tools landing in job cost". B only if Notes is used for something other than the claim today (one count of non-blank notes settles it).
  2. Does the claim go in the text to the tech? The mock says yes. It costs nothing and makes the claim mutual.
  3. Does the invoice form show the matched entry? The mock says yes, and this is most of the value. Without it, A is a rename.
  4. Label wording. "What they said they need" on the form, "Said they need" in the ledgers. Alternatives: "Asked for", "For what".

If A is picked: one PR, no migration, touches the two forms, the two ledgers, the SMS body, the invoice hint (and its kernel in supplyHouseInvoiceForm.ts, which today carries only the code set), the raise-a-purchase-order and dispatch-mode guides, one release note and one fragment. C follows as its own PR with the migration.
