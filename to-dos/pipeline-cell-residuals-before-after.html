The seam: the row's 40% Aug 7 is the 2026-08-07 back-fill (source = seed), not a typed number. The row's reader (v2.3432) dates the newest event of any source, so the seed beats the June report there. Job Summary's reader (v2.3372) lets a report's percent stand until a hand-typed one is newer — and nobody has ever typed on J931 — so the June 100 stands there. Same job, two readers, two dating rules.

After Three answers — pick a, b or c

Each panel is J931 under that rule, on the three readers that take the report's percent: Job Summary's Show filter and tiles, the Burn card on the Pipeline, and the Ready-to-bill prompt. The row itself does not change under any of them.

A

Whole-job reports only

A report's percent counts only when the report is a whole-job template — Status Report or Job Complete on the job, not a Note and not a visit's paper.

Needs one fact the report table does not carry cleanly today: which template is whole-job. The June 23 paper is a Status Report template filed for a visit — the rule has to read the visit, not the template name, or J931 still counts.
Right in principle, needs a classifier. A visit's status report is the common case in the field; if the rule keys on template name alone it changes nothing on J931.
B

Reports before the last Working entry are out of scope

A report filed before the job last entered Working (job_status_events) belongs to a previous run of the job and does not feed the current percent.

Smallest honest change. One `WHERE reported_at >= last_working_at` in the SQL reader, and `reportPctIsCurrent` follows. Wrong only for a job that never left Working — which is the case the rule leaves alone.
C

Leave it

The row is right. Job Summary reads 100% on J931 until someone types a percent — the seed does not count as typed; typing is the fix, once, per job.
