Stage Plan: build plan

Repo copy: to-dos/stage-plan/. Six stacked PRs that turn the mockups into the product: the line item becomes the stage record, the Bill tab and the generator set it, the Edit tab reads it back with a customer preview, and the GC portal shows a simple sequence in the company's voice. Each PR ships and deploys on its own. Mockups: Stage Plan in the Job Modal and GC Stages Sample Fixture in the artifact gallery.

The four rules everything follows

The line item is the recordOrder and kind live on jobs_ledger_fixtures. Bill sets them, Edit reads them, the portal shows them, draws follow them.
Order rows wait; Any rows don'tNumbered stages start when the one above passes. Diamond stages have their own dates. A plain line item is neither.
The GC sees our crew, never a subNo names, no "offered", one live stage at a time, one ask link on the next stage.
Draws follow stagesAn Order stage bills when it passes; an Any stage bills when it's done; a plain line rides on the final draw. Nothing bills out of order.

Data model

One additive migration, SET lock_timeout = '3s', idempotent, no new table.

ColumnTableTypeMeaning

shared_with_gcjobs_ledger_fixturesboolean default falseThe eye. Replaces job_stage_windows.offered_to_gc as the per-stage share flag; the job-level jobs_ledger.gc_shares_stage_dates stays as the master.
backfillbothtwo UPDATEsEvery existing fixture becomes stage_kind = 'any'; offered_to_gc = true on its window becomes shared_with_gc = true. offered_to_gc stays for one release, read nowhere new.

Nothing else moves: windows stay on job_stage_windows (one per fixture), picks and change requests on step_commitments, progress on the sheet, asks on the window. "Done" for an Any stage is the sheet's mark_work_done; "passed" for an Order stage is the sheet reaching inspection-passed, as the GC card already reads it.

One kernel, three views

src/lib/jobs/stagePlan.ts, pure and unit-tested, built in PR 1 and consumed by every later PR:

  • buildStagePlan({ fixtures, windows, orders, sheets, invoices, todayYmd }) → rows in display order, each with kind, number (Order rows only), badge (done / live / later / any / any-done / none), stateLine (the words on the second line), window, pick, pct, draw (paid / billed / ready / waits / later / none), sharedWithGc.
  • headline(plan) → "Stage 2 of 4 · Top-out · on site now" (Order rows only count toward N of M).
  • billable(plan) → which rows are ready to bill and why; the Bill tab and the Ready to Bill pipeline both read this, so "ready" is one fact.
  • gcView(plan) → the customer's rows: no names, Order rows as the sequence, shared Any rows under "Also on this job", the ask allowed on the next Order row only.

Decisions

  • Default kind for a hand-added line item: Any time. Settled 2026-09-07.
  • A stage is done when the customer pays its bill. Settled 2026-09-07. Passing inspection lets the next Order stage start and makes the draw billable; the green check and "Stage N of M" advancing mark paid.
  • Backfill: every existing line item becomes Any time. Settled 2026-09-07. Users stage a job by flipping rows to Order when they want to.
  • Order and kind are set on Bill; the selector sits on each row's second line; Stages sits above the job details on Edit. Settled.
  • Where a plain line item bills. Proposed: with the final Order draw; alone when the job has no Order rows.
  • Offer to GC on Subs → Work. Proposed: removed with the bundles; the eye on Edit is the only per-stage share control.
  • What makes an Any stage billable. Proposed: the sheet's my work here is done or 100%.

Risks and how each PR contains them

  • Ready to Bill drift. Two definitions of "billable" would fight. PR 2 makes the pipeline read the kernel; the kernel's tests are the contract.
  • Invoiced rows. A fixture already broken off into an invoice locks today; the selector stays disabled on locked rows so a paid draw can't change kind.
  • The covered-hatching logic in the segment bar is subtle (dollar bills not tied to a line). PR 2 keeps that code path and only changes block order and labels.
  • Old clients during PR 5's function deploy. The new payload keeps the old field names for one release with who always null, so a stale service worker never shows a name.
  • Version races. Claim at write time; expect main to move mid-train; renumber by rebase.
