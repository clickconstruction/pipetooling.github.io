One directory, three doors

What "tens of estimators" changes underneath. Access becomes one list of roles read by both the page shell and the database, so a tenth estimator or a new estimator-like role is one edit, not thirteen.

Who

Roles

  • dev, master, assistant, controller → Directory + Accounts payable
  • estimator → Directory only, filtered to supply houses and her trades
  • primary, superintendent → open question; assumed no tab, same as today
  • digital twins → read only, already fenced by the twin write blocks
One predicate, read twice

materialsTabsFor(role) · can_manage_supply_house_directory()

  • The shell asks the kernel which tabs to draw and where to redirect; the twelve literal role checks in Materials.tsx go away.
  • The database asks the SQL predicate on supply_houses and supply_house_contacts writes; the two policies stop listing roles by hand.
  • Both lists are generated from the same source so they cannot drift. Tests pin every role.
What

Data that makes sharing safe

  • supply_houses.vendor_kind replaces is_insurer, seeded by hand from the table below.
  • supply_house_service_types links a house to the trades it serves.
  • supply_house_contacts.created_by already exists; the directory shows it. Request rows already carry created_by and status.
  • The house's own contact_name / phone / email retire; main phone stays.

Decisions still yours

Each one changes a PR. The recommendation is what the mock-up assumes.

Do primaries and superintendents get the tab?

They sit in the same hidden bucket as estimators today and can already read houses.

Assumed: no — one door for the role that asked; add the others as a one-line kernel edit when someone asks.

Can an estimator add or edit a house, or only its reps?

Today's behaviour is both. With many estimators, a house is a company-level fact; a rep is field knowledge.

Assumed: both, but the office-only section is hidden and Kind defaults to supply house so an estimator cannot reclassify a vendor.

A house with no trades set

Sixteen houses will start with no trades until someone tags them.

Assumed: visible to everyone — an untagged house should never vanish from a restricted estimator.

One tab name

Office says "Supply Houses"; the draft says "Supply houses".

Assumed: Supply houses, matching the app's sentence-case tabs elsewhere; the office tab renames too.

Branches

Ferguson and Moore have several branches; the roster has one row each. With estimators in more than one area this becomes a question.

Assumed: out of scope — a branch is an address today; revisit if two rows for one house ever appear.

Who confirms the seed?

Five rows above are marked to confirm.

Assumed: you or Taunya answer in the to-do before the vendor-kind migration is written.
