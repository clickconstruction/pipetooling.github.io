# Dev gates (#188)

## The ask

The owner, 2026-10-26, after a look at the app's user experience with one lens being *fewer dev-only doors*: **list every dev gate and decide each: a gate, a role, or a confirm**, and **in dev settings show links to all the areas of the app that are dev only or controller only at the moment**. The first is this file. The second is Settings → System → **Dev doors**, the card *Only devs and the controller see these*, built from this table as PR 2 (`src/lib/settings/devDoors.ts`, whose test holds every link to a route the app serves and every row to a gate still in the code).

## How to read the table

- **Who today** is what the code does now: *dev* (`role === 'dev'`, `is_dev()`), *dev and controller*, *owner or dev* (`master_technician` or `dev`, `is_master_or_dev()`). No door is the controller's alone: every `=== 'controller'` check sits inside a wider set.
- **Gate** is the one place that decides it, as `file:line` or a helper or RPC name. Where the database guards it too, the policy or function is named, since a client change alone would not open it.
- **Shipped** is the version and the one line that says why it was gated, from `docs/recent-features/` or `docs/ACCESS_CONTROL.md`. *No reason recorded* means the gate shipped without one, which is itself a finding.
- **Recommendation**, one of three:
  - **gate** stays as it is, with the risk it guards named;
  - **role** opens it to a named role, which;
  - **confirm** opens it wider behind a typed confirm with a reason, the shape Collections uses to give up on a job (`StagesUncollectibleConfirmModal`, v2.4792) and the Lien desk's run uses for its batch reason (v2.5533): the act stays reversible or audited, so the gate can be a pause instead of a wall.
- Rows are grouped by the recommendation, the easiest **role** rows first. Within a group, by the page.
- **In ACCESS_CONTROL.md** says whether `docs/ACCESS_CONTROL.md` records the gate today; the *no* rows are listed again at the end, as the doc's own to-do.
