Is this the best we can do?

No. All three carry the same wrong idea: that a site has one current set and that a job points at a set. The site's own data says otherwise. The Lodge 25 set and the Bunker 43 set are both current, for different buildings, on the same day. Option B would mark one of them "replaced". And a job pointing at a set is how ten jobs got stuck on an old one in the first place: every new set means someone remembers to move every job.
  • Sets belong to a part of the site, not the site. An addendum to the Bunker says nothing about the Lodge.
  • A bid pins; a job follows. A bid was priced against one set and must keep saying which. A job builds from whatever is current for its building today and should never need moving.
  • An as-built is not a set that replaces another. It marks up a set. It should say which one, and it should stay with the job that made it.
  • "Newest" by the day a link was pasted is not a date. The date printed on the drawings is the date. A set also has the day it reached us, and those differ.

Option D · parts of the site, each with a current set

The register from B, with one change in its spine: a set belongs to a part (the Lodge, the Bunker, the ATV building, or the whole site), each part has one current set, bids pin a set, jobs name a part and follow. Our as-builts hang on the job and mark up the set it built from.

What the data needs

  • Parts of a development: name only. "Whole site" exists on every development without anyone making it.
  • Sets on a part: kind, from, dated, came, memo, folder, replaces, who made it current and when. One current per part.
  • A job names its part. A bid keeps its own set rows and gains "priced on".
  • An as-built is a set of kind as-built, on the job, marking up a set.
  • The robot's link on the bid stays exactly as it is.
Two tables and one column, then the screens above.

Option D on a standalone job

A job outside any development is a site of one. It owns its own part, so the same register, the same screens and the same crew press apply with nothing new to learn. When the job later joins a development, its sets come along as a part named after it.

What the data needs, standalone included

  • A part belongs to a development or to one job, never both. A job in a development names a part; a job outside one owns its part, made the day the job is made.
  • The sets table is the same table whichever owns the part. The job window's Plans section and the crew's phone are one component.
  • A new job from a bid starts its part with the set the bid was priced on as "building from".
  • The job's old plans link stays as a column and is written by the app to mirror the current set's folder, so nothing that reads it today has to change.
My view: D is the one worth building. A fixes the words and not the problem. B is D without parts, and the real site already breaks it. C is the right bones in the wrong house. Whatever is chosen, the first PR is the same small fix: stop counting a job's empty Plans folder as a set.
