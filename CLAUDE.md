# CLAUDE.md

Guidance for Claude Code (and humans) working in this repo. Hard rules only, one clause of reason each; the incidents behind them live in `docs/recent-features/` and the specialist docs. Entry order: this file → `AGENTS.md` (login, constraints) → `docs/AI_CONTEXT.md` (overview) → `docs/README.md` (index).

## DB migrations — the one rule that prevents drift

**Apply migrations ONLY with `supabase db push`, and only after the migration file is on `main` (or in the PR merging right now).** Never apply DDL via the Supabase MCP `apply_migration`, `execute_sql`, or the dashboard SQL editor — each leaves the migration ledger out of step with the repo (a server-minted version, no ledger row, or an orphan row from a dead branch), and `db push` then refuses. If an emergency ever forces MCP `apply_migration`, rename the new ledger row's `version`/`name` to match the repo filename in the same session.

- **Every new migration starts with `SET lock_timeout = '3s';`** (CI-enforced). There is no staging: DDL runs against prod while crews use the app, and an `ALTER TABLE` waiting on a lock queues every query behind it. With the timeout the push fails fast and you retry in a quieter moment.
- **Number new migrations from `origin/main`'s latest file** (`git ls-tree origin/main supabase/migrations/ | tail`), never from your branch, and register the file with `npm run claim -- --migration <file>`.
- **Migrations that CREATE TABLE end with BOTH `SELECT public.apply_read_only_write_blocks();` and `SELECT public.apply_read_only_stmt_blocks();`** — the restrictive RLS policies and the statement trigger that block writes from users flagged `users.read_only` (training mode). Miss either and the new table is writable by read-only users.
- Write migrations idempotent (`IF NOT EXISTS` / `CREATE OR REPLACE`) and additive when possible — they hit prod.
- App looks "database down"? Run `/db-freeze` (`docs/DB_FREEZE_RUNBOOK.md`) BEFORE restarting the instance — the freezes are lock pileups and a restart destroys the evidence.
- Check alignment any time with `npm run check:migration-drift` (CI runs it on main pushes touching migrations and daily).

## Deploy model (four separate tracks)

CI (`deploy.yml`) typechecks, lints, tests and deploys the **client** to GitHub Pages. The other three are manual — the first two against the linked prod project `yewfzhbofbbyvkvtaatw` ("plumbing-stage-manager"):

1. **DB migrations** — `supabase db push` (rule above). When a migration changes behavior the old client would misread, deploy the client first.
2. **Edge functions** — `supabase functions deploy <name>` (or MCP `deploy_edge_function`). Editing `supabase/functions/*` does nothing until deployed; `npm run check:edge-drift` says what is behind. `create-user` keeps `verify_jwt = false` in `config.toml` on every redeploy.
3. **Cloudflare Workers** — `scripts/cloudflare/`. `mcp-router` deploys from the repo (`npx -y wrangler@3 deploy --config scripts/cloudflare/mcp-router.wrangler.toml`); the other Workers are edited in the Cloudflare dashboard and mirrored there, so a change to either copy is made to both.

## Working conventions

- **Ship small**: one change → PR → auto-merge (`gh pr merge --auto --squash`); re-arm auto-merge after any push to a queued PR. Never `git add -A` — parallel sessions leave WIP in the tree; stage specific files.
- **Claim the version, don't derive it**: `npm run claim` reserves the next `v2.NNNN` for your branch (`docs/SESSIONS.md`); computing "newest + 1" races other sessions. When a race forces a renumber, rebase — never rebuild the branch with `reset --hard` + `git apply`, which discards the merge base and silently overwrites the other PR's entry.
- **Parallel sessions coordinate through the advisory ledger** (`docs/SESSIONS.md`): drop a session card in the main checkout's `.claude/sessions/active/` when starting a work stream and check `npm run sessions` before reworking a hot surface. The ledger is gitignored and shared across worktrees.
- **Kernels first**: extract logic into pure `.ts` kernels with unit tests (`npm test`); component render smokes (`*.render.test.tsx`, `renderWithProviders` from `src/test/renderSmokeMocks.tsx`) cover wiring.
- **Help guides ship with features**: a PR that adds or changes a user-facing flow adds or updates the guide in `src/content/help/` (frontmatter title/category/roles/keywords; slug = filename; headings start at `##`; the title is a lowercase completion of "How do I…", e.g. `title: bill a customer and get paid`). Illustrate with the mock-UI tokens in `src/lib/helpGuideIllustrations.ts` — `{{button:<variant>|Label}}`, `{{chip:<variant>|Label}}`, `{{icon:help|gear}}`, `:::example <caption>` … `:::` panels, `{{gif:<file>|caption}}` recordings from `public/help/`. `src/lib/helpGuideContent.test.ts` validates them in CI.
- **Release notes and developer docs ship with features**: every feature/fix PR adds **one new** `src/content/releaseNotes/v2.NNNN.ts` (a `ReleaseNote`: title + 1–4 user-readable bullets, no file paths; renders at Settings → Release notes) **and** the matching `docs/recent-features/v2.NNNN.md` fragment (first line `# v2.NNNN — <title> (<date>)`). `src/lib/releaseNotes.test.ts` fails CI when either is missing or a version is documented twice; its `LEGACY_*` arrays stay empty — restore the lost entry, never widen the list. Never edit the frozen aggregators (`src/content/releaseNotes.ts`, `releaseNotesArchive.ts`, `docs/RECENT_FEATURES.md`). Every migration gets `docs/migrations/<version>_<slug>.md`; every new or changed edge function gets its `docs/EDGE_FUNCTIONS.md` section (+ TOC line); a PR that renames a surface, adds a tab/section/modal or changes role permissions updates `PROJECT_DOCUMENTATION.md` / `GLOSSARY.md` / `ACCESS_CONTROL.md`. A PR that adds, renames or removes a page updates `docs/twins/APP_DIRECTORY.md` — `src/lib/twins/appDirectoryCheck.test.ts` fails CI when a brief names a path no route serves or a help slug with no guide.
- **Amend, don't add**: when a rule, a count or a fact changes, edit the sentence that already holds it — in this file, `AGENTS.md`, `docs/AI_CONTEXT.md`, `docs/README.md` and every specialist doc. Add a bullet, section or index row only when the fact has no home yet, and then give it exactly one; every other mention is a link. A rule carries at most one clause of reason; the incident that taught it stays in the fragment that fixed it. Entry docs are routers — no per-feature detail, version numbers or component inventories; frontmatter carries one `last_updated` and section names only.
- **Mechanical sweeps merge alone**: a script-driven change across many files (confirm()/alert() conversions, theme tokenization, bulk renames) is cut from fresh `main` and merged before the next feature PR on those surfaces; on a rebase conflict re-run the script on the new main instead of hand-resolving markers — the script is the source of truth.
- **Generated files are regenerated, never conflict-resolved**: on a rebase conflict in `src/types/database.ts` (or any generator output), take main's version and re-run the generator.
- **Theme tokens, not raw hexes**: light/dark themes use the CSS variables in `src/index.css` (`var(--text-muted)`, `var(--surface)`, `var(--border)`, …); CI fails on raw neutral hexes (`node scripts/theme-tokenize.mjs --check src`; without `--check` it auto-fixes). Saturated action/status colors stay literal; customer-facing and print surfaces stay light via `data-theme="light"` wrappers.
- Migration history is squash-baselined at `20250101000000_baseline.sql`; pre-baseline files live in `supabase/archive/migrations-pre-baseline/` (the "2027"-dated names there are typos — see the note atop `docs/MIGRATIONS.md`).
