`Checklist.tsx` is the task-checklist page, tab-switched on a single `activeTab` state (`type ChecklistTab = 'today' | 'history' | 'review' | 'manage'`, line 69). **The Roadmap left this page in v2.2916** (journey-map Tier-2 #41): [`src/pages/Roadmap.tsx`](../src/pages/Roadmap.tsx) (126 lines, `/roadmap`) mounts `ChecklistTechTreeTab` under [`ChecklistGoalsSection`](../src/components/checklist/ChecklistGoalsSection.tsx) (691 — the GOALS strip, stage ledger, 🔒 chain sheet, ⇅ reorder and 🔔 stage reminder that used to sit on Review). `?tab=roadmap` redirects to `/roadmap` for roles with the door (`canOpenRoadmap`) and to the role's default tab otherwise. The tech-tree dossier below applies to the component wherever it is mounted.

The page is **still internally seamed**: each tab is a separate in-file function component (`ChecklistTodayTab`, `ChecklistHistoryTab`, `ChecklistOutstandingTab` = the Review tab, `ChecklistManageTab`) with a small explicit prop surface. None has been moved to its own file yet, but since v2.2156 most of their leaf UI left the page — `ChecklistInstanceCard`, `ChecklistOutstandingSection`, `ChecklistComingUpSection`, `ChecklistHistoryLedger`, `ChecklistItemActivity`, `ChecklistCostButton`, `ChecklistManageTimeline`, `ChecklistReviewInboxSection`, `RoadmapTaskContextModal`, `VehicleTaskContextModal` — and much of the Stage-A inventory now lives in tested `src/lib/checklist*.ts` kernels (see the Stage-A table).

Consequence: Stage-B moves are still near-mechanical **file moves of already-isolated components** — after one seam PR, because a module-scope chip helper, two row types (`RoadmapTaskEmbed`, `ChecklistInstance`) and `UserRole` are shared across tabs (see substrate point 5). The real work is the remaining Stage A plus the completion-engine dedupe.

This map is coupling/refactor-oriented; for feature behavior see `PROJECT_DOCUMENTATION.md` and `GLOSSARY.md` (checklists, tech tree / roadmap).

## The shared substrate (or lack of one)

**There is still no shared data engine and no shared record pointer on this page.**

1. **Every tab self-loads** (`loadToday`/`loadUpcoming`/`loadCardEvents`, `loadHistory`, `loadOutstanding`, `loadItems`/`loadUsers`). No caches are shared; switching tabs remounts and refetches.
2. The only cross-tab **UI pointer** is `editItemId` → the shared `ChecklistItemEditModal` (Review + Manage). It stays in the parent.
3. Cross-surface **freshness is event-based**: `checklist-item-saved` (dispatched by [`ChecklistAddModal`](../src/components/ChecklistAddModal.tsx) — a **global** modal mounted in [`Layout.tsx`](../src/components/Layout.tsx), opened via [`ChecklistAddModalContext`](../src/contexts/ChecklistAddModalContext.tsx) — and by `ChecklistItemEditModal`) is heard by Review (`loadOutstandingRef`, 2080–2086), Manage (`loadItemsRef`, 3185–3191) and `ChecklistReviewInboxSection`. **New since the last map:** `checklist-instance-completed` (v2.2271) is dispatched by [`completeChecklistInstance`](../src/lib/checklistCompleteInstance.ts), Review's `markComplete` (2163) and `undoComplete` (2251, `detail: null`), and heard only by `ChecklistReviewInboxSection` (the sign-off queue) — Today's `toggleComplete` does **not** dispatch it. Both contracts must survive extraction unchanged.
4. **The completion engine's notifications exist four times; its next occurrence once** (since v2.3836 every path materializes the next `days_after_completion` occurrence through the kernel's `createNextChecklistRepeat`): Today's inline `toggleComplete` → `sendCompletionNotifications` 669–700 + `maybeCreateNextInstance` (now a two-line call); Review's inline `markComplete` side effects 2166–2218; the tested kernel `lib/checklistCompleteInstance.ts` (v2.2039 — used by Review's row activity panel `completePanelInstance` 2127 and Manage's activity panel 3519); and [`DashboardMyInboxCard`](../src/components/dashboard/DashboardMyInboxCard.tsx). **The copies disagree** — see Risk flags.
5. **Module-scope seam (new):** `roadmapGoalChip` 131–181 is called by Today (835, 918), the Review row (1770) and Manage (3387); type `RoadmapTaskEmbed` 96–103 is embedded in `ChecklistInstance` 71–94 (Today + History), `OutstandingInstance` 1517–1522 and `ChecklistItem` 3131–3152; `UserRole` 59–67 is used by the parent and Manage; `toLocalDateString` 218–223 by Today, History and Review. These must move to a shared module before any tab moves. `dueCardChip` 116–129 and `vehicleTaskChip` 188–214 are Today-only; `outstandingAgeChip` 1525–1560 is Review-only. (The JSDoc at 105–114 describes `roadmapGoalChip` but sits above `dueCardChip`.)

**What this means for extraction:** no seam *hook* is needed before moving tabs — each tab's props are its full contract — but one seam *file* is (point 5). The absence of shared caches is why this page is low-risk. The `?tab` router + Farm-Mode bounce + `editItemId` + the edit modal never move into a child.

### Risk flags

- **Days-after-completion next date (fixed v2.3836).** Today's `maybeCreateNextInstance`, Review's `markComplete` and `DashboardMyInboxCard` each computed the next date as `new Date(ymd)` (UTC midnight) + local `setDate` + local format — in America/Chicago **scheduled + N − 1** (`2026-09-25` + 3 → `2026-09-27`; for N = 1 the next date was the day just completed, so Today's exists-check returned and Review/Inbox hit the UNIQUE pair — the repeat stopped). All three now call the kernel's `createNextChecklistRepeat` (`checklistNextRepeatYmd` = `ymdAddDays`, tested), which also gives Review the exists-check. **Open owner call:** every path counts from `scheduled_date`, while the UI and guide say *N days after it's completed* — a task done late gets its next date early.
- **No render smoke** exists for either covered file (`Checklist.tsx`, `ChecklistTechTreeTab.tsx`), nor tests for `useChecklistTechTreeData`, `useTechTreeTaskMutations` or `domFullscreen`.
- Money math on this surface is the dev/controller **cost lens** only: `sumEstimateDollars` / `estimateAccuracy` / `estimateAccuracyByPerson` / `formatWholeDollars` / `formatMultiplier` are kernel-tested (`checklistCostEstimate.test.ts`, 13 cases); only the estimate-key pick (`roadmap_group_task_id ?? checklist_item_id`) is inline, twice — the row's `ChecklistCostButton` 1805 and the person-card total 2734–2740.

## Preserve-quirks list (odd but load-bearing — do not "fix" during the move)

1. **Role-dependent default tab** (`review` for staff outside Farm Mode, `today` otherwise) written with `replace: true` only when `?tab` is absent and `role` has resolved; Farm Mode bounces office tabs to `today`; `?tab=roadmap` redirects to `/roadmap` or rewrites to the role's fallback tab.
2. **Today = two lists, not one merge**: today's rows sorted by per-user `display_order`; overdue work goes to the separate Outstanding section (≤300 rows, qualified client-side — one-off / show-until-completed / last transition = reopened).
3. **Today's toggle no longer writes notes** — comments live in `checklist_instance_events` and the completion trigger logs the transition; the in-flight Set blocks double taps; revert restores the whole previous row.
4. **Forward deletes the original instance** and mints a single-shot `checklist_items` row (copying notify/reminder fields). Today's copy starts with `fwdAssigneeId=''` (placeholder-less select); Review's pre-fills the row's user.
5. **Window events are the only cross-surface refresh**: `checklist-item-saved` (Add + Edit modals → Review, Manage, sign-off queue) and `checklist-instance-completed` (kernel, `markComplete`, `undoComplete` → sign-off queue). Today's toggle does not dispatch the latter. Extracted tabs must keep both.
6. **History cell cycle** (dev edit mode, behind a confirm): incomplete → delete with a 2 s optimistic `deletedCells` window; completed → delete + reinsert (new row id); only the **last 60** repeating dates render; phones get the ledger and a 1-month default.
7. **`missed` filter double-gate**: server `scheduled_date < yesterday` AND client `reminder_scope !== 'today_and_overdue'`; rows collapse to one per task (`missedGroups`), and ✓ / 🗑 act on the whole group. The "Missed this week" tile counts something else — every incomplete instance (company-wide as RLS allows, assigned or not) from Sunday to yesterday, unfiltered and uncollapsed.
8. **`markComplete` verifies `updatedRows.length`** after UPDATE (`.select('id')`) and errors on 0 rows; its side effects wait out the 5 s undo window and flush on unmount or on the next ✓ — never lost, never sent for an undone completion.
9. **Reorder persists sequentially** (`display_order = i+1`, one UPDATE per row via `withSupabaseRetry`), keyed on (`checklist_item_id`, `user_id`) — order is per person.
10. **Manage completion is derived from ALL instances** of the loaded items in one unbounded `.in()` query; a one-off is "Complete" only when `total > 0 && !hasIncomplete`; open one-offs sort oldest-open-first (created date fallback) and opening an amber/red one records `aging_item_opened`.
11. **Tech tree loads all edges unscoped** then filters client-side; `blockingLoadOverlayRef` keeps refetches from unmounting the canvas.
12. **Layout cache keyed on `structuralKey`** (group ids + edges + collapsed set): task add/toggle never re-runs dagre. **Steady camera (v2.2291):** a pure add/remove of stages patches the cached layout in place (survivors keep positions, a new stage lands at the pointer or viewport centre, `patchedAltKeyRef` accepts the follow-up auto-collapse key as a hit) and never refits; `fitView` runs only on `organizeVersion` bumps (first population per roadmap, Organize, Collapse all, Show all) plus review mode's own scoped fit. Edges touching a hand-moved node fall back to smoothstep until Organize.
13. **Collapse-all bootstrap** runs once per (auth, roadmap); reconcile auto-collapses new stages (2.5 s glow via `recentlyAddedGroupId`) and prunes removed ids; a stage created from a connection drag or pane right-click keeps its drop position via `newGroupManualPositionFromConnectRef`.
14. **Fullscreen**: DOM Fullscreen API with a CSS `position: fixed` fallback (iPhone Safari), `useBodyScrollLock` + Esc in CSS mode, double-rAF `resize` so React Flow re-measures, and **ten portal consumers** (nine modals + the canvas menu) portal into the canvas shell while fullscreen (`roadmapModalPortalHost`).
15. **Task permissions** (`canActOnTask`, now in `useTechTreeTaskMutations`): `canEditStructure` always; otherwise the stage must be unlocked, the task not waiting behind an earlier sibling in a sequential stage, and the user an assignee — **unassigned tasks are staff-only**.
