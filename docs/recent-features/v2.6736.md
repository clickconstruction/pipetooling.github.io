# v2.6736 — The full typecheck runs one at a time across a machine's worktrees (2026-11-08)

Infra. On 2026-11-08 the Claude app had to be restarted for memory: two sessions' full typechecks (`node --max-old-space-size=10240 node_modules/typescript/bin/tsc -p tsconfig.json`) held about 9.5 GB each at the same moment, and the app itself another 3.5 GB across its windows, on a 48 GB Mac running many worktrees at once. Nothing coordinated them; each session was told by hand to run one at a time. Now `npm run typecheck` queues.

## What changed

- **`scripts/typecheck-queued.mjs`** (new) is what `npm run typecheck` runs. It takes a machine-wide lock, runs `tsc -p tsconfig.json` under the same 10 GB heap as before with any extra arguments passed through, exits with tsc's code, and releases the lock on the way out. `TYPECHECK_NO_LOCK=1` skips the lock; `TYPECHECK_LOCK_DIR` moves it.
- **`scripts/lib/typecheckLock.mjs`** (new, plain JS, no dependencies) is the lock: an atomic `mkdir` of `typecheck.lock/` under the MAIN checkout's gitignored `.claude/sessions/locks/` (every worktree resolves there through `git rev-parse --git-common-dir`, as the version claims' mirror does; outside a repo, the OS temp folder), with a `holder.json` naming the holder's pid, folder and start time. A waiter polls every half second and prints, at once and then every 30 seconds, who holds the lock, in which worktree, how long it has run and how long the wait has lasted. A lock whose pid is dead, or that never got its `holder.json` and is older than ten seconds, is taken over: the takeover renames the stale directory away first (atomic, one winner of two waiters) and removes the copy. Release removes the directory only while `holder.json` still names the releasing pid.
- **`src/lib/typecheckLock.test.ts`** (new, 17 tests): acquire, the live holder's refusal, release only by the holder, the dead-pid takeover, the unwritten-directory grace, the one-winner rename, the wait with its three lines over 75 simulated seconds, where the lock lives from the main checkout, a worktree, outside a repo and under the env var, and the wiring: the `typecheck` script, the heap, the env check, and that `ci.yml` and `warm-caches.yml` set `TYPECHECK_NO_LOCK` on their Typecheck steps.
- **CI unchanged in effect**: both workflows' Typecheck steps set `TYPECHECK_NO_LOCK: '1'`, since a runner is its own machine. `deploy.yml`'s `npm run build` runs `tsc -b` directly and is untouched. `check:workflow-parity` still passes.
- **Docs**: `docs/SESSIONS.md` gains the section *One typecheck at a time on a machine* (the fact's one home); `AGENTS.md` → Critical constraints §9's "run locally first" sentence says the typecheck queues and points there.

## Proof (two worktrees, 2026-11-08)

`npm run typecheck` in this worktree at 15:24:24 took the lock (`holder.json` named its pid and folder; its tsc child reached 6 GB within a minute). The wrapper started from the `deploy-main` worktree at 15:24:51 printed

```
typecheck: waiting for the lock held by pid 29027 in cranky-spence-2c54db, running 27 s; 0 s so far
typecheck: waiting for the lock held by pid 29027 in cranky-spence-2c54db, running 57 s; 30 s so far
```

and six more lines like them, one every 30 seconds, holding at 47 MB with no tsc of its own. The first finished clean at 15:29:22 (exit 0, four minutes 58 seconds); within a second the waiter took the lock (`holder.json` named its pid and the `deploy-main` folder) and its tsc was at 2.3 GB. A SIGINT to the waiter then stopped its tsc, it exited 1, and the lock directory was gone.

## What this does not cover

- `npm run build` and `npm run analyze` run `tsc -b` at the same 10 GB heap outside the lock. They run far less often locally than the typecheck.
- **`npm test` carries the same kind of risk, unchanged here.** `vite.config.ts` sets no pool, workers or heap, so vitest 2.1.9 uses its defaults: the `forks` pool with one fewer worker than the machine's cores (13 child processes on this 14-core Mac), each a Node process at Node 20's default heap limit (4,144 MB here, read from `v8.getHeapStatistics()`) and no cap of its own. One suite's forks are bounded by what the tests allocate, not by a setting; two sessions' suites at once are 26 forks. A follow-up could run the suite through the same lock, or cap `maxWorkers` / set `poolOptions.forks.execArgv` with a heap size, once a run's real peak has been measured.
