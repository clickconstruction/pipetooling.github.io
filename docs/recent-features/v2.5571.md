# v2.5571 — Schedule and Jobs: every job stays on the list as the ledger grows (2026-10-15)

The two un-ranged `jobs_ledger` reads nearest PostgREST's `max_rows` cap, paged with `fetchAllRows` before either crossed it. PostgREST answers a read that sets no `limit` with its first 1,000 rows and a 200 (`docs/TROUBLESHOOTING.md` § `[row-cap]`); on 2026-10-15 the Schedule Dispatch hub loaded 871 non-billing-only jobs and the Stages Paid in Full scope 767. Past the cap the lowest-numbered jobs would have left the hub's Jobs tab, the Add job to schedule picker and the block titles with nothing said, and the Paid in Full board would have stopped short. No migration; no edge function; nothing changes on screen today.

- **`src/lib/scheduleDispatchHub.ts`** — `fetchJobsLedgerForScheduleDispatchHub` wraps its read in `fetchAllRows`: a fresh query per page, `.range(from, to)`, and `id` as the second `.order()` after `hcp_number desc` so the pages never shuffle between requests. The `{ data, error }` shape is unchanged; the `billing_only = false` filter (v2.4958) and the select are verbatim.
- **`src/lib/fetchJobsLedgerWithDetailsForStages.ts`** — `fetchJobsLedgerStagesPrimary` pages the same way, for every scope and the `ids` path, and so does the `ready_to_bill` companion (working jobs carrying an RTB invoice). This is the read behind the Jobs board (`JobsListCacheContext`, `non_paid` then `paid`), Job Summary (`all`, so it rides on the fix too), Dispatch mode (`non_paid`) and the Accounts Receivable page. The rough server-side pre-sort is still by `hcp_number`; the board re-sorts by the effective number as before.
- **Tests** — new `src/lib/scheduleDispatchHub.fetch.test.ts` against `makeFakeRowCapSupabase` (`src/test/fakeRowCapSupabase.ts`): a second page when the first is full, one page when it comes back short, the filter, select and the two-column order on every page, and a failed page reported as `{ data: [], error }`. `fetchJobsLedgerWithDetailsForStages.test.ts` pins the `id` tie-break and the range on every scope, the ids path and the companion, and adds the two-page case over 1,400 paid jobs.

The console tripwire (`src/lib/supabaseRowCapTripwire.ts`, v2.2756) would have reported the first time either read came back as exactly 1,000 rows; this PR takes both off its list before it has to. The next un-ranged `jobs_ledger` reads are small (the hub's bids read is on `bids`, not the ledger) and none is near the cap.
