## The rule: derive the flow from the customers row (design B)

The owner's pick on 2026-11-02, over re-kinding the contacts (design A: a ninth contact kind, a data migration on the eight rows, a trigger to keep it in step with `customer_type`, and every reader of the contact kind learning the new value). The code already split the two ideas — `ContactKind` (`contacts/names.ts`, nine kinds, no `residential`) and `FlowKind` (`flows/facts.ts`), with `flowContactKind` folding `residential` back to `customer` — and v2.6385's `flow_step_check` already reads the flow this way in SQL. Only the readers were typing the contact row's kind as a flow's.

- **`flow_rows_for`'s card carries `customer_type`** (the migration): the `a_customer` CTE joins customers already; the card gains the one key for a customer's or an architect's contact. `flow_rows` and `flow_rows_kind` call it, so neither changes.
- **One kernel decides**: `contactFlowKindOf(kind, customerType)` in `facts.ts` (the hunk v2.6385 added, written here identically so the two PRs merge cleanly): `customer` + `residential` → the residential flow; anyone else their kind's. `flowContactKind` takes a contact's kind too and hands it back.
- **The contact row's kind is honest**: `load.ts`'s `ContactRow.kind` is a `ContactKind` (it is `contacts.kind`), `FlowCard.customer_type?` is the new key, and `nudgeRunInputs.ts`'s `RunContactRow.kind` is a `ContactKind`. The tests that built a `residential` contact row build a `customer` one.
- **The step card** (`flowPersonIo.ts`): the contact is read as its own kind and the flow told from the card after `flow_rows` answers; `FlowContact.kind` is the flow's. The Pipeline read moved out to **`residentialRowsIo.ts`**, `readPipelineRows({ customerIds, contactIds })`, one read for one homeowner or every homeowner at once, so Follow up shares it.
- **Follow up's Nudges from the flow** (`flowNudgesIo.ts`): `NUDGE_KINDS` gains `residential`; the three reads stay (`flow_rows_kind` takes contacts' kinds), each entry's flow is told from its card, the homeowners' Pipeline rows are read once and cut to each by `residentialRowsOf`, and a failed Pipeline read leaves their lanes empty rather than hiding anyone. The residential flow's def joins `flows`, so the row's step pill names *Paid* rather than `paid`.
- **The boards** (`boardRead.ts`): `readBoard` keeps a contact when its told flow kind is the board's, so the Customer board (Settings → Flows → Customer, *Before you save · who moves*) leaves homeowners off; the card parser reads `customer_type`.
- **The morning run** (`nudgeRunInputs.ts` + `messages-nudge-dispatch`): `RUN_KINDS` is every flow kind that is a contact's kind (so `customer` joins and `residential` leaves); once `flow_rows_for` has answered, the kernel's `runContactsOf(contacts, flowRows)` splits the GC customers off (the flow the run cannot read the page for yet) and counts them as `customersHeld`, in place of the function's own count query, and `nudgeRunReads` tells everyone left their flow from the card; the homeowners whose Pipeline rows and bills the function reads are the ones the card says. A homeowner whose card does not yet carry `customer_type` (the client deployed before the push) is held the same way, so nothing new goes before the push.
- **SQL bed** `residential_flow` § 6: a contact is never kind `residential` (`contacts_kind_known`) and the card reads `residential` / `commercial` / nothing. The SQL twin of the rule, `flow_step_check`'s residential branch, is v2.6385's and `messages_flows` holds its assertions (PR #6855, in flight beside this one).
