# v2.7886 — Dev seat: a trip's number in the read (2026-11-18)

## Why

The last part the trip record's card (#379) owed the dev seat. Every trip has a short number on its site since v2.7703, *Trip 5*, and the app shows it since v2.7707. A bill or a text cites it. The seat's read gave a trip's id and its days and never its number, so an agent asked about *Trip 5* had to guess which row that was.

## What changed

Server 0.106.0. No new verb, no RPC, no migration.

- **`read_trips`** gives each trip its `trip_number`, read off the trip's own row in the same GET.
- **`plan_trip`** names the number of a trip already kept (`trip.trip_number`, from `trip_save`'s dry run) and says a change keeps it. For a new trip it says the database hands out the number when the trip is kept. A note about days another kept trip already claims names that trip by its number, with its id beside it.
- **`apply_trip`**'s reply ends *It is Trip 7.*, from the number `trip_save` answers.

## Decisions

- **The seat cannot ask for a number.** `trips_take_number` hands it out. The seat reads it and says it.
- **A row with no number reads `null`.** The seat never makes one up from the order of the rows: the numbers run in the order trips were made, and the read is in the order they went out.

## Tests

`src/lib/devMcp/devMcpTrips.test.ts`: the select carries the number, the read gives it and gives `null` for a row without one, the plan names a kept trip's number and an overlapping trip's, the applied reply says which trip it is. `src/lib/devMcp/devMcpTrips.run.test.ts` runs the three verbs through the function's own handler with a stand-in `trip_save` that hands out numbers as the migration does.
