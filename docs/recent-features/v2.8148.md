# v2.8148 — Document builder: a tab left open can no longer save or publish over a newer draft (2026-11-20)

Punch list #404, one of the faults the review of 2026-11-20 found and did not fix. The client half. The database half is v2.8143, migration `20261120160000_document_builder_draft_no.sql`, which was pushed and proved on prod before this PR was armed. No function.

## What was wrong

A builder's draft and a job's sheet's draft are saved a moment after the typing rests. A save named nothing it was loaded at:

- `saveBuilderDraft` updated `WHERE key = …` and `saveSheetDraft` `WHERE id = …`. A tab left open wrote its old draft over whatever was there.
- The reply to that save carried the row back, with the row's newer revision. The tab then held the newer revision beside its old words, so its publish, which names the revision, passed the one guard there was. The old words went out as the next revision.
- A publish from a tab that had typed nothing wrote `draft` and `published` over a draft a teammate had saved and not published, since a saved draft does not move the revision.

## The fix

A save and a publish name the draft's number the page read, `draft_no`, which the database moves with every change to a draft or a revision.

- `sheetsIo.ts`: `saveBuilderDraft`, `publishBuilder`, `saveSheetDraft` and `publishSheet` take the number and write `WHERE … AND draft_no = n`. A row that moved on matches nothing.
- `documentBuildersIo.ts`: `guardedWrite` does the write and, when it landed on no row, reads the row again to say which it was. Gone: *This is no longer there.* The same write landing twice, as when its first reply was lost: taken as landed. Changed by someone else: refused, with the row as it now reads in `Landed.movedOn`.
- `startSheet`: one job has one sheet, so a second start is refused by the database. The sheet someone else started is read and handled the same way.
- `movedOn.ts` and `MovedOnPanel.tsx`: the panel. It names the thing, says whether a newer draft was saved or a revision was published, and offers two presses. **Load the newer one** takes the row as it now reads. **Save mine over it** saves what was typed, naming the number the newer draft is on. A revision someone published stays published either way.
- While the choice is open that one thing's saves wait, what was typed stays on the page, the bar reads *Draft not saved*, and its publish press is dead. Another job on the same page saves as before.
- The number a write leaves is taken from its reply at once, ahead of the next draw, so a second save that follows the first names the right one.

A read mark does not move the number, so marking a revision as read in one tab does not refuse a save from another.

## What it does not do

A page on the client from before this PR names no number and saves as it did, until it is reloaded. The database refuses nothing that names no number, by design: the migration went out first, under the old client.
