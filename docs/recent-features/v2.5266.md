# v2.5266 — Messages: the phone webhook checks that each call and text came from Quo, behind the scenes (2026-10-12)

The Messages build's cut 5, the webhook's own rules (`to-dos/gc-mode/messages/BUILD_PLAN.md` → Cut 5, `quo-webhook`, on branch `spike/gc-mode`), by helper 3, directed by the GC Review lead. One pure kernel with its test over made-up ids and a made-up key. No screen, no table, no edge function, nothing to deploy. Its partner, `src/lib/quo/events.ts` (v2.5261), reads the event itself.

- **`src/lib/quo/webhook.ts`**:
  - `verifySignature(headers, rawBody, secret, now)` checks a delivery the way Quo signs it, the Standard Webhooks scheme. It reads `webhook-id`, `webhook-timestamp` in Unix seconds and `webhook-signature` (space-separated `v1,<base64>` entries, any one matching, so a key can be turned over). The HMAC is SHA-256 over `{id}.{timestamp}.{raw body}`, keyed by the base64 after `whsec_`, compared in constant time.
  - It refuses a timestamp more than five minutes away either way. The signature is checked first, so a replayed real delivery reads as too old.
  - The HMAC runs on WebCrypto, which the browser, Node and Deno all carry. A local run reproduced the Standard Webhooks spec's published example signature, kept out of the repo because a `whsec_` literal trips secret scanning.
  - `seenBefore(id, seen, now)` keeps delivery ids 28 hours (Quo retries for about 27 and a half), says which ids to drop, and gives the row to record when the id is new.
  - `webhookAnswer(outcome)` gives 200 on handled, 200 on nothing to do with the reason logged, and 200 on a repeat. It gives 401 on a refused signature, saying no more than unauthorized. It gives 500 on a failure with `release` set, so the wrapper deletes its claim and Quo's retry is taken as new.
- **The order for the wave 2 edge function**: verify the signature; claim the delivery (insert on conflict do nothing, the insert being the lock against two copies at once); read and plan (`events.ts`); write; send any answer text; answer. Claiming before the answer text is sent keeps a HELP answer from going twice.
- **`message.delivered`, settled from Quo's docs**: Quo's support page names it "Text message sent from workspace and successfully delivered". The 2026-03-30 payload reference gives its resource as `id`, `direction` (outgoing), `text`, `media`, `status`, `createdAt`, with the message context's `userId`, `senderIdentifier` and `recipientIdentifiers`. Neither page limits it to texts sent through the API, so a text sent from Quo's own phone app comes back as this event.
  - The cut 5 edge function subscribes to it, and to `message.failed` and `message.undelivered` for a text that did not arrive.
  - `events.ts` reads it as an out text keyed by `quo_id`. A send of ours already wrote that line, so the event only fills what is missing and never replaces who sent it or the opt-out line.
  - The first live test is one text from Quo's phone app to a number we hold, to see it arrive. That answers the first half of `HANDOFF.md` call 4.
