# v2.4736 — Bids: the history knows an import from an edit (2026-10-06)

Punch list #73, PR 1b ([`to-dos/bid-history`](../../to-dos/bid-history/README.md)): the request tag. PR 1 (v2.4598) keeps every change on a bid, but each REST call is its own transaction and a bulk path writes one request per batch, so the ledger could not say that 23 count rows arrived as one import, or that the Labor tab's load sync, not the person who opened the tab, rewrote the hours. Migration `20261007050000_bid_changes_action_tag.sql` ([doc](../migrations/20261007050000_bid_changes_action_tag.md)); `twin-mcp` changed.

## The change

- **The tag.** [`bidActionHeader.ts`](../../src/lib/bids/bidActionHeader.ts): `BID_ACTIONS` (`counts-import`, `counts-clear-all`, `labor-sync`, `book-fill`, `robot-paste`), `withBidAction(query, action)` (the query builder's `setHeader`, so one call carries `x-bid-action`), `bidActionHeaders(action)` for a client whose every call is one action, and `BID_APP_ACTIONS` (the app's own: `labor-sync`), mirrored by `bid_changes_app_actions()` and held together by `bidActionHeader.test.ts`.
- **The trigger** reads it: `bid_change_action()` takes the header from `request.headers` as a slug or null; `record_bid_change()` is replaced in full to write `action` and `by_app` (true for an app action, false for a tagged press, null with no tag).
- **The paths tagged**: the Counts tab's import batches (`insertCountRows`) and *Clear all counts*; the Labor tab's load sync (`loadCostEstimateLaborRowsAndSync`: the minted rows, the count refresh, the drops); the Pricing tab's *fill from the book* (`fillMatchingBookEntries`); twin-mcp's `paste_counts` (the admin client's `global.headers`).

## Not tagged yet

The margin brush (its strokes go through the single-cell price write) and a book switch's copy (`copyPricesFromVersion`): each is a person's press on many rows and would read better as one action; both are left for PR 2's reader to show how they group by time first.
