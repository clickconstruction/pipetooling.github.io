# v2.8516 — A job's paper settings: the window opens on a development copy of the app (2026-11-24)

A development-only fault found on 2026-11-24 while the Sub NDA's screens (punch list #389) were drawn on a local dev server. The live app was never affected. No migration, no edge function, no help guide change.

## What was wrong

`JobPaperSettingsWindow` (v2.8184) is the window **Settings** opens on a paper's row under *Papers before this job opens* in a job's Documents tab, and **Add a paper** opens for a paper built from settings. It kept a still-here flag so a read that answers after the window closed writes nothing:

```ts
const live = useRef(true)
useEffect(() => () => void (live.current = false), [])
```

The flag was only ever cleared. React's StrictMode, which `main.tsx` turns on, mounts, unmounts and mounts again in a development build. The first mount's cleanup set the flag false and nothing set it true again, so `load()` dropped its answer at `if (!live.current) return`. The window stayed on *Loading…* for good, and a failed read never drew its reason either.

The built app mounts once, so the flag stayed true and the window loaded. The live walks of 2026-11-21 and 2026-11-24 passed. The fault stopped anyone who works on this window locally, and any picture of it drawn in the lens frame.

## What ships

The effect sets the flag true on every mount and clears it on the way out, the shape the other still-here flags in `src/` already have. The guard stays: it is what stops a state write after a real close.

## The same shape elsewhere

Every `useRef(true)` in `src/` was read, 35 in all, with every effect that is only a cleanup.

- **31 are still-here flags** (`live`, `alive`, `here`, `mounted`, `mountedRef`). 29 set the flag true in the body of the effect that clears it. `ShowUs.tsx` clears it in an effect that is only a cleanup and sets it true in its read effect, which runs again on the second mount, so it recovers. This window was the only one that never set it true again.
- **4 are not still-here flags** and are not this fault: `sessionSignalFirstRef` in `ClockInOutButton.tsx`, `firstRouteRef` in `UpdatePrompt.tsx`, `atBottomRef` in `JobActivityFeed.tsx` and `blockingLoadOverlayRef` in `useChecklistTechTreeData.ts`. Each is a first-run or a scroll mark. They were not checked for any other effect of a double mount.
- **The flag the other way round**, false until the component is gone: one, `useTakenDown.ts`, which sets it false in the body.
- **Effects that are only a cleanup**, 45 found in the two shapes searched (`useEffect(() => () =>` on one line, and the same opened on the next line): this window's and `ShowUs.tsx`'s were the only two that wrote a still-here flag. The rest clear a timer, close a link, revoke a file's address or empty a held value.

Nothing else was changed.

## Where

- `src/components/jobs/JobPaperSettingsWindow.tsx`.

## Tests

- `JobPaperSettingsWindow.render.test.tsx`, two new tests inside `<StrictMode>`: the window leaves *Loading…* and draws a required paper's settings, and a failed read draws its reason. Both fail on the old window, stuck on *Loading…*, and pass on the new one. The ten tests that were there pass before and after.

## Verified

By the tests alone, with a control run of the new tests against the old window. It was not opened on a dev server in this change: the session that found the fault proved the same one-line change there with a scratch patch. No walk on the live site, since the built app never had the fault.
