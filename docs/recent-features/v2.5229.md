# v2.5229 — GC mode: a GC customer's portal wears Click Construction's letterhead (2026-10-10)

The live walk's step 2 found the GC test customer's portal under the plumbing letterhead (*CLICK. Plumbing, electrical, and HVAC*). The owner picked option a) of Owner Billing's read-back: the function picks Click Construction's block for a customer whose jobs are all GC. The Portal lane (gc 3) co-signed it with six conditions, each kept below.

- **The rule** (`portalLetterhead` in `supabase/functions/_shared/portalLetterhead.ts`, pure): Click Construction when the customer has a GC job we build (`gcJobs`, O7c's `loadGcPortalJobs`) and no Pipeline job but its billing job (`jobs_ledger.billing_only`). That includes a GC project with no billing job yet. Mixed, none, or a link with the `gc` audience (a GC we work for, which sees no GC jobs) reads the plumbing company. `customer-portal` adds `billing_only` to its job select, and `PortalJobRow` gains it.
- **Click Construction's block** (`PORTAL_GC_LETTERHEAD`): the name is `GC_CUSTOMER_EMAIL_FROM_NAME`, which a test holds to `GC_COMPANY.name`, so there is no third literal. The tagline is *Construction* and the phone is the office's. The city, license and email lines are blank until the owner names the GC entity and its address (call 12), so the plumbing company's lines never stand under the GC's name. The plumbing block is `PORTAL_COMPANY` with *Plumbing, Electrical, and HVAC*, as the page drew it.
- **The page** (`CustomerPortal.tsx`): the line under the CLICK. mark is `payload.company.tagline`. It is blank while the page loads, so a GC customer never sees the plumbing line first, and it keeps the plumbing line on an error page. `parsePortalPayload` reads a payload with no tagline as the plumbing one, so the function and the page deploy in either order. The two cards that name the company, the property notice and the owner's records, read `company.name` as before. Under this rule they name Click Construction only when every job is a GC job.
- **Printing:** the letterhead block is not screen-only, so the first printed page carries the same company as the screen. Each later page's header (`PortalPrintPageHeader`) carries only the CLICK. mark, which both companies share. So the screen and the paper never name two companies.
- **What customers see:** the owner's sample marks its one job, its GC billing job, `billing_only` and picks its letterhead by the same rule, so it reads *Construction*. The homeowner and GC samples read the plumbing company.
- **Deploy:** `customer-portal`, and the other functions that bundle `_shared/customerSampleFixtures.ts` and `_shared/portalMergedBills.ts`: get-bid-proposal-room, get-contract-for-signer, get-estimate-for-customer, get-job-contract, get-rfq-quote-page, get-submittal-room, legal-portal and sub-portal. Their only change is the sample fixture and a type.
- **Tests:** `portalLetterhead.test.ts` covers each case of the rule, the sample's own plumbing block, and the GC block's empty lines and shared name. Mutants with `some` for `every`, and with no `gc` audience check, each fail. `CustomerPortal.render.test.tsx` shows the owner sample reading *Construction* and the GC sample reading the plumbing line, and a payload with no tagline drawing the plumbing line.
- **Guide:** *see what a customer sees on their portal* says whose letterhead a customer reads. **Docs:** EDGE_FUNCTIONS.md's customer-portal section.
