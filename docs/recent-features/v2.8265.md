# v2.8265 — Sub papers: a sub with no email gets one on the To line (2026-11-21)

Client only: no migration, no edge function. Punch list #350, the door the card called *a real door for a sub with no email*, built on the owner's word of 2026-11-21 (*Please do*).

## Before

`send-sub-paper-email` mails a paper to the roster's own address for the person, `people.email`, and nowhere else. A sub with none had a dead press, a yellow line, and Print or Download as the way out. Read on prod on 2026-11-21, counts only: 24 active subs, 13 with no roster email, 2 of those signing in with an address on their login.

Nothing in the app let the office add one. Every person is tied to a `users` row since #260, and the roster's edit form is drawn only for a row that is not. The desk's **Change…** is a dev's, changes the sign-in address, and does not copy onto an empty roster row. So only a dev could add one, through Settings → People, and only on a row another account made.

## What the database already allowed

Read on prod the same day, read only: the UPDATE policies on `public.people`. *Users can update own people* is `is_office_staff() OR master_user_id = auth.uid()`, so a dev, a master technician, an assistant and a controller may already write any roster row, a login behind it or not. The training, twin and archived fences stand over it. The gap was a screen, not a permission, so this ships with no migration.

The card's first pick was to have the function fall back to the login's address. That is not built: the function still sends only to an address somebody put on the roster row, and it is not changed or redeployed.

## Now

- **The To line takes the address in place.** In the send step the address is a `ChangeableValue`: *no email on the roster* for a sub with none, else the address. A press turns it into its field with **Keep** and **Cancel**. `rosterEmailCheck` (`src/lib/subWorkOrders/subPaperRosterEmail.ts`) holds the shape the function itself asks for, so the line keeps nothing the function would refuse.
- **The save** (`keepEmail` in `SubPapersWindowConnected.tsx`) writes `people.email` for the person and reads the row back. A refusal says its reason under the field. A save that comes back with no row says *Their roster row was not changed. Your account may not edit it.* On a save the window's contact changes, the yellow line goes and the press reads *Send 3 papers by email*.
- **The sign-in address is offered, never used unasked.** For a sub with no roster email the window reads `users.email` through `people.account_user_id`. When it has the shape, a line under To reads *They sign in as <address>.* with the press *Put <address> on their roster row* (`rosterEmailOffer`).
- **A wrong address is put right the same way.** The line is a press whether or not the row has an address.
- **Who.** The line is a press only for a viewer who may send: the four office roles, and not an account in training. A roster row that could not be read keeps its old words and no press, since what it holds is not known.
- The yellow line's door now reads *Press the To line above and type their email. You can also print or download the paper.* (`subPaperEmailDoor(true)`).

The function is handed the person's id, as before, and reads the roster row itself.
