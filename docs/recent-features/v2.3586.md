# v2.3586 — `pay:backfill --only link,split,lane`, and the first apply (2026-09-18)

The owner, 2026-09-18: *"Please go ahead and link all the transactions that we are confident enough to link."* Confident means the plan's `link` and `split` actions — id, exact amount, one send over several rows, memo, memo-group, memo-fill, Mercury, and the within-$5 corrections — not the sends to record and not the items left for a person.

## `--only`

`npm run pay:backfill -- --only link,split --apply` applies only the kinds named (any of `link`, `split`, `lane`); the dry run says how many actions apply would run. Without it, apply runs all three.

## The apply, on prod

With the export: 140 new Cash App rows imported; **253 applied, 4 refused**. The four are within-$5 *upward* corrections where the corrected amount would exceed the week's net pay — the `validate_pay_stub_payments_vs_net` trigger refused them, which is the right answer: the person was sent more than the week was worth, and the difference is an advance to record, not an amount to overwrite. They stay unlinked for the owner. Afterwards: 179 payments sourced to Cash App, 79 to Mercury, 3 to Apple Pay; 10 part memos; blank memos 35 → 14.

## Lesson

A correction that raises an amount can collide with net; the plan should say so before apply. Follow-up: mark those links `review` in the kernel when `amountAfter > remaining + amountBefore`.
