# v2.7178 — Materials on site: a box photo sent twice still lands (2026-11-13)

Punch list #344, PR 2. From the review of Materials → On site: *a photo taken with no signal is lost*. The photo's row is kept and sent later by v2.7173, which put every on-site write through the outbox. This PR is the bytes.

## What was wrong

- **A resend was refused.** `sendBoxPhoto` uploads to `box-photos` as `<job>/<photo id>.jpg` with `upsert: false`. A send that reached the bucket while the phone never heard back left the file there, and every later **Send now** of that shot was answered *The resource already exists*, which the code read as a failure. The row stayed *on the phone* with no path, the sweep reads rows, and the file was never filed. This is #338's fault in its 409 form; the bucket has insert and select policies and no update, so an upsert would be refused too.
- **No deadline.** A send on one bar could hang with the chip on *Sending…*.
- **Kept, when it was not.** `putPhotoBlob` was awaited before the send, so a phone whose own store is full or shut threw there, and the toast said the photo was kept on the phone.

## The change

`src/lib/materials/photoUpload.ts`:

- An upload answered *already exists* is a landing (`bytesAlreadyThere`, the bid photo fix's own helper): the path carries the shot's id, minted on the phone, so what is there is this shot. The send goes on to its row.
- The upload has `BOX_PHOTO_SEND_TIMEOUT_MS`, 30 seconds. Past it the shot is kept and **Send now** tries again, which is safe by the line above.
- The phone's keep is tried and its outcome held. A shot that did not send and could not be kept throws `BoxPhotoNotKeptError`; `PhotoPress.tsx` then makes no note for a photo that is nowhere and says to take it again. A phone that cannot keep the shot still sends it.

No migration: an update policy on the bucket would let a person overwrite a photo's bytes.

## Tests

`photoUpload.test.ts` (7), the send's first test, with the project's own answers for *already exists* and a refusal: under its own id and never an upsert, a landing when it meets its own file, a refusal thrown with the shot kept, no signal, a phone that cannot keep, neither sent nor kept, and the deadline.

## Not changed

A kept photo still waits for a person's **Send now**; it is not sent by itself when the signal returns. The kept bytes of a sent photo are not cleared from the phone. Both are on #344's list. Job, task and report photos are #338's own PR.
