# v2.7635 — Lien desk: a file that does not go up says why, and Try again sends it again (2026-11-17)

The owner, 2026-11-17, from the desk's *Filed liens: copies to mail* window and the run's *Add what was mailed*: "an upload failed but all it said was 'failed', what should we do about this?"

**Where the word came from.** Both presses send the file through `drive-link`'s `put` (`putJobFolderFile`, the Documents tab's own call). The function's catch-all answered every thrown error with `{ error: 'failed' }` and wrote the real reason to its log alone. `fnProblem` hands the body's `error` to the screen as it came, so the toast read `failed`. The named refusals (over 10 MB, no Drive folder, a file that did not come through, office only) already had their sentences; anything Drive or Google threw did not.

**What the failure was.** The function's log for 2026-11-17 holds one line: `uploadBytes` threw `SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON`. Drive answered the upload with a web page, which Google's front door sends when it is busy or a gateway failed, and the helper read it as JSON. A second press would most likely have gone through. The reader below names that case (*Drive sent a web page where its answer should be. It does that when it is busy.*) and offers the second try.

**The function names its reason.** `supabase/functions/_shared/driveFailure.ts` is a pure reader of the thrown error (`driveFailureOf`). The Drive helpers throw in a few fixed shapes (`Upload failed (403): …`, `Folder create failed (500): …`, `Google token exchange failed (400): …`, `Drive answered 503`), and each becomes a sentence that says who refused and quotes their words: *Drive did not take the file. Drive said: …*. A fetch nothing answered reads *The app could not reach Drive.* An error of the app's own is passed on, cut to 200 characters. The answer carries `why` (`drive`, `google`, `unreachable`, `unknown`) and `retry`: true for Drive's 408, 429 and 5xx, for a rate limit, and for a Drive out of reach. The status is 502 when Drive or Google refused and 500 when the app tripped. Only the office's `POST` door says this. The open link's `GET` still answers the bare word, so a stranger with a link learns nothing more.

**The client keeps the answer.** The new `src/lib/jobs/addFileFailure.ts` holds `AddFileFailure` (an error with `retry`), `addFileFailureOf` and `addFileCanRetry`; `jobFolderAddFileIo.ts` reads the body once in `addFileFailureFrom`. The pieces sit beside `jobFolderAddFile.ts` and not in it: that file is copied under `_shared/gcKernels`, and a change to it reads as drift on every function that holds the copy. The function's `retry` wins when it gives one. With none, the status decides (408, 429, 5xx). A call nothing answered reads *The file did not reach the app. Check the signal, then try again.* A bare `failed`, the word the function used to answer and the public door still does, is replaced by the caller's fallback and offers the second try.

**Try again on both presses.**
- `LienReceiptPhotoPress` holds the shot that did not go up. Its reason stands under the press (`role="alert"`), and where `retry` is true **Try again** sends the same shot under the same name. The toast still fires.
- `LienDeskRunModal` holds the failed file per row (`failedCopy`) and hands the reason and the retry to `LienRunMailedCopies`, which draws them under the row. A failure of the notice's own list write, after the file reached Drive, is not an `AddFileFailure`, so it offers no second try: a second upload would leave two files.

**What else changes.** Every other caller of `putJobFolderFile` reads the same sentences: Add a file on the Documents tab, the stamped scans, the hours statement's signed PDF. Their screens are unchanged.

**Not built.** `uploadBytes` in `_shared/driveUpload.ts` still reads Drive's answer with a bare `res.json()`, so the status of a page-shaped answer is lost; sixteen functions import that helper, so its fix is a change of its own with their redeploys. A press that clears a wrong receipt photo without a retake. A wrong file still stays in the job's Drive folder: the app deletes nothing from Drive.
