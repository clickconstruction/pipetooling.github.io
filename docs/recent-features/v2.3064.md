# v2.3064 — Sub sheet stage moves itself when the facts do (2026-09-07)

Subs residual (1), deferred since v2.2667 ("derive sheet status from anchored steps — override ships first"). Client only; the stored stage is untouched; no migration or edge-function change.

## The problem

A Sub Labor sheet's stage (`working → walkthrough → customer_pay`, v2.2767) was stepped by hand — the office on Jobs → Subs → Pay, or the sub from the portal's "My work here is done". Two facts the app already holds say the same thing without a click: the sub's own percent from the portal (`progress_pct`, v2.2931) reaching 100, and the signed work order's last picked (else proposed) day passing. When nobody clicked, the rail said *Waiting on work* on jobs that were plainly done, and the board sorted them wrong.

## What shipped

- **`src/lib/subSheetStageDerived.ts`** — `effectiveSubSheetStage(evidence)`: a stored *Waiting on work* reads as *Waiting on inspection* when the sub reported 100% or the signed window has ended. Nothing moves backwards; *walkthrough* and *customer_pay* stay as set (whether the inspection passed is not knowable from data). **A hand move after the evidence is a manual nudge that stands**: if the office or the sub set it back to *Waiting on work* after the 100% report, or after the window's last day, that choice wins. `subSheetWorkEndYmd(orders)` reads the latest end among the signed orders covering the sheet. Pure; 7 tests.
- **Applied everywhere the rail is built**: the Sub Labor pay table (rail, the pay-when rule, and the stage chip, which now carries an **· auto** mark whose tooltip says which fact moved it), the Work Orders board rows (sort and group follow the effective stage), the sheet story modal, and the sheet's work-order panel. The **→** and the stage menu still work from the effective stage, so "move to Waiting on customer" is one click as before.
- **Data**: the ledger and the story select `progress_pct` / `progress_at`; the tab's commitments select `picked_end` / `proposed_end`; `WorkOrderRowLike` and `LaborJob` carry the optional fields (`stage_auto_reason` is display-only, never persisted).
- **Help**: `share-a-sub-their-portal.md` explains the automatic move and the nudge.

## Not in this PR (follow-ups)

- **Persisting `auto`** through a trigger or RPC so the Activity feed gets a line and the portal reads the same stage. The portal (`sub-portal` edge function) still shows the stored stage; its sub-facing copy for *Waiting on inspection* assumes the sub pressed the button, so parity there wants its own pass with the Spanish strings (residual 2).
- Deriving *customer_pay* from a passed inspection: no data source today.
