# v2.7212 — Materials on site: fix a part's name that was typed wrong (2026-11-13)

The owner's ask of 2026-11-13: the box window should edit everything about a box, a part's name included. A name typed on site is the only name its line has, and the ledger takes inserts alone. On the site that prompted this, one crew member had fixed a name by counting the line to zero and adding it again, which the office page read as a shortfall.

## What changed

- **The database** (`20261113230000_on_site_part_renames.sql`, [`docs/migrations/20261113230000_on_site_part_renames.md`](../migrations/20261113230000_on_site_part_renames.md)): `job_part_renames`, insert only. Inserting a row is the act. A BEFORE trigger finds the job's typed ledger rows that carry the old name and fills the row. An AFTER trigger, so after the caller's own RLS let the row in, sets `part_name` on exactly those rows. It is the one update of the ledger, and of the name alone. The row keeps the ids it changed, so a second row naming it (`undo_of`) puts the old name back.
- **The rules and the words** (`src/lib/materials/partRename.ts`, pure, 6 tests): `partRenameVerdict` cleans the name, refuses a parts-book part and a name past 160 characters, and answers every box on the job that holds the old name and every box where the new name is already a line. `partRenameScopeNote` and `partRenameMergeNote` say both before the press. The press names the act: *Rename to 3/4 pex*.
- **The write** (`partRenameIo.ts`): one insert, then the job is read again. It is not an outbox press, since it changes rows the phone already drew, so it needs a signal and says the reason when it has none.
- **The screen** (`BoxTabs.tsx`): on Contents, **Fix the name** under a typed part opens a field in the line. After a rename the tab says what changed with **Undo the rename** while the window is open. A refusal is said in the database's own words.

## Why a rename changes rows in place

The other way was a second table every reader maps names through: the phone's kernel, the server's job summary, the scanned page, the dev seat's read and the site's rollup. Each would have to learn it, and one that did not would show the old name. Changing the name in place leaves every reader as it is. What append-only protects is kept: no quantity, reason, box or time changes, and the old name, who and when are on record with the rows touched.

## Who

Whoever may touch the job, by the gate every other on-site press uses. A training account and a digital twin are held by the fences.

## Left

- **A Same part? answer or a site price given to the old spelling stays with the old spelling.** Both are keyed by the name's words (`on_site_part_ties`, `on_site_prices`). Renaming a part that carries one means answering again.
- **No Undo after the window closes.** The record is there; no screen lists it yet.
- **The dev seat has no verb for it.** One could insert the same row under a plan and apply, with no further migration.
- **The types** follow the push as their own PR; the write names the table by hand until then.

## Deploy

One migration, no function. The client inserts into a table only the migration makes, so this is a *push right after the merge*: `supabase db push` from `main` after a dry run, then `npm run check:migration-drift`. Stacked on v2.7199 (#8023).
