# v2.4750 — Legal desk: the firm’s links carry its name, and every one is on the list (2026-10-06)

One migration (`20261007070000_legal_portal_links_named.sql`, pushed after merge), three edge functions redeployed (`legal-portal`, `legal-send-firm-link`, `legal-notify-dispatch`), the office's Firm's link window, the customer page's short-address fallback, the Lien desk's share line and a guide. The owner's ask on 2026-10-06, from the window as it was: *"I would like the link to be easier and include the firm's name just like our GC links, I would like all links we create to be viewable on this screen and with the ability to revoke them or rotate them."*

## What was wrong

The window showed one link, and only its state: *The link is live. Its address can be copied only when it is created or rotated.* That was item 22's hash-only rule ([v2.4647](v2.4647.md)) read to the letter: the office could not see the address it had made, only email it. The address itself was 64 hex characters on `/legal?t=`, nothing like `my.clickplumbing.com/knight-contracting-x7kq`, which is what a GC gets. And a firm had one link for everyone, so cutting off one person meant rotating the firm.

## What changed

- **The key reads like an address.** `legal_portal_link_new_key(name)` makes `<the firm's name as a slug, at most 40 characters>-<12 characters from a–z and 0–9>`, so a link is `my.clickplumbing.com/snell-law-firm-pllc-k4tp9x2mq7zr`. The tail is 62 bits of key; the name is for the eye. The table keeps the sha256 and Vault keeps the raw key per link, as item 22 built it. The portal functions change nothing for lookups: the key goes through `token_hash` as before.
- **The short domain carries it.** The Worker bounces `my.clickplumbing.com/<key>` to `/p/<key>`. The customer page finds no customer, then asks `legal-portal?token=<key>&probe=1` (new: answers `{ ok, firmName }` for a live key with no payload and no view row) and lands on `/legal?t=<key>`; a miss goes on to `/s/<key>` as before, so a dead sub link still lands on the sub portal's own bilingual error. One shared file, [`_shared/legalPortalAddress.ts`](../../supabase/functions/_shared/legalPortalAddress.ts), writes the address for the window, the welcome email and the firm's notices: the short form for a slug key, the direct `/legal?t=` form for a key made before this (64 hex characters).
- **Every link, on the list.** `list_legal_portal_links(firm)` returns every row the firm ever had, with the live ones' keys decrypted from Vault and the names of who made and who ended each. The window draws *The firm's own link*, *One person's link* and *Turned off*. A live link shows its address, *since … by …*, its welcome email's *Sent to … on … by …*, and Copy · Send… · Rotate · Turn off. A dead one reads *2026-09-11 to 2026-10-06 · rotated by Robert* (`revoked_by`, `revoke_reason`: rotated · off · replaced). A live link made before this says so and asks for a Rotate.
- **Several links per firm.** `purpose` is `firm` (one live per firm, the one every email carries, `legal_portal_link_token` reads it) or `person` (`label` required, any number). `create_legal_portal_link(firm, label)`, `rotate_legal_portal_link(link)` (same purpose and label, the old one dies as rotated) and `revoke_legal_portal_link_by_id(link)` are the window's three verbs. The confirms tell the firm's own link from a person's: rotating or turning off the firm's kills the link in every email sent; a person's is theirs alone.
- **Send… per link.** `legal-send-firm-link` takes `linkId`; a person's link greets that person by the label, the firm's own greets the handling person on file. The key is read by `legal_portal_link_token_by_id` on the server. The filed copy redacts the short address as it did `?t=`.
- **The old doors keep working** for the client that is live while the migration is pushed: `mint_legal_portal_link(firm, rotate)` creates or rotates the firm's own link; `revoke_legal_portal_link(firm)` turns every link of the firm off.
- **The Lien desk's share** reads the firm's own address through the list again, so *Copy the firm's link* is back after item 22 took it.

## Is this the best we can do?

- **Plain slug in the table, like a customer's?** No. A customer's short address opens one customer's bills; the firm's opens every account with the firm. The key stays hashed at rest and in Vault, and the office reads a live address back through one gated RPC. A dump of the table still holds no key.
- **Why not `/legal/<key>` on our own origin?** The owner asked for the GC's shape. The short domain costs two cheap misses (customer, sub) and one probe before the firm's page opens; the office's Preview stays on the direct, signed-in form.
- **A link per recipient on the notifications list instead?** The firm's people list is who gets emails; a link is who can open the portal. They overlap but are not the same list, and the owner's words were links. The firm's own link rides in the emails; person links are handed out by the office.
- **The Worker's unfurl** reads the slug as a title, *Snell Law Firm Pllc K4tp9x2mq7zr · Click Plumbing & Electrical*, over the customer card. A firm-aware card needs a dashboard edit of `portal-link-shell`; left for later.
- **Views per link?** Views count per firm (`public_page_views.entity_id`). Left as is.
- **`legal_replace_firm`** still revokes the old firm's links without a reason; the list reads them as *turned off*. Stamping `replaced` means re-creating that function; left for its next change.

## Deploy

1. Merge; the client deploys. Before the push the window says *The links list needs a database update that is not live yet.*
2. `supabase db push` (`20261007070000`).
3. `supabase functions deploy legal-portal legal-send-firm-link legal-notify-dispatch`. Until then: the probe 404s (a new key opens through `/legal?t=`, so the direct form in the window's Preview works; the short address waits for the deploy), the send goes to the firm's own link with the `/legal?t=` form, and the notices carry the direct form.
4. `npm run gen-types:linked` → the `chore(types)` PR.
