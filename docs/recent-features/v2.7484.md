# v2.7484 — Stickers: a sticker is reserved, never blank (2026-11-16)

Punch list #329. The owner's word of 2026-11-16, after he opened the window with Names `G92-200` and read the preview's strips over the stand-in address `0000-0000`: he never wants to print a blank sticker, he wants printing to reserve a place that is filled in later. The database has done that since v2.7072: `mint_sticker_run` makes a `box_stickers` row for each sticker at the press, with a code of its own and its name, and the row waits with no box until a scan or **These are on boxes** places it. Only the words were wrong. Client only, no migration, no function.

## What changed

- **The name.** `PRINT_STICKERS_LABEL` is *Print future stickers*: the press on the Materials strip (`MATERIALS_PRESS_LABELS` now reads the constant), the press on a job's On site strip with a new tooltip, the *Which job?* window, the print window's title and its aria label, and the guide heading `STICKERS_GUIDE_HEADING`, whose link reads `STICKERS_GUIDE_QUESTION`, *How do I print future stickers?*
- **The ask says what the press holds.** `stickerReserveWords(named)` draws one line over *New boxes made from these stickers go on …*: *Printing reserves each name and gives each sticker its own link. You say which box it is on later.* A run with no names: *Printing gives each sticker its own link and holds it for a box.*
- **The press.** The ask's press makes the run and prints it, and counts in the press's own name: *Print 109 future stickers, G92 to G200*, with copies *Print 200 sets of future stickers* (`futureRunPressLabel`). A run already made, the Runs fold's **Reprint** and **Print the rest**, reads plain *Print 109 stickers*, since its places are reserved and no longer to come. While the database works the line reads *Reserving the stickers…*, and a refusal with no words of its own reads *The run was not made. No sticker was reserved or printed.*
- **A made run says it is reserved.** `STICKERS_RESERVED_WORDS` under the title, over the strips with their real links: *These stickers are reserved. Each one holds its own link until you say which box it is on.*
- **The other screens.** The Runs fold's summary reads *Stickers reserved for this job, and how many are on boxes.* The hold on a second run over the same names reads *23 of these are reserved by an earlier run and are not on a box yet*. These are on boxes says *1 has no reserved sticker*. Scan a label says *A reserved sticker opens the sheet that puts it on its box.*
- **Signed out.** A reserved sticker's page reads *This sticker is reserved for a box*, then *It is not on a box yet. Sign in to say which box it is on.* (`BLANK_STICKER_TITLE`, `BLANK_STICKER_PUBLIC_DETAIL`), and the tab reads *Reserved sticker*. `box-read` is untouched: the words are the page's.

## What did not change

The code and the database still call the state `blank` (`StickerState`, `sticker_blank`, `blankStickersOf`): a rename there is a sweep across a surface with much in flight, and no person reads it. The preview fold's stand-in code and the job's line for its reserved stickers are the next two PRs. The mock-ups on the card keep the old name as drawn.

## The name is the owner's pick

The branch first read *Reserve stickers*. Offered both on 2026-11-16, the owner picked **Print future stickers**, his own phrase, before the PR merged. The branch's inner press read *Reserve and print 109 stickers*; it now counts in the same name. The state keeps the word *reserved*, his other word: a future sticker is one whose place is reserved. The name lives in one constant.
