# v2.4108 — Contracts & terms reads as an index: sections in the customer's order, one line per contract (2026-09-29)

Client only; no migration, no edge function. The owner, 2026-09-28, on the live page after v2.4098: *due to the large number of contracts in the application, I think it would be strategic to order them better so they are easier to navigate.* Order A and Order B drawn on the reader's canvas (artifact `EQ5hcH6ahKiXwWtzUwPpBT`, third row); the owner: *build order b.*

## Why

Eighteen tall cards in two groups, each printing its wording box, six facts and up to seven pills, in the catalog's order. Finding one contract meant scrolling the lot. Order A (sections and a jump rail, the cards as they were) still left the scroll; the wording box on every card is what makes them tall. The page should read like a table of contents first and a card second.

## What shipped

- **[`contractsIndex.ts`](../../src/lib/contracts/contractsIndex.ts)** (pure, 4 tests): `CONTRACT_AREA_ORDER` and `CONTRACT_AREA_HINTS` (the six sections, in the order a customer meets them); `needsLookReasons` (what went out differs or an unsent draft is behind · nothing set · review due — never *never reviewed*, which on the first day is every card); the lenses (`all`, `needs_look`, then each kind of wording) with `contractLensCounts` and `contractLensLabel`; `indexRowMatches` / `indexSection` (the lens and the find box, which reads the title, the name and the wording); `reviewWord`; `entryIdFromHash`.
- **[`SettingsContractsTab`](../../src/components/settings/SettingsContractsTab.tsx)** — the two groups become six area sections (`contracts-area-<area>`), each a list of rows. A row is a button (`aria-expanded`, `contract-row-<key>`) carrying the name, the audience and wording chips (*Notice* on the second group's cards), *Last changed*, the short review word, *Last sent* (amber when off) and a *Needs a look* chip, with *Read it* beside it; a press opens the card under the line (`data-open`), the same card as before minus its repeated title. The toolbar: the find box (`Find a contract`), the lens chips (`contract-lens-<lens>`, a lens with no card is not shown), *Open all* / *Close all* (`contracts-open-all`) over the rows the lens shows; *Jump to* scrolls to a section and greys one the lens empties. The counts card's sentence says how the page reads now.
- **Arrival** — the tab takes `openEntryId`; What customers see's door sets it in `Settings.tsx` before switching tabs, and the page's `#settings-contract-<id>` hash does the same on mount, so the linked card is open when the shell scrolls to it.
- **Guide** `see-every-contract-side-by-side` gains *Find a contract*; `docs/SETTINGS_TABS_ARCHITECTURE.md` row 7b.
- Tests: the tab's cases press *Open all* after the load (the rows start closed) and read the six headings; one new case walks a row, the lens, the find box, Open all / Close all and a card opened on arrival.

## Decided here

- **Needs a look is a lens, not a section.** The mock-up drew a section first; a section would list the same rows twice (two anchors, two test ids). One chip at the top does the same job with one click.
- **Rows start closed.** The point is the scan; *Open all* is one press for the old page.
- **The row's button reads *Read it***, the card's reads *Read it as the customer sees it*: the same door, a short name where space is tight.
