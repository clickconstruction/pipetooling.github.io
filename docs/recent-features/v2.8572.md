# v2.8572 — Checklist → Manage: deleting a task now says what happened (2026-11-25)

Punch list #369, from the walk of 2026-11-25 on the live site. No migration, no edge function.

**Seen.** Checklist → **Manage** → a task's **⋮** → **Delete** → the window *Delete checklist item?* → **Delete**. The task was deleted. No line said so in the five seconds after: the row leaving the list was the only sign.

**Read in the code, not seen.** Two more ends of the same press said too little.

- A delete that failed put the database's own message in the page's red line. That line is at the foot of the page, off screen on a long list.
- A delete the row rules refuse comes back with no error and no row. The window closed, the task stayed, and nothing was said.

**The mend**, in `ChecklistManageTab.tsx`, with its words in `src/lib/checklistManageDeleteWords.ts`:

- The delete asks for the row back (`.delete().eq('id', id).select('id')`). The same rows are deleted as before: a delete already needs to read the row it removes.
- A row came back: the window closes, the list is read again, and a toast reads *Task deleted.*
- An error: a toast reads the sentence *The task was not deleted* with the reason after it, through `formatErrorMessage`. The window stays open. A thrown failure, such as no signal, takes the same path.
- No error and no row: the window closes, the list is read again, and a toast reads *The task was not deleted. It is someone else's task, or it is already gone.* The row rules let a person delete a task they made and let the office delete any, so those are the two ways no row comes back.

The page's red line is no longer written by this press. The tab's own load still writes it.
