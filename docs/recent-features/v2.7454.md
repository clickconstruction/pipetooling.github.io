# v2.7454 — Painted maps: a thrown-away map's photos can be cleaned up (2026-11-16)

Punch list #345. A session walking the link train found that *Throw the map away* leaves the places' photo files in the `painted-map-photos` bucket: `deletePaintedMap` deletes the row, the lines and places cascade, and nothing removes the files. The ask was a client fix that removes them after the row is gone.

## Why this is a migration first

The client fix cannot work under the bucket's policies as they were. Both `painted_map_photos_files_select` and `painted_map_photos_files_delete` asked for the map's row, so once a map was gone nobody signed in could list or remove a file under its id. A `remove()` then answers with no error and removes nothing.

Removing the files first, while the map stands, was the other way. It was not taken: a delete of the row that then fails would leave the map standing with its photos gone, and an account in training could remove real photos and then be refused on the row. The owner picked the migration on 2026-11-16.

## What changed

`20261116234500_painted_map_photos_after_the_map.sql` (`docs/migrations/20261116234500_painted_map_photos_after_the_map.md`):

- `painted_map_stands(text)`, a yes or no past the caller's row security, so a map the caller cannot read is never taken for a map that is gone.
- One more branch on each of the two policies: once the map is gone, a file's uploader and the office may list and remove it, and nobody else reads it. The half that holds while the map stands is unchanged, and so is the insert policy.

`docs/ACCESS_CONTROL.md` carries the rule on the bucket's line. The bed gained `supabase/tests/painted_maps/60_photos_after.sql`.

## What it leaves behind

When a maker who is not office throws a map away, a teammate's photo on it stays in the bucket until the office removes it. The office can now list and remove such a file, which nobody signed in could before. Letting whoever threw the map away take every file under it would need a table that records who did; the owner was told it is there if wanted.

## Orphans on prod today

None. The bucket held 0 objects on 2026-11-16, read with the CLI's Storage list on the linked project. The same list on four other buckets answered with entries, so the list works. One painted map stood on prod, with no photo on any place.

## Every path that deletes a map

One: the *Throw the map away* confirm in `PaintedMapWindow`, the only caller of `deletePaintedMap`. Nothing cascades onto a map (`job_id`, `development_id` and `created_by` are each set null), and no edge function, dev seat verb, migration or script deletes one.
