# v2.4658 — Emails: a robot account can no longer send or receive them (2026-10-06)

Punch list #29 ([`to-dos/people-spine-residuals.md`](../../to-dos/people-spine-residuals.md)), item 2: the People spine's sweep of the edge functions. A mechanical sweep, merged alone. No migration and no client change. Fifteen edge functions and two shared modules change, deployed in waves after the merge (below).

## What was wrong

Fifteen edge functions looked their sender or recipient up in `users` with a hand-written `.eq('is_sample', false)`, a rule copied by hand that left digital twins in. Twins are estimators, so a twin's session passed the sender check of the two functions that email outside the company: `send-bid-pricing-package` (a GC) and `send-rfq-email` (a supply house). The to-do's plan was to read `roster_people` instead, but the functions cannot read it:
- every lookup runs as the service role, which the view answers with no rows
- the view carries no email
- `is_active_roster` leaves out devs, who send and receive these emails

## The change

- **[`supabase/functions/_shared/realAccount.ts`](../../supabase/functions/_shared/realAccount.ts)**: `REAL_ACCOUNT = { is_sample: false, is_digital_twin: false }`, the `users` half of the view's `is_pay_roster`. Archived stays with each caller, which words its own refusal.
- **[`scripts/sweep-real-account.mjs`](../../scripts/sweep-real-account.mjs)** rewrote every `.eq('is_sample', false)` to `.match(REAL_ACCOUNT)` and added the import. It folded `send-lien-desk-summary`'s separate twin filter into the same call. It is idempotent (`--check` changes nothing), so on a rebase conflict, re-run it.
- **Swept:** billed-report-email, crew-day-email-dispatch, money-waiting-email-dispatch, paid-job-email, payment-forecast-email-dispatch, recurring-job-report-dispatch, schedule-day-email-dispatch, schedule-share-dispatch, send-bid-pricing-package, send-lien-desk-summary, send-report-email, send-rfq-email, statement-round-email-dispatch, weekly-money-email-dispatch, weekly-movement-email-dispatch, `_shared/jobWatchers.ts`, `_shared/arReturnCaseNotify.ts`.
- **Left alone on purpose:** `create-user` (writes the flag), `dev-mcp` and `_shared/devMcpComposites` (View-as reads the sample accounts), `_shared/rosterRow.ts` (fixture accounts get no roster row).
- **The crew pickers (item 1) are pinned, not moved.** `activeUsersQuery` already applies the view's rule in one place, and the view lacks the email, phone and sign-in stamp the pickers read.

## Tests

- **`src/lib/people/realAccountSweep.test.ts`** checks four things:
  - no hand-written sample filter is left outside the four files kept on purpose
  - every function that uses the rule imports it from a path that exists (a bad path would only show after a deploy, as a function that fails to boot)
  - the rule refuses samples and twins
  - its list of files kept on purpose matches the script's
- **`src/lib/people/rosterRulePin.test.ts`** pins `REAL_ACCOUNT` and the pickers' `isActiveRosterPerson` to the view migration's `is_pay_roster` / `is_active_roster` expressions. A condition added to the view fails CI until both copies learn it.
- **`src/lib/people/realAccountSenders.run.test.ts`** and **`realAccountRecipients.run.test.ts`** run `send-bid-pricing-package` and `weekly-money-email-dispatch`'s own handlers on a fake database that applies their filters (`src/test/edgeFakeDb.ts`):
  - a twin sender is refused before the bid is read, and a twin recipient is refused
  - a twin queued for the weekly money report is marked unavailable, while the person beside it is mailed
  - both files fail on the pre-sweep functions, which let the twin through
