# v2.3554 — Estimate options, approve more than one — PR 1: the kernels, the column, the four functions (2026-09-17)

Taunya, 2026-09-17: *"Reminder to fix Estimates and the ability to approve more than 1 option."* Every option on an estimate has been an alternative since v2.2457 — radio cards, one Approve, one option frozen — so a customer who wants the heater *and* the softener *and* the hose bibs could not approve them together. Plan, decision and mock-up: `to-dos/estimate-options-approve-several/`. This PR is server-side and ships dark; PR 2 is the customer page, PR 3 the office builder.

## The model

Each option in `estimates.options_snapshot` carries a **`kind`**: `'choice'` (one of the alternatives — pick exactly one, the ★ pre-selects; absent = choice, so every existing snapshot behaves as today) or `'add_on'` (rides along with whatever they choose — tick any, none pre-ticked). An estimate whose options are all add-ons has nothing to choose between and needs at least one tick. The star rule: exactly one recommended, and on a choice whenever the estimate has one (a star asked onto an add-on moves to the first choice); an all-add-on estimate keeps its star on one add-on — that is the number the office forecasts before the customer decides (owner decision 3 unchanged: the pre-accept mirror is the ★ option's total).

Acceptance freezes **every** accepted option's lines, in offered order, into `line_items_snapshot` and their sum into `total_cents` — so the accepted document, the PDF, `createJobFromEstimateSubmit` and the Pipeline read exactly what they always read — and stamps the list in the new `estimates.accepted_option_keys text[]` (migration `20260917053000`). `accepted_option_key` keeps the chosen choice and is null when the estimate had no choice group.

## What changed

- [`src/lib/estimates/estimateOptions.ts`](../../src/lib/estimates/estimateOptions.ts) (+17 tests) and its dependency-free twin [`_shared/estimateOptions.ts`](../../supabase/functions/_shared/estimateOptions.ts): `kind` on the type and in normalize; `defaultEstimateSelection`, `toggleEstimateOptionSelection` (a choice replaces the other choice, an add-on toggles), `isValidEstimateSelection` → `option_required` / `option_unknown` with `estimateSelectionProblemMessage` for the words, `freezeAcceptedEstimateOptions(options, keys)`, `describeEstimateSelection` (*"Replace 50-gal" + 2 add-ons* · *3 options*), `setEstimateOptionKind`; `setRecommendedEstimateOption` refuses an add-on while choices exist. The single-key `freezeAcceptedEstimateOption` stays for the readers that predate this. The parity suite (`estimateOptionsSharedParity.test.ts`) now pins kind, the star rule, validity, the multi-key freeze and the selection words byte for byte across both kernels.
- [`accept-estimate`](../../supabase/functions/accept-estimate/index.ts): the body takes `optionKeys: string[]`; `optionKey` still works (a client from before add-ons — the one-element case of the same rule). The freeze writes `accepted_option_keys`; the staff notice reads *"Replace 50-gal" + 2 add-ons · $5,740.00*.
- [`_shared/estimateEmailLetterhead.ts`](../../supabase/functions/_shared/estimateEmailLetterhead.ts) (one builder, the staff Email preview renders it too): the ladder sorts choices above add-ons, labels an add-on **Add-on** and prices it `+ $…` when the estimate has a choice group; the text version says *choose one on the page, and add any extras*. `send-estimate-to-customer` passes `kind`. `get-estimate-for-customer` and `log-estimate-option-view` change no logic — they import the kernel and redeploy so the page receives `kind`.
- `docs/EDGE_FUNCTIONS.md` → accept-estimate's Body; `docs/migrations/20260917053000_estimate_accepted_option_keys.md`.

## Deploy

After merge: `bash scripts/db-push.sh` from a checkout at `main` **first** (the function writes the column), then `supabase functions deploy accept-estimate get-estimate-for-customer send-estimate-to-customer log-estimate-option-view`; regenerate types as a `chore(types)` PR. Everything is backward compatible in both directions: an old client sends one key and freezes one option; a new page (PR 2) sends both `optionKey` and `optionKeys`, so an old server still accepts it.
