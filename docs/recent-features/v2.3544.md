# v2.3544 — Submittals stage 6b: the three robot verbs (2026-09-17)

Client + one migration (`20260917020000_bid_submittal_tasks.sql`) + `twin-mcp` (four tools). PR 6b of [`to-dos/submittals/STAGES-5-6-BUILD.md`](../../to-dos/submittals/STAGES-5-6-BUILD.md); the owner lifted stage 6's gate on 2026-09-16.

## Why

Three chores in a submittal are reading — the fixture schedule off the plans, a house's PDF into per-tag sheets, a reviewer's marks into calls — and reading is what a twin does well. Every result lands on a screen the office already uses (the schedule modal's rows, the sheet strip's chips, the reviewer file's card) and **a person confirms every row; the robot never sends and never decides**.

## What shipped

- **Schema** ([migration doc](../migrations/20260917020000_bid_submittal_tasks.md)): `bid_submittal_tasks` — `kind` read_schedule · file_cut_sheets · read_redlines, `input` / `result` jsonb, the price-matrix status machine (queued · working · ready · blocked · cancelled · done), `claimed_by` / `heartbeat_at`, `reviewed_at` / `reviewed_by` when the office confirms. RLS: the pricing sharers queue, read, update on bids they can price; the twin writes through `twin-mcp` with the service role; both read-only appliers + the twin fence.
- **twin-mcp** (`supabase/functions/twin-mcp/index.ts`): `get_submittal_guide` (the brief, `docs/twins/submittals.md` → `briefs.ts` via `scripts/build-twin-mcp-briefs.mjs`), `next_submittal_task` (claims the oldest queued task with the conditional update, returns the bid, the kind, a 15-minute signed link for a file task, the tags on the bid and the revision's rows), `put_submittal_result` (per kind: schedule rows → `bid_specified_products` as `source = robot`, unconfirmed, never over a human tag; page guesses and redline annotations → `result`), `finish_submittal_task` (ready, or blocked with a reason). Estimator or pricer keys. The contracts and the cleaning live in `_shared/submittalRobot.ts` (+5 twin tests: tags upper-cased and de-duplicated by confidence, one guess per page inside the file, a mark with no tag is a question, the task line).
- **The tab** (`BidsSubmittalsTab.tsx`, `src/lib/submittals/robotTasks.ts` +4 tests): **Ask the robot to read the schedule** (a dashed panel when the bid has no schedule; a ready read lists the sure tags ✓ and the want-a-look tags with a checkbox — **Confirm N · leave M** confirms the chosen rows (`confirmed_at`) and drops the rest; *Discard the robot's rows*); **Ask the robot to split this file** on each vendor file of the sheet strip (`SubmittalSheetStrip` gains `guesses` / `robotLines` / `confirmLabels` / `onAskRobot` / `onConfirmGuesses`: dashed green chips for sure guesses, amber `?` for unsure, a tap on a chip assigns the page as a tap always did; **Confirm N · pick M** writes the sure pages through `writeItemPages` and leaves the unsure ones dashed); **Ask the robot to read the redlines** on a reviewer's redlined PDF (5b's card): the proposed calls list with **Confirm N · settle M** and *Take the unsure ones too* — each confirmed mark is a 5b entered decision with `decision_source = robot` (*read from Dana's file, confirmed by Wendi*), the thread line reads *read by the robot, confirmed by the office*, and every question posts to the thread as a system entry. Blocked and queued tasks can be dismissed / cancelled.
- **Unconfirmed robot rows** stay out of the picks and the compare: `loadPicksForBid` and `QuoteCompareModal`'s schedule read filter `source.neq.robot,confirmed_at.not.is.null`.
- Guide: *build a submittal package* → **Let the robot read it first**. `docs/twins/submittals.md` is the robot's brief; `docs/EDGE_FUNCTIONS.md` twin-mcp section; `docs/ACCESS_CONTROL.md`.
