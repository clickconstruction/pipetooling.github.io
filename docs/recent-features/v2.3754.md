# v2.3754 — A bill has an address that never expires: `/pay/<bill id>` (2026-09-23)

Punch list #36 (`to-dos/lien-notice-pay-codes/`), PR 1 of 4 — the groundwork under the pay codes. One new edge function, one new public page, no migration. Nothing the office sees changes yet.

## Why an address of our own

The office's hand-built lien packet (the *273 · Dudley (Lennox)* sample) carried a page of QR codes, one per unpaid bill, each pointing straight at Stripe's hosted invoice. Stripe expires that link 30 days after the due date (the nightly `refresh-stripe-invoice-links` sweep, v2.3589, keeps the *stored* column fresh — not the paper), and a lien notice is exactly the letter that gets paid late. So the codes the app will print carry `https://clicktooling.com/pay/<jobs_ledger_invoices.id>`, and that page fetches Stripe's current link at scan time. Built asking whether a bare 302 was the best we could do: it was not — a customer who scans a code from an old letter deserves to be told the bill is already paid rather than shown Stripe's page a second time, and one who scans with the forward blocked deserves a button.

## The change

- **[`pay-link`](../EDGE_FUNCTIONS.md#pay-link)** (`supabase/functions/pay-link/index.ts`, `verify_jwt = false`) — `GET ?id=<uuid>`: the row, then Stripe in the row's own mode, answering `{ state: open|paid|void, url, number, jobName, company, phone, amountRemainingCents, currency, paidOn }`. When Stripe's link differs from the stored one the row is brought up to date (v2.3590's rule), so a scan refreshes the link every other reader hands out. Stripe unreachable → the stored link and the row's own status, never an error page for a customer holding a phone. The id is the capability, as Stripe's own link is; anything that is not a UUID is refused before the database is touched; 60 opens a minute per address and 600 per isolate, in memory. One structured `pay_link_open` line per open.
- **[`_shared/payLink.ts`](../../supabase/functions/_shared/payLink.ts)** (pure; 12 tests from [`src/lib/billing/payLink.test.ts`](../../src/lib/billing/payLink.test.ts)) — `isPayLinkId`, `payLinkRowEligible` (billed or paid, and a Stripe invoice — a paper bill has no payment page), `payLinkStateFrom` (Stripe's word wins when it answered; the row's own status when not), `buildPayLinkPayload`, `parsePayLinkResponse`, `formatPayLinkCents`. **[`src/lib/billing/payLink.ts`](../../src/lib/billing/payLink.ts)** re-exports it and builds the address — `payLinkUrl(id)` always on the public origin, never `window.location.origin`, because a code drawn on a dev server is still scanned by a customer.
- **[`src/pages/PayLink.tsx`](../../src/pages/PayLink.tsx)** at **`/pay/:id`** (public, light, the portal's paper) — the bill's number and job, the amount still owed, *Opening your secure payment page…* and a forward after 1.2 s (`location.replace`, so Stripe's back button returns to where the customer came from, not to a page that forwards again) with a **Pay now** button under it; **Paid** with the day and *Nothing to pay*; a voided bill, an unknown id and a Stripe-less bill each say so with the office number to call. `payLinkView` (the answer → the page state) and the four states are tested in `PayLink.render.test.tsx`.
- **What customers see** (the `customerSurfaceRegistry` gate caught it on the full run): the route is placed on the homeowner journey as **Pay code** after *Bill by email* — `/pay/<sample token>` renders a sample bill and never forwards; a customer's journey (`personJourney`) answers the step from the same Stripe bills as *Bill email*, with the code's address as the link.
- Docs: the function's section in `EDGE_FUNCTIONS.md`, the page in `docs/twins/APP_DIRECTORY.md`, `config.toml`.
