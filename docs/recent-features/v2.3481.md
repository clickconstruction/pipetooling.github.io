# v2.3481 — The first price on a bid freezes it (2026-09-15)

Client only — no migration, no edge function. PR 1 of the *Frozen bid prices* to-do ([`to-dos/frozen-bid-prices/`](../../to-dos/frozen-bid-prices/README.md), landed by PR #3225 with the read-only proof against prod). Owner's report: *"updating prices is affecting new bids — when you update a price in the pricebook it is retroactively pricing bids that have already been submitted."*

## Cause

- A bid is meant to price from a frozen **copy** of a book (`clone_price_book_version_to_bid`; `price_book_versions.bid_id` = the bid). Until someone picked a book from the toolbar chip, pressed *Set up pricing*, or took the v2.2444 *Use $X on this bid* door, no copy existed: `deriveActivePricingId` fell through to a shared template (the viewer's default, or the template already holding the bid's rows — v2.2720), and **every write keyed to that template id with no ownership check** — `savePricingAssignment`, `writeUnitPriceOverrideRow` (typed prices, the solver's Apply, the margin brush), `fillMatchingBookEntries`, the scenario copies, and *+ Add "…" to the book* from a row search.
- None of the three copy-taking doors is on the path *New Bid → Counts → Labor → Pricing → assign*, so a bid priced that way stayed on the template for life. BP483 (created 2026-09-09, six days after the v2.2720 backfill) had 42 rows on the shared Default and no copy; the backfill had frozen the 188 older ones at *that day's* book, which is the BP315 drift the owner saw ($379,895.70 sent, $385,506.07 today).

## What shipped

- **Kernel** [`pricingWriteTarget.ts`](../../src/lib/bids/pricingWriteTarget.ts) — `resolvePricingWriteTarget({ selectedPricingVersionId, bidPricings, templates })` → `own` (one of the bid's copies) · `shared` (a template: write, then freeze) · `robot` (the twin write fence lives on the robot template — never clone, as the backfill skipped them) · `unknown` (templates not loaded yet, a deleted book — leave alone) · `none`. 7 tests.
- **The guard** `freezeSharedPricingAfterWrite()` in [`BidsPricingTab.tsx`](../../src/components/bids/BidsPricingTab.tsx), awaited after every write keyed to `selectedPricingVersionId` (11 sites: assign / remove an entry, the single-row price, the margin brush and its undo, the solver's Apply, the typed price, *Fill N matching from book*, *copy prices from …*, and an entry added into the active pricing from a row search). When the target is `shared`, it clones the template into the bid through the existing `cloneTemplateIntoBidAndActivate` — the RPC copies the entries **and carries the bid's template-keyed assignments and custom prices onto the copy with the entry ids remapped** — stamps `bid_version_id` (null on an unsplit bid, the same as the toolbar clone), points `bids.selected_price_book_version_id` at the copy, reloads, and toasts *"Took this bid's own copy of WENDI — edits to the shared book won't reach it."* A ref keeps it to one clone at a time. The write itself is unchanged — it lands where it always did, and the clone is what moves it — so a bid that already owns a copy sees no new query.
- **The drawer caption** now has two truths instead of one claim: on a copy, *"its own copy taken when it was first priced"* (was *"taken when the bid started"*, which was never how it worked); on a template, *"This bid has no copy yet — it shows Default as it stands today; the first price you assign takes this bid's own copy, and book edits stop reaching it."* The v2.2444 offer banner's wording moved the same way.
- **Help guide** `price-a-bid-with-the-workbench.md`: "Price from the book" says the first price freezes the bid; the drawer bullet says when the copy is taken and what *no copy yet* means.

## Left alone, on purpose

- The template-keyed rows written before the freeze stay behind, inert (the copy's rows are what the grid reads; `pickLegacyDataTemplateId` is only consulted on a bid with no copies). The v2.2720 backfill left its originals the same way; deleting them would show up in Recently deleted as a burst.
- **BP483 and the seven robot/twin bids** in the to-do's list are data, not code: BP483 takes its copy the next time anyone prices a row on it, or sooner by re-running `scripts/backfill-legacy-template-pricing.sql` (idempotent, skips robot templates) — the owner's call, see the to-do. The 90 bids the backfill froze at the Sept 3 book cannot be rebuilt (no entry history); PR 2 of the to-do (the sent-vs-today line) is the honest substitute.
- PR 3 (lock pricing after send) waits on the owner.

## Verified (worktree dev server as Robert, prod data, 2026-09-15)

A throwaway BP487 (two count rows, a cost estimate, no copy) opened on the shared WENDI. Assigning WC from the dropdown: one `price_book_versions` row for the bid (`name = 'WENDI'`, `source_version_id` = the WENDI template, `bid_version_id` null), the bid's pointer at it, the assignment on the copy with the remapped entry (and the inert original on the template). Typing $500 on LAV then wrote a custom price keyed to the copy with no second clone. BP483's drawer reads the *no copy yet* caption (nothing written there). BP487 was deleted afterwards. Not exercised: editing the shared WENDI book to watch the copy hold — that is the same mechanism every existing copy already relies on, and it would have changed a real book.
