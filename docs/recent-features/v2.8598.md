# v2.8598 — When the app was busy renewing your sign-in: plain words and a Retry (2026-11-25)

Punch list #406, from the simulator's fourth sitting on 2026-11-25, on the live site under heavy load. Client only. No migration, no edge function.

**Seen.**

1. Landing in View as a ZZ Test person, on Settings: the page read one red line and nothing else, *AbortError: Lock was stolen by another request*. It stood for a minute, with no press.
2. On the tally, a read of a job's boxes failed with the plain words, *The app was busy renewing your sign-in, so this did not load. Try again.* No **Retry** was offered.

**Part 1, Settings.** Three reads in `Settings.tsx` set the failure's raw `message`: the person's own row, the team list and the daily goals. With no role read yet, the page drew that message as its whole body. supabase-js writes a thrown error as *name: message*, which is the line seen.

- The three reads now say their failure through `formatErrorMessage`, which already turns a stolen lock into the plain words.
- The first read's failure is kept as a recovery failure (`recoveryFailureFromError`) and drawn on `OfflineRetryPanel` with `idempotent`. **Retry** clears it and runs `loadData` again.

**Part 2, the retry panel.** `isRetryableError` says a request whose sign-in lock was stolen is safe to send again: it was never sent. But `errorKindOf` classes it `unknown`, and the panel offered **Retry** for the network kind alone. So every screen on the panel drew the lock's words with nothing to press.

- `OfflineRecoveryLastError` has a new mark, `neverSent`. `recoveryFailureFromError` sets it from `isAuthLockStolenError`. The kind stays what `errorKindOf` says, since other callers read that kind for other things.
- `offlineRecoveryState` offers **Retry** for a failure marked `neverSent`, with the failure's own words and no offline copy.

**Not built: the read that runs again by itself.** The brief's pick had the panel read again once, unasked. The lock's words draw only after the caller's own retries have run out (`AUTH_LOCK_ERROR_MESSAGE`'s own comment). And a read that clears its error as it starts would give the panel a fresh failure each time, so *once* would loop on a lock held for a minute. The press is enough, and it is the person's.

**Tests.** The state kernel: a never-sent failure gets its Retry online and off, read and write, and never runs by itself. `recoveryFailureFromError`: a stolen lock as a result error and as a thrown one, a caller's own words, and three failures that are not marked. The panel's smoke, with the failure built as the tally builds it. A new smoke of Settings: the first read fails on the lock, the plain words and **Retry** draw, the raw words do not, and the press reads the row again. That one fails on main.

**Not in this PR.** A smoke on the tally itself: its test file is changed by the open PR for v2.8597, on the same lines. Why the lock is held so long on these walks was not read.
