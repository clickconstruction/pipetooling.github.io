# v2.6318 — Postgres logs from the terminal work again on Supabase’s new logs endpoint (2026-11-01)

The freeze runbook's Step 3 sends people to `scripts/pg-logs.sh` when no Supabase MCP is connected, and the script called the Management API's `analytics/endpoints/logs.all`, which Supabase removed. The way to its replacement was worked out by hand on 2026-11-01 while checking punch list #230's live edge function; this moves the script onto it. A script and two runbook lines, no migration, no edge function, no screen. The script only reads: one `GET`.

- **The endpoint.** `GET https://api.supabase.com/v1/projects/<ref>/analytics/endpoints/logs` with `sql`, `iso_timestamp_start` and `iso_timestamp_end`, authorised by `SUPABASE_MGMT_TOKEN` as before. The SQL is ClickHouse over one `logs` table that holds every service's lines. `select *` is refused (*restricted wildcard*), so the script names `timestamp` (ISO text, UTC), `severity_text` and `event_message`. Arguments and output are what they were: `<iso_start> <iso_end> [regex] [limit]`, `rows: N` on stderr, then `YYYY-MM-DD HH:MM:SS SEVERITY message` oldest first, one line per row. The severity column is `severity_text`, which on a Postgres line is the server's own `error_severity` (LOG, ERROR and FATAL seen in a day), where other sources say INFO.
- **Which `source` marks Postgres lines: `postgres_logs`, and only that one.** `select distinct source` over seven daily windows (2026-10-26 to 2026-11-01) gave the same eleven every day: `auth_audit_logs`, `auth_logs`, `edge_logs`, `function_edge_logs`, `function_logs`, `pgbouncer_logs`, `postgres_logs`, `postgrest_logs`, `realtime_logs`, `storage_logs`, `supavisor_logs`. Counting lines that only the server writes (`checkpoint starting|complete`, `database system`, `automatic recovery`, `connection received|authorized`, `disconnection:`) over 24 hours: 573 lines, all `postgres_logs`. Four more phrases (`still waiting`, `canceling statement`, `terminating connection`, `idle-in-transaction`) turned up 4 lines in `postgrest_logs` besides the server's own, PostgREST relaying a database error, so the script filters `source = 'postgres_logs'` and not on words. The poolers (`pgbouncer_logs`, `supavisor_logs`) are their own sources.
- **What the endpoint cuts without saying**, each found by asking and each now a guard in the script:
  - **24 hours from `iso_timestamp_start`.** A seven-day request answered with the first day only (the earliest and latest line were 24 hours apart), no error. The script refuses a longer window before any call. The Supabase MCP's `query_logs` says the same: the API caps the range at 24 hours.
  - **1000 rows.** A limit of 20000 over a window holding more than 5000 lines returned 1000. The script refuses a limit over 1000, and when the rows reach the limit it says older matches are cut.
  - **10 calls a minute** (`x-ratelimit-limit: 10`, reset 60). Past it the body is `{"message":"ThrottlerException: Too Many Requests"}` with HTTP 429, and a body with no `result` used to read as `rows: 0`. Any body without `result` is now `ERROR: <its words>` on stderr with exit 1, and the rate limit adds *10 calls a minute: wait a minute and retry*.
  - **Times must end in `Z`.** `+00:00` and `-06:00` get *Invalid ISO datetime*, so the script says so up front instead of passing that on.
  - **Backslashes are read twice.** `'\d'` reaches the regex as `d` (`wrote \d+ buffers` matched nothing while `[0-9]+` matched), and `'\\d'` does too; only four backslashes get through. Escaping to match that would break the day Supabase fixes it, so the regex goes in as `unhex('<hex>')`: `\d`, `\w`, `\b`, quotes and `(?i)` arrive as typed. The dialect is RE2 either way (ClickHouse `match`).
- **Also fixed**: a `.env.local` with no `SUPABASE_MGMT_TOKEN` line ended the script silently with status 1 (`grep` failed under `set -e`); it now says the token is missing and exits 2.
- **Real runs against prod, read-only, counts only** (project `yewfzhbofbbyvkvtaatw`, 2026-11-01 evening): a 30-minute window with the default regex and limit 1000 printed `rows: 464`, 464 well-formed lines in ascending time order, severity column LOG 462 and ERROR 2. A 24-hour window with limit 1000 printed 1000 lines (LOG 952, ERROR 48) and the limit note. The runbook's example regex over two hours printed `rows: 0`, exit 0. A 25-hour window stopped with the 24-hour line and exit 2, before any call. Differential checks over one fixed window agreed: `(?i)checkpoint` and `(?i)CHECKPOINT` 12 lines each, `checkpoint (starting|complete): \w+` 12, `checkpoint complete`, `wrote \d+ buffers` and `wrote [0-9]+ buffers` 6 each.
- **Runbook**: Step 3's *No MCP?* note and the 2026-09-07 stall entry's *Mgmt logs endpoint* line, both amended in place (the entry keeps `logs.all` as the name of what was flaky that night and says it has been replaced); `last_updated` moves to 2026-11-01. The script's header comment holds the endpoint's rules.
- **Not changed**: the runbook's next paragraph, `.claude/skills/db-freeze/SKILL.md`, `docs/runbooks/SUPABASE_INCIDENT_RUNBOOK.md` and `docs/PROJECT_DOCUMENTATION.md` still name the MCP tool `get_logs`, which the Supabase MCP now lists as `query_logs`; each needs the MCP connected to check what it returns before the words change.
- **Tests**: `src/lib/dbFreeze/pgLogsScript.run.test.ts` runs the script against a stub `curl` (23 cases): the call it makes and the order of its output, the regex as hex, the token from `.env.local`, every refusal before any call (window over 24 hours, end before start, offset or zoneless times, limit over 1000 or not a number) and the three that pass (exactly 24 hours, 1000, leading zeros), the limit note, and each kind of refused or empty answer. Breaking the 24-hour guard, the hex regex, the `grep` fix or the `result` check turns it red.
