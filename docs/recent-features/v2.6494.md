# v2.6494 — A check sent to Dispatch closes itself once the check is settled (punch list #245, PR 2a) (2026-11-04)

Punch list #245 (`to-dos/stage-check-to-dispatch/README.md`), the first half of PR 2, *the context window and the loop back*, built as a short train of two. This half is the self-close the card named with PR 1 (v2.6360): a check the crew sent to Dispatch is settled on the sheet three ways, and the request should close with a note that says how, so nobody closes by hand what the row already settled and the inbox never holds a row the crew answered. One migration, no client change, no edge function. PR 2b brings the context window on the inbox row, Reply, Close, the reply drawn under the crew's row, the push on a reply and the guides.

## What changed

- **Migration `20261104170000_stage_check_self_close.sql`** (`docs/migrations/20261104170000_stage_check_self_close.md`): three `AFTER` triggers over PR 1's two columns, each a `SECURITY DEFINER` function with `search_path` pinned since the crew cannot update `dispatch_requests`, all three sharing one close, `stage_check_close_settled`, callable by nobody but them.
  - **An answer** (`stage_checklist_answers`, after an insert or an update of `pick` or `answered_at` with a pick on the row): *Answered on the sheet by Luis Ortega · Yes*, closed in the answerer's name. A note saved or a photo attached before the pick settles nothing; a pick pressed again after a close finds nothing open.
  - **A skip** (`stage_checklist_skips`, after a live skip): *Skipped on this job by Sal Super: the hub is not poured yet*.
  - **A take off** (`stage_checklist_templates`, after `retired_at` is set): a job item closes its own stage's request, *Taken off by Sal Super*; a company question closes the request on every stage, *Taken off the company's list by Dee Dev*, in the Settings editor's name since the row names nobody.
  - **A promote** says so: `promote_stage_checklist_item` is restated with two lines that leave *Added to the company's list* for the retire trigger through a transaction-local setting, so a request open on a job item the office promotes closes reading *Added to the company's list by Dee Dev*, not as a take off.
- **The guard trigger** `dispatch_requests_guard_update` (baseline) admits the close unchanged: it holds the content columns and leaves `status` and the `closed_*` columns alone. No policy changes; the sender still cannot close their own by hand.
- **The SQL bed** `npm run test:pg:stage-check-self-close` (`scripts/pgtest-stage-check-self-close.sh`, `supabase/tests/stage_check_self_close/20_scenario.sql`, in `scripts/sql-beds.txt`): the migration twice, then every settle as each user under RLS: a note alone leaves the request open, the crew's own update of the request reaches no row while their answer closes it in their name, a second press after the close changes nothing and the content stands as written, a new send on the settled check is allowed and the skip closes it with the reason, the take off and the company retire each close theirs and nothing else, the promote says so and a later take off reads no stale note, a photo alone settles nothing, Dispatch's own answer on the sheet closes in their name, and a plain request and a request on another check stay open throughout, and a pick already there before the send settles it when pressed again.

## Decisions

- **A trigger, not a client write.** The crew answers under `can_report_stage_progress` and may not touch `dispatch_requests`; a close the sheet wrote would need a widened policy or an RPC, and would miss an answer written anywhere else (the Documents tab, the Pipeline sheet, a report photo path that later gains a pick). The table is the one place every settle passes.
- **`answered_at` moving counts, not only the pick changing.** The crew may have answered Yes before sending (*the pick so far* rides on the request), and Dispatch's reply may be *press Yes again*; `saveAnswerPick` writes `answered_at` on every press, so a re-press settles it. A note save and a photo attach leave `answered_at` alone and settle nothing.
- **A company question taken off closes every stage's request on it.** The check is gone from every sheet, so every request on it is moot; the note says *the company's list* so Dispatch reads why their row closed on a job they did not touch.
- **The closer is the settler.** `closed_by_user_id` is the answerer, the skipper or the retirer, so the inbox's closed block reads their name, and `notify-dispatch-request`'s close push (PR 2b fires it from the sheet) already allows the row's closer to send it.
- **The push follows the merge at any time.** Nothing in the client names a new object; until the push a settled check leaves its request open for Dispatch to close by hand, as PR 1 shipped.

## Test

The bed ran on the local Postgres 15 with the walk-kit's stand-ins (`supabase/tests/walk_kit/00_local_extras.sql`, the pgvector stand-in from the combine-rows bed) over every migration (1107 files), the migration a second time, then the scenario: 49 ok, PASSED. Four mutants each failed on the check that guards them: the answer trigger ignoring `answered_at` (*the same pick pressed again settles it*), the retire trigger ignoring the promote's note (*closed as added, not taken off*), the skip trigger never closing (*closed with the reason*), and the close ignoring the stage (*job B's request on the same question stays open*). Docker was not reachable on this machine; CI runs the same bed on the Supabase image from `scripts/sql-beds.txt`. `bash scripts/check-migrations.sh`, `npx vitest run src/lib/releaseNotes.test.ts`.

## Push

From a checkout at main after the merge: `supabase db push` (`20261104170000_stage_check_self_close.sql`), then `npm run check:migration-drift`. No types change (no new table or column) and no edge function.
