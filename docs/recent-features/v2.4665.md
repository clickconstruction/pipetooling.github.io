# v2.4665 — Card charges carry the purchase time (2026-10-06)

Migration `20261006061356_card_charges_window_purchased_at` (`docs/migrations/20261006061356_card_charges_window_purchased_at.md`). Punch list **#72** (`to-dos/tally-transactions-refresh.md`), for the Tally team queue, whose history read is #52's `list_card_charges_window`.

## Why

Mercury dates a card charge twice: `createdAt`, when the card was used, and `postedAt`, when the charge settled, a median 8 hours later and on another company day for 40% of charges. The Tally team queue keys a holder's day on the purchase, so its store runs and same-day chips need the purchase time from the read.

## The change

- **The read** returns `purchased_at` after `posted_at`: `raw ->> 'createdAt'`, cast only when it is shaped as an ISO timestamp and `pg_input_is_valid` says the cast would succeed, so a missing or stray value reads `NULL` and never fails the read. It is not named `created_at`, which on a row of this read would be taken for the table's own insert time. `RETURNS TABLE` gains a column, so both functions are dropped and created again in the one migration; their bodies are otherwise prod's, and the grants and comments are re-issued.
- **The window is unchanged**: it still filters and orders on `posted_at`, so People → Spending and Review's fuel on no job read the same charges.
- **The client**: `CardChargeWindowRow.purchasedAt` (`lib/banking/cardChargesWindow.ts`), null until the push and wherever Mercury sent none.

## Verified

- `cardChargesWindow.test.ts` (+6; the client-row check moved to the newest migration): the drops before the creates, lock timeout first; both column lists equal at 23 with `purchased_at` after `posted_at`; the client row type names every column of the newest migration; `purchased_at` comes from `raw` behind both guards, never `t.created_at`, and the window still keys on `posted_at`; the bodies equal prod's but for `purchased_at` (a one-word change to the filter fails it); grants and comments; the mapper reads the column, and null from a server without it.
- **A test bed**, `npm run test:pg:card-charges-window` (new): the three card-charges migrations as they ship, this one twice, then scenarios on a throwaway Postgres. It covers the shape and grants, the purchase time beside the posting day, an offset `createdAt`, none, `yesterday`, a day that does not exist, hour 24 and second 60 (the client refuses both, so the server does too), an ACH, a charge posted after the window, a duplicate, the payroll rule for each role, and a field login refused. Passed on Postgres 15.14 with the stand-in `pg_input_is_valid`. With the validity check removed, the bed fails on the `2026-02-30` row, the read itself erroring.
- Prod data, read-only as the owner: 13,775 of 13,797 transactions carry an ISO `createdAt`, 22 carry none (none since July 2026), none carries anything else.
- eslint; typecheck; `npm test` in full.

Waits for the push, after merge. Either order is safe: old clients ignore the column.
