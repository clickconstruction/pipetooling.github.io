# v2.6798 — Delete for a row made by mistake: the start date no longer holds it (2026-11-09)

The first live press of v2.6789's *Delete…* (PR #7461, walked on prod right after its push) answered *ZZ Test Hire A cannot be deleted: has a row in employment stints*. `people_stints_follow_dates` (`20261103203000`, v2.6481) writes an `employment_stints` row from the People record's own `start_date` / `end_date`, so every hire with a start date has one from the moment it is made, and the key scan in `delete_fresh_person` counted it as a hold.

## What changed

- **Migration `20261109140000_delete_fresh_person_stints.sql`**: `delete_fresh_person` replaced in place (same signature, grants and answer shape). The scan passes over `employment_stints.person_id` as it passes over the record's own `people.account_user_id`: the stint is the record's mirror, nothing else writes the table, and its key is `ON DELETE CASCADE`, so it goes with the record and is not named in `removed`. Every other key into `users(id)` or `people(id)` counts as before.
- Bed: `70_delete_fresh_person.sql` gains the stint table and D8; the kernel's hold words know `employment_stints` for any older function body.

## Release order

Merge, then `supabase db push` right after (`check:calls-ahead` marks the replaced function). Until the push, Delete on a hire with a start date keeps answering the stint as a hold and offering Archive; nothing breaks.
