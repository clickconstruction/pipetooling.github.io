# v2.7072 — Materials on site: the groundwork for stickers printed before their boxes (2026-11-12)

Punch list #329, PR 1 of 6. Grace asked on 2026-11-12 for stickers printed ahead of the boxes: print a run of 200, stick one on each box on site, say afterwards what it is, add boxes with no office step, and rename a box by scanning it. She took all seven of the card's calls as recommended (`to-dos/stickers-before-boxes/`). This PR is the sticker itself. It has one plain page and no press: no screen prints a run or places a sticker until PRs 2 and 3.

## Why a label could not come first

A label's code is `job_containers.code`, a generated column cut from the box's own row id. No row, no code. So a sticker is now its own row with its own code, cut from its own id by the same rule, and it points at a box or at nothing yet. `job_containers.code` is untouched, and every label printed so far keeps opening its box.

## What changed

- **The tables** (`20261113020000_box_stickers.sql`, [`docs/migrations/20261113020000_box_stickers.md`](../migrations/20261113020000_box_stickers.md)):
  - `sticker_runs`: a run printed at once. The job its new boxes go on, how many, the first and last number, copies of each, who printed and when.
  - `box_stickers`: one sticker. Its run, its `number` (one company-wide count, printed `0147`), its `code`, the box it is on (null while blank), who put it there and when, and `lost_at`.
  - `box_sticker_events`, insert only: placed, moved, taken off, lost, with the box it left and the box it went to. **Inserting a row is the act.** The row is judged by the caller's own RLS, and a trigger then moves the sticker. No client updates `box_stickers`.
  - `job_container_names`, insert only: a box's old name, its new name, who and when, written by a trigger when `job_containers.label` changes. The phone, the office, the dev seat and a job combine are all covered at once.
- **The functions**: `mint_sticker_run` (a run and its stickers in one call), `sticker_by_code` (the little a scan needs before it knows the job), `place_sticker` (a blank sticker onto a known box, or onto a new box made in the same transaction, named by the sticker's number when no name is typed). `place_sticker` and `mint_sticker_run` are `SECURITY INVOKER`: `on_site_can_touch_job` reads the ledger under the caller's own RLS, and inside a definer it would say yes to every job.
- **One code, one thing**: a run's mint cuts a new id for any code a box or a sticker already carries, and a new box whose code a sticker holds is refused. A sticker's code is read first everywhere.
- **The kernel** (`src/lib/materials/stickers.ts`), pure, 28 tests: `stickerNumberWords` (`0147`, five digits past 9999), `stickerRangeWords` (*0101 to 0300*), `stickerRunCounts` and `unusedStickersWords` (*96 stickers not used yet, 0205 to 0300*), `placingVerdict` (blank, *Marcus put 0147 on R76 a minute ago.*, lost, *This sticker was printed for Juniper Ridge. Use it here?*), and `codeLookup`, the verdict of the one resolver.
- **One resolver** (`resolveBoxCode` in `onSiteStore.ts`; `fetchContainerByCode` and `findContainerByCode` answer through it): a sticker's code and a box's own are asked in one round trip, the sticker first. A label never depends on the sticker read: when that read fails and a box carries the code, the box opens.
- **Signed in** (`src/pages/BoxCode.tsx`): a sticker on a box goes to that box on the On site tab, as a label does. A blank one reads *Sticker 0147 is not on a box yet*. A lost one, one on a retired box and one on a box of a job the reader is not on each say so.
- **Signed out** (`box-read`, `_shared/boxPage.ts`, `BoxPublicPage.tsx`): a sticker on a box answers that box's page as today, with *Sticker 0147* beside the code. A blank one answers 404 `sticker_blank` with its number and nothing else, and the page reads *Sticker 0147 is not on a box yet. Sign in to say what it is.* A lost one answers 410 `sticker_lost`. A build cached from before this reads those as *not a box on any job* and *a label that can come off*, which are both true of them.

## Who

- A sticker on a box follows its box's job through `on_site_can_touch_job`, as the box does.
- A blank sticker is read by whoever may touch the job its run was printed for. Nobody else lists one, so nobody collects codes ahead of their boxes. An orphaned run, its job deleted, is the office's.
- Whoever holds a sticker's code reads what `sticker_by_code` answers. The code is the capability, as it is for a label signed out.
- A run is printed by the office, a primary or a superintendent, on a job they can reach.
- Placing is open to whoever may touch the box's job. A training account and a digital twin write nothing.

## Checked on a database

Docker was not running, so the repo's SQL beds could not run here. The whole migration was applied three times to a throwaway local Postgres 15 with stub tables (the third time over the scenario's rows) and walked through 117 checks: every function, every refusal in its words, every direct write a client might try, and the four fences on each new table. Two races were run with two real sessions: two people placing one blank sticker at once (one wins, the other reads who and when, and the loser's new box is undone), and two runs printed at once (two unbroken blocks). The stub is not the app's schema, Postgres 15 is not the app's 17, so this proves the SQL's logic and not its fit. The dry run at the push still matters.

Nothing can be minted on prod before the push, and no screen mints after it, so the blank sticker's page is proved by the render tests and that run, not by a live walk.

## What a later PR can stand on

- **PR 2, print a run**: `mint_sticker_run(job, count, copies)` answers `{ run, stickers: [{ id, number, code }] }` in number order. A sticker's code goes through `labels.ts` as a box's does (`dashedCode`, the QR's address). A run and its stickers are plain reads under RLS. The office moves a run's unused stickers to another job by changing `sticker_runs.job_id`, the one column a client may update.
- **PR 3, the first scan**: `resolveBoxCode` answers `blank` with the sticker, `placingVerdict` words the sheet, `place_sticker` places. The same placing sent twice answers ok, so a phone that lost its signal may send again.
- **PR 4, change it afterwards**: a rename is an update of `job_containers.label`, and the history is already kept. Moved, taken off and lost are each one `box_sticker_events` row, and the table's trigger already holds their rules.

## Left

- A whole-job move or combine does not carry a run's job. `on_site_carry_job` moves the boxes, so every placed sticker follows. A run printed for the old job keeps naming it, or loses its job when that job is deleted, until the office changes it.
- No guide yet: there is no flow to follow until PR 2.

## Deploy

One migration and one function. The client calls `sticker_by_code`, which only the migration makes, so this is a *push right after the merge*: `supabase db push` from `main` after a dry run, then `supabase functions deploy box-read`, then `npm run check:edge-drift` and `npm run check:migration-drift`. Until the push a label still opens its box, since the resolver never lets the sticker read stand in a label's way. The types follow the push as their own small PR.
