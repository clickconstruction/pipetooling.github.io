# v2.2889 — Bank-label rule matches approve themselves server-side (org switch); a Needs You card counts the true exceptions (2026-09-05)

Journey-map Tier-2 #27 ("349 bank-label suggestions (~$139K "Unlabeled", oldest 16 d) wait for nobody", C6 — J33-F2/N3). The suggestion machine was always server-side (`mercury-webhook` mints a pending `mercury_accounting_label_suggestions` row on every delivery a rule matches; Apply rules mints in bulk), but the only approver was the v2.581 **Approve by default** checkbox — a per-user browser effect that ran only while that user had Banking → Accounting mounted. The approving now happens where the suggestion is minted, behind an org switch, and what stays pending is surfaced as a Needs You item.

## 1. The org switch and the server-side writer

- **Setting**: `app_settings.accounting_label_auto_approve_rule_matches` (`value_text` `'true'` | `'false'`; seeded `'false'` — ships OFF). Constant `ACCOUNTING_LABEL_AUTO_APPROVE_SETTING_KEY` in the kernel.
- **Kernel** `src/lib/accountingLabelAutoApprove.ts` + Deno twin `supabase/functions/_shared/accountingLabelAutoApprove.ts` (no imports, byte-for-byte the same behaviour): `shouldAutoApproveSuggestion(suggestion, rule, settings)` → `{ approve, reason }`, checks in the SQL writer's order — switch on → status pending → rule present + enabled → no hand-set assignment → not Internal Transfers on a transaction with job splits. `parseAutoApproveSettingValue` (only the literal `true` turns it on). Tests: `accountingLabelAutoApprove.test.ts` (gate order, each skip reason) and `accountingLabelAutoApproveSharedParity.test.ts` (the full 800-case input lattice must agree between the app copy and the edge copy).
- **Writer** `auto_approve_pending_accounting_label_suggestions(p_tx_ids uuid[])` (SECURITY DEFINER, service_role + internal callers only; migration `20260905180000`): re-checks every gate in SQL, then performs **exactly** the three writes `bulk_approve_accounting_label_suggestions` performs — `mercury_transaction_drag_sort_assignments` upsert, rule person/user attribution with `ON CONFLICT DO NOTHING` (hand-set wins), suggestion `status='approved'` / `final_label_id` / `resolved_at` — with **`resolved_by = NULL`** meaning "by the rule" (column comment added). Returns rows approved.
- **Two minting paths call it**:
  - `bulk_insert_accounting_label_suggestions` (client Apply rules / Apply rules by default) now ends with `PERFORM auto_approve_pending_accounting_label_suggestions(<tx ids in this payload>)` — return value is still rows *inserted* (the toast reads it; the toast copy says "approves itself" when the switch is on).
  - `mercury-webhook` — after `insert_accounting_label_suggestion_service` reports 1 row inserted, `autoApproveIfSwitchedOn` reads the setting (one read; returns immediately while it is off), evaluates the kernel with the suggested label's `default_key` and the tx's job-split presence, and calls the writer via RPC. Best-effort: a failure leaves the row pending, never fails the webhook.
- **No backlog sweep**: the migration mutates no suggestion rows. Everything pending on deploy day stays pending until someone clicks Approve all (the Needs You card points at it).

## 2. The Accounting tab

- The per-user **Approve by default** checkbox is gone: `readAccountingApproveByDefault` / `writeAccountingApproveByDefault`, the `accounting_approve_by_default` pref column read/write, the `approveByDefault` / `onApproveByDefaultChange` props, and the `accountingApproveByDefaultAutoTrigger.ts` kernel + test are all removed. (The `banking_user_prefs.accounting_approve_by_default` column stays on the table, unread.)
- In its place, the same toolbar spot shows **Rule matches approve themselves** `(org-wide · on/off)` — the org switch, read by everyone on the tab, flippable by `dev` and `master_technician` (new RLS policy `master_or_dev_update_accounting_label_auto_approve` lets a master UPDATE that one key; devs already had table-wide manage). New prop `myRole` on `BankingMercuryAccountingTabProps` replaces the two removed ones. The Approvals intro copy explains that what waits there is the exception list when the switch is on.
- `conflictSuggestionIds` (the Internal Transfers × job-splits badge/skip set) is now decided by the shared kernel, so the client's "conflict" is by definition what the server left pending.
- **Telemetry** `label_suggestion_approved{by: rule|user}`: client approvals (`handleApprove`, `approvePendingItems`) call `recordNavClick(userId, role, 'label_suggestion_approved', '#by:user[:N]')`; server approvals are `resolved_by IS NULL` on the row plus a structured `mercury-webhook` log line `{ event: 'label_suggestion_approved', by: 'rule', count, tx, rule }` (and `label_suggestion_left_pending` with the skip reason). The switch itself logs `label_auto_approve_switch` `#on` / `#off`.

## 3. Needs You: `label-approvals` (Dashboard + Quickfill twin)

- **RPC** `count_pending_accounting_label_suggestions(p_min_age_days int default 3)` → `(pending, stale, stale_amount, oldest_created_at)`; gate inside (`list_bulk_deletion_alerts` precedent): `dev` / `master_technician` / `assistant` — the roles `bulk_approve` accepts — get numbers, everyone else the zero row. `stale_amount` is Σ|amount| over the stale rows (the "Unlabeled" money).
- **Hook** `src/hooks/usePendingLabelApprovalsNudge.ts` (`LABEL_APPROVALS_MIN_AGE_DAYS = 3`; v2.2671 shape — focus refetch, zero row → null, cast precedent for the untyped RPC).
- **Kernel** `dashboardNeedsYou.ts`: new key `'label-approvals'` (rank 40 — billing accuracy, above hours approvals, below a stale tally), inputs `labelApprovalsEnabled` / `labelApprovals` / `labelApprovalsMinAgeDays`. Shows only when `stale > 0` **and** the oldest pending row is ≥ min-age — a same-week trickle never nags. Figure = stale count; detail names the money, the oldest age, and any newer rows still inside the window. Tests in `dashboardNeedsYou.test.ts`.
- Wired on `DashboardPinnedQuickRow` (office set) and `QuickfillNeedsYouSection` (the close ritual — enabled there too); action → `/banking?tab=accounting`.
