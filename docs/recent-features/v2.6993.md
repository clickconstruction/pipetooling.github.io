# v2.6993 — First look: the upload in pieces uses storage's signed address (2026-11-12)

Punch list #319, the spike (v2.6981). The first walk on the live site found that the real storage refused the page's upload in pieces: `POST /storage/v1/upload/resumable` with the link's one-file key as `x-signature` answered **403 `new row violates row-level security policy`**. The page fell back to one request, as built, and the 14 MB video still arrived. So nothing was lost, and nothing could pick up after a drop.

- **The cause.** Storage takes a signed upload in pieces at its own address, `/storage/v1/upload/resumable/sign`. The plain address reads the key as nobody's. Four requests against the live project settled it: the plain address answered 400 or 403 with or without the public key, and the signed address answered **201** with a `Location` both ways.
- **The fix.** `signedPiecesEndpoint` in `src/lib/firstLook/pieces.ts`, used by `showUsIo.ts`. The deployed build's Supabase address ends in a slash and the local one does not, so both doors (`showUsIo.ts`, `deskIo.ts`) now trim it: the live page had been asking `…supabase.co//functions/v1/first-look`, which worked and should not be relied on.
- **Proven before the merge**, from the local page against the live function and the live bucket, on a ZZ Test look: the upload was made (201), two pieces of 6,291,456 bytes landed, the signal was cut, the page read *Saved on this phone*, and with the signal back it asked storage how far it had got (12,582,912 bytes), sent the last 2,097,152 and no piece twice. A real recorded video went in one request and a text file named as a photo was refused by its first bytes.

No migration and no function deploy. The spike's five answers are on the card (`to-dos/show-us-the-problem/README.md`).
