# v2.4964 — My Time day editor: a reject and its payroll resync are one transaction (2026-10-08)

One migration (`20261009170000_reject_clock_session.sql`, **not pushed yet** — it waits for the next migration push) and the client that uses it, falling back until then. No edge function. Punch list **#46** row 10: the gap v2.4960's tests found and pinned, shipped apart.

## The bug

Reject session in the My Time day editor was two requests:

1. an `UPDATE` of `rejected_at` / `rejected_by` under the caller's RLS
2. `recompute_people_hours_after_session_edit`, to take an approved session's hours back out of `people_hours`

When the second failed, the session stayed rejected but payroll still counted its hours. The dialog read as if the reject had failed. If the person closed the editor instead of pressing Reject session again, the rejected row no longer showed to try again.

## The fix

- **Migration** `public.reject_clock_session(p_session_id uuid)` is `SECURITY INVOKER`, like `save_my_time_day`. It does the `UPDATE` under the caller's RLS, then `PERFORM`s the resync, in the one transaction PostgREST opens for the call, so a refused resync undoes the reject.
  - Everyone RLS lets update a row also passes the resync's actor check, so nobody who can reject today is refused.
  - One deliberate change, as `save_my_time_day` does: an `UPDATE` that changes no row (missing, or hidden by RLS) is raised. The browser's request used to succeed there with nothing written.
  - Doc: `docs/migrations/20261009170000_reject_clock_session.md`.
- **`src/lib/rejectClockSession.ts`** (new) calls `reject_clock_session` once. While the database has no such function (`PGRST202` / `42883`, until the push), it falls back to the two requests, verbatim. Any other answer is the caller's error.
- **`DashboardMyTimeDayEditorModal.tsx`**: `confirmRejectSession` calls it in place of the two requests. Everything around it is unchanged: the dialog, the refetch signal, `onLinkedSessionsUpdated`, and `onSaved` for a parent's sessions. The modal no longer imports `supabase` or `withSupabaseRetry`.

## Tests

- `rejectClockSession.test.ts` (new, 7):
  - one call and nothing else, and a refusal from it is the caller's error with no fallback
  - while the function is missing, the reject then the resync, in order, with `rejected_at` / `rejected_by`
  - in the fallback, a refused reject stops before the resync, and a failed resync comes after the reject (the gap the push closes)
  - what counts as a missing function
- `DashboardMyTimeDayEditorModal.render.test.tsx`: the pinned two-request test flips. Reject session now sends one `reject_clock_session` call and then re-reads the day; on a parent's sessions the parent refreshes; and a refusal changes nothing, the dialog saying why. A second block keeps the old two requests as the fallback while the function is missing: the order, a refused reject, and the failed resync.
- Mutations fail them:
  - falling back on any error, not only a missing function
  - never trying the one call
- The SQL bed: `supabase/tests/my_time_day_save/30_reject.sql` (new), on the save bed's stand-in schema with production's `clock_sessions` RLS, the real resync and a `rejected_by` column added as in production.
  - It checks the atomicity: a refused resync leaves the row unrejected and the hours at 4.
  - It also checks a person's own approved and pending rejects, another person refused, a team lead's reject, and the refusals.
  - A copy of the function that swallowed the resync's error failed it. The save scenario still passes.
