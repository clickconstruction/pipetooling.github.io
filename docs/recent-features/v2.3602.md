## The change

- **`get_stages_enrichment(p_job_ids uuid[]) → jsonb`** ([`docs/migrations/20260919025508_get_stages_enrichment_rpc.md`](../migrations/20260919025508_get_stages_enrichment_rpc.md)): `LANGUAGE sql STABLE SECURITY INVOKER` — one round trip returning `{ materials, fixtures, schedule_max, estimates }` keyed by job id; materials and fixtures rows as `to_jsonb(row)` in sequence order, `schedule_max = max(work_date)`, estimates as the banner candidates. Every table's RLS applies as it did to the client's own reads. Read against prod before merge: 114 jobs → the same per-table job counts as direct queries, 101 KB, 5.6 ms server-side.
- **Client** ([`fetchJobsLedgerWithDetailsForStages.ts`](../../src/lib/fetchJobsLedgerWithDetailsForStages.ts)): `fetchStagesEnrichment` calls the RPC and hands the payload to `parseStagesEnrichmentPayload` ([`lib/jobs/stagesEnrichment.ts`](../../src/lib/jobs/stagesEnrichment.ts), tested: the four maps, a timestamp trimmed to its day, a wrong shape → null). A failed call, a thrown call or a payload that is not the four maps runs `fetchStagesEnrichmentInPasses` — the v2.3600 chunked passes, kept whole — with one console line. `applyStagesEnrichment`, `pickLinkedEstimateForStagesBanner` and `mergeMaxScheduleWorkDateByJobId` are unchanged; the loader's tests pin both paths.
