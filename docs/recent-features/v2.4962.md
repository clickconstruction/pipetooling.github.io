# v2.4962 — GC mode: the schedule’s day math in one place (2026-10-08)

G-130 of the GC mode Gantt (`to-dos/gc-mode/GANTT_FEATURES.md`; its plan `to-dos/gc-mode/mockups/G-130.md`, both on branch `spike/gc-mode`). No migration and no screen change.

- **The move (commit 1).** `src/lib/gc/schedule/network.ts`, pure, holds the schedule's day math: the days (`dayNumber`, `daysBetween`, `isoOf`), the calendar (`holidaysOf`, `holidayOn`, `isWeekend`, `isWorkingDay`, `workingDays`, `holidaysIn`), the links (`lagOf`, `wouldLoop`, `waitOrder`), the spare days (`scheduleFloat`) and the pushes (`pushAfter`, `pushedAfterWords`, `PushedAfter`, with `lineOf`). They moved word for word from `schedule.ts` and `gantt.ts`. Five helpers that were private are exported (`dayNumber`, `isoOf`, `weekdayOf`, `waitOrder`, `lineOf`), so the two files can read them. `schedule.ts` and `gantt.ts` re-export every public name that moved, so no reader's import changes. `network.ts` imports neither file, so there is no loop. `to-dos/gc-mode/scripts/lift-same.cjs` with the config `g130.lift.json` (on the spike) shows every moved declaration the same as on `origin/main`, the five exported now listed as known.
- **The calendar in the spare days (commit 2).** `scheduleFloat` measures a bar with `workingDays(start, finish)`, not `daysBetween(start, finish) + 1`. The two agree for every bar that finishes on or after its start, so no number moves today. A bar that finishes before it starts now counts as no days long, as `workingDays` says for the bar. No fixture has such a bar, and the table refuses one (`gc_schedule_activities_dates_in_order`). The day a day can be off, the bars and the spare days change in this one file.
- `network.direct.test.ts`: the re-exported names are the kernel's own functions; the spare days on a chain with a side branch; a push three days out, two steps down, with work done left in place; a loop two steps down; and a bar that finishes before it starts, no days long in its spare days (6, where the old count read 7).
