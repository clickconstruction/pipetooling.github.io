# v2.8547 — Punch list: the merge queue is on the page (2026-11-24)

Punch list #444, PR 3 of four. The owner asked on 2026-11-24 to see the merge queue beside the pace of the list. The queue was already read: `ship-pace` writes one `app_settings` row (`ship_pace_v1`) every 15 minutes and Settings → How fast a change ships draws it. This change draws the same row on `/punch-list`. Client only: no function, no token, no migration.

## What changed

- **In the merge queue** (`PunchListQueue.tsx`, `#queue`) opens `/punch-list`, above the Burndown, since the queue is at most ten lines and the Burndown is long. The header says how many are in line.
- **The line.** Each change is one row with its values apart (`WorkedOutValue`): **Place** (*1st*), the title after its version, **In the queue** (*9 minutes*) and **To go** (*about 3 minutes*, or *no estimate yet* when GitHub gave none). The first ten are listed, then *and N more*. On a phone a row becomes the place and the title with the two times under the title, each led by its label.
- **The day.** Under the line: **Merged today**, **Merges an hour** (the row's last six hours of merges over six, to one decimal, since one hour swings and a whole day's average is dragged down by the night) and a column for each hour of the app calendar's day, midnight first, an hour not yet come left empty.
- **The buckets line** is the Settings tab's (`queueBucketsWords`), then a link to Settings → How fast a change ships for a role that has that tab.
- **How old the read is.** The as-of words are the Settings tab's (`paceAsOfWords`), amber past an hour, and the line stays as it stood. When a dev opens the page and the row is missing or over five minutes old (`QUEUE_FRESH_MINUTES`), the page asks `ship-pace` for one read and draws the row again: once an opening, never on a timer, and quiet when the function refuses. The read takes about twenty seconds, so the old line draws at once and the press reads *Reading GitHub…* until the new one lands. A dev also has **Read GitHub now**, with the function's answer beside it. A master reads the row as the cron left it, since the function answers a dev alone.
- **The other states.** An empty queue says *Nothing waiting on the queue.* and keeps the day. A queue the cron could not read says the Settings tab's one line. No row yet draws that tab's empty state. A lost signal draws `OfflineRetryPanel` with Retry; a refusal draws its reason alone.
- **Hide the queue** folds the block to its header, which then reads *4 in line · the next one in about 3 minutes · 6.2 merges an hour*. The device remembers (`punchListQueueOpen`).

## How it is built

`src/lib/todos/punchListQueue.ts` is the pure half: `queueRows`, `inLineCount` / `inLineWords`, `mergesAnHour`, `dayHours` (the row's 72 hours cut to today's twenty-four on the app calendar), `queueFoldedWords` (figures marked with `val`), `rowAgeMinutes` and `shouldReadOnOpen`. It imports the queue's words from `supabase/functions/_shared/shipPace.ts` and changes nothing there, so no function redeploys. The block reads through the Settings tab's own `shipPaceIo`, which the smoke fakes.
