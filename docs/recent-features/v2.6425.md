# v2.6425 — Imported clock sessions: a dev puts the days the app never recorded on the clock (2026-11-03)

The clock began on 2026-03-12. A worker's days before it live in the bank's payouts, in trip records and in the person's own word, and nothing in the app reads them: the Signed hours statement (#212) prints such a span as the worker's declaration, the Costs tab and the development scoreboard (#250) see nothing. The Gray Fox development needed its superintendent's year before the clock accounted for job by job, which is a question of rows, not of a new reader. This PR opens one door for those rows and nothing else.

## What changed

- **A third origin.** `clock_sessions.origin` admits `imported` beside `user_punch` and `salary_schedule` (migration `20261103030000_imported_clock_sessions.sql`). The insert policies still admit only `user_punch`, so no screen writes an imported row.
- **One door, devs only.** `import_clock_sessions(p_rows jsonb)` takes rows of person, job, day, in, out and a note that names the source (a bank payout, a trip in the card trail, the person's own account), writes each as an ordinary unapproved session with `origin = 'imported'`, and refuses a bad row by name and reason while the rest go in: an unknown or sample person, an unknown or billing-only job, out not after in or more than sixteen hours after it, a day that is not the clock-in's calendar day in the company's zone, an empty note.
- **Safe to run again.** One imported row a person, a day and a job (a partial unique index); a second run of the same rows inserts nothing and says how many it skipped.
- **The normal approval door.** The rows land unapproved. The typed-hours triggers record only `user_punch`, so an imported row holds nobody from approving it; a controller or dev approves it as any pending session, and the pay, the crew days, the first and last work day, the statement, the Costs tab and the scoreboard then read it as a punch.
- **Docs.** `ACCESS_CONTROL.md` (the door under the clock rules), `SALARY_CLOCK_SESSIONS.md` (the origin values), the migration page.
- **Bed.** `supabase/tests/typed_hours/50_imported_scenarios.sql`: the widened check and an unknown origin still refused, a controller refused, two rows in and the rerun skipping both, six refusals with their reasons and the good row still in, no typed entry, the importing dev's approval landing eight hours in the pay.

## Decisions

- **Rows, not a reader.** Every reader of the clock already handles a punch; the one thing missing was a way to make rows for days nobody punched. An import that looks like a punch needs no change to the statement, the Costs tab or the scoreboard.
- **The data stays out of the repo.** The function takes rows; the rows for the Gray Fox span are built from the bank, the case folder's trip ledger and the person's own word outside git, and go in from a dev seat after the push.
- **A note is required.** An imported day with no source is a guess; the door refuses it.

## Deploy

After the merge, from the main checkout: `supabase db push`; then `npm run gen-types:linked` as its own `chore(types)` PR (the function's signature). No edge function. Nothing in the client calls the function.

## Test

`npm run test:pg:typed-hours` runs the bed with the new scenarios. Live after the push: as the dev, call `import_clock_sessions` with one row twice; the first answers `inserted 1`, the second `skipped 1`; the row shows on the person's My Time day as pending; a controller approves it from People → Hours.
