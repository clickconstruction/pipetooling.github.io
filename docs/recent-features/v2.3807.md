# v2.3807 — A retired punch-list number stays retired (2026-09-24)

`to-dos/README.md` promises that a retired to-do's number is never refilled, so "#16" always means the same work — but `npm run check:todos` derived the next free number as one past the highest in the folder. When [v2.3797](./v2.3797.md) deleted `to-dos/legal-portal-lien-desk/` (#41, the highest), the checker started printing `Next free number: #41`, and the next to-do would have taken the Lien desk's handle. Scripts, one kernel and its test; no migration, no app change.

## The change

- **`nextTodoNumber(docs, assignedNumbers)`** (`src/lib/todos/todoBoard.ts`) takes one past the max over the folder *and* every number the repo remembers assigning. Two pure parsers feed it: `assignedNumbersInFragment` reads a `docs/recent-features/` fragment's "Punch list **#41**" / "punch list #34" / "to-do #27" citations (only those two phrasings, so "PR #3448" and "Journey-map Tier-2 #41" never count), and `assignedNumbersInGitLog` reads every `+number: N` / `-number: N` line of `git log --all --format= -p -- to-dos`.
- **`readAssignedNumbers(root)`** (`scripts/todos/readTodos.ts`) unions the two sources. Only `check:todos` calls it — the Vite build's `renderTodoBoardModule` never shells out to git, and it takes the numbers as an optional argument so the duplicate-number error names the same next free number the summary line does. A shallow CI checkout just contributes less history; the fragments still carry the record, and a checkout without git falls back to the fragments alone.
- The output line is unchanged (`Next free number: #42` today). `to-dos/README.md`'s Add step says where the number comes from.
- `todoBoard.test.ts`: a retired top number is not refilled; the fragment parser skips PR and journey-map numbers; the git-log parser ignores context lines and other keys.
