# v2.8215 — Bid photos: a bid's photos show on the job after the win, and on Documents → Photos (2026-11-21)

Punch list #306, PR 9 of the train, the piece the card said needed no further word. A migration (a view replaced, no table), a client change, no edge function.

## What was missing

A photo added to a bid from the Bid Board's camera showed in the bid's own window and nowhere else. Documents → Photos, the one list of every photo uploaded, did not list it. A job won from the bid did not show it either, or showed its Drive file as *Added in Drive* by file name when the job's photo folder was the bid's.

## What changed

- **The view** ([`20261121222237_uploaded_photos_bid_branch.sql`](../../supabase/migrations/20261121222237_uploaded_photos_bid_branch.sql), [its fragment](../migrations/20261121222237_uploaded_photos_bid_branch.md)): `uploaded_photos` gains a seventh branch, `source = 'bid'`, over `bid_photos`. Built on the live definition, read from prod first. A row names the bid and no job. Only a photo that stands is listed (added, not removed). A picture a text already carries is left out, so one Drive file is one row for every reader.
- **The photos kernel** ([`uploadedPhotos.ts`](../../src/lib/photos/uploadedPhotos.ts)): the `bid` source with its words (*Bid photo*, *Open the bid*), a **Bid photos** chip for the roles that can read a bid (`canSeeBidPhotos`), `bidFiledParts` so a picture the app filed reads as its caption with its sender as who, and a `bid-drive` thumbnail source. The bytes of a filed bid photo come through the `bid-photos` function, which answers whoever can read the bid ([`bidPhotoBytesIo.ts`](../../src/lib/bids/bidPhotoBytesIo.ts), moved out of `bidPhotosIo.ts` unchanged so the photo lists can use it without an import cycle).
- **The Job photos window** ([`JobPhotosWindow.tsx`](../../src/components/photos/JobPhotosWindow.tsx) over the new kernel [`jobPhotosFromBid.ts`](../../src/lib/photos/jobPhotosFromBid.ts)): the window reads the job's `bid_id`, then the view's rows for that bid (`loadJobBidPhotos`), and lays them in the grid with the job's own. Those rows are every source the view holds for the bid, so a picture texted on the bid's thread comes with them for a reader who can read the thread. A bid's tile reads **From the bid** ahead of who added it, the line under the grid counts them, the **Bid photos** chip and a search for *from the bid* show them alone. A bid's filed photo is now a known Drive file, so it is no longer drawn a second time as a hand-added tile. Its viewer names the bid and offers no **Edit the words**: a bid's photo is changed on the bid.
- **Documents → Photos** ([`DocumentsPhotosTab.tsx`](../../src/components/documents/DocumentsPhotosTab.tsx)): the chip, the row and the door, **Open the bid**, which opens the Bid Board on that bid. The Development page's Photos look reads the same view and takes the chip with it.

## Who sees a bid's photo

The view is `security_invoker`, so `bid_photos`' own policy decides: whoever can read the bid. That is the office and the estimator on every bid, and a primary on a bid they estimate, manage or made. A superintendent, a helper and a subcontractor read none, so a crew member's Job photos window is the job's own photos, as before. The branch joins no job, so it tells an estimator nothing about a job.

## Checked

- The new SELECT was run as a plain query on prod in a read-only session before the PR: it parses, its branches' types agree, and it reads the six standing photos on the ZZ Test bid. A read for one job plans without touching `bid_photos`.
- The SQL bed `bid-photos` applies the migration twice and asserts who reads a bid photo through the view; it runs in CI (Docker is another login's on the build Mac).
- Unit tests: `jobPhotosFromBid.test.ts`. Render smoke: `JobPhotosWindow.fromBid.render.test.tsx`.

## Not in it

- The Job Mode card's **Photos · N** line counts the job's own photos, not the bid's.
