# v2.6273 — The photo count badge survives a list that re-keys under its read (punch list #229, a fix to PR 3) (2026-11-01)

The live walk of punch list #229 on 2026-11-01 found it on the dev server: Jobs → Reports listed 578 cards and the ZZ Test report's card read *Stage progress: 1 photo* with no *📷 1* badge, while `loadReportPhotoCounts` answered the count in 657 ms when called by hand. No migration, no edge function.

## Cause

`useReportPhotoCounts` (v2.6256) keyed its effect on the ids joined in order and threw a read's answer away once the effect was cleaned up. The Reports tab re-ordered its rows while the first read was out, so the effect ran again, found every id already in its *asked* set, read nothing, and the abandoned read's answer never reached the state: `Map(0)` for good. Any list that re-keys inside the read's window lost every badge.

## What changed

- **`hooks/useReportPhotoCounts.ts`**: the key is the sorted set of ids, so a re-ordered list is the same list; a read's answer is kept whatever the list did meanwhile, since the counts are by id and a stale read is still true; a failed read still frees its ids for the next list.
- **`ReportPhotosStrip`**, the compact row: the Drive door's name read *Open … · in Drive in Drive*, the standing twice; it names the photo and the sender once now, with the standing in the title.
- **Test** `useReportPhotoCounts.render.test.tsx` (new, 2): the same ids re-ordered under the read keep its answer and read nothing new; a grown list reads only its new ids.
