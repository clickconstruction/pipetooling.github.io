# v2.7011 — Printing: a page waits for its pictures, so a code never prints as an empty box (2026-11-12)

The owner's helper printed a lien affidavit with its help sheet on 2026-11-12 and saved it as a PDF. Both codes on the sheet were empty boxes: *Scan for the full guide* in the corner and *Scan to record* beside the last step. Her question: should there be a code here, is this broken? It was broken.

## Why

`openHtmlPrintWindow` (`src/lib/jobsDocuments/printWindow.ts`) opens a window, writes the page into it and called `print()` in the same breath. A picture written into a new window is not loaded when the write returns, even a picture the page carries in itself as a `data:` address, which is how the help sheets draw their codes (`lienHelpGuideCode.ts`). Read in the installed Chrome on 2026-11-12, three runs out of three: at the moment of `print()` both pictures were not loaded, with no width; 0.8 seconds later both were loaded at 360 pixels. The browser prints what it has, and an unloaded picture with a size draws as an empty box.

`openHtmlWindowWhenReady` in the same file already waited for its pictures (v2.4335, a signed waiver's ink). The plain print window never did, and before the help sheets nothing it printed carried a picture that mattered.

## What changed

- **`openHtmlPrintWindow` waits for the page's pictures**, then prints. It still opens the window inside the press and still answers at once with whether the window opened. A page with no picture still loading prints in the same breath, as before, so the eighteen places that print words only behave as they did.
- **A picture that fails or never arrives does not lose the print.** A failed picture counts as settled, and the wait ends after `PRINT_PICTURE_WAIT_MS`, three seconds.
- `openHtmlWindowWhenReady` now shares the same two helpers, `picturesStillLoading` and `whenPicturesSettle`.

## How it was checked

- `printWindow.test.ts`: a page with no picture prints at once; a page with two pictures prints only after each has loaded or failed; a picture that never arrives prints at three seconds; a blocked window is reported.
- Live, on a local copy of the app signed in against the real data with every write refused: **Print for notarization** on a ready affidavit in the Lien window, in the installed Chrome, with the real window and only `print()` itself recorded. `print()` came 12 ms after the window opened, with both pictures loaded at 360 pixels, and the page drew both codes.

## Not verified

- No sheet went to a real printer and nobody has scanned a printed code with a phone. That was already open on punch list #314 and is now worth doing: every code printed before this fix may have been an empty box.
- Safari and Firefox were not run. The wait reads `img.complete` and the `load` and `error` events, which all three have.
