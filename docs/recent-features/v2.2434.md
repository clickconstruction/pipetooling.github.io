# v2.2434 — CT↔PT user bridge, Phase 1: join key + CT manage-user (2026-08-28)

First build phase of the CT↔PT user bridge (locked decisions: one-directional PT → CT,
thin secret-guarded verb bridge, uuid join key, weekly audit instead of sync machinery,
fail-soft everywhere).

**PT (this PR):**
- Migration `20260828090000_users_counttooling_user_id.sql`: `users.counttooling_user_id
  uuid NULL` — the durable join to the CountTooling auth uuid, replacing the email-string
  convention. Not a privileged column (the v2.695 column guard fires only on
  role/read_only/archived_at). Push after merge.
- `DigitalTwinsPanel`: per-twin **CT seat · linked / missing** chip on the seat-email row
  (green/amber; linked tooltip carries the CT uuid). Fail-soft cast query — the chip
  hides entirely until the migration lands, so the client ships first.

**CT (no PR train there; committed to CT main `bccdc62`, deployed 2026-08-28):**
- New edge function `manage-user` — the ONLY way CT accounts are managed now. Auth:
  `X-Bridge-Secret` vs `CT_MANAGE_USER_SECRET` (SHA-256-compared). Verbs: `create`
  (idempotent — existing email returns the existing uuid), `deactivate`/`reactivate`
  (Supabase auth ban `banned_until` — CT has no active column and we didn't invent one),
  `set_twin_flag`, `update_email`, `lookup`, `roster` (for the weekly drift audit).
  Called only by PT's `ct-bridge` (Phase 2), never a browser.
- Secret lives in PT main-checkout `.env.twin.local` (CT's repo does not gitignore
  `*.local` — never store it there); set on BOTH projects (`CT_MANAGE_USER_SECRET`, plus
  `CT_MANAGE_USER_URL` on PT for the Phase-2 proxy).
- Smoke-tested against CT prod: 403 without/with wrong secret, 400 bad verb, idempotent
  create, lookup, roster, deactivate→reactivate round-trip. Side effect: created
  twin-estimator-1's CT seat (`928dfc31-dfd8-49d9-b1cd-3f2586a8c984`, twin-flagged) —
  the seat that previously required an admin sign-in on CT.
