# v2.4072 — Bids page smoke: what Edit Bid writes is pinned (2026-09-28)

Tests only; no app code. Punch list **#51** (`to-dos/bids-edit-controller.md`), PR 2 of 5 — the guard for the three moves that take the Edit Bid controller out of `src/pages/Bids.tsx`.

## What is new

`src/pages/Bids.render.test.tsx`'s database stub now **records every write** the page sends — table, insert / update / upsert / delete, payload, `.eq()` filters — and can answer a `bids` update with no rows, which is what row security does to a write it refuses. Six new cases, *Edit Bid writes*, on one unsent bid:

- Opening it on the Edit face and closing it untouched writes nothing.
- A change saves itself after the pause: **one** update, **that field only**, on **that bid** (the debounce runs on fake timers; the page on real ones).
- Closing inside the pause saves the change first, once, then closes.
- A refused write keeps the window open with *Couldn't save your latest changes*; *Close without saving* closes it and writes nothing more.
- A required field left blank holds the save — nothing is written, not even on close.
- New Bid → *Create bid* inserts one bid, in the picked trade, and updates nothing.

Checked the other way round: five deliberate breaks of the page's Edit Bid code — the close skipping its flush, the save sending the unpruned payload, a refused write taken as saved, an invalid form saving, the write aimed at the wrong bid — were each caught by at least one case, and the page was restored.

## A quirk the cases pin as it is

On a bid with no sent date, every Edit Bid write also carries the eight sent-date stamp columns as `null` — the attestation merge answers "cleared" for an empty date, and the prune does not drop columns that are not form fields. Null over null, so no data changes, and it predates the second pass. The cases assert it exactly so no move in #51 changes it by accident; it is written on the #51 card to be dropped in its own PR afterwards.
