# v2.7565 — Lien desk: a record on a mailed notice no longer makes its signature read as gone (2026-11-17)

Punch list #370, found on 2026-11-16 while building *Sign it again* (v2.7502) and the take-back that clears a signature (v2.7503). The owner's answer then: *"add the promise to the punchlist, we'll have someone else build it later"*. Built the next day, before any screen shows a mailed notice's signature. The card is retired with this.

## What was wrong

A leader's signature is tied to a notice by `signed_fields_hash`, the hash of the notice's `fields` at signing. The hash covered the whole of `fields`. The desk also keeps four records of its own there, each written on a notice that has already been **mailed**:

- `fields.promise` (`notePromiseOnNotice`, `withPromiseRecord`),
- `fields.ownerCall` (`noteOwnerCall`),
- `fields.gcAuthorizedDirectPay` (`noteGcAuthorizedDirectPay`),
- `fields.courtesy` (`writeCourtesyRecord`, `withCourtesyRecord`).

None of them changes what the mailed paper said. Each changed the hash, so a mailed, signed notice that gained one read as unsigned from then on, with its ten signature columns still on the row. Every reader of a signature looks only at an approved notice today, so the stale hash had no symptom. It was a trap for the first screen that shows a mailed notice's signature.

## What changed

- **`supabase/functions/_shared/lienFieldsHash.ts`**: `lienFieldsHash` leaves the four record keys out before it hashes, at the top level of `fields` only. The list is `LIEN_FIELDS_RECORD_KEYS`. It is a list of record keys, never a list of printed keys: a key it does not name stays inside the hash, so a new field on the paper still voids a signature. The same word deeper in the draft (`notice.promise`) is part of the paper and stays covered. A value that is not a plain object hashes as it did.
- **One form of the hash.** A draft that holds none of the four keys hashes exactly as before, so no standing signature moves. Read on production before the change, read only: every row with `signed_at` set, and none holds any of the four keys. So the old whole-`fields` hash is not honoured beside the new one.
- **`src/lib/jobs/lienNoticeSignature.ts`**: a comment only. Its mirror under `supabase/functions/_shared/gcKernels/` is regenerated (`npm run gen:edge-kernels`).

## Not changed

- **The three lines that come with a cleared signature.** `runTakenBack`, `signatureCleared` and `redrawn` stay inside the hash on purpose: each is written in the update that clears the signature columns, so none of them meets a standing one. `runClosedPaid` stays inside it too.
- **No migration, no screen.** `sign_lien_desk_item_with_code` takes the hash from the client, so the database holds no second copy of the rule. The four writers and every reader of the four records are as they were.
- **The other two fixes on the card** were not taken: a rule that never asks a mailed notice (it needs the status at every reader), and moving the records out of `fields` (a migration and a change to every reader of the records).

## Deploy

Two functions bundle the hash and are redeployed after the merge (`npm run check:edge-drift` names what is behind): `notify-lien-approval`, through `_shared/lienApprovalPush.ts`, and `dev-mcp`, through the desk's mirrored kernels (`gcKernels/lib/jobs/lienDesk.ts`, which counts the notices to sign). Until they are, a function and the desk differ only on an approved notice that carries one of the four records, and the records are written on mailed notices.

## Tests

`src/lib/jobs/lienFieldsHash.records.test.ts` (new). The supabase client is mocked and the four real writers run, one over the other's output.

- The list equals the constants the writers use (`PROMISE_FIELDS_KEY`, `COURTESY_FIELDS_KEY`) and exactly the keys the four writers add. A writer that renames its key, or a fifth key in the list, fails.
- A draft with no record keeps the hash main gave it, pinned as a literal, with the stage checklist's answer hash beside it (`stageChecklist.ts` reads the same function).
- A mailed, signed notice reads as signed with no record, after each of the four writes, with each record alone, with a record written again, and when a record was already on it at signing. Five readers are asked each time: `lienRowUnsigned`, `lienItemUnsigned`, `lienSignatureStale`, `lienChipSigned` and `lienNoticeSignatureFromRow`.
- Twenty-five other changes still void a signature, alone and under a full set of records: the amount, the date, the months, a notice field added or removed, the GC's email, the cover letter, the wording, the pay lines, letter two's mark, an unknown new key, a record's word deeper in the paper, a near miss of a record key, the fields emptied or gone. No two of them hash alike.
- `runTakenBack`, `signatureCleared` and `redrawn` still change the hash, by their own builders.
- *Sign it again*: offered while the signature stands on a notice that carries a record, not offered once the paper changed or the notice is mailed; the clear takes the signature off and keeps the record, and the next signature stands through a later record.
- `lienSignatureAskable` (the function's reminder) does not ask again for a notice signed before a record was written.

The test was run against three wrong kernels and failed each: the old whole-`fields` hash, a printed key added to the list, and the records dropped at every depth. `lienFieldsHash.shared.test.ts` still holds the desk's rule and the function's rule to one answer.

## Not verified

- Nothing was walked on screen: no screen shows a mailed notice's signature.
- The card's production read (a mailed, signed notice that carries a promise reads as signed) could not be made: no signed notice is mailed yet. The nine signed notices are approved, and none carries a record.
- `notify-lien-approval` and `dev-mcp` are not redeployed by this PR.
