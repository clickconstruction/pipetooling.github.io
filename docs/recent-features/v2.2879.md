# v2.2879 — Add customer asks "Started as a prospect?" and closes the loop; the Convert tab starts on search (2026-09-05)

Journey-map Phase 4, Tier-2 #32 (C17; `pipetooling-journey-map` → `docs/JOURNEY_MAP.md` row 32 "0 prospects ever converted on either finish line"; J34 `customer-front-desk.md` F4 + F6, P4, N4). Client-only; no migration, no edge function. Decision #17 (write only after explicit confirm) governs every lane: the prospect is marked on **Save**, never on open.

## Why

Live on 2026-09-05: `prospects` with `prospect_fit_status='converted'` = **0**, `prospect_comments` with `interaction_type='converted'` = **0** — across the whole life of the pipeline, while assistants groom the list daily and the office mints customers every week. Both existing finish lines missed the motion:

- Follow Up's **Converted ✓** (`handleConverted`) flipped the status and left a comment but created **no customer** — the only documented lane (`work-the-prospect-calling-queue.md`) ended the pipeline with the customer still un-minted.
- The **Convert** tab created the customer but an effect pre-selected the calling queue's head on tab switch, which (a) put a never-called company under "Who are you converting?" and (b) suppressed the tab's own typeahead + "recently answered" suggestions (v2.2454), which render only when nothing is selected.
- **Add customer** (`NewCustomerForm`) — where customers are actually created — had zero prospect awareness (`grep -i prospect` → 0 hits).

The mark tail existed twice in `Prospects.tsx` (`handleConverted`, `handleConvertSubmit`) and nowhere else.

## What changed

### One kernel — `src/lib/prospects/prospectConversion.ts`

| Export | Kind | Purpose |
|---|---|---|
| `canAccessProspectPipeline(role, estimatorProspectsAccess)` | pure | The Follow Up gate (dev / master_technician / assistant / controller, or estimator with the flag). `Prospects.tsx`'s `canAccessFollowUp` and `NewCustomerForm`'s `showProspectSearch` both call it. |
| `prospectMatchesQuery(p, q)` | pure | Company / contact / address / email substring (case-insensitive) + phone digit-for-digit once ≥3 digits typed. Converted prospects never match. |
| `searchProspectsForCustomerForm(pool, q, limit=6)` | pure | Company-prefix hits first, then caller order. |
| `customerDraftFromProspect(p)` | pure | `{name, address, phone, email}` — only non-blank values; name falls back to contact when there is no company. |
| `prospectChipLabel(p)`, `prospectConvertedCommentText(name, customerId)` | pure | Chip text; the comment line `Converted to customer <name> (/customers/<id>)`. `prospects` has no customer-id column, so the comment carries the path. |
| `markProspectConverted(prospectId, customerId, customerName, userId, client?)` | async, never throws | `prospects.update({prospect_fit_status:'converted'})` then `prospect_comments.insert({interaction_type:'converted', …})`; returns `{ok}` / `{ok:false,error}`. Injectable client for tests. |
| `recordProspectConverted(userId, role, lane)` | telemetry | `recordNavClick(…, 'prospect_converted', '#<lane>')` → `ui_nav_clicks`; lanes `add-customer` / `convert-tab` / `follow-up`. |

Test: [`prospectConversion.test.ts`](../../src/lib/prospects/prospectConversion.test.ts) — gate table, matcher (text, phone digits, blank, converted, nulls), ranking + limit, draft mapping + fallbacks, comment text, and `markProspectConverted` against a fake client (happy path call sequence, update failure stops before the comment, insert failure reported, thrown client caught).

### Lane 1 — Add customer (`src/components/NewCustomerForm.tsx`)

- New first field **"Started as a prospect?"**: a `type="search"` input; the prospect pool (`CONVERTIBLE_PROSPECT_COLUMNS`, ordered by company) loads **once on the first keystroke** — never on mount, so Bids/Estimates mounts that never touch it pay nothing. Results (≤6) are buttons; Enter picks the first. Picking prefills name/address/phone/email via `customerDraftFromProspect` (blank prospect fields leave what the user typed) and collapses the search into a **From prospect: <chip>** row with an ✕ to unlink.
- Shown only when `!onSubmitForConvert && canAccessProspectPipeline(role, estimatorProspectsAccess)` (from `useAuth`, not the form's own `users.role` fetch, so it renders correctly from the first paint). The Convert tab mount (`onSubmitForConvert`) never shows it — that tab has its own picker.
- **Save tail**: after the `customers` insert succeeds and a prospect is linked → `markProspectConverted(...)` → on success `recordProspectConverted(…, conversionLane)`. Failure is `console.error`'d and never blocks the hand-off (the customer exists). `onCreated(customer, meta)` now carries `meta.convertedProspectId` (null when unlinked / failed).
- New props: `sourceProspect?: ConvertibleProspect | null` (pre-linked, for the Follow Up lane) and `conversionLane?` (default `add-customer`). `NewCustomerModalContext` / `NewCustomerModal` pass `initialValues`, `sourceProspect`, `conversionLane` through `openNewCustomerModal(options)`; existing callers (`Customers.tsx`, `BidFormModal`, `BidsBuilderReviewTab`, `Bids.tsx`) are untouched.

Render test: [`NewCustomerForm.render.test.tsx`](../../src/components/NewCustomerForm.render.test.tsx) — estimator without the flag: no search; estimator with the flag / assistant: search; subcontractor: none; Convert-tab mount hides it for a dev; a `sourceProspect` renders the chip + Unlink control.

### Lane 2 — Follow Up "Converted ✓" (`src/pages/Prospects.tsx` `handleConverted`)

Was: mark-only (status + comment + timer event + lock release), no customer. Now: opens the **global Add customer modal** (`useNewCustomerModal().openNewCustomerModal`) with `initialValues: customerDraftFromProspect(prospect)`, `sourceProspect: prospect`, `conversionLane: 'follow-up'`, and an `onCreated` that — only when `meta.convertedProspectId === prospect.id` — writes the `prospect_timer_events` row (seconds captured at open), releases the caller's `prospect_calling_locks` row, patches both caches, advances the queue pointer / URL, resets the timer, and toasts. If the user unlinked the prospect (or the mark failed) it toasts that the customer exists but the prospect is still in the queue, and changes nothing else. **Cancel writes nothing** — the v2.2850 lock intent/TTL wiring is untouched (the release still happens only on completion). Button tooltip updated.

### Lane 3 — Convert tab (`src/pages/Prospects.tsx`)

- **Deleted** the "when switching to Convert, default to current prospect from Follow Up" effect. The tab now opens on its search input with the "Suggested — answered in the last 30 days" chips visible (they were gated on `!convertProspectId`).
- `handleConvertSubmit`'s mark tail → `markProspectConverted(...)` + `recordProspectConverted(…, 'convert-tab')`; the local cache patches stay.

### Guides + docs

- `src/content/help/work-the-prospect-calling-queue.md`: the Converted ✓ bullet now says what actually happens (Add customer opens prefilled; Save creates and marks; Cancel changes nothing).
- **New** `src/content/help/add-a-customer.md` (Office; all pipeline roles + master): the Add customer form, Paste Fill, Customer Master, and one sentence per conversion lane.
- `docs/PROSPECTS_TABS_ARCHITECTURE.md`: Convert dossier (no default effect; shared mark tail; `defaultProspectId` prop dropped from the extraction plan), Follow Up handler note, preserve-quirk #12 rewritten (Convert **does** touch the prospect row now, via the kernel).
- `docs/PROJECT_DOCUMENTATION.md`: component tree line for `NewCustomerForm`.
