# v2.2414 — Per-GC Won/Lost in Edit Bid (2026-08-28)

Phase 2 of `docs/PER_GC_BID_PLAN.md`. Per-GC outcomes existed in data (board GC pills →
`bid_versions.outcome` + `rollUpOutcome`), but Edit Bid's Win/Loss segment hand-wrote
`bids.outcome` right past them — a bid could read Lost while every packet read waiting.

Zero schema. `BidGcSentPanel` GC rows gain the answer, `BidFormModal`'s segment derives:

- Row chip: `won` / `lost — <category>` (from the packet's versions' `loss_category`).
- Actions on undecided rows: **Won** (writes via the existing `setGcPacketOutcome` — a win
  auto-losses the other sent, unanswered packets and rolls the bid up) and **Lost…** (inline
  `BidLossCategoryChips` + note → `setGcPacketLossCategory`). Decided rows get **↩ waiting**.
- New panel props `bidOutcome` + `onOutcomeRollupChanged`: when the write rolls the bid-level
  outcome, the form's segment state syncs so Save can't clobber (the v2.2407 sync pattern).
- Segment rule on bids WITH versions: **Won / Lost buttons lock** (title points at the GC
  rows); **Open stays clickable** as the reset escape hatch (clearing a packet doesn't clear a
  decided bid — `setGcPacketOutcome`'s conservative guard — so Open + Save is the way back);
  **Started/Complete stays hand-set** (Phase 3 revisits deriving it from the linked job).
- `bid-gc-outcome-changed` dispatched so board GC lines refresh.

Verified live on BP398: Won → row chip + auto roll-up + segment flipped by itself; ↩ waiting;
Open + Save reset; board section membership followed each step.
