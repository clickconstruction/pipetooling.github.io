# v2.4848 — GC mode: the schedule's writes, so two people on one schedule never overwrite each other (2026-10-07)

PR 5 of the schedule's real build (`to-dos/gc-mode/SCHEDULE_REAL_BUILD.md`; its plan `to-dos/gc-mode/mockups/schedule-pr5.md`, both on branch `spike/gc-mode`): the schedule's writes, in `supabase/migrations/20261008040000_gc_schedule_writes.sql` (`docs/migrations/20261008040000_gc_schedule_writes.md`), after PR 4's (v2.4816).

- `gc_schedule_bump`, the version step (decision 5). Every plan write sends the version it read; a stale one is refused with `P0001` *The schedule changed while you were working.* and every change since as JSON in the DETAIL. A first draft makes the schedule's row at version 1.
- Eleven plan writes that check and bump the version and keep the plan at Start first (decision 7): `gc_schedule_draft`, `gc_schedule_move` (every kind of move), `gc_schedule_undo` and `gc_schedule_redo` (replayed from the move's own record), `gc_schedule_keep_what_if`, `gc_schedule_baseline`, `gc_schedule_split`, `gc_schedule_join`, `gc_schedule_add_activity`, `gc_schedule_remove_activity` and `gc_schedule_fail_inspection`.
- Four records that touch several rows, with no version (decision 9): `gc_schedule_set_places`, `gc_schedule_pass_inspection`, `gc_schedule_their_dates` and `gc_schedule_add_wait`.
- The guard, `gc_schedule_plan_guard`, on the plan's ten tables: the plan changes only inside a plan write, even for a dev; a record (a real day, a place, a pass) and a cascade pass.
- Every function is `SECURITY INVOKER`, so the tables' policies decide who may (dev only until the schedule's PR 10). A record's day is `public.app_today()`.
- `templateSaveProblem` words the two template shapes the table refuses: a schedule with no trade's line, and a substantial completion planned before the first start.
- `scheduleChangedRefusal` reads the refusal back from the error `checkSupabaseError` throws, for the window that was saving (the schedule's PR 8).
- The SQL bed `npm run test:pg:gc-schedule` (`scripts/pgtest-gc-schedule.sh`, `supabase/tests/gc_schedule/20_scenario.sql`) runs the writes against every migration, and the new *SQL beds* workflow runs it on a PR that touches the schedule's SQL, since no session on the office Mac can run Docker.
- `writes.words.test.ts` holds every refusal the SQL shares with a kernel to the kernel's own sentence, and every one to plain words.
