# v2.3219 — Bid basis: CountTooling exports the marked-up sheets into the Cover Letter, the letter says we bid to our marks (2026-09-10)

Migration `20260910120000_bid_plan_basis_exports.sql` (see `docs/migrations/`). Pairs with the CountTooling PR "Bid basis export" (bid-basis-model.js, features/bid-basis.js, the Export PDFs preset).

## Why

When a plan set is too rough to read and the owner will not send a cleaner copy, the office bids to its own marked-up copy: the letter has to say so, and every sheet with marks goes to the GC with the proposal. Until now that was a manual Export PDFs in CountTooling (setting every untouched sheet to Exclude by hand), a file named `takeoff-specific-pages_…`, a sentence retyped into the exclusions box that vanished on reload, and no record of which file went out.

## What shipped

**The bridge is two browser tabs, no server.** The Cover Letter opens the bid's CountTooling view link — `count_tooling_plans_link` (the Counts import) or, failing that, `count_tooling_link` (the twin pipeline's stamp) — in a new tab with `export=bid-basis&ref=b<bid_number>`. CountTooling's view-link boot sees the flag and opens its Export PDFs dialog preset: only pages carrying counters / runs / ducts / rooms (highlights and notes alone never select a page), report on, highlights off, notes on, a bid chip, and a "Saves as" row. On Download it saves the file, shows a Downloaded card (file name + Copy, sheets, "PipeTooling has been told"), and `postMessage`s a manifest to `window.opener`, targeted only at the PipeTooling origins (clicktooling.com, pipetooling.com, plus localhost dev ports when CountTooling itself runs on localhost). It also posts a lighter "loaded" notice as soon as the plan opens, carrying the takeoff's last-saved time.

**PipeTooling side**

- `src/lib/bids/bidBasis.ts` (kernel, tested): origin allow-list (`isCountToolingMessageOrigin`, localhost only under `import.meta.env.DEV`), manifest and loaded-notice parsers (type + version + file-name shape validated; everything else tolerated), `bidBasisExportUrl` (appends the flag to the stored view link, refuses non-CountTooling links), `expectedBidBasisFilename` (mirror of CountTooling's builder for the by-hand prefill), `shortSheetLabels` (strips CountTooling's default `<project> — ` prefix), `bidBasisClause`, `currentBidBasisExport` / `sortBidBasisExports`, `bidBasisTakeoffMovedSince`, `bidBasisInsertFromMessage`.
- `src/hooks/useBidBasisExports.ts`: loads the bid's rows, listens on `window` for the two messages (origin-checked, ref must match the bid), inserts the export row (earlier rows get `superseded_at`), keeps the latest loaded-notice time for the stale check; `stampManual`, `remove`.
- `src/components/bids/BidBasisCard.tsx`: the step-2 card (`bid-basis-card` id) in three states — *Plans as issued* with the button (only when the bid has a CountTooling link), *Marked-up plans · stamped* (file name + Copy, sheets, who/when, takeoff last saved, Export again · History · Remove), and the amber *Takeoff changed since* variant — plus the waiting dialog (`BidBasisExportModal`: the three steps, the expected file name, "Tab didn't open? Open it again", "Mark as attached by hand", Close) and the by-hand stamp dialog. `BidBasisExportsList` renders the history under Followup → Full bid details.
- Cover Letter: the **Bid to our marked-up plans** pill (persisted `bids.bid_to_marked_plans`; dashed and disabled until an export exists); `buildCoverLetterHtml` / `buildCoverLetterText` take a trailing `bidBasis` argument and render **Bid basis:** + the clause after the plan-date line, and the fixture header becomes "per our marked-up plans". Every letter path (single, packet sections, same-page alternates) passes it; the Approval PDF does not (internal document).
- Help guide `bid-to-your-marked-up-plans.md`.

## Decisions

- Stamp + canvas snapshot, not the PDF: the estimator's sent email holds the file; the row holds the name and the marks (CountTooling's Canvas JSON, KB-sized, re-importable by PDF hash).
- The clause auto-inserts when the pill is on — the attachment is the evidence, the pill is the human decision (a deliberate departure from the RFI "suggest, never insert" doctrine).
- No grant: the view link's email gate already admits clickplumbing.com and remembers the token per browser. A grant naming the viewer is a later refinement.
- No server-side PDF: CountTooling's export is browser-only (pdf.js raster + jsPDF, DOM-driven); a pdf-lib compositor would be a second renderer.
