# v2.3230 — get_plan_pages: the connector hands the robot its plan set page by page, so the Claude Desktop path no longer needs a person to drag PDFs in (2026-09-10)

Edge function `twin-mcp` v1.3.18 (redeploy). No migration.

## Why

The Desktop kickoff (v2.3207) was attended by design: a Desktop chat cannot call plan-fetch (it needs the twin token in a header), so a person had to open the plans link and drag the PDF into the chat at STG-2. Everything else in the pipeline was already a connector call.

## What shipped

- **`get_plan_pages(bid, pages?, embed?)`** on `twin-mcp`: fetches the bid's own set through plan-fetch with the caller's token (folders merged; a folder that exceeded plan-fetch's merge cap streams parts, which are joined with pdf-lib, up to 8 files / 60 MB), splits the requested pages (`'1-4,9'`, default `1-6`, at most 8 per call) into single-page PDFs in the `twin-plans-tmp` bucket (`plan-pages/<bid>/<setKey>/pNNN.pdf`, upsert, public like the bucket's existing use), and returns the page count plus `{ page, url, bytes }` per page. `embed: true` also attaches up to three of them (≤ 3 MB) as `application/pdf` resource blocks in the same reply, for clients that render embedded resources. Own/assigned fence; a 403/404 from plan-fetch comes back as the intake-share explanation; `[pipeline STG-2] get_plan_pages …` on the ledger.
- **Desktop kickoff** (`docs/twins/kickoffs/desktop-operator.md`): setup step 5 and STG-2 rewritten — the robot fetches pages itself, sheet index first, then the plumbing sheets by number; a person drags the PDF in only when the connector cannot read the set. The Code-side skill is unchanged (it has a shell and plan-fetch).
- `EDGE_FUNCTIONS.md` paragraph.

## What this does and does not prove

- Verified: the bundle compiles; after deploy, `initialize` reports v1.3.18 and `tools/list` carries the verb. The verb's body follows `stage_plan_pdf` (fence, bucket, public URL) and `ct_finish_takeoff` (plan-fetch with the token) exactly.
- Not verified here: a call with a real twin key (none on this machine), and whether a given Claude Desktop build reads a page PDF from the URL or from the embedded resource well enough to count fixtures on a drawing. Both forms are returned so the operator can find out on the first run; the kickoff keeps the drag-in fallback for that reason.

## Notes for the next session

- If page PDFs prove hard for the model to read as drawings, the next step is rasterising pages to PNG server-side (MCP `image` blocks) — not possible with pdf-lib alone; it would need a renderer the edge runtime can host.
