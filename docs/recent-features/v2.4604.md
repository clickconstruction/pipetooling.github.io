# v2.4604 — Database updates no longer hold up every page when a table is added (2026-10-05)

Migration only; no client change, no edge function. [`20261005222937_twin_fence_skip_existing.sql`](../../supabase/migrations/20261005222937_twin_fence_skip_existing.sql) makes `apply_digital_twin_write_blocks()` incremental, the same fix [`20260814185815`](../../supabase/migrations/20260814185815_read_only_stmt_blocks_skip_existing.sql) gave `apply_read_only_stmt_blocks()` (v2.1651).

- **The hazard**: the twin fence applier dropped and recreated its three `digital_twin_write_fence_*` policies on every RLS-enabled table (~250) on every call. `DROP POLICY` and `CREATE POLICY` each take ACCESS EXCLUSIVE, which blocks even SELECTs, held until the push commits. Every CREATE TABLE migration ending with the call locked the app's tables one by one, and one slow query on any table stalled the sweep for the full `lock_timeout` with everything already locked queued behind it.
- **The fix**: the applier skips a table that already has all three policies and creates only the missing ones on the rest; it never drops. The allowance chain is copied verbatim from v3 (`20260830210000`). A rerun after CREATE TABLE now locks just the new table.
- **New discipline**: a plain rerun no longer rebuilds an existing fence. Changing an allowance (including an existing table gaining a `bid_id` or `cost_estimate_id` column) takes a one-off migration that drops the affected policies first, then calls the helper. Stated in the function COMMENT and in [`MIGRATIONS.md`](../MIGRATIONS.md) → Writing a Migration.
- **House rule amended**: CREATE TABLE migrations now end with all three helpers: the two read-only blocks plus `apply_digital_twin_write_blocks()` ([`CLAUDE.md`](../../CLAUDE.md), `AGENTS.md`, `AI_CONTEXT.md`, `PROJECT_DOCUMENTATION.md`, `ACCESS_CONTROL.md`, `twins/HANDOFF.md`). MIGRATIONS.md no longer claims CI enforces the footer: no check does.
- **Rehearsed** on a throwaway Postgres 15.14 against v3 (details in [`docs/migrations/20261005222937_twin_fence_skip_existing.md`](../migrations/20261005222937_twin_fence_skip_existing.md)). Every rebuilt policy matched v3's on 22 tables covering each branch of the chain. A fenced rerun took no table locks. A held `jobs` read made v3's sweep cancel an app read and die on `lock_timeout`, while the new body returned 0 at once.

**Deploy**: `supabase db push` after merge, any time. `CREATE OR REPLACE FUNCTION` plus a self-test that creates 0 policies in prod, so no table locks. Not pushed in the authoring session.
