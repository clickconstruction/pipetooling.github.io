# v2.1898 — Changelog fragments cutover: per-version files end the every-PR merge conflict (2026-08-20)

Every PR used to prepend an entry to the top of `docs/RECENT_FEATURES.md` and `src/content/releaseNotes.ts` (176 edits each in the four days before the cutover), so any two open PRs conflicted with each other **by construction** — the dominant source of merge conflicts across parallel sessions. This PR converts all three prepend-magnet docs to **one file per version**, the [changesets](https://github.com/changesets/changesets) pattern: new files never conflict.

- **Release notes**: [`releaseNotes.ts`](../../src/content/releaseNotes.ts) is now a tiny aggregator — `import.meta.glob` (same idiom as [`helpGuideRegistry.ts`](../../src/lib/helpGuideRegistry.ts)) over `src/content/releaseNotes/v2.NNNN.ts` fragments, sorted newest-first, concatenated with the frozen [`releaseNotesArchive.ts`](../../src/content/releaseNotesArchive.ts). Settings → Release notes renders identically.
- **Feature docs**: `docs/RECENT_FEATURES.md` is frozen as the pre-cutover archive; each PR now adds `docs/recent-features/v2.NNNN.md` (format in the [README](README.md)).
- **Migration docs**: `docs/MIGRATIONS.md`'s per-migration changelog is frozen the same way; new migrations add `docs/migrations/<version>_<slug>.md` (format in the [README](README.md)); the best-practices/rollback sections stay in the frozen file.
- **Drift tests** ([`releaseNotes.test.ts`](../../src/lib/releaseNotes.test.ts)) enforce the pairing across archive + fragments: newest versions match, no version documented twice, no orphan release note, fragment filename = its `version`, docs fragment first line names its own version. The `LEGACY_*` hard-zero ratchets are unchanged.
- **Claim scripts**: [`claim-version.ts`](../../scripts/claim-version.ts) / [`sessions-status.ts`](../../scripts/sessions-status.ts) now read the newest version from fragment filenames too (new pure parser `parseNewestFragmentVersion` in [`sessionClaims.ts`](../../src/lib/sessionClaims.ts)), tolerant of either side of the cutover.

Also preps the merge queue: [`ci.yml`](../../.github/workflows/ci.yml) now triggers on `merge_group`, so the required `checks` context runs on queued merge results once the queue is enabled.

Client-only — no migration.
