# v2.6530 — The schema says every People record has a users row (punch list #265, PR 2) (2026-11-04)

Card #265, PR 2 of 3 (PR 1 is [v2.6529](v2.6529.md)). Since #260 every person is a users row; `people.account_user_id` stayed nullable because its key was `ON DELETE SET NULL` and the combine nulled a source's account. Both are gone.

## What changed

- **Migration `20261104230000_people_have_a_users_row.sql`** ([`docs/migrations/`](../migrations/20261104230000_people_have_a_users_row.md)): the trigger `people_needs_users_row` refuses a signed-in insert or unlink that leaves `account_user_id` NULL (every client path; a write with no caller — the service role, a migration, a bed's fixture — may still, since seven whole-schema beds seed roster-only records and the two records the backfill skipped stand until the desk links them); `people_account_user_id_fkey` is `ON DELETE RESTRICT`. The `NOT NULL` itself waits on the count reading zero and the beds seeding linked records. Bed S1–S3.
- **`invite-user` re-invites on the same id**: a pending invite (never confirmed, never signed in) used to be deleted and re-made; with the key on RESTRICT and the row being the person, the function deletes the auth account (which detaches the row), creates the new one on the same id unconfirmed (GoTrue's admin create takes `id`; `handle_new_user` re-attaches), and mints the invite link as before. Redeploy after the push.
- Docs: EDGE_FUNCTIONS (invite-user), ACCESS_CONTROL.
