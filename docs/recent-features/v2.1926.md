# v2.1926 — Promised pay dates (2026-08-20)

Part 3 of the expected-payment train (v2.1924 chips, v2.1925 forecast): the
durable home for the answer an assistant used to have to go ask for. When a
customer actually names a payment date, the office marks it and the board
carries it.

- **"mark promised date…"** link under the expected-pay chip on every Billed
  Awaiting Payment row (dev / master / assistant-like — primary sees promises
  but can't mark). Opens `SetPromisedPayDateModal`: date input, save, clear.
- A promise **overrides the statistical estimate**: the chip goes green
  ("✓ Promised Sep 25 · Malachi" — who marked it is part of the display), the
  payment forecast buckets the row by the promised date ("✓ Sep 25" rows),
  and a blown promise flips red ("5d past promise · Malachi").
- Migration [`20260821110000_job_promised_pay_dates.sql`](../migrations/20260821110000_job_promised_pay_dates.md):
  new `job_promised_pay_dates` table (one promise per job, `marked_by`/`marked_at`
  stamped) + `set_job_promised_pay_date(p_job_id, p_date)` (NULL clears;
  office-writer gate) + `list_job_promised_pay_dates()` (marker names joined;
  billed-money read gate). Table is RLS'd dev-only; all app access via the two
  SECURITY DEFINER RPCs; read-only training accounts blocked by the stmt
  trigger.
- Kernel: `billedExpectedPayModel` takes an optional promise (works even with
  no pay-speed data or bill date — a promise stands alone);
  `buildBilledPaymentForecast` takes the promise map;
  `parsePromisedPayDatesRpc` defensive parse. +5 kernel tests.
- `JobsStagesTab` loads promises next to pay speeds (same fail-soft posture)
  and refreshes the map after every save/clear.
- Help guide `see-when-a-customer-will-pay` extended with the promised-date
  section; `ACCESS_CONTROL.md` note for the writer gate.
