# v2.6775 — A card dispute that beat its own payment to the office now finds the payment (2026-11-09)

Punch list #76 (`to-dos/ar-returned-checks.md`), the defect the 2026-11-09 Stripe walk on prod found. Migration `20261109023000_ar_stripe_case_payment_backfill.sql` (`docs/migrations/`).

## What was true

- `stripe-webhook` → `record_ar_stripe_case` opens an `ar_stripe_cases` row on `charge.dispute.created` and keeps the bill's payment on it (`payment_id`: the bill's payment of this amount, else the newest). Stripe's dispute test card disputes the charge the instant it is paid, so the dispute event was handled about 13 ms before `invoice.paid` wrote the `jobs_ledger_payments` row, and the case opened with `payment_id` NULL. A live card dispute can land the same way when the two events run on parallel workers.
- The later `charge.dispute.updated` / `charge.dispute.closed` events only brought `stripe_status`, `due_by`, `reason`, `lost_at` and `closed_at` up to date. `list_ar_return_cases` reads `payment_live` from the joined payment, and `src/lib/jobs/arReturnCase.ts` draws **Put the bill back** only with it, so the lost ZZ TEST case's pane showed the read-back words and no press.

## What changed

- `record_ar_stripe_case`, the branch that finds the case already open: a dispute case with no payment runs the open branch's lookup again against the case's bill and fills `payment_id`. Nothing else in the function moved; the result carries `payment_filled`, which the webhook does not read.
- No client change. `put_back_lost_dispute_bill` and the pane work as shipped once the case holds its payment.

## Not in this PR

- A fallback in `list_ar_return_cases` from the case's `invoice_id` when no payment ever arrives: the press takes a payment off the job, so a case with no payment has nothing to put back, and the back-fill covers the race.
- The two ZZ TEST cases already open on prod hold their NULL until one of their dispute events is resent from the Stripe Dashboard's Workbench, which is the walk.
