# v2.3033 — Test-gap audit, pass 43: Dispatch crews get their first tests (2026-09-07)

Follow-up to v2.3032. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`dispatchSwimLanes.ts` (142 lines) is the data layer for the named, ordered crews on **Dispatch → People**: the two-table read folded into lane and member maps, and the writes — create, rename, delete and reorder a lane, assign a person (strict lanes: they move) and remove one. Five callers across the dispatch hub, the settings section and Quick Assign; no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Lanes read by sort order then name, members by sort order; the result carries per-lane member lists in that order and a person → lane map. Null results read as empty; a failed read comes back empty with the message.
- Create and rename trim the name and refuse a blank one before writing; reorder writes `sort_order` = position for every lane in the given order and stops at the first failure.
- Assigning a person deletes any existing membership first, then inserts the new one, so a person moves between crews rather than appearing in two; a failed removal stops before the insert.
- Every write failure comes back as the server's message.
