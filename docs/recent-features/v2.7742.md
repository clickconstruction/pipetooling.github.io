# v2.7742 — Tell the dev: a note always carries the app's version (2026-11-18)

Punch list #380, found by the live walk. The owner's yes of 2026-11-18 sent one test note on the live app as the dev. It saved, its push reached the devs, and its answer came back with the dot. It also went with `app_version: null`.

## Why

The box loaded the version when it first opened, by importing the whole release-notes list (v2.7658). On the live site that took about half a second at a desk. A Something went wrong note needs no words, so it can be sent faster than that, and it went without the version. A phone on a weak signal waits longer. A tab on an old build is worse: the site no longer serves that build's files, so the import fails, and that is the note where the version matters most.

## What changed

- **`virtual:app-version`**, a build-time module (`appVersionPlugin` in `vite.config.ts`, beside the lens's two), holds the newest release note in the build. The number comes from the file names in `src/content/releaseNotes/` (`newestReleaseNoteVersion` in `src/lib/newestReleaseNote.ts`, which imports nothing so the build config can run it), the same note `RELEASE_NOTES[0]` names.
- **`src/lib/appVersion.ts`** exports it as `APP_VERSION`. The root puts it on the note's state when the box opens, so the *Goes with your note* list shows it at once and every note carries it.
- The lazy import and its effect are gone from `TellTheDevRoot`.

## What it means

The version is the newest release note in the build. Release notes merge out of number order, so two builds in a row can read the same number. It still says how old a tab's build is, which is what a note needs.

## Tests

`appVersion.test.ts`: the newest name by number, names that are not a release note passed over, none gives null, and the module the build makes equals the newest file in the tree. `TellTheDevRoot.render.test.tsx` holds the version line on screen as the box opens.
