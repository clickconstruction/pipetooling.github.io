# v2.5935 — Every staff screen says why a save failed (2026-10-26)

Punch list #184, sweep D, PR 2 of 2: the codemod, after the kernel. v2.5898 taught `formatErrorMessage` (`src/utils/errorHandling.ts`) to read a plain-object Supabase result error, the shape `if (error) throw error` throws. That made the formatter's 916 call sites honest, but 648 more places never called it: they read `e instanceof Error ? e.message : '<fallback>'`, which shows the fallback for every plain object, so a refused delete on the Checklist read *Failed to delete* whatever the database said. No migration, no edge function.

## The codemod — `scripts/codemods/error-reason-sweep.mjs`

Parsed with the TypeScript compiler, one file at a time, re-runnable (the rebase rule: re-run it, never hand-resolve its diff). Three rewrites:

- **The ternary.** `X instanceof Error ? X.message : FB` → `formatErrorMessage(X, FB)`, the mirrored `!(X instanceof Error) ? FB : X.message` the same, and `X.message || FB` as the true branch the same. A fallback that only re-reads X (`String(X)`, `` `${X}` ``, `typeof X === 'string' ? X : …`, `'message' in X ? … : …`) is folded away, since the formatter reads a string and a plain object itself; a fallback of `undefined` or `null` is left alone and listed, because the caller is testing for "no message" (the two in `ClockInOutButton.tsx`).
- **The unbound catch.** `catch {` whose try block calls Supabase or an edge function and whose only statement is a toast or a setter given one string literal → `catch (e) {` with the literal wrapped: `showToast(formatErrorMessage(e, 'Could not save the record.'), 'error')`. Clipboard copies, PDF builds and partial-success warnings have no Supabase call in the try and are left alone.
- **The text test.** A network decided by `/fetch/i.test(message)` or `message.includes('fetch')` is listed for a hand fix as `errorKindOf(e) === 'network'`; on 2026-10-26 main it found none outside the public pages.

The import of `formatErrorMessage` is joined to an existing value import from `utils/errorHandling` or added after the last import.

**Skipped for now:** `src/components/settings/SettingsWhatEveryoneSeesTab.tsx`, which #6299 rewrites (the sweep would conflict with it); the line in the script's skip list is marked temporary and comes out, with a re-run on that file, once #6299 lands. **Skipped on purpose:** `src/lib/lens/seal.ts`, which runs before every other module and may import nothing heavy (`sealFirst.test.ts`; its two ternaries word console captures, not a screen); the error plumbing itself (`errorHandling.ts`, `offlineRecoveryState.ts`, `networkErrorMessage.ts`, `errorClassTelemetry.ts`, `readEdgeFunctionErrorBody.ts`), tests, and the public pages and the cards drawn on them (`pages/{CustomerPortal,SubPortal,PayLink,BidRoom,JobContractSign,EstimateAccept,ContractAccept,GcWordAsk,SubmittalRoom,EstimatePublicTerms,HazmatNoticePublic,LegalPortal,LegalConfirm,CustomerRating,SupplyHouseQuotePage,FileOpen}.tsx`, `components/{portal,subPortal,legalPortal}/`). A customer reads the class of a failure, never a server's words; their voice is a hand PR with one shared portal helper.

**The run on 2026-10-27 main (14:45Z):** 313 files · 645 ternaries → `formatErrorMessage` · 22 unbound catches bound and wrapped · 289 imports added.

## The kernel, refined — `describeCodedFailure`

Asking whether v2.5898's words were the best we could do turned up two things. First, a refusal with a sentence of its own lost what failed: *You don't have access to this record.* with nothing about the Division 22 ledger the screen was loading. Second, a fallback that ends on a full stop read *Could not save the record.: duplicate key …*. Both coded branches of `formatErrorMessage`, the plain result object and the Error that carries a code, now share one helper. A lost signal is still the offline copy alone. A code with a sentence of its own follows the screen's own sentence (*Failed to delete. You don't have access to this record.*). Any other reason follows it after a colon, the closing stop dropped (*Could not save the record: duplicate key …*). The default fallback is no sentence of the screen's, so the class sentence or the reason stands alone there. A `DatabaseError` keeps the v2.2843 words built from its operation name (*You don't have access to this fixture name audit.*), since those already say what failed.

One kernel takes a shorter reason on purpose: `writeNewJobChildRows` (`lib/jobs/jobFormSliceWrites.ts`) puts its reason inside *Job saved, but 1 line item did not save (…)*, so a lost signal there reads *no connection*, never the whole offline copy with its *nothing was saved*.

## The check — `npm run check:error-words`

`error-reason-sweep.mjs --check` writes nothing and exits 1 when anything is left to rewrite, printing each file and the command that fixes it. Wired into `deploy.yml` and `ci.yml` after *A batch button says its count* (the parity check holds the two in step). From this PR on, a new `instanceof Error ?` ternary, an unbound `catch {}` that toasts a literal after a Supabase call, or a text test on a message fails the build.

## The edge copy

Since v2.5881 a GC kernel the edge functions share imports `src/utils/errorHandling.ts`, so `scripts/edge-kernels.mjs` copies it to `supabase/functions/_shared/gcKernels/utils/errorHandling.ts`, and `edgeKernels.test.ts` holds the copy to the source. This PR regenerates it (`npm run gen:edge-kernels`). No edge kernel calls `formatErrorMessage`; they import the module for `withSupabaseRetry`, `checkSupabaseError` and the paging helpers. So nothing an edge function answers changes, but the 15 functions that bundle the copy read as behind in `check:edge-drift` until they are redeployed: customer-portal, drive-link, gc-card-bill, gc-customer-email, gc-trade-portal, get-bid-proposal-room, get-contract-for-signer, get-estimate-for-customer, get-job-contract, get-rfq-quote-page, get-submittal-room, legal-portal, photo-save, sub-portal and submit-portal-request.

## Is this the best we can do?

The better sentence names the operation: `checkSupabaseError(result, 'delete checklist items')` at the throw renders *You don't have permission to delete checklist items.* where the codemod's output renders *You don't have access to this record.* and *Failed to delete: …*. That stays the rule for new code. It is 361 hand-written names, not a sweep, and the fallback each screen already wrote carries the same words nine times in ten, so the codemod takes every screen most of the way in one PR and the names can follow surface by surface. The check is strict and safe because the codemod leaves nothing legacy for it to fail on: the theme-tokenize model, not a list of exemptions.
