# v2.2585 — AR exact-match sweep (2026-09-01)

Variant C of the owner-picked AR modal plan (mockups: "Who Sent This Check";
follows v2.2584's payer matching). One check = one bill is the everyday case,
and each one still cost a full select-search-type cycle in the modal.

- **New kernel `src/lib/jobs/arExactMatchSweep.ts`** (6 tests):
  `buildArExactMatchSweep(deposits, targets)` buckets by cents-exact amount
  (deposit `remaining_available` vs bill remaining) and pairs a bucket only
  when it holds exactly one deposit AND one open bill — several of either at
  the same amount become a reported "skipped" bucket, never a guess. Returned
  deposits and zero remainders are ignored; **Stripe-hosted bills are excluded
  entirely** (they keep the paid-outside-Stripe confirmation gate and stay
  manual), and a Stripe twin doesn't make its non-Stripe sibling ambiguous.
- **Modal UI (`BankPaymentsModal`)**: a green bar above the deposit list
  ("N deposits each match exactly one open bill — $X") opens a full-modal
  review panel: one row per pair (deposit amount · counterparty · posted →
  bill), all ticked by default, skipped buckets listed underneath. Apply runs
  the existing `apply_mercury_bank_payment_allocations` RPC per deposit
  (posted-day `paid_on`, kind badge label as payment type) with live
  progress; failures stay listed with their errors and "Retry failed" re-runs
  only them (successes are guarded from double-apply until the list
  refreshes).
- **New render smoke `BankPaymentsModal.render.test.tsx`** covers the v2.2584
  payer chip row and the sweep bar/panel wiring (seeded deposit RPC stub).
- Help guide `match-bank-deposits-to-bills.md` gains the sweep section.
  Client-only; no schema or RPC changes.

Live note: on ship day the real backlog (post filter restore) was six $250
DRF checks against five $250 bills — exactly the ambiguous bucket the sweep
refuses to guess; the bar correctly stays hidden there and those go through
the v2.2584 payer chips instead.
