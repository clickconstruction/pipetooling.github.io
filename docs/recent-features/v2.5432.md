# v2.5432 — The checks stop testing a pull request's older code once a newer push arrives (2026-10-13)

`ci.yml` gains a `concurrency` rule: group `ci-<PR number | merge-group head | ref>`, `cancel-in-progress` only when the event is `pull_request`. A merge-queue group's run and main's push run keep their own groups and are never cancelled; `deploy.yml` keeps its `pages` group untouched.

Why now: on the night of 2026-10-12/13 two builds (GC Messages wave 2 and the residential customer-communication build) were force-pushing rebases from eighteen helper sessions at once. Each superseded push left its old `checks` run (about 18 minutes) and `SQL beds` run holding runners, and at 04:50 UTC 23 Actions runs were queued or in progress while the merge queue's head group had waited since 02:16 UTC. `sql-beds.yml` already had the same rule (its group keys on the PR number or the merge-group head); this brings `ci.yml` level with it.

What does not change: the `checks` job's `run:` lines are untouched, so `scripts/check-workflow-parity.mjs` (ci.yml == deploy.yml) still passes; nothing about the tests, the typecheck or the lint moves.
