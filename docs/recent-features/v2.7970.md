# v2.7970 — Robots: an assistant can archive a twin and stop the rounds (2026-11-19)

Two new pairs on `dev-mcp` (server 0.115.0, 145 write verbs, 92 naming no RPC, 196 tools): **`plan_twin_archive`** → **`apply_twin_archive`** and **`plan_rounds_stop`** → **`apply_rounds_stop`**. The owner, 2026-11-19: "build the leftovers: archive a twin and stop the rounds".

## Why

The audit of what an agent can stand up alone left three presses in the app that were not on its numbered list. These are two of them. The third, a held seat's retry, is not built here.

## Archive a twin

- `archive = { twin }` archives the twin, by its `users.id` or its fleet address. `{ twin, restore: true }` restores it. Any other key is refused.
- Archive is the panel's two steps in its order (`DigitalTwinsPanel.archiveTwin`): one PATCH on `twin_credentials` as the dev sets `revoked_at` on every live key of the twin, then `archive-user` is called as the dev.
- A refused key write returns before `archive-user` is called, so a twin is never archived with a key still live.
- If `archive-user` refuses after the keys went, the reply says so and names the keys that were revoked. The plan must be made again, since its hash names keys that are gone.
- Restore calls `restore-user` with `{ user_id }`. The plan says how many keys are still live. After an archive from the panel or from here that is none. A twin archived from the People page keeps its keys, and the twin seat goes by the key alone, so the plan says that too.
- The `archive-user` body is `twinArchiveBody`, held equal to the client's `archiveTwinBody` by test.
- Neither function reaches CountTooling or TakeoffTooling. The plan says the twin's seats there are not touched.

## Stop the rounds

- `rounds = { twin, stop: true }` stops the rounds on every live key of the twin. `stop: false` starts them again. `key_id` names one key.
- The write is the Rounds card's own `robot_rounds_stop(p_credential_id, p_stop)`, called as the dev once a key through `restPost`. The RPC takes a dev or the master and a key still live. No table is written by the server.
- A key that fails is named with its reason and the rest go on.
- The plan reads the twin's live keys and, fail-soft, `robot_agents()` for what each key has in hand. A refused read is `null` and the plan says *could not be read*, never that the key is idle.
- `planCommitment` hashes each key through `roundsKeyCommitment`, which drops `last_seen_at` and `in_hand`. A robot working between plan and apply does not refuse the apply. A key stopped, started, minted or revoked since the plan does.
- A stop reaches the rounds only. A session a person starts by hand carries on, the key stays live, and the agent stays installed on the Mac.
