# v2.5084 — GC mode: the presses behind the trades' draws and pay applications (2026-10-09)

U6a of the Building lane's real build (`to-dos/gc-mode/mockups/building-u6.md`, on branch `spike/gc-mode`): the trades' money, in `supabase/migrations/20261010021000_gc_trade_draws.sql` (`docs/migrations/20261010021000_gc_trade_draws.md`). No screen yet: the Draws window (U6b) calls these once the types PR after the push has them.

- **Four tables**, dev only until Building's door opens them to the money roles:
  - `gc_draws`: a trade's pay application on its statement of work, with its words, money, waiver and status. One sent back keeps its row, and its resend takes the same number.
  - `gc_draw_lines`: what each draw claims on each line, and the percent we see on one we doubt.
  - `gc_sow_line_reports`: a trade's report on a line, append only.
  - `gc_change_order_trade_sends`: a signed change order sent to its trade, and the line it became.
- **The money is worked out in SQL** from what a pay application claims (`gc_draw_money`), by the kernels' `payApplication` and `drawMoney`, for the trade and the office alike. It is never taken from the caller.
- **The office's presses**: record a pay application that came by email or on paper, with its Drive link (`gc_draw_came_in`); approve it, approve it for less, send it back, mark it paid; record an unconditional waiver that came in; take a back-charge off an approved draw; send a signed change order to its trade.
- **The trade's presses**, the service role's only, for the Portal's P5c: report a line (it sets the line's real days on the schedule), send a pay application, sign the unconditional waiver, sign a change into its statement of work. New keys wait in `gcTradeSubmit.test.ts`'s WAITING map for P5: `sowNotSigned`, `drawWaiting`, `nothingToBill`, `splitLine`, `notPaidYet` and `alreadySigned`.
- **A kernel fix: a credit is taken once.** `drawLinesOf` in `src/lib/gc/building.ts` kept only a draw's lines with work above zero, so a change order's credit was dropped from the draw that took it. The next pay application took the credit again, and the credit's line never read billed, so the trade never closed out. It now keeps any line whose work moved this period (`thisPeriod !== 0`). `building.direct.test.ts` holds the credit's case, and the SQL keeps the same rule.
- **A kernel fix: a back-charge is never paid back.** `payApplication`'s line 7 summed each earlier draw's `net`, which a back-charge taken off it lowers, so the retainage release (`finalPayApplication`) asked for the charge back: $3,500 where $3,000 was held. Line 7 now counts what each earlier draw was certified for, before a charge came off. It reads `Draw.backCharges`, which `types.ts` gains word for word from the prototype (U2 lifted `Draw` without it). `building.direct.test.ts` holds the case.
- **Also**: `gc_sow_lines` lets a change order's line be a credit, and P4a's `gc_back_charges.taken_draw_id` gains its foreign key. The four tables join `src/lib/gc/doors.ts`.
- **The SQL bed**: `supabase/tests/gc_building/60_draws.sql` (99 assertions) runs beside the other Building scenarios, with the press in the harness's `PRESSES` list. Every draw's money in it equals the kernel's for the same claims. It also refuses a trainee, a twin, an estimator and a signed-in caller of the trade's presses. All 66 sentences pass `plainWordsFailures`.
