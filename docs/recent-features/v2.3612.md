# v2.3612 — Supervision, PR 2: Schedule dispatch marks a block nobody on it can run (2026-09-19)

PR 2 of five in [`to-dos/supervision/README.md`](../../to-dos/supervision/README.md) (PR 1: v2.3611). Client only; no migration.

## The change

- **Kernel** [`src/lib/schedule/blockGroupCoverage.ts`](../../src/lib/schedule/blockGroupCoverage.ts) (3 test groups): `coverageOfAssignees(ids, personById)` → `covered` (someone can run a job — a master, or a helper / sub with the switch off) · `unsupervised` (someone needs supervision and nobody can run it) · `unknown` (an assignee the roster read did not return — never a warning); office-only or empty blocks are `covered` (nobody to supervise). `buildBlockCoverageByKey(blocks, personById)` judges the legs of a linked group together, keyed by `shared_block_group_id ?? block.id`; `supervisionWarningFor(name, person, coverage)` is the modal's line.
- **The dispatch roster read** (`fetchUsersTabRosterForScheduleDispatchHub`) carries `needs_supervision` (default true when null), so Dispatch Mode's schedule, Quick Assign and Quickfill get the column for free.
- **The hub page** keeps `hubPersonById` beside `hubRoleByUserId`, memoises `hubBlockCoverageByKey` over the week's blocks, and threads it shell → panel → cell → card as `blockCoverageByKey`; the card takes `coverage` and draws an amber **unsupervised** pill on its time row (beside *moved by tech*), with the why in its title. `blockModalSupervisionWarning` feeds the Add / Edit block modal's new opt-in `warning` prop — an amber line under the person while a block is built, for a person who needs supervision on a block nobody can run (add: the person alone; edit: the block's whole group).
- Guides: `schedule-dispatch.md` gains *When nobody on a block can run the job*; `say-who-can-run-a-job.md` updated. `PROJECT_DOCUMENTATION.md` (the ScheduleDispatch tree line), `GLOSSARY.md` (linked crew block; needs supervision), `ACCESS_CONTROL.md` (Supervision), `SCHEDULE_DISPATCH_ARCHITECTURE.md` (the memos).
