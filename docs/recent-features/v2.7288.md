# v2.7288 — The kernel copy's index exports only what a function imports through it (punch list #359, PR 1) (2026-11-14)

Infra only: no screen and no running code changes. Fourteen edge functions uploaded the whole kernel copy because its index exported every entry; the index now exports the fifteen entries a function reads through it, and each of the fourteen uploads about half of what it did.

## Why

`supabase functions deploy --use-api` uploads every file an import reaches. The copy of the kernels (`supabase/functions/_shared/gcKernels/`, generated by `scripts/edge-kernels.mjs`) has an index that re-exported every entry's values, and five files outside the copy import that index (`_shared/gcCustomerSchedule.ts`, `_shared/gcTradePortalSchedule.ts`, `_shared/gcTradePortalSample.ts`, `drive-link/index.ts`, `photo-save/index.ts`), between them using fifteen entries: the schedule kernels and the three photo kernels. Every other entry is read by its own function by the file's path (the morning run's, My email's, the Monday email's, the Quo kernels, the dev seat's), yet the index exported it too, so every function that read one schedule kernel through the index uploaded the morning run's flow editor, the My email kernels, the Monday email and the rest. v2.6804 and the Bridge's email had already taken their entries off the index for this reason, one group at a time; #359's read on 2026-11-14 found the index still carried 1.37 MB of customer-portal's 3.01 MB.

## What changed

- **`ENTRIES` in the generator**: the fifteen entries read through the index keep exactly the names the five readers import (`portalScheduleX`, `DatesNotice`, `LateDoor`, `LateWaiting`, `PortalLookAheadWeek`, `PortalCrewWeek`, `CustomerStanding`, `LateFinish`, `CHANGE_ORDER_OFFICE_COLUMNS`, `DrawTableRow`, `DrawLineRow`, `LineReportRow`, `PhotoNameInput`, `PhotoLineRow` came off, since nothing read them there); the other 115 export nothing (`values: [], types: []`) and are still copied, since their functions import them by path. The rule lives in one place, the comment over `ENTRIES`; the per-group sentences that said it are gone.
- **The index** went from 384 lines and 26 export lines to the schedule and photo exports alone. Every importer's running code is the same: none imported a name that came off.
- **`edgeKernels.test.ts`**, § what the index carries: the on-index entries are exactly the fifteen; every name the index exports is imported through the index by some file outside the copy, and every name so imported is exported (a name exported for no reader rides every portal's deploy); the index reaches no kernel of the morning run, My email, the Monday email, the Bridge, the submittals or the bids; every off-index entry is reached by one of `IMPORTERS` by its path, so nothing in the copy is dead. The three tests that enumerated the off-index groups by hand (the Bridge's, the submittals', the firm's grid's) are folded into those.

## Is this the best we can do?

- The generator could read the five importers and write the index from what they import, so a new read through the index needs no `ENTRIES` edit. It would make the index depend on files outside the copy, which v2.6348 took out of the headers on purpose, and the test now fails the same drift in CI, so the names stay hand-listed.
- The remaining 1.6 MB of a portal is its own `_shared` reads, the eight portals' samples in one file (`customerSampleFixtures.ts`, 137 KB on each portal for one sample apiece, with a type import of `customerSampleLegal.ts` worth 23 KB) and the slim database types (315 KB) through five type imports. Those are later cuts on the #359 card.
- dev-mcp is untouched here: it reads no index. Its cuts are the sliver chains (`customerLang` → `portalI18n`, `textsSwitch` → `quo/send`, `overheadPartsAccountingBuckets` → `overheadOfficePartsReads`) and the slim types, PRs 2 onward.
