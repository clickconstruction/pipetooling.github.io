# v2.6939 — Every list of a large HR case is read whole from the dev seat, past 200 rows (2026-11-11)

Follows v2.6935, which made `get_case_brief` and `get_person_file` fit the door and paged the HR entries. That change listed one limit as not done: every other source was still one read of 200 rows, the door's cap. The live check after its deploy found `at_cap` naming a source on a large file. Nothing from any file is in this change: the tests run on a made-up case.

## What went wrong

- **`get_person_file`** read the attachments, the evidence records, the reports, the papers, the hours statements, the licenses, the write-ups, the attendance rows and the document index in one read each. A file with more than 200 attachments kept the newest 200, so an older record or entry showed fewer files than it has, or none. `at_cap` named the table and nothing read the rest.
- **`get_case_brief`** read the evidence index, the document index, the matter's steps and documents and the schedule's jobs the same way. It asked for 1,000 theme marks in one read, and the door answered 200, so a theme's count stopped short without a word.
- Both read names by a list of ids in one read. The door holds a URL to 6,000 characters, so a list of about 150 ids was refused.

## What changed

- **`_shared/devMcpComposites.ts`**: `newestFirst(rows, column)` puts paged rows back newest first, as `order ... ascending: false` gave one read (a row with no value first, ties in key order). `readRowsByIds(reader, table, select, ids)` reads a list of ids a hundred at a time, each read paged.
- **`_shared/devMcpPersonFile.ts`**: every source goes through `readAllRows` (the helper `every`), newest first where the one read was ordered: attachments by `created_at`, evidence by `dated_on`, reports by `occurred_date`, statements by `prepared_at`. The names of templates, users and jobs are read with `readRowsByIds`. `at_cap` names a table only past `readAllRows`' own stop of 5,000 rows, and its note says so. `PERSON_FILE_READ_CAP` is gone. The two rows of `person_files` stay one read.
- **`_shared/devMcpCaseBrief.ts`**: the evidence, the document index, the theme marks, the themes, the matter's steps and documents, the team rows and the schedule blocks are paged; the jobs and developments are read by id a hundred at a time. A list past 5,000 rows is named in `held` with its table.
- **`supabase/functions/dev-mcp/index.ts`**: server 0.64.0; both descriptions say every source is paged.
- **Docs**: the two rows in `docs/dev-mcp/README.md`; `docs/EDGE_FUNCTIONS.md` → dev-mcp.

## Tests

`src/lib/devMcp/devMcpBigCase.test.ts`, on `deepCase` in `bigCaseFixture.ts`: the made-up case with every list past 200 rows (230 evidence records with two files each, 215 documents, 430 theme marks, 260 steps, 205 matter documents, 210 licenses, 204 reports, 240 jobs). The brief counts each list whole, keeps the newest rows of a shortened one and still fits the door. The file counts every record, report and license, and the oldest record still has both its files. A list of exactly 200 rows is whole and not called short. A list of 5,001 rows is named in `at_cap` on the file and in `held` on the brief. `newestFirst` and `readRowsByIds` have their own tests. The version pin moved in every test that holds one.

## Release order

Merge, then deploy `dev-mcp` (`npm run check:edge-drift` names it). Live check, as the dev: `get_person_file { brief: true }` on a large file answers `at_cap` null.
