The owner's ask (2026-09-28): a GC wanted "a procurement log update with what has been released and lead times". Plan + self-review + mock-up: https://claude.ai/artifact/7wZt8WtED2n9AMTgA3eDtV (required date = the stage window's start; the room card visible to anyone with the link; no reminder cadence). PR 1 of the plan: the log on Submittals and the recorded updates. The GC's room card is the PR after this.

## The kernel — `lib/submittals/procurementLog.ts` (13 tests)

- `buildProcurementLog({ items, records, tagStage, stageDates })` → one `ProcurementRow` per submittal tag (tag order) then the hand rows: **released** = the approval's date (never typed); **expected** = the house's typed date, else ordered + lead time (`expectedSource: 'house' | 'derived'`); **required** = the item's stage's window start; **float** = required − expected (null once delivered); **order by** = required − lead time while unordered; a `status` (delivered · ordered · released · sent_back · awaiting · not_submitted) and `late`. `procurementHeadline`, `floatText` ("12 d" · "−14 d" · "on site" · "order by 11/03"), `statusText`, `submittalWord`.
- The stage of a tag: `fixtureHead` ("(3) HS - HAND SINK" → HS), `tagMatchesFixture` (the normalized tag, else the tag's letters — HS ↔ HS-1), `stageOfWeights` (heaviest, earliest on a tie). The job's dates: `stageOfStageName` (rough / underground → Rough In; top out / above → Top Out; trim / finish → Trim Set), `stageDatesFromJob` (the earliest window start per stage across the job's Order stages).
- Updates: `snapshotRows`, `diffProcurementLog(previous, rows)` (released, ordered with PO, expected a → b with "(house)", delivered, sent back, newly behind, a new note, added to / gone from the log), `buildProcurementUpdateHtml` (changed rows first, amber; the one line; the footer that says where each column comes from), `procurementUpdateText` (the email).
- Dates are ISO strings, parsed at local noon (`parseIsoDate`, `addDays`, `daysBetween`, `shortDate`).

## The reads — `procurementLogIo.ts`

`loadProcurementRecords`, `loadProcurementUpdates` (newest first), `loadTagStagesForBid` (the bid's count rows + `loadStageSplitsForBid` → `effectiveSplit`, else `defaultSplitForFixture`), `loadStageDatesForBid` (the job made from the bid → its Order fixtures + `job_stage_windows`), `procurementItemsFrom` (the newest revision's items with the house names in one read).

## The panel — `SubmittalProcurementPanel.tsx` (render smoke)

Under the rows table on the newest revision: the table (Tag · Product with the house and the stage · Submittal · Released · Ordered · PO · Lead · Expected · Required · Float · Delivered · Note), date boxes that write on change and text boxes on blur (the first write inserts the tag's record, later ones update); the expected box is grey when derived, amber when the house said, disabled once delivered; a hand row takes its label, lead time ("2 wk" / "10 days" / "in stock") and stage, and has ×. **Send update…** opens the card: the changes since the last update, To (prefilled with the room's reviewers, kept for the record), one line for the GC, then **Record, print and copy** — an insert into `bid_procurement_updates`, the sheet in a new window, the text on the clipboard. **Print the log**, **+ Add item**, **Updates sent (n)** with Open on each. `onCounts` feeds the strip.

## The strip — `submittalJourney.ts`

An eighth stage, **Procure** (anchor `submittals-procure`), lit on its own: current once anything is released (or, before the panel reports, once any row is approved), done once every released row is delivered and nothing is late. The all-approved line now reads "The procurement log is next." Tests for the eight stages.
