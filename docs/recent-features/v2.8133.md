# v2.8133 — Before we start: a second answer on arrival cannot replace a No (2026-11-20)

Punch list #382, from the audit of PR 10 (v2.8110). One migration and no client change: `20261120140000_start_check_arrive_once.sql` (`docs/migrations/20261120140000_start_check_arrive_once.md`). No edge function.

## The fault

The crew's card **Is it as told?** is read once and answered later. Two of ours who reach a site together both have it open.

- Hector says **No** on a bullet and sends. The office's stage turns red.
- Luis, whose card was read before that, presses **Yes, all as told**.
- `start_check_arrive` kept Luis's press. The bullet Hector said No to was still on the list to look at, so it became a yes we saw, in Luis's name, on a second arrival.
- The office reads the newest arrival, so the red was gone and so was the No. Only Dispatch's line was left.

The read, `start_check_arrival_state`, already asked about a stage once. The door did not hold the same rule. It took a lock to hold two arrivals apart and never looked for the first.

## The fix

`start_check_arrive` now reads the stage's first arrival after its lock and refuses a second answer: *Hector Helper already answered for this stage.* Nothing is written. The card shows those words as it shows any refusal.

## Found by reading, not on a job

Production held one arrival when this was written, on a ZZ test job, and no real job had a list. Nobody's No was lost.

## Checked

The SQL bed `30_arrive.sql` has two new checks, 26 in all: the second answer is refused by name, and it kept nothing. The bed ran first in the SQL beds workflow, since Docker does not run on the Mac this was written on.

## Left for the owner

After a No the stage is never asked about again, on a later trip either. That is the built default, *asked once a stage*. Whether a second trip should ask again is on the card's audit.
