# v2.6514 — Adding a person makes a users row: every worker is a user from day one — PR 2 (punch list #260) (2026-11-04)

PR 2 of 5 on punch list #260 (the model: every worker a users row from day one, a login attached later — PR 1 is [v2.6511](v2.6511.md)). Until this PR every "add a person" in the app inserted a People record alone, with `account_user_id` NULL: a person who could hold no clock session and no Charged as, so a job they worked priced short by every day they were out (#254's first pricing, 2026-11-04).

## What changed

- **Migration `20261104200000_add_worker.sql`** ([`docs/migrations/`](../migrations/20261104200000_add_worker.md)): `add_worker(name, kind, email, phone, notes, start_date)` makes the users row (role from the kind, `login_attached_at` NULL, every flag its default) and the People record linked to it in one transaction, for the office roles (`is_office_staff()`); refuses a blank name, a kind outside the roster kinds and an address another users row holds, each with its reason. Bed scenarios W1–W5 in `supabase/tests/users_without_login/30_add_worker.sql`.
- **One kernel behind every add** (`src/lib/people/addWorker.ts`: `addWorkerArgs`, `readAddedWorker`, `addWorker`; typed by name until the types PR): People → Users → **Add to roster** (`usePeopleRoster.ts`), **Hire** with no email (`hireWrites.ts` `addHireWithoutLogin`, `HirePersonModal.tsx`'s roster step now answers the user id too), the Hiring board's **Add to roster** (`TeamProspectsTab.tsx`), the workflow step form's add-a-person (`StepFormModal.tsx`), the sub-sheet form (`JobsSubLaborFormModal.tsx`), the work-order assembler (`WorkOrderAssemblerModal.tsx`) and Banking's two attribute-to-a-new-person pickers. Each form shows the function's reason when it refuses. `createRosterRow` stays for the one path that links a roster row to a login a pre-v2.3701 invite made.
- **A salaried hire no longer needs a login**: `hirePlan` drops the rule (the workday template belongs to the users row, which now exists) and adds the Workday step for any salaried hire; the roster step's label reads *Person … on the roster with no login; a login can be attached later*.
- **The Users tab's chip reads the column**: the roster's users read carries `login_attached_at`; `buildUsersTabKindRoster` maps it; `UsersTabRow` shows *login* only when it is set, *no login* otherwise (with the title *A person with no sign-in — their hours, pay, portal and paperwork work without one; a login can be attached later*), and offers Imitate only for a login.
- **Guide** *add someone to the roster*: Add makes the person with no login, who can hold clock sessions, a Charged as, a portal, paperwork, sub sheets and pay from that day; a login can be attached later.
- Docs: ACCESS_CONTROL (the add door and the guarded `login_attached_at` column), PROJECT_DOCUMENTATION (`add_worker`), the card's status.
