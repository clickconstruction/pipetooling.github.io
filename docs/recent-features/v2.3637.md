# v2.3637 — Jobs: a saved card split refreshes the job's tag slices with its total (2026-09-20)

Item 3 of [`to-dos/dispatch-residuals.md`](../../to-dos/dispatch-residuals.md) (a v2.2870 residual). Client only.

`useJobsMercuryAllocations` builds three maps on the full load — `mercuryCardChargesByJobId`, the invoice-linked map and `mercuryTagChargesByJobId` (job → tag → $, v2.2725). `updateMercuryCardTotalForOneJob`, the post-save refresh, rewrote the first two for the job and left the third, so after a split the tag lines under the card total were last load's.

- **Kernel** `tagSliceForOneJob` in [`mercuryTagSplit.ts`](../../src/lib/mercuryTagSplit.ts): the job's own rows through `summarizeCardChargeAllocations` (the shared Internal-Transfers rule) and `sumTagChargesByJob` — so the entry is the one a reload would compute. A test asserts it **equals the bulk map's entry** for the same job with an excluded transfer in the rows, and that a job with no cost-line charges returns null (the caller drops the entry).
- **Hook**: the one-job refresh makes the same two lookups the bulk load makes (bank category per transaction, label per transaction), in parallel with the exclusions, and sets or deletes the job's slice. The callback stays stable; it reads the current tags through a ref.

The to-do had proposed a server-side `sum by job_id`. That remains the durable form for the **bulk** map's cost as `mercury_transaction_job_allocations` grows; the staleness it was listed for is fixed here without a migration.
