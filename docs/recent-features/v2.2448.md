# v2.2448 — Enter signs you in (2026-08-28)

Wendi: *"can't hit enter to login have to press the button."*

Investigated first: the sign-in page has been a proper `<form onSubmit>` with a
`type="submit"` button since the first commit, nothing in the app intercepts keydown on
that route (verified with an instrumented listener — the keystroke arrives unprevented),
and `form.requestSubmit()` — the same pipeline implicit submission uses — works. So the
app was formally correct, and the failure lives in the machinery between the keyboard and
the form: implicit form submission is browser behavior, and password-manager overlays /
autofill dropdowns / PWA-webview quirks are a well-known class of things that swallow it.
(The in-app browser pane's own CDP key injection reproduces the class exactly: a keydown
reaching `input#password` with `key: ""` and no submission.)

Fix: stop depending on implicit submission. Both sign-in fields now carry an explicit
`onKeyDown` — Enter (outside IME composition) calls `preventDefault()` and
`form.requestSubmit()`, which runs the identical validation + submit path; a
`dispatchEvent(submit)` fallback covers pre-`requestSubmit` engines. In browsers where
Enter already worked, behavior is byte-identical (the implicit path is pre-empted, so no
double submit; the `loading` flag guards re-entry regardless).

`PasswordInput` gains an optional forwarded `onKeyDown` prop. New
`src/pages/SignIn.render.test.tsx` (5 tests) pins the contract — jsdom implements no
implicit submission at all, so the tests pass only through the explicit handler, which is
precisely the environment class being defended against. Button click and non-Enter keys
covered too.

Noted in passing, NOT changed here (product/security decision, not a bug fix): sign-in
saves the password in plaintext `localStorage` (`signin_password`) to pre-fill the form.
