# v2.6168 — Plan sets on a bid: the ground (2026-10-30)

The owner's third item of the Bids tab day, PR 1 of 2: *improving the plans upload such that multiple sets of plans can be uploaded all with their own name, memo, date, and link*. This PR is the table alone, so it can be on `main` and pushed before the client that reads it merges (`CLAUDE.md` → Deploy model: a client that calls a table only a pending migration creates holds the deploy). The surfaces — the bid form's Plan sets field, the Bid Board's picker — are v2.6169.

- **Migration `20261030200000_bid_plan_sets`** (`docs/migrations/20261030200000_bid_plan_sets.md`): `bid_plan_sets`, one row per set of plans on a bid — `name`, `memo`, `plan_date` (a civil date), `link` (a Drive link, the shape `bids.plans_link` takes), and what `plan-fetch`'s probe last read behind the link: `file_name`, `file_size`, `file_count`, `checked_at`, `check_note`. RLS: `SELECT` by `can_access_bid_for_pricing(bid_id)`; the three writes by the same gate and the five roles that fill the bid form's Plans section. The three house calls end it.
- **What stays**: `bids.plans_link` keeps meaning *the set the robot reads* — the robots' dispatch, `plan-fetch`, the Plans panel, the readiness line and the plans-waiting count are untouched. A bid whose link is on none of its rows will read as one set, the link on the bid itself (the fail-soft the CountTooling projects use), so nothing is backfilled.
- **Types**: `src/types/database.ts` hand-carries the new table; the next `chore(types)` regenerates it.
- **Plans stay Drive links, never an upload** (the owner, 2026-09-29, `bidPlansFolder.ts`): a "set" is a Drive folder or file link with its own name, memo and date; the robots read Drive and nothing else.
