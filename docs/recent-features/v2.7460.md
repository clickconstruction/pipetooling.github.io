# v2.7460 — Lien desk: a place to keep what was mailed, PR 1 of 2, the column (2026-11-16)

The owner, 2026-11-16, on the Lien desk's run: "after we print we should have the user upload what they are going to mail for easier reference later of what actually went out." Asked whether the office scans the whole stack once or one notice at a time, he picked **one file per notice**. Migration only: no client change, no edge function.

## What changed

- `supabase/migrations/20261117001500_lien_desk_mailed_copies.sql`: `job_lien_desk_items.mailed_copies`, a jsonb list, `[]` by default, held to an array by a check. Each entry is `{ url, driveFileId, name, at, by }`. See [`docs/migrations/20261117001500_lien_desk_mailed_copies.md`](../migrations/20261117001500_lien_desk_mailed_copies.md).

## Why a column, and why Drive

- The file itself goes where a job's other sent papers go: the job's own Drive folder, through `drive-link`'s `put` (`putJobFolderFile(jobId, 'sent', file)`, 10 MB), the same call the Documents tab's *Add a file* makes. So the job holds exactly its own mailed notice, and it can be found from Documents with no new screen.
- The lien file store (`lien-release-documents`) was the other choice. It holds 5 MB, takes PNG and PDF only, and a master reads only his own releases' folders there.
- The run can be closed between the print and the mail, so the notice has to remember the file until its mailing is recorded. The row's `fields` could not hold it: `lienFieldsHash` reads `fields`, and a change there makes the leader's signature read as stale. Hence a column of its own.
- When the mailing is recorded, the record takes the first link (`job_lien_filings.document_url`, the *Saved copy* the run already writes), so the Lien window shows it with no change there.
