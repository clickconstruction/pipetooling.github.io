# v2.6417 — Search every file deeply: the sweep reconciles, so a file moved into the Shared Drive is indexed whatever date it carries (2026-11-02)

Punch list #240, the owner's choice of 2026-11-02 for new files from here on: the sweep plus a reconcile step. The `file-index-sweep` cron lists the Shared Drive by Drive's `modifiedTime` since its stamp, and a file moved into the drive keeps its old modified time, so the sweep never listed it: 672 of the 775 job rows carry a date older than the drive itself. The one-time fill (v2.6364's `--fill`) had cleared the backlog, and nothing stopped new ones arriving. No migration; `file-index-sweep` and `drive-link` (which bundles the check kernel) redeployed after the merge.

- **`filesWithNoRow(files, rowIds)`** in `_shared/fileIndexCheckKernel.ts`: the listed files with no row, newest first, a file listed twice once, generic over the file so the sweep keeps each file's full Drive fields for the pass and the check its lighter shape. The check's `reconcile()` reads through it now, never a second copy. `ReconcileStep` and `reconcileStepWords` give the step's counts and its one log line.
- **`_shared/fileIndexReconcile.ts`**: `reconcileSweep(ctx, { max })` lists the whole drive with the sweep's own lister from the dawn (`filesChangedSince(ctx, DAWN, CHECK_FILES_MAX, true)`, as `indexCheck` does: a dozen Drive lists at today's 2,348 files), reads every row's id a thousand at a time with `.order().range()` until a short page (`allIndexRowIds`; PostgREST caps an answer at a thousand and says nothing), and hands the files with no row to `indexFiles`, newest first, up to the sweep's `limit` (40), with the pass's own `startedMs` taken after the listing so the lists never eat its budget; the request's parse spend (`ctx.spend`) stays shared with the stamped pass, since the worker's CPU is.
- **One call in the sweep, as the run's last step**, after the stamp is written and the rechecks are done, in its own try/catch: a heavy PDF that stops the worker, or a Drive error, costs neither the stamp nor the rechecks. Skipped when the stamped pass left files behind (`remaining`, or Drive had more), so a busy stream is drained first. Its result never reaches `sweepStamp` or the cursor: those old dates would move the stamp backwards. The answer carries `reconcile: { filesInDrive, capped, rows, noRow, taken, indexed, held, ms }`, null when skipped.
- **One log line a run**, counts only and never a file's name: *file-index-sweep reconcile: 2,348 files in Drive, 4,209 rows, 3 with no row, 3 taken, 3 indexed, 1 held, 4,312 ms.* Every cron call gives up at five seconds, so `net._http_response` has never kept a sweep's answer, and the cron secret is not local; the line is read through the management API's logs endpoint with `source = 'function_logs'` (`scripts/pg-logs.sh` shows the call, with `postgres_logs` in its place).
- **`scripts/file-index-check.ts`** says the sweep now takes a file with no row and a file changed since its row, forty a run, and that `--fill` takes the files with no row now, for when you cannot wait. The guide *Find a file when you do not know where it is* says a file moved in from another folder is read too.
- **Cost**: twelve Drive lists a run, about 1,700 a day, far under Drive's quota; a quiet drive with no file missing costs the lists and one row read, no writes. An edge function has about two seconds of CPU per request, and being last is the protection: if the logs show the worker stopped on most runs, the step moves to its own cron request (a migration), rather than being trimmed.
- **Not here**: Drive's `changes.list`; bid folders outside the Shared Drive (1,861 rows, the owner's open decision 4: the listing cannot see them, so their rows are never treated as gone); the runner's `--retry`; OCR, embeddings, and rows with no home.
- **Tests**: `src/lib/documents/fileIndexCheckKernel.test.ts` takes the helper (the whole file kept, newest first, a file listed twice once, one with no date last, a Set or a Map of ids, empty when every file has a row, and `reconcile` reading through it) and the step's words (counts only, a capped listing marked, no file named).
