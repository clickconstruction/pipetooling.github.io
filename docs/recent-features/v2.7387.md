# v2.7387 — Box labels: change the tape mid run and keep going (2026-11-15)

Taunya, 2026-11-15, on the first real run of the new labels: "I just printed my first batch, and Halfway through G37 I ran out of tape. Now I want to be able to replace the tape and keep going easily and restart from the app". Client only: no migration, no edge function.

## What was wrong

v2.7374 kept the rest of a stopped run, but only while the window stayed open, and only if the printer could be reached again. A printer that stops for want of tape still answers. So the window reconnected to it at once, read *no tape*, greyed the print press, and never asked the printer again: `link.status` was read at the connection and before each label of a run, and a grey press starts no run. A new cassette changed nothing on the screen. The only way on was to close the window, which threw away the boxes it had unticked and the one it knew was part way. The same reconnect also cleared the red line that said how many strips went and why (`adopt` cleared the slip).

## What changed

- **The window asks the printer again.** `PtouchLink.refresh()` in `ptouchUsb.ts` asks for the status and keeps the answer on the link. `ptouchNeedsRecheck(status)` in `ptouchRaster.ts` (pure) is a connected printer that cannot print as it stands: an error, no tape, or a tape the label is not laid out for. While that holds and nothing prints, both tape windows call `refresh` every `PTOUCH_RECHECK_MS` (3 seconds); a new cassette turns the printer's line to *24 mm tape · ready* and the press comes back, with no press. A printer that stops answering the re-check is let go, and the press becomes **Connect the P-touch**.
- **The foot says why the press is grey**, right above it: `ptouchCannotPrintWords` (*There is no tape in the printer.*), then *Put in the tape and close the cover. The window checks the printer by itself.*, with a quiet **Check the printer again** for a person who does not want to wait three seconds.
- **A stopped run is kept for the day.** `StoppedRun` in `labelPick.ts` (pure): the job, the day, the copies, the boxes left out and the one part way. `stoppedRunToKeep` writes it when a run ends part way (`pt.labels.stoppedRun` in `labelPrefs.ts`); `stoppedRunToResume` hands it back only for the same job on the same day, only for boxes the job still has, and only while something is left to print. Print labels opens on it with *Picked up where today's run stopped. 36 boxes are done and unticked. G37 has 3 of its 5 strips to go. Press Every box to start over.* A run that prints whole, or **Every box**, forgets it.
- **The red line stays.** An automatic reconnect no longer clears it; the **Connect the P-touch** press and the next run do.
- The two guides and the map's office Labels paragraph say it.

## The picks

- **A poll, not only a press.** The ask was to keep going easily. Three seconds is short enough to feel like the window noticed, and the status request is one small exchange with a printer that is doing nothing. It is never sent while a label prints: the effect runs only while the window is not busy.
- **Kept on the device, for the day.** Print labels has no run in the database. The day's limit is so tomorrow's window opens with every box ticked and nobody prints a short run by surprise; the line at the foot and **Every box** are the way out the same day.
- **Print blank stickers gets the re-check and not the kept run.** Its runs are in the database, and the Runs fold already has **Print the rest** for the stickers still blank.
- **No name for "the tape ran out" yet.** The printer's status has a bit for the end of the tape, but the reference this was written from could not be checked for this model today, so that bit still reads *The printer reported an error.* What the red line said on Taunya's screen will settle it.

## Tests

`labelPick.test.ts` (20, six new: what is kept, read back through storage, the same job and day, a fresh window otherwise, a run stopped inside its first box, the words), `ptouchRaster.test.ts` (the re-check and why). Smokes, `LabelsPrintModal.usb.render.test.tsx` (15): a new cassette and **Check the printer again**; the window asking by itself and stopping once the printer is ready; the tape running out mid run, then one press printing exactly the rest with the red line still there; a window closed and opened on the rest, and **Every box** starting over. `PrintStickersModal.usb.render.test.tsx`: the re-check.

The real window was also run against a stand-in for the printer on `navigator.usb` whose cassette ran out after seven strips: the window read no tape, saw the new cassette on its first ask, and the next run started at the part-way box's missing strip.
