# v2.6511 — Every worker is a users row from day one; a login is attached later — PR 1, the migration (punch list #260) (2026-11-04)

The owner, 2026-11-04, after punch list #254 priced its first job and five of that job's days still waited on people with no login: "What if we treated all people as just users with no login? this would make turning a person into a user easier than it has been previously". The design spike (card #260, PR #7030) answered yes: the auth server's admin create-user has taken a chosen `id` since GoTrue v2.155.0 (prod runs v2.197.0), so a login can be attached to an existing `users.id`; the one key in the way is `users_id_fkey`; 592 foreign keys already point at `public.users`, so a users row with no login flows through the clock, the standings, the salary schedule and the approvals unchanged. The owner chose the model over PR #7020 (a parallel `people_pay_record_days` table, closed unmerged). This is PR 1 of 5: the schema, with nothing on screen changing yet.

## What changed

- **Migration `20261104190000_users_login_attached_at.sql`** ([`docs/migrations/`](../migrations/20261104190000_users_login_attached_at.md)): `users_id_fkey` dropped; `users.login_attached_at` (NULL = a worker with no login), backfilled for every existing login; `users.email` nullable under `users_login_has_email` (a row with a login has an address; `users_email_key` stays); `handle_new_user` lands on the existing row when the auth user was created with its id (`ON CONFLICT (id) DO UPDATE` — `login_attached_at` set, the login's address taken, name, role and every other column kept); a new `on_auth_user_deleted` trigger detaches instead of the cascade that deleted the users row and every clock session under it; `users_guard_privileged_columns` refuses a client write to `login_attached_at`; `roster_people.has_login` reads the column.
- **`invite-user`**: its replace-a-pending-invite path deletes the pending `users` row itself, since deleting the auth account no longer cascades into it (a pending invite has no days; the fresh invite's row would otherwise land on `users_email_key`). Redeploy after the push.
- **Bed `supabase/tests/users_without_login/`** (`scripts/pgtest-users-without-login.sh`, in `scripts/sql-beds.txt`; runs locally with `PGTEST_PGBIN`): prod's `auth.users` / `auth.identities` shapes, the baseline `users` with its key and triggers, the roster view; `10_before.sql` shows today's refusal and today's cascade; the migration twice; `20_scenarios.sql` walks a worker with no login (B2), the roster view (B3), two days through `import_clock_sessions` unchanged (B4), the dev's RLS read and why `auth.uid()` checks are fine (B5), the guard (B6), the receiver FK that PR 5 re-points (F), a login attached on the same id with name, role, standing, days and the People link unchanged (C), a fresh id still inserting (C2), the sign-in sync (D), the login taken away with the worker and days kept (E), a re-attach taking the new address (E2).

## What does not change yet
