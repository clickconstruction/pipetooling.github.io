# v2.2995 — chore(db): the master_assistants / master_shares views get opaque id columns (2026-09-07)

Follow-up to Phase 5 ([v2.2987](v2.2987.md)). One migration, `20260907060000_grant_views_opaque_columns.sql` ([doc](../migrations/20260907060000_grant_views_opaque_columns.md)) — pushed by the agent after merge.

Found while regenerating `database.ts` after the Phase 5 push: PostgREST traces plain view columns to their base column, so every `users(id)` foreign key gained four relationships through the two views (+8.4k lines of `Relationships`, `Type instantiation is excessively deep` in `useBidPricingEngine` / `scheduleDispatchHub`). Wrapping each id in a `CASE` keeps the value and type and drops the trace. Types are regenerated in the next PR.

Gotcha for future views over `users`: never expose `users.id` as a bare column in a view unless you want every users FK to embed through it.
