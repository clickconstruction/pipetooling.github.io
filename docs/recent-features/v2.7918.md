# v2.7918 — Robots: an assistant can move a robot between read-only and its own bids (2026-11-19)

A new pair on `dev-mcp` (server 0.108.0, 133 write verbs, 80 naming no RPC, 184 tools): **`plan_twin_rung`** → **`apply_twin_rung`**. The owner, 2026-11-19: "build the next gap: the rung flip".

## Why

A twin the seat makes with `plan_twin` stands read-only. Moving it to fenced writes was a press on Settings → System → Digital twins, Graduate ↑ on the twin's row. The audit of what an agent can stand up alone listed it as the third gap.

## What it does

It moves a twin between the two rungs the ladder has built, as the panel's own write does (`DigitalTwinsPanel.setRung`).

- `rung = { twin, to }`. The twin is named by its users.id or its fleet address.
- `to: 1` is read-only. Every write the twin's own signed-in session tries is refused.
- `to: 2` is fenced writes. The twin write fence binds it to bids it made or is the assigned estimator on.
- `to: 3` is refused in words. Production is not built, here or in the panel.

## The plan

- It reads the twin as the dev through `twinRefQuery`, so a row that is not a twin is never found.
- It reads the twin's live keys by `id`, `label` and `created_at`. No hash and no usage date is read.
- It answers the rung the twin stands on, the rung it would stand on, and the keys that gain or lose writes.
- The hash commits to the rung and to those keys. A rung moved or a key minted or revoked since the plan refuses the apply.
- Refused in words: no such twin, an archived twin, a twin already on that rung.

## The write

One PATCH of `read_only` on the twin's `users` row, as the dev under the users table's dev update policy. It is held to a row still a twin, still live and still on the rung the plan read. The reply says `moved` and the rung the twin stands on. The way back is the same pair with the other rung.

## What the rung governs

The rung binds the twin's own signed-in session, the browser link `mint_session` gives. `twin-mcp`'s verbs write as the service role and never read it, so a shadow or a backtest runs the same on either rung. CountTooling has no read-only, so nothing is sent there, as the panel sends nothing.

## Also: a key in use can be revoked

`plan_twin_key_revoke`'s hash committed to each key's `last_used_at` and `last_seen_at`. `twin-mcp` stamps `last_seen_at` once a minute while a robot works, so the apply for a key in use could answer that the plan no longer matched. `planCommitment` now drops the two dates for that pair (`twinKeyCommitment`). The plan still shows them. Found by reading the code while building the rung pair: the revoke has not been run against a live key.

## Words amended

`plan_twin`'s plan and its closing line named the rung and a key's revoke as presses in the panel. They name `plan_twin_rung` and `plan_twin_key_revoke` now.
