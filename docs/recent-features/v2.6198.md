# v2.6198 — Offline in the field: the clock row stays, a kept clock-out reads true, and a kept note has your name (2026-10-30)

Three defects the live test of punch list #163's offline field queue found on clicktooling.com on 2026-10-30 (the train: v2.6074, v2.6099, v2.6100, v2.6101). The press itself held: a clock-in, a note and a clock-out sent with no signal each landed in order at their pressed times. What failed was the screen around the presses.

## What the live test found, and why

1. **After an offline clock-in the Dashboard's top row went** (the clock with its timer and Clock Out, Job Report, My Spend) and so did the header's role buttons, until a reload. The clock-in was not the cause. auth-js announces the session again (`SIGNED_IN`) every time the page comes back to the front, and another tab's sign-in renewal reaches this one by `BroadcastChannel`. Each announcement makes `useAuth` read the person's `users` row again. With no signal that read failed at the fetch layer, and `shouldRetryRoleRead` read it again only on a freeze code or while the app-health kernel said slow or unreachable, never offline. So the failure settled: role, name and flags went null. `DashboardPinnedQuickRow` draws its row only when `role != null`, and the header's buttons read the role. Nothing read the role again for the same person until the next announcement, so the signal coming back and the press landing changed nothing.
2. **Under a clock-out kept on the phone the clock drew the red write sentence** *No connection — the app couldn't reach the server, so nothing was saved* with Try again. The new press changed the clock's outbox signature, which read the clock again at once. With no signal that read failed, and `fetchSessions` drew the failure on v2.4350's line in the write wording of `networkErrorMessage.ts`.
3. **A note written offline read "Unknown" as its author until it landed.** The kept note's row carries `useAuth`'s `profileName`, which defect 1 had just set to null: the note at 9:58 came after the 9:57 announcement. The panel draws `author.name` or *Unknown*.

## What changed

- **A lost signal is not a missing role** ([`appHealth.ts`](../../src/lib/appHealth.ts) `shouldRetryRoleRead`, [`useAuth.ts`](../../src/hooks/useAuth.ts)). A role read that never reached the server is read again every 5 s, like a freeze's, and is never settled as null. The class comes from `classifyResultError`: status 0, or the engine's `TypeError` with no code. The role, the name and the flags already read stay on screen meanwhile. A refusal is still final, and an aborted read still waits for the slow rule. Only the same person keeps them: when the session changes to another person (another account, View as), the last person's role and name are cleared at once, so no one wears them while a read with no signal is read again. On a cold open with no signal the gate's 4 s watchdog still lets the app draw, and the role arrives when the read lands. This one change fixes defects 1 and 3.
- **The clock's read in read words** ([`ClockInOutButton.tsx`](../../src/components/ClockInOutButton.tsx)). A read that never reached the server draws on `OfflineRetryPanel` with `idempotent`, in the clock's words `CLOCK_READ_OFFLINE_WORDS`: *No connection, so the clock could not load today's time. It loads again when the signal is back.* It reads again by itself on the `online` event. The panel and its kernel ([`offlineRecoveryState.ts`](../../src/lib/offlineRecoveryState.ts)) take `offlineMessage`, a read's own words in place of the write sentence; every other panel is unchanged. A failure that is not the network keeps v2.4350's line and its Try again (the stolen sign-in lock).
- **A kept press reads nothing** ([`pendingSession.ts`](../../src/lib/offline/pendingSession.ts) `clockReadsAgain`). The clock reads again when a clock press it already knew landed, was refused or is gone, as PR 2 meant. It also reads again when a press it had not seen appears while the browser says online, such as one read back from the device after the clock's first read. A press kept with no signal was drawn by its own handler and sets off nothing.
- **A read that lands before a press does** ([`pendingSession.ts`](../../src/lib/offline/pendingSession.ts) `clockReadWithKeptPresses`). The clock lays the clock presses still on the phone over every read. A clock-out waiting closes its session at the pressed moment, on a real session or on one still on the phone. A clock-in waiting is a stretch of today, and the open session when nothing else is open. So the panel's read on `online`, racing the replay's send, never reopens a session the person clocked out of. A refused or landed press lays nothing.
- **Guides**: *keep working when the signal drops* says the clock shows a kept Clock Out as clocked out, and what its red line with no signal means. *know what No connection means and what was saved* says the four presses that wait on the phone work another way, since the clock's new line has the panel's What this means door.
- **`docs/TROUBLESHOOTING.md`**: the clock's read sentence has its row beside the write sentence.

## Known, not built

- **Every other read panel still says the write sentence** (*nothing was saved*) for a lost signal, as v2.5962 left it. `offlineMessage` is the door; making `idempotent` mean read words everywhere touches about 20 panels and their smokes, a sweep of its own.
- **A cold open with no signal and a clock-in kept from before** reads Clock In until a read lands. The overlay rides on a read, and with no signal none lands. The amber line says the press waits. Drawing the clock from the kept presses alone needs the clock's state derived from the last read and the queue, not set by each handler.
- **The Job Mode card** keeps its own read: after a kept clock-out with no signal its kept day still shows the job from the last read, as #183's kept day is meant to.
- **The guide *clock in and out with Job Mode*** (`job-mode-clocking`), in its *When you have no signal* section, still describes the clock press before #163: No connection, Retry, nothing recorded.
