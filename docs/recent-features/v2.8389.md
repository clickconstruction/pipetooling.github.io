# v2.8389 — Documents → Agreements finds who each paper is with by the shortest way (2026-11-23)

Punch list #430, the first of its two views. One migration on a view. No client change, no edge function.

## What was wrong

`agreements_on_file`, the view behind Documents → Agreements and the GC portal's paper lines, finds the customer, the supply house and the trade company behind a party's paper with three joins written as an equality onto a `COALESCE`. Postgres does not use such a join as an index condition on a table with row policies (v2.8301 taught it on Documents → Photos), so it filtered the whole table under its policies instead of looking the record up by its key.

## What changed

- **The three joins are a `CASE`** ([`20261123190000_agreements_party_join_by_key.sql`](../../supabase/migrations/20261123190000_agreements_party_join_by_key.sql), [its doc](../migrations/20261123190000_agreements_party_join_by_key.md)): the contact's own record when it names one, the record of the person the contact is when it does not. The same record, found by its key. The rest of the view is word for word what `20261123083000` wrote.
- **The bed holds it**: `paper-party` section 9 rebuilds the view as it stood, asserts five roles read the same lines from both, and reads the plan for an index condition on each of the three tables.

## Checked

- Not on prod: no read-only path to a plan was open from this session, so the card says so. A one-line read of the view as a dev answered.
- The shape on a local Postgres 15 under a column-reading policy: `Join Filter` over the whole table with the `COALESCE`, `Index Cond` on the primary key with the `CASE`.
- Not run here: the SQL bed, which needs Docker. It runs on the PR.
