# v2.2872 — The invite moment: role is an explicit choice, one human role label, training mode from the first minute (2026-09-05)

Journey-map Phase 4, Tier-2 #39 (J24 new-hire-first-day F2/F3/F6/F9, J25). The first thing the company ever says to a new employee was "You've been invited to join … as a **Master_technician**", and the dialog that sent it defaulted to that role — the second-most-privileged one — so one forgotten dropdown shipped a field hire with every office route. Training mode, the feature built for exactly this moment, was discoverable only from a hover tooltip on the row that exists *after* the account does.

## No privileged default

- `useActiveAccountsManagement` opens **Invite via email** and **Manually add user** with `inviteRole` / `manualAddRole` = `''` (type `RoleChoice = UserRole | ''`), never `master_technician`. Both `<select>`s carry a disabled placeholder `Choose a role…`, are `required`, and the label reads **Role \***.
- **Send invite** / **Create user** are disabled until `inviteFormValid(draft)` passes — email non-blank, a role chosen, and (manual add) a password. The handlers re-check and refuse with "Choose a role before …" so a stale button can't submit.
- Kernel: `src/lib/inviteUserForm.ts` — `inviteFormValid`, `roleChosen`, `roleTakesServiceTypes` (replaces the three inline `role === 'estimator' || …` checks), `userCreatedTelemetryTarget`, `roleChangeConfirmMessage`. 9 tests.

## One human label — dialog, Desk, email

- `src/lib/roleLabels.ts` → `HUMAN_ROLE_LABELS` + `humanRoleLabel(role)`, the GLOSSARY / ACCESS_CONTROL heading vocabulary: Dev · **Master** · Assistant · Controller · Estimator · Primary · Superintendent · Subcontractor · **Helper**. Unknown slugs fall back to "Snake_case" → "Snake case"; blank → `—`.
- `supabase/functions/_shared/roleLabels.ts` is the Deno twin; `roleLabels.test.ts` imports both and fails when the maps or outputs drift (the `publicEventThrottle` import pattern).
- Consumers: `ActiveAccountsPanel` (row select + both dialogs), `PersonDeskAccessSection` (its private `ROLES` label table is gone — `ROLE_ORDER` keeps the least-privilege-first order and labels via the helper), `invite-user` (email `{{role}}` — the local `displayLabelForRole` is deleted). `displayLabelForUserRole` in `userRoleDisplay.ts` now delegates to the helper, so `GuideBrowser` and Active Accounts search follow. `roleGuideLens.LENS_LABEL` ("Sub") is left alone — it is a phone-width chip with its own constraint.
- The live prod `email_templates.invitation` row is branded "Pipetooling" — that is **data**, editable at Settings → Templates → Invitation Email, which already exists; nothing in this PR touches it.

## Training mode at the invite moment

- Both dialogs gain **Start in training mode (read-only)** with the hint "They can browse everything their role sees, but every change is blocked until a dev switches it off. Clocking in and out still works."
- `invite-user` and `create-user` accept `read_only?: boolean` (400 `read_only must be true or false` on any other type; absent = `false`, so old clients behave as before) and write `read_only` on the `public.users` upsert alongside role/name. No migration: the service-role upsert passes `users_guard_privileged_columns` (`auth.uid()` IS NULL → allow) and `handle_new_user`'s insert is `ON CONFLICT DO NOTHING`, so the explicit upsert is what lands. Both responses echo `read_only`.
- **Deploy after merge:** `supabase functions deploy invite-user` and `supabase functions deploy create-user` — `create-user` keeps `verify_jwt = false` in `config.toml`.

## Confirm on the Active Accounts role select (Desk precedent)

- `updateRole` in the hook now no-ops on the same role and otherwise awaits `confirmDialog({ message: roleChangeConfirmMessage(name, from, to), confirmLabel: 'Change role' })` before the write — the copy the Person Desk already uses ("… Their navigation and access change on next load."). The select is controlled by `users`, so Cancel leaves it on the current role.

## Telemetry

- `recordNavClick(user, role, 'user_invited', '#<role>[:training]')` after a successful invite; `'user_created'` with the same target after Manually add. Rides `ui_nav_clicks`, no schema change.

## Docs

- `docs/EDGE_FUNCTIONS.md` — `invite-user` / `create-user` request params (`read_only`), flow, roles list (9, incl. `controller`), called-from paths.
- `docs/ACCESS_CONTROL.md` — Read-only (training) mode: flag at invite.

## Not changed

- People → Users "Invite as user" (`People.tsx inviteAsUser`) and Add-to-roster "Also invite them to sign in" derive the role from the roster kind — already least-privilege; they send no `read_only`, so those invitees start with writes on as before.
- `/accept-invite` (Tier-1 #1), the "resend" vocabulary (J24 F5), and the template brand are out of scope.
