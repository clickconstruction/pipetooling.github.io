# v2.8316 — HR files: the dev seat's `plan_hr_entry` and `plan_person_doc` name the roster row's id (2026-11-22)

Punch list #315, a loose end the live walk of v2.7976 found on 2026-11-20 and the card has carried since. `dev-mcp` 0.127.0. Words only: no migration, no new verb, no screen.

## What was wrong

`plan_hr_entry` and `plan_person_doc` told a caller to take `person_id` from `find_person`. That verb reads `users` and answers a login's `users.id`. Both doors look the id up in `people`: `dev_hr_entry_write` and `dev_person_doc_write` each run `FROM public.people pe WHERE pe.id = v_person_id` and raise *person … not found* otherwise. So a caller who did as the words said was refused, with no word on which id the door wanted.

Four places said it:

- the `entry` description on `plan_hr_entry`: *person_id (find_person)*;
- the `doc` description on `plan_person_doc`: *person_id (a people.id: find_person)*;
- the refusal for an `entry` with no usable `person_id`: *person_id is a people.id (find_person)*;
- the refusal that spells out the shape of `doc`.

`plan_case` and `plan_engagement` have said it right since v2.8000.

## What changed

The two tool descriptions (`supabase/functions/dev-mcp/index.ts`) now read as those two do: *person_id (the people.id get_case_brief answers in person.id; not find_person's users.id)*. The two refusals (`supabase/functions/_shared/devMcpWrites.ts`) read as `caseShape` and the engagement shape do: *the roster row's people.id, as get_case_brief and get_person_file answer it in person.id; find_person answers a login's users.id, which this door refuses*.

Nothing else moves. The doors, the plan hash and what each verb writes are as they were. A plan made before the deploy still applies after it: the hash covers the payload and the dry run's reply, never the description.
