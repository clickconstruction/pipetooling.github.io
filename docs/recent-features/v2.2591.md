# v2.2591 — AR link-vs-create guard (2026-09-01)

Variant D of the owner-picked AR modal plan (mockups: "Who Sent This Check";
last of the four — A v2.2584, C v2.2585, B v2.2590). The most error-prone step
for a non-expert: if someone already marked a bill paid by hand, the deposit
must be **linked** to that recorded payment (the v2.1191 "Payment received"
allocation kind) — allocating it as a new payment double-counts. Choosing
correctly required knowing the data model; now the modal notices.

- **New kernel `src/lib/jobs/arLinkCollision.ts`** (3 tests):
  `findRecordedPaymentCollisions(jobId, allocationAmount, recordedPayments)`
  — same-job, cents-equal (sign-insensitive) matches among the unlinked
  recorded payments the modal already fetches
  (`list_unlinked_payments_for_bank_payments`). Detection only; the assistant
  decides.
- **Modal UI (`BankPaymentsModal`)**: picking a billed line (chip, combo, or
  by hand) whose job carries a colliding payment renders an amber steer under
  the pick — "This payment may already be recorded… Linking it avoids
  counting the money twice" — with **Link that payment instead** (flips the
  line to the Payment-received kind with that row preselected and the amount
  locked; both mechanisms are the existing v2.1191 ones) and **It's a
  different payment** (dismisses per line; dismissals reset when the selected
  deposit changes). Payments already taken by another allocation line don't
  re-trigger the steer.
- New render smoke `BankPaymentsModalLinkGuard.render.test.tsx` (steer →
  link flip with locked amount; dismiss path). Help guide updated.
  Client-only; no schema or RPC changes.
