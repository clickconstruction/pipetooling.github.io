# v2.7553 — Stickers already reserved: choose how many copies of each to print (2026-11-16)

Punch list #329, following v2.7523. The owner pressed the new *Print the 58 reserved stickers* press, the stickers window opened on his run, and he wrote: *I need to be able to choose how many copies to be able to print, for example for each of these I need to print 5.* Client only, no migration.

## What was there

**Copies of each** was in the ask alone, where a new run is made. A window opened on a run already made (the reserved line's press, the Runs fold's **Reprint** and **Print the rest**, or a run just minted) printed the count the run was made with and offered no way to see it as a choice or change it. His run happened to be made with five, so the head already read *5 strips each. 290 strips.*, with nothing to press.

## What changed

- `PrintStickersModal.tsx` draws the same stepper on a run, under **From** and **to** (`copiesRow`, one piece of JSX for the ask and the run). It opens on the run's own `copies`, one to `TAPE_COPIES_MAX` (six), and rests while the printer runs.
- The head (`runStripsWords`, now handed the picked count), the press (*Print 58 sets, G93 to G150*), the strips sent over USB and the copies laid out for the browser's print window all follow it.
- It changes that print alone. `setRunCopies` does not write the device's remembered count (`labelPrefs.ts`), which belongs to the next new run, and nothing writes the run's row: no client writes a sticker or a run.
- `runCopiesWords` (`stickerRun.ts`) is the line beside it: *Every copy opens the same box.*, and once the count differs, *The run was made with 5 of each.* first.

## Checked

The kernel's test, render smokes through the print window (the count, the head, the press and the strips on the page follow; the device's count is not written) and over USB (four stickers at five each send twenty strips, nothing minted). Not pressed on the live screen by this session.
