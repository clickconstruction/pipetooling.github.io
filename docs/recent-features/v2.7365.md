# v2.7365 — Scores: the numbers are worked out on the server, so no wage comes to the browser (2026-11-15)

Punch list #360, PR 4 of the team scorecard's train. The card planned this as `team_scores(p_from, p_to)`, a SQL function "with the loader's arithmetic". Building it found that the loader's arithmetic is the Overhead page's pool (office and bid time at the office wage, office parts less internal transfers, tally parts), earned revenue, and the Costs tab's charge events, about 1,500 lines of TypeScript whose own header says *no SQL re-implementation, no second kernel to drift*. Three ways on were put to Taunya on 2026-11-15; she picked the edge function.

## What ships

- **`team-scores`**, an edge function ([`supabase/functions/team-scores/index.ts`](../../supabase/functions/team-scores/index.ts)): `POST { windowDays: 28 | 56 | 90 }`, signed in. It checks the scoreboard's gate itself (a real account, not archived, that is a dev, the owner, or has payroll access by `has_payroll_access()` asked as the caller), makes the scorecard's reads as the service role and answers with `ScorecardWire`: hours and dollars by job, the hurdle, the estimator rows. No person's wage is in it. It runs the app's own `readScorecard` and kernels from the kernel copy, as the Bridge's weekly sheet runs the Bridge's.
- **The reads take a client.** Seven files gain a `*Reads.ts` with the client passed in, and the app-side file becomes a thin binder of the app's client, the shape the overhead scan has had since v2.5880: `jobs/jobDayLedgerReads.ts`, `jobMaterialsCostSnapshotReads.ts`, `inKind/inKindCostReads.ts`, `jobs/cardChargeExclusionsReads.ts`, `banking/categoryTagsReads.ts`, `jobs/jobChargesTimelineReads.ts`, `scorecard/scorecardReads.ts`. No arithmetic moved; every body is the one that was there with `supabase` read as `db`. The kernel copy gains 27 files and `team-scores` joins its importers.
- **The tab** ([`teamScoresIo.ts`](../../src/lib/scorecard/teamScoresIo.ts), `useScorecard`): asks the function first. A 404 from the gateway means the function is not deployed, and the tab then makes the same reads in the browser, as before, for the people the gate already lets read wages. Any other refusal is shown in the function's words. Under *The hurdle* the tab says which it drew: *Read on the server. The hours and the dollars come to this page; nobody's wage does.*
- **Two reads answered to the service role** (migration `20261116070000_scores_reads_as_service_role.sql`, [its fragment](../migrations/20261116070000_scores_reads_as_service_role.md)): `list_people_pay_flags()` and `get_invoice_amounts_for_jobs()` decide what to return from `auth.uid()`, and the service role has none. On the edge the first would have answered with no rows and said nothing, so a closed job's team labor would have read every salaried person as hourly. Each gains the branch `list_tally_parts_with_po()` already has.

## Order

Merge, push the migration, then `supabase functions deploy team-scores`. Until the deploy the tab reads in the browser, so nothing anyone sees changes on the merge or on the push.

## What it does not do

- **The gate has not widened.** The function answers the people the tab already admitted. What changed is that their browsers no longer receive the pay table or everyone's clock sessions for this read. The estimator's own row (PR 5) is the first answer to someone outside the gate, and it is the function's to give.
- **A dev who shows ZZ test jobs** sees them left out here: the server always leaves test jobs out, as the Bridge does.
- **The labor count is still not kept with the priced margin.** A sent bid whose Labor tab is filled afterwards reads as judged while its kept cost has no labor in it (named in v2.7347). It is a rule for the stamp, not for where the read runs, and it goes with PR 5.

## Is this the best we can do?

- **Doubted: the SQL function the card planned.** Kept out. Nothing in SQL computes the overhead pool today, on purpose; a port would have been a second Overhead page and a second Costs tab to keep equal by hand.
- **Doubted: a SQL function for the wage-priced hours alone.** It was the small option. It is still a second copy of how a session is priced (the dual-rate rule, the id-then-name wage lookup), and it could not give an estimator the hurdle, since break-even also needs the office parts.
- **Doubted: running the reads as the service role at all.** A function that asks who is calling answers the service role with nothing, quietly. Checked each database function the chain calls on prod: `bid_estimate_breakdown` and `get_jobs_ledger_by_ids` do not ask, `list_tally_parts_with_po` already admits the service role, and the two that did not are in this PR's migration. The rest are table reads, which the service role makes past RLS.
- **Doubted: keeping the browser's read.** It is the fallback for the minutes between a client deploy and a function deploy, and for a function taken down. It reads only what the gate's people could already read. Kept, and the tab says when it is the one that ran.
- **Left for Micah, with my pick:** whether the fallback should go once the function has run for a while, so the pay table is never read by this tab. My pick is yes, in a later PR, once the two reads have been compared on live data for a few weeks.

## Checked live

2026-11-15, as the dev, after the merge (#8263), the push (the ledger reads fully applied, 1317 of 1317; `list_people_pay_flags` and `get_invoice_amounts_for_jobs` carry the service-role branch `list_tally_parts_with_po` already had; no types changed) and the first deploy of `team-scores`.

- **The tab reads on the server.** People → Scores on clicktooling.com drew both cards from one call to `team-scores` that answered 200 in 3.3 s, with the line *Read on the server. The hours and the dollars come to this page; nobody's wage does.* The answer's 85 field names hold no wage. A window the function does not serve (7 days) is refused with 400.
- **The server and the browser agree.** On a dev page signed in as the dev, the function's answer and the browser loader's read were made side by side for 28, 56 and 90 days and compared value by value: 1,406, 1,931 and 2,881 values, 581, 885 and 1,330 of them numbers, and not one differs. (The page ran PR 5's code, which adds two ids to each bid; the function deployed was PR 4's, so those ids alone were absent.)
- **Found: the fallback never ran.** The client reached prod at 01:28 UTC and the function was deployed at about 01:32. For those four minutes the Scores tab read *The scores could not be read.* for the people its gate lets in. A function that is not deployed answers the browser with a response that carries no CORS headers, so the page sees a failed request and never the 404 `teamScoresIsMissing` looks for. The deploy ended it. Two lessons: a function a client calls is deployed right after the merge and before the Pages deploy finishes, as CLAUDE.md says for a migration; and the fallback is fixed in v2.7370 to take a request that could not be made as *missing* too.
