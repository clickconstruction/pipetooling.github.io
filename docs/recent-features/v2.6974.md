# v2.6974 — Permits: an Austin permit's owner read from the lot the permit names (2026-11-11)

Punch list #316. The Property line found an Austin permit's owner by matching its street address at Travis County, then by the permit's point. Almost every Austin permit carries the county's own id for its lot (`raw.tcad_id`, the layer's `geo_id`). `permit-lookup` now asks by that id first.

## What was measured first (counts only, 2026-11-11)

Austin's feed, the 75-day window, commercial building permits that carry `tcad_id`: 848 rows on 700 addresses, every address put through the lookup's own code against the live layer.

- 604 addresses carry an id the layer holds, 81 carry one it does not, 15 carry an id that starts with R (Williamson County's).
- Of the 604, the address found the named lot 324 times, the point found it 251 times, the address found **another lot 28 times** and nothing was found once. That is 1 in 22 of the ids the layer holds and 1 in 25 of all 700.
- The card asked whether "another lot" is a parent lot with the address a unit inside it. It is not, in any of the 28: neither lot's middle sits inside the other's shape, no legal description names a unit, and the two lots are 7 m to 27 km apart. In 16 of the 28 the named lot is itself at the asked number and street (two or more lots share them and the pick took the other). The owner differs on 10 of the 28; on the other 18 the owner is the same and the lot's values, acres and appraisal link were the other lot's.
- No id on the layer sits under more than one parcel or more than one owner, so "the first row with an owner" has one answer. No address in the whole feed (3,355 with an id, every kind) carries two ids, so one kept answer per address stays right.

## Measured again through the new kernel (the same 700 addresses, before the deploy)

- The 604 ids the layer holds: **all 604 answered with the named lot by id**. The 28 on another lot fell to none, the one with no parcel found its lot, and the owner shown changes on 10.
- The 81 ids the layer does not hold: asked, nothing came back, and the address and the point answered exactly as before (7 a parcel, 74 none).
- The 15 ids that start with R: not asked, and answered as before (none: Travis holds no parcel in Williamson County).
- Every answer by id carried an owner and `matched_by: 'id'`.

## What changed

- **Kernel** (`supabase/functions/_shared/permitParcels.ts`): `ParcelSource.id` names a layer's id column, the key the permit's feed row keeps the id under and which ids are the layer's own. Only `TRAVIS_PARCELS` sets it (`geo_id`, `tcad_id`, not an id that starts with R). `idWhere` and `idQuery` build `geo_id = '<id>'` with the quotes doubled, the source's `outFields` and no shape. `parcelFactsById` reads the first row with an owner and marks it `matched_by: 'id'`. `ParcelFacts.matched_by` is now `'point' | 'id'`.
- **`permit-lookup`**: the body takes `permit_id`. For a county whose layer has an id column the function reads `city`, `address` and `raw->>tcad_id` off `permits` with the service client, uses the id only when that permit is the one at the address being looked up (the answer is kept under the address), and asks by id first. An id the layer does not hold falls back to the address and then the point, exactly as before. The kept `query` now lists every question asked, in order, joined by ` | `.
- **Kept answers**, the two traps the card named:
  - `askedOtherQuestion` read the first part of `query` as the address question. With the id question in front, every kept "no parcel" would have been asked again on every open. It now reads past the id question and the point. A row whose asking stopped at the id question (the county failed there) holds no address question and is left to its month, so a dead source is not hammered.
  - A kept found answer was never asked again inside thirty days, so a neighbour's owner would have stayed a month. `askedWithoutId`: a kept answer, found or not, whose `query` holds no id question for a permit that carries one is asked again once. The new row holds the id question and is then kept like any other.
- **Callers**: `lookupParcel`'s fourth argument is the permit (`{ lat, lng, id }`); `PermitSkimDeck`, `PermitBuildingSheet` and `WhoPulledItSheet` pass the permit's `id`. Every city sends it and only Travis's branch reads it.
- **Words**: none added. An answer by id is the exact lot, so `lotWords` and `parcelPointWords` say nothing extra for it. The guide `research-permits-for-work-to-bid.md` gained two sentences on Austin's lot and its line about the permit's point now says when that happens.

Tests: `permitParcels.test.ts` (the id question, the quote, the ids not asked, the facts by id, both kept-answer rules), `permitCityDoors.test.ts`, `ProspectsResearchTab.render.test.tsx` (the three screens pass the permit's id). Every id and row is made up.

Deploy: `permit-lookup` after the merge, from `main`. `permit-pull` bundles the two shared files too (through `permitCities.ts`) and runs the same code as before; `check:edge-drift` says whether it wants a redeploy. No migration.
