# v2.8104 — The main chunk's split, step 2: six more windows load on demand (2026-11-20)

Step 1 (v2.8098) took the three job windows out of the entry's chunk. This takes the next six, by the same means, and makes the helper better at its job. No migration and no function.

## Measured

| | Main chunk |
|---|---|
| Live site, 2026-11-20 morning | 9,465,107 bytes |
| After step 1 | 5,671,756 bytes |
| After this step, `vite build` on the branch | 4,307,275 bytes (54% under the morning's) |

The build's precache step passed. The Settings page's chunk (5,608,888 bytes) is now the largest precached file, so the cap in `vite.config.ts` cannot come down far until that page is split too.

## What changed

- **Bid preview** and **customer profile**: their providers (`BidPreviewModalContext`, `CustomerProfileModalContext`) hold the window through `lazyWindow`, with a `Suspense` around the window alone.
- **Person desk** and **user review**: the Layout mounted both all the time and each drew nothing until opened. `PersonDeskDrawerOnDemand` and `UserReviewModalOnDemand` read the open state and hand the window to `OnDemandWindow`, which mounts it at the first open and keeps it mounted after, so what the window does as it closes still runs.
- **Painted map**: `PaintedMapHost` stays in the Layout to hear a door from anywhere. Its start sheet and its map window load on demand, inside a boundary of the host's own.
- **Edit customer**: `EditCustomerModal` is a thin shell in the Layout. Its form loads on demand.
- **`lazyWindow` does two things `React.lazy` does not.** A window whose code has loaded is drawn at once, in the same pass as the press, with no fallback in between. And a load that failed is asked for again at the next open, where `React.lazy` keeps the failure until a reload. One mount keeps the component it started with, so a window never remounts when its code lands.
- **The guard.** The seven files are in `ON_DEMAND_WINDOWS`, and `ENTRY_SOURCE_BUDGET_BYTES` comes down from 16 MB to 12.5 MB: the entry now reaches 10.8 MB of source.

## Seen on the dev server

Each opened from a press, with what it holds: the bid preview from My Bids (169 ms), the Paint a map start sheet (232 ms), a person's window from Crew Day (400 ms), the customer profile from its link, and the edit customer form from the profile (twelve fields, closed with Cancel). The dev server compiles a file the first time it is asked for, so these times are slower than the built app's.

## What is left

- The older public pages in `App.tsx` are still imported eagerly (the Legal portal, the customer and sub portals, the pay link and others); the newer ones are already lazy. By the import trace they hold most of what a signed-in person still loads for nothing.
- The Settings page's chunk, 5.6 MB, is the largest precached file. The precache cap stays at 10 MiB until it is split.
