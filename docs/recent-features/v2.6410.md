# v2.6410 — A Pipeline search that cannot reach every job says so (2026-11-02)

The owner's yes, after v2.6405 left this one standing: the server lookup (`fetchLeanJobSearchIds`, v2.1825) is the only part of the Pipeline search that reaches the jobs the board has not loaded, every Paid in Full job and the scopes not loaded yet. When it failed, the effect dropped the failure in silence (`if (!res.ok) { setStagesServerSearchBusy(false); return }`), the board searched only its own rows, and the hint said *No match anywhere — Paid in Full included*. When the lookup found jobs whose rows then did not load (`fetchJobsLedgerWithDetailsForStages` answering `ok: false`), the same. The **#** jump's `jumpViaLeanLookup` returned `false` for both, so the chip flashed *No job matches that number*. Client only: no migration, no function change. Builds on v2.6405 (#6881), whose held-back count the hint reads.

- **The kernel `src/lib/jobs/stagesSearchLookupFailed.ts`.** `stagesSearchLookupFailedWords` gives the line: *Only the jobs already on the board were searched.* for a failed lookup, *2 more matches could not be loaded.* for rows that did not load. `stagesSearchLookupOfflineMessage` gives the lost-signal sentence for each, a read's words (nothing was lost, it runs again by itself), never the write sentence's *nothing was saved*. `stagesNumberLookupFailedWords` gives the # jump's toast, its own words for a lost signal and the server's reason for anything else.
- **The failure's kind.** `LeanJobSearchResult`'s failure carries `errorKind` (`errorKindOf`), as `FetchJobsLedgerFailure` already did, so the board can tell a lost signal from a refusal.
- **The search box.** The lookup effect keeps `stagesServerSearchFailure` (with `unloadedMatches`, null for a failed lookup), clears the earlier term's ids so they stop riding along as matches, and reruns on `stagesServerSearchAttempt`. `StagesSearchLookupFailed.tsx` draws the line and `OfflineRetryPanel` under it (`surface="pipeline-search"`, `idempotent`): Retry for a lost signal, a run by itself on the `online` event, the reason with no Retry for a refusal, and the error door. `stagesPaidSearchHint` takes `serverSearchFailed` and never says *nowhere* then; `stagesPaidHeaderSearchCount` reads *not searched* while the lookup failed and the paid rows were never loaded, so the header never counts them as none.
- **The # jump.** `jumpViaLeanLookup` answers `'failed'` with a toast for a failed lookup or rows that did not load; `StagesJobNumberJumpChip` keeps the field and the digits on `'failed'` and never enters its no-match state. A number nobody holds still flashes *No job matches that number*.
- **Guide.** *search jobs on the Pipeline board* gains *When the search cannot reach every job*.
- **Tests.** `stagesSearchLookupFailed.test.ts` (the words, one and many, both kinds, plain words); `stagesPaidSearchHint.test.ts` +2; `leanJobSearch.test.ts` +1 (a refusal comes back with `errorKind: 'server'`); `StagesJobNumberJumpChip.render.test.tsx` +1 (`'failed'` keeps the digits, no no-match title); `JobsStagesTab.lookupFailed.render.test.tsx` walks the wiring: six of its seven cases failed before the change, and the true no-match on the # jump passed on both sides.
