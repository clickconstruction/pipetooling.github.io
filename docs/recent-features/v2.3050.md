# v2.3050 — Test-gap audit, pass 58: the shared Mercury relation reads get their first tests (2026-09-07)

Pass 58 of the test-gap audit. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`fetchMercuryRelationsByTxIds.ts` is the one place fourteen surfaces (Banking's master list, Visuals and Accounting tabs, the transaction and allocation modals, People review, Wheels, the Quickfill sorting snapshot, Jobs, and the week-close and attribution writers) read Mercury job splits and person/user attributions — either for a fixed list of transaction ids (chunked `.in()`, each chunk paged) or the whole table (paged). It carries the J33-N1 lesson (an un-ranged read silently capped at 1,000 rows and the Link… modal seeded empty for the rest), and had no test of its own.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Id lists are cut into chunks of 200, each chunk its own query with the split or attribution columns, a stable order (transaction then row id for splits; transaction for attributions) and a `0–999` range; results come back in chunk order under a per-table retry label built from the caller's operation name.
- A full 1,000-row page for one chunk asks for that chunk's next page before moving on; a short page ends the chunk. The whole-table reads page the same way with no id filter and their own `(all)` labels.
- No ids means no read; a null page reads as no rows; a failed page throws rather than reading as "no relations" — the failure mode that would erase splits on the next Save.

## What shipped

- **`fetchMercuryRelationsByTxIds.test.ts`** (6) — a recording Supabase stand-in routed by the `.in()` chunk and `.range()` offset, with a retry wrapper that records its labels. Covers both id-list readers (chunking, query shape, per-chunk paging, empty/null/error) and both whole-table readers.
