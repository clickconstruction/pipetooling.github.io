# v2.7473 — Painted maps: throwing a map away takes its photos (2026-11-16)

Punch list #345, the client half. v2.7454 (#8352, `20261116234500_painted_map_photos_after_the_map.sql`) changed the bucket's rule so a file can be listed and removed after its map is gone. This is the app doing it.

## What changed

`deletePaintedMap` in `src/lib/paintedMap/paintedMapIo.ts`, the one thing that deletes a `painted_maps` row, now calls `removePaintedMapPhotoFiles(mapId)` once the row has gone.

- **The order is the row, then the files.** The files are listed under the map's id after the row is gone, then removed. This is the order the bucket's policies allow since v2.7454: once a map is gone, a caller is shown only the files they may remove, so what is listed is what goes. Before that migration the list came back empty for everyone.
- **It never blocks the delete.** The removal is not waited on, catches everything and answers nothing. The window closes as it did. A file left behind shows no error.
- **No file is touched unless the row went.** A delete that is refused, that removes nothing or that never lands lists nothing.
- **It removes what it is allowed to and is silent on the rest.** The office takes every file. A maker who is not office takes their own uploads. A teammate's photo on that map is not shown to them, stays in the bucket, and can be listed and removed by the office.
- A list reads a hundred names at a time and stops at a thousand. A name of any other shape than `<map id>/<file>.jpg` is left alone, and an id that is not an id lists nothing, so the bucket's top folder is never read.

`PaintedMapWindow` is not changed: its *Throw the map away* confirm already calls `deletePaintedMap`, and its render tests mock the io kernel whole.

## Tests
