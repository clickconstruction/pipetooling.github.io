# v2.8398 — Permits: the lot lookup passes its type check (2026-11-23)

A small fault the #405 overnight look found and left: `deno check supabase/functions/permit-lookup/index.ts` failed with TS2345 at line 151, `parcelIdOnPermit(admin, …)`, on main too. A deploy does not type-check, so nothing was blocked. Types only: no behaviour change, no migration.

## The cause

`parcelIdOnPermit` typed its client as `ReturnType<typeof createClient>`. `createClient` is generic, so that names the client with its type parameters unresolved (`SupabaseClient<unknown, …, never, never, …>`), and the client the handler makes, `SupabaseClient<any, "public", …>`, is not assignable to it.

## What changed

- The parameter is `SupabaseClient`, imported as a type from the same `esm.sh` module, as `accept-estimate`, `bill-read` and the shared `refuseArchivedCaller` already write it.

## Checks

- No `deno` binary on this machine. A `tsc` run over `permit-lookup/index.ts` with the `esm.sh` import mapped to the installed `@supabase/supabase-js` 2.99.2, and `serve` and `Deno` stubbed, gives exactly the TS2345 at 151:71 on main and nothing after the change. `deno check` on a machine that has it is the proof still owed.

## Owed after the merge

- `supabase functions deploy permit-lookup`. The function's running code is unchanged in meaning, so there is no hurry; until then `check:edge-drift` reads it as behind.
