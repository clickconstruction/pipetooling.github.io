# v2.6363 — A job photo is filed in Drive like a report’s (punch list #244, PR 2) (2026-11-02)

Punch list #244's second PR. PR 1 (v2.6359) made the `job_photo_notes` table; this PR teaches the sweep to file it.

## What changed

- **`photo-save`** (`supabase/functions/photo-save/index.ts`): the report photos' pass becomes one pass over a *named source* (`sweepNamedPhotos` over a `NamedSource`: the table, the bucket, the waiting read and the plain caption), run for the report photos as before and then for the job photos: up to twenty `job_photo_notes` rows with a `storage_path`, an `added_at` and no `filed_at`, oldest first, each copied into the job's photo folder named by day, sender and caption (`photoDriveName`), the row keeping `drive_file_id` and `filed_at`, the bucket copy deleted, a failure written on the row and tried again next run. The answer gains `jobPhotos: { saved, failed }`. Nothing else in the function changes.
- **`job-photos`** needs no change: its `files` action already reads the view's `source`, so a filed job photo comes back as `{ kind: 'photo', source: 'job' }`. The client's words for it (`lib/jobs/jobFolderFiles.ts` → `fromWords`): *From the app · a job photo*.
- `docs/EDGE_FUNCTIONS.md`: the fifth source under photo-save, the answer shape, the status line; the job-photos note.

## Deploy

`supabase functions deploy photo-save` after `20261102171500_job_photo_notes.sql` is pushed (PR 1), since the pass reads the table every run. No migration here.

## Test

`npm run check:edge-bundles` links the function; `npx vitest run src/lib/jobs/jobFolderFiles.test.ts`. Live, after the deploy and PR 3: a job photo added on a ZZ Test job reads *In Drive* within five minutes and the Customer Pictures folder holds it under its words.
