# v2.3252 — Discount line items PR 1: the discount kernel + the columns (2026-09-10)

Migration [`20260910223000_discount_line_items.sql`](../migrations/20260910223000_discount_line_items.md). Nothing visible changes yet; PR 2 draws the row.

## Why

Owner (2026-09-10): "I would like to be able to add discounts as line items … I was thinking a negative number but I should probably make this more robust like making it easy for a user to enter a %." Design review with the mockups, the "is this the best we can do" pass and the before/after: https://claude.ai/code/artifact/7109f02d-bf06-4fff-a5f2-2f3c0bfdff0a (Mockup B approved; approval trail only, no sign-off gate).

A plain negative price was a trap: the price input strips the minus, `fixtureInsertRows` writes any price ≤ 0 as null, and every bill-line kernel (Stripe allocation, the PDF allocation, the segment bar, the remainder's "sum equals target" test) prorates positive buckets — a negative bucket has no place in that math. And a percent typed into a price field is a one-shot calculator that goes stale the moment a stage price changes.

## What shipped

**A discount is a typed row.** `jobs_ledger_fixtures.line_kind = 'discount'`, `discount_pct` (live percent, or NULL for fixed dollars), `discount_basis_positions` (the work rows it applies to; NULL = all), `discount_reason`. The signed amount is stored NEGATIVE in `line_unit_price` with `count` 1 — chosen so the 29 readers that sum `count × price` (Job Total, revenue resync, money rollups) stay right without learning the kind, and a reader that filters to positive rows simply omits the discount rather than adding it as revenue.

**Kernel `src/lib/jobs/discountLine.ts`** (22 tests), the one place the rules live:

- `parseDiscountEntry` — `10%` is a percent, `500` / `$1,250.50` / `-500` are dollars.
- `derivedDiscountDollars` / `discountBasisRows` — a percent derives from its basis; a dollar amount is capped at the basis (`discountExceedsBasis` says when the typed figure was held).
- `syncDiscountRows` — the invariant keeper the form runs on every change: negative derived price, count 1, no stage kind, not shared with the GC, dead basis ids pruned; returns the same array when nothing moved.
- `discountSharesByWorkRow` — **a discount follows the work**: its dollars split across the basis rows by largest remainder, cents-exact, so any grouping of draws prints the whole discount exactly once (`discountBillLinesForWorkRows` sums the shares for the rows a bill covers; `netWorkLineCents` is a work row after its shares).
- `discountReadout` / `discountTwinLabel` / `discountBillDescription` — the row's second line ("10% off all 3 work lines · follows each draw · not on riders"), the other form beside the field ("−$3,774.50" / "1.32%"), and the customer's line ("Negotiated discount (10%)").
- `discountRowIsLocked` — locked once any basis row is on a bill (that bill already printed its share).
- `discountBasisPositions` ↔ `discountBasisIdsFromPositions` — the persisted basis, keyed on named-row positions like invoice links.

**One rule simplified during the build.** Mockup B said a percent follows the work and a dollar amount rides the final draw as its own line. Both now follow the work: the segment bar, dollar coverage, the remainder bundle and the invoice-from-segments math all run on net line dollars, and a $ discount that lived outside that model would have made the bar sum disagree with the Job Total. The customer sees "Referral thank-you −$200.00" on draw 1 instead of −$500 on draw 3; the office sees the same readout for both.
