# v2.8612 — A box's own screen: an added part counts its own line, and an empty box is due no count (2026-11-26)

Punch list #398, the lane with a migration. Two of the owner's answers of 2026-11-25. Asked *Adding one part marks the whole box as counted today. Is that wanted?*, the answer was *"No, the add counts its own line (Recommended)"*. Part A's item 2 of the same card, seen in the simulator the same day: the list's Count chip read *Count 2* for two empty boxes, and neither offered a count.

**Read.** When a box is due a count was worked out in three places in the client (`lastCountedAt` with `countIsDue`, `boxesNeedingAHand`, `jobMaterialsSummary`'s `stale`) and in two database functions that copied the rule on purpose: `on_site_door_facts`, which the Job Mode card's line reads, and `on_site_job_summary`, which the office's summary reads for a job past the 5,000-row read. None of the five read a row's note, and none asked whether a box held a line to count. A client-only mend would have left the phone's list disagreeing with the card's line and the office's chip (`small-fixes`' send-back of 2026-11-25).

**The mend.**

- **Migration `20261126014752_box_due_a_count.sql`** replaces both functions with the same arguments and answer. `on_site_door_facts`'s `due` leaves out a `counted` row whose note is *counted as added*, and counts only a box that holds a line to count. `on_site_job_summary`'s `last_counts` leave out the same rows, and its `lines` keep them: an added part did count that line. No table is made or changed. Page: `docs/migrations/20261126014752_box_due_a_count.md`.
- **One rule in the kernel** (`src/lib/materials/onSite.ts`). `ADD_COUNT_NOTE` moves here from `addPart.ts`, which re-exports it. `lastCountedAt` leaves a row with that note out. `lineIsCountable` is the count walk's own predicate, something on hand or a Can't find since the last count, and `countWalkKeys` reads it. `boxCountDue` is the rule whole: not Unsorted, a line to count, and no count inside 14 days. `lastCountedByBox` reads every box's last count at once for the site roll-up.
- **Every reader asks the rule.** The phone list's Count chip (`boxesNeedingAHand`), the office's chip (`jobMaterialsSummary` and its server twin), the Tally's and the Jobs tab's map pins and box headers, the Materials desk's figures, find rows and phone rows, the site roll-up's `due` and its glance's *due now* and *falls due this week* (`SiteRollupJob.lastCounted` carries each box's last count, from the ledger or the server's `last_counts`, since the lines alone cannot tell an add's count apart), and a box's row (`boxRowState` takes the Can't find count, so an empty box is never amber and a Can't find with none left still is).
- **The words are one constant on both sides.** `src/lib/materials/boxDueNote.test.ts` reads the migration and fails when the SQL's literal and `ADD_COUNT_NOTE` part.
- **The guides** *keep track of the material in the cages and boxes on site* and *see what is on every job site and what walked away* say that an added part counts its own line and that an empty box is never due.

**Order.** The client reads no new name: either side reads the other, so the push and the client deploy may land in either order. `npm run check:calls-ahead` names the two calls as functions the migration replaces and says no deploy waits for the push. The push is asked for by name and waits on its own yes.
