## The two sizes of a bundle

The bundle the CLI builds is an eszip: each file, its JavaScript and its source map. The CLI compresses it before the upload and prints the compressed size. Supabase stores it unpacked, and the Management API hands that back (`GET /v1/projects/{ref}/functions/dev-mcp/body`).

| | Size | Against the raw source |
|---|---|---|
| Raw source | 4.49 MB | 1 |
| Bundle, compressed (the CLI's `script size`) | 3.46 MB | 0.77 |
| Bundle, unpacked | 14.85 MB, 6.7 MB of it source maps | 3.31 |

Supabase's page says "Local bundling (Supabase CLI): up to 20 MB" and does not say which size. One accepted deploy at 3.46 MB and 14.85 MB cannot tell. If the compressed size counts, the seat has about 21 MB of raw source to go. If the unpacked size counts, it has about 1.5 MB.

## What changed

- **`.github/workflows/dev-mcp-deploy.yml`** replaces the test workflow. It runs by hand, on `main` alone, for `dev-mcp` alone, with `--use-docker --no-verify-jwt`. It stops before the deploy when Docker is not up and fails when the log shows a raw upload. Its summary carries the commit, the seat's version, the raw upload, the CLI's line and the bundle unpacked. One run waits at a time, and a newer dispatch replaces a waiting one.
- **`scripts/deploy-functions.sh`**: `dev-mcp` in the list is not sent from the machine. The script deploys the other names first, then dispatches the job on `main`, waits and prints the CLI's size line. The job deploys `origin/main`, never the checkout, and the script says so when the two differ. When its run is replaced by a newer one it follows that run. `DEPLOY_DEV_MCP_RAW=1` sends raw files from the machine as before, for a day GitHub cannot run the job.
- **`check:edge-bundles`** holds `dev-mcp` to 5.8 MB of raw source (`BUNDLED_UPLOAD_CEILINGS` in `scripts/lib/edgeUploadGraph.mjs`) and prints its room. 5.8 MB is about 19.2 MB unpacked, so the seat stays under 20 MB on either reading. Every other function keeps 4.5 MB.
- `CLAUDE.md`, `AGENTS.md`, the dev-mcp section of `docs/EDGE_FUNCTIONS.md` and punch list #359 say the same.

## What it does not change

- How any other function deploys.
- What the seat runs. The bundle holds the files main holds.
- The MCP `deploy_edge_function`, or a plain `supabase functions deploy dev-mcp` on a machine with no Docker daemon. Both still send raw files, which Supabase refuses past 5 MB with the live seat left as it was.

## Room, and what is left

At 0.25 MB a day the 1.31 MB to the new ceiling is about five days. A deploy accepted past 20 MB unpacked shows the compressed size is the one counted, and `BUNDLED_UPLOAD_CEILINGS` can then rise to about 12 MB, which is months. The way to learn it without waiting is one throwaway function deployed bundled at more than 20 MB unpacked and removed after. That creates a function on the production project, so it is the owner's to say. The cuts of punch list #359's step 3 make room under either reading.
