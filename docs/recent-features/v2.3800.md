# v2.3800 — Day book: a follow-up counts when the estimator wrote one (2026-09-24)

Close-out of [`to-dos/day-book`](../../to-dos/day-book/README.md) (#20): the three estimating-strip tiles the 2026-09-22 live pass left owed a row read, settled by reading Wendi's rows as the dev through the signed-in client (the dev-mcp key was revoked). One rule was wrong; the migration fixes it.

## What the reads said

- **Lost, no reason — 0 (census 2).** Bids 362 and 364 have `loss_category` null on the bid row and `gc_lost` on one version each. The rule (null on the bid *and* on every version) is as designed; the census on Sep 16 read only the bid column, or the version reasons were recorded after it. No change.
- **Prices asked → in — 0 asks (the pass read 1).** Every `bid_rfqs` row in the window is another estimator's; with Wendi picked the strip reads 0 today, as the census did. No change.
- **No follow-up in 7 days — 3 of 5 (census 2 of 5).** The RPC required `contact_method IS NOT NULL` on the entry (its comment: the robot pipeline's log lines carry none). But most human follow-ups carry none either — bid 393's *"sent in bid but they are being jerk faces to us…"* on the day of the send, 384's *"talked to northstar yesterday and today…"* — so a bid the estimator wrote about was counted as never followed up. The app's own stale rule (`submissionFollowupStale.ts`) counts any entry.

## The change

- **`20260924050000_day_book_followup_rule.sql`** re-creates `day_book_payload_for` with the body of `20260922190000` and one predicate changed in `strip_sent.unfollowed_n`: any `bids_submission_entries` row on the bid whose Chicago date falls from the first send through seven days after counts as the follow-up, excluding the app's outcome-change line (`notes LIKE 'Win/Loss changed from %'`, the literal `outcomeChangeBidNote.ts` writes). An entry before the send is not a follow-up to it (the old rule had no lower bound). With this, Wendi's window reads 2 of 5 — bids 392 and 384, whose first note after the send came on Sep 11.
- No new table; the two doors (`get_day_book_payload`, `get_day_book_payload_for_user`) are unchanged. **Deploy:** `supabase db push` after merge.
