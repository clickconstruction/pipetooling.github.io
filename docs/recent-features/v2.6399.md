- **The function** (`ship-pace`, `docs/EDGE_FUNCTIONS.md`): the cron's `X-Cron-Secret`, or a signed-in dev (`is_dev()` asked as the caller) for the press. It lists every open pull request and the closed ones by last update, newest first, until a page falls before the window less an hour (REST, 100 a page, ten pages at most), lists the merge queue's builds (Actions runs of the `merge_group` event since the window's day) and asks GraphQL how many pull requests sit in the queue, hands them to the kernel and upserts one `app_settings` row, `ship_pace_v1` (every signed-in user reads `app_settings`; the service role writes, so no policy or migration for the row). Actions or the queue refused leaves those fields null and the picture stands on the pull requests. No token is 503 `{ noToken }` and nothing written; GitHub refusing the pull requests is 502 and nothing written, so the row keeps the last good read and the section's stamp shows it ageing. About ten requests a run against a fine-grained token's 5,000 an hour.
- **Why a row in `app_settings` and not a table**: the house keeps a cron's single stamp or value there (`file_index_sweep_last_at`, `docsmit_credit_balance`), every signed-in user already reads it and only a dev or the service role writes, which is exactly the office read and the cron write this needs; a table would add three fence calls, a policy and a migration for one row.
- **The cron** (`20261102233000_ship_pace_cron.sql`): `ship-pace` at `9,24,39,54 * * * *`, a minute slot no five-minute, ten-minute or quarter-hour cron uses, `net.http_post` with the Vault `PROJECT_URL` and `CRON_SECRET` as the file-index-sweep is scheduled, unscheduled first so a second run leaves one row. No table, so no fence calls.
