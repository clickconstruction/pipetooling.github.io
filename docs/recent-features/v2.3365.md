# v2.3365 — Customers: the list shows at half a second, the counts and money arrive in one round trip (2026-09-12)

Migration `20260912051614_customers_list_bundle.sql` ([`docs/migrations/20260912051614_customers_list_bundle.md`](../migrations/20260912051614_customers_list_bundle.md)); no edge function. Owner ask: "when a user clicks on Customers it shows Loading customers for a long time."

## Why

Measured on the dev server as dev before the change: **56 requests, "Loading customers…" for 3.7 s**, over data that is small (418 customers, 829 jobs, 524 invoices, 661 payments). The page fetched the customer rows (0.5 s), then five count tables filtered by 150 customer ids per chunk with the chunks awaited one after another (15 requests, 1.2 s), then invoices and payments by 150 job ids per chunk the same way (12 requests, 1.7 s), then the unlinked-jobs count (0.3 s) — and cleared the spinner only after the last one. Round trips, not volume; on a phone each trip is slower and the wait was the 8–10 s people felt.

## What shipped

- **List first.** `fetchCustomers` sets `loading` false as soon as the customer rows are in; the counts / money / signal load behind it under a new `detailsLoading` flag. The summary strip's Owes figure shows "…" while it is on its way instead of a zero that then jumps.
- **One round trip.** `get_customers_list_bundle()` (SECURITY INVOKER — the caller's RLS on every table) returns every row the 55 requests used to: per-customer project / bid / note counts, the newest bid and estimate stamps, the jobs with a customer, their invoices and payments, and the unlinked-jobs count. Kernel [`customersListBundle.ts`](../../src/lib/customers/customersListBundle.ts) (+5 tests): `parseCustomersListBundle` (defensive, numbers as strings tolerated) and `deriveCustomersList` (counts keyed to the listed customers, jobs counted from the rows, `customersListRollup` for the money — unchanged — the unrecorded-paid count, the recent signal). The old chunked reads stay as `loadCustomersListBundleChunked`, used only when PostgREST reports the function missing (`isMissingRpcError`, the deploy window before the push).
- `src/types/database.ts` hand-aligned for the RPC (regen after the push).

## Verified

Kernel tests; typecheck · lint · theme check. Dev server as dev, same machine and link as the before-measurement: the list shows at **514 ms** (was 3,737 ms). Before the migration was pushed the fallback path filled the details in 4.1 s; the RPC timing after the push is in the PR.
