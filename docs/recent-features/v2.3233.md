# v2.3233 — Desktop kickoff: the five loop gaps closed — parked plans shells, question lanes, no invented choices, a resume check, refused claims reclaim (2026-09-10)

Docs only (the kickoff file, its tests, one help guide). No migration, no code, no briefs regeneration — `docs/twins/kickoffs/` is not in the twin-mcp bundle; the Console's **Copy Desktop kickoff** reads the file raw. Grace's decision after v2.3224's table read: "fix all five now".

## Why

Before the first live Desktop run (2026-09-09) a fresh agent with no tools table-read `docs/twins/kickoffs/desktop-operator.md` and found five places where a literal reader is stuck or does something the author does not want. Four needed no decision. The fifth — what to do with a shell whose plans a person cannot open — was answered by what shipped since: v2.3212 parks the plans ask on the human bid's needs sheet, v2.3223 lets **Attached — rerun** put that bid at the front of the next batch, and the dispatcher now hands an unlocked shell back to its robot (`resumed: true`). That design only works if the shell stays **open**; voiding it would break the rerun. So the rule is spelled out that way, and flagged here for Robert rather than waited on.

## What changed in the kickoff

1. **Parked plans shells.** "Never call `next_shadow` while your current shell is open and unlocked" (which, read with the STG-2 branch, left no legal exit) is now "while you are still estimating a shell", with the one exception named: a shell parked on a plans ask stays open and unlocked, is never `void_shadow`ed, and the robot claims the next; the dispatcher hands it back once a person answers. STG-2's failure branch says *park the shell* instead of "move on to reporting"; LOCK's "never leave a shell open and unlocked" carves out the parked one; REPORT and the closing summary accept `parked on plans: <what you asked for>` with no total.
2. **Question lanes.** Every `ask_question` names its `audience`: `'estimator'` for a judgment about the job (the v2.3210 shape rule), `'operator'` when the machine is in the way (no shape rule; table, tool and run names belong there). The permission-block hard rule says `audience: 'operator'` explicitly — the table read had the robot inventing choices to get a machine problem past the door.
3. **Plans asks carry no `choices`.** The door supplies the three taps (v2.3212); the prompt now says so instead of implying the shape rule applies.
4. **Resume check.** Door-check item 5 starts with `get_assignments`: any open, unlocked ZZ Shadow shell of the robot's is its first job, picked up from `get_work_state`, unless it is parked on an unanswered plans ask. The v2.3223 `resumed: true` sentence stays as the second half.
5. **Refused claims reclaim.** "wrong division → `void_shadow` it, and stop" ended a batch on one bad bid, and the doors have refused non-plumbing and holdout references since v2.3032 / v2.2952 anyway. Now: a refused claim is not a shell — report it in one line and call `next_shadow` again; a non-plumbing shell that somehow arrives is voided and the robot claims the next.

`desktopKickoff.test.ts` asserts each of the five (+1 test); the old "open and unlocked" assertion is retargeted. Help guide `run-the-robots-from-claude-desktop` gains a paragraph on parked shells and the two question lanes.

## Owner decision flagged (Robert)

A plans-blocked shell is **parked, never voided**. Consequence: the shell keeps its `twin_source_bid_id` pairing and its ledger, the human bid keeps its amber icon until someone answers, and coverage counts it as shadowed-in-progress. If he would rather such shells be voided after N days, that is a dispatcher rule (`next_shadow`), not a prompt change.
