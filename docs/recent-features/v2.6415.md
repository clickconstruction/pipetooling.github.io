# v2.6415 — Each group of SQL beds runs the migrations once and starts most beds from that copy, so a run takes half the build time (2026-11-02)

After v2.6404 every whole-schema bed still applied all 1,072 migrations itself, through one psql. Beside seven others on a 4-core runner, which gives about two beds' worth of CPU, that was about 150 s of each bed's run. Every bed in a leg built the same database.

- **The change**: `scripts/sql-beds-run.sh` makes the leg's migrated copy first. `pgtest_make_copy` in `scripts/pgtest-pull.sh` starts a container from the Supabase image and runs `pgtest_migrate` in it, as a bed would. It then stops the container cleanly and saves it with `docker commit` as a local image. The image carries the label `pgtest.migrated`: a checksum of the prod extras and every migration, by name and content. A bed whose start is `pgtest_migrate` runs on that image through `PGTEST_SUPABASE_IMAGE`. Its `pgtest_migrate` reads the label, checks that it names the same files, and applies nothing. A label for other files stops the bed. `PGTEST_LEG_COPY=0` turns the copy off.
- **The order in a leg**: the copy takes the first of the eight slots. The beds that can't use it start at once beside it. Those are the 9 that run a migration a second time or a seed before one, the 7 with no migration loop, and `bed-apply`. The 60 that can use it wait for it and start as soon as it is saved.
- **`pgtest_migrate`**: the prod extras as `supabase_admin` and then every migration, as one step a bed from the copy can skip. The extras can't just run again on the copy. Their `GRANT ALL` on the storage tables and `CREATE OR REPLACE` on the storage functions would undo what later migrations changed.
- **The sweep**: `scripts/codemods/sql-bed-loop-sweep.mjs` now takes a bed straight to this form, from the old per-file loop or from v2.6404's. In 60 beds it removed the extras line and replaced the migration step with `pgtest_migrate`. That includes `gc-schedule` and `walk-kit`, which keep their per-file loop for a local Postgres. Run from either starting point, it gives the same 69 files byte for byte. A step between the extras and the migrations makes it refuse a bed and leave it as it is. Today none has one.
- **Why a saved container works**: a probe on the runner (run 41582651438) found the image declares no VOLUME, so its data directory is in the container's own layer, which `docker commit` saves. The image stops with SIGINT, a fast shutdown with a checkpoint, so a container from the copy starts with no recovery. One leg migrated once in 36 s. Stopping took 1 s and saving 5 s, for a 360 MB layer. Ten containers from the copy answered in 1 to 2 s, eight of them at once in 3 s, all with the template's schema hash. A container from the copy only stores what it changes.
- **A copy that fails** is a warning, not a failure. Its beds then apply the migrations themselves, so a broken migration still fails every bed by name. A run with a broken migration in the middle of the history (run 41583595511) showed this. The copy failed, naming the file and its line 3. Then all five full beds failed, each naming the file. `bed-apply` passed beside them.
- **`bed-apply`** holds two more promises, with 18 checks now. A container labelled as a copy of these files applies nothing, and its psql never runs. A copy of other files is refused.
- **The proof**: main's beds and this branch's, each with a probe after the migration step, were dispatched together (runs 41583598903 and 41583602089). Every bed passed both ways, with 3,739 and 3,741 `ok:` lines; the two more are `bed-apply`'s new checks. All 69 beds gave the same `pg_dump -s` hash both ways (`5883f9dd521918e2`, 7,567,171 bytes), the 60 from the copy included.

- **What a leg spends now**: about 60 s pulling the 3.1 GB image. Then the copy, which takes longer beside the beds that run their own list: in leg 4 the copy and four of them ran together, and all five took about 160 s. The beds from the copy follow in waves of eight, about 15 s each.
