# v2.6806 — The dev seat reads a large file off a mail whole: in pieces that fit, with the argument that reads on (2026-11-09)

Found 2026-11-09 on server 0.49.0 during a read-only mail session: `read_mail_file` said it handed a file back as `content_base64` "up to 10 MB", but the door cuts every reply at `REPLY_MAX_CHARS` (80,000 characters, `_shared/devMcpDoor.ts` → `replyText`), and base64 is four characters for three bytes, so any file over about 59 KB arrived as a base64 string cut mid-way with the door's tail after it. Five supplier PDFs of 100 to 180 KB all came back that way. A cut PDF cannot be opened; only a first page could be salvaged by inflating its streams by hand, and a scanned one gave nothing. `plan_mail_file` → `apply_mail_file` was never affected, since the bytes stay on the server.

## The shape, and why

Two shapes were weighed. **Ranged reads** (built here): the verb takes `offset` and `length` and hands back a slice of the bytes that fits the reply, with the size and the sha256 of the whole file and `next_offset`. **A text read** (carded as punch list #296): the file's words read on the server by the file index's own reader, paged by character.

Ranged reads came first because they make the verb's own promise true for every kind of file — a scan, a picture, a spreadsheet, a signed PDF — with no parsing and no CPU budget to hold, and a caller that has the bytes can do anything with them. The text read is the cheaper way to *read* a text PDF (base64 costs an agent far more context than the words do), but it answers nothing for a scan and it brings the PDF reader's limits into the verb, so it is its own PR.

## What changed

- **`supabase/functions/_shared/devMcpMailFile.ts`** (pure; tests `src/lib/devMcp/devMcpMailFile.test.ts`):
  - `MAIL_FILE_SLICE_MAX_BYTES = 54_000` — 72,000 base64 characters, which leaves the door's 80,000 about 8,000 for the file's facts and the words. A multiple of three, so pieces read at the default length join as base64 text as well as bytes.
  - `mailFileReadArgs` takes `offset` (a whole number from 0; 0 when left out) and `length` (a whole number from 1; the cap when left out, and never more than the cap) and refuses anything else in words.
  - `mailFileReadReply(account, id, file, { offset, length })` takes the file as bytes (`MailFileRaw`) and replies `{ account, id, name, mime, size_bytes, sha256, offset, length, next_offset, read_next?, content_base64 }`. `sha256` and `size_bytes` are the whole file's on every piece; `next_offset` is null on the piece that ends the file. A file that fits comes whole in one reply with no `read_next`. One that does not says so in `read_next`, which stands before the bytes: which bytes these are, that a reply is cut at 80,000 characters, the `offset` to call with next, how many calls are left, and to join the decoded pieces and check them against the sha256. An offset at or past the end is refused with the file's size.
  - The fit is measured, not assumed: the reply is built, written as the door writes it (`replyText`), and the piece halved (kept a multiple of three) until it is under `REPLY_MAX_CHARS`, so a file with a very long name still never has the cut land inside its base64.
  - `mailFileWhole` makes the whole-file base64 the filing verbs send on, so `plan_mail_file` / `apply_mail_file` read exactly as before.
- **`supabase/functions/dev-mcp/index.ts`** (server 0.52.0, numbered behind v2.6804's 0.51.0, which merged first): `read_mail_file`'s description and schema say the above (`offset`, `length`), the server's instructions name the pieces, and the handler slices before the door writes. The verb is read-only and logged as before; `offset` and `length` ride in the call log's args. Each piece reads the file from Gmail again (Gmail's attachment read takes no range), so a file that belongs somewhere is still better filed with `plan_mail_file`.
- **Docs**: the verb's row and the *Oversized asks* line in `docs/dev-mcp/README.md`, the 0.29.0 paragraph in `docs/EDGE_FUNCTIONS.md` → dev-mcp, and the `mail-search` skill's line — each the sentence that already held the fact.
- **`to-dos/dev-seat-mail-file-text.md`** (#296): the text read, with where it plugs in.
