# v2.4139 — Delete job → Reassign to another job works when both jobs came from estimates (2026-09-29)

Taunya, 2026-09-29: *"I need to delete job #1031 and migrate the charges to #1033. I also need to delete job #1037 and migrate charges to #1034 … I got the same red error when trying to delete/migrate both."* Every job on that customer (J1031, J1033, J1034, J1035, J1037 — *Estimate for Kimberly Coe*, one per draw) was made from its own estimate.

## What was happening

`migrate_job_ledger_costs_and_delete` (the RPC behind Edit Job → Delete → *Reassign to another job…* and Pipeline → *Combine / Separate…*) moves every child of the source onto the target, including `UPDATE estimates SET job_ledger_id = <target>`. `estimates_job_ledger_id_unique` (baseline; partial on `job_ledger_id IS NOT NULL`) allows one estimate per job, so when the target already had one the statement raised, the function's `EXCEPTION WHEN OTHERS` arm answered `{ok:false, code:'migrate_failed', error:'duplicate key value violates unique constraint "estimates_job_ledger_id_unique"'}`, the transaction rolled back, and the modal showed that sentence in red. Nothing moved and nothing was lost. Two jobs made by hand, or one from an estimate and one not, never hit it — which is why the door had worked on every live pass so far (the 2026-09-22 ZZ cleanups reassigned hand-made jobs into J1032).

## The fix

- **Migration `20260929123000_migrate_delete_keeps_estimate_apart.sql`** — `CREATE OR REPLACE` with the v2.3900 body verbatim except the estimate step: when both jobs carry an estimate, the source's estimate gets `job_ledger_id = NULL` (what the FK's `ON DELETE SET NULL` does on a plain delete) instead of moving, and the ok payload carries **`estimate_unlinked: true`**; otherwise the link moves as before (`false`). The estimate keeps its record, status and customer on the Estimates page. `docs/migrations/20260929123000_migrate_delete_keeps_estimate_apart.md`.
- **`src/lib/jobs/migrateDeleteReply.ts`** (new kernel) — `migrateDeleteSuccessToast` / `combineJobsSuccessToast` compose the two doors' success toasts from the payload (the "Combined" note line as before) and append *This job's estimate stays on the Estimates page on its own — the target job already has an estimate of its own.* when `estimate_unlinked` is true. `JobFormModal.tsx` and `JobsCombineSeparateModal.tsx` call it in place of their inline ternaries.
- Help guide `combine-duplicate-jobs` gains the estimate paragraph; `docs/BILLING_FLOWS.md` points at the new definition.

## Verified

- `migrateDeleteReply.test.ts` (3 cases): the flag is read only as boolean `true`; each door's wording; the estimate line appended only when the flag is set.
- The diagnosis: the RPC body (`20260927233000`, live per `check:migration-drift`: 686/686 applied), the index (`20250101000000_baseline.sql`), and the jobs read through the app as the dev — J1031 (*Estimate for Kimberly Coe — 8275 Broussard*, Ready to Bill, $800, a pending 4-minute clock session so the delete gate demands a reassign) beside J1034 / J1035, all estimate-born.
- **Not run against Postgres here** (Docker down, and the pay-sources bed's stand-in schema does not cover this function's twenty tables). The proof is the push and Taunya's retry — J1031 → J1033 and J1037 → J1034 — which should now end with the success toast plus the estimate line.
