# v2.6714 — The file index reaches the HR file's files and the matter's documents (punch list #285, PR 1) (2026-11-08)

Punch list #285 (`to-dos/search-reaches-linked-file-text.md`), PR 1 of three: the file index (#240) reaches past the jobs Shared Drive to the files a person's HR file and a legal matter hold, so PR 2's case search can find a line of a call without the transcript being retyped into a named document. The owner's ask of 2026-11-08, after a case import: twenty-odd transcripts sat on evidence records as Drive-linked files and the seat's search read none of them.

## What changed

- **Migration [`20261108200000_file_index_reach.sql`](../migrations/20261108200000_file_index_reach.md)**: `file_index` gains `source` (`drive` | `hr_attachment` | `matter_document`), `source_id`, `person_id`, `matter_id` and `counsel_only`; a record's row is keyed on its own id (the key column keeps its name). The select policy opens a record's row to a dev alone and a restrictive policy refuses the seat as deployed a counsel-only row; `search_file_index`, `search_file_index_meaning` and `file_index_embed_due` read Drive rows alone, so Find a file and Gemini never see a record's words. Two queue functions, service role only: `file_index_records_due` (every attachment and unvoided matter document with no row, or a held one an hour on, newest first; narrowed by person or matter) and `file_index_records_drop_gone`. `dev_file_index_status` answers `by_reach`, `records_with_rows`, `records_without_rows`.
- **The records pass** (`supabase/functions/_shared/fileIndexRecords.ts`, the rules in `fileIndexRecordsKernel.ts`): the queue read, each record stamped `reading`, its bytes read from its bucket (a staged evidence file in `hr-files`, a matter document in `legal-matter-documents`) or from Drive (a linked file, by the id its link names, its kind and size read from Drive first so a Google Doc exports and a PDF is budgeted by its size), its text through the one reader, its row written with its reach. One file at a time inside the request's budget and the pass's spend, as the Drive pass runs. No chunks: the case search is words-only.
- **The reader** (`_shared/fileText.ts`): `textFromBytes` is the half past the download, so a bucket file is read by the same rules as a Drive file; `readWithin` races any read against the clock. **An email file** (`_shared/emlText.ts`, `textKindOf` → `eml` by `message/rfc822` or `.eml`): the kept headers (From, To, Cc, Date, Subject, encoded words decoded), the text parts decoded (plain over HTML; quoted-printable and base64 in their charset), each attachment named on a `File:` line, the base64 of an attachment never indexed.
- **The sweep** (`file-index-sweep`): a seventh step, `records` (10 a run), through the pass with the Drive token for linked files, in its own catch; the recheck, retake, OCR and reconcile steps read Drive rows alone (`.eq('source', 'drive')`), since a record's row is keyed on an id Drive would answer 404 for and the recheck would drop. The answer carries `records: { dropped, due, tried, indexed, held, remaining }` and the line says *Records: Indexed n files…*.
- **The hooks**: `hr-evidence-drive`, after one record is handled on a dev's call (not the cron's), runs the pass over that person's files with no row and answers `index`; the seat's `apply_matter_document` runs it over the matter, and `apply_person_evidence` runs it itself for a counsel-only record, which never asks the Drive filer. Fail-soft every time: the sweep's step takes what a hook missed within ten minutes. The app's Add evidence and the Legal desk's document save need no change; their files are taken by the filer's hook or the sweep.
- **Tests**: `src/lib/documents/fileIndexRecords.test.ts` (the kernel, `textFromBytes`, the pass against a recording client with a scripted bucket and Drive: the staged copy, the linked Google Doc, a failed download, a refused queue, a spent budget; the migration, the sweep and the hooks pinned), `emlText.test.ts`, `fileIndexKernel.test.ts` (the eml kind), `fileIndexPasses.test.ts` (the retake's Drive filter).
- **Docs**: `docs/EDGE_FUNCTIONS.md` (file-index-sweep, hr-evidence-drive, dev-mcp), `docs/HR_FILES.md` → Evidence, `docs/dev-mcp/README.md` (the file index row), the card.

## Read closer than the card

- The card drew an `enqueue a row on filing` by the two filers. The queue is the records' own state (a record with no row is due), so nothing is enqueued: the hooks run the pass at once and the sweep catches the rest. The app's Add evidence of a counsel-only record, which never calls the filer, waits for the sweep.
- OCR for a record's scan and search by meaning over a record's text are not in this PR: the OCR pass downloads from Drive, and the embedding queue excludes the new rows on purpose. A scanned letter on a record is held `scan`, named in `by_why`, and reads once OCR learns the bucket (a follow-up on the card).
- Find a file's two RPCs are replaced whole with one filter each; nothing else in them moved.

## Order

Push the migration, then deploy `file-index-sweep`, `hr-evidence-drive`, `dev-mcp` and `drive-link` (every writer of `file_index` now writes `source`). Then the types PR and the catalog.
