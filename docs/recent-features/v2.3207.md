# v2.3207 — Robots → Queue: Copy Desktop kickoff — run the shadow queue from a plain Claude Desktop chat (2026-09-09)

Client only; no migration, no edge change.

## Why

The Queue lens's per-bid "Copy robot prompt" assumes a harness that already has the twin-mcp connector: a Claude Code session in a repo checkout with the key exported (`scripts/twin-session.sh`, the `/bid` skill, the shadow-operator handoff). Asked whether a person could paste one prompt into **Claude Desktop** and have it bid every bid capable of being bid, the answer was no: the tab had no prompt that carried the connector setup, the key steps, or the loop, and the Code-side pipeline leans on a shell (`scripts/twin/twin.py`, plan-fetch with the key header, `gs` for oversized sets) and on subagents.

## What shipped

- **`docs/twins/kickoffs/desktop-operator.md`** — one self-contained kickoff for a machine with no repo and no terminal. Top half is the person's one-time setup: issue a robot key at Settings → Digital twins, put the `twin-mcp` connector into `claude_desktop_config.json` through the `mcp-remote` bridge (`--header X-Twin-Token:${TWIN_TOKEN}` with the key as an env value; Desktop's *Add custom connector* screen cannot send a header), restart, check the door with `get_brief`, and how plans get in (the person drags the PDF into the chat; a Desktop chat cannot call plan-fetch). Bottom half is the robot's instructions: score → orient → the blind rule → a **sequential `next_shadow` loop** (never claim while the current shell is unlocked, never two at once, stop at three shells per conversation, stop on `done: true`) → STG-1/2/3/5, LOCK, AUDIT, REPORT per the existing guides, with `ct_finish_takeoff` doing the CountTooling leg server-side → the owner's hard rules. The loop deliberately differs from `.claude/skills/bid/SKILL.md`'s "one `next_*` per run": Desktop has no subagents, so the batch is one chat working serially, and the rule that matters (no claim while a shell is open) is stated instead.
- **`src/lib/bids/desktopKickoff.ts`** — `twinMcpConnectorUrl(supabaseUrl)` and `buildDesktopKickoff(template, { connectorUrl })`, which fills the doc's single `{{CONNECTOR_URL}}` placeholder and throws if the placeholder is gone. Tests import the shipped markdown with `?raw` and assert the filled prompt carries the connector config with the key as an env var, the blind rule, the lock-before-claim rule, the three-shell cap, the hand-attached plans step, and no token-shaped string.
- **Robots → Queue lens** (`BidsRobotQueueTab.tsx`, dev only as before): a card above *Requested* — **Run the queue from Claude Desktop** with a blue **Copy Desktop kickoff** button (label flips to *Copied ✓* for two seconds, toast on success/failure, same pattern as the Digital twins panel's handoff button) and a collapsed **Preview the prompt** showing exactly what was copied. The connector URL is derived from `VITE_SUPABASE_URL` at render, so the copied prompt always names the project the app is running against.
- **Help**: new dev guide `run-the-robots-from-claude-desktop.md` (setup, running a batch, what it will not do). **Docs**: `docs/twins/HANDOFF.md` loop 3 and `TWIN_HARNESS.md`'s door section mention the Desktop path; `APP_DIRECTORY.md`'s Queue entry lists the button.

## Notes for the next session

- The Desktop path is attended by design: a person feeds each plan set. If that becomes the bottleneck, the missing piece is a connector verb that returns the shell's plan pages to the model (the edge side already has plan-fetch with the twin's token); until then the Code-side batch stays the unattended path.
- `mcp-remote` is a third-party bridge (`npx -y mcp-remote`). If Claude Desktop grows header support on custom connectors, the setup block in the kickoff shrinks to a URL and a header; the kernel and tests do not care.
