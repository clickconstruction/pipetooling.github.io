# v2.4244 — Edit Job: a payment’s Sent date saves by itself (2026-09-30)

Found by reading the code, not from a report: on Edit Job → Bill → ③ Payments received, a change to the **Sent** date alone started no save. The date showed in the box, the autosave said nothing, and the job closed without it. It was kept only when another Bill-tab edit (an amount, a line item, the Received date) happened to save in the same visit.

Why: the billing slice decides it has something to save by comparing `buildBillingSliceJson` with the JSON it last saved. v2.2303 added `sent_on` to the row type, the hydration and the writer (`diffPaymentRows`), and said it "rides the whole form pipeline" — but the slice JSON was not given the field. So the writer would have sent the date; nothing asked it to. Nothing else writes `jobs_ledger_payments.sent_on`: the "bank MM/DD →" button goes through the same `updatePaymentRow`, and the edit-mode Save button has been gone since v2.1080. No fragment or migration note says the omission was meant (`sent_on` is display-only — `paid_on` stays the pay-speed clock — which is a reason it went unnoticed, not a reason to leave it out).

- [`jobFormAutosaveSlices.ts`](../../src/lib/jobs/jobFormAutosaveSlices.ts) `buildBillingSliceJson`: each payment entry carries `s: p.sent_on ?? null`. The `?? null` makes a row with no `sent_on` key read the same as a null one.
- Same file, `paymentInsertRows` (the rows a **new** job is born with): now sends `sent_on`. New Job shows the same Sent box, and the date typed there was dropped at Create.
- Opening a job is still not an edit. The slice takes the first JSON it sees for a job as the saved one (`useJobFormAutosaveSlice`), and that JSON and every later one come from the same builder, so the new key is on both sides of the comparison. The undo snapshot (`jobFormUndo`) uses the same builder: a Sent-only change now lights Undo, as it should.
- One side effect to know: a re-read that brings back a payment whose `sent_on` differs from the form's now reads as an edit and is written back, as a differing `paid_on` or note always has.

Tests:
- `jobFormAutosaveSlices.test.ts` — the JSON changes when only Sent is set, moved or cleared; a row with no `sent_on` key equals a null one; **every field `diffPaymentRows` upserts, changed alone, changes the JSON** (the guard for the next column added to the writer); `paymentInsertRows` sends the upsert's fields less the id.
- `useJobFormAutosaveEngine.render.test.tsx` — a job that opens with Sent dates on its payments writes nothing, and neither does a second render of the same rows; a Sent-only change saves after 1.2 s and the upsert carries it; clearing it saves null; the close flush writes a Sent date typed just before closing.
- `JobFormPaymentsTable.render.test.tsx` — the Sent box hands the form `{ sent_on }` and nothing else, and null when cleared.

Not walked live, on purpose: the dev login writes to production, and the proof of this fix is a payment row changing. Without the fix the six new kernel and engine cases fail; with it they pass. Sent dates lost before today were never stored and cannot be recovered — they are blank in the database and need entering again.
