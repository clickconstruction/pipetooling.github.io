# v2.8466 — Document builder: a send that went but was not recorded has its own answer (2026-11-24)

Punch list #416, part 3, the build *A refusal key of its own for sent, not recorded*, which v2.8096 left for the function's next change. No migration. **One edge function changed and takes a deploy: `document-builder-send`.**

## What was there

`document-builder-send` sends the email first and writes the send's row after. When the row does not land it answered its `failed` key, *Something went wrong. Try again in a moment.*, with the truth in `detail`: *Sent, but not recorded: (what the database said)*. Since v2.8096 the page reads the first words of `detail` to tell that case from a send that did not go, since trying again sends a second email. That was a reader of a sentence, kept until the function could say it properly.

## What changed

- **The key.** `DOCUMENT_BUILDER_SEND_REFUSALS` (`_shared/documentBuilderSend.ts`) gains `sentNotRecorded`, status 500, with the words *The email went, but the send was not recorded here. Do not send it again.* They are the words the page already says.
- **The function.** Both sends answer it when the row does not land, the sheet to a trade and the builder to a GC, with the database's reason alone in `detail`.
- **The client reads both.** `sendWentUnrecorded` (`sendIo.ts`, pure) is true for the new key, and for `failed` whose `detail` opens *Sent, but not recorded*. `sendRefusalWords` takes its words from the key's own in both cases, so they never depend on what the answer's `words` hold.
- **So the order of the two deploys does not matter.** The new page over the old function reads the old answer. The old page over the new function reads the new key's words with the reason after them, which is the same sentence. A tab left open across the deploy says the right thing either way.

## The deploy

After the merge, from a checkout at `origin/main`:

```bash
bash scripts/deploy-functions.sh document-builder-send
```

Until then the function answers the old way and the page reads it as before. `_shared/documentBuilderSend.ts` is also read by `gc-trade-portal`, `customer-portal` and `document-builder-link`. None of them answers this key, so none needs a deploy for it, though `check:edge-drift` may name them as behind.

## Not changed

- `gc-trade-email` and `send-contract-for-signature` answer the same case the old way, `failed` with *Sent, but not recorded:* in `detail`. #416 names this one function. Their own pages are not the Document builder's.
- The one press for every party that is ready still names such a row among the ones it lists after, with these words as its reason. Whether that row should read as sent is a separate call.

## Tests

- `sendIo.test.ts`: the key's status and words, which hold no *try again*. The new answer with a reason, with none, and with its words lost. The two functions read the same. Every other refusal is a send that did not go.
- `sendIo.refusal.test.ts`, new: both sends off the wire, with the function's answer stubbed in each shape. The same words from each, never *try again*, and a send that did not go still says to try again with its reason.
- `npm run check:edge-bundles`: every function links, and none is over its upload ceiling.

## Seen, and not seen

Nothing here draws differently, so no harness was made. The words on the page are the ones v2.8096 put there, and the tests hold them for both answers. **Not seen:** the deployed function answering the new key. That takes a real send whose row fails to land, which a walk cannot make happen on purpose.
