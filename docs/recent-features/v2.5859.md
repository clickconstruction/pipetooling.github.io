# v2.5859 — Release of Lien window: the property record is the job’s own (2026-10-25)

The Release of Lien window (`LienReleaseModal`) had the gap v2.5832 closed in the Lien window: `loadPropertyRecord` read the link from the opener's copy of the job row (`job.customer_address_id`). A copy can lag a link made since it loaded. The Pipeline's property-kind badge links a job and keeps the link in memory until the board reloads (`usePropertyKinds.linkJob`). A window opened from such a row then showed step 4's *Link a property record* picker for a job already linked. The waiver's *Check from* fell back to the GC, because `ownerName` resolves from the linked record (v2.2614) and there was none.

## The fix

- `loadPropertyRecord` reads the link with `readJobPropertyRecord(job.id, job.customer_address_id)` (`src/lib/jobs/jobPropertyRecordIo.ts`, v2.5832): the link on the job's own row, then the record, the opener's link only when the row cannot be read. A job its own row leaves unlinked keeps the candidates (the customer's and the GC's records) with the address match as the default pick.
- The window's one other touch of the link is its own write (`linkPropertyRecord`), which already sets the chosen record in place.

## Tests

`src/components/jobs/LienReleaseModal.property.render.test.tsx` (new, job 891's shape). With an opener row that has no link while the job's own row links the record, step 4 shows *Property record: 11730 TX-29…* and no picker, and *Check from* names the record's owner. This case failed before the fix: the step drew the picker and *Check from* read *Burd & Assoc.* A job its own row leaves unlinked still gets the picker with the matching record picked.

## Docs

`docs/LIEN_RELEASE_MODAL_ARCHITECTURE.md`'s property record line names the reader. No guide describes the picker's trigger, so none changed.
