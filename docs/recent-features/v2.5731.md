# v2.5731 — Messages: the walk kit's server half (2026-10-22)

Punch list #142 (the walk kit) PR 7: the `walk` edge function, the one place the kit needs a server secret (`to-dos/walk-kit/BUILD_PLAN.md` § PR 7). The driver (`npm run walk`, PR 8) runs the loop through it and through the tester's own three sends.

- **The function** (`supabase/functions/walk/index.ts`, `verify_jwt = false` in `config.toml`): POST `{ action, … }`, gated by `X-Dev-Login-Secret` equal to `DEV_LOGIN_SECRET` (401 otherwise). `setup` makes the tester when missing (`walk-tester@walk.pipetooling.local`, *ZZ Walk tester*, an assistant in training mode flagged `is_walk_tester`, found on any page of accounts through v2.5724's helper, else created), then `walk_setup` (PR 4); `fallback: true` takes the owner's own phone and tells `walk_setup` the number is shared (§ 4). `open` reads bids@'s inbox as the service account impersonating the kit's address, finds the estimate email by the app's sender and the estimate's number, and GETs its accept link through `get-estimate-for-customer` with a browser's user agent, never as a preview, so the 👀 line is written. `reply-email` sends the words from bids@ to the team box's address in the estimate email's thread (`gmailSend`, new in `_shared/gmail.ts`). `text` posts the words from the bids box's Quo number to the team box's number, the same request `sendText` makes, with the vault's key (refused in the fallback walk, where the owner texts by hand). `seed-old` writes one three-day-old out text on the kit's contact, so Waiting on them can be read in a same-day walk. `cleanup` runs `walk_cleanup` and answers its counts or its refusal.
- **No secret leaves**: every answer carries ids, times and words; a link shows as its last four characters; `leakedSecret` (the kernel) scans each answer for the gate, the keys, the service account, the Google token minted and the Quo key loaded, and holds back one that carries any.
- **The kernel** (`src/lib/walk/walkFunction.ts`, mirrored): the ask, the Gmail search and the subject match, the accept link's token, the reply's RFC 2822 bytes and Message-ID, the seed row, the browser's user agent, the leak guard. `walkFunction.test.ts` covers each; `walkFunction.run.test.ts` runs the handler on the fake database with `fetch` caught: the gate, each action's request as the plan shapes it, the tester made once, no answer carrying a secret.
