# v2.3038 — Test-gap audit, pass 48: a job's card allocations with attribution get their first tests (2026-09-07)

Follow-up to v2.3037. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`fetchMercuryJobAllocationsWithAttributionForJob.ts` (137 lines) is the one read behind every "card charges on this job" surface — Job Summary, the Parts tab, the unattributed-charges list and per-person parts cost: the job's Mercury allocations paged with their transaction, filtered by the same Internal-Transfers rule as the bulk card-charge map, flagged when the charge is also linked to a supply invoice, and named through attributions → people or users. Five callers, no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- The read is paged and ordered by creation then id, carries the transaction embed, and asks the exclusion loader about every transaction seen; rows in the Internal Transfers bucket are dropped and never looked up for attribution, so the detail rows always sum to the card total.
- An invoice-linked charge stays in the list and carries the flag so Job Summary counts the purchase once.
- A person attribution wins over a user attribution even when the person's name is missing (the name reads as none); attributions, people and users are only asked for when there is something to name.
- Name resolution fails soft: a failed attribution, people or users read leaves the allocations in place without names. A failed allocation read throws. A job with no allocations asks nothing further.
