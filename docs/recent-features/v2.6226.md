# v2.6226 — A combined job keeps the old HCP and C# numbers (2026-10-31)

Feature with a migration (`20261031020000_job_prior_numbers`, `docs/migrations/20261031020000_job_prior_numbers.md`); no edge function. The owner, about to combine six Gun Dog import shells: *HCP 550, 549, 548, 422, 178 and 130 were all House Call Pro numbers from the old system, so we don't want to lose the House Call Pro number here. Is there a way for us to record multiple House Call Pro numbers for a job?*

## Change

- `jobs_ledger.prior_numbers text[]`: `'HCP 550'`, `'C# 543'`. `migrate_job_ledger_costs_and_delete` fills it from the source (its HCP #, its C#, its own prior numbers, each once); `search_jobs_ledger` matches it, so every picker on that RPC and the Combine window's own search find a job by an old number.
- `src/lib/jobs/priorNumbers.ts` (tested): the entry shape, the parse, the labels in the job's prefix (*JP550*), the words (*also JP550, JP549*; the chip's *also 550 · 549*).
- `jobsStagesRowShared.tsx`: the Pipeline row's number chip carries the prior numbers in its title. `DevelopmentPieces.tsx`: the Jobs & bids table's job line ends *also 550 · 549* (`MemberJob.prior_numbers`, a fail-soft read of its own in `fetchDevelopmentPage`, so the page stands before the push). The Combine window's *What does Combine do?* and the guide *combine two duplicate jobs into one* say the numbers are kept.
- `src/types/database.ts` hand-adds the column so the client typechecks; the generator's run after the push replaces it.

Not in this PR: a hand editor for prior numbers (the combine writes them), and a *same bill, counted twice* combine — CP543 CONCRETE PLANT and JP468 Diamondback are one $8,620.50 bill recorded twice, but the Combine tool refuses a source with a payment and adds the source's revenue to the target, so that pair waits on a mode that moves costs and numbers without doubling the bill.

Deploy: `supabase db push` after the merge (no screen waits on it), then `npm run gen:types`.
