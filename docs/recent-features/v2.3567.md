# v2.3567 — Dispatch inbox: the phone-number request self-heals (2026-09-17)

Item 1 of `to-dos/dispatch-residuals.md`, the one-kernel-change residual from the v2.2880 / v2.2883 sweep.

## The gap

The **add a customer phone number** request (v2.1024 — the red phone on Dashboard job cards) mirrors the photos-link request exactly, including its only auto-close: `JobFormModal` closes it on a blank→set transition of `jobs_ledger.customer_phone`. A request filed against a job whose number was already set — set outside the Job form, or set before the request — never sees that transition, so it stayed open until someone closed it by hand. The photos-link request had the same flaw and got a sweep in v2.2880; the phone did not.

## The change

[`picturesDispatchRequests.ts`](../../src/lib/picturesDispatchRequests.ts) now names both kinds in one table, `SELF_HEALING_REQUESTS` — the action, the `jobs_ledger` column it asks Dispatch to fill, and the closing note — and the two readers take the kind as an argument: `jobIdsForRequestSweep(rows, action)` and `pickOrphanedRequestIds(rows, valuesByJobId, action)`. The pictures-only names stay as thin wrappers for their call sites. The guard is unchanged: a job whose column was not read is never swept.

[`useDispatchInbox`](../../src/hooks/useDispatchInbox.ts)'s sweep reads `id, job_pictures_link, customer_phone` for the union of both kinds' job ids in one query, then closes each kind's orphans with its own note — *Customer Pictures URL already set — closed automatically* / *Customer phone already set — closed automatically*. Same rules as before: dispatch-inbox-eligible viewers only, silent, each id remembered so a refused update is never retried into a reload loop.

Four new kernel tests (the table, the per-kind pick, the unread-job guard, the per-kind id collection).

## Verified

Kernel tests; the Dispatch inbox on the dev server loads clean with the new sweep in place. No open orphaned phone request existed to watch close, and none was fabricated — the sweep's first real run is on the next inbox load that finds one.
