# v2.7663 — Tell the dev: the answer comes back to you (2026-11-17)

Punch list #380, PR 4 of six: the answer. Until now the line a dev typed when closing a note was drawn in the dev's inbox alone, so the sender never learned whether anyone read it. That is what stops people sending.

## What a person sees

- **Your notes**, under the box: the sender's last six notes, newest first. Each carries a chip: *Sent* with the day it went, *Answered* with the day the answer was written, or *Closed* when it was closed with no words.
- **The answer** sits under its note, with a green rule. An answer not seen before is drawn bold for that one showing.
- **The dot.** The floating wrench and the header's wear a green dot while an answer is unread. Listing the notes reads them, so opening the box clears it.

## How it is built

- **No new column and no new policy.** A sender already reads their own rows, and the answer is `closed_note`, which **Answer and close** in the inbox writes.
- **`myNotes.ts`**: `isAnswered` (closed with words), `unreadAnswerCount`, and `myNoteLine`, the note as the box lists it. Unread is the time the box last listed the notes, kept per person per device.
- **No read at boot for most people.** A device asks for answers when the shell comes up only if it has sent a note or listed some before (`pt_dev_notes_known_<user>`). Everyone else asks nothing until they open the box.
- **`loadMyNotes`** filters on the sender, because the owner and a dev are shown every row.
- **The dot's count** lives in a small store (`answerDot.ts`, `useUnreadDevAnswers`), so the header's wrench and the floating one read the same number.

## Not in this PR

No push to the sender when an answer is written. The dot shows the next time the app is opened on a device that has sent a note.
