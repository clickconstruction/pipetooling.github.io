# v2.3203 — Counts bid picker: count-row tallies paged past the 1,000-row cap (2026-09-09)

Client only; no migration. The `[row-cap] bids_count_rows` tripwire (v2.2756) fired on the Bids page on 2026-09-09.

## What was wrong

The Counts tab's bid picker tallies count rows per bid for its left column (v2.2381) with one un-ranged `select('bid_id').in('bid_id', …)` per 100 bids. PostgREST answers an un-ranged read with at most `max_rows` (1,000) rows and a 200, so any 100-bid chunk whose bids carried more than 1,000 count rows between them lost its tail silently: those bids showed a low count, or none, with nothing in the error path. The Adopt-bid modal (v2.2133) ran the same read over up to 400 candidate ids at once for its "N count rows" preview — the same cap, plus a 414 risk from the id list.

## What shipped

- New kernel [`src/lib/bids/countRowTallies.ts`](../../src/lib/bids/countRowTallies.ts): `loadCountRowTalliesByBid(client, bidIds)` runs the read through `fetchAllRowsChunkedIn` (150-id chunks, each paged with `.order('bid_id').order('id').range(from, to)`) and folds it with the pure `tallyRowsByBidId`. Throws `DatabaseError` on a page error rather than returning a short tally.
- [`BidsCountsTab`](../../src/components/bids/BidsCountsTab.tsx): the picker effect calls the kernel; on failure the column stays absent, as before.
- [`AdoptBidModal`](../../src/components/bids/AdoptBidModal.tsx): the count-row read goes through the kernel; the sibling `bid_versions` and `price_book_versions` reads over the same id list are chunked and paged with `fetchAllRowsChunkedIn` too. A failed load now shows an error toast instead of silently rendering an empty candidate list.
- Regression test `countRowTallies.test.ts` with the fake-cap client from `partsCatalog.test.ts`: 120 bids × 30 rows (a single chunk is three times the cap) must tally to 30 each, every call ranged.

Docs: `docs/TROUBLESHOOTING.md` → "[row-cap]" was followed as written (fix 1, page it). Release note `v2.3203.ts`.
