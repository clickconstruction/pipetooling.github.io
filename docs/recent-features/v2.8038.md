# v2.8038 — Gear menu: Job Mode, Dispatch Mode and Task Mode are one at a time (2026-11-20)

The owner's walk of the app on an iPhone, 2026-11-20: *"I notice that a user can select job mode and task mode at the same time, and this doesn't make sense, it seems they should be mutually exclusive."* The screenshot showed the gear menu with **Job Mode** and **Task Mode** both ticked while the page was in Task Mode. Client only: no migration, no edge function.

## What was wrong

The three page modes were stacked on purpose. Each kept its own stored value (`dashboard_job_mode_<user>`, `farm_mode_<user>`, `dispatch_mode_<user>` with `users.dispatch_mode_enabled` behind it), the menu ticked every stored value, and `Layout.tsx` drew whichever won by Task > Dispatch > Job. So:

- The menu could tick two or three rows, and only one of them was the page.
- A master technician has Dispatch Mode on before they ever choose. One who took Job Mode from the Dashboard's card got the Dispatch Mode bar under a Job Mode Dashboard, because `Dashboard.tsx` read Job Mode's stored value directly and the shell read Dispatch Mode's. The usage ledger shows both of the company's master technicians in that state.

## The rule

In one pure kernel, [`pageMode.ts`](../../src/lib/pageMode.ts):

- **One mode is drawn** (`resolvePageMode`): the first that is on in the order Task Mode, Job Mode, Dispatch Mode, or `full` with none.
- **The tick is the page** (`pageModeTicks`): a row is ticked only when its mode is the one drawn.
- **A press switches to that mode** (`pageModeWrites`): its own value goes on, every mode above it in the order goes off, and the ones under it are left alone. A value that would not change is not written.
- **Switching a mode off goes back to the mode the person had**: it clears that one value, and the page falls to what is stored under it.

[`usePageMode`](../../src/hooks/usePageMode.ts) holds the three toggles' own hooks to the kernel and is the one door that switches a mode. `Layout.tsx` (the gear rows, the phone bar's Modes rows, the Task Mode strip's Exit) and `Dashboard.tsx` (the page fork, the Job Mode card, the Needs you door) read and write through it. Each toggle keeps its storage, its same-tab event (`dashboard_job_mode_changed`, `farm_mode_changed`, `dispatch_mode_changed`) and, for Dispatch Mode, its server row, so every screen that listens for one still follows.

## The decisions

- **Task Mode off goes back, it does not land on the full app.** Switching Task Mode on writes Task Mode alone. A field hand who drops into Task Mode for a task comes back to Job Mode, and a sub or helper whose Job Mode is on with nothing stored is not left on the full Dashboard.
- **Job Mode is ahead of Dispatch Mode.** The order was Task > Dispatch > Job. Job Mode is a pick made on this device, and nobody who can hold Dispatch Mode has Job Mode on unless they switched it on here. Dispatch Mode follows the person to every device and is on for assistant-like roles and master technicians before they choose. With Job Mode ahead, picking Job Mode on a phone writes nothing to the server, so Dispatch Mode stays on at the desk, and switching Job Mode off goes back to it. The other order would have needed a server write that switched Dispatch Mode off everywhere.
- **What a master technician sees change.** One who holds both from before reads as Job Mode: the Job Mode Dashboard they chose stays, and the Job Mode bar takes the Dispatch Mode bar's place. **Dispatch Mode** in the gear menu switches back, and takes Job Mode off on that device.
- **No migration.** Nothing stored is rewritten on load. A device holding two or three values reads by the same order.

- Who may hold each mode, and each mode's default: `dispatchModeEligibleForRole` and `dispatchModeDefaultForRole` are the two inline role tests moved out of `Layout.tsx` and `Dashboard.tsx` as they were.
- The three toggles' kernels and hooks, their stored keys and their events.
