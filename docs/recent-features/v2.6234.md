# v2.6234 — Lock a bid version so only you edit it (2026-10-31)

Feature with a migration (`20261031140000_bid_version_lock`, `docs/migrations/…md`); no edge function. The owner, after two estimators' separate Gun Dog bids became versions: *in versioning a user should have the option to lock down that version so only they can edit, if they choose; this should definitely not be enabled by default.*

## Change

- Migration: `bid_versions.owner_user_id` / `locked_by` / `locked_at`; `bid_version_lock_refusal` and the guard triggers on every table that carries a version (and the pricing facets' children), `bid_versions_set_owner` and `bid_versions_lock_guard`; each lock or unlock writes a `bids_submission_entries` line. Nothing is locked by the migration.
- `src/lib/bids/versionLock.ts` (tested): who may lock (the owner, a dev, a master), who may unlock (the holder too), whom the lock blocks, the badge's words (*Locked · you* / *Locked · William*) and titles.
- `BidVersionPicker.tsx`: the 🔒 badge under a locked version's name with who to ask; the 🔓 / 🔒 press beside the pencil for those who may; the write through `bid_versions`, the toast, `reloadVersions`. A refused write anywhere shows the database's words through `formatErrorMessage`.
- `src/types/database.ts` hand-adds the three columns; `npm run gen:types` after the push replaces it. The guide *bid one project to multiple GCs* gains *Lock a version*; `docs/ACCESS_CONTROL.md` records the rule.

Not in this PR: the version's owner is whoever made or adopted it (older versions took the bid's estimator); handing a version to someone else is a database update the picker does not yet offer. Deploy: `supabase db push` after the merge, then `npm run gen:types`.
