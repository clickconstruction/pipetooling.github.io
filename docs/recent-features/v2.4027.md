# v2.4027 — Edit Job: a discount applied in Bill Customer no longer makes the job save twice (2026-09-28)

Client only; no migration, no edge function. The third of the three behaviours row 4 of punch list **#46** wrote down and did not change.

## What was wrong

Bill Customer writes a discount row straight to the database (`apply_job_discount`) while Edit Job is open. The form re-reads its line items (`rehydrateFixturesFromDb`) and re-baselines the billing slice on the render that carries them. The new rows also started the slice's 1.2 s debounce, and `markSavedNow` set the baseline without cancelling it — so the timer fired and the slice wrote revenue, payments and every line item (delete + re-insert) exactly as they already were.

## What shipped

- `useJobFormAutosaveSlice.markSavedNow` cancels the pending debounce before it sets the baseline. Edit Job's engine is its only caller; Edit Bid and the estimate draft run on the same hook and do not call it.
- `useJobFormAutosaveEngine` re-baselines through `billingRereadFromDb`, which does nothing when the slice had an edit waiting or a save in flight. The re-read replaces the line items only; a payment typed a moment earlier is not in it, so the save that edit is owed still runs. Before this change the redundant save is what carried it.

## Tests

- `useJobFormAutosaveSlice.render.test.tsx` (new, 3): the waiting save is dropped; the next edit saves after its own wait; nothing waiting, nothing changes.
- `useJobFormAutosaveEngine.render.test.tsx` (20): the case that pinned the second write now expects none; an edit after the re-read saves; a payment typed before the re-read is written with the re-read rows.
