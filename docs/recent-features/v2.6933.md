# v2.6933 — Bids and permits: the bid's reads past 1,000 rows (punch list #307) (2026-11-11)

`supabase/config.toml` sets `max_rows = 1000`, so the API cuts every read that asks for no range at 1,000 rows and says nothing. v2.6924 paged three Permits reads. The docs catch-up of 2026-11-11 (PR #7659) found four more in `src/lib/research/bidSiteIo.ts` that asked for more than the API gives.

None had lost a row yet. Counted on the database the same day, with house numbers read a little more loosely than the app reads them: the Bid Board's one read for San Antonio holds 738 rows, the Builders worklist's 817, and every bid's numbers together 964. `builder_customer_answers` holds none and 497 customers are live.

## What changed

- **`loadPermitsByHouseNumber`** (the RPC `bid_site_permits`): a page at a time through `fetchAllRows` (`src/lib/supabasePaging.ts`). The function's own order is day, number, type, and the table's unique key also holds the source, so one permit in both of San Antonio's feeds on one day would tie and a tie can shuffle between pages. No row ties today. The pages are cut by `id` instead, and `sitePermitOrder` (`bidSitePanel.ts`, pure) puts the answer back newest first, so a caller reads the same order as before. Each page is asked bare first and retried on a failure that is not a missing function, as the one read was.
- **The function still stops at 5,000 rows** by its SQL `LIMIT` (`SITE_PERMITS_RPC_LIMIT`). No migration: the largest real ask is under a fifth of that. A read that returns exactly 5,000 warns once in the console through `warnIfRowCapHit`, so that cut is not silent either.
- **`loadNameAnswers` and `loadAllNameAnswers`**: one paged read, `readEveryAnswer`, oldest first with the answer's `id` settling two saved in one instant. The newest decisive answer stands, and it is the one a cut would have lost. A missing table is still null. Any other refusal now throws with its reason in the house shape.
- **`loadCustomerNames`**: paged by name and `id`, each page retried.

## Left as they are

- `loadBidsOfCustomers` (three reads at `.limit(500)`) and `loadRecentBidsWithCustomer` (`.limit(1000)`, the worklist's stated newest thousand) ask for no more than the API gives. Their limits are still silent caps: the busiest customer has 55 bids.
- `loadBuilderKinds` asks for the keys it is handed, one a call today.
- The read of `permits` that stood in before the function was pushed (400 rows a house number, three numbers at most) is unreachable now and was not touched.

## Tests

`bidSiteIo.paging.test.ts`, against a stand-in that cuts an un-ranged read at 1,000 as the API does: 2,340 permits over three pages, each ordered by `id`, back newest first; a page that times out once asked again; the missing function, null for many numbers and the table for a few; the warning at 5,000; 2,300 answers for the worklist and 1,150 for one GC's rows, ordered by day then `id`; the missing table; 1,204 customers. Ten mutants each fail a test, and the file as it was fails seven of the eight. `bidSitePanel.test.ts`: the order, and a tie settled the same way from either side.

Live, signed in on the dev server against the real API, read only: for 180 house numbers in San Antonio the function holds 3,317 permits. The plain read returned 1,000. The paged read returned all 3,317, each once, newest first, in 2.5 s over four pages. 1,849 of the 2,317 the plain read lost were plumbing permits.
