# v2.6408 — The file index leaves the largest plan sets to Drive's search, so a read never runs out of memory (2026-11-03)

v2.6332 raised the index's PDF cap from 8 MB to 50 MB, trusting its time budget to keep a read inside the platform's limits. The first live test after its deploy, one call each on the ZZ test bids' held plan sets, answered otherwise: an 11 MB set read through (as a scan, its sheets having no text layer), a 25 MB set ended its worker in 8 seconds with *Memory limit exceeded* in the function's log (HTTP 546, `WORKER_RESOURCE_LIMIT`), a 29 MB set ran out its 20-second read, and a 76 MB set stayed `big` with no download. The time budget bounds CPU, not memory: pdf.js holds the whole file and several times it in decoded streams, and 256 MB is the worker's whole allowance, shared with every other request in it.

- **`TEXT_PDF_MAX_BYTES` is 12 MB** (`_shared/fileIndexKernel.ts`): over it a PDF is `big` with no download, as v2.6306 held everything over 8 MB. The pages cap stays 1,000 and the time budget stays, so a long written spec under 12 MB is still read through and a plan set under it as far as its time goes.
- **`PASS_READ_MAX_BYTES` is 16 MB**: past the first file, a request starts a PDF only while the PDFs it holds stay under that, and the next call reads the rest (`passMayTake`, the rest being `remaining`).
- **A search's ten excerpts share 24 MB** (`EXCERPT_PDF_LIMITS.passMaxBytes`), checked in `fileText` after each download and before its parse, since the ten downloads land at once.
- **What it costs**: the PDFs between 12 and 50 MB stay `big` in the index, as they were before v2.6332. Drive's search, which runs behind the index every time, still finds them by their words.
