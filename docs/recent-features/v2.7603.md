# v2.7603 — Prospects: what the calling queue does when a card leaves is one tested rule (2026-11-17)

Step 2 of the order in `docs/PROSPECTS_TABS_ARCHITECTURE.md`, its second part (Stage-A rows 4 and 10). No behaviour changes.

**Four kernels in `src/lib/prospects/callingOrder.ts`.**

- `queueAfterRemoval(queue, index, id)` gives the queue without the card, the pointer's new place and the id now under it. The pointer keeps its place, so the card that followed comes up; when the last card left, it steps back onto the new last card. Six handlers in `src/pages/Prospects.tsx` each wrote this inline as `nextList` and `nextIdx`: `handleDeleteProspect`, `handleNoLongerFit`, `handleCantReach`, `handleConverted`, `handleBenchSave` and `leaveQueueAsLanded`. All six call the kernel now.
- `indexAfterOtherRowLeft(queue, index, id)` is `handleBenchSave`'s other branch: a landing from the list or the Board takes a row that is not the deck's card, and the pointer steps back one when that row sat before the card, so the same card stays up.
- `insertColdest(queue, row)` is Send back's re-insert: added once, then the whole queue coldest first, never-contacted rows leading, ties by company name. A row already in the queue hands back the same list, so React still sees no change.
- `queueWindowStart(index, length, limit)` is the first row of the queue peek.

**Why these first.** This is the arithmetic that decides which company comes up next after every outcome. It had no test, and a copy that drifted from the other five would have shown as one press landing on the wrong card.

**Size.** `Prospects.tsx` went from 5,389 lines to 5,377.

**Proof.** 20 new tests in `callingOrder.test.ts`: the card under the pointer, the last card, the only card, an id not in the queue, a pointer past the end; the row before and after the card; the coldest insert's four orders and its same-list answer; the peek at the top, in the middle, at the end and on a queue shorter than the peek. The handlers keep their order of setters, so the renders are the same.

**Not in this PR.** The map's row 8, the Subs deck's order inside `loadFollowUpProspects`, moves with the loader in the data-seam step: its by-rank branch awaits a read in the middle, and cutting it apart from the loader would change when that read runs.
