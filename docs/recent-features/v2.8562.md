# v2.8562 — A reload that hangs after an update now lets go (2026-11-24)

Punch list #406, a fault the simulator's walk of that card met beside it on 2026-11-25. The reload path's earlier mends are on punch list #85 (`docs/recent-features/v2.8377.md`, `v2.8379.md`, `v2.8431.md`, `v2.8458.md`, `v2.8463.md`). Client only: no migration and no edge function.

## What was seen

In an iPhone simulator's Safari, on the live site, in an hour when three deploys landed:

1. **Exit** from View as. The page read *Updating app…* for about 80 seconds.
2. A fresh load read the same for about 30 more.
3. Then *This page could not load*, and its **Reload** press went grey with *Checking for a signal…* for 90 seconds or more. The site itself answered in a fifth of a second.
4. Quitting Safari cleared it.

No console or network log came off the simulator, so which promise hung there is not known. The walker said it may be the simulator's Safari and not a phone.

## What the code says: the app, in any browser

Every reload on this path is `hardReloadFromRoot` (`src/lib/hardReload.ts`). It unregisters the service worker and empties the caches, and it navigated only after that wipe settled. The wipe had no end of its own:

- **A browser runs one registration's jobs in order.** `unregister()` is a job, and so is an install. An unregister asked for while the same worker is installing waits until the install ends. That is the service worker standard's job queue, not one browser's habit.
- **An install ends only when the whole precache is on the device.** The worker's install event waits on workbox, and workbox 7.4.1 fetches the precache one file at a time (`PrecacheController.install`, *Cache entries one at a time*). This build's precache is 1,548 files, about 48.5 MiB.
- **Every load starts that install.** `UpdatePrompt` registers the worker at once on every load. A load that follows a wipe has no worker and no cache, so it installs from nothing. Entering View as wipes too (`AuthHandler` in `App.tsx`), so a walk through View as always stands on a fresh install.
- **Right after a deploy is the worst moment.** Every hashed file has a new name, so none of the precache is in the browser's own cache either. The same deploy is what takes a page's chunk away and starts the recovery reload.

So a reload asked for inside an install stood on *Updating app…*, or on a grey **Reload**, for as long as the install took: seconds on a desk, a minute or more on a phone. Three places had nothing to end them:

| The wait | What it stood on | Its end before |
|---|---|---|
| `hardReloadFromRoot` waiting on the wipe | whatever asked for the reload | none |
| **Reload** on the fallback, after the network answered yes | a grey press and *Checking for a signal…* | only the page leaving |
| *Updating app…* after the recovery reload fired | the whole page | only the page leaving |

The probe is not one of them. It gives up after five seconds, and a no gives the press back. A grey press past five seconds means the network answered yes and the reload never left.

Nobody watched the registration's job queue on the simulator, so this reading is not proven there. It was measured on the built app instead, under *Seen on the built app*. The three waits are in the code either way.

## What changed

- **The wipe is held to three seconds.** `wipeBeforeLeaving` in `src/lib/hardReload.ts` settles when the wipe is done or when `WIPE_DEADLINE_MS` has passed, whichever comes first, and never rejects. `hardReloadFromRoot` leaves on it, once. On a quiet page the wipe is a few promise turns, so nothing waits longer than it did.
- **The View as door uses the same wait.** `AuthHandler` in `App.tsx` reloaded only after the bare wipe. It now reloads after `wipeBeforeLeaving`.
- **A dead Reload comes back.** On a yes the press still stays dead while the page leaves. If the page is still here after ten seconds (`ROUTE_RELOAD_LAND_MAX_MS`), the press is live again and says *The reload did not finish. Press Reload to try again.* The **Fix app** link is under it, as before. A second press asks the network and reloads again.
- ***Updating app…* gives way.** `chunkLoadRecovery.ts` now remembers when the started reload fired. Ten seconds after that (`CHUNK_RELOAD_LAND_MAX_MS`), with the page still here, `RouteChunkBoundary` draws its fallback in place of *Updating app…*: *This page could not load — the app may have just been updated.*, **Reload** and **Fix app**. The wait before the reload fires is not counted. A save in flight still holds it for up to half a minute, and typed words hold it until they are sent or cleared, as before.

## Why leaving at the deadline is safe

The wipe unregisters before it touches a cache. So at the deadline one of two things is true:

- **The worker is still registered.** Then no cache has been touched. A worker in control serves its own whole build, and `UpdatePrompt` brings that page onto the new build the usual way. A worker that is only installing controls nothing, and the load comes from the network.
- **The worker is gone.** Then the load comes from the network, which is what the wipe was for.

Neither leaves a worker in control of an empty precache, the state the wipe's order exists to prevent.

## Left as it was

- **A customer's page** (`PublicPage`). Its loading look already offers **Try again** after ten seconds, and its reloads go through `hardReloadFromRoot`, so the deadline covers them.
- **The small *Updating app…* note over a window** (`WindowLoadBoundary`) and a page's own error boundary. They still read `chunkRecoveryReloadStarted`, which is unchanged. The page behind the note stays usable.
- **Hard Reload in the gear menu and the broadcast reload.** Neither draws a waiting look. Both get the deadline.
- **No second navigation.** A `location.replace` a few seconds after the first try was weighed and left out. It would restart a load already on its way on a weak signal, and nothing seen says the navigation itself was what hung. The press coming back covers it, with a person deciding.
- **The fallback after a stall stays when the address changes**, where the boundary itself started the reload. It has its press and its link.

## Seen on the built app

On 2026-11-25, this branch's own `npm run build`, served from the Mac by a throwaway server that was never committed. Every file under `/assets/` took a tenth of a second, so the install was long. Headless Chromium and headless WebKit, the engine Safari runs, through Playwright. The page was the sign-in page, with no sign-in and no site but the Mac.

| What was asked while the worker was installing | Chromium | WebKit |
|---|---|---|
| A bare `unregister()`, as the wipe sends it | answered after 102.3 s, in the same millisecond the install ended | answered after 102.8 s, in the same millisecond the install ended |
| The app's own recovery reload (`vite:preloadError`, as after a deploy) | asked the server for its new page after 3.0 s, and landed on it | asked the server for its new page after 3.0 s, and landed on it |

The first row is the fault: before this change the reload waited on that answer. The second row is the mend: the worker was still installing when the page left, the install went on behind the new page, and the new page drew.

## Tests

- `hardReload.test.ts` (10, was 3): a registration whose `unregister()` never answers. The page leaves at three seconds and not before, once, with the page kept for `index.html` to put back. An answer after the deadline does not leave twice. An answer before it leaves at once.
- `chunkLoadRecovery.test.ts` (39, was 33): stalled only after the reload fired and ran past the limit, never while a write or typed words hold it, and a second try a minute later is a new wait.
- `routeReload.test.ts` (10, was 7): the `stalled` view and its words under `plainWords`.
- `RouteChunkBoundary.render.test.tsx` (18, was 13): the press comes back with its line and a second press reloads again, *Updating app…* gives way to the fallback, and it stays while a save holds the reload.

## Not tested

- **No phone and no simulator ran this.** The two engines above are headless builds on a Mac. Safari on an iPhone was not tried.
- **The fallback and its press in a real browser.** They need a sign-in, and the local build has no database behind it. The render tests hold them.
- **The View as door** (`AuthHandler`) has no test of its own. It uses the helper the tests hold.
- **A real deploy landing on an open page.** It cannot be staged on demand. The walkers' recipe is in the thread's report.
