# v2.4003 — Bids: last contact is read in pages, for the bids on screen (2026-09-28)

Client only; no migration, no edge function. Punch list **#46** row 5 (`to-dos/decomposition-queue.md`): the read fix the Bids map names under step 8 (`docs/BIDS_TABS_ARCHITECTURE.md`). A behavior fix, shipped apart from the move (v2.3999).

## What was wrong

Every time the Bids page loaded its bids it read the whole `bids_submission_entries` table — no filter, no order, no range — to work out each bid's last contact and last update. PostgREST answers an un-ranged read with at most 1,000 rows and a 200. Measured on production on 2026-09-28: **752 rows**. Nothing was lost yet; the read was about a busy month from the cap. Past it, an arbitrary part of the log would have gone missing with no error: bids on the board and in the Followup lenses showing a stale last contact, or none — and a bid that was called last week sitting in the never-called pile.

## What changed

- **`src/lib/bids/bidEntryRecency.ts`** — `loadBidEntryRecency(client, bidIds)` (7 tests): the entries of the bids in hand, asked for in chunks of 150 bids, each chunk paged with a stable `bid_id, id` order — the shape `loadCountRowTalliesByBid` has had since v2.3203. A test builds 2,400 entries over 200 bids and pins that every bid keeps its newest entry, and that the old read would have lost most of them.
- **`useBidsPageData.loadBids`** calls it with the bids it just loaded. A failed read shows no recency and still hands the bids back, as before; no bids, no read.

## What a person sees

Nothing today — the same dates, from the same rows. Measured live on the Plumbing board (346 bids): three requests returning 478, 236 and 10 rows, where there was one returning all 752. On By builder (every trade) it reads every trade's entries, in pages.

## Left

One read per load is still more than this needs: an RPC that answers the newest entry per bid would be one small response. It needs a migration; not done here.
