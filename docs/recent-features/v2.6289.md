# v2.6289 — My email: the follow stops 60 days after a conversation's newest mail (punch list #230) (2026-11-01)

Punch list #230, a follow-up to PR 4 (v2.6279, #6715; `to-dos/messages-my-email/README.md`, the PR 4 row). PR 4 followed a tagged conversation while `coalesce(last_read_at, tagged_at)` was within 60 days. Every good read set `last_read_at` to now, so a conversation that still read was followed for good: the cron posted every five minutes for as long as anything was ever tagged, and the work grew with every tag. The intent is to follow a conversation while it is alive, so the window now keys on its newest mail. Nothing in the client changes. The function's section is [`docs/EDGE_FUNCTIONS.md` → gmail-mine](../EDGE_FUNCTIONS.md#gmail-mine).

- **The window**: a conversation is followed while its newest mail, or its tag when that is later, is younger than 60 days: `greatest(last_mail_at, tagged_at)`, as `followWindow`'s PostgREST `or` (`last_mail_at.gt.<since>,tagged_at.gt.<since>`) and as the cron's gate. `FOLLOW_WINDOW_DAYS` stays 60, now counted from the newest mail.
- **The decision on a tag with old mail**: a conversation tagged today whose newest mail is 90 days old **is** followed, for 60 days from the tag. The brief leaned the other way, since the tag's own read lands everything so far. But the tag writes a grey line on the thread that says *Later mail in it lands here by itself*, and tagging an old conversation is the moment someone is about to pick it up again. With `coalesce(last_mail_at, tagged_at)` a reply sent after that tag would never land, and a conversation tagged with its newest mail 50 days old would be followed for 10 days. With `greatest`, every tag is followed for at least 60 days, and then while mail keeps coming. The cost stays bounded: a tag adds at most 60 days of one metadata read per run. Flipping to `coalesce` is the one `or` in `followWindow`, the gate, and the run test *follows a conversation tagged today whose newest mail is 90 days old*.
- **`email_tag_threads.last_mail_at`**, migration [`20261101172319_gmail_mine_follow_window.sql`](../migrations/20261101172319_gmail_mine_follow_window.md): the newest mail in the conversation when it was last tagged or read well, with an index on it, and the cron `gmail-mine-follow` scheduled again with the new gate. Tried twice on a local Postgres 15 with stubs, the PR 4 gate first to show the bug.
- **The tag** sets `last_mail_at` to the newest mail of the conversation it read: `newestMailAt`, the latest Gmail `internalDate` of its mails, with a draft, Spam, Trash and a chat left out as the tag leaves them. The tag's own time stands in when no mail has one.
- **The follow** reads the thread's headers anyway. A good read sets `last_read_at` to now and moves `last_mail_at` up to the newest mail they carry, never back, so a mail deleted from Gmail never pulls the window in. `FOLLOW_TAG_COLUMNS` reads `last_mail_at` for that floor. A row it cannot read keeps its `last_mail_at` and ages out the same way.
- **The follow reads in turn**, found by an independent review of PR 4's order. PR 4 ordered `last_error` nulls first, then `last_read_at`, 100 a run. Once 100 healthy conversations were in the window, every row that ever failed sorted after them and was never read again. One Gmail 5xx, one 429 or one failed token exchange, which marks all of that person's rows, stopped later mail on those conversations for good, and `last_error` never cleared. Now a failed read sets `last_read_at` to now beside `last_error`, and the order is `last_read_at` ascending, nulls first, then `tagged_at`. A failed row goes to the back and is read again in its turn. It never hogs the front run after run either, which PR 4's failed-last order was there to stop. The migration amends `last_read_at`'s comment to say so.
- **The pure half**, [`src/lib/myMail/mineFunction.ts`](../../src/lib/myMail/mineFunction.ts): `followWindow` rewritten, `followSince` and `FOLLOW_WINDOW_DAYS` re-commented, and the new `newestMailAt`. The edge copy is regenerated, its index exporting `newestMailAt` (`scripts/edge-kernels.mjs`).
- **Tests**: `mineFunction.test.ts` covers the window as PostgREST reads it, including a row read five minutes ago whose newest mail is 61 days old, and `newestMailAt`: drafts, Spam, Trash and chats left out, Postgres's spelling of the row's time, never back. `gmailMine.run.test.ts` covers four things. A tag keeps the newest mail, the draft after it left out, and falls back to the tag's time when no mail has one. A follow that lands a newer reply moves `last_mail_at` on, a run with nothing new leaves it, and a deleted mail never moves it back. A conversation whose newest mail is 61 days old is not read though it was read yesterday, and neither is a tag 61 days old on older mail, while one whose mail is 59 days old is read. A conversation tagged today with mail 90 days old is read, and a reply after the tag lands. A run's worth of healthy conversations and one older one that Google answers with a 503 shows the order: the next run reads the one never read first, then the failed one, which lands its mail and clears its reason. PR 4's order test now expects a failed read to move `last_read_at`. The fake Google gained `down`, a conversation whose read answers 503. The new `followWindowSql.test.ts` holds the migration's gate to `followWindow` and to `FOLLOW_WINDOW_DAYS`. The run tests fail against PR 4's window, against a plain `coalesce`, against PR 4's failed-last order, and against a failed read that leaves `last_read_at` alone. The function passes a strict `tsc` with stubs for its two URL imports, with and without `noUncheckedIndexedAccess`.
- **Docs**: `EDGE_FUNCTIONS.md` (the tag's row, the follow's window, order and marks, the sentence that said a healthy conversation is followed for good, the deploy order) and `MESSAGES_ARCHITECTURE.md` (the crons' table).

## After the merge

Push first, then redeploy. `supabase db push` from a clean checkout of `main` pushes this migration, with PR 4's `20261101154949` first if it is not pushed yet. Then redeploy the function (`supabase functions deploy gmail-mine --no-verify-jwt`), then the importers `npm run check:edge-drift` names, since the copy's index changed. The order matters this time. A function redeployed before the push stops every tag before its row is kept (its lines are written, and a second tag after the push finishes it) and runs no follow until the column is there. The push alone is harmless. After the push, `npm run gen-types:linked` picks up `last_mail_at`, shipped as its own `chore(types)` PR; nothing in the client reads it.
