# v2.7208 — A last day set in the Lien window moves the row behind it (2026-11-13)

The owner, 2026-11-13, with the Lien desk's Deadlines tab behind *Liens on job 226*: *"I noticed when a day is set the underlying jobs don't refresh with the new dates … when I close the modal I don't want to lose my place on the page but I do want the main page to update."* Client only.

## Why the row stood still

`LienInstrumentsModal` saved the day, re-read the job's last-work columns into its own `lastWorkPatch`, and called `onLastWorkSaved()` with nothing. Both openers answered by re-reading the lien clocks and the desk (`setClocksRefresh` + `refetch` on `LienDeskPage`, the same pair in `JobsStagesTab`). But a Deadlines row, and a billed row on the Pipeline, count from `job.lien_last_work_on` on the jobs list the page already holds (`lienCalendarRows.ts`, `handLastWorkYmd`), and neither re-read touches that list. The row kept its old clock until a full reload. Reopening the window showed the old day too, since it opens on the list's copy of the job.

## What changed

- **New kernel `lienLastWorkJobs.ts`**: `withJobLastWork(jobs, jobId, facts)` returns the list with that one job's last-work columns replaced. It is the same array when nothing changed and the same object for every other job, so a host's rows stay mounted. `withJobsLastWork(jobs, rows)` does it for a reader that holds several fresh jobs, writing only the columns each row carries. `lienLastWorkFactsOf(row)` cuts a read down to the five columns.
- **`LienInstrumentsModal`**: `onLastWorkSaved(jobId, facts)` hands up the job and what it re-read; `facts` is null when that read came back empty.
- **`LienDeskPage`, `JobsStagesTab`**: write the facts into the jobs list cache (`setJobs((prev) => withJobLastWork(prev, jobId, facts))`), then re-read the clocks and the desk as before.
- **A recorded filing**: `onRecorded` on both openers now re-reads the lien clocks as well. It re-read the desk alone, so a notice, an affidavit or its service recorded in the window left the row's flags as they were.
- **The desk's own last-day line** (the Notices pane) reports a save with no job named. `LienDeskPage` lays the desk's fresh read of its jobs (`data.jobsById` carries `lien_last_work_on` and `last_work_date`) over the list whenever that read lands, a no-op when nothing differs.
- **Closing the window** was already a state change with no navigation. With the list patched in place there is no remount, so the scroll position holds.

## Tests

- `lienLastWorkJobs.test.ts` (7): the one job patched and the rest the same objects; the same array when nothing changed; a clear; a partial read; and a February job that read *Lien gone* having a date ahead once its day is set in September.
- `LienInstrumentsModal.property.render.test.tsx`: a save hands up `('job-891', { the five columns })`, and null when the re-read is empty. Both failed before the change (the callback was called with nothing).
- New `LienDeskPage.lastWork.render.test.tsx`: the page writes the day onto the job in its list, re-reads the clocks and the desk, and keeps the window open; a recorded filing re-reads the clocks; a day in the desk's fresh read reaches the list. Three of its four failed before the change.

## Walked

On the worktree's dev server with live data, at 1400 and 390 wide, on the Lien desk's Deadlines tab and on the Pipeline. Nothing was written: the one save was answered inside the browser, and later reads of the job were the real answer with that day laid over it. In all four, the row behind the open window moved (a greyed *lien window closed · Worked later? ›* row became a row with days to its flag; a billed row's *Lien gone* became *Lien by* a day), and after the window's × the list's scroll position was the number it was before.

## Not done, and why

- **A read that started before the save and lands after it** can lay the old day back over the list for a moment on the Lien desk page; the re-read the save itself starts then corrects it.
- **The window opened from a job's Documents tab** has no row behind it and passes no callback.
