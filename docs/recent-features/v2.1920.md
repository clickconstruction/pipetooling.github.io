# v2.1920 — Follow-up activity RPC set-based + candidates cache (2026-08-20)

Part 3 of the OOM-crash-loop remediation (parts 1–2: v2.1917, v2.1919).
`list_job_followup_activity(p_today)` was the incident's #1 statement-timeout
offender (16× in 48h): three bare correlated aggregates per open job meant
per-row RLS evaluation over every historical note/event, on every office
Dashboard mount.

- Migration [`20260821020000_followup_activity_set_based.sql`](../migrations/20260821020000_followup_activity_set_based.md):
  adds the missing `job_status_events (job_id, changed_at DESC)` composite
  index (baseline only had single-column indexes) and rewrites the RPC body as
  `LEFT JOIN LATERAL … ORDER BY … LIMIT 1` probes — the newest RLS-visible
  row per job instead of aggregating all of them. Same signature/result shape;
  no client change, no type regen. Deliberately does NOT reuse
  `jobs_ledger_thread_note_stats_cache.last_note_at` (it skips clock stamps;
  for follow-ups, stamps are activity).
- [`jobFollowupStore`](../../src/lib/jobs/jobFollowupStore.ts): 5-minute
  candidates cache (shared in-flight promise) so Dashboard remounts and the
  banner→deck handoff reuse one fetch; the deck passes `force: true` so an
  opened review session is never stale. Pinned by
  `jobFollowupStore.cache.test.ts`.

Apply with `supabase db push` after merge (safe before or after the client
deploy — no contract change).
