# v2.3289 — Costs tab overhead covers the whole job; the day ledger's session cache is shared (2026-09-11)

Client only; no migration. Follows v2.3271 (the amber band), whose fragment recorded the known difference between the two hosts.

## Why

`useJobBurnOverhead` loaded the day ledger over [first charge … today] capped at 120 days, with no cache, on every job window open for wage roles. Truncation dropped activity as well as carry, so an older job's true cost on the Costs tab read lower than Job Summary's (J621: $791 vs $960 on 2026-09-10), and Burn's overhead-so-far under-counted. The owner asked for the pros and cons of widening the cap and chose the proposal: cache, the pool's start rather than a fixed span, keep Burn's rate recent, and label anything the start cuts.

## What shipped

- **`lib/jobs/jobDayLedgerSessionCache.ts`** (+4 tests): `jobDayLedgerCacheKey` (`jobDayLedger:v5:<user>:<start>:<end>`), `readCachedJobDayLedger` / `writeCachedJobDayLedger` (one-hour TTL, storage injectable, corrupt entries ignored), and `loadJobDayLedgerCached` — cache hit, else ONE in-flight load shared by every caller asking for the same window, then cached; a failed load frees the slot. `useJobSummaryView` now uses it (same key and TTL as before — no behavior change there; a forced reload bypasses the read).
- **`lib/jobs/jobBurnOverheadWindow.ts`** (+3 tests): `jobBurnOverheadWindow(firstEventYmd, today)` → `OVERHEAD_POOL_FIRST_YMD` → today (new constant in `overheadAllocation.ts`, 2026-02-19 — the first day office cost exists; move it only if history is backfilled), bounded by a 730-day hard cap. The **same window for every job**, on purpose: carry lands from a job's Working move, which can precede its first charge by weeks (J621 earned two weeks of carry in April before its first charge in August — a first-charge start lost it), and one shared window means every job window in a session reads ONE cached ledger. `sinceYmd` names the start when the job's first event (charge, payment or report — `firstEventYmdOf`, was `firstChargeYmdOf`) predates it. `JOB_BURN_OVERHEAD_RATE_DAYS` = 120.
- **`jobDayLedger.ts`**: `jobOverheadPerFieldDaySince(lines, sinceYmd)` (+2 tests) — Burn's per-field-day rate over the last 120 days; carry-only lines add dollars, not days, as before.
- **`useJobBurnOverhead`**: loads through the shared cache (keyed by the signed-in user), `shareToDateUsd` over the full window, `perFieldDayUsd` from the recent rate, and returns `sinceYmd`.
- **Chart**: `JobChargesTimelineChartView` takes `overheadSinceLabel`; the standalone chart formats `sinceYmd` ("Feb 19, 2026") and the legend's amber clause gains *· since Feb 19, 2026, where office cost begins* only when something was cut.
- Help guide `job-charges-timeline.md`: the Costs tab band covers the whole job; the since note.

## Verified

Typecheck · lint · theme check · `npm test`; live via headless Playwright: J621's Costs tab true cost now reads $960.26, Job Summary's 12-month figure (it read $791.43 under the 120-day cap and would have read $792 under a first-charge start), and the session holds one `jobDayLedger:v5:<user>:2026-02-19:<today>` entry for every job window opened. The since clause is unit-tested only: no job can show it yet — the earliest field session in the database is 2026-03-15, after the pool's first day.
