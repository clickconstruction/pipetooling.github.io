# v2.2101 — Vehicle task delete no longer orphans the assignee's checklist row (2026-08-22)

Reproduced live 2026-08-22: assign a vehicle maintenance task and delete it in the same page session, and the one-off checklist task survives on the assignee's Today list ("2021 Ford Transit — TEST — vitals chip"). Root cause: the complete/delete/reassign cleanups in [`PeopleVehiclesTab.tsx`](../../src/components/people/PeopleVehiclesTab.tsx) read `checklist_item_id`/`checklist_instance_id` off the task object captured in local component state — a row that can predate the assignment's writes (both ids null in memory while the DB row has them), so cleanup silently skipped. A delete after a page reload worked fine.

Fix: `fetchChecklistLinkIds()` re-SELECTs the two ids from `vehicle_maintenance_tasks` by task id immediately before any checklist cleanup, in all three flows (complete, delete, reassignment's old-row replacement). In the delete flow the fetch happens before the confirm dialog, so the "It also comes off the assignee's checklist" warning is now accurate too. The resolution rule lives in a kernel, `resolveChecklistCleanupIds` in [`vehicleFleet.ts`](../../src/lib/vehicleFleet.ts): the fresh row wins outright — including its nulls, since after a reassignment stale local ids point at rows that no longer belong to the task — and local state is only the fallback when the fetch failed (+1 test in `vehicleFleet.test.ts`).
