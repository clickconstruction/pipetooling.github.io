# v2.6387 — Today's sends: a moved visit's text expires with its visit (2026-11-02)

PR 3 of three on Taunya's report of 2026-11-02 (PR 1 v2.6385, PR 2 v2.6386). Migration
`20261102200000_nudge_offers_about_on.sql` (`docs/migrations/20261102200000_nudge_offers_about_on.md`), **pushed right
after the merge**; **redeploy `messages-nudge-dispatch`** after the push.

## The cause

The homeowner's text — *Your visit moved to Thursday, October 22, 2026, 8:00 AM to 12:00 PM* — sat under *ready to
send* on November 2. The schedule's move wrote it as an offer with no morning (`offerRescheduledVisit`, v2.5597), and
nothing judged an offer's freshness: `todaysSends` read a row as held only on the run's `held_why` or a missing number,
the run's own sweep touched office-made offers only to send the ones with a `send_on` ≤ today, and the row carried no
day to judge by (the words name it; the columns did not). The job's two blocks were on 2026-10-22 and the visit had
happened, so the text would have told the customer about a visit behind them.

## What shipped

- **The row carries the day its words are about**: `nudge_offers.about_on`, written by the schedule's move
  (`rescheduledOffer.ts` passes the moved block's `workDate` as `OfferMake.aboutOn`; `nudge_offer_make` gains
  `p_about_on`, the seven-argument function dropped first so PostgREST has one match). Null for a text about no day.
- **The window holds a stale text first of all** (`offers.ts`'s `staleOn` and `heldStaleWords`; `todaysSends` takes
  `now`, the day read in the app's zone): *This text names a visit on Thu Oct 22. That day has passed. Put this one
  away with Not this one.* — over the run's own hold and over a missing number, since there is nothing to fix on it.
  Send all skips it; the Dashboard's line counts it held.
- **The 9 AM run puts stale texts away before planning** (`messages-nudge-dispatch`: `dismissed_at` now,
  `dismissed_why` `stale`), leaves them out of the planner's *offered already*, and counts them as `expired` in the
  summary (`nudgeRunLog.ts`: *2 texts were put away because the visit day passed.*; the Settings card's last-run line,
  `appSends.ts`, says the same); a dry run lists them under `stale` and writes nothing.
- **The kernel copy** (`npm run gen:edge-kernels`): `nudgeRunLog.ts` with the count, and `facts.ts` caught up with
  v2.6385's `contactFlowKindOf`, which PR 1 left behind.
- **Guide** *work Today's sends*: a moved visit's text is held once the day passes and put away the next morning.
  Docs: `GLOSSARY.md` → Today's sends, `MESSAGES_ARCHITECTURE.md`, `EDGE_FUNCTIONS.md` → messages-nudge-dispatch, the
  migration's doc. `src/types/database.ts` carries the column and the argument by hand until the regen after the push.

## The real row

The open offer on prod was made before this column existed, so its `about_on` is null and nothing judges it. The owner
decides data fixes on real rows; the guarded statement is in the PR and in the session's final message. Once it runs,
Today's sends holds the row and the next 9 AM run puts it away. Not this one puts it away sooner.

## Deploy

moved visit makes no offer, quietly, and the window reads as empty while the line still counts), then
`supabase functions deploy messages-nudge-dispatch` and `npm run check:edge-drift` for the other importers of the copy.
Then the regen of `database.ts` and the dev-mcp catalog, as a chore.
