# v2.3023 — Pages deploy: queue the newest push instead of cancelling the run in flight (2026-09-07)

Found while waiting to retest the Team fixes on clicktooling.com. `deploy.yml` had `concurrency: { group: pages, cancel-in-progress: true }`: every push to `main` cancelled the ~15-minute run (checks → build → deploy) already going. On 2026-09-07 twenty PRs merged between 07:19 and 16:30 UTC, twelve consecutive runs were cancelled, and not one completed — the site stayed on the 07:19 build (`e0345af1`) all day while main carried v2.3001 → v2.3017.

- **Change**: `cancel-in-progress: false`. GitHub keeps one running and at most one *pending* run per concurrency group (a newer push replaces the pending one), so runs complete every ~15 minutes and each deploy is at most one behind `main`. Workflow only — no client code, no migration.
- Not changed: `ci.yml` (PR checks) keeps its own behaviour.

Verify: after two merges a few minutes apart, `gh run list --workflow deploy.yml --branch main` shows the first `success` and the second `queued` → `success`, not `cancelled`.
