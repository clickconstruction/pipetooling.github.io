# v2.5882 — Settings → Dev doors: every door only a dev or the controller can open, as one list of links (2026-10-26)

Punch list #188, PR 2 of two. The owner's ask of 2026-10-26, after a holistic look at the app with one lens being *fewer dev-only doors*: *in dev settings show links to all the areas of the app that are dev only or controller only at the moment*. PR 1 (`to-dos/dev-gates/README.md`, docs only) is the audit: 124 doors, each with the code that gates it, why it was gated when it shipped, and a recommendation (gate, role or confirm) for the owner to mark. This PR is the card built from it. No migration, no edge function.

- **`src/lib/settings/devDoors.ts`** — the kernel: `DEV_DOORS`, one row per door a link can land on (113 rows), each with its `to` (the route with the `?tab=`, query or `#anchor` that opens the tab, card or window), its `who` (*dev*, *dev and controller*, *owner or dev*; no door is the controller's alone), one plain-words line of what it is, and its `gate` as a file and a short literal the file still holds. `devDoorsByArea` groups them in the areas' order; `devDoorCounts` and `devDoorsHeadLine` make the card's first line. A door in a tab that is itself dev-only is one row for the tab with its blocks named in the line; a dev-only block inside a tab other roles see is a row of its own.
- **`devDoors.test.ts`** — the pattern of `twins/appDirectoryCheck.ts`: every link's path must match a route `src/App.tsx` declares; every row's gate file must exist and still contain its text; every *what* line passes `plainWordsFailures`; ids are unique and every area is a known one. A gate that moves, a route that is renamed or a door that opens wider fails CI on the row, so the list cannot rot silently.
- **`src/components/settings/DevDoorsCard.tsx`** — Settings → System → **Dev doors** (`settings-dev-doors`, a new group in `settingsGroups.ts` for a dev, first in the System zone; `settingsSearch.ts` finds it by *dev only*, *controller only*, *doors*, *who can open*; `e2e/settings-tabs.spec.ts` and `settingsGroups.test.ts` carry the tab). The card **Only devs and the controller see these**: the head line with the counts, the rows grouped by area, each a `Link` with the who chip (the gate's file and text on hover) and the what line. Read-only: it opens doors and changes no gate. `DevDoorsCard.render.test.tsx` draws every row and checks each link's href, label, chip and line.
- **Docs**: `docs/PROJECT_DOCUMENTATION.md` §9, `docs/SETTINGS_TABS_ARCHITECTURE.md` (the master table, the role matrix), `docs/GLOSSARY.md` (Access Control → Dev doors), `docs/ACCESS_CONTROL.md` (Settings (selected) and a pointer to the kernel as the list of dev and controller doors), the Settings line of `docs/twins/APP_DIRECTORY.md`, and a paragraph in the guide *set up my profile and notifications*.

Six Settings anchors the audit found outside `SETTINGS_HASH_ANCHOR_TO_TAB` (`settings-phone-texts-email-count`, `settings-org-defaults`, `settings-bid-job-backfill`, `settings-quick-add`, `settings-typed-hours`, `settings-recent-emails`) are linked by their tab here, not their anchor, until they are mapped (the to-do's problem 4).
