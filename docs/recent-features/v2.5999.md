# v2.5999 — Two live to-dos on one punch-list number fail CI: the 2026-10-27 case pinned (2026-10-27)

Tooling only, no client change. The companion of v2.5998 (`npm run claim -- --todo`). On 2026-10-27 PRs #6330 and #6331 both wrote a card numbered #204 and #6329 and #6339 both #205; the sessions caught it from the PR titles and renumbered by hand before either second PR reached the merge queue, so the queue never had to refuse one.

## What was already true

`findTodoProblems` ([`todoBoard.ts`](../../src/lib/todos/todoBoard.ts)) has reported `duplicate_number` as an **error** since v2.3708 — it names both files and the next free number — and [`check-todos.ts`](../../scripts/check-todos.ts) exits 1 on any error. `ci.yml` runs `npm run check:todos` on every pull request and on the merge queue's build, where a second PR's card meets the first's, so the second of two colliding PRs fails there until it is renumbered. Nothing in the kernel, the script or the workflow changed.

## What changed

- **The test** (`todoBoard.test.ts`): the 2026-10-27 shape — two cards that both took #204, with #205–#207 held by other branches — is one `duplicate_number` finding, severity `error`, on the second file, naming both files and #208 as the way out (never #205, which another branch holds).
- **Docs**: `to-dos/README.md`'s *Check* step says a shared number is an error on the queue's build; `docs/SESSIONS.md`'s *Limitations* names `check:todos` beside the release-notes test as a backstop.

## Verify

`npx vitest run src/lib/todos`. In a checkout, give two to-dos one `number:` and run `npm run check:todos`: *ERROR two to-dos carry #N: … the next free one is #M* and exit 1.
