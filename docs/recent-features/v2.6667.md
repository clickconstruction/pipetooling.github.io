# v2.6667 — Messages: a mail too big to copy no longer stops the bids@ reader (2026-11-07)

Follow-up to v2.6649, whose cause was wrong. That PR read the 429 on the bids row as the reader knocking too fast. The project's function logs (Management API `GET /v1/projects/{ref}/analytics/endpoints/logs`, ClickHouse SQL over one `logs` table, `source = 'function_logs' | 'function_edge_logs' | 'edge_logs' | 'storage_logs'`) tell another story.

- **What happened.** The last good bids@ run was 2026-11-06 20:44:03Z. From 20:45:08Z every `gmail-sync` call answered 546 with *Memory limit exceeded*, about 190 in a row, until 00:20Z on 11-07. Each one read Gmail message `1a1b29b453e52e9b`, a general contractor's bid mail (storage shows its `0.1-image.png` written again every minute), copied its small picture, began fetching its next attachment, and died three seconds later. A worker that dies writes nothing, so the history point, the label and `last_error` stayed as they were, and the next minute did it all again. The first 429 (`Gmail /labels failed (429): User-rate limit exceeded`) came at 00:21:02Z, not 20:44Z: three and a half hours of fetching the same large file as bids@ spent the mailbox's per-user Gmail download allowance (Google's bandwidth limits are per user, shared by every client, and answer exactly *429 User-rate limit exceeded* with a retry time; the IMAP figure is 2,500 MB a day). The team box, a different user, read on. The 429 did not clear at Google's midnight Pacific (08:00Z), so the window rolls; it should open again about a day after the fetching stopped, between 20:45Z on 11-07 and 00:21Z on 11-08. *Retry after* is always fifteen minutes past the request and is not the end of the limit.
- **Why it would happen again.** When Google opens the window, the reader reads from history point 432211 and meets `1a1b29b453e52e9b` first, so the same loop would start over. This PR must be deployed before then.
- **The guard** (`src/lib/emailIn/copyStop.ts`, mirrored): before a run fetches a mail's files it writes `copyMarkWords(id, bytes)` into the row's `last_error` and keeps it on the context (`onMark`); a run that ends well clears it, as it always cleared `last_error`. A run that finds a mark (`copyStop`) waits while the run that wrote it may still be alive (`COPY_RUN_LIMIT_MS`, seven minutes, longer than a worker lives), answering `{ ok: true, held: true, until, copying }` with nothing written, then takes that mail with every file as `left_in_gmail: 'not_copied'` and nothing fetched (`ctx.bare`). A run that stops before it reaches the marked mail, or throws on a mail after its mark, keeps the mark ahead of its own words (`keepMark`), so a 429 still holds through `readerHold` and the run after the hold still takes the mail bare. `takeOne` now wraps `takeMail` to clear the bookkeeping whatever became of the mail.
- **The decode** (`base64UrlBytes` in `gmailMessage.ts`): a slice of a megabyte at a time into one array, instead of three whole-string replaces and a whole binary string beside the bytes. A 20 MB file's 27 MB of base64 took well over 100 MB before. `gmail-mine`, `walk` and `dev-mcp` share it.
- **Tests**: `copyStop.test.ts` (the words, the mark read back, wait then bare, a mark the 429 hold leaves alone and one that rides a 429, the fetch count); `gmailMessage.test.ts` (every slice size, every tail length, line breaks, malformed input); `src/lib/gc/edgeKernels.test.ts` holds the mirror.
- **Docs**: `docs/EDGE_FUNCTIONS.md` § gmail-sync, `docs/MESSAGES_ARCHITECTURE.md` and `readerHold.ts`'s own comment amended to the cause.

No migration. **Redeploy** `gmail-sync` once merged (`supabase functions deploy gmail-sync`), before about 20:45Z on 2026-11-07. `gmail-mine`, `walk` and `dev-mcp` carry the leaner decode at their next deploy. What happens next on prod: the held runs go on until Google answers; the first good run marks `1a1b29b453e52e9b`, fetches its file once more and may die; seven minutes later a run takes it with its files left in Gmail and reads on from there, so `last_ok_at` moves. The mail's files stay in Gmail for the office to open there.
