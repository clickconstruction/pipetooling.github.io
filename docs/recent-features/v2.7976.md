# v2.7976 — HR files: the dev seat reads the rows the file numbers and writes a case (2026-11-19)

Punch list #315, upgrade 2, PR 3. `dev-mcp` server 0.118.0. One new pair, no migration. The owner's go for the whole train, 2026-11-11; Grace's word to resume, 2026-11-19: "Please build".

## What was wrong

The database has numbered an evidence record and a case item since migration `20261113080000`, and People → HR has shown both since v2.7107. A session read neither through the seat. It learned a record's number from the screen, or typed one into a title. The open items and the log of a case stayed prose in the file's *Agent notes*, which is where two sessions took one number on one day.

## What changed

- **The reads carry the number.**
  - `get_person_file`: each evidence record carries `exhibit_no`, and so does the record's Timeline line, `brief` or not. `evidence_note` says how to cite one.
  - `get_case_brief`: the evidence index carries `exhibit_no`, and the manifest's `evidence` part says how many records are `numbered`.
  - `search_case`: an `evidence` hit carries `exhibit_no`, a `file` hit its record's as `record_exhibit_no`, and a transcript's document hit as `evidence_exhibit_no`. One read by id, joined in the kernel, so `dev_case_search` stays as it is.
  - A record kept before the file numbered them carries no key, so the index of a large file is no longer than it was. A read of the numbers that is refused leaves the hits as the search answered.
- **The brief reads the case.**
  - `open_items`: the open items by the number the file gave each, who has each, when it was opened, the first 200 characters of its detail with `detail_more` counting the rest, the counts, the standing in words, and the five closed last.
  - `log`: the whole count and the newest ten lines.
  - A case that cannot be read answers null for its block and is named in `held`. The manifest's `case_items` part says how to cite an item, how to read the rest and which pair writes both.
  - A brief too long for the door leaves an item's detail out first and cuts the open items last.
- **A new evidence record says its number.** `plan_person_evidence`'s reply carries `exhibit`: the number the record would take, read through `person_file_next_exhibit_no` over GET. It is read, never taken, and outside the plan hash, since the plan already commits to the person's record count. `apply_person_evidence`'s reply names the number the record took.
- **One new pair, `plan_case` → `apply_case`**, POSTs `dev_case_write`, the door the Case view writes through.
  - `case = { person_id, session?, items?, log? }`. An item change is exactly one of `add`, `set`, `close`, `reopen`.
  - The file numbers a new item. `item_no` goes inside `add` only for an item people already call by a number, and a taken number is refused.
  - Every item change writes its own log line, so a closed item and its line land in one write.
  - The shape is checked in the door's own limits. A value the door would cut short without saying, an owner or a session past 120 characters, is refused in words.
  - The dry run performs the write and unwinds it in the database. The plan names each item by the number it would take, with its before and after, and its reply holds no clock and no id the run made.
  - An item or a line added by anyone since moves the plan, and the apply refuses.
- **The call log keeps a case change short.** `dev_mcp_calls` keeps the person, the session, each change by its kind and number, and how many lines. It keeps no title, detail, reason or line. A call of fifty changes would also have passed the log's 4,000 characters and lost the plan hash the one-apply rule reads.
- **Kernel** `supabase/functions/_shared/devMcpCase.ts`, over the tab's own `personCase.ts`. It has no app import and nothing that runs at load.
- Counts: 149 write verbs, 55 over 23 RPCs, 200 tools.

## Is this the best we can do?

Three answers changed the build.

The first build said `exhibit_no: null` on every record with no number and put a note on each new block. On the test's large case that pushed the brief past the door's size, and the fit cut the evidence index to pay for it. The key now rides only on a numbered record, the manifest counts them, and the two blocks carry rows alone, with their one note on the manifest's part.

What is left costs that case about five hundred characters. It sat two hundred under the budget, so its narrative index now comes as an outline of 30 of its 45 headings, named in `shortened` with the call that reads the rest. A file with open items pays more, by their rows: the fit takes an item's detail out first and the open items last.

The card read the brief's items from the rows the manifest already counted. The brief now draws them, so a failed read is named in the brief's `held`, as a failed read of the correction links is. A null block always has its reason beside it.

The card did not say what the call log keeps. An HR entry's plan is logged whole. A case change is logged by its kinds and numbers, which keeps an item's words in one table and keeps a long call's hash readable.

## Not done here

- Old records are not numbered. Running `dev_evidence_number_backfill` on a real file is the owner's call, per person.
- A file's prose items are not moved into rows. That is the owner's call too.
- `list_kept_plans`, `keep` and `drop_kept_plan` are the next PR.
