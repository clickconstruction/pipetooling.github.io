# v2.3633 — MCP servers, PR 1: the pass-through Worker and a connector address taken verbatim (2026-09-20)

PR 1 of [`to-dos/mcp-servers.md`](../../to-dos/mcp-servers.md): the twins' MCP server moves behind `https://mcp.clicktooling.com/twin`, with `/dev` reserved for the dev server. Nothing is switched yet — the Supabase address stays the one every button copies until the owner has the Worker live and PR 2 flips it.

## The change

- **[`scripts/cloudflare/mcp-router.worker.js`](../../scripts/cloudflare/mcp-router.worker.js)** (new, reference copy — the live Worker is pasted in the Cloudflare dashboard, as with the other two): a route map (`/twin` → the `twin-mcp` function), every method forwarded so OPTIONS / GET 405 / POST answer from the function itself, an allowlist of request headers (`content-type`, `accept`, `authorization`, `x-twin-token`, `x-dev-token`, `mcp-protocol-version`, `mcp-session-id` — no cookie, nothing Cloudflare adds), unknown paths 404, `cache-control: no-store` and `noindex` on every reply. It holds no secret and reads no key: auth, the fence and the mint rate limit (counted per twin in `twin_runs`, not per IP) stay in the function. twin-mcp never reads the request's own URL, so the proxy is invisible to it.
- **[`_shared/twinConnectorUrl.ts`](../../supabase/functions/_shared/twinConnectorUrl.ts)** (new kernel, +2 tests in `desktopKickoff.test.ts`): `twinMcpConnectorUrl` appends the function door to a bare origin, as before, and takes an address that already carries a path verbatim. `twin-setup`'s `TWIN_MCP_PUBLIC_URL` was read as a base origin only (`…/functions/v1/twin-mcp` appended), which the new address could not satisfy; the function and the client's copy buttons (`src/lib/bids/desktopKickoff.ts` re-exports the kernel) now share the one reading.

## Deploy

`supabase functions deploy twin-setup` (behaviour unchanged while the secret is unset). Then the owner's step: Workers & Pages → create `mcp-router` from the reference copy, route `mcp.clicktooling.com/*` on the clicktooling.com zone, a proxied DNS record for `mcp`.

## Verify

The kernel tests; the Worker exercised locally against a stubbed upstream (a POST to `/twin/` forwards `content-type` + `x-twin-token` and drops `cookie` / `cf-connecting-ip`; `/dev` answers 404). Live, once the route exists: the `initialize` probe in the to-do's verify section answers `serverInfo.name = pipetooling-twin-mcp`.
