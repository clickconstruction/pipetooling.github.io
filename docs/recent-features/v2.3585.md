# v2.3585 — `set_person_hours` clears by setting days to 0; a permission gap is an error (2026-09-18)

Mike Z's cleanup through `pay:person` (v2.3584) voided his eight reports, cleared his hourly wage and marked Michael Zinna not staff — but reported `hours cleared: removed 0`. `people_hours` has no DELETE policy for payroll users, only for team leads over their members, so the function's DELETE matched nothing under RLS and returned a quiet zero. The Hours grid never deletes; it sets a day to 0 through the UPDATE policy.

## The fix — [`20260918110000_pay_person_hours_zero.sql`](../migrations/20260918110000_pay_person_hours_zero.md)

`set_person_hours(…, 0, …)` now sets each existing row in the range to 0 and raises when any row in the range still carries hours; `> 0` upserts and raises when fewer days took the value than were set. The audit row carries `existing` / `zeroed` / `set`. The command prints "n of m row(s) set to 0".

## The lesson, kept in the agent doc

A SECURITY INVOKER function inherits the caller's RLS. When the app has no UI that deletes a row, there is usually no delete policy either; do what the grid does. And a write that can be filtered to nothing by RLS must count what it changed and raise on the gap, never report success from a zero.
