# v2.4239 — Procurement log: a date box saves a finished date only (2026-09-30)

Found on prod on 2026-09-30: bid B375, tag FD, `ordered_on = 0001-02-12`. The Ordered, Expected and Delivered boxes on Bids → Submittals → Procure called `write(...)` from `onChange`. A browser reports a date on every key that completes one, so the year "2026" arrives as `0002-…`, `0020-…`, `0202-…`, `2026-…` — four writes. Each write set `saving`, which disabled every date box while it ran (read from the code, not reproduced — reproducing it writes to prod): the digits typed next went nowhere and the year 0002 stayed saved. Changing a day from 30 to 15 has the same shape (09/01 saves on the first digit). Clearing one part of a date to retype it saved null.

- [`procurementLog.ts`](../../src/lib/submittals/procurementLog.ts): `isPlausibleLogDate(iso)` — a real `YYYY-MM-DD` day with its year in `LOG_DATE_MIN_YEAR`–`LOG_DATE_MAX_YEAR` (2000–2100). `readLogDateEntry(raw, stored)` reads a box: `save` (a plausible date, or null for an empty box), `unchanged`, or `unfinished`. A bad date already stored can still be cleared or replaced.
- [`SubmittalProcurementPanel.tsx`](../../src/components/bids/SubmittalProcurementPanel.tsx): the three date fields join the per-row `drafts` the text fields use. `dateBox(row, field, shown)` gives the three boxes one set of handlers:
  - a change that follows a key press in the box is **typed**: it waits in the draft, and saves on blur or Enter;
  - a change with no key press is a **pick from the calendar** (or the iPad's date wheel): it saves at once, as before, unless it is unfinished;
  - on blur, an unfinished draft is dropped with a toast (*That date was not finished, so it was not saved…*) and the box shows the saved date again. A box left with a part missing (`validity.badInput`, e.g. `09/30/yyyy`) is wiped the same way — the browser reports that as an empty value, and it must not read as "clear the date".
- The rows are still built from the saved records only, so Expected (ordered + lead time) and Float never read a draft.
- `write(...)` now runs one write at a time through a promise queue and looks the row's record up again (`recordsRef`) when its turn comes. The date boxes are no longer disabled while a save runs (`busy` only), so a click from Ordered into Delivered lands; the second box filled on a row with no record yet updates the record the first one made instead of hitting the `(bid_id, tag)` unique index.
- Guide *build a submittal package* → the procurement log section says when a date saves.

**Not changed:** B375's FD date. Nothing in this PR touches prod data; emptying the box in the app clears it, and that is the office's call.

**The same pattern elsewhere (surveyed, not fixed here):** date boxes that write on the change event with no check on the year — the lien contract-ended date (`JobFormLienContractRow.tsx`), the sub-labor sheet date (`JobsSubLaborTab.tsx` → `useSubLaborLedger.updateLaborJobDate`), a sub's document expiry (`PeopleSubsTab.tsx`), a partnership agreement's sign-by date (`PartnershipAgreementsTab.tsx`). Debounced autosaves (800–1500 ms) can also catch a half-typed year if the typist pauses: the job contract's dates, the lien waiver's dates, Edit Bid's three dates, the payment Received date, an estimate's valid-until.

Walked live in dev (Chromium) on B375's log, on a row with no dates, without saving anything: typing `09/30/2` and leaving the box wrote nothing, emptied the box and showed the toast; typing `09/30/2026` fired the four change events and wrote nothing while the box had focus, and Expected and the headline did not move; `09/30` with no year was wiped on leaving. The save itself (blur, Enter, a calendar pick, an emptied box) is covered by the render test, not walked live, because it would have written to prod. Not seen in Safari: if Safari sends no key events from its date field, a typed date there saves on the change that finishes a plausible date, and a half-typed year is still held back.
