# v2.8091 — The dev seat gets a test deploy that bundles it first, to see if the larger size limit applies (2026-11-20)

CI only: one new workflow, run by hand. No screen, no function source and no check changes. The owner asked why the dev seat keeps meeting a 4.5 MB limit, whose limit it is and whether it can be raised, and said yes to one test deploy.

## What the limit is

Supabase takes an edge function two ways, and publishes a size for each ([its bundle size page](https://supabase.com/kb/troubleshooting/edge-function-bundle-size-issues), read 2026-11-20):

- **Raw source files, bundled on Supabase's server: 5 MB.** "When you deploy without local bundling, bundling runs on the server, which has a lower infrastructure limit." This is `supabase functions deploy --use-api`, and what the CLI falls back to when Docker is not running.
- **A bundle the CLI builds with Docker before the upload: 20 MB.** The same page: "bundle it locally with the Supabase CLI to get the higher limit."

`scripts/deploy-functions.sh` has passed `--use-api` since 2026-11-03 (#6933), after a Docker deploy sat sixteen minutes pulling the runtime image. So the 5 MB that refused `legal-portal` (v2.7135) and `dev-mcp` (v2.7256) is the raw path's limit, and the 4.5 MB of `check:edge-bundles` is this repo's margin under it. No plan, setting or support request is documented to raise either number.

## Where dev-mcp stands

On main at 06092126f0 it uploads 4.49 MB in 286 files: the verbs' own files 1.78 MB, the kernel copy 1.02 MB (of which the function runs 0.17 MB), `index.ts` 0.65 MB, other shared helpers 0.60 MB, `catalog.ts` 0.42 MB. It grew from 3.50 MB on 2026-11-16, about 0.25 MB a day and 40 KB a plan and apply pair. Trimming buys days at that rate. The other functions are at 1.5 MB or less.

## What changed

`.github/workflows/dev-mcp-bundled-deploy-test.yml`. It runs only by hand, only on `main`, only for `dev-mcp`, and only when the person types the function's name:

```bash
gh workflow run dev-mcp-bundled-deploy-test.yml --ref main -f confirm=dev-mcp
```

- It installs CLI 2.72.7, the version the sessions deploy with, so the bundling is the one thing that differs.
- It stops before the deploy when Docker is not up. With no daemon the CLI would send raw files and the run would answer nothing.
- It deploys with `--use-docker` and `--no-verify-jwt`, as the repo's script does but for the bundling.
- Its summary carries the size the CLI printed (`script size`) and the outcome. It fails when the log shows a raw upload.

A hosted runner has Docker. The Mac the sessions run on has Docker Desktop under another account, and a session cannot reach its daemon. The job uses the `SUPABASE_ACCESS_TOKEN` secret the two drift workflows already use.

## What it does not change

- How any function deploys. `scripts/deploy-functions.sh` is untouched, and `CLAUDE.md`'s deploy model stands.
- The 4.5 MB ceiling of `check:edge-bundles`.
- What `dev-mcp` runs. The drift check read it current with main before the test, so an accepted deploy puts the same code up, bundled another way. A refused one leaves the live function as it was.

## After the test

The result goes to the owner: the bundled size, whether Supabase took it, the seat's version, a live call and the cold start after. Making the bundled deploy the seat's standing way, and giving `check:edge-bundles` a second ceiling for it, is a separate decision and a separate change. If the test settles nothing more, this workflow is removed.
