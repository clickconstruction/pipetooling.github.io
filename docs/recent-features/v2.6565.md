# v2.6565 — The dev seat searches the company’s own mailboxes: one Gmail search across every login, read-only by scope (2026-11-06)

The owner asked whether domain-wide delegation lets a robot look across every account for a supply house's bill or a job's thread, and then to build it. The delegation already exists: the bids@ reader (`gmail-sync`) and Messages → My email (`gmail-mine`) read a login's mailbox as that person under the service account's `gmail.modify` grant, and `gmail-count` under `gmail.metadata`. What was missing was a door the dev seat could use across logins, and a scope that cannot write. Server 0.28.0.

## What changed

- **The kernel** (`supabase/functions/_shared/devMcpMailSearch.ts`): the arguments resolved against the Workspace's logins (`users` on the delegation's own domain, read off `GMAIL_IMPERSONATE_USER`; an address, its local part or the name People uses; every current login when left out; a login outside the Workspace refused by name), `since` / `until` folded into Gmail's `after:` / `before:`, `max` 1–100 an account (20 when left out), at most 40 accounts a call; a hit from a message's headers and Gmail's snippet, never a body; the reply newest first across the mailboxes with each account's count and whether Gmail has more; Google's refusals in words (the scope not on the grant names the admin step; a login Google no longer holds says so).
- **The seat** (`dev-mcp`): `search_mail(q, accounts?, include_archived?, since?, until?, max?)` and `read_mail(account, id)`, each minting a token as that login with **`gmail.readonly` alone** (`GMAIL_READONLY_SCOPE`), four accounts at a time and eight hits at a time; `read_mail` hands back the headers, the reader's words up to 30,000 characters, the labels and the files by name, kind and size, the bytes staying in Gmail. The verbs name no write of the Gmail helper, and the test holds that. Every call lands on `dev_mcp_calls` with its query and its accounts.
- **The Gmail helper** gains `gmailMessageHeaders` (one message, `format=metadata`, the headers named).
- **The docs**: the seat's README row, the `dev-mcp` note in `EDGE_FUNCTIONS.md`, `DRIVE_INTAKE_SETUP.md` → Domain-wide delegation now says which Gmail scopes the grant holds and the one line that adds the read-only scope, and `ACCESS_CONTROL.md` names what the seat can read.

## The admin step

Until the Workspace admin adds `https://www.googleapis.com/auth/gmail.readonly` to the service account's delegation (admin.google.com → Security → Access and data control → API controls → Manage domain-wide delegation → the client → Edit), every account answers *refused* with that step named, and nothing is read. The verb never falls back to `gmail.modify`: read-only by scope is the point.

## Test

`devMcpMailSearch.test.ts`: the arguments (every login, the archived on asking, by address, local part or name, the refusals, the dates and the caps), a hit's shape, the reply's order and counts, Google's refusals in words, the batches' order, `read_mail`'s arguments and reply, the server's declarations over the read-only scope with no write named, and the docs' rows. The version pins in the seat's other tests move to 0.28.0.
