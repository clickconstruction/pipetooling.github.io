# v2.6230 — Adopting a bid as a version brings its plan sets and CountTooling projects along (2026-10-31)

Feature with a migration (`20261031123000_adopt_carries_sets_and_counts`, `docs/migrations/…md`); no edge function. The owner, on Gun Dog's bids by William, Trace and Wendi made before versions existed: *the William version has its own count tooling and his own pricing. He also bid an older version of the plans.* `adopt_bid_as_version` (v2.4xxx, 2026-08-23) already moved counts, takeoff and pricing per version; the two tables keyed on the bid alone stayed behind.

## Change

- Migration: `bid_version_id` on `bid_count_sources` and `bid_plan_sets`; the adopt (re-stated from 20261031015000's body, whose pull-table moves go through the SECURITY DEFINER helper `robot_fixtures_follow_adopt` — never the direct UPDATEs that broke every new version on 2026-10-31) carries both (the target's own rows by the same token or link win; the source's bare links become rows), each plan set's memo prefixed *From B<n>, adopted as the version <name>*.
- `BidPlanSetRow` / `BidCountSourceRow` gain `bid_version_id?`; both selects read `*` so Edit Bid stands before and after the push. `versionChipWords` (tested) and `fetchBidVersionNames` (fail-soft) put the amber *version · <name>* chip beside a set in `BidPlanSetsField.tsx` and a project in `BidCountSourcesField.tsx`.
- The guide *bid one project to multiple GCs* says what an adopt carries now.

Not in this PR: the Counts tab still lists every project on the bid whatever its version; a per-version filter there is the next step if it is wanted. Deploy: `supabase db push` after the merge, then `npm run gen:types`.
