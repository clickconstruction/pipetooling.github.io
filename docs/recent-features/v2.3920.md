## What left `src/components/schedule/ScheduleDispatchHubPage.tsx`

The two pure halves of `loadHub`'s `wagesPromise` → `src/lib/scheduleDispatch/hubWages.ts`, verbatim:

- **`hubWageLookupNames(rosterIds, nameByUserId)`** — the names the page asks `people_pay_config` for: trimmed, one of each, in roster order; a missing or blank name and the exact word `Unknown` are skipped.
- **`buildHourlyWageByUserId(rows, rosterIds, nameByUserId)`** — every roster id → hourly wage; 0 for no name, no pay row, or a wage that is not a finite number; the later row wins when two share a name.

What stays in the page: the `canShowHubExpectedManpowerPayroll` gate, the empty-names early return (an empty map, not a map of zeros), and the `people_pay_config` read itself with its retry name. `ScheduleDispatchHubPage.tsx`: 3,040 → 3,024 lines.

## Tests

`src/lib/scheduleDispatch/hubWages.test.ts`, 18 cases — among them the ones that say how the money can come out as `$0`:

- The match is **case-sensitive**: a pay row under `abraham` does not pay `Abraham`. The bid board's labor cost lowercases both sides (`payConfigLookupKey`); the hub does not, and its query would not return the row either. Recorded on the map's quirk #11.
- A wage stored as text, `null`, `NaN` or infinite reads as 0.
- Two people with the same name get the same wage; a later pay row with no wage zeroes an earlier one.

## Left, on purpose

- Matching names without regard to case would change what the Expected Manpower column shows; it is a behavior change and would be its own PR.
- The playbook's cross-surface seam #16 (one wage-lookup loader for the eight files that read `people_pay_config`) is not attempted here.
- `to-dos/decomposition-queue.md` is not touched: one docs PR updates the card for the parallel batch.
