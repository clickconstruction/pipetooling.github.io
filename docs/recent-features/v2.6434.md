# v2.6434 — A header search that cannot reach the server says so (2026-11-03)

The header's side of v2.6410 (#6889), which left the global search box out on purpose. The box reads jobs, bids, estimates and customers from the server (`search_jobs_ledger`, `search_bids_for_clock`, `search_estimates_for_nav` and the `customers` table) and finds the doors, which are pages, Settings cards and guides, on the device. `HeaderGlobalSearch.tsx` read `res.data ?? []` and ignored `res.error` on every one of them, in the office's `Promise.all` and in the field lookup's own jobs read, and the customers read swallowed its failure to `[]`; so a lost signal or a refusal read *No matches. The box looks in jobs, bids, estimates, customers, pages, settings and guides.* (or the field mode's *your jobs and the guides for your role*), which was false: nothing of that kind was searched. Client only: no migration, no function change.

- **The kernel `src/lib/search/headerSearchFailedReads.ts`.** `headerSearchFailedRead` turns a result's error into `{ kind, failure }` through `recoveryFailureFromError`, with the kind's own lead (*Could not search jobs. You don't have access to this record.* for a refusal; a lost signal is told by its class, never its text). `headerSearchFailedLines` groups the failed reads by failure, so four reads lost to one signal are one line with one Retry: *Jobs, bids, estimates and customers were not searched.* A field role's lookup says *Your jobs were not searched.* `headerSearchNothingMatchedWords` gives the line in place of *No matches* when no row came back: *Nothing matched in bids, estimates, customers, pages, settings and guides.*, the kinds that answered first, then what the device holds.
- **The box.** The search effect keeps `failedReads` beside `results`, reruns on `searchAttempt` (the panel's Retry, and its run by itself on the `online` event), drops an answer that lands after the words changed, and clears the failures with the results. `HeaderSearchFailedReads.tsx` draws the lines on `OfflineRetryPanel` (`surface="header-search"`, `idempotent`, `busy` while a search is in flight): under the rows that did come back, or in place of *No matches* with the nothing-matched line last. *No matches* stays for the case where every read answered.
- **Guide.** *search for jobs, bids, customers, and estimates* gains *When the box cannot reach the server*.
- **Tests.** `headerSearchFailedReads.test.ts` (the words one and many, both modes, a lost signal and a refusal and a bare Error, the grouping, plain words). `HeaderGlobalSearch.failedReads.render.test.tsx` walks the wiring with a stub that answers each read by name: six of its seven cases failed before the change (a lost jobs read says jobs were not searched with Retry and never *No matches*; the bid row that answered still draws with the line under it; a refusal's reason with no Retry; four reads lost to one signal are one line and one Retry; Retry runs the read again and a read that answers takes its line away; a field role's *Your jobs*), and the true no-match case passed on both sides.
- **Live, on the dev server against prod as the dev**, with the page's `fetch` failing only the jobs RPC. Before the stub, `1004` found its job. With the stub rejecting `TypeError('Failed to fetch')`, `1003` read *Jobs were not searched.*, the no-signal sentence with Retry, and *Nothing matched in bids, estimates, customers, pages, settings and guides.*; the old sentence was nowhere on the page. With the stub lifted, Retry found the job and the lines went away. With the stub answering 403 and code `42501`, the box read *Jobs were not searched.* and *Could not search jobs. You don't have access to this record.* with no Retry.
- **Not changed.** The ZZ-ids read still degrades to names alone when it fails, since it is a filter, not a search. The doors-only box has no server read and no failure line.
