# v2.7064 — Tasks: add a photo of the spot when you give a task (2026-11-12)

Punch list #328, PR 6 of 8. Grace's ask: "Having a geographic location and a photo should be enough that it should be really easy for users to orient around a task." The place has been there since v2.7059. Until now the photo could not be: only the person doing a task could put a photo on it, and never when it was made.

## The decision: this is not a task photo

A task photo (`task_photos`) is the doer's. It rides a day's card as proof of the work, it counts toward the finishing photo a task can ask for, and the Drive sweep files it. A giver's picture among them would read as proof of work, and would let a task that asks for a finishing photo close on a photo taken before it began. So the giver's photo has its own column and its own bucket, and none of the doer's rules can see it. Nothing in the task photo code changed.

## What changed

- **The column and the bucket** (`20261113000000_task_spot_photos.sql`): `spot_photo_path` on the task and on the roadmap task, the private bucket `task-spot-photos`, `can_write_task_spot_photo(name)` and three policies. Whoever may write the task's Done when lines may put its photo, and whoever may read the task may see it.
- **Giving** (`TaskSpotPhotoField.tsx`): **Photo of the spot**, under Place in the Add and Edit windows. On a hand-held device the press opens the camera. The picture is shrunk on the device to the office's own photo size, which drops the camera's data, so no position travels with it.
  - A new task has no id to file a picture under, so the Add window sends the picture right after the task. A picture that does not land says *The task was sent, but its photo did not save*, why, and where to add it, and leaves the window open, as the Done when lines do.
  - The Edit window sends a new picture on Save, and takes the old file out of the bucket.
- **A roadmap task** has the field on its card (`RoadmapTaskPlaceSection`), where a picture saves itself on the pick. The roadmap's Add task window does not have it yet: a planner adds the picture from the task's card.
- **Doing**: the photo sits beside the picture from above inside the place's block, each 150 tall, and a press opens it full size (`TaskSpotPhotoView`). A task with a photo and no place shows the photo by itself. A picture that will not load draws nothing.
- **Reading** (`useTaskSpotPhotos`): the paths in one read, a roadmap task's behind the tasks with none, then one signing. Any of it failing is no photo, and the card is the card it was.

## Checked on a database

The migration was applied twice to a throwaway local Postgres 15 with stub tables and exercised as four made-up people, 21 checks for this migration among 38 for the train's three: who may put a photo, who may see it, five malformed names refused without an error, another bucket untouched. The stub is not the app's schema, and the real storage schema is Supabase's, so the dry run at the push still matters.

## Known, and left

- One photo a task. A second replaces the first.

## Also in this PR: Where is it? opens over a roadmap task's window

Found on a later walk, 2026-11-13, before any of it was live. A roadmap task's two windows, its card and Add task, sit at layer 10050, far above Add a task. The *Where is it?* sheet opened at Add a task's picker layer, so on the roadmap it opened behind the window that asked for it, where nobody could see it. The fault came in with roadmap places (v2.7063).

- `windowLayers.ts` names the two roadmap layers, `ROADMAP_TASK_WINDOW_Z` and `ROADMAP_TASK_PICKER_Z`, and its test holds their order.
- `TaskPlaceSheet` takes a `zIndex` and `TaskPlaceRow` a `sheetZIndex`. The roadmap's card and its Add task pass the picker layer. Add a task and Edit keep the default.
- The sheet mounts inside the element that fills the screen when there is one, since the roadmap's canvas can go full screen and then only what is inside it shows.
- `TaskPlaceRow.render.test.tsx` holds both layers.
