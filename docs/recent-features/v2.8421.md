# v2.8421 — Help: a guide's short address opens the guide (2026-11-23)

Found on the Bills sent walk of 2026-11-23 (punch list #422). No migration, no edge function.

## What was wrong

A guide link is written `/help/<slug>` inside a guide, in the docs and in a hand-off. The app's only help route was `/help`, with the guide named by `?g=<slug>`. Inside a guide the renderer rewrites the link, so a press worked. Typed into the address bar or pasted from a message, `/help/see-which-bills-went-out` matched no route, fell to the catch-all, and opened the Dashboard, or the Bridge for a dev, with no word about the guide.

## What changed

- A route `help/:slug` sends the address to `/help?g=<slug>`, in place, so Back does not bounce.
- A heading's anchor rides along: `/help/<slug>#<anchor>` lands on the heading.
- A renamed guide's old slug still answers, since `GuideBrowser` already maps it.

## How it is built

- `src/lib/helpGuideUrlParam.ts`: `helpGuideAddressFromSlugPath(slug, hash)`, pure. The slug is encoded, never written raw.
- `src/App.tsx`: `NavigateToHelpGuide` and its route, beside `help`.
- `docs/twins/APP_DIRECTORY.md` says both addresses open a guide.

## Tests

`helpGuideUrlParam.test.ts`: the guide's address, an anchor kept, an empty slug to the list, a slug encoded.
