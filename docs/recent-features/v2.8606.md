# v2.8606 — The merge queue runs three shards, and a script line in package.json keeps a pull request's pick (2026-11-25)

Two things the first evening of v2.8596 showed.

## Three shards

Two shards were to make a merge-queue build about 16 minutes at the median. The first five builds took 20.0 to 21.1 (the table is in `docs/recent-features/v2.8596.md` → Measured): a shard of two ran 13.8 to 19.6 minutes, because each runner transforms nearly every module of the app before its tests, about 3.5 minutes whatever its share. The owner, asked two or three with those numbers: *We can do three.*

- `ci.yml`'s matrix for `merge_group` is `["1/3", "2/3", "3/3"]`. `scripts/check-workflow-parity.mjs` holds the list to every shard of one count, as before.
- **Runners**: a queue build is 4 jobs, so six builds at once is 24 against the org's 20. That is past the count v2.8596 was held to, and it is the owner's call for the shorter build: a leg that finds no runner waits, it does not fail. A build costs about 55 to 65 runner-minutes by the fixed cost above, against 45 to 55 with two shards.
- **Expected**, until measured: a shard about 12 to 16 minutes, a build about 13 to 18 with the typecheck leg the long pole about one build in three (it was 5.9 to 20.7 on those five).

## A script line in package.json keeps the pick

`scripts/lib/nearTests.mjs` ran the whole suite on a pull request's own run whenever `package.json` changed. Every SQL bed adds one line there, `"test:pg:<name>": "bash scripts/pgtest-<name>.sh"`, so the first pull request with a bed after v2.8596 (#9874) ran all 5,948 files on its one runner. In the six days before, 26 of 739 merges changed `package.json`, every one a script line, and none changed `package-lock.json`.

- `scriptsOnlyPatch(patch)` reads the compare API's patch for the file and answers yes only when every changed line is one `"key": "string"` entry whose key is not one of package.json's own string fields (`type`, `main`, `version` and the rest of `PACKAGE_TOP_FIELDS`). `wholeSuiteReason` then lets `package.json` through; `scripts/ci-near-tests.mjs` hands it the patches (`patchesOfCompare`).
- **Why that is safe**: a script line cannot change how a test runs, and a test that reads `package.json` reads the disk, so it is a reader and runs on every code PR. A dependency line has the same shape, and its change is in `package-lock.json` too (`npm ci` refuses a lock out of step), which always runs the whole suite. A changed line of any other shape (an object, a number, a boolean, a bracket), one of the file's own fields, or no patch at all runs the whole suite.
- **Tests**: `src/lib/nearTests.test.ts` pins a bed's line, an edited script with escaped quotes, the refusals, the dependency case beside the lock, and that the script hands the patches over.
