# v2.8379 — A customer's second Try again asks the network, and reloads only on an answer (2026-11-23)

Punch list #85, the third of the three faults v2.8327 left (`docs/recent-features/v2.8327.md`, *What is left*: *a browser that wrongly says it is offline*). The first two are v2.8377. The owner said yes in chat on 2026-11-23 to: the second press reloads anyway. Client only: no migration and no edge function.

## Before

A page a customer opens from a link (`PublicPage`) that lost its code while the browser said it was offline drew *You are offline. This page will load when you are back online.* with **Try again**. Every press answered *Still offline. Try again when you have a signal.* and never reloaded, for as long as `navigator.onLine` stayed false. A phone can report that wrongly. The customer was then held on the page until the phone changed its mind, with the browser's own reload as the only way out.

## The risk in the plain fix

The owner's yes was to a second press that reloads anyway. The thread that left this fault named the cost: a reload while truly offline *emptied the caches and landed on the browser's own error page*. The reload here is `hardReloadFromRoot`, which unregisters the service worker and deletes every cache before it navigates. With no network that leaves nothing to draw. A count of presses cannot tell a phone that is wrong from a phone that is right.

## The design: ask first, reload only on an answer

`publicPageTryAgainAct(online, pressedOffline)` in `src/lib/publicPageLoad.ts` decides what a press does:

| The browser says | Press | What happens |
|---|---|---|
| online | any | Reloads, as before. |
| offline | the first | Answers in words, as before. Nothing is asked. |
| offline | the second, and each one after | Asks the network once (`probeForSignal`). Reloads only when it answers. |

**The ask** is one `fetch` of `/favicon.svg?signal=<the time>` with `cache: 'no-store'` and no cookie, given up after five seconds (`PUBLIC_PAGE_PROBE_TIMEOUT_MS`).

- **No cache can answer it.** `no-store` passes the browser's HTTP cache. The service worker answers only for what is in its precache and for navigations (`src/sw.ts`), and a `fetch` is not a navigation. The icon itself is precached, so the bare address would be answered from the phone with no network. The key on the address is what stops that: the precache matches an address exactly, but for the campaign keys it ignores by default, and `src/sw.ts` names none of its own. So the request reaches the network or fails. A test fails a PR that tells the service worker to ignore keys.
- **Only the site's own answer counts.** `probeAnswered` wants an OK answer whose type is the icon's (`image/svg…`). A sign-in wall on a shop's or a hotel's network answers every address with its own page, and that page is not the network this page needs.
- **It never throws and never waits without end.** No network, a refusal, a wall, or five seconds with no answer are all a plain no.

While the ask is out the page says *Checking for a signal…* and the press is dead, in the theme's dead-press pair (`deadPress.ts`), so a third press cannot send a second ask. On a yes the page takes the same road as an online press: the loading look, then `hardReloadFromRoot`. On a no it says *Still offline. Try again when you have a signal.* again, and the press is live again. Ten presses with no network send ten small asks and reload nothing.

Nothing else changes. The page still reloads by itself when the browser's `online` event comes. The automatic recovery reload still never starts while the browser says it is offline.

## Why the first press does not ask

The owner's yes was for the second press. The first press on a phone that says it is offline keeps its instant answer in words. Asking on the first press would be safe by the same design, and it would save a wrongly offline customer one press. That is the owner's call, and it is one line in `publicPageTryAgainAct`.

## What is left

Between the answer and the reload the signal can still drop, and the reload then lands on the browser's error page. The window is the moment between two requests to the same server. It was open before this change for every online press too.

## Proved on the built app

On 2026-11-23 the app was built (`npm run build`) and its `dist` served locally. A headless browser registered the build's own service worker, waited until it controlled the page, and asked from there:

| The network | The request | The answer |
|---|---|---|
| there | the ask (`/favicon.svg?signal=…`, `no-store`) | 200, `image/svg+xml` |
| gone | the bare icon (`/favicon.svg`) | 200, from the precache |
| gone | the ask | failed |
| gone | the ask again | failed |
| back | the ask | 200, `image/svg+xml` |

So with the service worker in control and no network, the ask cannot be answered, and the page cannot reload.

## Seen

On 2026-11-23, on a throwaway harness page on the dev server (never committed), with a headless browser at 390 by 844 and 1,280 by 800, in light and in dark. The harness drew `PublicPage` around a page whose import is refused, with the browser told it is offline, on the portal's paper and on the landing's photo and white box. Nothing was wider than the screen. No live page was opened.

- **The first press.** *Still offline. Try again when you have a signal.*
- **The second press, the network gone.** *Checking for a signal…* with the press grey, then *Still offline…* with the press copper again. The page stayed.
- **The second press, the network there.** *Checking for a signal…*, then the loading look and the reload.

## Seen on the live site

On 2026-11-24, on clicktooling.com, after the deploys that hold this change, with a headless Chromium at 390 by 844 and 1,280 by 800. The build's own service worker was registered and in control, with its precache whole. Three pages were opened at their bare address, so no customer's link was used: `/estimate/terms` on the plain page, `/portal` on the portal's paper and `/estimate/accept` on the landing's white box, each at both widths. The page's file was taken out of the precache, the browser was set offline and the page reloaded. It drew *You are offline. This page will load when you are back online.* with **Try again**, 44 tall, and nothing was wider than the screen.

- **The first press.** *Still offline. Try again when you have a signal.* No request left the page.
- **The second press and the third, the network gone** (four of the seven runs). *Checking for a signal…* with the press dead, the ask (`/favicon.svg?signal=…`) failed, then *Still offline…* with the press live and copper again. The same document stayed, with no navigation and no browser error page. With the ask held open for two and a half seconds the press was grey, and a press on it sent no second ask.
- **The second press, the network there and the browser still saying offline** (`navigator.onLine` held false and the `online` event held back in the test browser). The ask was answered 200, `image/svg+xml`, by the site's server, not by the service worker and not from a cache. The page left for `/?nocache=…` and came back on its own address, drawn. Seen as the second press on three runs and as a later press on four.

Two small things. On the reload the ask was answered too fast to catch *Checking for a signal…* and the loading look between the press and the leaving. Offline, the landing drew its white box on the dark ground with no photo: the test had emptied the browser's HTTP cache.

Chromium only. Safari on a phone was not looked at.
