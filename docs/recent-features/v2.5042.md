# v2.5042 — Sub portal: a sub's note now reaches the dispatch group's phones (2026-10-09)

`submit-sub-portal` (**redeploy after merge**). Found while tracing what signed-out pages call for the blanket revoke (#5110). Punchlist assigned the fix.

## What was wrong

- Every dispatch note a sub leaves on the portal writes a `dispatch_requests` row, then calls `notify-dispatch-request` for the push. That covers availability, a day off under a pick, work done, a progress note, a declined offer and a signed order.
- The call carried no `Authorization` header, so the notifier answered 401 (*Unauthorized - No authorization header*). `fetch` does not throw on a 401, so nothing was logged.
- The inbox row was always there, but no phone heard it.

## What changed

- **`supabase/functions/_shared/internalFunctionCall.ts`** builds one function's call to another as a trusted internal caller: a JSON POST with the service-role key as the bearer. `notify-dispatch-request` accepts exactly that token for announcing a new request (v2.3246). `submit-portal-request` already sends it inline for the customer portal.
- **`submit-sub-portal`** sends its notify call through it. It logs a non-2xx answer (`notify-dispatch-request refused <status> <body>`) instead of dropping it.
- **`docs/EDGE_FUNCTIONS.md`**: the sub portal's section carries the change, and the notifier's internal-caller line names both callers.

## Verified

- **`src/lib/subs/subPortalDispatchNotify.run.test.ts`** runs the function's own handler against a fake database and a recorded `fetch`:
  - A sub's availability note is written, and its push goes to `notify-dispatch-request` with `Authorization: Bearer <service key>` and the new request's id.
  - A 401 is logged while the sub still gets `{ ok: true }`.
  - The kernel builds the URL, method, headers and body.
- **Mutants:** each fails a test.
  - Drop the bearer in the kernel: two tests fail.
  - Send the old bare headers from the function: one fails.
  - Drop the refusal log: one fails.
