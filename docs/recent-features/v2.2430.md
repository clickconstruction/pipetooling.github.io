# v2.2430 — Waiting to hear lens: notes are not contacts (2026-08-28)

First bug caught by the digital-twin estimator pilot (2026-08-28,
`docs/twins/missions/estimator.md`): the Followup → **Waiting to hear** lens
computed each bid's effective last contact with a fallback map built from **every**
`bids_submission_entries` row — including method-less notes. That contradicts the
owner-locked v2.2413 rule (`docs/PER_GC_BID_PLAN.md` Phase 1: only entries WITH a
`contact_method` are contacts; the `bids.last_contact` trigger already enforces it).
Repro: bid b13 "LA Fitness Austin TX" has one 2026-05-01 entry with
`contact_method` NULL ("left vm") — the Bid Board correctly showed no last contact,
but the lens showed "Last contact 5/1" and dropped the bid out of the never-called
bucket (it should read ~339d never-contacted).

## What changed

- New kernel `buildBidEntryRecencyMaps` in `src/lib/bids/bidContacts.ts` (unit
  tests alongside): one pass over the entries → `lastContactByBid` (method entries
  only, mirrors `isContactEntry`) **and** `lastActivityByBid` (every entry).
- `Bids.tsx` now selects `contact_method` with the entries and feeds the
  **contacts-only** map to `BidsWaitingToHearLens` and `BidsCallQueueTab` (both
  used the same fallback). The Followup / Builder-review "Last update" surfaces
  (`submissionFollowupStale.ts`, `customerLastContact.ts`) keep the any-entry
  map — their semantics are "latest note activity", where a note is an update.
- ±1-day drift fixed: the lens's `shortDate` took the UTC date off ISO instants
  while the Bid Board renders last contact in the browser's local calendar
  (`bidBoardLastContactParts`) — an evening call showed as the next day, one day
  younger. The lens now renders instants in local time and takes its "(Nd ago)"
  from `bidBoardLastContactParts` itself, so board and lens always agree.

No DB change; no migration.
