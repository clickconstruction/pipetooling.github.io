# v2.2516 — Robot bid audits: the schema (2026-08-30)

Groundwork for the Wendi audit loop v2 (owner decision 2026-08-30; design in
`docs/twins/FEEDBACK_LOOP.md`, superseding the three-channel v1). Migration
`20260830230000_bid_audits.sql` adds:

- **`bid_audits`** — one row per twin bid under audit: `bid_id` (unique),
  `ct_project_id` + `ct_view_url` (the CountTooling quick link, minted via CT's
  `create_view_link` RPC at audit-open time), `status`
  (`pending → done → digested`), and the three lifecycle timestamps
  (`requested_at` / `completed_at` + `completed_by` / `digested_at`).
- **`bid_audit_notes`** — the conversation: `section`
  (`counts | footage | pricing | scope | general`), `kind`
  (`note | question | answer | receipt`), `parent_id` threading (answers hang off
  questions, receipts off notes), and digest bookkeeping (`digested_at`,
  `digest_outcome` ∈ `doctrine | books | code | bid_only`).

Access: staff policies mirror the bids family (`bids_rfis` pattern). Twin lanes are
structural (restrictive policies): a twin can open an audit and later close it as
`digested`, but can never set `done` (finishing is the human auditor's act); twin
note kinds are limited to `question` and `receipt` (`note`/`answer` are human).
Both read-only appliers + the digital-twin write fence rerun at the end; the fence
auto-detects `bid_id` so twin writes stay confined to own/assigned bids.

UI (Audits tab on the Bids page), the finish→CT-reviewed bridge, and the b405
backfill ship in the follow-up PRs of this train.
