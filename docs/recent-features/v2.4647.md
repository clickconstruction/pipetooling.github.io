## The defect

`legal_portal_links` kept the raw token beside its hash, and the four office roles that read the legal tables could read it: the Firm's link dialog selected it to show and copy the link, and `mint_legal_portal_link(p_rotate => false)` handed an existing raw token back. Whoever holds it can act as the firm.

## The catch, and the design

Every email to the firm carries the live link, so a strictly hash-only table would have emailed the firm a dead link. The live link's raw token moves into Supabase Vault, encrypted, readable only by the service role through `legal_portal_link_token(firm)`; the table keeps only the hash, and a CHECK holds the raw column empty. Migration page: [`docs/migrations/20261006072618_legal_portal_links_hash_only.md`](../migrations/20261006072618_legal_portal_links_hash_only.md).

## What changed

- **Migration** (not pushed): the Vault backfill, the CHECK, the office's column grant without the token, a mint that returns the raw token only on create or rotate, Vault cleanup on rotate and revoke, and the service-role read for the emails.
- **`legal-notify-dispatch`**: the link in each email comes from `legal_portal_link_token`; while the RPC is missing (before the push) it falls back to the raw column, so the deploy goes first.
- **`legal-portal`**: the office's preview by firm id. `?firm=<id>&preview=1` with a signed-in session answers when the caller passes `legal_office_can_read()`; 401 otherwise. No link lookup, no counted view.
- **The Firm's link dialog** ([`src/lib/legal/legalPortalLinkState.ts`](../../src/lib/legal/legalPortalLinkState.ts)): reads the table with the token and falls back to without it, so it works before and after the push. After it, the link shows only in the session that created or rotated it; otherwise *The link is live. The link can be copied only when it is created or rotated…* **Preview ↗** opens by the key when known, else by firm id.
- **The firm's page**: `/legal?firm=<id>` (no key) fetches by firm, shows an *Office preview* band, and saves no act.
- **The journey** (People → a firm): a live link counts with or without a token and opens as the office preview; `loadFirmRows` no longer reads the token.
- **Guide** `share-your-attorney-their-portal`: copy the link right away; Preview works any time; rotating stops every emailed link.
- **`docs/ACCESS_CONTROL.md`**: the office reads every column but the token; mint returns it only on create or rotate; the preview by firm id.

## Is this the best we can do?

- **Strict hash-only?** It would break every email's link. Vault keeps the token for the server alone, which is what "not readable at rest" has to mean while the emails carry it.
- **Should the office still copy the link later?** Only by rotating. That is the point: a key the office can always read is a key every office account holds.
- **What does the office lose?** The Lien desk share's "copy the firm's link" line (it read the raw column) goes quiet after the push. Preview survives, by firm id.
- **Could the push break the emails?** Only if the dispatcher is not deployed first; it falls back to the raw column until the RPC exists, so the order in the migration page is safe.
