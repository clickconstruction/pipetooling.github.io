# v2.2755 — Takeoffs parts catalog pages past the 1,000-row cap; rows never render blank (2026-09-04)

Wendi (estimator): "in Takeoffs the Add part line and Add part are not adding parts, they aren't saving" on BP396 MPH LIVSTE (Combined). Suspected cause was the v2.2707 Old/New retirement; it is unrelated (no Takeoff file changed since August). **Root cause: PostgREST's silent `max_rows = 1000` cap** on the tab's whole-catalog `material_parts` load. Plumbing crossed 1,000 parts in mid-June 2026 (845 → 1,102 by 2026-07-01; 1,713 on 2026-09-04). Ordered by name the truncated list ended at "DEN52 208V 9KW 3 PHASE", so every part from "DI…" through Z was invisible to (a) the row search, which filters the in-memory list and said "No parts match", and (b) saved rows, whose name lookup missed and rendered an empty "Search parts…" box with "Part · —". Her line was saved and linked the whole time. Because each save *looked* lost, she created "K-25077-0 KINGSTON…" four times (three 2026-09-03, one 2026-09-04); "OS-25" was created twice on 2026-09-02 the same way. Fifth recurrence of the cap class (v2.976/978 Crew P&L, v2.1004-era team labor, People Review, Settings backups).

## Client only — no migration, no edge functions

- New kernel [`src/lib/materials/partsCatalog.ts`](../../src/lib/materials/partsCatalog.ts) on the existing `fetchAllRows` / `fetchAllRowsChunkedIn` pager: `loadPartsCatalog(serviceTypeId, select?)`, `loadWholePartsCatalog`, `loadPartsByIds`, `loadWholePartPricesCatalog`, plus pure `missingPartIds` and `mergeCatalogParts`. Stable `name, id` order. 10 tests with the fake-cap client (1,713 parts / 2,189 prices; asserts every page is ranged).
- [`BidsTakeoffTab.tsx`](../../src/components/bids/BidsTakeoffTab.tsx): all four `material_parts` loads (rough-model-active effect, authoring-modal-open effect, and the two post-PartForm reloads) use the kernel. **New fallback effect**: any part id a rough line references that the loaded list lacks is fetched by id and merged in (ids already tried are remembered so an RLS-hidden part can't loop the effect) — a row can no longer render blank because of what the catalog load returned.
- [`AssignTakeoffPartModal.tsx`](../../src/components/bids/AssignTakeoffPartModal.tsx) (Pricing margin column's assign-a-part), [`useMaterialsCatalog.loadAllParts`](../../src/hooks/useMaterialsCatalog.ts) (Materials assembly/template pickers), [`Duplicates.tsx`](../../src/pages/Duplicates.tsx) (parts AND prices — the cleanup tool was itself truncated), and [`useSettingsCatalogs.loadOrphanMaterialPrices`](../../src/hooks/useSettingsCatalogs.ts) all page now. The Materials parts table (already `.range`-paginated), the backup exports, and every `.in()` / `.eq('id')` / `.limit()` read were already safe.
- Not changed: the search itself is still client-side over the full list (~1.7k rows with `part_types(*)` is fine); a server-side `ilike` search is the next step if the catalog keeps growing.
