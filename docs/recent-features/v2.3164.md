# v2.3164 — Signature pad paints white paper + dark ink in both themes (2026-09-08)

Fix, no migration. Reported from the live Bid Room right after v2.3159: the drawn-signature box rendered **black** with near-black ink, so a drawn signature was nearly invisible (see the screenshot in the PR).

## Cause

`signature_pad` was constructed with `backgroundColor: 'var(--surface)'`. A canvas `fillStyle` cannot resolve CSS custom properties, so the assignment was ignored and `clear()` filled the pad with the context default — black — while `penColor: '#111827'` drew near-black on it. This predates the Bid Room work: `ContractAcceptSignatureForm` (contract accept page, lien release modal) had the same options since the pad was introduced.

## Fix

- [`components/contracts/SignatureTypeOrDrawInput.tsx`](../../src/components/contracts/SignatureTypeOrDrawInput.tsx): new exported constants `SIGNATURE_PAPER_COLOR = 'rgb(255, 255, 255)'` and `SIGNATURE_INK_COLOR = 'rgb(17, 24, 39)'` feed both the pad options and the canvas CSS background. Deliberately theme-independent: the canvas *is* the PNG the office files, prints and shows on the signed record, so it stays paper-white under the dark theme too. `rgb()` rather than hex so `theme-tokenize --check` (which rewrites neutral hexes) leaves the literal alone; the comment in the file says why.
- Regression test in `SignatureTypeOrDrawInput.render.test.tsx`: the mocked pad records its constructor options; the test asserts real colors and that neither is a `var(…)` string, and that the canvas element's inline background matches.

## Verified

Local dev (Bid Room sample room), with `prefers-color-scheme: dark` emulated: canvas computed background `rgb(255, 255, 255)`, corner pixel 255/255/255, drawn strokes sampled as dark pixels; exported PNG is dark-on-white. The same component serves the contract accept page and the lien release modal, so all three surfaces are fixed together.
