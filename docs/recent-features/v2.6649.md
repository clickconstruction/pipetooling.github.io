# v2.6649 — Messages: the bids@ reader waits out Gmail's rate limit instead of knocking every minute (2026-11-07)

Follow-up the close of punch list #223 left (2026-11-07): since 2026-11-06 20:44Z every run of `gmail-sync` on the bids row failed with `Gmail /labels failed (429): User-rate limit exceeded. Retry after …`, the time in the words moving forward on every run, while the team row read every minute beside it. Nothing new to bids@ reached Messages for twenty hours.

- **The cause, read through the dev seat and the repo.** Gmail's retry time sat exactly fifteen minutes past each run's request (a run at 16:42:02Z was told *Retry after 16:57:02Z*), and the cron ran the reader every minute. Every request inside Google's window moved the window forward, so a reader that knocked once a minute never got out. Within this Google project only `gmail-sync` (every minute) and the walk kit's `walk` (on a press) read Gmail as bids@: `gmail-count` was off with no box on `email_box_watch`, `gmail-mine`'s follow read one tagged conversation as Taunya every five minutes, and the dev seat's `search_mail` ran eight times in two days as the logins, never as bids@, which is not one. What first tipped bids@ over at 20:44Z was not read: the project's function logs could not be opened from the session (the dashboard wanted a sign-in and the Management API's logs endpoint answered empty, then a backend error), and the reader's own reads before it were light (two lines landed that afternoon, the last at 19:50Z). The hold below ends the twenty-hour kind of outage whatever the first cause.
- **The hold** (`src/lib/emailIn/readerHold.ts`, mirrored into `_shared/gcKernels`): `readerHold(state, now)` reads the row's `last_error` and `updated_at`. A 429 (`isRateLimited`: the status `gmail.ts` writes, or Google's own *rate limit* words) holds the box until the time Google named (`retryAfterIn`), else fifteen minutes past the row's save (`RETRY_AFTER_DEFAULT_MS`), either at most an hour past now (`RETRY_AFTER_CAP_MS`). `runBox` reads the row first, and a held box answers `{ ok: true, held: true, until }` with nothing written and nothing asked of Gmail, so the row keeps the 429's words and time and Settings' health line (`readerHealthWords`) reads them as before. The other box runs as before: each box is its own try.
- **The label by its kept id.** The row's `label_id` was written on every good run and read on none: each run opened with `/labels` to find *In ClickTooling* by name. Now `runBox` takes the row's id and asks Gmail by name only when the row holds none (the first run of a box). `putLabel` wraps the two label presses in `takeOne`: a 400 (*Invalid label*) or 404 means someone took the label off the box, so it is found or made again by its name, kept on the context for the run and saved on the row, and the press tried once more; any other refusal is the message's own and stops the run as before. The `already` check by `labelIds` falls through for a stale id and the held-line press repairs it.
