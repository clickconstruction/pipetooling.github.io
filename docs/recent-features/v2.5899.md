# v2.5899 — Dev MCP keys kept in Vault, so a live key can be copied again (2026-10-26)

The owner, on Settings → Your account → Dev MCP keys with six live keys and five revoked: "I would like to be able to copy to clipboard an existing key." Nothing could be copied: the card generated the key in the browser and stored only its sha256 (`20260920063130`, "plaintext exists only at issue time"), and `dev-mcp` looks a key up by that hash. Offered **A** a one-press reissue (revoke and mint, the label kept), **B** keep each new key encrypted from now on so Copy works later, or **C** copy the snippet with the key blank, he chose **B**.

- **Issue goes through `dev_mcp_issue_key(p_token, p_label)`** (`20261026190000_dev_mcp_keys_in_vault.sql`, [`docs/migrations/`](../migrations/20261026190000_dev_mcp_keys_in_vault.md)): the browser still generates the key; the definer checks the caller (a dev, not a twin, not in training mode) and the key's shape, stores the sha256 as before for the lookup and the key itself in Supabase Vault (`dev_mcp_credentials.secret_id`). While the function is missing (client ahead of the push) the card falls back to the old hash-only insert and shows that key once.
- **Copy on each live kept key**: a confirm (*Copy "label"?* — the key is shown and put on the clipboard, the copy logged with your name) → `dev_mcp_reveal_key(p_credential_id)` → the key on the clipboard (`Copied the key`) and the same panel as a new key, titled *Your key for "label"*, with Copy setup command / shell line / key / header value. The reveal is for the caller's **own live** key only; another dev's key is refused like a missing one; each reveal writes one `dev_mcp_calls` row (`verb reveal_key`, `target dev_mcp_credentials`, the label in `args`), and the row shows *copied 2d ago* from that log. A key issued before 2026-10-26 has no secret and says *cannot be copied* (its title says to issue a new one and revoke it).
- **A revoke forgets the secret**: `dev_mcp_credentials_forget_secret()` runs `BEFORE UPDATE OF revoked_at` (live → revoked) and `BEFORE DELETE`, deletes the `vault.secrets` row and clears `secret_id`; a Vault refusal is a NOTICE, never a blocked revoke. So only live keys are recoverable, and only through the reveal.
- **No clipboard**: when `navigator.clipboard` is missing or refuses, the card draws the text under the buttons and selects it (the nicknames window's rule, v2.5806), with a warning toast saying to press ⌘ C.
- **Migration window**: the card reads the table with `secret_id` and retries without it on `42703`, so the keys still list (no Copy, no *cannot be copied*) until the push. Deploy the client first, then `supabase db push`; `dev-mcp` itself does not change (`docs/EDGE_FUNCTIONS.md` untouched). A `chore(types)` PR after the push regenerates `src/types/database.ts` and `dev-mcp/catalog.ts`.
- **Words**: the card's intro says Copy shows a key again and is logged, and that a key issued before 2026-10-26 cannot be copied; the guide *connect my coding agent to PipeTooling* gains **Copy a key again** (the steps, the log, the old keys, the no-clipboard case); `docs/dev-mcp/README.md` → Connect and `docs/ACCESS_CONTROL.md`'s `dev-mcp` paragraph carry the two functions, the trigger and the own-key rule.
- **Tests**: `devMcpKeys.test.ts` (`devMcpKeyCanCopy`, `lastRevealByKey`, the two migration-window error tests); `DevMcpKeysCard.render.test.tsx` (issue through the RPC with no insert; the hash-only fallback shown once; Copy → confirm → reveal → clipboard + panel, the old key's *cannot be copied*, the *copied …* read from the log; the selection when there is no clipboard; the retry without `secret_id`; not switched on).
