The owner, 2026-11-02 afternoon, on the merge queue: *I don't like that things are moving at the slow speed they are and I want to better understand what sacrifices we would need to make them move faster.* The read of the day, from the queue's GraphQL state and the `ci.yml` run list:

So each merge cost two full builds and about 50 runner-minutes, the day about 125 runner-hours; the queue drained three entries per 27-minute cycle, about 6.7 an hour, while arrivals ran about 7 an hour, so the backlog grew all day; and under `ALLGREEN` a flaky Test in one entry ejected it to the tail (another queue's wait, and a hand to re-arm auto-merge) and rebuilt the entries behind it. Two of the eight options weighed (the others: a paid plan for runner headroom, sharding vitest, a lighter PR build, flake work, a self-hosted runner for the queue, fewer PRs) cost almost nothing and went in the same afternoon.

- **The ruleset *main merge queue* (id 21096786), changed through the REST API, no code**: `grouping_strategy` `ALLGREEN` → **`HEADGREEN`** and `max_entries_to_build` 3 → **6**; `merge_method` SQUASH, `max_entries_to_merge` 5, `min_entries_to_merge` 1 with a 1-minute wait and `check_response_timeout_minutes` 240 unchanged, no bypass actors. Head-green merges a group when its head build is green, so a flake in an intermediate build neither ejects that PR nor rebuilds the ones behind it; a real failure still fails the head build, which carries the same commits. Six builds double the queue's ceiling to about 13 an hour where runners allow; at the afternoon peak the 20-job cap is the next wall.
- **`ci.yml` — a docs-only change runs the doc readers alone.** A new step after `npm ci`, *Which files changed*, asks the compare API for the files between the build's base and head (`github.event.merge_group.base_sha…head_sha` on a queue build — every entry in the group, so a code PR ahead keeps the full suite — and `pull_request.base.sha…head.sha` on a PR) and pipes the body to `scripts/ci-docs-only.mjs`, which writes `docs_only` and `doc_tests` to the step's outputs. **Test** runs `npm test` when `docs_only` is not `true`; **Test the doc readers** runs `npx vitest run` over the five tests that read `docs/`, `to-dos/`, `.claude/` or a release note from disk (`releaseNotes.test.ts`, `appDirectoryCheck.test.ts`, `punchListView.test.ts`, `todoBoard.test.ts`, `sessionClaims.test.ts`) when it is. The kernel `scripts/lib/docsOnlyChange.mjs` (plain JS, no dependencies) holds the patterns — `docs/`, `to-dos/`, a root `*.md`, `.claude/`, `src/content/releaseNotes/v2.NNNN.ts` — and is fail-safe: no files, a body that does not parse (the API down), a list at the API's 300-file cap or one file outside the patterns runs everything; a help guide under `src/content/help/` is code, since the guide tests read it. Typecheck, lint, the edge bundle link and every house check still run on a docs-only build; they cost about three minutes together.
- **Tests**: `src/lib/docsOnlyChange.test.ts` pins the patterns both ways, the four verdicts, the outputs' shape, that every listed test exists, that every module reading docs from disk has its test on the list (a new reader joins both), and that `ci.yml` runs the readers from the step's output and not from a second list. Run against real compares before the merge: a docs-only merge (#6811) read *docs-only*, a code merge read *full suite* naming its files, and an empty body read *full suite*.
- **Docs**: `CLAUDE.md`'s CI sentence names the docs-only path; `AGENTS.md`'s Branch + PR step names the queue's settings.
- **What it does not change**: the floor. A code PR still needs a 25-minute PR build and a 25-minute queue build, and the Free plan's 20 concurrent jobs still pinch at the peak. The next steps, in order, are runner headroom (GitHub Team), sharding the Test step across four jobs, and the flake list (that day: the UTC-day tests after 7 PM Central, a restored `matchMedia` shim, the stage-checklist fold race, the dev-mcp catalog).
