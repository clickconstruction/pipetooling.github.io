# v2.6404 — Each SQL bed applies its migrations through one psql, so a run of the beds takes 40% less build time (2026-11-02)

After v2.6372 a run of the SQL beds was five legs of 12 to 16 minutes. Most of a bed's time was its migration loop: 1,072 `docker exec` calls, one per migration, through one Docker daemon, with eight beds side by side on a 4-core runner. Timed on one runner, that loop took 477 s for eight beds at once, and one psql for all the files took 236 s.

- **The change**: `pgtest_apply` in `scripts/pgtest-pull.sh` takes a bed's files in order. It copies them into the bed's container with one `tar` over `docker exec` and runs them through one psql. Before each file psql writes the file's name to stderr, then `\connect` opens a fresh session and `\i` runs the file. The 69 beds in `scripts/sql-beds.txt` with a migration loop now call it. The 7 with no such loop keep what they had.
- **The sweep**: `scripts/codemods/sql-bed-loop-sweep.mjs` made the change and can be re-run (`--check` lists what is left). A loop that only applies each file became `pgtest_apply supabase/migrations/*.sql`. The 9 beds that also run a migration a second time, or a seed before one, keep their loop with its comments and conditions. That loop now lists the files, and `pgtest_apply "${files[@]}"` follows it, so each second run keeps its place. `gc-schedule` and `walk-kit` keep their per-file loop for a local Postgres (`PGTEST_PGBIN`), which has no container. A bed copied from main before this lands still works, and a second run of the sweep moves it.
- **What stayed true**: a failing migration stops the bed and the bed prints `FAILED applying <file>` with the error, or `FAILED re-applying <file>` for a second run. The error now also gives the line in that file (`psql:supabase/migrations/<file>:3: ERROR: …`) where the old loop said `psql:<stdin>:3`. Each file gets a clean session, so a `SET lock_timeout` or a temp table never reaches the next file. The files run in the order they ran before.
- **Why `\i` and not the files fed into psql's stdin**: a probe on the runner fed three pairs of files through one psql with `cat`. A file with no final semicolon ran into the next file, and the error named the wrong file. A file with `\q` ended the whole run with exit 0, so every file after it was silently skipped. A file that ended inside a string swallowed the next file's lines. With `\i`, psql reads each file to its own end, as the old loop did, and a `\q` ends only its file. None of today's 1,072 files does any of this. Timed the same way, `\i` took 238 s for eight beds at once, against 247 s for the stream.
- **Why `tar` and not `docker cp`**: the first proof run copied with `docker cp`, which failed on two of four containers 13 seconds old with "Could not find the file /tmp in container". `tar` over `docker exec` uses the same path as every psql call, and no bed has failed that way since.
- **A new bed, `bed-apply`**: the other beds only see the helper pass, so `scripts/pgtest-bed-apply.sh` holds its promises against a bare Supabase Postgres with no migrations, in about 20 s. It checks 16 things. Files run in the order given, a file given twice runs twice in place, and each file gets a session of its own, with no lock or setting carried over. A file with no final semicolon or newline ends with the file. A failure names its file and its line and stops the run, and a failed second run says `re-applying`. A file that ends inside a string fails as itself. A run cut short, which exits 0, still fails. A run that never reaches psql says so. A `\q` ends only its own file. Its fixtures are `supabase/tests/bed_apply/`.
- **The proof**: on `ci-test/` branches with the same migrations, a probe after each bed's migration step hashed `pg_dump -s` as `supabase_admin`. All 69 beds gave the same hash before and after (`abd4e62dafb03dd8`, 7,543,846 bytes), the 9 with second runs included. All 76 beds passed both ways with the same 3,718 `ok:` lines. A broken migration in the middle of the history failed all seven full beds in its leg, each naming the file and its line 3, while `bed-apply` passed beside them. A row count per table did not compare, since cron jobs write rows while a bed runs, so its total grew with the bed's own length.
- **What a run costs now**: the two full runs went out together, so they shared the same queue and runners. The probe adds a few seconds to every bed, the same on both sides.

  A full bed beside seven others took 359 s at the median before and 225 s after, and the slowest 514 s against 274 s. A bed still spends most of its time on the migrations: they were done at 222 s at the median after, against 357 s before. v2.6372's three runs on main had legs of 564 to 1,022 s and 66 to 72 job-minutes.
- **What did not help**: turning off `fsync`, `synchronous_commit` and `full_page_writes` saved 5% (226 s against 238 s for eight beds), so the disk is not the limit. Eight beds at once took four times as long as one bed alone (238 s against 60 s), so a 4-core runner gives about two beds' worth of work at a time.
- **Not changed**: what each bed tests, which beds run, the legs, the gate, and the four beds outside the list (`bid-next-followup`, `combined-copies`, `materials-model-flip`, `supply-house-words`), which CI never runs to prove a change. Every bed still applies all 1,072 migrations itself, so that work is the next cost.
