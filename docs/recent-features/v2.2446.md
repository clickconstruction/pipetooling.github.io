# v2.2446 — Segment billing reaches the last stage; the auto remainder stops lying (2026-08-28)

Taunya, on job 978 (two line items, $1,980 + $1,650): *"The one for $1980 generates right. But
when trying to make the 2nd invoice the amount changes."* Reproduced end-to-end on a scratch job.
Two stacked defects, one server + one client:

**Server — the zero-remainder envelope.** Every Ready-to-Bill job carries the elastic primary
remainder bundle (the "auto" draft) that `ensure_single_ready_to_bill_invoice_for_job` resizes
after every invoice mutation. When a segment/partial invoice consumed the *whole* remainder, the
resync branch UPDATEd the primary to $0.00 and returned
`{error: 'Nothing left to bill; invoice amount would be zero'}`. Every resync caller threw on any
error envelope — *after* its invoice insert had succeeded — so the user saw a failure banner, no
refetch (stale screen), and a zombie $0.00 auto draft. Migration
`20260828170937_ensure_rtb_zero_remainder_deletes_primary.sql`: that branch now DELETEs the
never-sent primary (same plain DELETE as `delete_ready_to_bill_invoice`; the Stripe-finalized
guard above it is unchanged) and returns `{ok: true, fully_allocated: true, primary_deleted:
true}`. The primary-absent zero-remainder branches keep their error envelopes — Bill Customer's
ensure-on-open depends on them.

**Client — the auto bundle counted as allocated.** v2.1134 taught the segment-coverage kernel
(`dollarCoverageForSegments`) and the ensure RPC to exclude the elastic primary from the allocated
basis, but the Edit-Job New-Invoice/slider stack (`allocatedInvoiceDollars` /
`unallocatedBillableDollars` in `src/lib/jobs/jobFormBreakOff.ts`, feeding `useBreakOffSlider`,
the blur clamp, the prefill, `getEditJobBillableRemaining`, and the segment-select bar sync)
never got the memo. Since the auto draft always equals the remainder, every RTB job read
**"100% Billed / 0% Left to bill"**, segment selection synced the New Invoice card to $0, and any
typed amount blur-clamped to $0 — Taunya's "the amount changes". `allocatedInvoiceDollars` now
skips `ready_to_bill` rows with `is_primary_rtb_bundle === true` (billed rows always count), which
also makes the `jobSegmentsCoverage` comment claiming the two bases match true at last. The
full-remainder → Bill Customer redirect in `createInvoice()` keeps working, now against the true
remainder.

**Client — resync failures are reported, not conflated.** New kernel
`src/lib/jobs/ensureRtbRemainderResult.ts` (`ensureRemainderResyncOutcome`, unit-tested):
`ok` envelopes and the pre-fix fully-allocated error strings ("Nothing left to bill…", "No
remainder to bill…") are success for post-mutation resyncs — the caller's invoice already exists.
All four resync sites (segment create + partial create + hazmat fee split in `JobFormModal.tsx`,
partial modal in `JobsStagesTab.tsx`) now refetch/reload regardless and report a real resync
failure as "Invoice created, but the remainder draft did not re-sync: …" instead of throwing; the
draft-delete resync in `JobFormInvoiceList.tsx` swaps its narrower regex for the kernel.
`SendRecordInvoiceModal` maps the new `ok+fully_allocated` shape to its friendly "nothing left to
bill" message (it previously would have said "Unexpected response from server").

Deploy order is free: old client + new RPC sees `ok` where it saw an error (success path); new
client + old RPC treats the old error strings as benign. Help guide
`split-a-job-into-stages` gains a Good-to-know bullet explaining the **auto** draft's lifecycle.

**Known follow-up (not in this PR):** the Pipeline board's partial-invoice modal basis
(`jobBillingUnallocatedDollars` in `src/lib/jobsStagesBoard.ts`) still counts the primary bundle
("same basis as ensure RPC" comment is stale since v2.1134); it also feeds board row-building and
`promoteJobToBilledIfFullyInvoiced`, so it needs its own carefully-scoped pass.
