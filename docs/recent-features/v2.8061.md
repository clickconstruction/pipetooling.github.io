# v2.8061 — HR files: a read of its own that fails is named on the file (2026-11-20)

Found by the audit of punch list #315. No migration, no seat change.

## What was wrong

The HR file reads three things apart from the Timeline's sources: the correction links (`person_file_amendments`), the evidence numbers (`person_file_evidence.exhibit_no`) and the standing (`person_engagements`). Each read is fail-soft and returns `heldWhy`. `PersonFilePanel` dropped it for the links and the numbers, and passed the standing's only to the Standing window.

- A links read that failed drew every entry with no *Corrected* chip. A reader took a corrected entry as the latest word.
- A numbers read that failed drew no *Ev #n* and no numbering strip.
- A standing read that failed left the strip reading *Standing…*, the words of a file with no stretch, and took the Employment lines off the Timeline.

Nothing on the screen said a read had failed. Walked on the local app with each read answered 503 on `ZZ Test Hand`.

## What changed

- `PersonFilePanel.tsx` keeps `amendHeld` and `numbersHeld` beside `standingHeld`. The file's *Not read here:* line, which already named a held Timeline source, names each of the three with its reason. The links' words say what the reader loses: *the correction links, so a corrected entry is not marked*.
- The strip's press reads *Standing not read* when the standing's read failed. It still opens the window, which says why.

## Verification

- `PersonFilePanel.heldReads.render.test.tsx`: no line when every read answers, the links named alone, the numbers and the standing named together with the strip's words.
- The help guide `keep-private-employee-files` says what the press reads.
