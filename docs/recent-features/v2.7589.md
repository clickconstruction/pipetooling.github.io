# v2.7589 — Tasks: an assistant can set, move or take off a task's place (2026-11-17)

The second of the dev seat's three task PRs, on `dev-mcp` (server 0.96.0, 117 write verbs): **`plan_task_place`** → **`apply_task_place`**. The owner's ask was to "set locations" on tasks.

## What a place is

A task's place is a named point on the map, *Pump house*, in columns on the task as written. It is not an address. The giver sets one in the New task window and changes one in Checklist → Manage → Edit, and both write the place kernel's columns (`taskPlaceColumns`) on the task's own row. This pair makes that same write, as the dev under RLS.

The doer's own press, `add_task_place_from_the_spot`, is not the door. It fills a missing place from a phone's reading, and refuses a place with no reading and a place that is already there.

## Four ways to say a place

A person at a desk rarely has a latitude. Each way ends as a point, and the plan shows it with a map link before anything lands.

- **A point**: `lat` and `lng`.
- **An address**: the app's own saved point for it first (`address_geocodes`, read and never filled), then the Census geocoder. The function does not call `geocode-one`, because that function saves what it finds and a plan must write nothing.
- **A job**: its address, found the same way.
- **Like**: the name of a place another task already carries, as the window's chips offer it.

`plan_task` takes its place the same four ways.

## The write

- One update that asks for the row it changed, so a row RLS kept is said.
- A task that came from a roadmap keeps its place on the roadmap task, as the app keeps it. The plan says which row it writes.
- A painted map on the task follows the task windows' rule: a map that led to the old place comes off with it, and a map on a task with no place stays. The rule is one line here, held equal to `taskMapAfterPlace` by a test, since importing that file would carry the painted-map kernels into every upload.
- `clear: true` takes the place off.
- Refused: a place that cannot be found, the place it already has, a clear with none to take off.
- No RPC and no migration. It tells nobody.

## What an independent review found

A second reader went through all three task PRs before this one opened. The hash, the window's refactor and the filters held. These did not, and are fixed here:

- **A real second act was turned away.** A place set, taken off and set again hashed like the first time, and the call log refused it. The same for a task given, deleted in the app and given again. Both verbs are refused by their own state now, as Materials on site's presses are: a replay finds the place already there, or the task already given.
- **A dropped connection mid-apply** surfaced as a bare tool error with no task id. Every write after the task row is a named step now.
- **A roadmap task with a place on its own row**: the card reads that row first, so that is the row the verb writes.
- **The same point under the same name** over a place a phone had set counted as a change, and would have dropped the phone's margin and the map. It is no change.
- **A place taken by its name** now brings the painted map that leads to it, as its chip does.
- **`get_task`** showed a weekly task's five weeks ahead and never today's row, its thread or its photos. It reads the days around today.
- **`find_task`** read every match's open days in one read of 200 rows, so later matches read as closed. Each task has its own read, and a person's list is read a page at a time.
- **A person named by a short name** could be cut from the twenty rows by archived accounts and twins. The roster's filters ride in the read.
