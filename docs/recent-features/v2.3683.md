# v2.3683 — Lien desk: every open month is back on the notice (a same-day fix) (2026-09-21)

One migration, no client change. Fixes [v2.3680](./v2.3680.md).

## What went wrong

v2.3680's `CREATE OR REPLACE` of `list_lien_notice_months` was written from `20260914180000_lien_desk.sql`, the migration that first created the function. But `20260914190000_lien_desk_affidavits.sql` (v2.3412) had already redefined it: a job counts when billed **or** with a billed invoice, and once any of its months is inside the look-ahead window every unnoticed month with an open window rides along. The push at 19:3x replaced that body; within the hour job 258's Months card showed July without August and gate 4 read *Jun, Jul*.

## What shipped

- **Migration [`20260921203000_lien_notice_months_restore_window.sql`](../../supabase/migrations/20260921203000_lien_notice_months_restore_window.sql)** — v2.3412's body again, with v2.3680's rule kept: a closed month that is unnoticed and unrecorded since 2026-09-14 stays, and brings its job into the window (`silent` CTE, unioned into the window's job set). Pushed the moment it was written. Detail: [`docs/migrations/20260921203000_lien_notice_months_restore_window.md`](../migrations/20260921203000_lien_notice_months_restore_window.md).

## The rule this teaches

Before `CREATE OR REPLACE` on any function, grep its name across **every** migration and start from the newest definition — the file that created it is rarely the file that last changed it. `docs/MIGRATIONS.md`'s best-practices section carries this now.
