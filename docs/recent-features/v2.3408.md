# v2.3408 — Pipeline: click "Progress & payment" to sort rows by % complete, 0 → 100, session-only (2026-09-14)

Client only; no migration, no edge function.

## Why

Owner, 2026-09-14: "I would like to be able to click on the title Progress & payment and have it sort jobs by % complete from 0 to 100%. When the user leaves and comes back I would like it to drop this sorting record." The board had two row orders (newest job number, time added — v2.1807), both picked from the ⋯ menu and the second remembered per device. Nothing ordered the rows by how far along the work is.

## What shipped

- **Sort-mode kernel** [`jobsStagesSortMode.ts`](../../src/lib/jobsStagesSortMode.ts) (+2 tests): a third mode `progress` with the ⋯-menu label *Percent complete (0 → 100)* and the chip word *% complete* (`STAGES_SORT_MODE_ACTIVE_CHIP_LABELS`); `toggleStagesProgressSort` (progress ↔ number). **Session-only by construction**: `saveStagesSortMode('progress')` returns without touching storage and `loadStagesSortMode` can never yield it — so the remembered pick (classic or time added) comes back the moment the user leaves and returns, and a hand-planted `progress` in storage still loads as the classic order.
- **Board kernel** [`jobsStagesBoard.ts`](../../src/lib/jobsStagesBoard.ts) (+2 tests): `sortStagesJobsByProgressAsc` — `pct_complete` ascending, effective job number breaks ties, a job with **no percent sinks below 100%** (the column shows it blank, so it must not read as a 0). `buildJobsStagesBoardLists` routes the mode; sections never reorder, only their rows.
- **The header** — new [`StagesProgressPaymentHeader`](../../src/components/jobs/StagesProgressPaymentHeader.tsx), mounted by both `JobsStagesTable` and `JobsStagesUnifiedTable` in place of the static `<th>`. With an `onToggleProgressSort` prop it is a button (`aria-pressed`, `th[aria-sort=ascending]`, a faint ↕ at rest, a lit *0 → 100* while sorted); without one (the Follow-Up deck embeds pass `hideHeader` anyway) it stays plain text. +3 render cases across the two table smokes.
- **The tab** [`JobsStagesTab`](../../src/components/jobs/JobsStagesTab.tsx): passes the toggle to the six section mounts (Waiting · Working · Ready to Bill · Billed · Collections · Paid); the *Sorted: … ×* chip beside ⋯ now reads its word from the mode (`time added` / `% complete`), and the ⋯ menu's Sort group lists the new mode automatically (it maps `STAGES_SORT_MODES`). Phone card lists have no header row; the ⋯ menu and the chip are the doors there.
- Help guide *sort the pipeline by percent complete* (+ a pointer from *sort the pipeline by when jobs were added*).

## Decisions taken (owner can flip)

- Clicking the lit header restores job-number order (not a descending pass) — the ask was 0 → 100 only.
- No-percent jobs sink below 100% rather than sorting as 0%.
- Turning progress on does not clear a remembered *time added* pick — that is what "drop this sorting record" leaves behind.

## Verified

Kernel suites (`jobsStagesSortMode`, `jobsStagesBoard`), the three Stages render smokes, release-note + guide drift tests, typecheck, lint, theme check; dev-server pass on Jobs → Pipeline (header click reorders Working 0 → 100, chip appears, reload restores the classic order).
