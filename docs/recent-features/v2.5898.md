# v2.5898 — A refused save says why, not "Failed to save" (2026-10-26)

Punch list #184, sweep D, PR 1 of 2 (the kernel before the codemod). The audit behind the to-do found one fact that shaped every count: a Supabase result's `.error` is a **plain object** parsed from the body (`@supabase/postgrest-js` builds a `PostgrestError extends Error` only under `.throwOnError()`), and the app throws it bare with `if (error) throw error` in 361 places. `formatErrorMessage` (`src/utils/errorHandling.ts`) read `instanceof DatabaseError`, a fetch-layer `TypeError`, `instanceof Error`, then a string, then the fallback — it had **no branch for a plain object**, so on every one of those throws it returned the caller's fallback whatever the server said, exactly what the 634 `e instanceof Error ? e.message : '…'` ternaries show. `formatPostgrestOrUnknownError` had the branch all along, with its `Code:` / `Details:` lines meant for a `pre-wrap` box. No migration, no edge function.

- **`formatErrorMessage`** gains the plain-object branch, between the Error branch and the string one, under the same rule as the rest (v2.2843: the class decides, never the text): a `code` or a `status` is classified by `classifyResultError`; `network` renders the offline copy; `42501` renders *You don't have access to this record.* and `22P02` / `PGRST116` the broken-link sentence (`describeClassifiedError`, no operation name to lead with); any other server reason **follows the caller's fallback** — `formatErrorMessage(err, 'Could not save the note')` → *Could not save the note: duplicate key value violates unique constraint "notes_pkey"* — the way an operation name leads a `DatabaseError`'s, or stands alone when the caller gave none; a codeless object is read by its message, with the fetch signature as the last resort; an object with no words at all still reads as the fallback. `[error-class]` telemetry fires as it does for the other branches.
- **`UNEXPECTED_ERROR_MESSAGE`** is exported: the default fallback, so a caller can tell the default from its own sentence.
- **Tests** (`errorHandling.test.ts`, +7): the RLS refusal, the missing row, the reason after the fallback and alone, the fetch-layer result object, the codeless object both ways, the wordless object and an array, a 502 with no body code.
- **Reach**: every one of the 916 existing `formatErrorMessage` call sites that receives a bare result object is honest from this PR on, with no call-site change. PR 2 (`error-reason-sweep.mjs`) rewrites the ternaries onto the formatter and adds `check:error-words` to CI; the public pages and the portal cards are left to a hand PR, since a customer reads the class and never the server's words (the to-do's *Is this the best we can do?*).

**Is this the best we can do?** The alternative was `checkSupabaseError` at every bare throw, which carries an operation name and so writes *Failed to delete checklist items: …* instead of *Failed to delete: …*. That is the better sentence and stays the rule for new code (`CLAUDE.md`); it is 361 hand-written names, not a sweep, and the fallback the caller already wrote is the same words nine times in ten. The kernel branch takes the whole app most of the way in one change; the names can follow surface by surface.
