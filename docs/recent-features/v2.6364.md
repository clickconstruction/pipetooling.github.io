# v2.6364 — Search every file deeply: the index check says which files are in the index and which are not (2026-11-02)

Punch list #240, after the one-time backfill (v2.6343): the owner asked how we track which uploaded files are in the index and which are not, so we know when to index again or index more. A `file_index` row is the record of a file a walk reached, with its reason when it has no text; nothing recorded the files no walk reached, and the walk by home cannot reach some by design: a job with only a pictures link (`index_job` needs the folder link), anything in the Shared Drive outside a job's or bid's folder, a file deeper than three folders. This adds that record, one reconciliation of what the Shared Drive holds against what the index holds, and the door to fill what it finds. No migration; `drive-link` redeployed.

- **`drive-link` `{ action: 'index_check', max?, sample? }`** — the sweep's own lister (`filesChangedSince` from the dawn of the drive, inclusive, folders left out, capped at 10,000 files, `capped` when the drive holds more) against every row (a thousand at a time in a total order, since PostgREST answers at most a thousand whatever `.limit()` asks), reconciled by `_shared/fileIndexCheckKernel.ts` → `{ filesInDrive, capped, rows, filesWithNoRow, filesChangedSinceRow, rowsOutsideListing, rowsOutsideListingOn: { job, bid, none }, rowsWithText, rowsByWhy, missing: [{ id, name, mime, modified }] }`, `missing` being the first `sample` files with no row, newest first (25, at most 500, 0 for counts alone). A read of Drive and of our table, nothing written; a dev's door (403 for the other roles), so the training-account line PRs 3 and 4 edit stays untouched. Modified times compare as instants (Drive's `Z` against PostgREST's `+00:00`).
- **A row outside the listing is not a file gone.** A bid's folder can sit outside the Shared Drive, readable because it is shared with the service account, and its files have rows the drive's listing never shows. Only asking Drive by id can tell, which is what the sweep's recheck does (twenty rows a run, about the whole index a day), so the check counts those rows by what they belong to and does not ask for a pass on their account.
- **`scripts/file-index-check.ts`** — `npx vite-node scripts/file-index-check.ts` signs in as the dev-login identity (`scripts/lib/paySession.ts`), calls the door and prints the counts in plain sentences, then whether the index wants a pass. `--list` adds the first files with no row by name, which stay on that computer. `--fill [--pause 1500]` indexes the files with no row through `index`, one file a call, two hundred a round, until none are left or a round gains nothing (`fillContinues`), counts only; one file a call because an edge function has about two seconds of CPU per request, so a heavy PDF can stop its own call and no other, and its row keeps the stamp it was given before the read.
- **The runner keeps a stopped home to walk again** (`recordOutcome` in `scripts/lib/fileIndexBackfill.mjs`). The run marked two old bids done after the worker hit the CPU limit (HTTP 546) three tries running, with most of one's files unread, and its summary called them homes *the app could not open*, which they were not: both had listed and had rows. A home the function refused or stopped on, or that ran out of rounds, now stays out of `done` with its counts apart, and the summary says *the function refused or stopped on, to walk again*.
- **The card** holds the run's counts in *Where it stands*, and its next and blocker lines say what is left.
- **Tests**: `src/lib/documents/fileIndexCheckKernel.test.ts` (the reconciliation: files with no row, instants in both spellings, a file listed twice, rows outside the listing by home, the reasons, the sample's order and size; the words, plain and capped, with no file's name in them; what wants a pass and what does not; when a fill goes round again and what it counts); `driveLink.test.ts` takes the new ask.
