# v2.3246 — Customer Waiting, PR 1 of 4: priority on inbox requests (2026-09-10)

Migration `20260910220000_request_priority.sql` (doc: `docs/migrations/20260910220000_request_priority.md`) + four edge functions redeployed (`submit-portal-request`, `customer-portal`, `notify-dispatch-request`, `notify-estimator-request`). No client change in this PR.

## Why

Robert: "customer portals … when a customer sends a request it should be a high priority request in the dispatch or estimator inbox … it should look different in the inbox and people in that inbox should see the high priority request as a banner at the top of the page following them around the app … if they downgrade the request it should remove the high priority status … messages from customer portals should offer a phone number button in the inbox to call the customer right away."

What the code said before this PR: no priority concept anywhere (not a column, not in the sort, not in the badge — open rows sort oldest-first, so a customer's emergency sank under three-week-old errands); the phone the customer typed was saved in `pending_payload` and never selected by the inbox; both portal forms wrote to `dispatch_requests`, so "Ask us to bid" never reached the estimator; and the intake's push fan-out called `notify-dispatch-request` with no bearer, which returned 401 on every portal request since v2.1986 — no push ever fired for one.

Design: mockup + self-review + revision at https://claude.ai/code/artifact/a4b6cba5-7d7d-42aa-93c2-26c54a391877 (nine findings; the ones that changed the design: the banner must know when a teammate has already called; the Call button cannot hang on an optional field; the wait, not the label, is the pressure; lowering must keep its reason; bids belong to Estimating).

## What shipped

- **Schema** — `dispatch_requests` and `estimator_requests`: `priority` (`normal | high`), `priority_changed_at/by`, `last_called_at/by`; `estimator_requests.pending_payload`. Partial `*_open_high_idx`. `estimator_requests` + `estimator_request_notes` join the realtime publication (they never had — the estimator inbox's subscription was silent).
- **RPCs** — `set_request_priority(inbox, id, priority, note)` and `log_request_call(inbox, id, phone)`: SECURITY INVOKER, one transaction each (row stamp + thread note `Priority lowered — <note>` / `📞 Called <phone>`), boolean result. Who may act = who may close today (group member or dev).
- **Intake** (`submit-portal-request`) — every portal row lands `priority = 'high'`; `visit` / `stage_window` → Dispatch, `bid` → Estimating when `estimator_group_members` is non-empty, else Dispatch. `pending_payload` gains `customerId`, `phone` (typed, else on file), `phoneSource`. Title: *Customer waiting — {name} asks for a visit: …*. The push fan-out now presents the service key.
- **Phone on file** — `_shared/portalCustomerPhone.ts`: `customers.contact_info->>'phone'`, else the newest `jobs_ledger.customer_phone`. `customer-portal` adds `customerPhone` to its payload for PR 4's form prefill.
- **Notify functions** — a service-role bearer is a trusted internal caller for the `created` fan-out only (row read as admin, author check skipped); closes/reopens stay user-only.

## Decisions taken without an answer (flag if wrong)

- Sub-portal requests (`submit-sub-portal`) stay `normal` — subs are not customers.
- A high request stays high until a person lowers or closes it; nothing auto-lowers overnight.
- The estimator group in prod: whoever is in it gets bid requests from now on; if it is empty they fall back to Dispatch, so nothing is lost either way.
