# v2.7953 — Pipeline: the line no longer says the refresh did not land while it is still landing (2026-11-19)

## Why

The session cutting `JobsStagesTab.tsx` into parts (punch list #46 row 2) saw a false failure line on clicktooling.com while checking its last cut. It left the fix out of its own PRs, which must not change behaviour.

Seen again on build `index-DfX0q0gF`, 2026-11-19, with `fetch` wrapped. On a move from the Dashboard to the Pipeline the line read *Updating jobs…* with *board from just now* at 0.2 s, then *Showing the board this device remembered — the refresh did not land.* from 1.4 s to 2.1 s, then the live board. All 131 reads answered 200 or 201. The false line started when `get_stages_enrichment` went out and ended when it came back. On a plain reload of `/jobs?tab=stages` it showed for 2.2 s. On the first visit, with nothing remembered, the same enrichment took 5.2 s, so a slow morning would hold the false line that long.

The cause: the jobs cache keeps the remembered rows up until the enrichment landed, so a half board is never kept (`useKeptRead`'s `loading` counts `jobsListEnriching`). The flag it handed out, `jobsListRefreshing`, went off when the main read landed. The board reads a remembered board that is neither loading nor refreshing as a failed refresh.

## What changed

- **`keptBoardFlags`** (`src/lib/jobs/keptBoardFlags.ts`, new kernel): the two flags the cache hands out while the remembered rows show. Loading is off. Refreshing is on while any read is out, the enrichment too, and stays on until `useKeptRead` reports `failed`. With no remembered rows on screen the cache's own flags pass through untouched.
- **`JobsListCacheContext`** hands out `jobsListLoading` and `jobsListRefreshing` through the kernel. Nothing else in the cache changed: the refs that gate scope fetches and the tab's freshness are as they were.
- **`JobsStagesTab.tsx` is not touched.** Its line already reads the two flags the right way, and its smoke (`JobsStagesTab.snapshotChip.render.test.tsx`) holds the words.

## Who else reads the flag

`jobsListRefreshing` now stays on through the enrichment, only while the remembered board shows, which is the first load of a session on a device that kept a board:

- **The Pipeline's line**: *Updating jobs…* with the chip, where it said the refresh did not land.
- **The HCP Jobs tab**: *Updating…* through the same second or two, where it showed no line over the remembered rows.
- **`Jobs.tsx`**: New Job and Edit Job answer *Please wait until jobs finish loading.* and a `?newJob=` or `?edit=` link waits, for that second or two longer. They already waited while the main read was out, and until the enrichment lands the rows on screen are still the remembered ones.
- **The three Quickfill hooks** (`jobsListBusy`): unchanged. Their full read has no enrichment.
- **`jobsListSnapshotAt`**, `data-kept-read`, the chip, the muted money and the held row presses: unchanged.

## Tests

- `keptBoardFlags.test.ts`: six cases, among them the enrichment over a remembered board, the render between the last read landing and the live rows, a failed read with nothing out, and a new try after a failure.
- `JobsStagesTab.keptBoardStatus.render.test.tsx` (new): the real cache over the real board, with the reads held. The main read lands and the enrichment is still out: the line reads *Updating jobs…board from 5 min ago* and the failure line is absent. On the old code this case fails with the failure line on screen. A live read that fails still shows the failure line with the chip.
