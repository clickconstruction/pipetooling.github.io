## Ticks and bank matches

The spike's draft of the function did not look at either. A sending is one money movement: `set_sub_payment_checked` and `match_sub_payment` act on every row of a sending, and a sending's rows share one bank line. So the function refuses rows matched to different bank lines, and the client holds such a group first. It writes `sending_id` alone, which fires neither trigger on the table, so every tick and match stays as it was. Rows ticked unevenly are gathered as they are. That state exists already, since an amount edit clears one row's tick, and the next tick on any row covers the sending.
