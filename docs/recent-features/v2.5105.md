# v2.5105 — What customers see: the sample bid room is built like a real one (2026-10-09)

Punch list #103 (`to-dos/customer-samples-through-kernels.md`), PR 1. No migration. Edge functions to redeploy after the merge are listed under *Deploys owed*; until then the sample shows the old room and nothing breaks.

## What was wrong

Settings → What customers see has shown the GC's bid room since v2.2758 (`/bid-room?t=sample`, `sample-done`). `sampleBidRoomResponse` wrote the revision payload by hand: it copied `SAMPLE_BID.options` into `options`, set `header_brand` itself and sent `add_ons: []`. A real payload is built by `buildBidRoomRevisionPayload` when the Cover Letter tab publishes, and read back by `parseSharedBidRoomPayload`. So nothing held the sample to the builder's rules, and:

- the with-and-without alternates of v2.4197 never showed on the sample;
- no option carried a `bid_version_id` (v2.4728);
- the signed sample's outcome was not the shape `sign-bid-room` writes (no `add_ons_taken`, `add_on_keys`, `option_version_id` or `rev_number`).

## What changed

- **The publish kernel moved to `_shared/`.** `buildBidRoomRevisionPayload`, `roomHeaderBrandForServiceType` and the two input types moved from `src/lib/bids/bidRoomPayload.ts` to a new [`_shared/bidRoomPublish.ts`](../../supabase/functions/_shared/bidRoomPublish.ts), unchanged. The src file re-exports them, so the Cover Letter tab, `BidRoomPanel` and every test import exactly as before. The kernel sits beside the parse twin (`_shared/bidRoomPayload.ts`), not inside it, so `sign-bid-room` and `send-bid-room-link`, which only read a payload, keep their bundle.
- **The sample takes a real revision's path.** In [`_shared/customerSampleFixtures.ts`](../../supabase/functions/_shared/customerSampleFixtures.ts), `SAMPLE_BID`'s two priced sections (*To Plans* and *PEX in lieu of copper*, each now with a sample bid version) and one with-and-without add-on (*Alternate 2 — Clubhouse restrooms*, $4,850) go through `buildBidRoomRevisionPayload`, then a jsonb round trip and `parseSharedBidRoomPayload`, the read `get-bid-proposal-room` makes of a stored revision. The builder decides the keys, totals, brand and add-ons. `_shared/customerSample.ts` is untouched, so the functions that only read the sample names keep their bundle.
- **The open sample** now offers the add-on, ticked to start as on every real room, so its total reads $61,193.00 (the base and the add-on).
- **The signed sample** carries the metadata `sign-bid-room` writes on a signature that keeps the default: the base, its version, the add-on taken and the grand total.

## Tests

`src/lib/bids/sampleBidRoom.test.ts` (4, new): the sample payload equals the kernel's output for the bid's sections and add-on, and the room page's own parse reads it unchanged; the options, versions, add-on and brand a published room carries; today's Settings for exclusions and terms, trimmed as the kernel trims; the signed outcome in `sign-bid-room`'s shape. A mutant that drops the add-on from the sample fails three of the four. The parity, builder, won-option, Cover Letter, room page, link email and sample email suites pass unchanged: 56 tests in all, the new four included.

## Found, not fixed

**A reloaded signed room drops the add-on's name.** `BidRoom.tsx` reads `outcome.metadata.add_on_names` for its *Signed by …* line, which only the page's own just-signed state sets. `sign-bid-room` saves the names as `add_ons_taken`. So once a GC who took an add-on reloads the room, the line reads *Signed by Pat Sample — “To Plans” · $61,193.00.* The total counts the add-on, but its name is gone. The signed sample now shows exactly that, read in a render probe, because it carries the real shape. The fix is one read in `BidRoom.tsx` plus a render test, a PR of its own.
