# v2.6721 — The seat's backfill takes a person: the files already on a record, indexed (punch list #285, PR 3) (2026-11-08)

Punch list #285 (`to-dos/search-reaches-linked-file-text.md`), PR 3 of three, on PR 1's pass ([v2.6714](./v2.6714.md)) and PR 2's search ([v2.6719](./v2.6719.md)): a case filed before the index reached the HR file has its files read on one ask, so the twenty-odd transcripts of the case imported on 2026-11-08 are searchable without a retype. No migration.

## What changed

- **The person scope** (`supabase/functions/_shared/devMcpIndexBackfill.ts`): `BACKFILL_SCOPES` gains `person`; the plan carries `person_id` (a `people.id`, with scope person alone; never `after_job` or a `job_id`). `personBackfillCommitment` hashes the person, the `retry` switch and every file they carry, sorted — so an apply that indexed files still matches and a file filed or removed since refuses. `personBackfillPlanReply` answers the counts (`files`, `files_read`, `files_held`, `files_due`, by record kind, by where the bytes are), the first eight files due with their record, what a read costs and the how; `personBackfillApplyReply` answers `due`, `tried`, `indexed`, `held`, `remaining`, `done` and the next step; `recordsBatch` caps a call at 25 (10 by default), each a bucket or Drive read.
- **The seat** (`dev-mcp`, server 0.44.0): `plan_index_backfill` / `apply_index_backfill` branch on the person scope before the job walk — the person read as the service role, every attachment on their file and every unvoided document on their matter listed, the index rows and the queue (`file_index_records_due`, PR 1) read to say which are read, held or due; the apply runs `recordsPass` over the person with the plan's `retry`, the gone rows dropped first, a Drive token minted only when a linked file is met. The descriptions of both verbs name the scope.
- **The records pass** gains `retry` (`_shared/fileIndexRecords.ts`): false takes records with no row alone and leaves a held row to the sweep.
- **Tests**: `src/lib/devMcp/devMcpIndexBackfill.test.ts` (the parse, the commitment's order, the plan reply with and without retry, the apply reply, the batch, the server and the README pinned), `src/lib/documents/fileIndexRecords.test.ts` (retry false).
- **Docs**: `docs/dev-mcp/README.md` (the file index row), `docs/EDGE_FUNCTIONS.md` (dev-mcp), the card.

## Read closer than the card

- The card drew `plan_index_backfill { scope: 'person', person_id }` listing the files with no row and `apply_index_backfill` queueing them. The apply indexes them in the call (the pass, a batch at a time) rather than queueing, since the queue is the records' own state and the sweep already drains it; the apply is for the case that cannot wait ten minutes a batch of ten.
- The job scopes are untouched: `backfillJobsQuery` never sees a person plan.
