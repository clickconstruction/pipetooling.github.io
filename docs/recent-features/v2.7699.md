# v2.7699 — Lien desk: a wrong mailed copy taken off goes to Drive's trash, and you can put it back (2026-11-17)

The owner, 2026-11-17, after v2.7635 and v2.7642: "Should we add a press that clears a wrong receipt photo without a retake, or remove or delete a wrong file from the drive? Please help me mock up, ask yourself Is this the best we can do, and then build."

**The answer was both, as one press.** The press that clears a receipt without a retake was already on its way in another change (**Take off** and **Replace** on every receipt, PR #8589). What neither it nor the mailed copy's **Take off** (v2.7525) did was touch Drive: the link came off and the wrong file stayed in the job's folder, beside its retake and under the same name. This change builds the Drive half and puts it on the mailed copy. The receipt press takes the same door in the next change, once #8589 is on main.

**What "is this the best we can do" changed.**
- *Trash, not delete.* The file goes to Drive's trash and stays 30 days. The app's service account is a Content manager on the jobs Shared Drive: it may trash a file and may not delete one, so trash is also the strongest act it has.
- *One press, not a second "Delete from Drive".* A second press is the one that gets skipped. The ask before the take-off says where the file goes.
- *Put it back.* A slip on the right file is the mirror mistake, and a phone photo may exist nowhere else.
- *A file a record still uses is never trashed.* When a mailing is recorded the notice's first mailed copy becomes the filing's saved copy, so one file can have two homes.
- *A busy Drive does not hold the take-off.* The link comes off first and stands. The trash is a second step with its own **Try again**.

**The function's door.** `drive-link` takes `trash` and `untrash` (`_shared/driveTrash.ts`, pure rules; `trashDoor` in the function). Three fences, in order:
1. A Pipeline job, and a file whose parent is the job's **Team only → Sent by us** folder. The folder is found with `childFolder` and never made.
2. For a trash, every row of `job_lien_filings` and `job_lien_desk_items` for the job is read as the service role and searched as text for the file's id (`lienRowsUse`). A row that still names it refuses the trash with *A lien record still uses it.* Searching the whole row finds a link in a column nobody listed.
3. A `PATCH` of `trashed`, never a delete, with a note on the file: *Taken off in the app by <name> on <day>.*

Both asks are no-ops on a file already where they would put it. A training account and a twin are refused. The two asks are parsed by `parseTrashAsk` ahead of `parseOfficeAsk`, so the shared parser that other functions hold is unchanged. Drive's refusal is thrown as `Trash failed (<status>): …` and read by `driveFailureOf`, which gains the two shapes.

**The client.** `src/lib/jobs/jobFolderTrash.ts` holds the words, `driveFileIdOfUrl` and `fileTakenOffWords`; `jobFolderTrashIo.ts` holds the calls. `takeFileToTrash` never throws: it answers `{ where: 'trash' }` or `{ where: 'drive', why, retry }`, so the caller's own write is never undone by Drive's mood.

**The run window.** `LienDeskRunModal.removeCopy` awaits the list's write, tells the desk, then asks the trash. `offCopy` holds the file just taken off and where it is. `LienRunMailedCopies` draws the line under the row: *Taken off. The file is in Drive's trash.* with **Put it back**, or *Taken off. The file stays in Drive.* with the reason and, where a second try can help, **Try again**. **Put it back** untrashes the file when it was trashed, then lists it again through `restoreLienMailedCopy`, which reads the list fresh and never lists a file twice. The ask reads *Take <name> off this notice? The file goes to Drive's trash. Drive keeps it there 30 days.*

**Not in this change.** The receipt press (**Take off** and **Replace**), which waits on #8589. Files taken off before today stay where they are: nothing can tell a wrong file from a right one after the fact.

**Tests.** `src/lib/documents/driveTrash.test.ts` (the ask, the row search, the note, Drive's refusals), `src/lib/jobs/jobFolderTrash.test.ts` (the words, the id, the calls and the three outcomes), `lienMailedCopies.test.ts` and `lienMailedCopiesIo.test.ts` (the words and Put it back's write), `LienRunMailedCopies.render.test.tsx` (the line and its presses) and two cases in `LienDeskRunModal.render.test.tsx` (take off, trash, put back; a busy Drive, then a refusal).

**Deploy.** `supabase functions deploy drive-link`. No migration. Against the old function the new client's take-off still stands and the line reads *The file stays in Drive* with the old door's refusal.
