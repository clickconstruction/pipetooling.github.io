# v2.8077 — Before we start: a press that landed is never reported as lost (2026-11-20)

Found by the Fable 5.2 audit of punch list #382 (Before we start). Client only: two hooks and their tests. No migration, no edge function.

## What was wrong

Every press on Before we start goes through one function, `press`, in [`useJobStartChecks`](../../src/hooks/useJobStartChecks.ts) (the job window's Documents tab) and [`useSiteStartChecks`](../../src/hooks/useSiteStartChecks.ts) (the Development page's Schedule look). It ran `await write(io); setLoaded(await read())`. One throw covered both steps, and every caller's catch says the write failed.

So a write that landed, followed by a read that failed (a lost signal, a timeout), was told to the person as a press that was not kept. The screen still drew the list from before the write, and the same press was still there:

- **Use the four** on an empty stage. The four bullets were added, the read after them failed, the toast said *The list was not added.*, and the starter was still on screen. A second press wrote eight bullets.
- **Go**. The Go landed, the read failed, the panel stayed open with the read's reason. A second press wrote a second standing Go, which the database does not refuse. *Take the Go back* then took back only the newest, so the stage still read Go.
- **A tick**. The box stayed empty, and the next press hit the unique index on live yeses and showed a raw duplicate-key reason.

## The fix

In both hooks, `press` now treats its two steps apart:

- A failure of the **write** is still thrown to the caller, who says the press was not kept, as before.
- A failure of the **read after a write that landed** is not thrown. It is caught and kept as the hook's `failure` with `recoveryFailureFromError`, the same call each hook's load effect makes. The section already draws `OfflineRetryPanel` for `read.failure` in place of the list (`JobDocumentsStartChecks`, `DevelopmentScheduleCard`), with Retry on `reload`. A lost signal reads *No connection, so this could not load. Nothing was lost. It loads again when the signal is back.* and reads again by itself.
- `press` then resolves, so a caller closes its panel or its field as after any write. The list that is out of date is not on screen, so no press on it can write a second time.
- A read that lands inside `press` clears a failure left standing, as the load effect does.

## Tests

- [`JobDocumentsStartChecks.render.test.tsx`](../../src/components/jobs/JobDocumentsStartChecks.render.test.tsx): the memory io is wrapped so the read right after `addBullets` rejects once with a fetch-layer error. *Use the four* is pressed. The test holds that no text says *was not added*, the retry panel shows, the starter and its press are gone, one write was made, and after Retry the stage shows exactly four bullets.
- [`useSiteStartChecks.render.test.tsx`](../../src/hooks/useSiteStartChecks.render.test.tsx), new: a Go whose read after it fails is not thrown, the failure is kept with kind `network`, and a reload clears it and shows one Go. A write that fails is still thrown and keeps no read failure. A later press whose read lands clears the failure.

Run both ways: against the hooks as they stood on `main` the new render case failed (*Unable to find role="button" and name "Retry"*) and two of the three hook cases failed (*expected TypeError: Failed to fetch to be null*). With the fix all pass, with the rest of both files and `DevelopmentScheduleCard.render.test.tsx`.

## Not changed

A read that fails for a reason other than a lost signal draws its sentence with no Retry, as the first load of the list always has. Opening the job window or the page again reads again.
