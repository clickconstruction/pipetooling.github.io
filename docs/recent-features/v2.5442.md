# v2.5442 — Messages: the morning reminders the app sends itself, written and switched off (2026-10-13)

Messages, cut 5, PR C of the morning run of the reminders the app sends itself (`BUILD_PLAN.md` → Cut 5 and section 6; section 7's decision 3: per step, off until the owner turns it on). On PR A's reads (v2.5436, `flows/nudgeRunInputs.ts`), PR B's two rows (v2.5438, `20261014012000_messages_nudge_settings.sql`) and the Quo functions (v2.5281). The new edge function is `messages-nudge-dispatch` (`docs/EDGE_FUNCTIONS.md` → messages-nudge-dispatch). Its cron is PR D, a migration of its own, pushed only after the function is deployed.

- **The run**, at 9 AM Central. The cron fires at 14:00 and 15:00 UTC, and `runHourNow` picks the tick that is 9 AM.
  - It reads everyone's flow as the service role, set-wise, and `nudgeRunReads` puts each person together the way their panel does.
  - `planNudgeRun` picks the morning's texts.
  - Each text goes through `sendText` with the purpose `nudge`, the path `quo-send` takes: the opt-out line when a rule says, from its box's number, picked as `quo-send` picks it (R6: the box they last texted on this number, else their kind's, else the company number's). A number that sent STOP to that box is kept back as opted out.
  - Then it writes the `nudge_sent` row (`sent_by` `'app'`) and the thread's event line, keyed so a retry writes nothing twice.
- **A dry run** (`{ "dry": true }`, the cron secret or a signed-in dev, any hour) answers the texts as they would go, every reminder kept back with why, and the summary. It sends nothing and writes nothing.
- **The summary** (`src/lib/flows/nudgeRunLog.ts`, `runSummary`) is what the owner reads first. It is kept in `app_settings` `messages_nudge_last_run_v1`: the texts that went, the reminders kept back counted by why, the texts that did not go with their words, who could not be read, and that customers wait, all in plain words (*No text went. 12 reminders were kept back because the app does not send that step yet.*).
- **Customers wait** until the run can read their page. `customer_portal_views` and `customer_portal_papers` are the office's alone, so the run leaves customers out and never texts one off a partial read. Widening the two reads is a migration of its own, if the owner turns a customer step on.
- **Two switches** gate a text: the step's own, `{}` as it ships, so every step is off and every run sends nothing, and Settings → Phone and texts → **Send texts**, which `sendText` checks. While Send texts is off, `sendText` answers `textsOff`, and the run counts that text and the rest as kept back, never as texts that did not go.
- **The copy of the kernels** (`_shared/gcKernels/`) gains the flow kernels the run needs, 106 files from 93, and `messages-nudge-dispatch` joins its importers. To keep the copy loadable, `nudgeRunInputs.ts` takes `firstName` from `contacts/names.ts`, and `quickReplies/kernel.ts` and `flows/facts.ts` take their `ContactKind` type from there, not from `contacts/kernel.ts`, which reaches `customerSimilarity.ts` and an edge file. `APP_SENDS_SETTING_KEY` is now `appSettingsKeys.ts`'s. The dev-mcp catalog names the new function, so `check_edge_boot` can probe it.
- **Tests**: `nudgeRunLog.test.ts` (8) covers the 9 AM tick in summer, in winter and on both change days, the summary's counts and order, a dry run, Send texts off counted as kept back, the refused cap, and every sentence against the plain-words rules. `edgeKernels.test.ts` holds the regenerated copy and its importers. The function was type-checked against the copy with the Deno imports stubbed.
- **What customers see** places the reminder on the company-number text steps, `gc-text` and `sub-text`, as it places `quo-send` and the webhook's answer (`customerSurfaceRegistry.ts`). It is the same text, opt-out line and thread.
- **One rule, one home**: the flow panel (`useFlowPerson`) now names a person with `flowFirst`, the rule the run uses, so the panel and the run call a person the same.
- **Deploy**: `supabase functions deploy messages-nudge-dispatch` and `dev-mcp` (its catalog), after `quo-send` and `quo-webhook`, then PR D's cron.
