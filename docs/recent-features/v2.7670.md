# v2.7670 — Trips: the dev seat reads a site's trips and files one (2026-11-17)

Punch list #379, PR 4 of nine: the dev seat. Three verbs on dev-mcp (server 0.99.0, 121 write verbs): `read_trips`, and `plan_trip` then `apply_trip`. No migration and no screen. The table and its one write door, `trip_save`, are PR 2's.

## Why

The first three PRs give a working Trips look. A site that already has a year of trips has them in a ledger somebody kept by hand. This PR lets a dev's agent file those trips on the owner's word, one plan at a time, and read back what is kept.

## What landed

- **`read_trips(development_id | job_id)`**. The trips kept on a development, as the reader under RLS, in the order they went out. Each trip comes with its first and last day, where it stands (`planned`, `out`, `back`), its days by kind, its people with their own days, what it was for, who asked, how it went, billing, the jobs its work goes on, and `via` and `agent_label`. With `job_id` it reads the trips a job with no development holds by itself, and the trips whose work goes on that job. One GET a page: each `trips` row carries its `trip_people` and `trip_jobs`, the way the Trips look reads them.
- **`plan_trip(trip)` then `apply_trip(trip, plan_hash)`**. A trip saved whole through the app's own `trip_save(p, p_dry_run)`, as the dev, with `via = 'mcp'` and the robot's `agent_label`. The verbs ride the shared plan and apply block in `dev-mcp/index.ts`, the way a History line does.
- **`supabase/functions/_shared/devMcpTrips.ts`**, the one new kernel. It is pure: the reads come in through a reader.
- **The rules are reused, not written twice.** `src/lib/trips/tripDays.ts` joins the kernel copy (`scripts/edge-kernels.mjs`), so where a trip stands, its span and its counts are `tripStanding`, `tripSpan` and `tripDayCounts`, the same functions the look calls.

## The shape of a trip

`{ development_id | job_id, people: [{ name, days, person_id?, user_id? }], agent_label, id?, purpose?, asked_by?, asked_who?, asked_how?, outcome?, billing?, job_ids? }`.

Days come two ways, and both become the stored form:

- an object, `{ "2026-10-30": "road", "2026-10-31": "site" }`;
- a list of runs, `[{ from: "2026-10-31", to: "2026-11-03", kind: "site" }]`. A run with no `to` is one day. A later run wins a day two runs name. A run is at most 120 days.

Refused in plain words: a day that is not a real calendar day, a kind outside `ready`, `road` and `site`, a person with no name, the same name twice, nobody with a day, neither a development nor a job, both of them, a run longer than 120 days, words longer than the table holds, and a development, a job or a `person_id` nobody can find.

## Three things the server does before the dry run

They happen the same way at plan and at apply, so the two hash alike.

1. **The days** are read into `{ day: kind }`.
2. **A stable id.** `trip_save`'s dry run makes a random id when `p.id` is absent, and the plan hash covers the dry run's reply. A plan and its apply would never match. So a trip with no `id` gets one from `tripStableId`: sha256 of the trip as it was asked for, with its people in name order, written as a uuid with the version and variant bits set. The id is read from the ask before the roster is laid over it, so the same ask is the same trip whoever has joined the roster since.
3. **People by name.** A person with no `person_id` is looked for among the roster's unarchived `people`, by name, trimmed and whatever its case. Exactly one match fills `person_id` and `user_id` (`people.account_user_id`). No match, or more than one, leaves a name alone. The plan says which for each person: *on the roster*, *a name alone: not on the roster* or *a name alone: two people have this name*. A `person_id` the call gives is kept, must name someone, and fills a missing `user_id`.

The development or the job is read as well. `trip_save`'s dry run does not look at it, so a wrong id would otherwise fail at the write on a foreign key.

## What the plan says

The database's own dry run answers `would: add | change`, the trip's id, the counts and the first and last day. Beside it, and never inside the hash, the plan names the site or the job, where the trip would stand today, each person with their days by kind and how they were tied to the roster, what it was for, who asked, billing and the jobs. It also names any day one of its people already has on another trip kept in the same place, since that is most often the same trip filed again with a word changed and no id.

## One apply per plan

`apply_trip` is in `stateGuarded`, so the call log's one-apply rule is not asked. The database's own answer holds it:

- A new trip's plan says `add`. Once it lands, the same payload's dry run says `change`, the hash no longer matches, and a second apply is refused as a plan mismatch.
- A change applied twice saves the same trip over itself. No second thing is made.
- The log's rule would only get in the way: it would refuse a trip deleted in the app and filed again, and a trip put back the way it read before.

One gap is left open and written down: `trip_save`'s dry run answers counts and no before image of a trip it would change. A trip edited in the app between a plan and its apply is replaced without a refusal. Closing it is a change to the dry run's reply, which is the table's.

## What a trip never does

Nothing here names a clock row, a bill or a cost. There is no delete verb: deleting a trip is done in the app. Only a dev's own key writes, and `view_as` refuses both write verbs as it refuses every other.

## Housekeeping

- `SERVER_VERSION` 0.99.0. The instructions count one hundred and twenty-one write verbs, fifty-three of them over twenty-two RPCs. `trip_save` is the first of those the database does not gate to devs. It is the app's own door, open to the office roles, so the write block's own dev check is what holds the seat to a dev.
- The three trip tables are younger than the generated catalog. Until a types PR brings them in, the server reads them by the kernel's own column lists (`TRIP_TABLE_COLUMNS`).
- The call log keeps a trip's home, its names and a count of each person's days, so a long crew's days never push an apply's `plan_hash` past the log's cut.
