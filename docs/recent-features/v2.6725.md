Send one from their thread.* under a text that went. The tie (`src/lib/estimates/acceptLinkTie.ts`, v2.5697) matched only `/estimate/accept?t=` links and hashed their token against `estimates.public_token_hash`, the emailed link's hash; the text's link has been a share link since v2.6657 (PR 1), whose hash sits in `estimate_share_links.token_hash`, so every text since then had read as none.

## What changed

- **The tie reads both shapes** (`acceptLinkTie.ts`): `shortCodesIn` reads the code off `https://<host>/e/<code>` (a host is required, so a bare `/e/` in prose is no link; lower-cased as the `portal-link-shell` Worker forwards it, since `share_estimate_link` mints lowercase), `linkTokensIn` reads both shapes in the body's order, and `textsCarryingLink` takes the estimate's share hashes beside the emailed link's `tokenHash` and keeps a text whose token hashes to any of them. A PR 1 or PR 2 text (the share token or the ten-letter code on the accept page) is tied the same way. Tests for both shapes, the capitals, the trailing period and the bare path.
- **The share links' hashes** (`shareLinkHashesIo.ts`, new): `estimate_share_links.token_hash` for the estimate, every link it ever made, stopped or not (the text went either way). The table grants SELECT to a signed-in user over an estimate they can read (migration `20261019050000`), so the office needs no new read.
- **What went** (`whatWentIo.ts`): the body filter admits `/e/` beside `/estimate/accept` (an `or` in place of the `ilike`), the share hashes are read with the channels and the texts, and the tie takes them. `whatWentIo.test.ts` (new) holds the short-link text beside the emailed one, the no-estimate path and a refused read naming its reason.
- **The job tie** (`estimateTextsTieIo.ts`): `tieEstimateTextsToJob` takes `estimateId` (the Estimates page's Create job passes `row.id`), reads the same hashes best effort, and the texts on the short link move onto the job the estimate becomes, as the emailed link's did since v2.5706.
