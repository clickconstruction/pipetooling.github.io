# v2.3494 — New Sub Labor: the Date of Labor box reads as editable (2026-09-15)

Client only; no migration, no edge function, no change to what the date means.

Taunya, entering a sub's invoice: *"this one isn't super important but I need to change the date to match the date on the sub invoice."* She could already change it. She did not know she could.

## Why it read as printed

On the **new-sheet** path the control is not a visible input. `JobsSubLaborFormModal` renders the short date as centred text with the real `<input type="date">` stretched over it at `opacity: 0` — the v2.1628 trick, because a native date input cannot render the MM/DD/YY form the office reads. Hiding the input also hides the browser's calendar indicator, so every affordance went with it. The **Service type** `<select>` sitting immediately to its right keeps its native arrow, so on one row one control advertises itself and the other does not.

The **edit** path was never affected: it renders a plain native date input, indicator and all. That asymmetry is now deliberate and pinned by a test rather than incidental.

## What changed

- `src/index.css` — new `.subLaborDateBox` class: hover darkens the border to `var(--text-muted)`, `:focus-within` takes the action blue with a soft ring, and the mark tracks both states. Hover and focus-within cannot be expressed as inline styles, and this file already carries that pattern (`.myInboxRow:focus-within`), so the rules live here rather than in a component `<style>` block. Honors `prefers-reduced-motion`.
- `src/components/jobs/JobsSubLaborFormModal.tsx` — the non-editing branch only: the class, an inline 15px calendar mark (`aria-hidden`, `currentColor`), `justifyContent` `center` → `space-between`, `minWidth` `9ch` → `11ch`. The overlaid input keeps its `aria-label="Date of Labor"`, so the field is still announced once.
- `src/content/help/record-sub-labor-on-a-job.md` — the date had one clause ("Date and service type live here too"), which is part of how this stayed invisible. It now says the box is a picker, names the calendar mark as the tell, and says the date is what files the cost in the right week.

## What was deliberately not done

- **No change to `job_date`.** It stays the cost date for sub labor, read by about 25 files including Job Summary, Crew P&L, the Bridge, People Review, the team board week query and the charges timeline. Nothing moves in any of them.
- **No revert to a plain native date input** on the new path — that would undo v2.1628 and lose the short display form.
- **No invoice date or invoice number field.** The sheet still has `invoice_link` and nothing else; giving the invoice its own date is a separate, larger question, since a sub who invoices in October for September work must not push cost into the wrong month.
- **No weekday on the date**, and no change to the default. Both were on the table and both were cut to keep this pass to the affordance.

## Caught by the live pass

The first cut left `border: 1px solid var(--border-strong)` in the element's inline style. An inline shorthand outranks any class rule, so `:hover` and `:focus-within` could set the ring and the mark's color but **never the border color** — the state change was half-drawn and looked like a flicker. Unit tests could not see this: jsdom does not resolve `:hover`, and both rules exist either way. The border moved into `.subLaborDateBox`; the inline style keeps layout only. Both files carry a comment saying why, because the next person to "tidy" the border back inline would silently break it again.

## Verified

Typecheck, lint, full test run (1,429 files, 12,043 tests), theme token check. Four new render-smoke tests in `JobsSubLaborFormModal.render.test.tsx`: the mark is present and `aria-hidden` while the input keeps its label; the MM/DD/YY form still renders; a typed date reaches the input and redraws the short form; and the edit form has no `.subLaborDateBox`, pinning the scope.

Live pass on prod data at Jobs → Subs → Pay → New Sub Labor, measured from computed style rather than by eye:

| | Border | Mark |
|---|---|---|
| Rest | `--border-strong` | `--text-muted` |
| Hover | `--text-muted` | `--text-700` |
| Focus | action blue + 2px ring | action blue |

Both themes confirmed through the app's own override, not a forced attribute: light rest reads `#aab2bd` / `#6b7280`, dark reads `#4b5563` / `#9ca3af`, and focus is the same blue on both grounds. `elementFromPoint` over the mark returns the date input, and a real click on the mark focuses it, so tapping anywhere in the box still opens the picker — the mark never intercepts. Setting 2026-09-11 redrew the box as `09/11/26`. At 375px the page has zero sideways overflow and the row wraps, with the box 111px wide.
