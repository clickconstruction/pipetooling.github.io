# v2.6811 — The dev seat says a new job starts at Working (2026-11-09)

Seen on the first real use of `plan_job` → `apply_job` (v2.6790): fifteen jobs made from the seat for one customer. Every plan said `readiness.status: "waiting — the Pipeline moves it…"`, every apply said the job "is on the Pipeline at Waiting", and all fifteen rows read back from `jobs_ledger` with `status: working`.

**The row was right and the words were wrong.** The verb's insert names no `status`, as `JobFormModal.createJob`'s insert names none, so the row takes the column default. The baseline's default was `waiting`; `20260722264000_new_jobs_start_working.sql` moved it to `working` (no trigger sets a status on insert). v2.6790's words were written from the baseline.

- **`supabase/functions/_shared/devMcpJobs.ts`**: `newJobDryRun`'s `readiness.status` reads `working — a new job starts there (the table's default since 20260722264000)…`; `jobAppliedWords`' `next` reads `… is on the Pipeline at Working (a new job's default)…`. What the verb writes is unchanged.
- **`supabase/functions/dev-mcp/index.ts`**: `apply_job`'s description says the Pipeline shows the job at Working. **`SERVER_VERSION` is not moved by this PR**: no verb, argument or reply shape changed, and five open PRs each move the version and its pins in the tests.
- **Docs**: the `plan_job` row of `docs/dev-mcp/README.md`, the #293 card's two lines, and v2.6790's release note, which told the office the job starts at Waiting.
- **The guard** (`src/lib/devMcp/devMcpJobsStage.test.ts`): reads the newest default on `jobs_ledger.status` out of `supabase/migrations/`, and holds the plan's words, the apply's words, the tool description and the README row to that stage, with the plan naming the migration. A later move of the default fails the test until the words follow. It also holds that the row carries no `status`.
