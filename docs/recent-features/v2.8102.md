# v2.8102 — HR files: a plan taken off is not applied, an entry plan commits to what it replaces, the log keeps the hash (2026-11-20)

The audit of punch list #315, findings 1 to 3. The owner, 2026-11-20: "Yes, build them". `dev-mcp` 0.122.0. No migration, no new verb.

## What was wrong

Upgrade 3 of #315 keeps an agent's plan on the server for the owner's yes, so another session can apply it days later. Three things the card says of a kept plan did not hold.

- **A dropped plan could still be applied.** The apply path never read `dev_seat_kept_plans` before it wrote. `settleKeptPlan` ran after the write and only for a waiting row. A session that had read the plan, or read it again by id (`list_kept_plans { id }` answers the arguments and the hash of a row in any state), could call `apply_hr_entry` and file it. `drop_kept_plan`'s description said the row "is never applied".
- **A kept `plan_hr_entry` never went stale.** The hash is the payload plus the dry run's reply, and `dev_hr_entry_write` replies with counts and lengths. A plan that rewrote the narrative hashed the same whatever the narrative held, so it could be applied over a text saved after it was planned.
- **The one-apply rule could not see a long plan.** `loggableArgs` replaced a row past 4,000 characters with `{ truncated, preview }`, and `priorApply` matches on `args->>plan_hash`. On the live log 13 of 36 landed `apply_hr_entry` rows had no hash key (15 of 232 `apply_history_entry` too). With a plan that never goes stale, two sessions applying one kept plan would file every entry twice. `priorApply` also ignored a failed read of the log.

No entry is on a file twice and no dropped plan was applied: read on the live rows by count, 2026-11-20. Every kept plan so far is on the test person.

## What changed

- **`keptPlanOff`** (`dev-mcp/index.ts`, over `keptPlanOffQuery` and `keptPlanOffWords` in `_shared/devMcpKeptPlans.ts`). Once the dry run matches, `apply_hr_entry`, `apply_person_doc` and `apply_person_report` read the kept plans under their verb and hash that wait, were dropped or went stale. Only rows whose arguments are the arguments sent count. One still waiting lets the apply through, so a plan kept again after a drop is a new ask. Otherwise the newest dropped or stale one refuses the apply, with who dropped it and why. A read that fails refuses the apply.
- **`hrEntryReply`** (`hrEntryReplacedKinds`, `withReplaces`). A plan that sends `summary`, `narrative` or `narrative_append` gets `replaces: { summary?, narrative? }` joined to the dry run's reply before the hash, at plan and at apply: when each document last changed, as the dev reads `person_files`, null for one not written yet. A plan of entries alone is untouched and hashes as before, so no plan in a session breaks.
- **`loggableArgs`** keeps `plan_hash` on a cut row, lower-cased as the hash is compared. **`priorApply`** throws when the log cannot be read, which refuses the apply.
- `settleKeptPlan` says so when it cannot read the kept plans after an apply that landed.

## What this does not fix

- Rows cut before this deploy have no hash. A plan applied before today and applied again unchanged is still let through, for the verbs whose log row is their arguments whole.
- Another dev's key cannot apply a kept plan: the dry run's reply carries the keeper's name, which is in the hash. The owner's call (who may apply) comes first.
- The audit's other findings (the case item guard, the counter and a title's number, the kept-plan door's counsel-only check, the strip's standing on a day ahead) each need a migration or his choice.
