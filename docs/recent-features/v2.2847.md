# v2.2847 — Labor tab waits for the bid's version before loading; no cost-estimate row minted just by opening (2026-09-05)

Journey-map Phase 4, Tier-1 #10 (private repo `pipetooling-journey-map`, `docs/journeys/takeoff-to-price.md` rows **F1 / T1 / N1**, cluster C44). Will's decision 17 (2026-09-05): records are written only after an explicit user commit.

## The bug

Count rows are per bid Version (`20260823034820_count_rows_per_version.sql:114` moved Base rows onto a Base version; every later insert carries the active version), and the engine's takeoff loaders read the active version synchronously from a bid-tagged ref (`selectedBidVersionIdRef`, `resolveTaggedVersion`). The Labor/Takeoffs effect in [`Bids.tsx`](../../src/pages/Bids.tsx) (search `J11-F1`) called `loadCostEstimateData` the moment a bid was picked — before that ref pointed at the new bid — so `activeVersionIdForBid` returned null, `applyVersionFilter` emitted `.is('bid_version_id', null)`, and the count-rows read came back empty on **every versioned bid**: "Add fixtures in the Counts tab first." with no HOURS table, indefinitely. Only the Counts and Takeoffs engine effects resolved the version first (v2.2132); the Labor effect's deps omitted `selectedBidVersionId`, so the resolve the Counts effect performed a moment later never re-fired it. Any tab round-trip healed it (the effect keys on `activeTab`). The deep-link `?bidId=` path looked fixed only because `laborBookVersions` (a dep) arrived after the ref resolved.

Same load path, both branches, also inserted a `cost_estimates` row (`ensureCostEstimateForBid`) — including from the false-empty frame, and from a Takeoffs visit.

## The fix

- **Effect gate (deps + resolve, mirroring the Counts effect)** — the `Bids.tsx` effect now adds `selectedBidVersionId` to its deps and, when `shouldLoadCostEstimate({ bidId, resolvedFor: selectedBidVersionIdRef.current, versionId })` is false, resolves the version itself (`loadBidVersions` → `pickActiveVersion` → `setSelectedBidVersionId`) before loading, with a `cancelled` flag like the Counts effect. `loadAfterResolve` decides whether to load directly or wait for the state change to re-run the effect — setting the same value React already holds (Base → Base across two unsplit bids) schedules no re-render, so waiting would leave the tab on the skeleton forever. Chosen over lifting the resolve into `loadCostEstimateData` because the effect owns cancellation and the pattern already exists twice in the engine; `refreshAfterCountsChange` and `handleLaborBookVersionChange` call the loader only after the ref is resolved.
- **Skeleton** — the engine tracks `costEstimateResolve: PricingResolveState` (begun/settled inside `loadCostEstimateData`; a same-bid reload does not re-begin, so a labor-book change never flashes). `Bids.tsx` derives `laborPanel = laborEmptyState({ resolved, rowCount })` and passes `panel` to [`BidsLaborTab`](../../src/components/bids/BidsLaborTab.tsx), which renders the v2.2367-style `bid-resolve-*` skeleton ("Loading this bid's fixtures and hours…") for `'skeleton'`; the sentence renders only for `'empty'` (a settled bid with zero rows).
- **Lazy mint** — `loadCostEstimateData` no longer calls `ensureCostEstimateForBid` on the zero-rows branch (`shouldMintCostEstimateOnLoad`), so a bid with no fixtures — including the old false-empty frame — gets no `cost_estimates` row from Labor or Takeoffs. **Residual, by design:** a bid whose resolved version *has* count rows still mints on load, because the HOURS table is built from `cost_estimate_labor_rows` (which need the parent row) and Pricing reads those rows for its margins; moving labor rows in-memory until first edit is a labor-row model change and out of scope. Write-time entry points that mint: `ensureCostEstimateForBid` (PO creation in Takeoffs), and the with-rows sync (first fixture added → `refreshAfterCountsChange`).
- **Kernel** — [`src/lib/bids/laborTabLoadGate.ts`](../../src/lib/bids/laborTabLoadGate.ts): `shouldLoadCostEstimate`, `loadAfterResolve`, `laborEmptyState`, `shouldMintCostEstimateOnLoad`, with colocated tests. Engine seam test [`useBidPricingEngine.laborLoad.render.test.tsx`](../../src/hooks/useBidPricingEngine.laborLoad.render.test.tsx) (recording supabase stub): count rows filter on `eq('bid_version_id', <active>)` not `is(null)`; zero rows → no `cost_estimates` insert, `ensureCostEstimateForBid` → exactly one; rows → one insert on load + labor-row sync; `costEstimateResolve` settles `ready`.
- **Telemetry** — `recordNavClick(userId, role, 'labor_tab_empty_state_shown', '/bids?tab=labor&rows=N&version_resolved=B')` once per bid the empty state is shown for (`ui_nav_clicks`). `version_resolved` is true by construction; a row with `false` means the bug is back.
- `loadCostEstimateCountRows` now returns `null` on a read error (was `[]`, indistinguishable from "no fixtures"); the loader settles the lifecycle as `error` and the error banner carries the message.
