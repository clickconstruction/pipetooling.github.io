# v2.6235 — Making a new bid version works again (2026-10-31)

A prod regression found by the live test of the robot fixtures copies, fixed in one migration, `20261031015000_bid_copies_pull_rows_definer` (`docs/migrations/20261031015000_bid_copies_pull_rows_definer.md`).

## What broke

`20261031010000_robot_fixtures_copies` (#6591, v2.6188, punch list #221 PR 3) carried `bids_count_rows.plan_tag` through the copies. It also taught the count-row clone to re-key the robot's take onto the cloned rows, and the adopt to move the robot's pull with the rows. Each did it with a plain `UPDATE` of `bid_fixture_pull_rows` or `bid_fixture_pulls`, inside a SECURITY INVOKER function. `20261030230000_robot_fixtures` (v2.6180) had closed both tables to writes from signed-in users on purpose. Postgres checks that privilege when the statement starts, even when no row matches. From the push at 2026-10-31 05:27 UTC, every new version and every adopt failed for every signed-in user with *permission denied for table bid_fixture_pull_rows*. That covered Add GC, Try a variant, the Pricing tab's new version and the Workbench's adopt.

**How it was found.** The plan-tag copy session ran the live test as the dev on ZZ Test bids b559 to b561. A duplicate kept its plan tags. `materialize_bid_version` worked, and `create_bid_version` answered 403. Every ZZ row was deleted. The bid copies SQL bed would have caught it, but it is not in `scripts/sql-beds.txt`, so CI does not run it.

## What changed

- **Two SECURITY DEFINER helpers**, the shape the robot-fixture RPCs already have. `robot_fixtures_follow_clone` re-keys the bid's pull rows only onto that bid's rows on the target version, and does nothing for a signed-in caller who cannot price the bid. `robot_fixtures_follow_adopt` moves the pull only into a version of the package, only once the adopted bid has no count row left, and refuses a caller who cannot price both bids. Neither is executable by `anon`.
- **`clone_count_rows_to_bid_version` and `adopt_bid_as_version`** call the helpers in place of the two updates. Their bodies are otherwise verbatim from `20261031010000`, and v2.6188's rule is unchanged.
- **Docs**: `ACCESS_CONTROL.md` names the two helpers beside the five robot-fixture RPCs. The comment in `bidCopySql.test.ts` names them too.

- The take re-key and the adopt's move need a robot pull, which only the service role writes, so the live check covers the version and the tag, not the re-key.
