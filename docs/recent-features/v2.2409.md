# v2.2409 — Star-delete guard checks every packet, plus a DB backstop (2026-08-27)

Incident (2026-08-27 ~4:38 PM): price_book_versions 69491f86 on BP384 WAS the
NORTHSTAR packet's `starred_price_book_version_id` and was still deleted through
the Price modal. The Delete guard compared the scenario against
`customerFacingPricingId` — the VIEWED packet's ★ — but the scenario card row
falls back to the bid-wide unscoped list when the viewed packet has no scoped
scenarios (legacy pointers, v2.2404), so a session viewing packet A could open ✎
on packet B's ★ card with Delete enabled. The FK is ON DELETE SET NULL, so the
DB silently nulled NORTHSTAR's ★.

- New kernel `src/lib/bids/starredScenarioGuard.ts`:
  `versionStarringScenario(bidVersions, scenarioId)` finds the packet whose ★ is
  the scenario regardless of which packet is viewed;
  `scenarioIsCustomerFacing(...)` adds the unsplit-bid bid-level fallback.
  8 unit tests, including the exact incident shape.
- `BidsPricingTab` Price modal: `isBase` is now "any packet stars it OR it's the
  viewed customer-facing id"; when the starring packet isn't the viewed one, the
  disabled tooltip names it ("<GC>'s letter is built on this price — star
  another price for that packet first.").
- `confirmDeletePricingVersion` gets the same check as a belt — it also covers
  the pricing-name form's "Delete version" button, which had no star guard at
  all.
- Server backstop: migration `20260827230000_block_delete_starred_price_book_version.sql`
  adds a BEFORE DELETE trigger on `price_book_versions` that raises while any
  live packet stars the row (SECURITY DEFINER so RLS can't hide the starring
  packet). Cascade deletes of a packet or a whole bid still work: the
  referencing row is gone before the cascade reaches `price_book_versions`.
