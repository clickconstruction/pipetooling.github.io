# v2.4803 — A check Stripe already holds moves to the right job in one press (2026-10-07)

Client plus two edge functions redeployed (`reverse-stripe-invoice-out-of-band-payment`, `void-stripe-invoice-for-revert`); no migration. PR 2 of punch list #98 (`to-dos/held-stripe-marks/README.md`); PR 1 is [v2.4801](v2.4801.md). The stuck case: a check marked paid in Stripe before v2.4801 (job 186, Taunya's check), or after the seven days. Stripe never reopens a paid invoice, so the repair is still a credit note and a fresh bill (v2.4082) — but it is one press now, the money goes where it belongs, and the trail tells the truth.

## What changed

- **Move to job… on a Stripe-held row.** [`JobFormPaymentLine`](../../src/components/jobs/JobFormPaymentLine.tsx) offers it when `stripeHeldMoveOffered` holds — Stripe holds the bill paid by our whole-bill mark (`stripeHoldsPaymentReason` = `paid_in_stripe`) and the bill is Paid here; a credit-note part payment keeps Undo part payment instead. The sub line reads *reverses the Stripe mark; this bill goes out again*.
- **The Move window runs four steps** ([`JobPaymentMoveModal`](../../src/components/jobs/JobPaymentMoveModal.tsx), `confirmHeld`): the credit note (`reverse-stripe-invoice-out-of-band-payment`, whose RPC takes the payments off the bill), the send-back (`sendBackStripeBilledLine` → `void-stripe-invoice-for-revert`, the row gone, the job Ready to Bill), the landing on the other job (`mark_invoice_paid` on its one open bill with room — held for seven days like any check — else a plain `jobs_ledger_payments` row under Other money), and the `moved` event on `jobs_ledger_payment_events` with the snapshot and the landed row's id. The window lists them under *What happens, in order* before the press (`stripeHeldMoveSteps`), picks the landing when the destination is picked (`planHeldLanding`), and when a step after the credit note fails it shows what is done and what is left by hand (`stripeHeldMoveStoppedWords`: *Open View bill on J186's Billed row and press Check didn't clear · send back…, then record the $6,200.00 check 1042 dated 2025-10-28 on J922 by hand*). The reverse step writes nothing on failure, so it is a plain error. Kernel [`stripeHeldPaymentMove.ts`](../../src/lib/jobs/stripeHeldPaymentMove.ts).
- **The reason travels.** `stripeHeldMoveReason` builds *Moved to J922 · wrong job*; the reverse function writes it as the whole-bill credit note's memo (it had none), and `void-stripe-invoice-for-revert` takes an optional `reason` that replaces *payment did not clear* in the note it would issue and in the `removed` event's `oob_mark_reversed:` reason. `invokeVoidStripeInvoiceForRevert` / `sendBackStripeBilledLine` carry it; every other caller is unchanged.
- The window takes `stripeModeForBilling` (the Edit Job form passes the role's mode, as it does to the Undo window).

## Decisions taken

- **The landing is held, not closed.** A check that moves onto a Stripe bill is recorded there the way Mark Paid · Check records since v2.4801 — the ledger row only, Stripe closed by the sweep seven days later — so the same mistake twice is still one press.
- **One open bill with room, else the job.** Two open bills, or none that fits, land the check under Other money with no bill picked; a person pins it. The window says which before the press.
- **Client-run steps, as the Undo window runs them.** The to-do had planned one server-side function; the two existing functions plus one RPC and one insert, in the order the Undo window already chains, needed no new server surface. Each stop after the credit note leaves words, never a silent half-move.
