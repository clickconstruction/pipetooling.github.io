# v2.7651 — HR files: an agent reading a file is told every part of it and how to open each (2026-11-17)

The owner, 2026-11-17: "the first thing we need to do is decide if we should give agents a prompt when they go to look at HR files to make sure they can see everything and can find everything easily." A session read one large file through the dev seat as the test, and the answer was a manifest from the tool with the prompt beside it. The owner: "Yes, build it." Server 0.97.0. No migration, no new verb, nothing written to any file.

## What the read showed

- The server's instructions said `get_person_file` reads a file whole. On a large file it is shortened, and so is `get_case_brief`. Neither said in one place how many of each thing the file holds.
- The instructions never named `get_case_brief`, and a client shows only their opening.
- No reply gave a count of every part, so a reader could not tell what it had not seen.
- `search_case` does not reach the papers, licenses, write-ups or hours statements, and did not say so.
- A search for a full name found no one where the roster holds a first name alone.

## What changed

- **`get_case_brief` opens with `reading` and `manifest`.** `reading` is the rules for an HR file and the receipt an agent ends with. `manifest` is one line a part: its whole count, its counsel-only count where it has one, and `open`, the call that reads it on. Both come from `supabase/functions/_shared/devMcpPersonManifest.ts`, a pure kernel, and no fit step touches them.
- **The Timeline's numbers are `get_person_file`'s own.** The brief runs that verb's reads and kernel for the papers, statements, licenses, write-ups, attendance and field reports, and reads its new `tally` and its line counts. A count in the manifest is the count that verb answers.
- **What only the manifest needs is read light.** Six reads of ids alone: the file index, the case items and log, the standing, the kept plans, the tagged mail. Each is fail-soft into its own part: `count: null` and `held`, never zero.
- **`get_person_file` says `read_first`** and carries `tally`, the files and the rows behind the lines, never shortened.
- **The instructions send an HR read to the brief in their second sentence**, and no longer say whole.
- **`find_person` tries each word** when the whole name matches no one, and says so in `note`.
- **`search_case`'s `note` opens with what it does not search.**
- **The brief's theme counts read a kept mark as kept.** A mark the agent proposed and a dev then kept was still counted under `proposed`, so a file whose marks were all kept read as waiting. The count now follows the app's own rule, `markIsProposed`: proposed, not kept, not removed.

## Checked on a real file

The branch's kernel was run against one large file through the deployed door's reads, read only, before the deploy. Its counts matched a count made by hand the same day, and the theme counts matched the file's own notes.

## The guard

`MANIFEST_PART_OF_SOURCE` names a manifest part for every source the Timeline draws. `src/lib/devMcp/devMcpPersonManifest.test.ts` fails when the kernel gains a source the manifest lacks, and holds the rules to general words: no year, no figure, no id.

## What it costs

The brief reads the file's Timeline sources a second time, through `getPersonFile`. On a large file that is two more pages of entries and of evidence. The big-case tests count the reads.

## Deploy

`supabase functions deploy dev-mcp` from `main` after the merge. Until then the seat answers as the version deployed before it.

## Not built

- A skill for coding agents. The rules reach every client through the tool.
- A count of the files inside a person's Drive folder. The manifest counts the record folders and names one, whose parent is the person's folder.
- A fence on counsel-only material. The seat reads it since v2.6986. The rule in `reading` is held by the reader.
