# v2.7600 — App updates: the automatic reload looks again when it would fire (2026-11-17)

Client only. No migration, no edge function.

## The incident

2026-11-17, during the live walk of punch list #368. A tab opened onto a build one behind. Its first paint was quiet, so it decided an automatic reload at 16:48:04 UTC (the stamp in `sessionStorage['pipetooling-auto-reload-last']`). At 16:48:06 a press began a write to the `bid-plan-set-files` edge function. The reload landed inside that write. The function finished its work, a Drive folder and a `bid_plan_sets` row, but the page that asked was gone: the edge log shows the OPTIONS and no completed POST, and the files that should have followed were never sent until a second press. The walk's driver was a fast script. A person who opens the app and taps Clock in or Send within a few seconds of the page loading meets the same gap.

## Why

`tryAutoReload` asked [`decideAutoReload`](../../src/lib/autoReload.ts) once. `applyUpdate` then posted SKIP_WAITING and reloaded when the new worker took control, or after a fixed 4 seconds, with no second look. Whatever began in between was cut off: a write, a dialog, a field taking the cursor.

Reading the gap turned up a third reloader. `vite-plugin-pwa`'s prompt mode adds its own listener once an update has been announced, and reloads on workbox-window's `controlling` event when `isUpdate` is set. workbox-window 7 sets `isUpdate` for every page that loaded under a worker and dispatches `controlling` on every `controllerchange`. So the plugin reloaded this tab on the worker change whatever the component thought, and it reloaded **every other open tab** the moment one tab took the update, with no look at what those tabs were doing. The comment in `UpdatePrompt` that said the plugin's reload does not fire for a polled update described an older workbox.

## What ships

- **[`autoReload.ts`](../../src/lib/autoReload.ts)**: `decideReloadLanding`, the second look, pure. It answers `reload`, `wait` (with when to look again) or `stand-down`.
  - The pill's own Reload press is held by nothing but the worker: it reloads on the worker change or after `RELOAD_FALLBACK_MS` (the old 4 seconds).
  - An automatic reload stands down to the pill when the page was touched after the decision, a dialog is open, a field is focused or a component holds unsaved work. It stands down at once, before the worker has taken over.
  - A write in flight is waited out, never cut. After it comes back the page must stay quiet `LANDING_SETTLE_MS` (1.5 seconds), because a write is often the first of a chain, a row and then its files. A write still in flight `LANDING_WAIT_MAX_MS` (30 seconds) after the decision is not waited out: the pill takes over.
  - The touch rule covers every moment, not only first paint. The press that caused a route change comes before the decision, so only a touch after it counts.
- **[`UpdatePrompt.tsx`](../../src/components/UpdatePrompt.tsx)**: `land` asks the kernel when the worker changes, when the fallback runs out, when a write begins or comes back (`subscribeUnsavedWork`) and on a touch (capture phase, before the press's own handler). `applyUpdate(asked)` only starts the reload.
  - One `controllerchange` listener is added before `registerSW` adds workbox-window's. While an update is known here it takes the event and stops it (`stopImmediatePropagation`), so the plugin's reload never fires and the second look owns every reload. With no update known (a first install claiming the page) the event is left to workbox.
  - A worker change with no reload pending here reloads nothing: another tab took the update, or this tab stood down. The pill stays, and the next quiet moment reloads with no gap, because the worker has already switched. The pill's Reload in that state reloads at once.
  - SKIP_WAITING cannot be taken back, so a stood-down tab may run the old build under the new worker until its next quiet moment. A chunk it then misses has its own recovery (`chunkLoadRecovery`).
  - The loop guard's stamp is now written when the reload fires, not at the decision, so a decision that stood down does not block the next quiet moment for a minute.
  - A later `onNeedRefresh` clears the took-over mark: a newer worker is waiting, and the reload should wait for that one.
- Help guide `app-updates`, `TROUBLESHOOTING.md` and `APP_SHELL_ARCHITECTURE.md` amended.

## Tests

- `UpdatePrompt.render.test.tsx` +11, with a bare `EventTarget` standing in for `navigator.serviceWorker`: the incident replayed (a write begun after the decision, the worker taking over mid-write, the old 4 seconds running out, then the reload landing after the write and its settle beat), a second write behind the first, a write that never returns, a touch and a dialog in the gap, the stood-down tab's next move and its pill, the pill's press through a write, another tab taking the update, and a worker change with no update known.
- One existing assertion moved two lines down: the stamp is read after the reload, where it is now written.

## Not verified live

There is no service worker on the dev server, so the worker change is a dispatched event in the render tests. Two things rest on reading the libraries, not on a run: that the plugin reloads on every worker change today, and that a listener added before `registerSW` hears `controllerchange` first (workbox-window adds its own after an awaited registration). The tab that takes this build does so on the old logic. The deploy after this one is the first live run of the new one.

## Not in this change

Writes that do not go through the Supabase client, such as a direct upload, are not counted and are unknown to the second look. A component that runs one can say so with `useHoldsUnsavedWork`. The chunk recovery's own reload takes no second look either.
