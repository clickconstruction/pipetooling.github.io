# v2.7987 — HR files: the dev seat keeps a plan for a yes, lists the ones that wait and drops one (2026-11-19)

Punch list #315, upgrade 3a, the seat's half. `dev-mcp` server 0.119.0. One new write verb, one new read verb, no migration. Grace's *Build it now* for upgrade 3, 2026-11-13; her word to resume, 2026-11-19.

## What was wrong

`dev_seat_kept_plans` and its two doors have been live since v2.7122, and People → HR has listed the table under *Waiting on you* since v2.7125. Nothing wrote a row. A plan still lived in the session that made it, so the owner said *Apply it* in each session, and a plan was lost when its session ended.

## What changed

- **Keeping a plan is a key on the plan, not a verb.** `plan_hr_entry`, `plan_person_doc` and `plan_person_report` take `keep: true` with `words` and `session?`.
  - The plan runs as it always does. After its dry run the seat POSTs `dev_kept_plan_keep` with the verb's own arguments, the plan's own hash, the reply as shown, the words and the session's name.
  - The reply gains `kept_id`. When the door refuses, it gains `not_kept` with the reason, and the plan still stands in the session.
  - The ask is checked before the dry run. `keep` on an apply, on a verb the list does not take, without words, with a file's bytes, with anything marked counsel-only, or past 380,000 bytes of arguments is refused in words.
  - A reply past 48,000 bytes is stored as its hash and the first of its words, and says so.
- **`list_kept_plans(person?, id?, show?)`** reads the list.
  - Without `id`: the plans that wait, the longest wait first, then the ones that went stale in the last seven days, as People → HR lists them. `person` narrows to one file. `show: all` lists every kept plan.
  - With `id`: one plan whole, with its arguments, the reply as kept and the call that applies it. A session that did not make the plan can apply it.
  - The seat sends its own query as the dev. The door's generic reads redact a column named `*_hash`, and a kept plan is no use without its hash.
- **An apply settles the plan.**
  - `apply_hr_entry`, `apply_person_doc` and `apply_person_report` that land mark the waiting plan under their verb and hash applied.
  - An apply whose dry run no longer matches marks the plan stale, with the mismatch in words. It does so only when the arguments sent are the arguments kept, so quoting a kept plan's hash over other arguments changes nothing.
  - Both are fail-soft. Neither decides the apply.
- **`drop_kept_plan(id, why)`** takes a waiting plan off with a reason, through `dev_kept_plan_decide`. The row stays. A plan already decided is refused.
- The brief's manifest points its `kept_plans` part at `list_kept_plans`, and the reading rules say a plan that waits for the owner's word is kept.
- **Kernel** `supabase/functions/_shared/devMcpKeptPlans.ts`, over the tab's own `keptPlans.ts`.
- The version's note is in `docs/dev-mcp/SERVER_NOTES.md`, where notes live since v2.7999.
- Counts: 150 write verbs, 56 over 24 RPCs, 202 tools.

## Is this the best we can do?

Three answers changed the build.

The card listed `keep`, a list and a drop. With those alone a kept plan applied in a session would have waited on the list for good, since nothing marked it applied. The apply now settles it, so the list is true without a second press.

The card's list had one argument, the person. A session that did not make a plan needs its arguments and its hash to apply it, so the list answers one plan whole by id. That is the point of keeping a plan outside a transcript.

A dry run that errors leaves the plan waiting. Only a hash that no longer matches turns it stale. A lost signal or an expired sign-in also fails a dry run, and neither says anything about the plan.
