# v2.3649 — MCP servers, PR 5: dev-mcp's health checks — check_sampler, check_connections, check_locks, check_migration_ledger, check_edge_boot (2026-09-20)

PR 5 of [`to-dos/mcp-servers.md`](../../to-dos/mcp-servers.md). dev-mcp 0.3.0. One migration.

## Why it needed a migration

The freeze monitor (`monitoring.health_checks`, `monitoring.connection_samples`), `pg_stat_activity` and `supabase_migrations.schema_migrations` are outside the `public` schema: PostgREST cannot read them, and an edge function cannot run ad-hoc SQL. The plan row said "one named use of the service role"; the brief found the better shape — four small `SECURITY DEFINER` functions in `public`, gated `is_dev()` inside, EXECUTE to `authenticated` only. They are then ordinary RPCs the GET door reaches **as the dev**, and the service role is not involved at all.

## The change

- **Migration [`20260920232141_dev_health_rpcs.sql`](../../supabase/migrations/20260920232141_dev_health_rpcs.sql)** — `dev_health_sampler_gaps(p_hours)`, `dev_health_connections()`, `dev_health_locks()`, `dev_migration_ledger_tail(p_n)`; each returns one `jsonb`. Detail and the pre-merge test in [`docs/migrations/20260920232141_dev_health_rpcs.md`](../migrations/20260920232141_dev_health_rpcs.md).
- **[`_shared/devMcpHealth.ts`](../../supabase/functions/_shared/devMcpHealth.ts)** (new, pure): `HEALTH_RPCS` (verb → RPC), `healthRpcArgs` (whole numbers only), `healthReading` — the one-line reading that opens each reply, on the runbook's thresholds (a gap over 90 s is a freeze window, a sample over 250 ms the early warning, a `Lock` wait is Mode A, a sample older than 180 s means the sampler itself stopped) — and `isBootError` / `edgeBootReport`. The lock reading names the blocker and says to read the runbook; no verb terminates anything.
- **[`dev-mcp`](../../supabase/functions/dev-mcp/index.ts)**: the four verbs are one GET each, under fixed RPC names from the kernel — so they answer as soon as the migration is pushed, before a `gen-types` run lists the RPCs in the catalog. `view_as` a non-dev reaches the RPC and is refused by its `is_dev()` gate. `check_edge_boot` OPTIONS-probes every function, 16 at a time, 5 s each, with no key, and names any `503 BOOT_ERROR` (the outage class of v2.1523, which `check:edge-drift` cannot see); it refuses a non-dev identity itself, since it reads as nobody.
- **[`build-dev-mcp-catalog.mjs`](../../scripts/build-dev-mcp-catalog.mjs)** also emits `EDGE_FUNCTIONS` (every `supabase/functions/<name>/index.ts`, 123 today). **Consequence**: a PR that adds, renames or removes an edge function re-runs the script, or `devMcpCatalog.test.ts` fails CI with the command to run.
- `get_recent_errors` stays dropped: edge and Postgres logs sit behind the Management API, which needs a personal access token this server should not hold.
- Docs: `dev-mcp/README.md` (the verbs table), `EDGE_FUNCTIONS.md` → dev-mcp, `DB_FREEZE_RUNBOOK.md` Step 2 (one sentence — and that these verbs hang during a stall like everything else through PostgREST), the migration fragment, the to-do.

## Deploy

After merge: `supabase db push` → `supabase functions deploy dev-mcp` → `npm run gen-types:linked` and `node scripts/build-dev-mcp-catalog.mjs` as the usual `chore(types)` PR (then one more `dev-mcp` deploy so `find_rpc` lists the four RPCs).

## Verify

Each verb answers as a dev with a `reading`; `view_as { role: 'helpers', verb: 'check_locks' }` is refused by the database (`devs only`); `check_edge_boot` reads "All 123 edge functions boot."; `check_migration_ledger`'s newest row is `20260920232141 dev_health_rpcs`.
