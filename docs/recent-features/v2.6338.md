# v2.6338 — Search every file deeply, PR 4: search by meaning, Gemini embeddings and pgvector behind a secret (2026-11-02)

Punch list #240's fourth PR, on the card's recommended default: **Gemini `gemini-embedding-001` at 768 dimensions**, one key in the GCP project the app already has, read from the secret `GEMINI_API_KEY` at call time. The code is complete and deployed; the provider answers only once the owner's one step is done (`docs/DRIVE_INTAKE_SETUP.md` → Search by meaning). Migration `20261102051500_file_index_meaning.sql` (`docs/migrations/20261102051500_file_index_meaning.md`): pgvector, `file_index_chunks`, three columns on `file_index`, the hybrid RPC; `drive-link`, `file-index-sweep` and `dev-mcp` redeployed after the push.

- **The provider behind one module.** `_shared/embeddings.ts`: `embeddingsSetup()` reads the key (null when unset); `embedTexts(setup, texts, task)` POSTs batches of a hundred to `batchEmbedContents` with `outputDimensionality: 768`, the key in the `x-goog-api-key` header (never the URL: a network error's message carries the URL, and that message lands on a row every office reader sees), each batch waited for `EMBED_READ_MS` (twenty seconds), and answers the vectors or the provider's own reason, never throwing and never naming the key. The rules are pure in `_shared/embeddingsKernel.ts` (`chunkText`: about 3,200 characters with 400 of overlap, cut on a space and opened on a word, forty chunks per file at most (`chunksCut` says when the text runs longer, and the row keeps `chunksCutNote`); the endpoint, the request, `embedReadAnswer` checking one vector per text of the right size, `embedDue`, the distance cap `MEANING_MAX_DISTANCE = 0.45`), tested from `src/lib/documents/embeddingsKernel.test.ts`.
- **In the pass.** `indexContext` carries the setup; after a row with text is written, `embedRow` cuts it, embeds the chunks as `RETRIEVAL_DOCUMENT`, replaces the file's rows in `file_index_chunks` and stamps `embedded_at`; a refusal stamps `embed_tried_at` and `embed_note`, and the row is due again a day later. `embedPass` is the sweep's catch-up (`embed`, 10 per run): rows with text and no `embedded_at` (every index write clears the stamp, so a re-indexed file is embedded again; PostgREST cannot compare two columns, so the cleared stamp is the whole test), no Drive read, so every file indexed before the key catches up by itself. A row that lost its text (a revised file read as slow, big, error or scan) loses its chunks too, so stale wording never finds it.
- **The search.** `drive-link` `{ action: 'search_index', words }` is Find a file's first answer now (the client called the RPC directly since v2.6319; through the function it can embed the query; it mints no Drive token, so a search costs no token exchange and Google being down costs the floor alone): with the key set, the query embedded as `RETRIEVAL_QUERY` and `search_file_index_meaning` (the words' top sixty and the nearest chunks within the distance cap fused by reciprocal rank, k = 60) answers; without it, or when the embedding refuses (logged), `search_file_index` answers by the words alone → `{ rows, meaning, note }`. `{ action: 'embed_probe' }` is a dev's one made-up call: one sentence embedded, the dimensions or the provider's reason back.
- **The box.** When the index found nothing by the words (nothing at all, or hits by meaning alone), Drive's own search still runs behind it (`needsDriveBehind`, `driveBehindMeaning`): Drive's hits first, then the meaning hits Drive did not name, so a loose match by meaning never hides a file Drive finds by its name; Drive refusing costs the floor, never the index's hits. `findAFileFromIndexAnswer` reads `by` and `chunk_text`; a hit found by meaning alone shows the nearest chunk's opening as its line with no marks (`meaningExcerpt`) and a quiet *by meaning* tag (`foundByWords`; *by the words and the meaning* for both); the count line reads *3 files say or are about “…”, from our index.* (`FindAFile.render.test.tsx`, `findAFile.test.ts`).
- **Hardened in review before the push.** The catch-up query compared `embedded_at` with the literal string `indexed_at` (PostgREST has no column-to-column filter), so it failed on every call and no file indexed before the key would ever have got chunks; the key rode in the URL, where Deno's network error message would have copied it into `embed_note` and the sweep's log; the HNSW scan answered at most `hnsw.ef_search` (40) rows, so one forty-chunk spec book filled the vector side (`SET hnsw.ef_search = 200` on the RPC); a hit by meaning alone switched Drive's search off; a file that lost its text kept its stale chunks; every `search_index` call minted a Drive token it never used; the Gemini call had no timeout; a failed chunk delete stamped nothing; a chunk could open mid-word.
