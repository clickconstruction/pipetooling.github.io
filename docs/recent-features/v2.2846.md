# v2.2846 — Ready to Bill and Billed never list bills on paid jobs; Stripe / email / HCP refuse to bill a paid job unless asked twice (2026-09-05)

Journey-map Phase 4, Tier-1 #2 sub-item **(a)** ("One bill truth"; private repo `pipetooling-journey-map` → `docs/journeys/bill-a-customer.md` J3 findings #1, #2, N1, N2; `docs/journeys/get-paid-chase-ar.md` J4 Verification #1). Sub-items (b) portal semantics and (c) the shared bill-truth kernel are separate PRs.

## What was wrong

- **J3-1 (blocker):** both Dashboard "Ready to Bill" rows on walk day were stale never-sent drafts on **Paid-in-Full** jobs (job 688 · $5,500 · open 5 months; job 903 · $185 · open 1 month) with live **Bill Customer** buttons. The RTB loader was `jobs_ledger_invoices .eq('status','ready_to_bill')` with a join that never selected the job's status, so no render-time filter was possible; the modal had zero occurrences of "paid"; `create-stripe-invoice` checked only the INVOICE status (`ready_to_bill`, which a stale draft satisfies) and its payments guard applied only to the billed→Stripe conversion branch; `send-physical-invoice-email` and the HouseCall Pro record path gated on invoice status alone; `maybePromoteJobToBilledAfterCustomerInvoice` skips paid jobs as `already_terminal`, so the job would have sat at Paid while a real Stripe invoice demanded money.
- **J3-N2:** the default Stripe view's "What the customer will see" affirmatively asserted **Amount paid $0.00 · Amount remaining $185.00** on the fully-paid job (invoice-scoped payment math), contradicting the Physical PDF's "Paid in full" block in the same open.
- **J3-2 / N1:** Dashboard "Ready to Bill (2)" vs Pipeline "Ready to Bill (0)"; Dashboard "Billed Waiting for Payment (73)" vs Pipeline 59 + Collections 8. The board keys on JOB status (`jobsStagesBoard.ts`: RTB = jobs with status `ready_to_bill` ∪ working jobs carrying an RTB draft — a paid job can never appear); the Dashboard emitted every un-bundled invoice row regardless of job status. J4-1's DB probe: 65 billed invoices = 56 on billed jobs + 8 on working jobs + **1 on a paid job**.

Will's decision 6 (2026-09-05): an **open bill is defined by invoice status** — a billed, unpaid invoice is owed regardless of job stage (the 8 on working jobs stay) — and a bill on a **paid** job is the exception this PR removes.

## Mechanism

**One predicate, shared verbatim** — [`supabase/functions/_shared/paidJobBillGuard.ts`](../../supabase/functions/_shared/paidJobBillGuard.ts) (no imports; the app imports it directly like the other `_shared` kernels; tests in `src/lib/paidJobBillGuard.test.ts`):

- `shouldBlockBillOnPaidJob({ jobStatus, allowRebill })` — true iff `jobStatus === 'paid'` and `allowRebill !== true`. Unknown status never blocks (the guard adds a stop, never removes one).
- `PAID_JOB_BILL_BLOCKED_MESSAGE` = "This job is already paid in full — nothing to bill."
- `allowRebillFromBody(body)` — strict boolean `true` only.
- `buildPaidJobBillBlockedEventRow` / `logPaidJobBillBlockedBestEffort(admin, …)` — the `job_activity_events` row (`event_type: 'rtb_paid_job_blocked'`, `financial: true`, `detail: {source_id, invoice_id, channel, job_status}`) written with the service role when a channel refuses; never throws, never fails the request.

**Dashboard units (Stage 2 + Stage 3)** — [`dashboardBillingInvoiceUnits.ts`](../../src/lib/dashboardBillingInvoiceUnits.ts) + [`buildReadyToBillDashboardUnits.ts`](../../src/lib/buildReadyToBillDashboardUnits.ts):

- `DASHBOARD_INVOICES_JOBS_LEDGER_SELECT` embed now selects `status`; `DashboardInvoiceJoinRow.jobs_ledger.status` and the flattened `InvoiceForDashboard.job_status` carry it (stripped again by `dashboardInvoiceToPaymentModal`).
- `buildReadyToBillDashboardUnits` and `buildBilledWaitingDashboardUnits` drop invoices whose `job_status` is `paid` before any bundling (`isDashboardBillOnPaidJob` / `withoutDashboardBillsOnPaidJobs`). The bundling scan therefore never finds a paid job's primary draft either. Working-job break-offs, RTB-job drafts and billed-job invoices are unchanged. The hook (`useDashboardBillingInvoices.ts`) is untouched — the select constant carries the new column. **The Pipeline board is not changed** (it already had the rule).
- Tests: paid-job draft → excluded (specimens 688/903, board says 0 → Dashboard says 0); working job with RTB draft → included; billed job → included; unknown status → included; billed invoice on a paid job → dropped from Stage 3, billed invoice on a working job → kept.

**Server guard** (both functions need redeploy — see EDGE_FUNCTIONS.md):

- [`create-stripe-invoice`](../../supabase/functions/create-stripe-invoice/index.ts): the job select adds `status`; right after the existing `Job not found` check, `shouldBlockBillOnPaidJob({ jobStatus: jobRow.status, allowRebill: allowRebillFromBody(body) })` → logs `rtb_paid_job_blocked` and returns **409** `{ error: PAID_JOB_BILL_BLOCKED_MESSAGE, code: 'job_already_paid' }`. New body flag `allow_rebill?: boolean`. The existing `Invoice must be Ready to Bill` check, the idempotent-retry branch and the v2.2045 conversion branch are unchanged and run first.
- [`send-physical-invoice-email`](../../supabase/functions/send-physical-invoice-email/index.ts): the `jobs_ledger` select adds `status`; same guard, **first sends only** (`resend: true` re-emails an already-billed invoice and writes nothing, so it is not a new bill). Logs with a service-role client when `SUPABASE_SERVICE_ROLE_KEY` is set (this function previously used only the user client). Same 409 shape, same `allow_rebill` flag.
- **HouseCall Pro record** has no edge function — it is a direct `jobs_ledger_invoices` UPDATE from the modal — so the modal gate below is the only stop on that channel. A DB-side guard (trigger/RLS) would be a migration and is deliberately out of (a); note it for (c).

**Modal** — [`SendRecordInvoiceModal.tsx`](../../src/components/jobs/SendRecordInvoiceModal.tsx):

- `jobIsPaid = isPaidJobStatus(billCustomerJobDetails?.status)` (the same `fetchJobWithDetailsById` the previews already use — `JobBillingContext` in the payload has no status) and `paidJobBlocked = shouldBlockBillOnPaidJob({ jobStatus, allowRebill })`.
- When `jobIsPaid`, a red notice under the channel tabs shows the shared message plus "Bill this job again anyway" (`allowRebill`, reset on every open / job change). `outsideReady` (which gates the Stripe "Create Stripe invoice" and HCP "Save" buttons, and feeds `physicalSendReady` for "Send email") is false while `paidJobBlocked`. The Stripe `StripeBillPreSubmitPreview` ("What the customer will see", with its "Amount paid $0.00") is not rendered while blocked (J3-N2). `confirmOutsideBill` (HCP) refuses with the message as a belt-and-braces stop. Both edge invokes send `allow_rebill: true` only when ticked, so the server error renders through the existing `readEdgeFunctionErrorBody` path in trade language if the client gate is ever bypassed.
- Telemetry: `bill_customer_opened{job_status}` was **not** added — `job_activity_events` has no client write policy and no insert RPC, so there is no client-side event helper to hang it on; the server-side `rtb_paid_job_blocked` event covers the refusal. Adding an open-event needs an RPC (or an edge hop) — flagged for (c).

**One-time sweep** — [`StaleDraftBillsOnPaidJobsSection.tsx`](../../src/components/settings/StaleDraftBillsOnPaidJobsSection.tsx) over kernel [`staleDraftBillsOnPaidJobs.ts`](../../src/lib/staleDraftBillsOnPaidJobs.ts) (tested), rendered in Settings → Data & recovery (dev-gated by the parent, like the rest of the tab). Chosen over a migration because this is user data deleted by a person, and over "use the existing Delete draft bill button" because this PR removes exactly those rows from the Dashboard (so that button is gone for them) and Edit Job hides ✕ on an auto-maintained remainder draft. "Check now" lists `jobs_ledger_invoices` where `status = 'ready_to_bill'` and `jobs_ledger.status = 'paid'` (PostgREST `!inner` embed + `.eq('jobs_ledger.status','paid')`); **Retire draft** calls the existing `delete_ready_to_bill_invoice` RPC (office gates, `ready_to_bill`-only, archived in Recently deleted). Two rows exist live today (jobs 688 and 903). SQL recipe for a read-only check (no writes — the RPC is the delete path):

```sql
select i.id, i.amount, i.created_at, i.is_primary_rtb_bundle,
       j.hcp_number, j.click_number, j.job_name, j.status as job_status
from public.jobs_ledger_invoices i
join public.jobs_ledger j on j.id = i.job_id
where i.status = 'ready_to_bill' and j.status = 'paid'
order by i.created_at;
```

## Verify after deploy

1. Dashboard (dev/master/assistant): "Ready to Bill (N)" equals Jobs → Pipeline "Ready to Bill (N)"; "Billed Waiting for Payment (N)" equals Pipeline Billed Awaiting Payment + Collections (the 8 billed-on-working-job rows still count on both).
2. Edit Job on job 903 → Invoices list → **Send bill…** on the $185 draft: the modal shows the red "already paid in full" notice, no Stripe preview, all three send buttons disabled; tick "Bill this job again anyway" → preview and buttons return. **Cancel.**
3. Settings → Data & recovery → "Draft bills on paid jobs (dev)" → Check now → both specimens listed; Retire each; Recently deleted shows the rows.
4. `job_activity_events` for a refused send: `event_type = 'rtb_paid_job_blocked'` (only reachable by bypassing the modal gate — e.g. an old client tab).

## Rollback

Client: revert the PR (the select column is additive; `job_status` is ignored by old code). Edge: redeploy the previous `create-stripe-invoice` / `send-physical-invoice-email` — the `allow_rebill` flag is simply ignored by the old functions. No migration.
