# v2.6001 — Pricing: a price you type as 0 is saved as $0.00 (2026-10-27)

Wendi, on BP545 LAVENDER SPRINGS BLDG 2 the same afternoon as her video (v2.6000): "Why can't I make something
zero? Trying to change the WS - FIXTURE amount to zero and it won't let me. Have seen this bug before." Her
screenshot is the Workbench grid: WS - FIXTURE, a Fixture row, 1 × $12,500.00, no cost, an *assign…* chip, and the
Traditional breakdown under it. She typed 0 into the sale price, left the cell, and $12,500.00 came back.

## The mechanism

Two things, one cause. The grid's row kernel (`computeBidPricingRows` in
[`bidPricingRowCalculations.ts`](../../src/lib/bidPricingRowCalculations.ts)) had no way to say "nothing prices this
row": its `unitPrice` was `override ?? entry ?? custom ?? 0`, so an unpriced row and a row priced at $0 both read 0.
v2.2396 (Wendi's own ask that August: "everything is set to zero, set unpriced items to a dash") settled it by rule:
a saved 0 is not a price. From then on the sale-price cell drew a 0 as the — placeholder, the solver and the priced
meter counted it unpriced, and `commitWorkbenchTypedPrice` dropped a typed value `<= 0` as if nothing had been typed
(`if (!Number.isFinite(v) || v <= 0 || v === before) return`). The Revenue cell's solver (`impliedUnitPrice`) refused
a result of 0 the same way. So a zero could be neither typed nor shown, and she had "seen this bug before".

## What changed

- **The kernel tells a $0 price from no price.** `ComputedBidPricingRow` gains `priced`: true when an override, a book
  entry or a custom price prices the row, whatever the figure. `unitPrice` is unchanged (0 in both cases).
  [`decoratePricingRows`](../../src/lib/bids/decoratePricingRows.ts) carries it onto the grid's rows.
- **The grid reads `priced`, not `> 0`**, in the six places that read a 0 as unpriced: the sale-price cell's idle text
  and its editing seed, the row's `savedUnit` (the live totals, the meter, *Show unpriced only*), the solver's
  unpriced set, and the copy-prices loop (a $0 copies like any other price). A row nothing prices still shows the dash
  and still counts as unpriced, so v2.2396's rule stands for what it was written for.
- **A typed 0 saves.** `commitWorkbenchTypedPrice` refuses only a negative; the "nothing changed" compare reads the
  saved price through `priced`, so a 0 on a $12,500 row is a change. The write is the same as any other price
  (an override on a book-priced row, a custom price otherwise). A draft of 0 while typing drives the live totals too.
- **Revenue 0 is a $0 price** ([`workbenchCellSolve.ts`](../../src/lib/bids/workbenchCellSolve.ts)): `impliedUnitPrice`
  refuses a negative result instead of a non-positive one, so Revenue 0, or a Profit that eats the row's whole cost,
  prices the row at $0.00.
- The guide [price a bid with the Workbench](../../src/content/help/price-a-bid-with-the-workbench.md) says it under
  the typed-price paragraph.

Looked at and left alone: the grid's Count and Cost/unit cells are read-only (the count is the Counts tab's, where a
count must be above 0 or the row goes; the cost is the takeoff's and Labor's), so there is no guard to fix there. The
cover letter lists a $0 row among the inclusions like any other row and never prints a per-row price; a whole section
at $0 stays out of the letter as before. The margin brush's undo value and the priced-margin stamp still read `> 0`,
where a $0 row contributes nothing either way.
