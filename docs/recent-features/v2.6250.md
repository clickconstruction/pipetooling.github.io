# v2.6250 — Adopting a bid leaves a line on both bids' logs (2026-10-31)

Fix with a migration (`20261031203414_adopt_logs_both_bids`, `docs/migrations/20261031203414_adopt_logs_both_bids.md`); no edge function. Found in the ZZ Test dry run of 2026-10-31 that rehearsed the Gun Dog adopts (the William, Wendi and Trace bids becoming BP556's versions, punch list #208): the adopt moved every row by its id and nothing was lost, but it wrote no line on either bid's log, and the change ledger attributed every moved row to the target while the source's own retirement (`adopted_into_bid_id`, `working_board_archived_at`) is not a column it records. A retired source's record read as if nothing had happened to it.

## Change

- `adopt_bid_as_version` counts what each move touched (`GET DIAGNOSTICS` after the count-row, price-scenario, plan-set and CountTooling-project moves) and, before the source retires, writes a `bids_submission_entries` line on each bid through `adopt_logs_both_bids`, a SECURITY DEFINER helper in the shape of v2.6235's `robot_fixtures_follow_adopt`: the table's insert policy admits fewer roles than may adopt (no primary, no superintendent, no creator outside the office), so written as the caller — the first cut of this PR — a primary's adopt would have failed on RLS and rolled back whole (found by a read-only check of prod on 2026-10-31, before the push; the lock's line never met the policy because `bid_versions_lock_guard` is itself a definer). The helper refuses a caller who cannot price both bids, holds a twin to its own bids, and the read-only statement trigger still fires inside it; the `bid-copies` SQL bed now runs an adopt as a primary and asserts both lines. The source reads *Robert adopted this bid into B556 "231 Gun Dog Trail Bunker & Lodge" as the version "William · Initial". Moved there: 12 count rows, 1 price scenario, 0 plan sets, 0 CountTooling projects. The cost estimate and this log stay here.*; the target reads the mirror, ending *The old bid left the board and stays searchable by its number.*
- The retire step clears the source's remembered price scenario (`selected_price_book_version_id`): it moved to the new version, which keeps it as its ★, and on the retired row it pointed at a scenario of another bid's version — the dry run's finding 4. The column is one the change ledger records, so the source's own history now carries a *price book* row for the day it was adopted.
- No client change: the Bid window's log already draws every entry, so both lines show as soon as the push lands. The guide *bid one project to multiple GCs* says both logs get a line.

Not in this PR: the change ledger's column list (`bid_changes_bid_columns()`) is deliberately what a person types on a bid, and adding `adopted_into_bid_id` would re-create the `bids` trigger under a short lock; the log lines are the record, and the ledger can follow in its own PR if the owner wants the retirement there too.

Deploy: `supabase db push` after the merge. Nothing waits on it.
