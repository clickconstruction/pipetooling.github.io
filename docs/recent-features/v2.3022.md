# v2.3022 — Test-gap audit, pass 33: Bank payments kind badges get their first tests (2026-09-07)

Follow-up to v2.3021. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`bankPaymentsKindBadges.ts` (170 lines) holds the nickname and colour a Mercury transaction kind wears on **Jobs → Bank payments** and in the Banking sorting config: the colour normaliser, the stored-JSON parser, the localStorage cache, the org-wide `app_settings` read and write, pruning to the kinds Mercury actually offers, and the light-or-dark text pick. The nickname also becomes `payment_type` when a bank payment is applied. Two callers, no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Colours accept `#rrggbb` and `#rgb` (expanded), come back lowercase and trimmed, and anything else is rejected. A stored entry with a blank colour takes the neutral default; one with an invalid colour is dropped, as is a blank or over-long kind key.
- The payment-type label is the trimmed nickname when set, else the formatted kind.
- The local cache validates on the way back in, so a corrupt or invalid cached entry reads as absent.
- The org read reports whether the row exists so a device-only cache can be migrated: a blank or unparsable row exists with no badges; no row or a failed read reports no row. The write upserts the whole map as JSON under the settings key.
- Text goes dark on light backgrounds (the neutral default included), white on dark ones, and dark on junk.
