# v2.8596 — CI in three jobs: the merge queue shards its tests and a pull request tests near its change (2026-11-25)

The ask, 2026-11-25: the ledger and the punch list should move faster. The managing session's read at 20:45 UTC was that CI wall time is the limit, and the person said yes to a lane that cuts it. The read of the day, from the step times of the last 45 green runs of each event (code changes only):

| Measure, one `checks` job on one runner | Merge queue | Pull request |
|---|---|---|
| Whole job | 27 to 59 min, median 39 | 25 to 47 min, median 37 |
| Typecheck | 1 to 17 min, median 6 | 1 to 14 min, median 1.5 |
| Test (`npm test`, 5,940 files) | 22 to 37 min, median 28 | 22 to 39 min, median 28 |
| Install, lint and the checks | about 4 min | about 4 min |

Every code PR paid that twice, then the deploy. The typecheck is slow when the cache it restores is several merges behind the build, which is the usual case in the queue.

## What changed

`ci.yml` is three jobs, on both events:

- **`static`** (*typecheck, lint and the checks*): everything the old job ran except the suite, on one runner, in the old order, restoring the same cache. It also runs the five doc-reading tests on every build (about half a minute), where the old job ran them on a docs-only change alone.
- **`test`**: a matrix.
  In the merge queue it is the whole suite in two shards (`npx vitest run --shard=1/2` and `2/2`), a runner each.
  On a pull request it is one leg, *test near the change*: `scripts/ci-near-tests.mjs` picks the tests and `npx vitest run` takes the list.
  A docs-only change ends each leg in seconds, before its install: every leg asks `scripts/ci-docs-only.mjs` for itself, so no job waits on another for a runner.
- **`checks`**: the gate, under the name branch protection requires (`checks` and `sql-beds`, both app 15368). It needs `static` and `test` and runs only to fail, under `always()`, when either did not answer `success`. A skipped job takes no runner and counts as a passed required check, which is how `sql-beds`'s gate has worked since v2.6357. So a green build shows `checks` as *skipped*.

No repo setting, ruleset or branch protection changed.

## The pick on a pull request

The rule is `scripts/lib/nearTests.mjs`, pinned by `src/lib/nearTests.test.ts`:

- **Near**: every test whose imports reach a changed file. The graph is Vite's own: the script starts vitest's server without running a test, transforms each test file as a run would and resolves its imports through the same plugins, so an alias, an `import.meta.glob` and a `?raw` import are followed as the run follows them. 21,179 files, 36 seconds on the office Mac.
- **Readers**: every test whose imports reach a module that reads files instead of importing them. No graph can say which files a source-scan test opens, so they all run, on every code PR. A module is a reader when it imports a Node built-in that is not on a short list of ones that cannot open a file (so `fs`, `child_process`, `module` and any built-in nobody has listed yet all count), a package that reads the repo (`typescript`, `esbuild`, `vite`, a globber), or a `virtual:` module, which a plugin in `vite.config.ts` writes from files on disk. On 2026-11-25 that was 323 modules and 332 of the 5,940 tests. They were found by walking the graph, not by a list kept by hand.
- **The whole suite instead**, on the pull request's one runner, when the picker cannot tell: the compare did not read, the list is at the API's cap of 300 files, the change touches `package.json`, `package-lock.json`, `vite.config.ts`, a root `tsconfig*.json`, `.npmrc` or `.nvmrc`, the change touches what picks the tests (`ci.yml`, the picker and its rule, the docs-only script and its rule), the graph did not build, the graph did not list a test file the PR changes, or the picker itself threw. The step prints which.
- A changed snapshot file runs the test that owns it.

`vitest related` and `--changed` walk the same graph and would have been one line. They throw on this repo: vitest 2.1.9 re-reads a `?raw` import without its query and tries to parse the Markdown as a module (699 such files are in the graph). The script treats a file that does not transform as a leaf.

**What the lighter run lets through, and why that is weighed as acceptable.** Under `ALLGREEN` a failed queue entry throws out the groups behind it, so the question is how often the old PR run caught a test failure the new one would not. The 17 PR runs that failed in their Test step from 2026-11-20 to 2026-11-25 were replayed against the pick, each with its own changed files: in 15 the failing test is in the pick (8 near the change, 7 through the readers: the dev seat's catalog three times, the edge kernel copies, three source scans); one run had no failing test (vitest's process died closing, after 5,739 passed); one was a flake in a test the change did not touch, which the lighter run rightly does not run. Over the same days the typecheck failed 15 PR runs and the checks 8, and those all still run. What can still slip: a test that reaches a changed file through `vi.importActual` alone with no import on the way, and a change in one PR that breaks a test only together with another PR's change, which only the queue could ever see.

## Runners

The org runs 20 jobs at once. A queue build starts 3 jobs (`static` and two shards) and a pull request's run 2 (`static` and one test leg); the gate takes none when the build is green. Six queue builds at once is 18. A leg that finds no free runner waits, it does not fail. Runner time per code change goes down, since the PR's own run no longer holds a runner for the whole suite: about 37 minutes of one runner before, 4.8 of one and 3.5 of another on the first run after.

Two shards, not three, by that count. The estimate behind it was wrong: two were to make a build about 16 minutes at the median and made 20 to 21, so v2.8606 went to three on the owner's word.

## Held together by

`scripts/check-workflow-parity.mjs`, the first step of `static`, now also fails when a job of `ci.yml` typechecks or lints without restoring the cache or by another key, when the `checks` gate is missing, is not under `always()`, does not need every other job of the file or does not ask each for `success`, and when the queue's shard list is not every shard of one count or no step runs `--shard=${{ matrix.part }}`. Six broken copies of the file were each refused.

## The way back

One revert restores the single job: `git revert` of this PR's squash commit, through a PR like any change. `ci.yml` runs from the content being built, so the revert's own PR run and queue build already use the old single job; nothing else needs undoing, and the caches are untouched (same key, same paths).
