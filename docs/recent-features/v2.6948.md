# v2.6948 — A note the dev seat plans on a bid with no date can now be written (2026-11-11)

Found by a record-keeping session on 2026-11-11 (server `pipetooling-dev-mcp 0.65.0`). Four notes on new bids were planned with `{ bid, text }` and no `on`. Every `apply_activity_note` with the same input and the returned `plan_hash` was refused with *the plan you quoted … is not what this dry run gives now*, and nothing was written. The bids had not changed and their note threads were empty. Planning the same input twice, seconds apart, gave two hashes. The same words with `on` set to that day applied first time.

## The cause

`activityNoteDryRun` took the dry run's own clock and `activityNoteRow` put it in the bid row's `occurred_at` when the note named no day. The reply carried that row under `writes.row`, and `planHash` covers the whole reply. The apply runs the dry run again, a moment later, so its hash could never match: no undated bid note could be applied since the verb shipped (v2.6822). A job's undated note was never affected: its row leaves `created_at` out and the table stamps it.

## What changed

- **`supabase/functions/_shared/devMcpActivityNote.ts`**: `activityNoteDryRun(p, world, me, today)` takes no clock. The plan's row comes from the new `activityNotePlannedWrite`: a dated note's row whole (noon of its day comes from the payload), an undated one without the column the clock fills, which `writes.stamped_at_apply` names (`occurred_at` on a bid, stamped by the server as it writes; `created_at` on a job, stamped by the table). The plan's `at` reads *the time of the apply* in place of *now*. `activityNoteRow(p, world, me, now)` is unchanged and is called once, by the apply, after the hash matched and the one-apply check.
- **`supabase/functions/_shared/devMcpWrites.ts`**: `planCommitment` holds a named HR document's `archived_at` as `archived` (true or false) for `plan_person_doc` / `apply_person_doc`, through `personDocCommitment`. See the audit below.
- **`dev-mcp`**: the note case hands the dry run no clock; `plan_activity_note`'s `on?` words say an undated note is stamped when the apply writes it. `SERVER_VERSION` is unchanged: no verb or argument changed, and the open seat PRs each move the version pins.

## The audit: every plan verb, for a hashed "now"

Read for a clock-derived value in what the hash covers: the server's own dry runs, and the dry-run branch of the latest definition of each wrapper RPC.

- **Same cause, fixed here — `plan_person_doc` with `archive: true`**: `dev_person_doc_write`'s dry run answers `document.archived_at` with its own `now()` when the ask archives, so no named document could be archived through the seat. The commitment now holds archived or not; the instant before the change is still held under `changes[].before`, so a document archived or restored since the plan still moves the hash.
- **Already handled**: a cost batch (its plan commits to the before images only) and a clock session approve (`approved_at`, v2.6524). The hours statement's `asOf` is stamped after the hash check (v2.6414).
- **Clock used to refuse only, never in the reply**: `plan_password_reset` (the ten-minute resend rule, a ban still running), `plan_history_entry`, `plan_matter_event`, `plan_matter_statement`, `plan_person_evidence`, `plan_hours_statement`, the Materials on site verbs (their `at` is the literal word *now*).
- **The day, not the moment — left as they are**: `plan_bill` fills a due date left out with today; `plan_submittal_log`'s *next* line and `plan_paper`'s *came* day read today; `dev_legal_document_write` fills `sent_on` / `received_on`, and `dev_legal_plan_write` fills `done_at`, with today when left out; `dev_person_license_write` answers `expired` against today. Each moves only when midnight in the app's calendar falls between a plan and its apply, and then the row would land on another day: asking for a new plan is the right answer.
- **Clean**: the rest (`dev_bid_write`, `dev_hr_entry_write`, `dev_legal_gap_answer_write`, `dev_legal_narrative_write`, `dev_on_site_move_job`, `dev_theme_marks_write`, `dev_theme_review_write`, and the server's dry runs for a job, a job update, the job marks, a payment, a combine, an account, a login, submittal rows and a plan set).

## Tests

- `src/lib/devMcp/devMcpActivityNote.test.ts`: the same undated bid note planned at two times gives one hash (it gave two on the old kernel), with a GC and on a job too, and across midnight; the planned row has no stamp and names the column; a dated note keeps noon of its day in the row and in the hash; the hash still moves with the words, the GC and a new line on the thread; the server builds the stamped row only after the hash check.
- `src/lib/devMcp/devMcpWrites.test.ts`: an archive planned at two times hashes the same, and a document archived or restored since moves it.
