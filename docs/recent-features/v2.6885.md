# v2.6885 — Box photos: the Drive files follow a job whose Materials on site moved (2026-11-10)

Punch list #297, carded 2026-11-09 from the on-site move (v2.6808). A box photo's row moves with its box when a job's Materials on site are moved to another job, but the file the photo sweep already filed stayed in the first job's Drive photo folder. Nothing was lost, since a row names its file by its own Drive id and `box-read` streams it by that id. What was off was the folders: the new job's Drive folder did not list the photos, and the old job's kept pictures of a site that was never its own.

## Why it is a function's ask and not a line in the move

The move's dry run does the write, reads both jobs and unwinds it, and the plan hash commits to what it read. A Drive move cannot be unwound or dry-run that way, has an outcome per file, and making the target's photo folder is itself a write in Drive. So the files move after the rows land, by an ask of the function that filed them.

## What changed

- **`supabase/functions/_shared/boxPhotoRefile.ts`** (new, pure; tests `src/lib/photos/boxPhotoRefile.test.ts`):
  - `refileAskOf(body)`: null for the sweep's call, the job for `{ refile_box_photos: <job_id> }`, a refusal in words for anything that is not a job id.
  - `refileStep(file, folderId, namesInFolder)`: what one file needs. Nothing when the folder is among its parents; a move out of every folder it sits in, under `nextFreeName` when the folder holds its name (any case); a hold with its reason for a file Drive no longer holds or one in Drive's trash.
  - `refileResult` / `refileWords`: the reply and its words, what moved, what was there already, what was held and why, what was not reached.
  - `refiledForSeat`, `movePhotoWordsWithRefile`, `moveReplyWithRefileWords`, `movedPhotosInDrive`, `NO_REFILE_NEEDED`: the dev seat's half.
  - `nextFreeName` moved here from `photo-save/index.ts`, so the sweep and the re-file name by one rule.
- **`supabase/functions/photo-save/index.ts`**: a second kind of call. A body that names `refile_box_photos` is taken from the cron (its secret) or a dev (their session: `refuseArchivedCaller`, then `is_dev()` as the caller); the sweep stays the cron's alone. `refileBoxPhotos` reads the job's `job_box_photos` rows with a `drive_file_id`, resolves the folder with the sweep's own `photoFolderOrWhy`, lists it once, and moves each file not in it. A hold's reason is written on the row's `fail_why` (the app draws that only on a photo that is not filed, so a crew never sees it); a row that is where it belongs has one cleared. One ask spends at most 40 s moving (`REFILE_BUDGET_MS`) and answers how many are left. A job with no folder to land in holds every row with the folder's reason.
- **`supabase/functions/_shared/driveJobFolder.ts`**: `folderFiles` (a folder's files by id with their names, paged) and `driveFileState` (name, parents, trashed; null on 404). **`_shared/jobFolders.ts`**: `moveFile`, `moveFolder`'s call for a file, with every current parent removed and an optional new name.
- **`supabase/functions/dev-mcp/index.ts`** (server 0.61.0): after `apply_materials_move`'s RPC lands, when the reply counts a photo already in Drive, the server asks `photo-save` as the dev for the target job and adds the answer as `photos.refiled`. A failed ask never undoes the move: the reply says the move stands and names the ask. The database's photo words still say such a file stays in the first job's folder, so the seat rewrites that one sentence in the plan and the apply; the plan hash is taken from the database's own reply first, and a test reads the migration so a change to the sentence fails there. The two verbs' descriptions say the same.
- **Docs**: the `plan_materials_move` row in `docs/dev-mcp/README.md`, `docs/EDGE_FUNCTIONS.md` → photo-save and → dev-mcp, `docs/MATERIALS_ON_SITE_ARCHITECTURE.md` (the move, and The gaps → Photos).
- **`to-dos/box-photo-files-follow-the-job.md`** (#297) stays open with what is left.

## What is left

- **A combine.** The office combines jobs and the ask takes only a dev, so either the gate widens to whoever may combine or a nightly pass finds the rows. Not decided here.
- **Asking alone from the seat.** A move applied before this release cannot be applied again, so its files have no way to follow from the seat. One was applied on prod on 2026-11-10. A dev can still make the ask of `photo-save` with their own session.
