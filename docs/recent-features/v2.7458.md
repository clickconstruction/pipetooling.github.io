# v2.7458 — Plans: the dev seat can change the Drive link of a set already saved (2026-11-16)

Proposed from an inventory of one development on 2026-11-16: 18 saved sets whose `plan_sets.link` points at a file the company does not own (some in another party's Drive trash, some the intake service account cannot open), while the company's Shared Drive holds its own copy of each. Nothing could move a saved set's link to that copy. Removing the row and adding it again would break every `replaces_set_id` and `marks_up_set_id` that names it, and the part's `current_set_id`. This is the dev seat's half; the app's **Change the link** press ships beside it. No migration.

## What landed

- **`plan_plan_set` / `apply_plan_set` take `set = { set_id, link, memo? }`** (`supabase/functions/_shared/devMcpPlanSets.ts`, payload action `change_link`). With `set_id` the verb changes the link of that `plan_sets` row, and its memo when `memo` is passed, and takes nothing an add carries: a name, a kind, a part or `make_current` beside `set_id` is refused with the keys named. Same plan then apply rule, same verbs, no new one.
- **The dry run reads back** the set as it stands (name, kind, source, dates, memo, link, what it replaces and marks up), the link before and after, whether the part builds from this set, and under `job_plans_link` each job naming the part with its plans link before and after. A link that differs only by Drive's tail is said to be the same target; a set with no link is said to take its first.
- **The mirror needs no call.** `plan_sets_mirror_on_change` fires `AFTER UPDATE OF link` on any set and calls `plan_part_mirror_job_links(part)`, which writes the part's *current* set's link onto every job naming the part (migration `20261101210000`). So a link change on the current set moves the jobs, and one on an older set moves none. The test pins those three lines of the migration.
- **RLS already allows it.** `plan_sets_update` passes for `plan_part_can_write(part_id)`, the roles that insert a set; `markPaperCame` and the change line update rows the same way.
- **Apply reads back.** One PATCH on the set's own row: the link, the memo when passed, and the file facts read behind the old link (`file_name`, `file_size`, `file_count`, `checked_at`, `check_note`) set to null, since they described the old file. Then the seat reads the row again and refuses with *Nothing changed* when it did not take the link, and reads each job's `job_plans_link` and names any job the mirror did not reach.
- **Refusals**: a paper kind (papers are `plan_paper`'s ground), a set that is not visible, a part that is not visible, and a link equal to the one the set has.
- **The hash** commits to the set's `updated_at`, its link, the part's current set and each job's link before, so a change since the plan refuses the apply, and a link moved there and back is planned afresh.
- **`dev-mcp` server 0.92.0**, with its pins in thirty test files.

## Tests

`src/lib/devMcp/devMcpPlanSets.test.ts`: the input shape, the reads in order, the dry run for a current set and an older one, the four refusals, the hash, the apply's one update and its read-back, the row that took nothing and the job the mirror missed.

## Deploy

`supabase functions deploy dev-mcp` after the merge. Until then the seat answers a `set_id` with the add's shape error. No prod row is changed by this PR.
