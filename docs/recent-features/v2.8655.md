# v2.8655 — A developer can read the list of TakeoffTooling accounts from here (2026-11-26)

The first PipeTooling piece of the accounts train (one staff account across PipeTooling, CountTooling and TakeoffTooling, managed from People). Edge only: no migration, no client change.

## What was there

`tt-bridge`, the dev-only proxy to TakeoffTooling's `manage-user`, forwarded three verbs: `create`, `lookup` and `set_twin_flag`. It was built for the robot seats. CountTooling's proxy, `ct-bridge`, has forwarded `roster` since v2.2435, and the Monday audit reads it. Nothing in PipeTooling could list TakeoffTooling's accounts.

## What changed

- **`tt-bridge` forwards `roster`.** One word added to `ALLOWED_VERBS`. The verb reads every TakeoffTooling account (`tt_user_id`, `email`, `role`, `is_digital_twin`, `active`, `last_sign_in_at`) and writes nothing. TakeoffTooling's own function gained it on 2026-11-26, with `deactivate`, `reactivate` and `update_email`, which this proxy does not forward yet.
- `docs/EDGE_FUNCTIONS.md` → `tt-bridge` names the verb.

## After the merge

**Owes a `tt-bridge` deploy** (`bash scripts/deploy-functions.sh tt-bridge`), on the owner's yes and the push slot. Until it is deployed the proxy answers `roster` with *Unknown or missing verb*, and the Sites lens that reads it says TakeoffTooling could not be read.

## Checked

`npm run check:edge-bundles` for `tt-bridge`. The verb itself was not called from here: it needs a signed-in dev and the deployed proxy.
