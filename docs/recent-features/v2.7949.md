# v2.7949 — A tight header row gives, so the gear stays on screen at 320 px (2026-11-19)

Found from the production smoke on 2026-11-19, which stayed red on the Bid Board at 320 px after v2.7912 and v2.7927 had fixed the tools row. No migration, no edge function, no new page.

## What was wrong

`e2e/viewport-smoke.spec.ts` read the Bid Board 322 px wide in a 320 px screen. The tools row was not the cause: it ended at 304 px. Every element past the edge was found by its box, and the one not inside a scroller was the header's gear. Hiding the gear brought the page back to 320.

Measured on a local preview as the dev, at 320 px on `/bids?tab=bid-board`:

| The header's row | px |
|---|---|
| The row inside the nav's 8 px of padding a side | 304 |
| The left end: the menu, home and search | 113.5 |
| The three coloured presses | 33.5 each |
| The worded **Bid** press, which only the Bids pages draw | 53.3 |
| The gear | 36 |
| The row with the wrench and the people press in the gear menu and its gaps closed to 2 px | 313.3 |

So the row was 9.3 px too long at its last resort. v2.7781 made the row one line that never wraps and gave it three steps: presses leave for the gear menu, the gaps close (`tight`), the way back from View as shortens. It measured the dev's row on the Dashboard, which has no **Bid** press. With nothing left to give, the right end kept its slot and the gear ran 1.3 px past the screen; the smoke's account read 2.

## The fix

A tight row's coloured presses give (`navRowPressGive` in `src/lib/navRowFit.ts`). Each takes `min-width: 0`, so the browser shrinks them by exactly what the row is short, in proportion to their widths. Their icons hold their size (`NAV_ROW_ICON_HOLD`, `flex-shrink: 0`), so only padding goes. The five presses of the phone's row carry it: the Job Mode call press, Task Dispatch, Ask estimating, Task and Bid. The gear and the left end never shrink.

- **Only on a tight row.** `useNavRowFit` measures the presses as drawn. A press that could shrink on a row that fits would be measured short, and the fit would answer from that.
- **It cannot flap.** Once the presses have given, the row fills its width at 2 px gaps. The fit counts the plain 8 px gaps, which that row cannot hold, so it stays tight.
- **Why not a narrower Bid press alone:** that fixes the one row measured. A leader's row in Job Mode on the Bids page is longer still.

## Correcting two earlier fragments

`v2.7912.md` and `v2.7927.md` each said the Bid Board's `scrollWidth` equalled its width at 320 px. It did not. The second walk read 321 against an inner width of 321, and the inner width was itself the widened page. Both fragments now say so.
