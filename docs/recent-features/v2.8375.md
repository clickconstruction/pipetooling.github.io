# v2.8375 — People → HR: an agent can add a large file as evidence by itself (2026-11-23)

dev-mcp 0.129.0. The owner, 2026-11-23, with three recordings on his Desktop to add to a person's file, two of them over the cap: *is there any way you could build a MCP too to upload evidance? could we add this to the dev verbs? How could I get us to a point you can do things like this for me without my intervention*. One migration, two edge functions, no new verb.

## What was there

`plan_person_evidence` took a file two ways. Sent as `content_base64`, it rode inside the tool call: through the agent's own output, which fails past about 50 KB of text, and through the function's JSON body, capped at 10 MB a file. Or linked as `{ name, drive_url }`, for a file a person had already put in Drive, since the seat reads Drive and does not write there. So for any file of real size the agent stopped and asked the owner to drag it into Drive.

## What changed

- **A file can be declared instead of sent.** `{ name, staged: true, size_bytes, sha256, mime? }` in `evidence.files`, up to 50 MB (`EVIDENCE_STAGED_MAX_BYTES` in `_shared/personEvidence.ts`). The project's storage limit was read from the management API on the day: 52,428,800 bytes a file, so no bucket setting has to change.
- **The plan answers where the bytes go.** Its reply gains `upload`: one entry a declared file with the path in the private `hr-files` bucket, storage's signed upload address for that one path (asked for as the dev, good for two hours and one upload) and the `curl` line that sends the file. The bytes go from the agent's machine to the bucket and through nothing else.
- **Nothing is kept between the plan and the apply.** The record's id and each file's id are worked out from the plan's hash (`evidenceUploadIds` in the new kernel `_shared/devMcpEvidenceUpload.ts`), so the plan's addresses and the apply's reads name the same paths. A plan run again for the same evidence answers the same paths, and says *already in place* for a file that was sent.
- **The apply holds the file to the plan.** It reads each declared file back as the dev, digests it, and checks its size and sha256 against the plan before any row is written. A file not sent yet refuses in words. A file that is not the planned one is taken out of the bucket and the apply refuses. A file sent inside the call beside it is taken back out too.
- **The database takes it.** Migration `20261123183000_evidence_staged_file_cap.sql` moves `dev_person_evidence_write`'s cap on a file from 10 MB to 50 MB and changes nothing else. A file sent inside a call keeps its 10 MB, checked by the seat.
- **Drive takes it.** `hr-evidence-drive` read every staged file whole before it uploaded it. A file over 8 MiB now goes through `_shared/driveCopyInPieces.ts`, the loop `photo-save` sends a customer's video with, one 8 MiB piece at a time. A counsel-only record is still never filed in Drive.

## The recipe

1. `shasum -a 256 <file>` and `wc -c <file>`.
2. `plan_person_evidence` with the file as `{ name, staged: true, size_bytes, sha256 }`.
3. Run the plan's `upload.files[].run` line in the shell, from the folder that holds the file.
4. `apply_person_evidence` with the same evidence and the plan's hash, on the owner's word.

## What is left

- A file sent and never applied stays in the bucket at the path the plan named. Nothing reads it and nothing sweeps it.
- The filer keeps no upload address between runs, so a large copy that runs out of time starts again on the sweep.
- A file over 50 MB still goes as a Drive link.
- `plan_matter_document` still takes its file inside the call. The same form would fit it.

## Order after the merge

Push the migration first (`supabase db push`), then deploy `dev-mcp` (`bash scripts/deploy-functions.sh dev-mcp`) and `hr-evidence-drive`. Deployed ahead of the push, nothing breaks: the database refuses a declared file over 10 MB in words until the push.
