# v2.6356 — Every set of plans says what changed from the one before it (2026-11-02)

The owner, on the real site's Plans look (punch list #239): *I would like to see all the different versions of plans. Right now we have this functionality, but I don't think we do a good job explaining in the notes what changed between plans and this seems like the most important thing to record.* A `plan_sets` row carried a name, a kind, a source, two dates, a link, a memo and the set it replaces, and nothing for what moved between one set and the next; the memo's own placeholder asked for *what changed, in a line*, and on the site it held who sent the set and where the file is instead. GC mode's per-sheet ledger (`gc_plan_set_items`) is the other end, and the card had already refused it for plumbing bids: nobody types a sheet index. This PR gives the fact one field and asks for it at the one moment the person knows it.

- **Migration `20261102160000_plan_set_changes.sql`** (`docs/migrations/20261102160000_plan_set_changes.md`): `plan_sets.changes text NOT NULL DEFAULT ''`, and `plan_part_switch_words` (PR 6's History words) ends with ` · what changed: …` when the set carries them. Additive; no new table.
- **The kernel** (`src/lib/plans/planSets.ts`): `PlanSetRow.changes` and `NewSetDraft.changes`; `partTimeline(sets)` runs a part's plain sets newest first, each with the set before it (the one it says it replaces when that row is on the part, else the next older by date); `timelineEntryFor`, `changesLineWords` (*What changed from Issued set: …*), `changesMissing` (a set that followed another with nothing written), `changesPlaceholder` (the cue names the set the new one would replace) and `CHANGES_PRESS`. Tests in `planSets.test.ts`.
- **The form** (`PlanSetForm.tsx`): a *What changed* field under the memo, set mode only; the memo's cue now reads *Who sent it, when, and where the file is*. `planSetsIo.ts` reads the column (whole-row reads, `setRow` filling the default), sends it on the insert only when written, and gains `updateChanges`.
- **The line** (`src/components/plans/PlanSetChangesLine.tsx`): under a set's memo on the job's Plans section (`JobPlansSection.tsx`, the current set and each older set) and on the Development page's Plans look (`DevelopmentPartsCard.tsx`, the memo cell and the older-sets fold). To the office, a set that followed another with nothing written shows **Write what changed**, a set with a line shows **Edit what changed**, and the editor's press says **Save what changed**; the Development page's writes gain `writeChanges`.
- **Guide** *keep the plans on a job*: the step on the form, the History line's new tail, and *Say what changed on an older set*.
- **Not in this PR**: the mail door's prefill from the email body waits on the Papers doors (#6762), whose `MailPaperDoor.tsx` is not on main yet; the robot's draft of the change line from the two sets' PDFs is the second step the owner agreed to, a PR of its own with an edge function and a live call. The Plans look's layout (date first, dashed rules, the presses grouped right) is a sibling PR of the same day.

## Deploy

`supabase db push` soon after the merge. The reads tolerate a deploy ahead of the push: `planSetsIo.ts` reads a set's columns whole (`*`) and fills `changes` with its default when the ledger lacks it, and a set with no change words inserts without naming the column; until the push only the two writes of the words themselves are refused, with PostgREST's reason shown. The dev-mcp catalog carries the column, so `supabase functions deploy dev-mcp` after the push (`npm run check:edge-drift`).
