# v2.7909 — Liens: an assistant can take a wrong mail receipt off a filed lien (2026-11-19)

Two verbs on `dev-mcp` (server 0.113.0, 139 write verbs, 86 naming no RPC): **`plan_lien_receipt_off`** → **`apply_lien_receipt_off`**. The owner, 2026-11-19, asked how the wrong receipt files should come off eleven filed liens: "Build the verb".

## Why

A file in a receipt slot reads as proof. Once a copy carries one, the desk stops asking for it.

On 2026-11-18 the clerk's stamped PDFs went into the receipt press on all twenty-two envelopes of eleven filed liens, the same file twice a lien, before anything was mailed (v2.7846 tells that story and added the press's own doubt). Those files were left in place: "Each comes off with **Take off** on its slot." That is twenty-two presses by hand, and the seat had no way to do one.

`plan_lien_service` could not help. It always needs the day mailed, and it keeps a receipt the filing already holds unless the call brings a new one.

## The pair

`receipt = { job_id, copies: ["owner", "original_contractor"], because }`, or `receipts` for up to 20 filings a plan.

- Each copy is named. A receipt is never taken off by default. `contractor` reads as `original_contractor`.
- `because` is one line, 10 to 300 characters, on why the file is not that copy's mail receipt. It is read back in the plan and kept in the call log.

**The plan writes nothing.** It reads the job and its live filed affidavit, the one `plan_lien_service` records on, and answers each entry on its own:

- **ready**, with its own `plan_hash`: each receipt that comes off and what becomes of its file, the proof before and after, and the `sends` the write sets.
- **refused**, in words: a job not visible, a job with no filed affidavit, a named copy that carries no receipt (it says which copy does), or a job named twice in one call.

A lien already recorded as mailed gets `leaves_no_receipt`: after the take-off that copy has no proof, and `read_lien_filings` lists the filing as *proof* left until the real receipt is added.

## What each file is

Beside the hash, and never in it, the plan reads each receipt file's `name`, `size` and `sha256Checksum` and the saved copy's, one GET a file on the read-only Drive token. No file is opened. `files_on_record.reading` says what the facts tell:

- both copies carry the same file, byte for byte;
- a receipt is the filing's saved copy itself;
- a receipt is within 2,000 bytes of the saved copy, so it may be the lien;
- or nothing in the facts says these are not mail receipts, and each should be opened first.

It is a reading for the person, never a verdict. A Drive read that fails says so, and the plan stands.

## The apply

1. Reads everything again and stops when the hash no longer matches.
2. Writes `sends` alone on the filing's own row, as the dev under RLS. The merge is `lienSendsWithoutReceipt`: the copy's send keeps its method, its number, its day and whatever a mail provider put on it, and a send left with nothing is dropped.
3. The write is held to `kind = affidavit`, not voided, and `served_at` as the plan read it. A day recorded or taken back since the plan lets no row through.
4. Reads the row back. Only when no named copy still carries a receipt is a file moved.
5. Sends each file to Drive's trash through `drive-link`'s `trash` action. That door takes only a file in the job's *Team only › Sent by us* folder that no lien record of the job names. Drive keeps it 30 days. One file named by both copies is asked for once.

A file the door leaves is named with its reason, and the receipt is still off the filing.

**The day served is never written.** No body of this pair carries `served_at`, and the test pins it.

## Held to the press

The seat cannot import `src/lib/jobs/lienReceiptFile.ts`, which is the browser's. `lienSendsWithoutReceipt` is its own ten lines, and the test holds it equal to `lienSendsWithProof(sends, copy, { receiptUrl: '' })` on eight shapes of `sends` for both copies.
