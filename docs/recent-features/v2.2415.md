# v2.2415 — Bid→Job asks which GC gave the job (2026-08-28)

Phase 3 of `docs/PER_GC_BID_PLAN.md`. `JobFormModal.applyPrefillFromBid` hardcoded "the bid's
GC/Builder IS the job's GC" (v2.1182) — wrong the moment a bid has packets for several GCs.

- New kernel `resolveWinningPacket` (`src/lib/bids/gcPackets.ts`): exactly one won real packet
  is the winner; shared-letter wins never count; >1 won flags `multiple`.
- `applyPrefillFromBid` now loads the bid's versions/sends/recipients, groups packets
  (`groupVersionsByGc`), and resolves:
  - **one recorded winner** → import proceeds silently from that GC (seeds `bids.agreed_value`
    from the packet's sent value when empty);
  - **no winner, multiple GCs** → `PickWinningGcModal` asks once; the pick records that
    packet's Won via `setGcPacketOutcome` (auto-losses the other sent, unanswered packets,
    rolls the bid up, fires `bid-gc-outcome-changed`) and then imports;
  - **outcomes ambiguous** (>1 won) → the same picker chooses which packet the job is for,
    writing nothing;
  - **single-GC bid** → untouched, the v2.1182 behavior.
- The job's GC/Builder, customer, contact info and date-met all follow the chosen GC (fetched
  when not already loaded). Shared-letter picks import with that customer and note that
  nothing was recorded on the bid (their answer still rides the bid).
- Job revenue stays fixture-derived (documented deviation) — only `bids.agreed_value` is
  seeded, never job numbers.

Verified live on BP398: picker offered both GCs, own-GC pick wrote Won + rolled the bid up,
board GC line and section membership followed; reset via ↩ waiting + Open + Save.
