# v2.6331 — Company papers: no folder yet reads as a next step, not an error (2026-11-02)

Found the night v2.6309 deployed, in the read-only look at Documents → Company against the deployed `drive-link`: with no company folder set, the tab drew *No company folder yet. Set it on Documents → Where files go.* in red in `OfflineRetryPanel`, with its error door, instead of the `EmptyState` with a **Where files go** press that v2.6309 designed. Client only, no migration and no function.

- **Why.** supabase-js answers a non-2xx call as `{ data: null, error }` whose `error.context` is the function's Response, and a Response's body can be read once. `companyFilesIo.ts` called `fnProblem` (which reads the body for the words) and then its own `fnWhy` (which read it again for the reason): the second read rejected, the catch made it null, so `CompanyFolderRefused.why` was always null and the tab never saw `no_company_folder`. The render test mocked the whole io, so it never met a real Response.
- **The fix.** `fnRefusal` in `companyFilesIo.ts` reads a refusal once and answers the words and the reason together (the body's `error`, else the transport's message, else the fallback; the body's `why`). `loadCompanyFiles` and `putCompanyFile` throw `CompanyFolderRefused` from it.
- **Tests.** `companyFilesIo.test.ts` runs the io over the answer supabase-js really hands back, a refusal whose context is a real `Response`: the 409 keeps both its words and `why: 'no_company_folder'`, a 403 put keeps its words with no reason, a lost signal keeps the transport's words, and a good list and a good put read as before. The reason test failed on v2.6309's code before the fix.
- **Seen, not touched.** `whereFilesGoIo.ts`' `setWhereFilesGo` has the same two reads (`fnProblem`, then `fnWhy`), so `WhereFilesGoRefused.why` is always null too; no screen reads it today (the tab shows the error's words, which arrive), so nothing looks wrong.
