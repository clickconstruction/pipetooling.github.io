# v2.3402 — Deflake the BankPaymentsModal render smokes (2026-09-14)

Test-only; no app code, migration, or edge function changed.

## The flake

`BankPaymentsModal.render.test.tsx` ("leads a matched deposit with the payer chip row and offers the exact-match sweep") failed twice on 2026-09-14 in GitHub Actions (run 34858423605 on PR #3131 and main's deploy run for PR #3129) on PRs that never touched it, while passing locally every time. The footer sentence stayed on `Remaining $1,625.00 — pick a bill…` after the payer chip was clicked instead of reading `Applies $1,625.00 to 876 · …`.

## The race

Selecting the deposit resets the allocation lines in a passive effect (`useEffect` on `[open, selectedId]` in `BankPaymentsModal.tsx`) that flushes *after* the render the test's `waitFor(/their open bills/)` sees — React schedules it through its scheduler, so on a loaded CI runner it can still be pending when the test resumes. The chip click then enqueues its pick on an empty line list, and the reset lands after it and wipes the pick. The sentence kernel reads "pick a bill" for both an empty list and one untouched line, so waiting on the footer text alone would not have proved the effect had run.

## The fix

The empty `ar-allocation-row` only renders once that reset has run, so both suites now `await screen.findByTestId('ar-allocation-row')` before clicking a payer chip:

- `BankPaymentsModal.render.test.tsx` — the wait before the chip, and the post-click footer assertion moved under `waitFor` (same regex, same meaning).
- `BankPaymentsModalLinkGuard.render.test.tsx` — the same latent race sat in front of both chip clicks; hardened the same way.

## Verified

Both suites 6/6 green in a loop (also 8/8 with the machine under CPU load; the race could not be reproduced on an M-series Mac), `npm run typecheck`, `eslint` on the two files, release-note drift test.
