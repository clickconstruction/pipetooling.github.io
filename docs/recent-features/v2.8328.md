# v2.8328 — Permits: San Antonio's nightly read no longer skips a permit dated just before its start (2026-11-23)

Punch list #405 ([the card](../../to-dos/permits-market-page/README.md)), the loose end *The pull's second reading starts too late after a jump* on its *Left to do and to walk* list. Built on the owner's go of 2026-11-22. An edge function and its kernels; no migration, no client change.

## What was wrong

Since v2.8256 `permit-pull` reads San Antonio's applications feed twice in a run: once by filing day, and a second time by the day each permit was issued. Each reading starts a number of days before the newest day held in its own column.

- The read of that newest day sat inside the loop over the readings. So the second reading read the newest `issued_on` after the first reading had already upserted its rows.
- The first reading writes `issued_on` too: an application filed last week that already has its permit lands with a fresh issued day.
- On a night the first reading moved the newest issued day forward, the second counted its ten days back from the new day. Permits the city had dated before that start were never read.
- Nothing reads them again. The first reading only goes back ten days of filing, and the second's start only moves forward.

As the card's walk counted it against the city's feed on 2026-11-22, counts only: 9 applications read as waiting while the city listed a permit for each, 4 commercial and 5 for houses, all with one issued day. By the same walk, the first reading had moved the newest issued day forward by a week that night. Neither was counted again for this change.

## The fix

- **Every reading's start is worked out before a row is written.** `permit-pull` reads the newest held day of each day column the feed's readings use (`passDayColumns`), then asks `passStarts` for every start at once, then begins the first page. Nothing inside the readings' loop reads a newest day or counts a start.
- **The second reading looks back thirty days.** A `FeedPass` carries `lookbackDays`: 10 for a feed's own reading (`PULL_LOOKBACK_DAYS`), 30 for the second (`ISSUED_AGAIN_LOOKBACK_DAYS`). Thirty covers a night the second reading does not finish while the first still moves the newest issued day on, and a permit the city posts days after the day it dates it.
- **A newest day after today counts as today.** `pullSinceDay` now holds a future day to today. A day typed a year ahead would otherwise put a reading's start past every row still to be read, and it would stay there. This is every feed's rule, not San Antonio's alone, and it can only make a reading start earlier.
- A read back as history and a run with `since` in its body start where the body says, as before. No newest day is read for either.

The kernels are `passStarts` and `passDayColumns` in `_shared/permitCities.ts`, beside `feedPasses`, and `pullSinceDay` in `_shared/permitFeed.ts`. The function keeps one small read, `newestHeldDay`.

Cost of thirty days: the second reading asks for about a month of issued applications. By the walk's count that is some 360 rows of the kept kinds, which is one page.

## Tests

`permitCities.test.ts`, a new group *the day each reading starts from*:

- the two look-backs, and 10 on every other city's feed and on a read back as history;
- a night like the one the gap opened on: with the days held before the run, the second reading starts early enough for a permit dated four days before the newest issued day, and ten days back from the day the first reading wrote starts past it;
- a pull that was down for weeks: thirty days counted from what the first reading has just written still misses a permit issued while it was down, and counted from the days held before the run it does not;
- no day held in a column is a first run for that reading, 75 days back from today, whether both columns are empty or only the issued one;
- a newest day after today counts as today, today itself is a day like any other, and the count crosses a month and a year;
- a `since` in the body starts every reading on that day;
- a feed read once starts where it always did;
- the order itself, read off `permit-pull/index.ts`: the newest-day reads, then `passStarts`, then the loop, then the first page, then the first upsert, with no second read or count inside the loop. This test fails on main's file.

`permitFeed.test.ts`: `pullSinceDay` with a look-back it is told, and the future day.

`npm run check:edge-bundles` links all 202 functions. `deno check` passes on `permit-pull`. On `permit-lookup` it fails on a line of that function's own file that this change does not touch, the same on main.

## Deploy

`supabase functions deploy permit-pull` once this is on main. Two bundles hold the changed shared files:

- `permit-pull`: its own file, `_shared/permitCities.ts` and `_shared/permitFeed.ts`.
- `permit-lookup`: the two shared files, through `permitCity`. Its behaviour does not change, and `npm run check:edge-drift` will name it as behind until it is deployed too.

## The proof, after the next nightly run

- The run's log line for `sa-applied` carries `issuedSince`. It reads thirty days before the newest issued day held on that feed's rows before the run.
- The comparison that counted the gap reads 0: no application reads as waiting while the city lists its permit.

## Not in this change

- An application the city takes off its feed still reads as waiting. That is the card's next loose end.
- A number the city lists twice, once with a permit and once without, is read as having its permit, as before.
- The second reading's start is still counted from a day the first reading moves. If the second reading alone failed for more than thirty nights while the first kept running, a gap could open again. A start kept per reading would close that, and it asks a column on `permit_pulls`.
