# v2.2841 — Banking: User Sort loads every transaction; the Link… sheet reads current splits and never REPLACEs over a stale seed (2026-09-05)

Journey-map Phase 4, Tier-1 #3(a) (J33-N1/N3, `pipetooling-journey-map` → `docs/journeys/banking-reconcile.md`). Live counts on 2026-09-04: `mercury_transactions` = **13,065** (1,798 posted in the last 90 days); the master list's `.limit(15000)` returned **1,000**. `mercury_transaction_job_allocations` = **2,060**; the "fetch all" `.limit(100000)` returned **1,000**. PostgREST's `max_rows` (1000) caps every un-ranged response silently — `.limit(n > 1000)` does not lift it, and the RPC set-returning reads are capped the same way. `max_rows` is unchanged.

## What was wrong (two stacked caps)

1. **Transaction list** — `loadAllRows` / `loadUnlabeledRows` in [`Banking.tsx`](../../src/pages/Banking.tsx) asked for 15,000 rows and got 1,000; `rowsTruncated` (`list.length >= 15000`) never fired, so the "⚠ capped at 15,000" chip stayed hidden and the User Sort headline read "Without person: 1000 · Not split to jobs: 1000 · (1000 of 1000 loaded)" against a 13k table.
2. **Relation maps** — [`fetchAllJobAllocations` / `fetchAllAttributions`](../../src/lib/fetchMercuryRelationsByTxIds.ts) read the whole relation tables un-ranged (comment believed `.limit(100000)` cleared the 1000 default). 1,060 allocation rows were missing, so those transactions rendered as **Not split** and — the dangerous part — seeded `MercuryTransactionAllocationsModal` (the **Link…** sheet) with `initialAllocations = []`. `replace_mercury_transaction_splits` is DELETE + INSERT of the modal's list; one Save from that stale-empty seed erased the transaction's real splits (and, via the same RPC, its attribution) with no warning.

## Mechanism now

- **Paged reads everywhere this PR touches**, via [`fetchAllRows` / `fetchAllRowsChunkedIn`](../../src/lib/supabasePaging.ts) (`.range()` under a stable `.order()` until a short page):
  - `loadAllRows`: `mercury_transactions` ordered `posted_at desc nulls last, id desc`, page 1000, **`maxRows: 15000`** — a new `fetchAllRows` option that is a *real* ceiling, so `rowsTruncated` and the ⚠ chip fire only at the actual cap. 13,065 rows → 14 requests.
  - `loadUnlabeledRows`: the same, on `supabase.rpc('list_unlabeled_mercury_transactions', …).range(from, to)` — the RPC already orders `posted_at desc nulls last, id desc`.
  - `fetchAllJobAllocations` / `fetchAllAttributions`: paged whole-table reads ordered `mercury_transaction_id, id`. Kept as whole-table (not by-id chunks) deliberately: Banking's master list *is* the whole table, so ~3 + ~6 paged requests beat ~130 sequential 200-id `.in()` chunks; completeness is identical (pages until a short page). Visuals rides the same helpers.
  - `fetchJobAllocationsByMercuryTxIds` / `fetchAttributionsByMercuryTxIds`: now `fetchAllRowsChunkedIn` (200-id chunks, each chunk paged) — closes the theoretical >1000-rows-per-chunk hole for the by-id callers (Snapshot section, Detail modal, Jobs, Wheels, …).
- **Relation-map kernel** [`mercuryRelationMaps.ts`](../../src/lib/mercuryRelationMaps.ts) (`buildMercuryRelationMaps`, tested): Banking's inline split/attribution grouping extracted; scopes rows to the loaded ids and gives every loaded id an explicit null attribution (what `countSortingUnmatched` reads). [`bankingSortingCounts.test.ts`](../../src/lib/bankingSortingCounts.test.ts) pins the headline: a 1,000-row truncated map over 2,060 rows counts 1,060 "Not split"; the complete map counts 0.
- **Link… sheet reads the DB, not the page map** ([`MercuryTransactionAllocationsModal.tsx`](../../src/components/MercuryTransactionAllocationsModal.tsx), the `TransactionDetailModal` pattern): on open (staff paths — everything except `tallySelfService`) it fetches this transaction's allocations + attribution by id, replaces the prop seed (`lines`, person, `seedPersonId`/`seedUserId`), and remembers the DB state as `serverSeed`. `canSave` is false until that read lands (`seedStatus !== 'ready'`), with an inline "Checking this transaction's current splits…" / "Could not read… Save is off · Retry" banner. `initialAllocations` / `initialPersonId` / `initialUserId` are now documented as placeholders for staff paths. Tally self-service keeps the prop seed on purpose: those roles cannot read the relation tables (RLS returns `[]` with no error, which would look like "no splits") and their RPCs are scoped to their own card.
- **Optimistic-concurrency guard** ([`mercuryAllocModalSeed.ts`](../../src/lib/mercuryAllocModalSeed.ts), tested): `handleSave` re-reads the transaction by id right before `replace_mercury_transaction_splits` and runs `decideSplitSaveGuard(serverSeed, current)` — splits compared order-insensitively at cents with blank ≡ null notes, plus person/user. `'changed'` (another save landed since open) → no RPC, error toast, banner flips to "Splits or person changed… Nothing was saved · Reload current splits"; `'unverified'` (no seed) → no RPC. The RPC itself is unchanged (no migration): the guard is client-side, two cheap 1-id reads per save.
- **Accounting riders** ([`BankingMercuryAccountingTab.tsx`](../../src/components/banking/BankingMercuryAccountingTab.tsx)): `loadPending` (J33-N3, pending `mercury_accounting_label_suggestions`, ordered `created_at desc, id`) and `loadAssignmentsForList` (`mercury_transaction_drag_sort_assignments`, ~11k rows, previously `.limit(100000)` → 1,000: most labeled rows looked unlabeled in the Sorting Ledger) are paged with `fetchAllRows`. The per-rule backfill-candidates read stays un-ranged (small) with `warnIfRowCapHit`.
- **Telemetry**: the paging helper had no hook, so [`warnIfRowCapHit(label, rowCount)`](../../src/lib/supabasePaging.ts) `console.warn`s `row_cap_hit <label>` once per label per session when an un-ranged read returns exactly 1000. Wired to the one un-ranged read left in this PR's path (Accounting backfill candidates); paged reads can't hit the cap.
