# v2.4029 — Edit Job: removing a payment no longer makes the job save again (2026-09-28)

Client only; no migration, no edge function. The second of the three behaviours row 4 of punch list **#46** wrote down and did not change. Stacked on v2.4027.

## What was wrong

Remove (a saved line), Unlink and remove, and Move to job… each write through an RPC and then re-read the job and set the form's payments from it. None of the three moved `hydratedPaymentIdsRef` — the ids the billing slice diffs against — and none re-baselined the slice. So the changed payments started the 1.2 s debounce, and the save that followed asked to delete the id that was already gone (a no-op, seen live on J1053) and wrote revenue, the payments and every line item back unchanged.

## What shipped

- `useJobFormAutosaveEngine` hands back `paymentsRereadFromDb(found)`: it sets `hydratedPaymentIdsRef` from the job just read and re-baselines the billing slice through v2.4027's `billingRereadFromDb` — which leaves the save alone when the slice had an edit waiting or a save in flight.
- `useJobFormPaymentActions` calls it in the Remove and Unlink re-reads, and `JobFormModal` in the Move re-read, each just before `setPayments`.
- The re-reads that already moved the ids (a payment recorded on the bill, an undone part payment, `refreshEditingJobAndHydratePayments`) are as they were.

## Tests

- `useJobFormAutosaveEngine.render.test.tsx` (23, +3): after the re-read nothing is written; the next save carries no payment delete; a line item typed just before is still written, without the stale delete.
- `useJobFormPaymentActions.render.test.tsx` (18): Remove and Unlink tell the engine, before the rows are set; a payment recorded on the bill does not.
