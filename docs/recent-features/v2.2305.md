# v2.2305 — Cross-stage drop targets everywhere + move confirmation (2026-08-25)

Owner ask: dragging tasks between groups from the normal Map view, with a
per-move confirmation modal.

v2.2267 built cross-stage drops (whole-box `__group__` droppables, DragOverlay,
pointerWithin collision) but gated the box targets on the task-edit grip mode;
v2.2273's no-mode hold-to-lift then became the primary drag, leaving row-to-row
cross-group drops technically alive but affordance-less, and box/collapsed
drops dead outside the mode.

## Changes

- `ChecklistTechTreeGroupNode`: box droppables (+ ring + "Move here — becomes
  N.M" end slot) arm for all editors (`dropEnabled = canEditStructure`), not
  just reorder mode. The empty-group drop zone also shows during any active
  drag.
- `ChecklistTechTreeTab.onTaskDragEnd`: a drop whose destination group differs
  from the source no longer applies immediately — it stores the computed
  renumbering as `pendingTaskMove` and opens the new
  `ChecklistTechTreeMoveTaskModal` (task title, from/to stage pills with
  "was 64.1" / "becomes 65.2", people/notes/history reassurance; Cancel,
  backdrop, or Esc = untouched; Move task applies the stored updates).
  In-stage reorders apply instantly, unchanged. Same rule in grip mode.
- Guide: *add a stage* → "Move a task to another stage" rewritten (hold
  anywhere, no mode needed, confirmation described).

## Verification (live, prod data, throwaway TEST MOVE A/B stages)

Hold-lift (no mode) → drop on B's box → modal with exact labels (was 64.1 →
becomes 65.2); Cancel → rows unchanged; redo + Move task → task lands as
65.2, source renumbers; in-group drag → instant swap, no modal. Stages
deleted after, zero orphans. Hidden-pane gotcha for posterity: expanding a
group re-layouts, so element rects captured before the next frame are stale —
measure after a frame pump.
