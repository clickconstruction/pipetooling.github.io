# v2.3427 — Edge `_shared/ipGeoValidation.ts` is strict-clean, with a client↔edge parity test (2026-09-14)

Engineering hygiene; closes the v2.3026 to-do. Type-narrowing in one `_shared` edge module plus one new client test. No migration, no behaviour change, no user-facing surface.

## Why

`resolve-ip-geolocation` refuses private, loopback, link-local, CGNAT and malformed addresses before calling the geo-IP provider; the client (`src/lib/ipGeolocationMaps.ts`) mirrors the same gate to decide whether a clock punch or estimate view gets a map pin. The two tables were "the same by construction" only — the edge copy failed the app's tsconfig (`noUncheckedIndexedAccess`: possibly-undefined regex groups and destructured octets), so no client test could import it the way the accounting-label parity tests import their `_shared` twins.

## What shipped

- **[`supabase/functions/_shared/ipGeoValidation.ts`](../../supabase/functions/_shared/ipGeoValidation.ts)** — the four regex groups and the `[a, b]` octets are narrowed with explicit `undefined` guards. Same outputs for the same inputs: the guards are unreachable when the regex matched, and the existing `Invalid IP address` reason is what the unreachable octet branch would return.
- **[`src/lib/ipGeolocationMapsSharedParity.test.ts`](../../src/lib/ipGeolocationMapsSharedParity.test.ts)** (2) — imports both gates and asserts the same verdict for 38 addresses (each private range with its boundary neighbours, loopback, link-local, CGNAT, 0/8, malformed IPv4, blank, IPv6 loopback/link-local/unique-local bracketed and not, IPv4-mapped IPv6); pins the edge module's three refusal reasons.
- `ipGeolocationMaps.test.ts` — the "cannot import the edge twin" comment now points at the parity test.
- `to-dos/engineering-hygiene.md` — the bullet is removed.
