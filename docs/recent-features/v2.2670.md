# v2.2670 — Salary-schedule sessions auto-approve (2026-09-03)

First PR of the overhead-feed repair pair (with the pending-approvals Needs You card): salaried users' clock sessions are MATERIALIZED BY THE SYSTEM (`origin = 'salary_schedule'`, `salary_sync_one_user_clock_sessions`) yet still waited on a human approval. During the Aug 2026 approvals stall (~3 weeks with zero approvals company-wide, 152 sessions / 799h pending) these system rows were a third of the backlog, silently starving `people_hours` and the People → Overhead pool/denominators.

## DB (migration `20260903010000` — fragment in docs/migrations/)

- New `auto_approve_salary_clock_sessions()` (SECURITY DEFINER): approves closed `salary_schedule` sessions with the SAME write semantics as `approve_clock_sessions` — incremental `people_hours` upsert (`+hours` on the day), `resolve_pay_person_id_from_clock_user`, `sync_crew_jobs_from_clock` / `sync_crew_bids_from_clock` per approved row.
- Deliberate differences from the interactive RPC: callable only by pg_cron (`auth.uid() IS NULL`) or dev; bad rows (blank name, ≤0 hours) skip instead of aborting; `approved_by` / `entered_by` stay NULL (system attribution, never clobbers a human's `entered_by` on the day); 2-hour settle buffer after clock-out so the salary sync's close/adjust pass always wins; the flag re-check in the UPDATE backs out the hours increment if an interactive approve/reject/revoke raced in.
- pg_cron job `auto-approve-salary-sessions` every 30 min (plain-SQL job, `connection_usage_monitor` precedent). Kill switch: `app_settings` key `auto_approve_salary_sessions_disabled_v1` = `'1'` (no unschedule needed).
- First run drains the existing pending salary backlog (35 sessions as of Sep 2) — no separate backfill.
