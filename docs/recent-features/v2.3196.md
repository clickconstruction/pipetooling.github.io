# v2.3196 — Cost batches: audited, reversible cost reallocation for agents (2026-09-09)

Migration `20260909161532_cost_batches.sql` (`docs/migrations/`) + a client kernel; no UI yet. Owner call while booking an 800-row cost correction onto the Diamondback jobs: raw SQL from an agent session had invisible intent (the tool safety layer kept blocking it), an undo that lived in a CSV in a folder, and nothing in the app saying what moved or why. "Should we build tools so it's easy for an agent to manipulate this in the future?" — yes: the HR-files pattern (v2.2232) applied to job cost. Contract: [`docs/COST_BATCHES.md`](../COST_BATCHES.md).

## What shipped

- **Two audit tables** — `cost_batches` (label, reason, source_ref, author, op_count, summary, `reverted_at`) and `cost_batch_ops` (seq, op_type, `target`, `before_image`, `after_image`). The before-image of every row an op touched **is** the undo. Dev read-only; no client write policies exist — rows are written only by the definer RPCs.
- **`cost_batch_apply(p, p_dry_run = true)`** — one JSON batch, one transaction, five operation types and nothing else: `allocate` (bank transaction → job, optionally replacing the catch-all job's allocation; the allocation set can never exceed the transaction), `supply_repoint`, `clock_repoint` (never onto bid time), `other_charge` (**description must start with `ESTIMATE`** — the only way an estimate enters a job from a batch), `thread_note`. Payments tables are unreachable by construction. **Dry run is the default and is the real code path**: it performs every write, builds the summary, then unwinds via a private SQLSTATE caught inside the function — so a dry run that returns is an apply that will succeed on the same data.
- **`cost_batch_revert(batch_id, reason)`** — restores before-images in reverse order, marks the batch reverted, leaves a note on each touched job. Once.
- **`cost_agent` role** — least privilege: SELECT on the planning/audit tables, EXECUTE on the two RPCs, no direct write anywhere. Password set out-of-band (`COST_AGENT_DB_PASSWORD` in `.env.local`), never in git.
- **Kernel** — [`costBatchPayload.ts`](../../src/lib/costBatches/costBatchPayload.ts): the op types, `validateCostBatchPayload` (mirrors the SQL rules so a planner rejects a bad payload before the round-trip), `summarizeCostBatchOps` (the same by-job shape the function's summary reports, plus what left each `from_job`), `buildCostBatchPayload`. 10 tests.
- **Access model** documented in `docs/ACCESS_CONTROL.md`; index row in `docs/README.md`.

## The convention (short form)

Plan in a human-readable file → dry-run and match its totals to the cent → real dollars move, estimates are labelled `ESTIMATE` → note every touched job in the same batch → one basis per cost (clock sessions **or** bank pay for a period, never both) → revert and re-apply rather than hand-patch.

## Not in this PR

A dev screen (Banking → Cost batches: list, expand ops, revert). Devs read the two tables and call the RPCs from SQL until then; agents use the role. Types regenerate after `db push` (`npm run gen-types:linked`).
