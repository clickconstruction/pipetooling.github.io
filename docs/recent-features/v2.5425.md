- **`messages.tied_by`**: the user whose `tie_message` last set a line's job, an untie included. It is null when the line took the contact's starred job as it came in (the Quo and email readers), or no job, and nobody has tied it since. Until now the two looked the same, so the New lane's **Which job?** (`src/lib/followUp/newLane.ts`, `tiedByHand`, v2.5394) could not tell them apart.
- **`tie_message`** stamps `auth.uid()` in the same `UPDATE` that sets the job, and is otherwise as the spine wrote it. It stays `SECURITY INVOKER`, so training mode and a digital twin are still refused. The office team gains `UPDATE` on the one column for it, as cut 2's `back_by`. `set_default_job` and the readers never write the column.
- **No index**: the New lane reads a contact's lines, which `messages_thread` already serves.
- **The bed** (`supabase/tests/messages_spine/20_scenario.sql`, section 7, and the runner's header) pins five things: the estimator stamped by a tie and again by an untie, the reader's line on the star carrying nobody, the column grant, and the line training mode and a twin could not tie carrying nobody. It runs in CI's SQL beds on this PR.
