# v2.7746 — Edit Job: a line added on another screen is no longer saved over (2026-11-18)

## Why

Punch list #391 (Put a trip on a bill) adds a press that writes one line to a job from the Trips look. Its card found the edge that press would cut on, and which two presses cut on today: the Job window's billing save keeps only the lines its form holds. `writeBillingSlice` upserts the form's lines, deletes every line of the job not among them, and writes the job total from the form's lines. Nothing compared against the database first. A window that was open before a line was added somewhere else (a discount through `apply_job_discount` from Bill Customer on another screen, a change order's lines through `apply_estimate_to_job`) deleted that line at its next billing save and wrote the total without it. The same window on the same screen was safe only because opening the Job window again remounts it, and Add discount covered its own window through `rehydrateFixturesFromDb`.

This is PR 1 of that card's four. It stands alone and needs nothing from the trip train.

## What changed

- **`src/lib/jobs/jobFormSliceWrites.ts`**
  - `writeBillingSlice` reads the job's line ids before it writes anything (`select id from jobs_ledger_fixtures where job_id = …`) and takes `heldLineIds`, every line id the window's form has held. `lineIdsNeverHeld` names the database's lines that are neither held nor in the form now. When there is one, the slice writes nothing (no revenue, no payment, no line, no discount event) and answers with those ids in `linesChangedElsewhere`. Otherwise the writes run exactly as they did, in the same order with the same payloads and filters.
  - A line the form read and the person then deleted is held, so it is still the form's to delete. A line the form made and has not saved is in the form, so it is still the form's to write.
  - The words: `LINES_CHANGED_ELSEWHERE_WORDS`, and `LINES_CHANGED_ELSEWHERE_UNREAD_WORDS` for when the lines could not be read again. They say *somewhere else*, not *another screen*, because a writer on the same screen whose window does not re-read the lines is refused the same way.
- **`src/hooks/useJobFormAutosaveEngine.ts`**
  - `heldLineIdsRef` gathers the ids of the form's rows on every render, for the open job. Only the form's own rows count. A re-read that replaced `editing` alone has not put its lines in the form, and a save would still drop them.
  - On a refusal `persistBillingSlice` calls `rehydrateFixturesFromDb` (the seam Add discount uses), shows the words for 15 seconds, and answers that the save failed. The slice reads *error* and stays dirty, so the close guard asks as it does after any failed save.
  - No merge (the card's default 6). The re-read replaces the form's lines with the database's, so the person's last change to the lines is gone and is made once more. A payment typed with it is not lost: the render that carries the re-read lines differs from the last saved state, so the slice saves again 1.2 seconds later, with the line that was added elsewhere now among its lines and in its total.
  - A save queued behind a refused one runs before the render that carries the new rows, with the old rows still in the refs. It is refused again by the same read, and `rereadForLinesRef` keeps it from reading the job or saying the words a second time.

Identity, materials and team are not touched, and neither is `useJobFormAutosaveSlice`, which Edit Bid and the Estimates draft share.

## What it costs, and what it leaves

- One small read per billing save.
- The read and the delete are two calls, so a line added between them is still lost. That gap is one save long. It used to be as long as the window stayed open. Closing it for good is the transactional write the `TODO(billing)` at the head of `jobFormSliceWrites` asks for.
- A line *deleted* somewhere else is still written back by a stale window's next save, as before. This guard is about lines added.
- The bill presses (`useJobFormInvoiceActions`) flush the billing slice first and go on whatever the flush answers, as they do after any failed save.

## Tests

- `jobFormSliceWrites.test.ts`: the read comes before any write; a line the form never held means no write at all and the line named; a line read and then dropped, a line made in the form, and a job with no lines each save as before; a failed read is thrown with nothing written; `lineIdsNeverHeld` by itself. The harness counts the guard's read apart from the writes, so every sequence pinned before this change is asserted word for word as it was.
- `useJobFormAutosaveEngine.render.test.tsx`: the refusal with its re-read and its words; the save after the re-read keeps the line in the upsert, the delete's keep list and the total; a payment typed with the refused change is saved by the save the re-read starts; a deleted line is not a line added elsewhere; a re-read that set the job alone is still refused; the lines that cannot be read again; a queued save; and the other three slices saving as before while the billing save is refused. Each was run against a mutant of the guard and failed, after a control run passed.
- The identity, materials, team and re-read tests that were there are unchanged and pass, as do the tests of `useJobFormAutosaveSlice` (Edit Bid's and the Estimates draft's hook), which this change does not touch.

## Live walk

2026-11-18, from this branch's dev server against the live database, on one ZZ test job with one line, in two browser tabs each holding the job's window on Bill.

1. The second window added a line and saved it. The job held two lines.
2. The first window, opened before that, pressed **+ Add line item**. Its save wrote nothing. The words came up, its lines were read again and it showed the second window's line and the new total. The database still held both lines.
3. The first window added its line again, over the lines it now held. It saved, and the job held three lines.
4. The second window, now the stale one, changed a price. It was refused the same way, the price went back, and the first window's line was still in the database. Before this change that save would have deleted it.
5. Both test lines were deleted in one window and the job is back to its one line and its total.

The walk used a second Job window as the other writer. The card names Add discount from another screen. It is the same case to the guard, a line the form never held, and it was not walked.
