# v2.8392 — Job cost reads each person's pay by the shortest way (2026-11-23)

Punch list #430, the second of its two views. One migration on a view. No client change, no edge function.

## What was wrong

`people_hours_recorded`, the view behind a job's Cost and Labor panels, Jobs crew P&L, bid labor and pricing and the Projects board, joins the pay config with an equality onto a `COALESCE` of the name from either side of its full join. Postgres does not use such a join as an index condition on a table with row policies (v2.8301 taught it on Documents → Photos), and `people_pay_config`'s self-read policy reads the name. So every pay row was filtered under its policies for every person-day, instead of the one row looked up by its key.

## What changed

- **The join is a `CASE`** ([`20261123190100_people_hours_recorded_pay_join_by_key.sql`](../../supabase/migrations/20261123190100_people_hours_recorded_pay_join_by_key.sql), [its doc](../migrations/20261123190100_people_hours_recorded_pay_join_by_key.md)): the approved row's name when there is one, the pending sessions' name when there is not. The same pay row, found by its key. The rest of the view is word for word what `20260909022534` wrote.
- **A new bed holds it**: `people-hours-recorded` seeds every side of the full join, rebuilds the view as it stood, asserts four readers read the same rows from both, and reads the plan for an index condition on the pay row.

## Checked

- Not on prod: no read-only path to a plan was open from this session, as punch list #430's card says. A one-line read of the view as a dev answered.
- The shape on a local Postgres 15 under a column-reading policy, with the view's own full join: `Join Filter` over the whole table with the `COALESCE`, `Index Cond` on the primary key with the `CASE`.
- Not run here: the SQL bed, which needs Docker. It runs on the PR.
