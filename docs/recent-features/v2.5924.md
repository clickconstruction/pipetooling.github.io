# v2.5924 — His signing code signs the lien waiver too (2026-10-26)

Punch list #150 shipped the leader's signing code for lien NOTICES (v2.5788 the code + RPCs,
v2.5791 the desk's field) and its fragment named the Release of Lien window as the follow-up.
The owner asked for exactly that while designing the modernized Bids → Lien Release tab

there — he types his name and his code, and the waiver is signed as his own act.

## What changed

- **Migration `20261026193000_lien_release_sign_code.sql`** (`docs/migrations/…md`): the
  release table's mode CHECK widened to `code` (v2.2616 made it `type`/`draw` only, so a code
  signature failed the row's check); `check_lien_sign_code` — the one checker over `user_sign_codes`, factored so the waiver RPC
  shares the desk's exact lockout (clients cannot execute it; the desk's own function is left
  untouched) — and `sign_lien_release_with_code`, the waiver twin of the desk's RPC: office or
  leader calls it, the signer must be a live master/dev, the release unvoided and `issued` or
  `awaiting_signature`; the right code stamps the row `signed` in mode `code` with
  `signed_on_device_of` naming the screen. **Push after merge.**
- **Kernel** ([`lienReleaseLifecycle.ts`](../../src/lib/jobs/lienReleaseLifecycle.ts)): the audit
  sentence gains the mechanism — *Typed by Malachi Whites with his signing code in ClickTooling
  on October 26, 2026 at 2:14 PM CT, on Wendi's screen, consent recorded.* —
  and `lienReleaseRowSignature` passes mode `code` through (it renders as the cursive name, like
  `type`; `LienWaiverSignature.mode` widens in `lienWaiverRelease.ts`).
- **[`lienReleaseSignIo.ts`](../../src/lib/jobs/lienReleaseSignIo.ts):**
  `signLienReleaseWithCode` — the RPC, the desk's answer shapes (`wrong` with tries left,
  `locked` until when, `none`, `not_live`), then best-effort: the `waiver_code_used` push and the
  signed PDF stored as the pad's path stores it.
- **[`LienReleaseSignModal`](../../src/components/jobs/LienReleaseSignModal.tsx):** with a present
  leader whose code is ready, an untouched pad gives way to the code once the status arrives (as
  the desk does): his name in the cursive face over the rule, a password field under the page
  (*Four to six digits, his alone…*), *Draw instead* / *{First} types his code instead*, the
  disclosure naming the code, and **Sign it with his code**. Wrong answers land under the button
  with the tries left; no code set leaves the pad leading with nothing offered.
- **`notify-lien-approval`** gains `kind: 'waiver_code_used'` + `release_id`
  (`lienWaiverCodeUsedPush` in `_shared/lienApprovalPush.ts`): the signer alone hears *Your
  signing code signed a lien waiver · 878 · Take 5 Seguin · $3,800 · signed Oct 26 · on Wendi's
  screen*; the email says the signed waiver sits under *Already on this job* and to change the
  code under Settings if it was not him. Logged `lien_waiver_code_used`. **Deploy after merge.**
- **Guide** *send a GC our lien waiver*: the code paragraph under *Get the leader to sign*,
  linking the Lien desk guide's *Your signing code*.

`lienReleaseSignCode.test.ts` (4: the audit sentence's mechanism and screen; ok signs through the
RPC, tells the signer and stores the PDF; wrong carries tries left and tells nobody; a missing RPC
answers not_live), `LienReleaseSignModal.code.render.test.tsx` (4: code ready swaps the pad for
the cursive name and signs through the IO; a wrong code lands under the button; Draw instead; no
code set leaves the pad). Existing lifecycle/modal suites unchanged and green. The new
`lien-release-sign` SQL bed (`npm run test:pg:lien-release-sign`) signs a waiver with the
leader's code through RLS over the whole schema: the office signs on its own screen, a wrong code
counts down, five lock it, a voided or already-signed waiver and a non-leader signer are refused,
training mode and a field user are refused, and the checker stays closed to clients.
