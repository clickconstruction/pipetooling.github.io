# v2.7182 — Sign-in opens the page you asked for (2026-11-13)

v2.6994 left this open under *Is this the best we can do?*: a phone that is not signed in scans the **Scan to record** code on a lien help sheet, signs in and lands on the default page. The owner asked on 2026-11-13 for every open Lien desk item to be closed. This one is the app's sign-in for every page, so the fix is there and not in the Lien desk.

The owner then asked the wider question the same day, not knowing this was in hand: *we have QR codes that a user will scan that requires them to sign in, and when they sign in it brings the user to their desktop rather than where the QR code was trying to bring them.* So this also checks every code the app draws, and holds each one with a test.

## What was wrong

Reproduced on the dev server at 390 wide, signed out, for both addresses the code draws (`lienWindowHref(jobId, 'affidavit')` and `lienDeskHref({ kind: 'affidavit' })`):

- `ProtectedRoute` sent a visitor with no session to `/sign-in` and kept nothing. The address bar read `/sign-in`, with no query.
- After the sign-in, `SignInRoute` sent the person to the role's landing.

A return address already existed. `POST_LOGIN_REDIRECT_KEY` in the browser's storage was written by three doors (the standalone `/task` launch, a box label's page, a file link) and read by `SignInRoute`. The gate never wrote it, and the emailed one-time link landed on `/dashboard`, which never read it. So this mends that one mechanism. No second one was added.

## What changed

- **One rule, in a kernel.** `safeReturnAddress` in `src/lib/signInReturnAddress.ts` decides what may be kept: a path on this site that starts with one `/`, with its query, and its hash when the hash is a plain heading anchor. Everything else reads as nothing and falls back to the role's landing: another site in any spelling (`https://…`, `//host`, `/\host`, a path whose dot segments resolve to `//host`), a tab or a line break, an address past 2,000 characters. The site's root and the sign-in page read as *no place asked for*. A sign-in token or an error in the hash is never kept.
- **The gate keeps the address.** `SignedOutGate` (`src/components/SignInReturn.tsx`) is what `ProtectedRoute` draws for a visitor with no session. It writes the address under the same key, then sends them to sign in.
- **Only for a visitor who arrived signed out.** `gateMemory` keeps nothing when the visit held a session before, so a press on **Sign out**, or a session that ended, lands the next person on their usual first page as it did. A signed-out visitor who asks for the root clears an older address, so the newest ask wins.
- **One writer, and a kept address is good for an hour.** `keepReturnAddress` holds the address to the rule and stores the time beside it (`POST_LOGIN_REDIRECT_AT_KEY`). The gate, the box page's press, the file link and the Add Task launch all call it. Past `RETURN_ADDRESS_KEEP_MS` the address reads as nothing. Without that, the gate writing on every signed-out visit would leave a scan somebody gave up on to decide where a sign-in days later lands. An emailed sign-in link is good for an hour too, and carries the address itself. An address stored with no time, by an older build, still reads.
- **One reader.** `LeaveSignIn` is what `SignInRoute` draws for a signed-in person. It reads the address in the render and spends it in an effect. The old code read and removed in the render, and StrictMode renders twice.
- **The password sign-in reloads onto the address, not onto wherever the app is.** `SignIn.tsx` hard-reloads after a sign-in to clear caches. By then the sign-in route has already moved the app to the address. A page that opens a one-shot door from its address (`?lienwindow=`, `?stagesJob=`) takes the door off once it has opened, so a plain reload could land on the Pipeline with no window. The reload is now onto `/sign-in?next=<address>` (`signInHrefCarrying`), which sends the signed-in person on, the same every time.
- **The emailed link carries the address.** With an address waiting, `signInWithOtp`'s `emailRedirectTo` is that same `/sign-in?next=<address>` (`magicLinkLandingPath`). A mail app may open the link in a browser that shares no storage with the one that asked, so storage alone would not do. With nothing waiting the link lands on `/dashboard`, as it has since v2.2524.
- **`?next=` is held to the same rule.** A link someone else writes can name only a page on this site, which is no more than a direct link to that page already does.

No edge function and no migration. The redirect allow list already covers every path on the site (`supabase/config.toml`: `site_url` and `https://clicktooling.com/**`).

## Every code the app draws

Found by reading every file that draws one (`qrcode.react`, `qrMatrix`, the pay code's two helpers). `src/lib/qrDoors.test.ts` now holds the list, so a new code fails a test until someone says what it opens.

| The code | Opens | Needs a sign-in |
|---|---|---|
| A lien cover sheet, **Scan to record** | the job's Lien window, affidavit tab | yes, the gate |
| A lien batch sheet, **Scan to record** | the Lien desk's Affidavits list | yes, the gate |
| A lien notice sheet, **Scan to record** | the job's Lien window, § 53.056 notice tab | yes, the gate |
| A lien sheet's **Scan for the full guide**, and the guide code on *Today's mail* | a guide's share page, which is public and sends a person on to the guide in the app | yes, at the guide |
| A machine's label | the machine's check, `/m/<code>` | yes, the gate |
| A box label, a tape strip, a manifest, a sticker | the box's page at `prts.co/b/<code>` | no. Its **Sign in to record a use or a count** press does, and keeps the box |
| A bill's pay code, on screen, printed, on a lien notice's pay page and on a mailed letter | the bill's pay page | no |
| The code in a statement, a bill or a release email | the customer's or the GC's portal | no |
| A portal's own code, a sub's portal code | that portal | no |
| A First look's code | the look, `/show/<code>` | no |
| A procurement sheet's code | the GC's review room | no |

Two links that are not codes use the same sign-in: a kept file link (`/files/…`) and the Add Task icon (`/task`).

Each door that needs a sign-in keeps its address under the one key, and the sign-in page sends the person on. `SIGN_IN_DOORS` in `signInReturnAddress.test.ts` runs every door through the password form and the emailed link, with and without storage.

Two cases the owner's question raises:

- **A phone whose sign-in ran out.** A scan is a fresh load. Supabase tries to renew the session, fails, and the app has no user at any point. The gate reads that as a visitor who arrived signed out and keeps the address. Walked with a session aged a day and a dead refresh token.
- **An iPhone with the app on its home screen.** A scan opens Safari, not the installed app, and Safari holds its own sign-in. Signed out there, it is the same road: sign in, land on the page. The session then lives in Safari. iOS gives a web page no way to hand a scan to the installed app.

## How it was checked

- `signInReturnAddress.test.ts` (34 cases) holds the rule, the gate's three decisions, the link's round trip, the hour, storage that is missing or refuses, and one case per sign-in door. `SignInReturn.render.test.tsx` (8 cases, under StrictMode) holds the wiring. `qrDoors.test.ts` (4) lists every file that draws a code with what it opens, and refuses a second writer of the address.
- On the dev server at 390 wide, signed out each time:
  - `/lien-desk?tab=affidavits` → sign-in page → sign in → the Lien desk on **Affidavits**.
  - `/jobs?tab=stages&lienwindow=<a ZZ test job>&lientab=affidavit` → sign in → that job's Lien window on **Mechanic's lien**. Walked the slow way round on purpose: the reload was held 2.5 s after the session landed.
  - A job door, `/jobs?tab=stages&stagesJob=<a ZZ test job>` → sign in → the Pipeline with the door taken, the same as opening it signed in.
  - A guide, `/help?g=file-a-lien-and-never-miss-its-deadlines&via=share` (where the sheet's other code lands) → through the emailed link's landing with the stored address cleared first, as another browser would have it → the guide.
  - Signed in on `/jobs`, then signed out: the sign-in page, nothing kept.
  - An old address in storage, then the root, signed out: the address cleared, and the sign-in landed on the role's first page.
  - A session aged a day with a dead refresh token, then the lien notice sheet's address → sign in → the job's Lien window on **§ 53.056 notice**.
  - A machine label's address (a code no machine carries) → sign in → that code's page.
  - A real box's address → its public page → **Sign in to record a use or a count** → sign in → the box's screen on **On site**. Nothing was recorded.
  - An address kept two hours before → the role's first page, and the address cleared.
- Before the change the first two landed on the role's first page with nothing stored.

## Is this the best we can do?

- **The session was set by the dev login, not by a typed password.** An agent holds no password. The walk signed in on the sign-in page through `dev-login`'s token and then ran the same reload the form runs. The form's own two lines were read, not pressed.
- **No real email was sent.** The emailed link was walked by opening the address it would land on, with a session in its hash as Supabase writes it. That GoTrue accepts `/sign-in?next=…` as a redirect on the live site rests on the allow list above. If it ever refused, the link would land on the site's root, signed in, which is the old behaviour. Worth one real try by a person: fail a password twice on a scanned address, press **Email me a sign-in link**, tap it.
- **A sign-in that does not pass the sign-in page lands on the first page.** That is a password reset, an invite, and the sign-in email the office sends from People. The person is signed in after it, so a second scan lands right. Sending them on from there would also move a dev who is looking at the app as someone else, so it was left.
- **Not walked on a real phone.** The camera's scan, Safari beside the installed app, and a real emailed link opened from the Gmail app all want one try by a person.
- **A role that may not open a page** is sent where that role is always sent, signed in or not. That is the role guard's rule and is unchanged.
- **A session that ends while a page is open still lands on the first page.** Keeping that page would also keep it for the next person at a shared browser after a sign-out. Left as it was.
- **`/dev-login`, the reset pages and the invite page are not behind the gate**, so they keep nothing and need nothing.
- **Found, not fixed:** an address no route serves (`/help/<slug>` typed into the address bar is one, since a guide's real address is `/help?g=<slug>`) goes to the root, signed in or out. Signed out it now also clears a waiting address, which is the root's rule.
