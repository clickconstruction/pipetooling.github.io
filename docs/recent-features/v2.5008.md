# v2.5008 — Edit Job: a payment moved here and then removed says so (2026-10-09)

Client only. No migration, no edge function. This builds the owner's call of 2026-10-09, from the decisions walk, on *a moved payment that is then removed*. The owner chose (b): a *removed* line in the trace (*$1.00 removed · Robert*), the way the sub sheets write one, and the reason says *removed*, never *unlinked*.

Punch list #22's walk found it ([v2.3576](v2.3576.md) → *Walked 2026-10-08*). $1.00 moved J904 → J907, then Remove took it off J907. J907 kept *$1.00 moved here from J904* over no payment, because the trace drew `moved` events only. Remove had stored the reason *unlinked* although no bill held the payment.

## The line

`jobPaymentTraceLines` (`src/lib/jobs/jobPaymentMove.ts`) now reads `removed` events too. A removal from this job goes right under the *moved here* line of the same payment (by `payment_id`), under its latest arrival when the payment came here twice. Its words:

- `$1.00 removed · Robert`: the amount, then who, then the reason in words.
- The reason comes from `jobPaymentRemovedReasonWords`:
  - Remove stores *unlinked* on every plain removal. With no bill behind the payment (the event's `invoice_id` is null), it adds nothing: the line already says *removed*. With a bill, it reads *unlinked from its bill*.
  - *unlinked_stripe_bill_unrecorded* reads *unlinked from its Stripe bill*.
  - *bank_failed* reads *the bank returned it*, then the bank's reason when there is one.
  - A typed reason reads as typed.

A removal of a payment that never moved here still draws nothing, as before. The held-Stripe move writes a `removed` event on the job it left. That event has the old payment's id, so it never doubles the *moved →* line there.

- **Edit Job** (`JobFormPaymentsTable.tsx`): the removed line is marked ✕ and indented under its arrival.
- `useJobPaymentTrace` reads `invoice_id` with each event.
