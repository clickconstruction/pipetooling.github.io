# v2.5585 — Prospects: the strips wait for their first read instead of saying it failed (2026-10-16)

Punch list #113's eighth PR (Grace, after the walk's report: "should we fix the strips' could not be read flicker too"). The GC work strip (v2.5561) and the bench strip (v2.5560) each held one state that started as `null` and was also set to `null` when the read failed, so for the half second before the first answer every open of Jobs to GC said *the Project Board could not be read* and every open of Subs said *the bench could not be read*. Right words for a failure, wrong for a load.

- **`src/lib/prospects/stripState.ts`** (new, pure; 1 test): `StripRead<T>` is `T | null | undefined`, and `stripReads(state)` reads it as *loading* (undefined, until the first answer), *failed* (null) or *ready* (the rows, even none).
- **`Prospects.tsx`**: `benchTrades` and `gcWork` start `undefined`; each strip draws nothing while `stripReads` says loading, so the deck's area is quiet until the lane answers; a failed read keeps today's words; the counts draw as before. Nothing else reads the states differently (`benchTrades ?? []` already covered both).
- **Docs**: the Prospects map's kind note; the to-do's PR table.

Verified by the kernel test, typecheck and lint, and live on the dev server: twelve paints sampled on each lane's open never showed the failure words, and a read blocked on purpose showed them.
