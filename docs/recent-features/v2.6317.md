# v2.6317 — dev-mcp: a plan set or a paper on a plan part, and a filed set lands on the job's part (2026-11-02)

Punch list #239 (`to-dos/plan-sets-by-part/`) built plan sets by part (v2.6297, v2.6298, v2.6302) and papers beside them (v2.6312, v2.6313). The owner asked whether everything the train added is reachable through the MCP seats: the reads were (`read_rows` on `plan_parts` / `plan_sets`, once the catalog carried them), the writes were not. This PR adds the writes to the dev seat and routes a filed bid set onto the job's part. No migration.

- **Four write verbs** (`supabase/functions/dev-mcp/index.ts`, server 0.14.0; `_shared/devMcpWrites.ts`; the kernel `_shared/devMcpPlanSets.ts`): `plan_plan_set(set)` → `apply_plan_set(set, plan_hash)` and `plan_paper(paper)` → `apply_paper(paper, plan_hash)`, the seat's grammar as `plan_history_entry → apply_history_entry` has it — plan is a dry run under a `plan_hash`, apply re-runs the dry run and writes only when the hash still matches, one apply per plan, refused through `view_as`. **No RPC**: these rows (`plan_sets`, `plan_parts`, a lane's request) are the ones the job window's Plans section writes as rows under RLS (`src/lib/plans/planSetsIo.ts` `addSet`, and `keepPaper` / `markPaperCame` with v2.6313), and no RPC exists for them, so the seat writes the same rows as the dev under the same RLS (`plan_part_can_write`) through `restRows` — the one place a write verb reaches a table and not a dev-gated RPC; `WRITE_VERBS` marks them `rpc: null`. The dry run is the server's own read of the part (`readPlanPartWorld`): the part as it stands (its set count, what it builds from), the row as it will be written, and for a paper the ask and the History line the trigger will write (`planPartDryRun`); the hash commits to all of it, so a set added or switched on the part since refuses the apply.
- **A set** (`set = { part_id? | job_id?, name, kind, source, dated?, memo?, link?, replaces_set_id?, marks_up_set_id?, make_current? }`): a drawing kind only (a paper kind is refused toward `plan_paper`); `make_current` is true when the part builds from nothing and false otherwise unless passed; a set made current replaces the current one, as the section's *Add the set and build from it* does; an as-built is ours, on its job, marks up the current set unless told otherwise, and never becomes what the part builds from. The job's old plans link follows by the database's trigger, and since v2.6344 a switch on a development's part writes the site's History line by trigger too, one per job on the part; the plan shows that line (`partSwitchLine`).
- **A paper** (`paper = { action?: keep | came; … }`): a paper kind, one of five sources (the GC reads *the owner*), `came_on` (today in the company zone when left out), `goes_with_set_id` (a drawing on the part), `replaces_paper_id` (a paper on the part), `owed` (no link; the ask required) and `ask { lane: estimators | dispatch, words }`. Apply writes in the section's order: the question into `estimator_requests` / `dispatch_requests` (`askRow`'s shape, about the job or the site), then the `plan_sets` row naming it, then the lane's push (`notify-estimator-request` / `notify-dispatch-request`, as `sendAsk` invokes it — a push that does not go never fails the keep and the reply says so). `action: came` on an owed paper clears `owed`, lands the link and stamps `came_at`. The History line is the trigger's (`plan_set_paper_words`); `paperHistoryLine` writes the same words into the plan, and the test holds them to the trigger's SQL.
- **A filed set lands on the job's part**: `plan_file_plans` / `apply_file_plans` read the bid's jobs that name a plan part (`filedPlansTargets`), commit them into the plan hash (`job_parts`, so a part made since refuses the apply) and, after `dev_bid_write` stamps the bid, insert a `plan_sets` row on each distinct part (an issued set from the GC with the file's name, size and page count as plan-fetch keeps them), current where the part had no set; a part that refuses is named with its reason and the rest go on (`plan_parts.sets` in the reply). A part that already holds the filed link keeps its row (`planLinkKey`, the database's `plan_set_link_key`): a re-filing lands in the same project folder, and since v2.6342 a job opened from the bid takes the bid's set by trigger. `bid_plan_sets` stays the bid's own, as the ground migration says: *a bid pins what it was priced on*. twin-mcp's `file_plans` (server 1.11.0) does the same after drive-intake answers with a `plans_link` (`landFiledPlans`): the bid's own `bid_plan_sets` row when none carries the link yet, and the part rows, with the admin client as `put_plan_memo` writes.
