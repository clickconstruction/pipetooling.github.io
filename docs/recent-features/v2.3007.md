# v2.3007 — Test-gap audit, pass 23: the Job Follow-Up store gets its first tests (2026-09-07)

Follow-up to v2.3006. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`jobs/jobFollowupStore.ts` (267 lines) is the IO under Job Follow-Up Mode: the stage-day settings, the review history and its reviewer names and job labels, the candidate deck (open-stage jobs merged with the `list_job_followup_activity` RPC), recording a review or snooze, and the "Put back in queue" un-review. Only its candidates cache had a suite (`jobFollowupStore.cache.test.ts`); the rest — three callers across the deck modal, the nudge hook and the queue count — did not.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Every read degrades instead of throwing: settings fall back to the defaults on an empty table or a failed read, reviews / reviewer names / job labels to empty, and a failed activity RPC (migration not yet applied) still yields the jobs, each treated as active right now so none reads "quiet forever". Writes (save settings, record review) throw so the caller can say so.
- The settings row maps both ways, is fetched with `limit(1)`, and is saved as one row with `updated_at` and `updated_by`.
- Reviews come newest-first, capped at 5,000. Reviewer lookups and job labels ask nothing for an empty id list; unnamed users are skipped; labels read "HCP · name".
- Candidates are the jobs in the five open stages; the RPC is called with today's date; a job with no activity row gets the current time and no next-scheduled date.
- Un-review deletes only the newest review of the job, reports false when there is none (no delete issued) or the read fails.
