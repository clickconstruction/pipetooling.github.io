# v2.2779 — Statement round RPC: diff certification with the client's row keys (2026-09-04)

Follow-up to v2.2771 (same afternoon), caught by the pre-first-dispatch fidelity check: `get_statement_round_for_user` reported Malachi 0 ready / 3 held while the GC Review panel showed 2 in his round.

- **Cause.** The RPC keyed every invoice row by invoice id. The GC Review rollup keys a job with exactly one billed invoice by **job id** (`buildBilledStageRows` → `job_with_merged_billed`; `GcReviewRow.key` is the invoice id only for `kind: 'invoice'` rows), so every such GC failed the snapshot diff server-side.
- **Fix.** Migration `20260904202939` ([doc](../migrations/20260904202939_statement_round_client_row_keys.md)) re-creates the RPC with a `group_rows` CTE that re-keys single-invoice jobs by job id before the diff. Applied via db push while this PR merged; the first migration's file is unchanged (immutable once applied — this is why it is a second file). `src/types/database.ts` is the generator's output after the push (no shape change beyond formatting).
- **Second finding, same check.** With every single-line job re-keyed, Loberg flipped to "changed": `buildBilledStageRows` only bundles the single line for jobs whose **status is billed** — a working job's billed break-off stays an invoice row. Migration `20260904204442_statement_round_job_status_keys.sql` ([doc](../migrations/20260904204442_statement_round_job_status_keys.md)) joins `jobs_ledger` for the status. Verified read-only against every round GC: zero unmatched rows.
- **Verified read-only via psql** after the final push: Malachi's payload lists Knight Contracting as ready; RMC- Dudley Mason reads "changed" because it has a real post-certification change (19 certified rows vs 18 live) — the panel shows the same.
