# v2.5863 — The Labor tab saves only after you edit (2026-10-25)

Bid history's last piece (to-do #73). The 2026-10-08 live walk of Put back found that after a Put back the tab's refetch re-armed the Labor tab's autosave, which wrote the same rows back (204s, no ledger rows — the trigger skips an unchanged value). Harmless, but a read should not count as an edit, and every load, bid switch and refetch paid the same write storm.

## The gate

The autosave effect in `BidsLaborTab.tsx` saved everything on a 1.5 s debounce whenever any of its inputs changed identity — and its row arrays (`costEstimateLaborRows`, the five direct-cost tables) are replaced by every load and refetch too. It now runs only while a person's edit waits: `hasPendingLaborCellSaves` (new in `src/lib/bids/laborCellSaveState.ts`, tested) reads the J11-F8 per-cell save map, where every editable input already marks its key on change. A load marks nothing, so it saves nothing. Switching estimates clears the map, so the last bid's unsaved edit never writes onto the next.

## Two edit paths that never marked

Gating on the map made every unmarked edit path a lost save, so both were marked:

- the GSA travel lookup, which fills the meals and hotel rates (`travel:meals`, `travel:hotel`);
- a direct cost's description box in `BidsDirectCostsSection.tsx` (`{kind}:{rowId}:note` — its stage amounts already marked).

Direct-cost add/remove, the labor queue save, Fill from the book and the unmatched band write to the database directly and refetch; under the gate those refetches no longer trigger a redundant full sweep.

## Tests
