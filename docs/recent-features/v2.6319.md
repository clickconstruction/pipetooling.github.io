# v2.6319 — Search every file deeply, PR 1: our own index under Find a file (2026-11-02)

Punch list #240's first PR, the one that needed no decision: a text index of our own in Postgres, fed on a press and by a sweep, read by Find a file before Drive. Migration `20261102040500_file_index.sql` (`docs/migrations/20261102040500_file_index.md`); `drive-link` and the new `file-index-sweep` deployed after the push, `dev-mcp` redeployed for its catalog.

- **The table.** `file_index`: one row per Drive file in the jobs Shared Drive, keyed by Drive's id, with its job or bid (walked up through the folder links the app knows, as Find a file's search does) and the job's customer, which of the job's folders holds it (`folder_kind`: top, plans, pictures, photos, sent, other), the folders between (`path`), name, kind, size, modified time, the extracted text capped at 200,000 characters with its source (`export`, `pdf_layer`, `plain`; `ocr` is PR 3's) or why there is none (`scan`, `kind`, `big`, `slow`, `error`, and `reading`, the stamp a request leaves before it reads), a PDF's page count, and a stored tsvector weighted name A, path B, text C with a GIN index. The office and the estimators read through RLS (`is_office_or_estimator`); only the service role writes. The RPC `search_file_index(words, max_hits)` ranks with `websearch_to_tsquery` and `ts_rank_cd`, and computes a `ts_headline` with `<mark>` around the words for the rows that made the cut alone (a materialized CTE), with the job's and bid's numbers and names joined in.
- **One reader, lifted.** v2.6306's `fileText` moved out of `drive-link` into `_shared/fileText.ts` (the same caps: a PDF under 8 MB and 40 pages through unpdf's dynamic import, under 20 characters being a scan; a text file under 2 MB; a Google file exported as text; a picture a scan), the folder homes and the cached folder reads into `_shared/fileHomes.ts`, and the walk itself with every pure rule into `_shared/fileIndexKernel.ts` (no imports, tested from `src/lib/documents/fileIndexKernel.test.ts`). The excerpt line reads through the same reader, so there is one.
- **The pass, and the CPU limit.** `_shared/fileIndex.ts` is the one pass every indexer runs: the plan against the table (`indexPlan`: a file not in the table or modified since its row; a held row only with `retry`), then one file at a time inside a wall-clock budget, each walked up, stamped `reading`, read, and upserted, answering `indexed`, `held` with the reason and `remaining`. An edge function has about two seconds of CPU per request and a 40-page PDF can spend it, so a request the platform stops mid-read leaves its `reading` stamp, which the next pass reads as held (`slow`) instead of reading the same file again forever; the caller loops on `remaining`.
- **`drive-link`'s doors.** `{ action: 'index', driveFileId }` indexes one file; `{ action: 'index_job', job, retry? }` lists the job's folder tree three levels deep (its plans and pictures links too, when an older job keeps them elsewhere) and takes forty files a call, the held list being every held row of the job once nothing remains. Both write our table and never Drive, so a training account is refused. `parseOfficeAsk` takes the two asks (`driveLink.test.ts`).
- **`file-index-sweep`.** A new cron function every ten minutes (three minutes past the folder sweep's slot) with the cron secret: the files modified in the Shared Drive since its stamp (`app_settings` `file_index_sweep_last_at`, less two minutes), oldest first, forty a run, indexed through the pass; twenty rows with the oldest check asked about in Drive, a trashed or gone file losing its row and a changed one indexed again; the stamp moved to now when it handled everything and Drive had no more, else to the cursor `passCursor` gives (the last listed file handled, taken or passed over as current, stopping at the first left untaken), so a page of files the backfill already indexed never holds the stamp (found in review by the backfill session before the merge). `config.toml` keeps `verify_jwt = false`; the dev-mcp catalog lists it for `check_edge_boot`.
- **Find a file.** `findAFileIo.searchJobFiles` calls the RPC first (`search_file_index`, thirty hits); rows become hits with the headline's marks as the excerpt (`headlineToExcerpt`, two marks a space apart merged so the phrase bolds as one) and `text_why` as the quiet note; no rows, or the RPC refusing (the migration not pushed yet, a role outside the policy), falls back to `drive-link`'s `search` exactly as before. `FindAFileRead.source` says who answered and the count line reads *3 files say “rock clause”, from our index.* or *…, from Drive.*; the hint under the box says the order.
- **Index this job's files.** `JobDocumentsIndexFolder` under the job window's Documents tab's In the folders, for the office roles that make folders: the press runs `index_job` round after round until nothing remains (at most fifty rounds), counting as it goes, then says what was indexed, lists up to five held files with the reason and the rest as a count, and offers *Try the held files again* when a held file read slowly, failed or was too big; a refusal shows its reason with Try again; a job with no folder links draws nothing. Kernel `lib/jobs/jobIndexFolder.ts`, io `jobIndexFolderIo.ts`, render smoke `JobDocumentsIndexFolder.render.test.tsx`.
- **Guide.** *Find a file when you do not know where it is* gains *What the search reads*: the order, what the index reads today, the press, the sweep.
- **Hardened in review before the merge.** The pass compared Drive's `modifiedTime` (`2026-10-14T15:00:00.000Z`) with the row's `modified_at` as PostgREST reads it back (`2026-10-14T15:00:00+00:00`) as strings, so every known row counted as changed: a job of more than forty files would have re-read its first forty on every press and never reached `remaining` 0, the recheck would have re-read twenty rows a run (its `reading` pre-stamp nulling good text first), and a PDF that killed a request would have been re-read every run — `sameInstant` compares the instants. `filesChangedSince` answered `more: false` when the cap landed on a page boundary, so a burst of sixty photos would have lost twenty — `more` is the next page token. The two-minute overlap could hold the stamp still forever once forty files sat inside it, all current — a stamp that is a file's modified time now carries `#cursor` (`SWEEP_CURSOR_MARK`) and is listed from inclusively with no overlap; a wall-clock stamp keeps the overlap. The stamp is seeded at `now()` by the migration (the history is the backfill's; set it to 1970 to walk the whole drive). The recheck dropped a row on any 403, which is also how Drive says a rate limit — a rate-limited row stays. A Google Sheet exported as `text/plain`, which Drive refuses, so every Sheet was `kind` — `exportMimeOf` asks for CSV; a refused export is `error` (a retry reads it again), `kind` only on a 400, `big` on `exportSizeLimitExceeded`. A jobs root Drive does not answer for made the sweep list every drive the account sees — it is the request's failure now. The 200k cut lands on a whole character (`cutText`). `file_index_customer_idx` for the customer key. And Drive's search fills in behind the index's hits now, as the hint promised (both asked at once, `driveBehindIndex`), so a hit from the index never hides the file Drive would have found while the index is only part full. The select policy admits a digital twin, since a twin is an estimator; v2.6396 closes that.
