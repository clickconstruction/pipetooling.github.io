# v2.3600 — Pipeline load speed, PR 2: the board paints first, the enrichment lands after (2026-09-18)

PR 2 of four in [`to-dos/pipeline-load-speed/README.md`](../../to-dos/pipeline-load-speed/README.md) (Grace, 2026-09-16: *"look at the jobs, stages tab, and look at load speed"*). Client only; the screen does not change.

## The change

- **Two halves in the loader** ([`fetchJobsLedgerWithDetailsForStages.ts`](../../src/lib/fetchJobsLedgerWithDetailsForStages.ts)): `fetchJobsLedgerStagesPrimary` (the scope query, the ready-to-bill companion, the min-HCP floor) → `primaryRowToJobWithDetails` (one mapper, shared with the Job Summary slim path); `fetchStagesEnrichment(ids)` runs the three passes — materials + fixtures, schedule work dates, estimate candidates — **together with `Promise.all`**, each in `.in()` chunks of 150 and each degrading on its own. `fetchJobsLedgerWithDetailsForStages` is the two halves in sequence, so the AR page, Job Summary, Dispatch and the full-list load are unchanged in shape and faster in the second half.
- **Kernel** [`lib/jobs/stagesEnrichment.ts`](../../src/lib/jobs/stagesEnrichment.ts) (3 tests): `applyStagesEnrichment` puts the four fields on rows; `patchJobsById` lays enriched rows over the cache by id — only those four fields, so a mutation that landed meanwhile keeps its status and money, a row that left the board is not resurrected, and a row the enrichment did not cover is left alone.
- **The Stages cache paints first** ([`JobsListCacheContext.tsx`](../../src/contexts/JobsListCacheContext.tsx)): `runFetchScopes` and `fetchScopeIfNeeded` fetch the primary rows, `setJobs` them, clear `jobsListLoading` / `scopeLoading`, release the in-flight lock, and only then run **one** `fetchStagesEnrichment` across every painted row (not one per section) and patch it in. `jobsListEnriching` is exposed for the interval; an enrichment for a board that has since changed key is dropped, not applied. `runFetchJobs` (other tabs) is unchanged.
- **Three board-keyed effects key on the id set** and no longer re-run when a scope merge or the enrichment patch re-mints the same rows: the Activity column's next-appointment read (`fetchStagesUpcomingScheduleForJobs`, held until the list has loaded), and the GC statement-sender reads in the tab and in `usePipelineMoneyOpportunities`.
- Readers of the four fields already read "not yet" as empty: no stage bar until the fixtures land (`stageBarAvailable`), the field date falls back to `last_work_date`, the estimate footer renders nothing for `null`.

## Measured (dev server, prod data; cold page on Reports — a tab that does not load the list — then an SPA click to Pipeline, every section open; two runs after)

| | before | after |
|---|---|---|
| Board visible (rows on screen) | 1.09 s | 0.74 s · 0.83 s |
| Supabase requests before the board | 16 | 12 |
| Requests per visit | 66 | 66 |
| Enrichment passes landed | (with the board) | ~2.1 s |
| Last response ended | 3.36 s | 3.44 s · 3.80 s |

The board shows ~0.3 s sooner, from 12 requests instead of 16, and every section fills in at once instead of section by section. The count did not fall: the device's open sections still load as one scoped fetch plus two on-demand scope merges, and each merge enriches its own rows — three rounds of the four passes, as before. That is PR 3's shape (one RPC per round). The last response is the labor loaders' tail (`people_hours_recorded` × 3 pages), unchanged.
