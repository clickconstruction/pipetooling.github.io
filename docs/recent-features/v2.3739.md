# v2.3739 — Approving on an iPhone: the Full name box keeps what AutoFill put in it (2026-09-22)

Reported by a customer over text the same morning, with a screenshot: the Approve Estimate sheet on iPhone Safari, the Full name box empty, the agree box ticked, *Please enter your full name.* in red — "it defaults right back". Client only, no migration.

## What was wrong

Every signing surface held the name in a **controlled** input (`value={printedName}`). React rewrites a controlled box from state on every render. iOS Safari's AutoFill — the contact-name suggestion above the keyboard, offered because the box says `autocomplete="name"` — writes into the box **without firing an input event** (a long-standing WebKit behavior: [facebook/react#1159](https://github.com/facebook/react/issues/1159), [ErrorPro/react-google-autocomplete#199](https://github.com/ErrorPro/react-google-autocomplete/issues/199)). So state stayed `''`; the next render — ticking the consent checkbox, or the scroll-driven `approveInView` flip — put `''` back in the box. Submit then saw an empty name. Reproduced in the current build at 375 px by setting the box's value without an event and ticking the checkbox: the box read `''` afterwards.

The customer's screenshot also shows the pre-v2.3118 sheet (one checkbox, the old disclosure) under a *A new version is ready* pill: her Safari was serving a build from before Sep 8 out of the service-worker cache (she is a repeat customer — seven estimates). That did not cause the bug (the same controlled input is in every build) but it means this fix reaches her only after she taps **Reload**.

## The change

- **[`signerNameField.ts`](../../src/lib/signerNameField.ts)** (+4 tests) — `resolveSignerName(stateValue, domValue)`: the box's text wins over state, trimmed; `drifted` says the caller should sync state.
- **[`SignerNameInput.tsx`](../../src/components/contracts/SignerNameInput.tsx)** (+3 render tests) — the shared Full name box, **uncontrolled**: `defaultValue`, state follows on change *and on blur* (blur catches a silent fill), a parent-driven `value` change (a reset, the staff preview's `''`) writes through in an effect keyed on `value` only — so a re-render with unchanged state never touches the box. `autoComplete="name"` stays (the suggestion is the point).
- **`EstimateAcceptBody`**, **`ContractAcceptSignatureForm`** (contracts, sub portal, job contract sign, lien release), **`BidRoom`** (the proposal sign and the change-order card) — each renders `SignerNameInput` through a ref and its submit reads the box with `resolveSignerName`, syncing state when it drifted. Nothing about the payloads, the hints or the cursive preview changed.

## Not run live on iOS

No iPhone was available to the session (the simulator runtime is installed but not Xcode, so nothing can tap in it). The mechanism was reproduced and re-verified in the browser pane at phone width; the AutoFill trigger itself is the documented WebKit behavior above.
