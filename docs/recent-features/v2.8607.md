# v2.8607 — Working hours: taking them off a salaried person leaves the standard week (2026-11-25)

Punch list #429, the fault the live test of 2026-11-24 found. The owner's two answers of 2026-11-25. Asked *Taking working hours off a salaried person leaves the week's hours as they were last set. What should taking them off leave?*: *"Clear the week's hours too"*. Asked the same day, in a second round, whether the picks stood, among them *#429: clearing a salaried person's working hours leaves the standard week, not zero paid hours* with the pick *The standard week*: *"Yes, all picks"*. Together: the week's own hours are cleared, and the person falls to the standard week.

**Read.** `set_working_hours` (`20261123075925_working_hours_door.sql`) worked out `v_moved` only when `p_days` was not null. A take-off wrote its `person_available_hours` row and never touched `people_pay_config.salaried_week_hours`, so the seven numbers stayed where the last set put them. The row's window said so: *Their set week on pay stays as it is.* The column is `NOT NULL DEFAULT '{0,8,8,8,8,8,0}'`, and both readers of a week, `salaried_hours_on` in the database and `salariedWeekOf` in the app, take that default as 8 hours Monday to Friday. So the standard week is that value written, never a null and never seven zeros.

**The mend.**

- **Migration `20261125225108_working_hours_take_off.sql`** replaces the function, with the same arguments and the same answer. A take-off for a salaried person with a set week in force, whose pay row holds another week, writes the standard week. It is a change to pay like any other: it starts this week, it needs a reason, and it leaves one `pay_admin_events` line with the row before and after. A dry run answers `pay.moved` and `pay.after` for it. No table is made or changed, and no row is corrected. Page: `docs/migrations/20261125225108_working_hours_take_off.md`.
- **A take-off with nothing in force moves no pay.** A week typed on pay for a person nobody set hours for still stands. So do hours saved for next week and taken off before they start. The screen offers no take-off there, and the door holds the same line for any other caller.
- **`workingHoursTakeOffPlan`** (`src/lib/people/workingHoursEdit.ts`) is the window's plan: whether pay moves, the Sunday, the words and the line said after. It reads the same facts as the field's plan and counts the earlier weeks with no pay report the same way.
- **The row** (`PersonDeskWorkingHoursRow.tsx`). When pay moves, **Take working hours off** opens a window with a box, and its press is dead until the box holds words. The window says what the week on pay is today and that it goes back to the standard week. When pay does not move it is the plain confirm, with one line that pay stays on the standard week for a salaried person.
- **The guide** `set-someones-working-hours` gains *Take working hours off*.

**Not in this PR.** The dev seat's `plan_pay_setup` still plans a take-off as moving no pay. Its apply goes through the same door, so after the push the door's rule holds there too: a take-off from next week that would move pay is refused in the door's words, and one from this week resets the week with the seat's reason on the pay log. The plan's words are behind until the seat's planner reads the rule, which is a `dev-mcp` version of its own.

**Rows on prod.** Read through the dev seat on 2026-11-25, nothing written. Three pay rows are salaried, and none of those people has a set row. The only set rows belong to two ZZ Test people, both with their hours off and neither salaried. So no pay row is in the fault's state, and nothing needs correcting.
