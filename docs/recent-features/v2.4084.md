# v2.4084 — Autosave keeps a change you undo while it is saving (2026-09-28)

Client only; no migration, no edge function. Found on punch list #51's live walk (PR 4b, v2.4083) and reproduced on `main` — not caused by that train.

## The bug

`src/components/jobs/useJobFormAutosaveSlice.ts` — the autosave engine behind Edit Job (through `useJobFormAutosaveEngine`), Edit Bid and the Estimates draft. Its effect starts the debounce when the slice differs from the baseline, and the baseline moves only when a save resolves. An edit made **while a save is in flight** that puts the slice back to the value **from before that save** matched the old baseline, so the effect started no clock. When the save then landed, the baseline became the value just saved and the slice was dirty — but no dependency changed, so nothing rescheduled a save. The form sat at "Unsaved change…" until the close guard's flush or the tab-hidden flush wrote it.

Live, on the Bids page (b464 ZZ Takeoffs Test): project name changed, then restored 2 s later while the first save (PATCH + the board reload, ≈2.1 s) was still running — one PATCH, then nothing; the row kept the changed name until the window was closed. Edit Job's save is fast (≈0.2 s), so there it needs a quicker hand, but the engine is the same.

## The fix

When a save succeeds and the slice is still dirty and enabled, with no clock running and no follow-up queued, the slice starts the clock (its own `debounceMs`). The other in-flight cases were already right and are unchanged: an edit to a new value starts the effect's clock, and a clock that fires during a save queues one follow-up. A disabled slice starts nothing (and the effect starts the clock itself when it is enabled again). A new unmount cleanup drops that clock, since no run of the effect owns it.

## Verified

- `useJobFormAutosaveSlice.lifecycle.render.test.tsx` gains three cases (28 now): the put-back value saves on the clock after the save ends (red before the fix); the clock does not start on a disabled slice, and unmounting drops it; an edit to a new value during a save is saved once, not twice. Four deliberate breaks of the fix — no unmount cleanup, ignoring `enabled`, ignoring a running clock, saving at once — each caught.
- Live on the dev server: the Bids walk above now writes the change, then the restore 1.2 s after the first save ends, then "Saved"; closing writes nothing more. Edit Job on *ZZ TEST Row 4 live check* — change and restore the name: two writes, "All changes saved", the row as it was.
