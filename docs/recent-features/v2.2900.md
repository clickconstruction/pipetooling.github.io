## The kernel — `src/lib/workflow/stepAssignment.ts` (+ `stepAssignment.test.ts`, 10 tests)

- `WORKFLOW_ASSIGNABLE_USER_ROLES` — every role the app knows (`ROLES` from `src/lib/userRoles.ts`), so a new role is assignable without touching Workflow. The test pins it equal to `ROLES` and names the office roles the old superintendent list left out (dev, master, assistant, controller, estimator, superintendent). RLS (`Users can select users`, 20260905090000) decides what each viewer gets back — a superintendent reads office roles through the literal role arms plus `master_adopted_current_user`, which is why widening the client list is enough.
- `buildWorkflowUserRoster(rows)` — splits one users read into the picker `roster` (`activeRosterOnly(..., { includeDev: true })` from #19's `src/lib/people/activeRoster.ts`: no twins, no archived, dev kept because the owner takes steps) and `userNamesLower` (every readable account — the "(not a user)" suffix compares against this, so a step held by an archived account is not re-labelled a ghost for dev viewers). Chosen over `fetchActiveUsers` because that helper filters archived/twins server-side and the page needs both sets from one read.
- `notifyAssignedDefaultsOnAssign(previousName, nextName)` — returns `NOTIFY_ASSIGNED_ALL_ON` only when a blank assignee becomes a person; reassignment (A → B) and clearing return `null` so an office that switched a toggle off keeps that choice.
