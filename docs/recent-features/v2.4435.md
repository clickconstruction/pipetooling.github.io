# v2.4435 — Submittals: the groundwork for fixtures you buy without the GC (2026-10-02)

Wendi, 2026-10-02, on BP375: "some items do not need to be on submittals, so can we have a way to deselect and exclude items from this process?" The owner's pick: each fixture, and each part, is one of three — *GC sees it*, *Order only* (bought, never shown to the GC) or *Left out* (not submitted, not ordered). Mock-up, two passes: https://claude.ai/artifact/VHfgwjigciY5BjkGKmtYiv

PR 1 of the train: where the state lives, and every GC-facing reader leaving it out, before any screen can set it. Migration [`20261002193129_submittal_order_only`](../migrations/20261002193129_submittal_order_only.md); three edge functions to redeploy after the push.

## What was missing

Today a fixture is either a row on the revision or not. The × on a draft row deletes it and unticks it on the takeoff list, which also drops it from the procurement log, because the log is built from the revision's rows. *Order only* existed for a part (`bid_submittal_item_parts.on_submittal`) and not for a fixture. Nothing on the GC side filtered rows: the room, the package and the GC's copy of the log read every row.

## What changed

- **The flag.** `bid_submittal_items.order_only`. It is the one truth: no reader infers the state from a row's parts, which keep their own picks underneath.
- **The kernel** [`orderOnly.ts`](../../src/lib/submittals/orderOnly.ts): `isOrderOnlyRow` (only a stored true), `gcRows`, `orderOnlyRows`, `orderOnlyInsert` (names the column only when true, so an insert is accepted in the window between the client deploy and the push).
- **The GC's room.** `gcRoomItems` and `officeOnlyTags` in [`_shared/submittalRoomPayload.ts`](../../supabase/functions/_shared/submittalRoomPayload.ts). `roomRowsFrom` leaves order-only rows out, so the room, *What the GC sees* and the *The GC's page reads* line agree. `get-submittal-room` drops the rows before it loads their parts, and keeps their procurement lines out of the payload. `submit-submittal-review` drops a call on one.
- **The office's counts.** The tab builds `gcItems` once. The tiles, *N still need a cut sheet*, the decisions summary, *They approved all of it*, the package, the page walk, the sheet strip and the robot's confirms read it.
- **The robot.** `twin-mcp` `next_submittal_task` leaves order-only rows out of `rows_on_revision`.
- **The state survives.** A new revision (`carriedRowInsert`), a rebuild from the picks (`PreviousItem.orderOnly` → `SubmittalRowDraft.orderOnly` → `draftToItemInsert`) and a split keep it.

## Not yet

Nothing sets the flag. The procurement log's rule for an order-only row (ready to order without the GC's call) and its place on the GC's copies ship with the screen that sets it, in PR 2.
