# v2.6019 — Developments on bids: the column, the picker, the board, and the suggestion by address (2026-10-28)

Punch list #208, PR 1 of six (`to-dos/developments/README.md`). A development is already a record on jobs (v2.1198): a named row, the house icon on the Pipeline, a filter, GC Review's By development. The owner asked for it on bids too, so a site with many moving pieces reads as one thing. The real example has 13 bids and 29 jobs at one address, 9 of the jobs tagged and none of the bids, so the suggestion by address ships in the same PR: without it the real site would be 33 edits.

## What changed

- **Migration** [`20261028170000_bids_development_id.sql`](../migrations/20261028170000_bids_development_id.md): `bids.development_id uuid references developments(id) on delete set null`, the partial index `idx_bids_development_id`, and the backstop `bids_development_master_match`, which mirrors the job's trigger as it stands — a no-op under one company (v2.2984), kept as the hook for a same-master rule. `bids` carries no `master_user_id`, so there was no column to compare against in any case.
- **Edit Bid** ([`BidFormModal.tsx`](../../src/components/bids/BidFormModal.tsx)): the Links cluster at the top right gains **Development** beside Project — [`BidFormDevelopmentPicker.tsx`](../../src/components/bids/BidFormDevelopmentPicker.tsx), the same select and inline *+ New development* as `JobFormDevelopmentEditor` over the same kernel (`developmentPickerOptions`, `validateNewDevelopmentName`); the list and the create come from [`useDevelopmentPicker.ts`](../../src/hooks/useDevelopmentPicker.ts) (a name-only row under the company owner), so `Bids.tsx` threads nothing new. The field is `developmentId` in `useBidEditForm` (reset, load, values, setters), `development_id` in `bidFormPayload`, and its own group in `bidUpdatePrune`, so the Edit tab's autosave writes it alone when it alone changed and never clobbers it otherwise. Office roles may create; an estimator picks from the list.
- **The Bid window** ([`BidPreviewModal.tsx`](../../src/components/bids/BidPreviewModal.tsx)): a house line under the number line with the development's name, a plain label until PR 2 makes it the door to the Development page. `fetchBidForPreview` and the board's `loadBids` (`useBidsPageData`) embed `development:development_id(id, name)`; `BidWithBuilder` gains `development`. The preview's select constant is typed as a plain string: the literal grew past what supabase-js's type parser walks.
- **The Bid Board** ([`BidsBidBoardTab.tsx`](../../src/components/bids/BidsBidBoardTab.tsx)): the house line under the GC on the desktop row and the phone card, a *Development* fact in the opened row, the search matching the name, and a house filter beside the search that appears once any bid has a development — *All developments*, each by name, *No development set* — narrowing every section and count. Kernel [`bidBoardDevelopment.ts`](../../src/lib/bids/bidBoardDevelopment.ts) (`developmentFilterOptionsFromBids`, `filterBidsByDevelopment`, `bidMatchesDevelopmentQuery`, `bidDevelopmentName`, `developmentFilterLabel`), the Pipeline's `jobsStagesBoard.ts` pair as the pattern. The empty words ([`bidsEmptyWords.ts`](../../src/lib/bids/bidsEmptyWords.ts)) name the filter — *None of the bids are in Harlow Ranch. All developments* — and one press clears it with the search and the Marked switch when several hide the rows.
- **New Job from a won bid** ([`useJobFormImport.ts`](../../src/hooks/useJobFormImport.ts)): the import reads `development_id` and sets the job's Development with the customer and the address; a bid with none leaves the field alone.
- **The suggestion by address**: kernel [`notInIt.ts`](../../src/lib/developments/notInIt.ts) — `normalizeAddressKey` (case, punctuation, spacing, a trailing zip and the common street suffixes), `suggestDevelopmentByAddress` (the development whose members share the address, the record itself never counted, archived and unnamed developments never named, the larger group when two share an address) and `developmentSuggestionWords` (*4 bids and 6 jobs at this address are in Harlow Ranch.* · **Put it in Harlow Ranch**, `pluralNoun` from `batchWords`). [`useDevelopmentAddressSuggestion.ts`](../../src/hooks/useDevelopmentAddressSuggestion.ts) reads the members (every bid and job in a development, with its address) once per open of a saved record with no development; [`DevelopmentAddressSuggestionLine.tsx`](../../src/components/developments/DevelopmentAddressSuggestionLine.tsx) draws the line on Edit Bid (under the header cluster) and on Edit Job (under the Development fact row, [`JobFormEditFactRows.tsx`](../../src/components/jobs/JobFormEditFactRows.tsx)); the press sets the field and the form's own save writes it. PR 3's page line reads the same kernel.
- **Tests**: `bidBoardDevelopment.test.ts` (+8), `notInIt.test.ts` (+11, the line held to the plain-words rules), `bidsEmptyWords.test.ts` (+4), `bidFormPayload.test.ts` (+1), `bidUpdatePrune.test.ts` (+1); the form-values literals in five tests and the import hook's render test gain the field.
- **Docs**: the guide `group-jobs-into-a-development` becomes *group bids and jobs into a development* (slug unchanged; estimators added to its roles; Put a bid in a development, Let the address do it, the Bid Board and Bid window lines); `GLOSSARY.md` → Development; `BIDS_SYSTEM.md` (the `project_id` paragraph, Search Functionality, Table Columns, the schema block); the migration doc.
