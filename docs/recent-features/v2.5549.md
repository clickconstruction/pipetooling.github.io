# v2.5549 — Messages: a text from a number on the roster lands on that teammate (2026-10-14)

The second PR of the owner's ask of 2026-10-14 (the first, v2.5546, gave the spine its eighth kind, the card its *One of our own team* choice and today's roster its contacts). The seed covers the roster as it stood when the migration ran; a teammate added after it, or given a number later, would still have arrived as a number nobody has named. Migration `20261015020000_quo_place_number_roster.sql`; no client change, no edge function change (the webhook already reads `placed_kind` through `contactKindOf`, which knows `team` since v2.5546).

- **`quo_place_number`**: when no contact holds the number (`contact_for_channel` finds nothing), it reads the roster before it makes an unknown contact: a `people` row, not archived, whose phone has the number's key (`contact_channel_key`). The line lands on that person's contact, made now with the roster's kind (`sub`, else `team`) when the seed has not made it, with the number as its channel; `made` says whether the contact is new. An archived person's number is nobody's, as before. The office's own presses are unchanged; the function stays the service role's.
- **Tests**: the SQL bed `supabase/tests/quo_messages` (+4 under *the roster's own numbers*: a helper's number lands on them, made now, with the roster's name; the same number again lands on them, made no more, and one channel holds it; a sub's number lands on the sub; an archived person's number makes an unknown contact). Docker is not running on this Mac, so the bed runs in CI's SQL beds workflow.

What does not change: a number the roster lacks still comes through *Who is this?*, and *One of our own team* writes it onto the roster (v2.5546), so the next text from it is theirs by this rule.
