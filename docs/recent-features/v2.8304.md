# v2.8304 — Documents → Photos: the list shows the chip you pressed last (2026-11-22)

Found on the live walk of v2.8215 (punch list #306, PR 9), next to the list's timeout (v2.8301). A client change. No migration, no edge function.

## What was wrong

Documents → Photos asks again on every chip and every typed word, so more than one read is out at once. They do not come back in the order they left. On the walk the first screen's read, **All**, took eight seconds and failed. **Bid photos**, pressed meanwhile, read in a third of a second. The failure then landed, and its red line sat over six photos that had read.

The same gap let a slow read that succeeds replace the rows of the chip pressed after it.

## What changed

- **The newest ask wins** ([`newestAsk.ts`](../../src/lib/newestAsk.ts)): `next()` starts an ask and hands back a check that is true only while no later ask has started. Pure, with its own test.
- **The Photos tab's `load`** ([`DocumentsPhotosTab.tsx`](../../src/components/documents/DocumentsPhotosTab.tsx)) takes a check for each read. A read that is no longer the newest drops its rows and its failure, and leaves the loading mark to the read that is.

## Checked

- `newestAsk.test.ts`, three tests.
- `DocumentsPhotosTab.render.test.tsx`, two new tests over a fake io with a first read held open: one fails it late, one lands it late. Both fail with the check taken out.
- Not walked live. Once v2.8301's migration is pushed the first read no longer takes eight seconds, so the race is hard to make by hand.

## Left

Other lists that ask again on a chip were not read for the same gap. `JobPhotosWindow` already guards its reads with a `live` flag.
