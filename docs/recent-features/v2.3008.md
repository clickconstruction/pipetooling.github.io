# v2.3008 — The primary address is a property (2026-09-07)

Customer properties train, PR 2 of 4 (v2.3004 shipped the property lookup). One migration (`20260907100000_customer_address_primary.sql` — **`supabase db push` after merge**); no edge function.

## Why

Only "additional" address rows could carry the legal record (county, legal description, owner of record) or be linked to a job through `jobs_ledger.customer_address_id`. The primary address was a plain string on the customer, so the customer's own house — the most common lien target — could not be lien-ready without being typed twice. The mock-ups made the primary a starred row in one list; this PR lays that foundation without moving any consumer off `customers.address`.

## What shipped

- **Migration**: `customer_addresses.is_primary` (one per customer, partial unique index), a backfill that gives every addressed customer a primary row (starring an existing row that already spells the address), and sync triggers in both directions so `customers.address` is a mirror of the ★ row — the New Customer page, `merge_customers` and every map link / picker / prefill keep reading and writing `customers.address` unchanged. Details in `docs/migrations/20260907100000_customer_address_primary.md`.
- **Edit customer → Addresses (N)** (was "Additional addresses"): every property in one list, the ★ primary first with a *Primary* tag; ☆ on any other row sets it as primary (the trigger demotes the old one and the form's Address field follows). Editing the ★ row's address and saving updates the Address field too; the Address field's hint says where its legal record lives.
- **Customer page** contact band: the primary row is no longer repeated beside the header address (the hub filters `is_primary`).
- Pickers that already list `customer_addresses` rows (Job form → Property record, lien release / instruments / prefill) now naturally include the primary property, so the customer's own house can be linked and become lien-ready.
- `database.ts` carries `is_primary` by hand until the next gen-types run; every read is `select('*')`, so the client works before the push (the ★ write fails with a toast until then).

Deliberately not moved: the form still has its Address field — PR 3 (the two-column modal) removes it in favour of the list.

## Verify

After the push: Edit customer on a customer with one address → Addresses (1) shows it starred. Add a second address, click ☆ → it becomes ★, the Address field and the hub header change to it, the old one stays as an extra. Edit the ★ row's text → Save address → the Address field matches. Job form → Property record picker lists the primary property.
