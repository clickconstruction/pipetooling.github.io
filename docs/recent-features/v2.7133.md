# v2.7133 — Bid photos: a photo whose first send was cut off lands on the next try (punch list #306, after PR 8) (2026-11-13)

A bug in v2.7097 (PR 8), found the morning after it merged and before it was live, by reading the bucket's policies and then asking the project. No migration and no edge function change.

## What was wrong

- `sendBidPhoto` uploaded the shot with `upsert: true`. The `bid-photos` bucket has insert, select and delete policies and no update policy (migration `20261110195527_bid_photos`). An upsert onto an object that is already there takes the update path, and the project refuses it.
- Read on the project on 2026-11-13 with one test object under the ZZ Test bid's folder, deleted after: the first upload answered 200; the same upload again answered HTTP 400 with status code 403, *new row violates row-level security policy*; the same upload with no upsert answered HTTP 400 with status code 409, *The resource already exists*.
- When it bites: the replay sends a kept shot again only after a try failed. When that try's upload had landed and its answer was lost, or the upload landed and the row write was lost while the bytes could not be taken back, every later try was refused. `sendKeptPhotos` counts a refusal as a failed try, so the press waited, the bar turned red the next morning, and the photo never landed although its bytes were in the bucket. v2.7097's fragment said the opposite, and that sentence is amended.

## What changed

- `sendBidPhoto` (`src/lib/bids/bidPhotosIo.ts`) uploads with `upsert: false`. An upload refused because its object is already there (`bytesAlreadyThere`, `src/lib/photos/shotTiles.ts`) goes on to the row, an upsert on the shot's id that the row's update policy allows its adder. The path carries the shot's own id, minted on the phone, so what is there is this shot. A first send is the same insert as before.
- An update policy on the bucket would also have fixed it. It was not chosen: it lets a person overwrite a photo's bytes to fix one resend, and it needs a migration pushed to prod.

## Not changed, and found in the same reading

The job photos, task photos, report photos and counter ticket sends upload with `upsert: true` too (`jobPhotoNotesIo.ts`, `taskPhotosIo.ts`, `reportPhotosIo.ts`, `ticketsIo.ts`). The `job-photo-notes` bucket has no update policy either (migration `20261102171500_job_photo_notes`); the other three buckets were not read. Each of those queues' resends after a lost answer is likely refused the same way. They are not fixed here: each is its own feature's, and `bytesAlreadyThere` is the two lines each would take.

## Test

`npx vitest run src/lib/bids/bidPhotosIo.test.ts src/lib/photos/shotTiles.test.ts`. The send with the storage client mocked on the shapes the project answered: a first send uploads once with no upsert and writes the row; a resend answered *already exists* writes the row and takes nothing back; an upload refused for another reason throws and writes no row; a lost signal throws with the network kind; a row refusal takes the bytes back. The first two fail on the old send.

Walked live on clicktooling.com on 2026-11-13, at phone width on the ZZ Test bid: the first upload of a photo reached the office (200) and its answer was dropped in the browser, so the tile read *Kept on this phone.*; the next try answered *The resource already exists*, wrote the row (201) and added the photo (200), once. The test photo was taken back after.
