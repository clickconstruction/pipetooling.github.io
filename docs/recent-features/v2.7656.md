# v2.7656 — Prospects: a card is free for the next caller as soon as you move on (2026-11-17)

A fix, found by the Prospects page's first render test (v2.7615) and held until the page's cuts were done. The owner said to fix it.

**The defect.** The calling lock (v2.2850) is taken on intent and meant to be released when the caller moves on. All eight releases were written `void supabase.from('prospect_calling_locks').delete().eq(…).eq(…)` with nothing after. The Supabase client sends a query only when it is awaited: its builder is a thenable, and the request goes out inside `then`. So none of the eight was ever sent. A lock stayed until it went stale, 30 minutes on, and for that long the prospect was hidden from every colleague's deck.

**The fix.** `releaseCallingLock(prospectId, userId)` in `src/lib/prospects/callingLockIo.ts` builds the delete and ends it in `then`, which sends it. A refusal or a lost signal is let go: the lock is advisory and a row left behind goes stale by itself. All eight sites call it:

- the release effect in `useCallingLock` (another card, another tab, leaving the page), which still releases only a lock this tab took;
- `handleNoLongerFit`, `handleCantReach`, `handleConverted`, `handleBenchSave`, `leaveQueueAsLanded` and `handleNextProspect` (twice), which release the caller's own row on the card they leave.

Didn't Answer and Answered still release nothing: the caller is still on the card.

**The table's rule** already allows it: a caller may delete their own lock row (the baseline's policy). Nothing to migrate.

**A guard, so the shape cannot come back.** `src/lib/unsentQueries.test.ts` reads every source file and fails on a `void supabase…` query builder that no `then`, `catch` or `finally` follows. It passes a call that already hands back a promise (an edge function's `invoke`, `auth`, `storage`, the channel calls) and skips a comment that quotes the shape. A read of the whole app found two such writes and no other: this one, and the alert dismissals' save, fixed in v2.7654.

**Proof.**

- The render smoke's stand-in is lazy the way the real client is, so the case that pinned the defect (*no release is sent*) failed the moment the fix went in. It now expects the release.
- Five new cases, 119 in all: moving to another card releases the lock this tab took; leaving the deck for another tab does too; a card nobody locked is not released by a look; Not a fit and Can't reach release the caller's lock on the card they leave; Didn't Answer keeps it.
- 2 unit tests on `releaseCallingLock` and 3 on the guard's reader.

**Read in the migrations, not changed.** The lock table's update policy lets a caller change only their own row. `takeCallingLock` takes over a colleague's stale lock with an upsert, which updates their row, so the database refuses it; the code treats the refusal as "no lock taken" and the call goes on. With releases now sent, a stale row is left only by a closed tab or a crash. The map records it as quirk 38; a fix is a policy change, which is the owner's call.

**Not checked live.** No lock was taken or released on the live site by this session.
