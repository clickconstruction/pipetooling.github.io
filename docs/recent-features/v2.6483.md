# v2.6483 — A teammate can see their own logbook (2026-11-04)

Punch list #255's next logbook PR (`to-dos/technician-progress-signals/`, mock-up `own-logbook.html`). The owner, 2026-11-04: *"Some employees have a log of the work that they've done. I would like to offer a button to expose that log."* The logbook (v2.6472) opened only for the office. Now the office shows it to its teammate, one at a time.

## What changed

- **The migration** `20261104120000_logbook_shares.sql` (`docs/migrations/20261104120000_logbook_shares.md`): the `logbook_shares` table (one row a teammate shown, `shown_by`, `shown_at`; the Licenses audience inserts and deletes, a teammate reads their own row) and `my_logbook()`, a SECURITY DEFINER read on `auth.uid()` that answers NULL without a share row. With one, it answers the caller's approved closed hours (the rows `list_user_license_hours_log` returns), the licenses under their name, current teammates' supervising licenses (master, contractor; unexpired; not archived) for the signer line, and the office job's id.
- **The office's press** on `/logbook/:userId`: a strip under the header, *Dario cannot see this logbook…* with **Show Dario this logbook**, then green, *Dario sees this logbook in the app's menu. Shown Nov 4 by Lou Lead.* with **Stop showing**. The Licenses tab row says *Dario sees it* beside Open logbook.
- **The teammate's door**: **My logbook** in the gear menu (`useOwnLogbookShown`) opens `/my-logbook`, the same page (`Logbook own`) written to them: *Your logbook*, the goal cards, the licenses held, the log, both prints. No Edit, no Add a license, no strip; the words that told the office to press Edit tell the teammate to ask the office.
- **Kernel** `src/lib/logbook/logbookShare.ts`: `shareStripWords` (the day on the company calendar) and `parseMyLogbook`. Tests: `logbookShare.test.ts` (7), `Logbook.render.test.tsx` (+3: the press and Stop, the own page without the office's controls, the not-shown words).
- **Guides**: a section *Show a teammate their logbook* in `keep-a-teammates-logbook-and-print-it-for-the-board`, and `see-my-own-logbook` for the teammate.
- **The SQL bed** `npm run test:pg:logbook-shares` (`scripts/pgtest-logbook-shares.sh`, `supabase/tests/logbook_shares/`, in `scripts/sql-beds.txt`).

## Decisions

- **One press a teammate, not everyone with hours** (the ask: a button, "some employees"). A stale license date reads as a wrong count, so the office looks first.
- **A new narrow read, not a wider gate.** `list_user_license_hours_log` and `person_licenses` stay closed to teammates; `my_logbook()` answers only for the caller and only with a share row, and sends only the supervising licenses the signer line needs.
- **The gear menu**, which every role has, over the role-split nav. The Your week card (#255, later) brings the number to the dashboard.
- **Print stays** on the teammate's page: the summary sheet goes to the board with the signed form.

## Testing

- The SQL bed's scenario passed on PGlite (Postgres 17 in WebAssembly) with stand-ins for `auth`, `users`, `people`, `person_licenses`, `clock_sessions`, `jobs_ledger`, `service_types`, `app_settings` and the role checks, and the real `list_user_license_hours_log` migration. Docker was not reachable on this machine. It ran the migration twice, then the scenario. A deliberately wrong expectation fails it. CI runs the same bed on the full schema.
- `npx vitest run src/lib/logbook src/pages/Logbook.render.test.tsx`, the help-guide suites, `npm run typecheck`.

## Push and deploy

The client calls `my_logbook()` and `logbook_shares`, which only the migration creates: `supabase db push` right after the merge, then `npm run gen-types:linked` as its own `chore(types)` PR. Until the push, the strip shows the refusal's reason and the menu row stays off.
