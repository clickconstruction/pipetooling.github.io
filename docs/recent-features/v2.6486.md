# v2.6486 — The Subs tab counts a settled order and its paid sheet once (2026-11-04)

v2.6479 made People → Subs' track record count each attributed sheet paid in full as settled, plus each settled step work order. But `settle_step_commitment` on a step-anchored order inserts a `people_labor_jobs` sheet for the released amount, writes it to the commitment's `labor_job_id` and keeps `step_id`; the tab hands a step order no `sheetLabel`, so the order counted, and once the office paid the minted sheet in full that sheet counted again: one piece of work read "2 settled". The order is the primary record (the fragment's rule, "a settled step work order still counts"), so its sheet now rides on it.

Not changed, for the record: a settled sheet-anchored order whose sheet is still unpaid counts 0 until the payment lands, because v2.6479 excludes the order ("its sheet already is" counted) and the sheet counts only when paid.

## What changed

- `src/lib/people/subsHqRows.ts`: `SubsHqCommitmentInput` gains `laborJobId`; `buildSubsHqRows` builds the set of sheet ids held by settled step orders (`status === 'settled'`, no `sheetLabel`, a `laborJobId`) and skips the paid-sheet settled increment for a sheet in that set. The sheet still counts toward `sheetCount`, `balanceDue`, `backchargeTotal` and `lastWorkedYmd`.
- `src/components/people/PeopleSubsTab.tsx`: passes each commitment's `labor_job_id` through as `laborJobId` (the select already read it).
- `docs/PEOPLE_TABS_ARCHITECTURE.md`: the Subs section states the settled-count rule for both anchors.
- Tests: `src/lib/people/subsHqRows.test.ts` adds a settled step order plus its paid minted sheet → 1 settled (read 2 before the fix), and the same order with the sheet unpaid → 1 settled with the balance still due (fails under the over-correction that skips an order with a sheet id). `PeopleSubsTab.render.test.tsx` unchanged, still green.
