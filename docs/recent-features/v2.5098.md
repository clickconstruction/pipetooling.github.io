# v2.5098 — Bids: Undo takes back a whole change in History (2026-10-09)

Bid history PR 6 (punch list #73, `to-dos/bid-history/README.md`), the last PR of the card's plan. Directed by PUNCHLIST and built by Helper 11. No migration and no edge function: every write goes through PR 4's and PR 5's functions or a plain delete under the presser's own policies.

## What shipped

- **Undo on an action line.** In the History window, an action of several changes has **Undo** beside its time. It shows only for someone `can_edit_bid` admits, read once when the window opens (`loadCanEditBid`). A single-line action keeps its line's own Put back as its undo.
- **One press, newest change first** (`bidUndoPlan`, then `runBidUndo`, in `bidHistoryUndo.ts`):
  - a changed value goes back through `put_back_bid_change` with no column, so every column that change touched;
  - a removed row comes back through `restore_bid_removed_row`. A row of the same delete that hangs on a removed count row, version or estimate rides with that parent, and parents go first. A row already back when its step comes counts as done;
  - a row the action added is removed from the client by id, under the presser's own policies, tagged `put-back` (`removeBidAddedRows`, 100 ids a request). It removes only from the tables the delete archive keeps (`BID_UNDO_REMOVABLE_TABLES`). An added count row takes what the action hung on it. PUNCHLIST chose this on 2026-10-09 over leaving imports out, and puts it to the owner as a confirm-after.
- **Nothing is lost for good.** An undone import's rows land in the delete archive. Each one has Put back, and the Undo itself is a new History line (*Removed 23 count rows with Undo*) whose own Undo brings them all back. The window says so after the press.
- **When Undo is off**, the line says why instead of offering it:
  - a person's later change hangs on a row the action added, and the line names them (*Undo is off. A later change hangs on rows it added: Tub price.*);
  - it added rows Undo cannot remove: schedule lines, which the archive does not keep, or a version or an estimate, whose rows the ledger cannot key back;
  - it removed a schedule line;
  - a row it changed was removed since;
  - a row it removed is past the archive's 90 days.

  The app's own later writes (book picks minted for new rows, the labor sync) do not count, since the app makes them again. An action of the app's own offers no Undo.
- **The result is said at the top**, as PR 5's put back is. A refused step is said in the function's own words and the rest still run (*“Brushed 2 prices” is partly undone. WC-1: …*). The window also says when Undo wrote over a value set again since, and when a restored field came back empty. Then it reads again and tells the open bid's tabs (`BID_HISTORY_PUT_BACK_EVENT`).
- **Captions**: an Undo's removals read *Removed 2 count rows with Undo*. An Undo of several kinds of change reads *Put back 3 changes*.
- **The guide** *price a bid with the Workbench* has the Undo paragraph.
