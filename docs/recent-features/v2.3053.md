# v2.3053 — Test-gap audit, pass 60: the dispatch hub's Subs-lane loads get their first tests (2026-09-07)

Pass 60 of the test-gap audit. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`subs/subDispatchFetch.ts` (v2.2929/v2.2930) loads what the dispatch hub's Subs lanes and the "subs on site" strip show: live sub work orders with their stage window and fixture name, the crew assigned to each job, and sub off-days. The span and range rules it defers to have a suite; the fetch itself had none.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Live orders (offered, accepted, approved) are read with their job embedded, capped at 1,000; the stage windows and then the fixtures are read only for the ids those orders reference, deduped, each under its own retry label. Nothing referenced means no follow-up read.
- Each order maps to the lane shape: a blank display name reads as "Sub"; the job label is `#<number> · <address>`, falling back to the name, then "Sub work order"; a blank fixture name reads as no stage.
- Only orders whose span touches the range are returned — an offered order sits on its window rather than its pick, and an undated order is dropped.
- Crew lookups dedupe ids, drop blanks, read in slices of 150, and group by job with each user once; a failed slice returns what was grouped so far with the message.
- Off-days read only `kind = off` inside the range, capped at 2,000, grouped by person.
- Every reader degrades to empty plus the error string, as the hub's other fetches do.

## What shipped

- **`subs/subDispatchFetch.test.ts`** (7) — a recording Supabase stand-in routed by table and `.in()` slice, with a retry wrapper that records its labels. Covers the three reads' shapes and the skipped follow-ups, the row mapping and its fallbacks, the range filter hand-off, slicing and grouping, and the failure shapes.
