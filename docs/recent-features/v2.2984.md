Phase 4 of [`docs/ONE_COMPANY_PLAN.md`](../ONE_COMPANY_PLAN.md). One migration, `20260907010000_one_company_backfill_owner.sql` ([doc](../migrations/20260907010000_one_company_backfill_owner.md)) — **pushed by the agent after merge** (standing approval 2026-09-07).

## What shipped

- **Backfill**: 176 rows across 9 of the 15 `master_user_id` tables repointed to `company_owner_user_id()`, with user triggers paused per table so no activity events, `updated_at` bumps or cascades fire. The holders were an estimator (76), an assistant (75) and a dev (25); every `master_user_id` FK is `ON DELETE CASCADE`, so this also stops an account archive/delete from taking company records with it.
- **Guards**: `developments_gc_customer_master_match_fn` / `jobs_ledger_development_master_match_fn` → no-ops.
- **Catalog**: the grant tables and the six main `master_user_id` columns carry comments saying what they are now.

## What Phase 4 does not do

The plan said "rename `master_assistants` / `master_shares`". The Phase 2 census found ~52 SECURITY DEFINER functions still reading them inline, and `sync_company_access_grants()` (v2.921) keeps them complete so those gates pass for the whole office. Renaming would break every one of those functions at call time. So: comments now, rename/drop after the Phase 5 function sweep.
