# v2.8123 — A one-time job to learn which size Supabase counts against its 20 MB limit (2026-11-20)

CI only: one workflow, run by hand, once. No screen, no function source and no check changes. The owner said "Yes, run the probe" on 2026-11-20.

## The question

Supabase holds a function bundled with Docker to 20 MB ([its bundle size page](https://supabase.com/kb/troubleshooting/edge-function-bundle-size-issues)) and does not say which size it means. A bundle has two:

- **Compressed**, which the CLI prints as `script size`.
- **Unpacked**, which Supabase stores and the Management API hands back: each file, its JavaScript and its source map, about 3.3 times the source.

The dev seat's bundle was accepted on 2026-11-20 at 3.46 MB compressed and 14.85 MB unpacked, which cannot tell them apart. So `check:edge-bundles` holds the seat to 5.8 MB of source (v2.8117), about five days of room at 0.25 MB a day. The compressed reading would allow about 12 MB, which is months.

## The probe

`.github/workflows/zz-bundle-size-probe.yml` runs only by hand, only on `main`, and only when the person types the function's name:

```bash
gh workflow run zz-bundle-size-probe.yml --ref main -f confirm=zz-bundle-size-probe
```

It writes a throwaway function in the runner, `zz-bundle-size-probe`: an `index.ts` that counts the lines of padding modules of made-up words. Nothing of it is in the repo. It deploys it bundled twice with CLI 2.72.7, the version the seat's job uses.

| Deploy | Source | Unpacked, about | Compressed, about | Accepted means | Refused means |
|---|---|---|---|---|---|
| 1 | 7.5 MB | 23 to 25 MB | 6 MB | the unpacked size is not held to 20 MB | it is, and deploy 2 is skipped |
| 2 | 14 MB | 42 to 46 MB | 12 MB | a seat of 12 MB of source would be taken on both sizes | a limit sits between the two, and the summary carries Supabase's words |

After each accepted deploy the job reads the stored bundle's size and calls the function once, to see that a bundle of that size boots.

## What it touches on the production project

- One new function, for about a minute. It answers one line of JSON, reads nothing and writes nothing. It deploys with `--no-verify-jwt`, as every function here does, so the one call needs no key.
- The job stops before any deploy when a function of that name already exists, so it never touches one that was there before it.
- The delete runs whatever happened before it, by the CLI and then by the Management API if the function is still there. The job fails, with the command to run by hand, if it is still there after.
- No other function, no table and no setting.

## After the probe

The result goes to the owner. Raising the seat's ceiling in `BUNDLED_UPLOAD_CEILINGS` is a separate change and the owner's to say. This workflow is removed in the change that writes the result down.
