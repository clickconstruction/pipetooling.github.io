# v2.8308 — Permits: a shared phone or web domain is a reason a name may be a customer (2026-11-22)

The client half of two things punch list #307 left when it closed: *the phone is not kept*, and *a phone or web domain in Compare*. The server half is v2.8296 (migration `20261122233000_permit_contact_phone.sql`, pushed 2026-11-22). No migration and no edge function here.

## What was there

**Find their names on permits** offered a name for two kinds of reason: a permit on an address we bid to the customer, and how alike the two names read. A name on permits that answers the customer's own phone was not offered unless its words happened to match. #307's plan graded the same phone or web domain *Likely*, beside one name beginning the other, and held it until a phone was on hand.

## What changed

- **A shared phone or web domain is a reason of its own.** A green chip reads *The same phone, (512) 555-0101* or *The same web domain, example.com*. It sits after the site's chip and before the name's.
- **A name is offered on that reason alone**, however unlike the two names read. It carries the grade of one name beginning the other, so it leads the names that only share a word.
- **Compare gains two rows**, each drawn only when one side holds something: *Phones we hold for them* beside *Phones listed with this name*, and *Web domains we hold for them* beside *Web domains found for this name*. A row is marked green when the database's read says the two share a value, and the shared value is listed first on both sides.
- **Looks like a customer** on Builders carries the same reason, and so does the Dashboard's count of names waiting, since both call one function.
- **Nothing is tied by any of this.** A person still presses **Same company**, **Works for them** or **Not them**.

A name already answered is not offered again, their own name is never offered, and a name marked as filing for others stays out, whatever it shares.

## How it is built

- `nameLikeness.ts`: `suggestNames` and `lookAlikePairs` take the shared values by name key. `contactMatchesByCustomer` and `foldContactMatches` turn the read's rows into them, one GC under two customer rows read as one. `compareRows` takes what each side holds (`compareContactsOf`, by the database's own two rules `phoneDigitsOf` and `contactDomainOf`). `listedLineWords` says the line under a name in words that are true of how it was found.
- `bidSiteIo.ts`: `loadNameContactMatches` and `loadAllNameContactMatches` read `permit_name_contact_matches`, a page at a time, and answer null when the function is not on the database, as the answers read does. `loadNameByKey` reads a name Builders does not carry by its key. `loadPermitsOfName` asks the phone with a name's permits and drops it when the column is missing. `loadOurContactRows` and `loadCompanyLookupFacts` read what each side holds for Compare.
- `FindNamesSheet.tsx`: the sheet reads the shared values with its other reads. Compare reads what each side holds as an extra: when that cannot be read, the three rows it always drew still show, with the reason under them.
- `lookAlikeWorklist.ts`, `lookAlikeIo.ts`, `usePermitLookAlikes.ts`: the worklist's one read for every city carries the shared values.

## What the read ties, and what Compare shows

- The tie is the database's word. A value under more than three names, or held for more than three customers, ties nobody, so a permit service's number can sit on both sides of Compare unmarked.
- Our side is read from the customer's own row and its people. The database also reads the contacts spine. A value it ties from there is shown on both sides of Compare, since the read named it.
- The city's side is the phone on the name's permits and what a company lookup found. A phone looked up for the call list shows only when it is the one shared.
- Austin's feed is the one that lists a phone. The other four cities list none.

## The look

Seen on the dev server as the dev, on live data, one page at a time, at 393 × 852 in the browser pane. Nothing that writes was pressed.

- **Find their names on permits**, for a customer with one such name: the name led the list with the green phone chip over its grey *Shares the word* chip, in the green border the top name gets. Before this change the same name stood on its grey chip alone, with nothing to say it was more than a shared word. The sheet was 369 px wide in a 393 px page with nothing past its edge.
- **Compare** on that name: eight cells, the last two marked green, the same phone on both sides. No web domains row, since neither side holds one.
- **A customer whose only match is its own name**: nothing new is offered, as before. Three of the six pairs on prod today are a customer's own name.
- **Looks like a customer** in Austin: 26 names, the two that share a phone first. `innerWidth` and `scrollWidth` both 393.

*Is this the best we can do* changed one thing, caught in the code before the look: a name a shared phone brings in that Builders does not carry would have said *Listed on a permit on an address you bid to them*, which is not true of it. It says how many permits it is on.

Counted on prod, read only, after the push: Austin keeps a phone on 4,703 of its 4,928 permits, under 1,308 names, and six customer and name pairs share a phone or a web domain.

Not seen: a web domains row on live data (no pair with a domain is a different name with bids to look at), 375 px, dark, and a desk width.
