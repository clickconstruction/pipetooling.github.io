# v2.8727 — HR files: a case's items take no write but through their door (2026-11-27)

Punch list #315, the first finding of the audit of 2026-11-20. One migration that revokes privileges on two tables, two beds, and no client change. The answer of 2026-11-25 recorded on the card: *Fix all of them; the leak closed by revoking the direct grants.* The push is owed after the merge, on its own yes, and was not done.

## What the audit found

A signed-in user who is not a dev could learn whether a person's case held Item N. `person_case_items` granted INSERT to every signed-in user and left the refusal to its row policy. A BEFORE INSERT trigger runs first, and the table's guard looked the number up: *item N already stands on this file* for a number that stood, and the policy's words for one that did not. The insert never landed, and nothing else was told.

## What the build found

The correction links, `person_file_amendments`, have a guard of the same kind. Its migration never took away what a new table is given by default, so `anon` and the signed-in role each held every privilege on it. An insert that named two ids learned whether each was on a file, whether on the named person's file, and whether a link stood, and it could be sent with no sign-in. The ids are random ones a caller would have to hold already, so it tells less than *Item N* did.

## What changed

- **Migration `20261127075633_case_items_direct_grants_revoked.sql`.** INSERT and UPDATE on `person_case_items` are revoked from the signed-in role. On `person_file_amendments` everything of `anon` is revoked, and the signed-in role's DELETE, TRUNCATE, REFERENCES and TRIGGER. With no privilege the database refuses the statement before any trigger runs, in the same words whatever it names. No table, column, row, policy, trigger or function is made or changed. Its page: [`docs/migrations/20261127075633_case_items_direct_grants_revoked.md`](../migrations/20261127075633_case_items_direct_grants_revoked.md).
- **The beds.** `person-file-numbers` no longer writes the items directly as a dev: it shows that write refused, and the door still working. `person-file-amendments` gains the cases for `anon`. Each bed's script applies this file after the older migration it runs twice, since the older one grants again.
- `docs/ACCESS_CONTROL.md` and `docs/HR_FILES.md` say who holds what on both tables. The card's audit section says what is built and what is left.

## What nothing loses

The HR tab, the dev seat and every other writer of the case items go through `dev_case_write`, a dev-gated definer's function that needs no privilege of its caller. No screen, edge function or other database function writes the items directly. No screen reads or writes the links signed out.

## Still open

The signed-in role keeps INSERT and UPDATE on `person_file_amendments`. The HR tab adds a link and takes one off by writing the table as the signed-in dev, so those two cannot go until the tab writes another way. A signed-in user who is not a dev can still put the guard's question to the links. Two ways close it, and the pick was asked of the person on 2026-11-27:

- Move the tab's two writes behind `dev_hr_entry_write`, the dev-gated door the dev seat already uses for a link and a withdrawal, then revoke the two grants in a later migration.
- Make the guard ask who is calling before it answers anything, and leave the grants.

## Order

The client calls nothing the migration creates and writes neither table in a way it takes away. Any order of the merge and the push is safe. No deploy and no types PR is owed.

## Tests

Both beds ran whole on a local Docker on 2026-11-27, on the Supabase image with every migration applied, and both passed.

- `npm run test:pg:person-file-numbers`, 57 assertions. New: the signed-in role holds SELECT on the items and nothing else, and `anon` nothing. An estimator's insert is refused with `42501 permission denied for table person_case_items` for a number that stands, one that does not and none, and so is an update. A dev's own insert at the table is refused the same way, and the door still adds an item. The guard still refuses a taken number for the table's owner.
- `npm run test:pg:person-file-amendments`, 43 assertions. New: `anon` holds nothing on the links, the signed-in role holds SELECT, INSERT and UPDATE alone, and the HR agent's key reads and adds as before. With no sign-in, four inserts that used to answer four ways are refused in one way, and so are a read, an update and a delete.
- **The numbers bed's first whole run failed on its own case.** The scenario switched to the `hr_agent` role, which the real image refuses to the bed's owner. It was written on a stand-in schema, and this was its first run on the real one. The case now reads the role's right to call its door as a privilege.
- **Before and after on the same bed.** With `anon`'s privileges given back inside a transaction that rolled back, the four inserts answered four ways. As the file leaves things they answer one way. A signed-in estimator's still answer four ways, which is the half that is still open.
- `npm run check:todos`, `npm run check:doc-lines` and the release notes test pass.
