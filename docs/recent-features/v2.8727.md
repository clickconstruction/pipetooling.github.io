# v2.8727 — HR files: the case items and the correction links take no write but through their doors (2026-11-27)

Punch list #315, the first finding of the audit of 2026-11-20. One migration that revokes privileges on two tables, two beds, and no client change. The answer of 2026-11-25 recorded on the card: *Fix all of them; the leak closed by revoking the direct grants.* For the links, the pick of 2026-11-27: *A, the door*. The push is owed after the merge, on its own yes and once v2.8730's client is live, and was not done.

## What the audit found

A signed-in user who is not a dev could learn whether a person's case held Item N. `person_case_items` granted INSERT to every signed-in user and left the refusal to its row policy. A BEFORE INSERT trigger runs first, and the table's guard looked the number up: *item N already stands on this file* for a number that stood, and the policy's words for one that did not. The insert never landed, and nothing else was told.

## What the build found

The correction links, `person_file_amendments`, have a guard of the same kind. Its migration never took away what a new table is given by default, so `anon` and the signed-in role each held every privilege on it. An insert that named two ids learned whether each was on a file, whether on the named person's file, and whether a link stood, and it could be sent with no sign-in. The ids are random ones a caller would have to hold already, so it tells less than *Item N* did.

## What changed

- **Migration `20261127075633_case_items_direct_grants_revoked.sql`.** INSERT and UPDATE on `person_case_items` are revoked from the signed-in role. On `person_file_amendments` everything of `anon` is revoked, and everything of the signed-in role but SELECT. With no privilege the database refuses the statement before any trigger runs, in the same words whatever it names. No table, column, row, policy, trigger or function is made or changed. Its page: [`docs/migrations/20261127075633_case_items_direct_grants_revoked.md`](../migrations/20261127075633_case_items_direct_grants_revoked.md).
- **The beds.** `person-file-numbers` no longer writes the items directly as a dev: it shows that write refused, and the door still working. `person-file-amendments` gains the cases for `anon` and for a signed-in caller, and writes its own links through the door where it wrote the table. Each bed's script applies this file after the older migration it runs twice, since the older one grants again.
- `docs/ACCESS_CONTROL.md` and `docs/HR_FILES.md` say who holds what on both tables. The card's audit section says what is built and what is left.

## What nothing loses

The HR tab, the dev seat and every other writer of the case items go through `dev_case_write`, a dev-gated definer's function that needs no privilege of its caller. No screen, edge function or other database function writes the items directly. Since v2.8730 the tab writes a link through `dev_hr_entry_write`, as the seat does, and `hr_agent_write` is the one function that writes the links. No screen reads or writes the links signed out.

## The links, and the order

The HR tab used to add a link and take one off by writing the table as the signed-in dev, so INSERT and UPDATE could not be revoked while it did. Two ways were put to the person: the tab's writes move behind `dev_hr_entry_write` and the grants are revoked, or the grants stay and the guard asks who is calling first. The pick was the door. v2.8730 moved the tab's writes, and this migration revokes.

**The client first, then the push.** A tab still open on a client older than v2.8730 writes the links table itself. After the push its link would be refused until the tab reloads, with the entry it wrote first left unlinked and the toast saying so. The case items' half has no such order. No deploy and no types PR is owed.

## Tests

Both beds ran whole on a local Docker on 2026-11-27, on the Supabase image with every migration applied, and both passed.

- `npm run test:pg:person-file-numbers`, 57 assertions. New: the signed-in role holds SELECT on the items and nothing else, and `anon` nothing. An estimator's insert is refused with `42501 permission denied for table person_case_items` for a number that stands, one that does not and none, and so is an update. A dev's own insert at the table is refused the same way, and the door still adds an item. The guard still refuses a taken number for the table's owner.
- `npm run test:pg:person-file-amendments`, 50 assertions. New: `anon` holds nothing on the links and the signed-in role SELECT alone. An estimator's four inserts, a dev's own insert and the same four with no sign-in are each refused in one way. `hr_agent_write` is the only function that writes the table. Where the scenario wrote the table as a dev it now writes through the door.
- **The numbers bed's first whole run failed on its own case.** The scenario switched to the `hr_agent` role, which the real image refuses to the bed's owner. It was written on a stand-in schema, and this was its first run on the real one. The case now reads the role's right to call its door as a privilege.
- **Before and after on the same bed.** With the privileges given back inside a transaction that rolled back, four inserts answered four ways for a caller with no sign-in and for an estimator. As the file leaves things they answer one way for both.
- **v2.8730's two calls on the same bed, with the grants gone.** A link landed, made by the dev. A withdrawal stamped it. A second withdrawal answered *no live link*, which the tab reads as done.
- `npm run check:todos`, `npm run check:doc-lines` and the release notes test pass.
