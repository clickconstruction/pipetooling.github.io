# v2.8039 — On an iPhone, Loading no longer hides behind the camera (2026-11-20)

The owner's walk of 2026-11-20 on an iPhone: *when the app is refreshing and saying "loading" it is doing so behind the title bar where the camera is.* No migration and no function. CSS and five class names.

## What was wrong

The app is installed on the Home Screen with a translucent status bar, so the page starts at the top of the glass and anything with no header over it must pay `env(safe-area-inset-top)`. The header pays it. The screens that draw **before** the header, or **in place of** every route, did not: each was a bare `padding: 2rem` block, so its one centred line sat 32px down, and the Dynamic Island ends near 59px.

| Screen | Where | When it shows |
|---|---|---|
| *Loading…*, the slow words, *Taking too long? Fix the app* | `AuthGateLoadingScreen`, `App.tsx` | every cold start, the gear's Hard Reload, an automatic update's reload |
| *Updating app…* | `RouteChunkBoundary`, the copy around `<Routes>` | a page chunk the newest deploy no longer serves, while the reload starts |
| *This page could not load* with **Reload** | the same boundary | that reload has already been spent |
| *Opening…* | `TaskShortcut` | the Add Task icon's launch, before the session is read |
| *Signing in as …* | `DevLogin` | the dev sign-in link |

The Reload button of the third row was the worst of them: a press under the status bar is not a press.

A corner toast had the same fault on two kinds of page. It measures the header's foot, and falls back to 16px from the top where there is no header (sign-in, the gate) or the header has scrolled away.

## What changed

- **`.appBareScreen`** (`src/index.css`): `padding: 2rem`, `padding-top: calc(2rem + var(--app-top-chrome, 0px))`, centred. The five screens draw in it and drop their inline padding. `--app-top-chrome` is `env(safe-area-inset-top, 0px)`, which is `0px` in a browser tab and on Android, so nothing moves there.
- **`.appMain .appBareScreen`** keeps the plain 2rem. The Layout wraps its outlet in the same `RouteChunkBoundary`, under the header, where the nav has paid the inset already.
- **The corner toast**'s top is `max(<measured>px, calc(16px + var(--app-top-chrome, 0px)))`. Under a header at the top of the page the measured value wins, as before.

## What was checked and found right

- `index.html` draws no words before React mounts: `#root` is empty.
- Every `Suspense` in `App.tsx` has `fallback={null}`. The Layout's one, `RouteLoadingFallback`, draws inside `<main>` under the header.
- Every page's own *Loading…* (the Checklist's, the Dashboard's cards, the rest) is in flow inside `<main>`, under the header.
- The windows and drawers pinned to the top already pad by `--app-top-chrome`. The update pill is pinned to the bottom.

## Not in this change

The banners the Layout draws **above** the header (training mode, the digital twin line, Customer Waiting, the Add Task shortcut) start at the top of the glass and pay no inset. They are not loading states and a sibling session is in the header today, so they are left as a follow-up.

## Tests

`src/lib/bareScreenInset.test.ts` reads the rule and the five screens: the class pays the inset once, pays nothing more under `.appMain`, and none of the five carries a padding of its own.

## Verified

On the dev server at phone width with `--app-top-chrome` forced to 59px, before and after. A real inset needs an installed iPhone: the browser pane reports `env(safe-area-inset-top)` as 0. The owner confirms on the phone after the deploy.
