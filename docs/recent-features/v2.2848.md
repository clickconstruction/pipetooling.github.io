# v2.2848 — Job window role branch: superintendents, estimators, controllers open the read pane; dead Create Job links hidden (2026-09-05)

Journey-map Phase 4, Tier-1 #7 (J9 F1/N1 "the window closes itself", J31 N2/adj1/adj2 "the per-project Create Job link is dead"). Client-only; no migration.

## Mechanism

**Before.** [`JobDetailModalContext.tsx`](../../src/contexts/JobDetailModalContext.tsx) branched on `canEditJobs = !isSubcontractorLikeRole(authRole)`, so every non-sub role got the tabbed [`JobWindowModal`](../../src/components/jobs/JobWindowModal.tsx). The window always mounts the embedded [`JobFormModal`](../../src/components/jobs/JobFormModal.tsx) in edit mode (Edit + Bill panes are one form instance, hidden on the Job tab). The form's init effect calls [`fetchJobWithDetailsById`](../../src/lib/fetchJobWithDetailsById.ts) — a direct `jobs_ledger` select with the child embeds — which returns null for any role the baseline SELECT policy ("Devs, masters, assistants, primary can read jobs ledger", a literal role array) refuses. On null the form toasts **"Job not found or you do not have access."** and calls `onClose()` — the whole window's close. Net effect for **superintendent, estimator, controller**: every desktop door to a job (Dashboard Superintendent Jobs / Assigned Jobs rows, Workflow job chips, Estimates → job, Customers → job) opened a window that closed itself ~1 s later. v2.2647 gave superintendents DB rights to read and post job thread notes, but this was their only desktop route to a thread mount.

**After.** One pure kernel decides the surface: [`resolveJobWindowMode(role)`](../../src/lib/jobDetailModalRole.ts) → `'window' | 'read-only'`, defined as exactly `isStaffFullJobLedgerDetailRole(role)` — the predicate the read pane already used for its two-tier fetch. The provider renders `JobWindowModal` only for `'window'`; everyone else gets the standalone read-only [`DetailJobModal`](../../src/components/jobs/DetailJobModal.tsx), whose limited path (`fetchLimitedLedgerRow` merged over the caller's `assignedJobsRows`) never touches the edit form. `DetailJobModal`'s ⚙ Edit gear and `handleEditJobClick` gate on the same kernel, so a read-only role is not offered an Edit that would route through the opener bridge straight back to the pane. Chosen over "render the window with only the Job tab" because it is a one-predicate swap onto a path sub-like roles have exercised since v2.1675, and it never mounts the form for a role whose fetch would fail.

| Role | Before | After (`resolveJobWindowMode`) |
|---|---|---|
| dev, master_technician, assistant, primary | Job window (Job · Edit · Bill) | **window** — unchanged |
| superintendent | window → self-close ~1 s | **read-only** pane; thread notes post (v2.2647) |
| estimator | window → self-close | **read-only** pane |
| controller | window → self-close | **read-only** pane (see note) |
| subcontractor, helpers | read-only pane | **read-only** — unchanged |

**Controller not widened.** The prompt asked whether controller should pass the full fetch instead. The `jobs_ledger` SELECT, INSERT, UPDATE and DELETE policies in the baseline gate on literal role arrays (`dev`/`master_technician`/`assistant`/`primary`, or `master_technician`/`assistant` for INSERT); `is_dev()` is role = dev only, and v2.662's `is_assistant()` widening does not reach these policies. Widening the client predicate would only move "Job not found" into the read pane. Follow-up (DB): add controller to the `jobs_ledger*` policies (or route them through `is_assistant()`), then add `controller` to `isStaffFullJobLedgerDetailRole` and `canCreateJobsLedgerRow` in the same PR.

**Dead Create Job links.** [`canCreateJobsLedgerRow(role)`](../../src/lib/jobsLedgerCreateRole.ts) mirrors the INSERT policy (dev, master_technician, assistant). [`Projects.tsx`](../../src/pages/Projects.tsx) (the rail's "+ Job" pill) and [`Workflow.tsx`](../../src/pages/Workflow.tsx) ("+ Create Job") hide the link otherwise. For superintendent and primary the `/jobs?newJob=true&project=…&tab=stages` target was rewritten to the Reports tab and the newJob effect never fired (J31 N2).

**Telemetry.** On every open the provider records one [`ui_nav_clicks`](../../src/lib/navClickTelemetry.ts) row: `control = 'job_window_opened'`, `target = '#window' | '#read-only'`, `role`, `from_path`. **Invariant: the self-close must hit zero** — there is no longer any code path that mounts the edit form for a role whose full fetch returns null. Watch `#read-only` opens per role against thread-note / report activity to see whether the pane is enough for estimators and controllers.

## Verify

1. Impersonate a superintendent with a project assignment → Dashboard → **Superintendent Jobs** (or Assigned Jobs) → click a job title. The Job Detail pane opens and stays open; no toast. Scroll to the notes thread and post a note — it lands (v2.2647 policies).
2. Same as an estimator from Estimates/Customers → job; as a controller from anywhere that opens Job Detail. Pane, no tabs, no self-close.
3. As dev: the same rows still open the Job · Edit · Bill window; Edit autosaves as before.
4. Superintendent / primary → Projects rail and a project's Workflow: no "+ Job" / "+ Create Job" link. Dev / master / assistant: link present.
5. `select role, target, count(*) from ui_nav_clicks where control = 'job_window_opened' group by 1,2` — read-only roles only ever produce `#read-only`.
