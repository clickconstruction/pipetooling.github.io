# v2.2357 — Body scroll-lock leak: timer fallback for the sentinel's recompute (2026-08-26)

Bug: open a bid's preview modal from the Bid Board (click the bid number),
click an "Open in Bids" quick link (e.g. Pricing) — the navigation closed the
modal but `document.body` kept the scroll-lock inline styles
(`overflow: hidden; position: fixed; top/left/right`) forever; the page could
no longer scroll.

Root cause: `BodyScrollLockSentinel` (v2.2186) coalesced its recompute
exclusively through `requestAnimationFrame`. The browser suspends rAF
callbacks while `document.visibilityState` is `hidden` (background tab,
paused webview, embedded preview pane), so the release recompute scheduled by
the modal's unmount never ran. The modal, the preview context, and the
`bodyScrollLock` refcount kernel were all correct — the scheduled release
just never fired. (Same starvation also meant a modal opened in a hidden
document never acquired the lock at all.)

Fix: new pure kernel `src/lib/frameFallbackScheduler.ts` —
`createFrameFallbackScheduler(host, run, fallbackMs = 150)` arms both a frame
and a timer per schedule; whichever fires first runs once and disarms the
other. The sentinel now schedules through it (injectable host, unit-tested in
`frameFallbackScheduler.test.ts`, including the frames-never-fire leak path).

Verified live in the embedded preview pane (where `visibilityState` stays
`hidden` and rAF is fully starved): pre-fix the lock stuck permanently after
the quick link; post-fix it engages on modal open and releases on navigation,
and the normal visible-tab path is unchanged.
