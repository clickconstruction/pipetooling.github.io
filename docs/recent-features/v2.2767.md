# v2.2767 — Sub sheet stages: Sub Labor walks a sheet, the portal tracks it, the job hears it (2026-09-04)

Owner ask: cycle a sub sheet through "waiting for work to complete → waiting to inspect → waiting for customer to pay" on Jobs → Sub Labor, show it on the sub portal, let the sub mark the work done to trigger the next stage, and post to the job's Activity feed. Owner picked from the proposal (artifact 851255fb): the **tracker rail** on the portal card, the word **walk-through** (the Inspections tab means city inspections), keep the sub's optional note, and let the office step a sheet **back**.

## DB (migration `20260904195443_sub_sheet_stages.sql`, fragment in docs/migrations/)

- `people_labor_jobs` gains `stage` (`working` | `walkthrough` | `customer_pay`, NOT NULL default `working`), `stage_changed_at`, `stage_changed_by` (NULL when the sub or automation moved it), `stage_source` (`office` | `portal` | `auto`), `stage_note`. **Paid is derived** (open = $0), never stored. The two-value `portal_status` from 20260902220000 is folded in (one-time carry: `complete` → `walkthrough`) and deprecated in place — the column stays so the deployed function keeps working until redeploy.
- `set_sub_sheet_stage(p_labor_job_id, p_stage, p_note)` — office writers (dev / assistant-like / master), either direction, stamps changed_at/by + `source = office`, replaces the note. `sub_sheet_stage_label(text)` keeps the chip wording in SQL.
- Trigger `people_labor_jobs_stage_to_activity` (the `jobs_ledger_completeness_to_activity` shape): on a stage change, find the job by number (`lower(btrim(hcp_number)) = lower(btrim(job_number))`, newest first) and insert a `job_activity_events` row, type **`sub_stage_change`**, summary `Sub labor · Danny Vasquez: Waiting on work → Waiting on walk-through (from the sub portal) · “note”`, actor = the office user or NULL for portal/auto, `detail` = `{source_id, from, to, source, contractor, note}`. A sheet with no matching job still changes stage; it just doesn't post.

## Edge functions (deploy `sub-portal` + `submit-sub-portal` after the migration)

- `sub-portal`: sheets carry `stage`, `stageChangedOn` (YMD), `stageSource` instead of `status`. Shared builder `_shared/subPortalStatement.ts` normalizes unknown stages to `working`. Sample fixture: sheet 1 at walk-through (portal, yesterday), sheet 2 at customer-pay.
- `submit-sub-portal`: new kind **`mark_work_done`** `{ token, laborJobId, note? }` — the sheet must be in the link's person's `people_labor_job_assignees` and at `working` (else 404 / 409); moves it to `walkthrough` with `source = portal` + the trimmed note (≤300), then drops a **"Ready to walk — Danny Vasquez · 1004 162 Forest Drive"** dispatch note (`pending_payload.kind = 'sub_work_done'`) with the usual `notify-dispatch-request` fan-out. Returns `{ ok, stage, stageChangedOn }`.

## Client

- **Kernel** [`lib/subSheetStage.ts`](../../src/lib/subSheetStage.ts) (+4 tests): the stage list and order, `next`/`prev`, office labels (`Waiting on work` / `Waiting on walk-through` / `Waiting on customer`), hints, chip tones, `describeSubSheetStageChange`, `subSheetStageStamp` ("Danny, from the portal · Sep 4" / "Malachi · Sep 6").
- **Portal** [`pages/SubPortal.tsx`](../../src/pages/SubPortal.tsx) `SheetCard`: the header chip now reads the stage (In progress / Walk-through next / Customer to pay); under Agreed · Paid · Open a **four-dot rail** (Work · Walk-through · Customer pays · You're paid — done dots green, the current one copper) and one sentence per stage (the walk-through one dated when the sub moved it); the office's payable-after / hold-reason line still prints beneath. While the sheet is at *working*, a screen-only **✓ My work here is done** button opens a two-line confirm with an optional note → `mark_work_done`; success flips the card locally (rail + "Thanks — we'll schedule the walk-through"). Sample mode short-circuits like the other actions. Every string in `subPortalI18n.ts` in EN + ES. Payload parser (`subPortalPayload.ts`) defaults a missing stage to `working`, so an old function and a new client coexist.
- **Sub Labor ledger** [`JobsSubLaborTab.tsx`](../../src/components/jobs/JobsSubLaborTab.tsx): new **Stage** column — chip in the app's status colors (amber / violet / blue; green **Paid** when open ≤ $0, immovable), a `→` that advances one stage, click the chip for the three-stage menu (jump or step back), a "· sub" mark and the stamp line when the sub moved it, the note behind ✎. `useSubLaborLedger` selects the stage columns (legacy fallback select still covers a pre-migration DB), resolves mover names, and adds `setLaborJobStage` (RPC + local patch).
- **Sheet editor** [`SubSheetPortalFieldsBox.tsx`](../../src/components/jobs/SubSheetPortalFieldsBox.tsx): the Status dropdown (Auto / In progress / Work complete) is replaced by a three-button stage control with the "Last moved by …" stamp + the sub's note; payable-after and hold reason unchanged. Save writes the stage through `set_sub_sheet_stage` only when it changed, then the two pay fields through the existing RPC (passing `portal_status = null`). The form modal patches the ledger row + its own row on save.
- **Activity feed**: `sub_stage_change` registered in [`lib/jobActivityEvent.ts`](../../src/lib/jobActivityEvent.ts) under the **Sub labor** tag (teal, status bucket).
- Help: `share-a-sub-their-portal.md` (stages section), `record-sub-labor-on-a-job.md` (stage chip).

## Later (automation hooks, one `stage_source = auto` writer each)

The job's move to Billed → every sheet on it to `customer_pay`; the customer's payment landing → `payable_after`; a walk-through scheduled → the sentence's date. Nothing here needs redesigning for them.
