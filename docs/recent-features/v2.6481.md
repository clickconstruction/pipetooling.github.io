# v2.6481 — Every stretch a person worked is kept (punch list #256, PR 2) (2026-11-03)

Punch list #256's second PR (`to-dos/bring-back-a-teammate/`). A person's employment dates were one pair on the roster row, so a teammate who left and came back three years later would have their first stint written over. This PR keeps every stint and lets a restore leave old roadmap tasks parked. PR 1 (v2.6480) is the kernel; PR 3 is the Bring back window that uses both.

## What changed

- **The migration** `20261103203000_employment_stints.sql` (`docs/migrations/20261103203000_employment_stints.md`): the `employment_stints` table, its read policy (whoever sees the people row sees its stints), the trigger `people_stints_follow_dates` on `people` that keeps it, the backfill (one stint from each row's pair), the three fence calls.
- **`restore-user`** takes `restore_roadmap`. `false` deletes the user's parked open roadmap assignments before clearing `archived_at`, so the restore trigger gives none back; the answer carries `roadmap_tasks_discarded`. Absent or `true` is today's behaviour (`docs/EDGE_FUNCTIONS.md`).
- **The SQL bed** `npm run test:pg:employment-stints` (`scripts/pgtest-employment-stints.sh`, `supabase/tests/employment_stints/`), listed in `scripts/sql-beds.txt` so CI runs it on the full schema.

## Decisions

- **A trigger, not client writes.** End employment, Pay & schedule, the Employment tab, the sub bench and Bring back all write `people.start_date` / `end_date` already. One trigger on those columns keeps the stints for every path, as `roadmap_assignees_follow_user_archive` does for archiving, and nothing in the client changes.
- **The people row's pair stays the current stint.** Every reader (the salary clamp, `roster_people`, `list_team_member_start_dates`, the HR tab) keeps reading it, which is the owner's call 1: tenure counts from the day back.
- **A return is an end cleared with a new start on or after the old end.** *Ended by mistake* keeps the old start, so it reopens the stint; the sub bench's Reactivate re-stamps the start, so a same-day bench and back is a new stint.
- **Discard before the flip.** The roadmap trigger restores parked rows the moment `archived_at` clears, so `restore-user` deletes them first. If the account update then fails, the old tasks stay discarded and the person stays archived; a retry finishes the restore.

## Testing

- **The SQL bed's scenario** passed on PGlite (Postgres 17 in WebAssembly) with stand-ins for `auth`, `users`, `people` and the fence functions. Docker was not reachable on this machine. It ran: the migration, the seed, the migration twice more, then the scenario. A deliberately wrong expectation fails it, so the checks are live. CI runs the same bed on the full schema.
- **The roadmap flag's premise** was checked on PGlite with the real `20260826034043` migration. Archiving parks two tasks. A restore gives both back. Deleting the parked rows first leaves both unassigned.
- **Bundling:** `node scripts/check-edge-bundles.mjs` reports all 178 functions bundle.
