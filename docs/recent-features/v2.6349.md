# v2.6349 — Stage checklists: a tap on a stage's name holds while the section finishes loading (2026-11-02)

A fix to punch list #237's PR 1 (v2.6328): the Documents tab's Stage checklists section (`src/components/jobs/JobDocumentsChecklists.tsx`). No migration, no function.

- **The race.** The section decides each stage's first fold in an effect, once, when the rows first read (a ready stage folds to one line on a phone; the desk shows every row), and it wrote that first fold with `setFolded(first)`, replacing the whole map. A tap on a stage's name that landed after the rows painted but before that effect ran was queued first, and the effect's replacement was applied after it, so the tap was undone. React runs a passive effect from a render a promise started in a later task, so the window is real on a slow phone and in a loaded CI runner.
- **The fix.** The effect merges under what is already there: `setFolded((f) => ({ ...first, ...(f ?? {}) }))`. A stage someone tapped keeps their choice; every stage nobody touched takes the first fold as before. Either order of the two updates now ends in the same state.
- **Why it mattered now.** The render test *folds a stage on its name* hit the window in the merge queue (run 41453294365, 2026-11-02 13:28 UTC) and dropped other PRs from the queue: it reads the button the moment after the click, and the late first fold had set it back to open. The test is unchanged; with the merge it cannot fail on this order.
- The same line rides unchanged in punch list #237's PR 1b (#6798) and takes this fix cleanly when either lands.
