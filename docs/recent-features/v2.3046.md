# v2.3046 — Test-gap audit, pass 55: the office address anchor gets its first tests (2026-09-07)

Follow-up to v2.3044. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`officeAddressSettings.ts` (124 lines) holds the company office's address and coordinates — the anchor for the bid form's "Distance to Office" auto-fill: the stored JSON's validation, the `app_settings` read, upsert and delete, geocode-then-save from Settings, and the anchor resolution that falls back to the Map default view centre when no office address is set. Two callers, no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- A stored office address is accepted only with in-range finite coordinates and a non-blank address, which is trimmed; blanks, bad JSON, arrays, out-of-range or non-numeric coordinates and a missing address all read as unset. Serialise and parse round-trip with extra fields dropped.
- The read looks the row up by its settings key; no row or an invalid row reads as unset; the upsert writes the serialised value under the key; the delete removes the key; a failed read or write throws.
- Saving from an address requires a non-blank address, geocodes the trimmed text, and saves the returned point with the typed address; a geocode refusal is translated with its detail, a transport failure and an unexpected payload each map to a message, and nothing is saved on any of them.
- The anchor is the office address when set, else the Map default view centre labelled by its address with its source named, else null.
