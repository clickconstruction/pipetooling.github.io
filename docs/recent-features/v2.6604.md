# v2.6604 — The crew reads the plans of the job they are on, on a development too (punch list #272) (2026-11-06)

Migration `20261106234500_plan_parts_crew_reads.sql` (`docs/migrations/20261106234500_plan_parts_crew_reads.md`) and the second half of the SQL bed `plan_sets_author`; no client change. Found 2026-11-06 by that bed's first run (v2.6583): a subcontractor on the crew of a job inside a development read no plan part. `plan_part_can_see` (`20261101210000`) read a development's part through its `developments` row under the caller's own RLS, and `developments_select` admits the office, estimators, primaries, superintendents and a master's shares, never a crew. So on such a job the Plans section had no *Building from* and *Add our as-built* (v2.6298, v2.6345) found nothing to add to; a job outside any development owns its part and the ledger shows the crew their jobs, so there the press always landed.

## Change

- **`plan_part_crew_can_see(part)`**: the signed-in user is on the crew of a job that builds from the part (`jobs_ledger.plan_part_id`) or owns it, crew as `helper_on_job` (v2.5526) reads it — the team table, or a schedule block on the job this week or last. `SECURITY DEFINER` with `row_security = off`, since the team table's SELECT policy hides a helper's own crew row. Executable by `authenticated` and `service_role`, by `anon` not.
- **`plan_part_can_see`** gains it as a third branch; **`plan_parts_select`** the same branch inline (the policy reads its own row's columns, and the definer reads `plan_parts` with row security off, so it does not come back into the policy). `plan_sets_select` reads `plan_part_can_see(part_id)` and opens with it. `developments_select` is not widened: a crew member still reads no development row, and the Plans section's *Building from* names the part. `plan_part_can_write` starts from `plan_part_can_see` and adds the five office roles, so the crew still changes no part and no set but their own as-builts and papers (`plan_set_crew_on_job`, v2.6583).
- **The bed `plan_sets_author`**, second half: jobs C and D on one development, each building from a part the development owns, a subcontractor and a helper on C's crew. Each reads no development row, yet C's part, its issued set and their own as-built there; neither reads D's part; the subcontractor keeps an as-built on C and is refused one on D and a change to C's part; the helper keeps an as-built on both his jobs and cannot touch the subcontractor's; the office reads all four parts. The structure is read from `pg_policies` and `pg_proc`: the select policy and the gate name the crew read, which is a definer with row security off. `scripts/pgtest-plan-sets-author.sh` re-applies this migration too, so a second run must change nothing.
