# v2.7838 — Workflow page: opening it no longer creates a workflow (2026-11-18)

Punch list #397, "Stages onto the job", PR 1 of 7. This one touches only the Workflow page; the other six touch the job form and the bid import.

## What was wrong

A read-only walk on 2026-11-18 found that opening `/workflows/:projectId` for a project with no workflow sent `POST /rest/v1/project_workflows`. The page's load called `ensureWorkflow`, which inserted a draft row named `<project> workflow` whenever it found none. A person who opened the page to look left a record behind.

## What changed

- **The open only reads.** The load effect and `refreshSteps` call a new finder, `findWorkflow`, which reads `project_workflows` and `gc_projects` and stops. `ensureWorkflow` still finds or creates, behind the same per-project mutex, and only a person's press reaches it: **Start a workflow**, a first step, a template, a projection.
- **The decision is a kernel**, `workflowFindStep` in `src/lib/workflow/workflowStart.ts`: a found workflow is used, a GC project gets none (v2.4846, pressed or not), an open with none is `empty`, and only a press is `create`. The same file holds the inserted row (`newWorkflowRow`) and the empty state's words (`noWorkflowWords`).
- **A project with no workflow draws an empty state** under its header: *No workflow on this project yet. Steps you add here show to the people they are assigned to.* and one press, **Start a workflow**. It is the repo's `EmptyState` over `emptyWords`' *make* kind. The press shows to the roles whose insert the database takes (`canStartWorkflow`: dev, master, assistant and controller). Every other role reads the first sentence alone.
- **The header stays**: the project's name, its edit press, the Superintendents strip and the Jobs strip need no workflow. **Add step**, the Projections & Ledger panel and the stage list with its template card wait for the workflow.
- **Start a workflow** does the insert the open used to do. The workflow lands in state and the page's load effect reads its steps as on any open. While it runs the press reads *Starting the workflow…*, and a second press joins the first one's call.
- **A refused insert names its reason.** The failure goes through `formatErrorMessage` under *The workflow could not be started.* and shows in the page's banner (`error`), so the empty state and its press stay. Before, a failed create went to `loadError` and replaced the page. A read that fails on the open still replaces the page, as before.

## Who gets the press

The brief for this PR named `canManageStages`, which counts a superintendent. The one insert policy on `project_workflows` (*Users can insert workflows for projects they have access to*, last altered in `20260927220000_controller_policies_the_rest.sql`) admits dev, master, assistant and controller, and no superintendent. A press drawn for a superintendent would refuse every time, so it is left off for them. Before this change a superintendent who opened such a project read *Failed to create workflow* in place of the page; now they read that there is no workflow yet. If superintendents should start workflows, that is a policy change, a follow-up.

The 3 workflows live today open exactly as before.

## Tests

`workflowStart.test.ts` holds the decision's eight cases, the row and the words by role. `useWorkflowStepsEngine.render.test.tsx` pins the hook: an open with no workflow sends no write, a re-read sends none, the press sends one insert and then reads the steps, three calls at once send one, a lost insert race adopts the winner, a refused insert lands in `error` with its reason, and a GC project gets none on a press too. `Workflow.render.test.tsx` pins the page: no write on open and the empty state's words and press, one insert for two quick presses and then the page as before, a subcontractor and a superintendent read the first sentence with no press, a controller gets the press, a refusal shows in the banner and keeps the press, and a GC project still sends nothing.

Nine mutants each failed a named test, with a passing control before and after: the open calling `ensureWorkflow`, the re-read calling it, the kernel always creating, the mutex removed, the GC check removed, the press shown to every role, the press shown to a superintendent, the reason dropped from the failure, and a press's failure replacing the page.
