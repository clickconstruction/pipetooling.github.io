# v2.6125 — Quickfill: Unpriced fixtures reads the tally again (2026-10-30)

Found by punch list #178's read-only walk of clicktooling.com on 2026-10-30: Quickfill → Unpriced fixtures' read answered 400 on every load, twice per visit (the station's banner and Quickfill's count). Since v2.5964 (punch list #184 sweep B, shipped in PR #6325 as v2.5962 · 5964 · 5965 · 5966), `loadUnpricedFixtureRows` (`src/lib/quickfill/unpricedFixturesIo.ts`) asked `list_tally_parts_with_po()` for `job_id, part_id, fixture_cost, created_at`, ordered by `created_at` then `id`. PostgREST orders an RPC read only on the columns its select returns, so the `id` tiebreak answered 42703 *column record.id does not exist*. Both callers are fail-soft, so the station kept a zero and drew no banner, which reads as nothing waiting. No migration, no edge function.

## What changed

- **The read selects `id`** beside the four columns. The tiebreak stays: `created_at` alone can tie, and a tie lets the `.range()` pages shuffle between requests (`fetchAllRows`).
- **The pin**: `unpricedFixturesIo.test.ts` holds that every column the read orders on is in its select. On the old read it fails with `[ 'id' ]`.

## The rule, measured live

As the dev on the dev server, against prod through the app's own client: an RPC read that orders on a column its select leaves out answers 400 42703 (`select=job_id&order=created_at` gives *column record.created_at does not exist*). A filter on such a column answers 200 (`select=job_id&part_id=is.null`, and the `or=(fixture_cost.is.null,fixture_cost.eq.0)` filter). So the rule is about the order alone. A table read is not affected, since PostgREST orders it on the table's own columns.

## The sweep

`src/` holds 807 `.rpc(` calls. A TypeScript AST walk over every chain rooted at `.rpc(`, through casts and parentheses, found two that order: this read, and a lens test's fake client that selects nothing and so returns every column. No other RPC read both narrows its select and orders, so nothing else had the slip. The same walk over `supabase/functions/` and `scripts/` found none. The two RPC builders kept in a variable (`dispatchSettingsJobsSearch.ts`, `BidsPricingTab.tsx`) neither select nor order.

## Verify

Live on the dev server as the dev, 2026-10-30: the page's two reads answer 200 with `select=id,job_id,part_id,fixture_cost,created_at` and `order=created_at.asc,id.asc`, and the old query answers 400 42703. The dev's tally holds no fixture-only row, so the station draws nothing for the dev either way. Not yet seen: the deployed app after the merge, where the two reads should answer 200 and a waiting fixture should draw the banner.

## Is this the best we can do?

For the read, yes. The lens's PostgREST (`src/lib/lens/answer/postgrest.ts`, punch list #194) orders an RPC's rows on the stored row merged with the projection, so it answers this request 200 where PostgREST answers 400. A lens walk of Quickfill could not have caught the slip. Refusing an RPC order on an unselected column there, as PostgREST does, is its own change.
