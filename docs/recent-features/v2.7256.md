# v2.7256 — Edge functions no longer upload the whole database types file (2026-11-14)

Infra only: no screen and no running code changes. 17 of the 190 edge functions uploaded the generated `src/types/database.ts` (1.48 MB) on every deploy, and `dev-mcp`, at 5.02 MB, was refused with HTTP 413 on 2026-11-13.

## Why

The copy of the kernels (`supabase/functions/_shared/gcKernels/`, `scripts/edge-kernels.mjs`) pointed each type import of `Database`, `Tables` or `Json` at the whole file in `src`, so `deno check` could read it. Deno erases a type import at run time, but `supabase functions deploy --use-api` uploads every file an import names, a type-only one too. `check:edge-bundles` and the drift check walk only the imports that run, so nothing in CI saw the upload grow.

## What changed

- **A slim database file in the copy.** The generator writes `gcKernels/types/database.ts` (`DATABASE_TYPES`): of the public schema, every table, view and function a string in the copy names, and what a kept function's arguments or `SetofOptions` name in turn, each member line for line as the generated file writes it, with every enum, composite type, the other schemas, the helper types and `Constants`. On 2026-11-14 that is 106 of 665 tables, 2 of 13 views and 11 of 1,218 functions, 0.32 MB. Row types stay real.
- **The names are read, not listed.** `stringWords` reads every string literal and template text of each file the copy holds, comments and regexes left out. That covers a `.from('…')`, an `.rpc('…')`, a `Tables<'…'>`, a `Database['public']['Tables']['…']`, an embed in a select and a table name kept in a constant. A relationship names its table as a string and needs no other table. An edge file outside the copy that imports the slim file is read too: `bridge-weekly-sheet` now takes its client type from it.
- **The file is read in its parts** (`databaseParts`), which must put the file back line for line, or the generator refuses with the reason. So a change in how `supabase gen types` writes the file stops the generator rather than writing a broken copy.
- **A types regenerate flows through.** `gen-types:local` and `gen-types:linked` run the generator after the types, so `scripts/db-push.sh` rewrites the slim file too. A types PR that skipped it fails `edgeKernels.test.ts`, which regenerates the copy.
- **`check:edge-bundles` holds the upload.** It walks each function's upload as the CLI does (`scripts/lib/edgeUploadGraph.mjs`, type-only imports included). A function past `UPLOAD_CEILING_BYTES`, 4.5 MB of raw source, fails the PR with its three biggest files, and every run prints the five biggest.

## Checked

- `npm run gen:edge-kernels -- --check`: the copy matches (336 files).
- `npm run check:edge-bundles`: all 190 link, every upload under 4.5 MB (dev-mcp 4.01 MB after #8089).
- `edgeKernels.test.ts` (23) and `edgeUploadGraph.test.ts` (5), with the words, the parts and the slim file on planted files; the 337 test files that read the functions pass.
- `tsc` over the copy's index and its off-index entries against the slim file: no errors. A probe that puts a number in a `bids` row's `id`, or reads a table the slim file left out, fails as it should.
- `deno check`: `customer-portal` passes. `dev-mcp` and `bridge-weekly-sheet` give the ten and two errors `main` gives, word for word but for the order of one union in one message.

## After the merge

Redeploy the 17 so each uploads the smaller set. `check:edge-drift` names seven of them, whose bundles that run change in comments and type-import paths alone: `bridge-weekly-sheet`, `customer-portal`, `dev-mcp`, `drive-link`, `gc-trade-portal`, `messages-notify`, `photo-save`. The other ten reach the slim file by type imports alone, so their running code is the same and the drift check does not name them; each takes the smaller upload at its next deploy.
