# v2.3277 — Robot price matrix, PR 6: "Set up on this Mac" — one command connects Claude Desktop, and the key is never shown (2026-09-11)

Client + migration `20260911043553_twin_setup_codes` (**push after the client deploys**) + new edge function `twin-setup` v1.0.0 (**deploy after merge**; `verify_jwt = false` in `config.toml`). Plan: [`docs/PRICE_MATRIX_PLAN.md`](../PRICE_MATRIX_PLAN.md).

## Why

After PR 5 the pricing robot worked end to end, but connecting a Mac to it took three hand steps on a dev-only page: issue a key (shown once), paste the key into a Terminal command when a silent prompt asked, then quit and reopen Claude Desktop. The owner asked how to make those "as easy as possible … where the user can paste the key in a way the agent can plug it into the right place." The answer is that nobody should hold the key at all.

## What shipped

- **Set up on this Mac** — a button on three doors: **Robots → Scoreboard → Pricing robot** (every estimating-staff role — the card now renders before the robot has run, as the place to start it), **Robots → Console** (step 1 of both the *From Claude Desktop* and *Pricing robot* columns), and each twin's row on **Settings → Digital twins**. The dialog ([`TwinSetupDialog`](../../src/components/bids/TwinSetupDialog.tsx)) asks whose Mac it is (that becomes the key's label), mints a one-time **setup code**, and shows one Terminal command with the four steps beside it: copy · open Terminal · paste, Return · new incognito chat, paste. A 10-minute countdown and a *Make a fresh one* door when it lapses.
- **The command** ([`buildDesktopSetupCommandFromCode`](../../src/lib/bids/desktopKickoff.ts)) carries the code, not a key. Pasted into Terminal it: redeems the code at `twin-setup` (which mints the `twin_credentials` token server-side and returns it once, to that machine), merges the `twin-mcp` connector into `claude_desktop_config.json` with the token as its env value, quits Claude Desktop if it is running and reopens it so the connector loads, and puts the robot's kickoff on the clipboard. It is a Node script (Node is already required for `mcp-remote`), so a Mac without the command-line-tools python works too. The key is never printed, typed, or on a clipboard. Verified against a stub server with stubbed `pgrep`/`osascript`/`open`/`pbcopy` and a scratch HOME: merges beside an existing connector, restarts, copies; a bad code exits 1 with the server's words. 5 kernel tests.
- **`twin-setup` edge function** — `mint` (staff session; devs for any twin, the other estimating roles only for a **pricer** — key issuance for the bid robots stays dev-only) returns a ~49-bit code (`K7Q2-M9XD-4T`, Crockford-ish alphabet, 10 minutes, 10 per minter per 10 minutes); `redeem` (no session — the code is the auth) claims the row with a conditional UPDATE (two Macs racing get exactly one winner), mints the credential, stamps `credential_id`, logs a `twin_runs` row (`mission = setup`), and returns token + connector URL + the kickoff filled in + the check call. A miss costs 400 ms and says only that the code is invalid, used, or expired.
- **Shared kickoffs are generated:** `scripts/build-twin-mcp-briefs.mjs` now also writes `supabase/functions/_shared/twinKickoffs.ts` from the two Desktop kickoff docs, so the text a redeemed code puts on the clipboard is the document the Console copies. Both kickoffs' *One-time setup* sections lead with the short way and keep the key-based way as the long way; the pricer now says in one line that the connector answered before it works.
- **Console:** the old key-based command stays as a secondary **Key-based command** button on both columns.
- Docs: `EDGE_FUNCTIONS.md` (`twin-setup`), migration fragment, `docs/twins/HANDOFF.md`, `docs/twins/TWIN_HARNESS.md`, help guides *run the robot estimator from Claude Desktop* and *get supply house prices on a bid*.

## Still open

Windows has no path (the config location and the quit/reopen are Mac's). `twin_setup_codes` rows are never pruned (tiny; a dev can `DELETE … WHERE expires_at < now() - interval '30 days'` when it matters). The Scoreboard card offers the pricer's setup to every estimating-staff role by design — the pricer never bids; the bid robots' setup stays on dev pages.
