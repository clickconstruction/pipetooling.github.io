# v2.3027 — Test-gap audit, pass 37: sending a billed invoice back gets its first tests (2026-09-07)

Follow-up to v2.3026. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`voidStripeInvoiceForRevert.ts` (155 lines) is what runs when a billed invoice is sent back — a job reverting to Ready to Bill, the Dashboard billing pipeline, a write-down, or a subcontractor's Collect Payment send-back: it decides which lines need a Stripe void, calls the `void-stripe-invoice-for-revert` edge function, cleans the ledger line through an RPC (with a fallback for the older edge that only reverted the line), and sweeps every billed line on a job. Five callers, no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- A billed line needs a Stripe void when it carries a Stripe invoice id or was sent through Stripe; anything not billed never does. Only a dev follows the Stripe test / live preference; every other role bills live.
- The edge call sends the invoice id, the Stripe mode and the caller's bearer token (the sub send-back adds the job id for the edge's team and flow checks), and its answers map to: success → ok; the body's own `error` → that message; an error with a readable body → that detail; a bare error → its message or "Failed to void Stripe invoice"; anything else → "Unexpected response from server".
- The ledger clean-up deletes the billed line by RPC and, when the RPC says the line is no longer billed (an older edge already reverted it), deletes the ready-to-bill line instead; each failure surfaces the RPC's own error, with "Failed to remove billing line" as the fallback.
- The per-job sweep reads the job's billed lines, voids the Stripe-backed ones through the edge and then cleans the ledger, deletes the rest by RPC, stops at the first failure, and is a no-op success with nothing billed.
