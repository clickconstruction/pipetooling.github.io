# v2.2759 — Upcoming-payroll clock sessions page past the 1,000-row cap (2026-09-04)

First live catch of the v2.2756 row-cap tripwire, the same day it shipped: every Dashboard load logged `[row-cap] clock_sessions returned exactly 1000 rows with no limit`. The upcoming-payroll estimate (Dashboard AP card, People → Pay stubs header, Employment tab pay totals) reads every roster member's non-rejected, non-revoked sessions since `upcomingPayrollFetchStartYmd` — a window that walks back to the oldest unpaid stub, currently 2026-05-10. Four months of one roster is past PostgREST's cap, so the estimate was silently understated.

## Client only — no migration, no edge functions

- New kernel [`src/lib/upcomingPayrollSessions.ts`](../../src/lib/upcomingPayrollSessions.ts): `loadUpcomingClockSessions(supabase, userIds, fromYmd)` on `fetchAllRowsChunkedIn` (150-id `.in()` chunks, each paged with a stable `work_date, id` order). 2 tests with the fake-cap client (2,400 sessions across 12 people).
- [`useDashboardFinancials.ts`](../../src/hooks/useDashboardFinancials.ts), [`PeoplePayStubsTab.tsx`](../../src/components/people/PeoplePayStubsTab.tsx), and [`PeopleEmploymentTab.tsx`](../../src/components/people/PeopleEmploymentTab.tsx) all call it; each keeps its existing "no estimate" fallback on error.
- Left alone on purpose: the fetch window itself. It grows with the oldest unpaid stub; clearing old stubs is the owner's lever, and paging keeps the number right regardless.

Verified from a worktree dev server: the Dashboard no longer logs `[row-cap] clock_sessions`; kernel tests + release-notes drift test green, `tsc -b` clean.
