# v2.8473 — Maps: a place to remember an address the map cannot place (2026-11-24)

Punch list #408, step 1 of the train of three in [`to-dos/remember-unplaced-addresses.md`](../../to-dos/remember-unplaced-addresses.md). One migration, [`20261124091500_address_geocode_misses`](../migrations/20261124091500_address_geocode_misses.md). No screen changes.

## Why

An address no map service can place is kept nowhere, because `address_geocodes` holds only a point. So every screen that lists the record asks OpenStreetMap, Google and the Census again on every open. The card's read of 2026-11-20 put that at 80 to 250 calls a day for five addresses. The owner said to build it on 2026-11-24.

## The owner's three calls, built to the plan's picks

Each can be flipped.

1. **Shared memory, not one per phone.** This migration is the shared one. Flipping it means dropping the table and keeping the memory in each browser instead.
2. **A miss stands 30 days.** The table holds no number of days. Step 2 holds it in one named constant, so a change needs no migration.
3. **No pin by hand.** That stays a card of its own. A job nobody can place stays off the maps, and its line says so.

## What changed

- **`address_geocode_misses`**: the address key `address_geocodes` uses, the reason, and the day it was checked. Any signed-in user reads and writes a row. The server stamps the day on every write. Nobody deletes a row by hand.
- **A saved point takes its miss away.** A trigger on `address_geocodes` deletes the miss for the same address after every insert and update, whoever saved the point.
- The four fences close the migration, so a training account, a digital twin and an archived account write no miss.

## What differed from the card

- The card's plan had each function delete the miss on a hit. Six writers save a point today, so the delete is a trigger on `address_geocodes` instead, and no user holds a delete on the new table.
- The card did not say who sets the day. The server does, because the table is open to every signed-in user.

## Verified

- A new SQL bed, `supabase/tests/address_geocode_misses/` (`npm run test:pg:address-geocode-misses`), on the whole schema. It ran here on 2026-11-24 against a throwaway Postgres with every migration applied, and the migration applied twice more with nothing added. All 23 checks passed. Every person and address in it is made up.
  - A subcontractor writes a miss and reads it. The day is the server's, not the day sent. A blank reason and a key under three characters are refused.
  - A helper reads it and checks it again: the upsert keeps one row, carries the new words, and cannot backdate the day.
  - Nobody deletes a miss by hand, a dev included.
  - A training account reads a miss and writes none. A digital twin writes none. An archived account reads none and writes none. `anon` neither reads nor writes.
  - A point saved to `address_geocodes` takes the miss for that address away, on an insert and on an update, and leaves another address's miss alone.
- CI runs the same bed from `scripts/sql-beds.txt`.
