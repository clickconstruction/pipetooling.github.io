# v2.4388 — Takeoffs: a new version or a duplicate keeps its stage boxes and Sold in rules (2026-10-01)

Punch list #78, found on 2026-10-01 while confirming that Combined's stage boxes make By Stage redundant (#77). The owner: build it first, test it thoroughly, and ask of the plan *is this the best we can do?* Once By Stage retires, the boxes are the only stage data a bid has, so every copy has to keep them.

## What was wrong
Three functions copy or move a bid's Combined part lines, and all three were last written before the stage boxes (v2.3671) and the Sold in rule (v2.3406) existed.
- **A new version** (`create_bid_version`) copied the lines without their Sold in rule and copied no stage boxes.
- **A duplicate** (`duplicate_bid_to_service_type`) had the same two gaps.
- **An adopt** (`adopt_bid_as_version`) moved the lines and left the boxes filed under the retired bid, where the Stages panel never reads them.

## What changed
- **Migration `20261002100000_combined_copies_keep_stages`** ([doc](../migrations/20261002100000_combined_copies_keep_stages.md)). A new version and a duplicate copy every box, a fixture's onto the cloned count row and a line's or a bundle part's onto the cloned line. The lines keep their Sold in rule. An adopt moves the boxes with their rows. One `UPDATE` gives back the boxes an earlier adopt left behind.
- **The duplicate also keeps eight columns** it had fallen behind on: a labor row's `kind`, `unit`, `source` and `source_note`, and the cost estimate's four travel columns. A sub line or a per 100 ft row copied without them was costed as a counted fixture.
- **A test that runs the copies.** `npm run test:pg:combined-copies` builds a throwaway copy of the whole schema (the Supabase Postgres image with every migration applied, about a minute) and runs `supabase/tests/combined_copies/20_scenario.sql` as an estimator through RLS. The old functions fail its second step. The new ones pass all fifteen.
- **A test that stops the next one.** [`bidCopySql.test.ts`](../../src/lib/bids/bidCopySql.test.ts) reads each function's newest body against the generated types. A column added to a copied table, or a new table that hangs off a count row, fails CI until the copies learn it. It fails ten ways on the old bodies.

## Asked: is this the best we can do?
The plan named two gaps. An audit of every table with a `count_row_id` and every column the copies name found more. The duplicate's labor and travel columns are fixed here, because the function was being rewritten and a copy that changes a bid's cost is the same fault. Four others change what a copy means, so they are punch list #79 with a default each: quoted fixture costs follow no copy, a duplicate of a bid with versions stacks every version's rows, a duplicate keeps pointing at the first bid's own prices, and an adopt leaves a submittal's takeoff picks behind.
