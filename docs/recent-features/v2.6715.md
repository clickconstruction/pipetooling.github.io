# v2.6715 — A mail conversation onto an HR file: the seat's mail tag lands a thread as dated entries on a person, each with its Gmail id (2026-11-08)

Punch list #289 (`to-dos/mail-onto-hr-file.md`). The seat's mail tag (v2.6568) put a whole Gmail conversation onto a job; a conversation about a person had no door, and the mails that bore on a former teammate's case had to be retyped as entries by hand with nothing on the entry saying which mail it came from. Server 0.41.0. Migration `20261108194723_hr_mail_tag.sql`.

## What changed

- **A person target on the mail tag** (`plan_mail_tag` / `apply_mail_tag`, `_shared/devMcpMailTag.ts`): `tag.person: { person_id, stop? }` in place of `tag.job`. The seat POSTs gmail-mine's `tag` with `person` as the dev through the same seat door (`as`, `plan`); the plan (`MyMailPersonTagPlanOk`) lists each mail as entry · already · skip with the day it lands on, whether a follow already stands, and the counts; the hash commits to the account, the thread, the person, `stop`, `following` and each mail's gmailId and kind; apply plans again, compares, asks the log and tags. An archived login's box may be read for a person tag, since the entries are the dev's. Both targets named is refused.
- **The landing** (`gmail-mine`, `tagPerson`): one `person_file_entries` row per mail, `source` `conversation`, `entry_date` the mail's day in the app's calendar, the content a fixed shape — From, To, Cc, Subject, Sent, the files by name and size (a picture placed in the body left out), then the body as plain text cut at 30,000 characters with a line saying how much stays in Gmail — written as the dev who applied (`created_by`, `author_label`), with `gmail_message_id` and `gmail_thread_id`. The kernel is `src/lib/myMail/personTagPlan.ts` (`planPersonTag`, `mailEntryContent`, `personEntryRow`), generated to the edge copy; the preview is `personTagPlanPreview` in `mineFunction.ts`. The `email_tag_threads` row is kept first with `person_id`, so the follow knows the conversation whatever the entries do. No label is put on the mail and no line is written in Messages.
- **The entry remembers the mail**: the two columns, nullable, and the partial unique index `person_file_entries_gmail_once` on `(person_id, gmail_message_id)` as the dedupe — a thread tagged twice adds only the mails the file has not seen, a second apply racing the first lands nothing twice (a duplicate key is counted `already`), and the entry's mail reads back through `read_mail(account, id)`. Gmail's ids are per mailbox, so the same mail tagged out of two boxes is two entries.
- **Later mail follows** (`followFiles` in gmail-mine's cron `follow`): the person rows in the window, each box's login read whether archived or not, each mail no entry holds read whole and landed through the same plan as the dev who tagged; the job query now takes the job rows alone. `MyMailFollowOk` carries `entries`.
- **Stop following**: `tag.person.stop: true` plans lifting the follow (the plan says whether one stands and how many entries the file holds for the conversation) and on apply deletes the row; every entry stays. The press on the Timeline the card named is not built: the seat is the door for now.
- **One target a conversation a box**: a conversation on a job is refused for a person and a conversation on a file is refused for a job or an untag by the person's own press (`MY_MAIL_ON_FILE_WORDS`); `fillRows` reads the job rows alone. The check `email_tag_threads_one_target` takes `_one_job`'s place, and the read policy closes the person rows to everyone but a dev.
- **Counsel-only is not an entry's concern**: a mail whose content is counsel-only goes on as an evidence record with the tick (`plan_mail_file` with `to.kind person_evidence`), never as an entry; the docs and the skill say so.
- Docs: `docs/dev-mcp/README.md`, `docs/EDGE_FUNCTIONS.md` (dev-mcp 0.41.0, gmail-mine), `docs/HR_FILES.md`, `docs/MESSAGES_ARCHITECTURE.md`, `.claude/skills/mail-search/SKILL.md`, `docs/migrations/20261108194723_hr_mail_tag.md`.
