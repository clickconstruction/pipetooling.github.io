# v2.4192 — Submittals: Assign pages opens the vendor file once, and scanned pages show (2026-09-29)

No migration, no edge function. The owner's report (2026-09-29, with a console log from clicktooling.com): "when a user clicks the Assign pages… button and opens the modal, it crashes her computer."

## What was going on

The log (32,891 lines) is one loop. `SubmittalAssignPagesModal` (v2.4143) opened the file in an effect keyed on `loadBytes`, and the tab passed `loadBytes={() => downloadFile(…)}` — a new function every render — so any re-render of the tab destroyed the open document (*Worker task was terminated*, 30 times) and downloaded and re-opened the file, thumbnails and text for every page again. The loop closed through the file's line (v2.4171): `textsDone` was never reset on a re-open, and the effect that reported the read to the tab (`onReads`) depended on `texts`, so the second read reported after *every page* with a partial count; `noteFileReads` saw a different `namesRows`, wrote `bid_submittals.source_files` and reloaded the tab; the reload re-rendered the tab, which handed the modal a new `loadBytes`, which destroyed the document and opened it again. Per page: a storage download, a pdf.js document, a database write, a full tab reload. The log counts 314 page renders and 375 read reports for one 75-page scanned file before the browser gave out.

The same log shows a second defect on the same file: 97 warnings *Ensure that the `wasmUrl` API parameter is provided* and *Unable to decode image … JBig2 failed to initialize*. pdf.js 6 decodes JBIG2 and JPEG 2000 images — every scanned vendor PDF — in WebAssembly loaded from a directory the app has to name, and none of the three call sites named one, so scanned pages rendered blank everywhere: the walk, the strip's *Show the pages*, the Form Studio's page canvas, the RFQ reply reader.

## What shipped

- **The modal opens the file once per file.** The open effect is keyed on `file.path`; `loadBytes`, `onReads` and the rows are read through refs; the open resets `texts` / `textsDone` / thumbnails / the reading-size pages so a real re-open (a different file) starts clean; the file's line is reported once, at the end of the read, from the whole read — the separate `onReads` effect is gone. **The tab** hoists `downloadFile` to module scope and hands the modal `assignLoadBytes` (a `useCallback` on the file's path) and `assignGuesses` (a `useMemo` on the tasks) instead of a new arrow and a new map per render. Either half alone stops the loop; both are right.
- **pdf.js's run-time files ship with the app.** [`src/lib/pdfjsAssets.ts`](../../src/lib/pdfjsAssets.ts): the three directories (`wasm`, `cmaps`, `standard_fonts`) under `/pdfjs/`, `pdfjsAssetPath` (a request path → the file it names, nothing outside the three directories and no dot files) and `pdfjsDocumentOptions(base)` (`wasmUrl`, `cMapUrl` + `cMapPacked`, `standardFontDataUrl`). The `pdfjs-assets` plugin in `vite.config.ts` serves them from the installed `pdfjs-dist` in dev and copies them into `dist/pdfjs/` at build — nothing vendored into the repo, nothing to drift from the installed version (3.9 MB in dist, fetched only when a document needs one).
- **One opener.** [`src/lib/pdfjsDocument.ts`](../../src/lib/pdfjsDocument.ts): `loadPdfjs` (lazy import, the worker from the bundle — the eight lines that had been copied into three files), `getPdfLoadingTask(bytes)` (the options named; the task owns `destroy`) and `getPdfDocument(bytes)`. `pdfThumbnails.ts`, `PdfPageCanvas.tsx` (its per-buffer cache kept) and `extractReplyText.ts` open through it.

Tests: `pdfjsAssets.test.ts` (the path guard, the option URLs); the modal's render test gains *opens the file once* — the host re-rendering twice with new callbacks and a new rows array calls `loadBytes` and `openPdf` once, reports the read once, and unmounting destroys the document once (fails on the old modal: `openPdf` called twice).

Verify: `npx vitest run src/lib/pdfjsAssets src/components/bids/SubmittalAssignPagesModal src/components/bids/BidsSubmittalsTab`; `npm run build` copies the three directories into `dist/pdfjs/` (3.9 MB); `curl -sI localhost:<port>/pdfjs/wasm/jbig2.wasm` on the dev server answers 200 `application/wasm`.

Verified 2026-09-29 on BP398 through this worktree's dev server (the dev login, production data, nothing written by hand): Assign pages… opens the walk on the 2-page NWS file with page 1 drawn and *Already on WC-1*; with `fetch` and `Worker` counted in the page, Cancel and open again makes two storage downloads and two workers — React StrictMode's development double mount, one of each in production — and the counts do not move over the next twenty seconds while the read lands and the tab reloads. The vendor file on BP398 is vector, so no wasm was fetched there; the JBIG2 path is covered by the served-asset check above and pdf.js's own loader.
