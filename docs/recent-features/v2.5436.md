# v2.5436 — Messages: the morning reminders read everyone's flow the way their own panel does, behind the scenes (2026-10-13)

Messages, cut 5, PR A of the morning run (`messages-nudge-dispatch`; `BUILD_PLAN.md` → Cut 5 and section 6). The run's planner, `planNudgeRun` (`flows/nudgeDispatch.ts`, v2.5270), takes everyone's flow; nothing on main put everyone's flow together, only one person at a time in their panel (`useFlowPerson`). `src/lib/flows/nudgeRunInputs.ts` does it from the rows the edge function will read set-wise as the service role. Pure. No screen, no table, no migration, no edge function yet: the switch's seed and policy are PR B, and the function and its cron are PR C, after the Quo functions (#5452).

- **`nudgeRunReads(rows, now, { origin, options })`** builds `planNudgeRun`'s input. Each person is put together the way their own panel puts them together, through `personFlowFrom`, so the run reads a person the way Follow up and the step card do:
  - their kind's flow as the office edited it, or the seed's when a kind has no steps on the database (`flowsByKind`, as `readFlowDef`);
  - their `flow_rows_for` rows, holds, reminders sent, step notes and what we owe them;
  - their thread's newest 50 lines (`newestLines`, `PERSON_LINES`), so lines the run reads past those change nothing;
  - a customer's page as cut 8 reads it back.
  It also gives `channelIds`, the `contact_channels` row each text goes to, and `unread`, the contacts whose rows did not come back or whose kind has no flow, for the run's log.
- **The owner's switch** (`appSendsFrom`, `APP_SENDS_SETTING_KEY` = `messages_nudge_app_sends_v1`): one key per step id under its kind, as `{ "trade": { "portal": true } }`, read from the row's `value_text` as stored. Only `true` under a known kind turns a step on; anything else, text that is not JSON, and the seed's `{}`, is off. The kinds nest because a step id is unique only within its flow: the sub flow (#5586) brings `asked`, `onsite` and `yes`, which the customer flow already has.
- **The number** (`textNumberOf`): of their numbers that never sent STOP, the one their thread last carried a line on, else the first added. With every number stopped, the newest of them, so the run logs it as stopped. An address is never a text number.
- **The link** (`portalLinkOf`): a trade partner's live page from the office's preview (`previewPath`, `/t/<token>?preview=1`) without the preview mark, on the app's address. A customer's link comes in from the run, by customer id, when it has one.
- **The rest**: `quickRepliesFrom` keeps the team's quick replies with their presses (the app has no lines of its own, so a line marked mine is left out); `nudgeSentFrom` reads `nudge_sent` with the GC project as the job, as `marksFrom` does; `flowFirst` is what the flow calls them, the panel's rule (`useFlowPerson` moves onto it once #5525 lands).
- **Tests** (`nudgeRunInputs.test.ts`, 24) over the prototype's demo trade partner Tom on Fri Oct 2 at 9 AM: the run's Tom equals his panel's; with the seed's `{}` nothing sends and his reminder is kept back as off; with Portal opened on he gets one text with his page link, and a second run that morning, from the first run's `nudge_sent` row, sends none; an older text of ours past his newest 50 lines drops out as it does on his panel. Planted regressions each fail a test: any truthy value turning a step on, every line read instead of the newest 50, a stopped number keeping its channel.
