# v2.3006 — Test-gap audit, pass 22: workflow-step notifications get their first tests (2026-09-07)

Follow-up to v2.3005. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`workflow/stepLifecycleNotifications.ts` (307 lines) is the shared sender behind every workflow-step email and push: the Workflow page and the Dashboard Projects card both call it when a step is started, completed, approved, rejected or reopened. It decides who hears (the assignee, the step's subscribers, the next step's assignee on a handoff, the prior assignee on a rejection), resolves each recipient (person id first, then a user by exact name, then an active person by name), and hands the payload to the `send-workflow-notification` edge function. Its siblings in `workflow/` were all tested; this one was not.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Nothing is sent without both a project id and name, and an action outside the five lifecycle actions sends nothing after the step read.
- An assigned person with an account notifies their **user** (user email and id) even when the step's display name is stale; a person without an account notifies the person's email with no user id; without a person id the user is matched by trimmed exact name, then an active person by name, then nobody.
- Subscribers are only notified when a session user is known: pass the id, pass null to skip, or leave it undefined and the sender asks Supabase Auth itself. An unnamed subscriber is addressed by their email.
- The payload carries the template, the step id, recipient email / name / user id, the push title and body (only the handoff sets them), the deep link `…/workflows/<project>#step-<step>`, and the variables (name, email, project and stage names, assignee, link, plus `previous_stage_name` and `rejection_reason` where relevant).
- Completed and approved behave the same: assignee, subscribers, then the next step's assignee gets "Your turn: Step completed" with the previous stage named. The last step has nobody to hand to; a rejection on the first step has nobody prior.
- An edge-function error or throw is logged and swallowed, and later sends in the same action still go out.
