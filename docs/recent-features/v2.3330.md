# v2.3330 — Cash App reconciliation, PR 4: the Cash App ID field on Record payment, `advance` as a pickable offset kind (2026-09-11)

Client only. Closes the loop the tool depends on: from now on a Cash App payment recorded by hand carries its Transaction ID, so the reconcile's rule (a) matches it exactly and the review list only ever holds what was truly forgotten.

## What shipped

- **Record payment** (`People.tsx`, the modal only): a **Cash App ID (optional)** input above Note. When filled, the memo is `cashAppPaymentMemo(id, note)` → `Cash App #D-… "note"` (uppercased id). After the `pay_stub_payments` insert (now `.select('id')`), a best-effort update files the matching `cashapp_transactions` row — if it exists and is still in `review` — as `recorded` / `match_rule = manual` with the payment link and the report's person. A miss only leaves the row for the next import's rule (a).
- **`advance` offset kind**: `PersonOffsetKind` gains it; **Add offset** offers "Advance (pay sent ahead of a report)"; the Offsets tab labels it **Advance**; the tab's link-only "apply to a stub" path refuses it with a pointer to the Less step (the same guard employee credit has), because an advance must become a deduction row, which only the Less modal writes.

## Left as is, flagged for the owner

`PersonOffsetFormModal` still labels employee credit "(overpayment / advance)" while `POSITIVE_OFFSET_TYPES` treats employee credit as money *we owe them*. The new `advance` kind is unambiguous (they owe us; a charge until deducted). Whether old advances filed as employee credits should be re-typed is a data decision, not made here.
