# v2.2849 — Moneyfill card charges: "Sort in Banking → User Sort" opens the tab on the charge; queue reads share Banking's paged allocation fetch (2026-09-05)

Journey-map Phase 4, Tier-1 #13 (C10 = J5-1 / J33-F1, `pipetooling-journey-map` → `docs/journeys/weekly-money-close.md` #1, `banking-reconcile.md` F1). Sequenced after Tier-1 #3(a) (v2.2841, PR #2580) per the map's constraint 2: before #2580 the target tab's headline counts were 1000-row cap artefacts and its Link… sheet could erase splits, so sending weekly card-charge traffic there would have amplified a data-loss path.

## What was wrong

`MoneyfillCardChargesSection.tsx` rendered one **Assign in Banking sorting** button per unsplit card charge whose handler was a bare `navigate('/quickfill')` under `title="Assign job splits in Quickfill → Banking sorting"`. Quickfill's `banking-sorting` section is org-hidden via `quickfill_hidden_section_ids`, so every click (19 buttons · ~$10k on the walk night) landed at the top of Quickfill with no sorting section in the DOM — a dead end inside the weekly close. The working door, Banking → **User Sort** (`/banking?tab=sorting`, `parseBankingView` maps it for dev, assistant-like and master), was never named. Moneyfill is dev + controller; Banking's gate is `isAssistantLike` (assistant ∪ controller) ∪ dev ∪ master, so no gate change is needed (J5's caveat (a) was wrong at the gate; the data-layer controller refusal is #28's).

**Not in this PR's premise:** Moneyfill has no allocation write path — the section is read-only and links out (WEEKLY_MONEY_PLAN "link, never a second editor"). There is no second save path to unify and no reroute-of-an-allocation to confirm; the single writer stays `MercuryTransactionAllocationsModal` → `replace_mercury_transaction_splits`, guarded by v2.2841's `decideSplitSaveGuard`.

## Mechanism

- **Kernel** [`moneyfillWeekClose.ts`](../../src/lib/moneyfillWeekClose.ts): `MONEYFILL_CARD_CHARGES_SORT_PATH = '/banking?tab=sorting'` and pure `cardChargeSortHref(counterparty)` → `/banking?tab=sorting&q=<encodeURIComponent(trimmed counterparty)>` (no `q` when blank). Tested in [`moneyfillWeekClose.test.ts`](../../src/lib/moneyfillWeekClose.test.ts) (never Quickfill; encoding/trim; blank → no `q`).
- **Button** ([`MoneyfillCardChargesSection.tsx`](../../src/components/moneyfill/MoneyfillCardChargesSection.tsx)): label **Sort in Banking → User Sort** (the tab's real label — J5 caveat (b)); `title` says where it goes and what to press there; `onClick` → `recordNavClick(userId, role, 'moneyfill-card-charges', href)` then `navigate(href)`. Section copy now names the fix surface ("Split each one in Banking → User Sort (Link…)"). Telemetry: the map's `moneyfill_card_charges_assign_clicked` lands in `ui_nav_clicks` as `control = 'moneyfill-card-charges'`, `target = <href>` (existing kebab-case control convention; no migration).
- **Banking `?q=`** ([`Banking.tsx`](../../src/pages/Banking.tsx)): `bankingSearchText` seeds once from `searchParams.get('q')?.trim()` on mount (lazy `useState`), so the User Sort (and Ledger) search box opens pre-filled. Deliberately read-once: the URL is not kept in sync with later typing, and the master/assistant `?product`/`?tab` normalizer copies `prev` so `q` survives. First deep-link param Banking honours beyond `product`/`tab` (BANKING_TABS_ARCHITECTURE's "no deep links carry ids" is still true — `q` is a search, not a record pointer). The User Sort default slice is the last 90 days; Moneyfill's default close week (previous complete week) is inside it.
- **One read path for "is this charge split?"**: `fetchUnsplitCardChargesForWeek` now pages the week's `mercury_transactions` via `fetchAllRows` (ordered `posted_at, id`) and reads allocations via `fetchJobAllocationsByMercuryTxIds` — the same 200-id-chunked, per-chunk-paged helper Banking's User Sort uses since v2.2841 — replacing an un-ranged `.in(...)` that the PostgREST 1000-row cap could have silently truncated. The predicate is unchanged and identical to `countSortingUnmatched.withoutJobSplit` (no allocation rows ⇒ not split); the two surfaces still scope differently by design (this queue: card purchases in the close week; User Sort: every row in the configured slice), so their headline numbers are not expected to be equal — only to agree per charge.

## Verify

1. As dev or controller, open `/moneyfill` on a week with unsplit card charges. Each row's button reads **Sort in Banking → User Sort**; hover shows the counterparty it will search for.
2. Click one: lands on `/banking?product=mercury&tab=sorting&q=<counterparty>` (product is stamped by the normalizer for assistant/master; dev keeps `?tab=sorting&q=`), the **User Sort** tab is selected, the search box holds the counterparty, and the charge is in the visible rows. Press nothing else.
3. `ui_nav_clicks` gains a row `control = 'moneyfill-card-charges'`, `target = '/banking?tab=sorting&q=…'`, `from_path = '/moneyfill'`.
4. Back on Moneyfill, the queue count matches the number of that week's negative debit-card transactions with zero `mercury_transaction_job_allocations` rows (the same rows User Sort marks "Not split" when filtered to the week).

Revert the PR — client-only; no migration, no edge function, no schema.
