# v2.3223 — "Attached — rerun" on a plans ask also puts the bid at the front of the next robot batch (2026-09-10)

Client only; no migration, no edge change.

## Why

v2.3212 put a robot's plans ask on the human bid's needs sheet with three taps. Tapping **Attached — rerun** saved the answer and nothing else: the robot would read it whenever a run next called `get_answers`, and the hourly batch only claims new bids, so the fix could sit. The tap promised a rerun; it should ask for one.

## What shipped

- **Shared predicate** `answerRequestsRerun(answer)` (`_shared/twinQuestionKind.ts`): true for the default tap and for any typed answer that says rerun / re-run / run again / try again / go again. Tests cover the taps, free text, and the "runoff" false positive.
- **Needs sheet** (`RobotNeedsSheet.tsx`): when a **plans** ask is answered with a rerun answer, `onAnswer` carries `{ rerunBidId }` — the human bid the sheet is open on. Decisions and the other two taps carry nothing. The row's caption now says what the tap does.
- **Page** (`Bids.tsx` `answerRobotQuestion`): after the answer row is written, a `rerunBidId` stamps `bids.robot_requested_at / robot_requested_by` — the same write as the green robot icon's *Front of the line next batch* — with the optimistic local patch and the refused-write guard. Toasts: *Answer saved — the robot goes again, front of the line next batch*, or, if the stamp is refused, *Answer saved, but the rerun request did not stick — use the robot icon to move it up*. The answer is never lost to a failed stamp.
- **What the stamp does downstream**: the bid reads green on the Queue lens and in `get_shadow_queue.requested`. The dispatcher will not hand the bid out again while the robot's shell exists (`twin_shadow_runs` marks it taken), so the run that acts on it is the robot **resuming its own shell**. The bid skill and the Desktop kickoff now say so up front: an answered rerun against a shell you hold unlocked is your run — skip the claim, redo STG-2 with the new set, lock. `/bid b378` also resumes (open_shadow is idempotent per reference).
- Help guide `let-the-robots-shadow-a-bid.md` amber-icon bullet updated. New render smoke `RobotNeedsSheet.render.test.tsx`.

## Notes for the next session

- The batch operator prompt (`shadow-operator.md`) still launches agents on `/bid next` only; the skill's new rule makes each agent check answered reruns first, so no routine change is needed, but a bid with an answered rerun and no agent running that hour waits for the next batch like everything else.
- If reruns pile up, the dispatcher could learn to hand back an unlocked shell whose plans ask was answered (`next_shadow` reading `twin_questions`), which would make the stamp sufficient on its own. Not built; watch the Queue lens first.
