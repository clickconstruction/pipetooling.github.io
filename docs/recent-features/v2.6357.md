# v2.6357 — A clean build no longer waits in line for the SQL beds check (2026-11-02)

`sql-beds`, the job at the bottom of `.github/workflows/sql-beds.yml`, is the one check branch protection requires of the beds. It ran on every build with `if: always()` and only read two results, so a job with a median of 3 seconds queued behind the whole runner backlog. It now runs only to fail. With every result good it is skipped, which takes no runner, and GitHub counts `skipped` as a successful required check.

- **The condition is a positive test:** `always() && !(changes success && (bed success || (bed skipped && (beds == 'false' || draft))))`. `always()` is what holds a red bed out. Without a status function GitHub adds `success()`, a failed bed then skips the job, and a skip passes. `!cancelled()` would pass a cancelled run the same way, and is the alternative GitHub's docs recommend, so a comment on the job says why not.
- **Two states that passed now fail:** a bed that was wanted but skipped, and a `changes` job that succeeded with no `beds` answer.
- **A failed diff fails closed:** `changes` read `git diff` through process substitution, so a diff that failed (a base not in the checkout) said `beds=false` and exited 0. It now reads the diff into a variable first. Proved in a local repo, never seen in a real run.
- **The header's false sentence is gone.** It said the queue's build always runs the beds, but 135 of 167 queue builds since 11-01 ran none. An entry is diffed from the group ahead of it (`merge_group.base_sha`), so an entry with no bed's file behind a migration runs none and leans on that entry's beds. That is sound only while the queue's "Only merge non-failing pull requests" stays on, and the header now says so.

## What the wait cost

- In the queue: the gate was the last required thing to finish on 16 of 98 landings from 11-01 to 11-02, adding 91 minutes, 54 of them on #6771's last build.
- On pull requests, 22:00 to 10:30Z: last on 31 of 127 runs, adding 643 minutes. PRs with no beds waited up to 84 minutes for it, finishing up to 70 minutes after `checks`, and an armed PR enters the queue only then.

## Proof

Ten `workflow_dispatch` runs of the candidate on throwaway branches, with a tiny bed list:

| Scenario | `bed` | Gate |
| --- | --- | --- |
| Every bed green | success | skipped |
| A bed fails | failure | failure |
| A bed hits `timeout-minutes` | cancelled | failure |
| Run cancelled, beds running | cancelled | failure |
| Run cancelled, legs held by `max-parallel` | cancelled | failure |
| Run cancelled during `changes` | cancelled | failure |
| `changes` fails | skipped | failure |
| Red, then `gh run rerun --failed` goes green | failure, then success | failure, then skipped |
| `beds` output empty | skipped | failure |
| Bed skipped although wanted | skipped | failure |

On main's real branch protection, a never-armed PR (#6806, `checks` stubbed, closed unmerged) read `CLEAN` with the gate skipped and `BLOCKED` with a red bed, and a re-run that went green cleared the red back to `CLEAN`.

On the real queue, a failed `sql-beds` with `checks` green has already removed entries as `failed_checks`, within 6 seconds on #6760 and #5193 and 25 on #5494. Since the check became required, none of the 12 queue builds with a red gate reached main. A failed gate is the path that is not changing.

In a real merge queue, on a throwaway public repo holding main's protection, main's queue settings and this workflow (`clickconstruction/merge-queue-gate-proof`, archived; `checks` is a stub and a hung bed times out in one minute):

| Case | Gate | Queue |
| --- | --- | --- |
| Docs only, no beds | skipped | landed 24 seconds later |
| Beds ran and passed | skipped | landed 5 seconds later |
| A bed red | failure | removed as `failed_checks` 8 seconds later |
| A bed timed out | failure | removed as `failed_checks` 16 seconds later |
| The run cancelled with a bed running | failure | removed as `failed_checks` 27 seconds later |
| A docs entry behind a slow red one | skipped | stayed queued for 24 minutes, was rebuilt without the red one and landed |
| A bed red once, re-run within seconds | failure, then skipped | kept its place at the head and landed 28 seconds after the skip |

None of the red cases reached main. An entry at the head is removed within seconds of a red gate, so a re-run there keeps its place only if it beats that.

## What this does not fix

The gate only waited in a long line. From 04:00 to 10:15Z on 11-02, of 6,675 job-minutes, PR bed runs took 41%, queue groups already dead 28%, PR `checks` 22% and builds that landed 7%. The gate took 4 job-minutes. A model of 30 PRs landing on a busy night moves from 8.2 to 8.0 hours on this change alone. The same day v2.6372 ran the beds eight at a time on each runner and the queue's build concurrency went from 3 to 6. Together those reach about 2.8 hours in that model, and the gate's wait hardly shows until a line forms again. The Team plan's 60 jobs would do about what v2.6372 does. Nothing landed from about 05:00Z to 08:00Z that night because date-dependent tests failed every tree, which no workflow change helps.
