# v2.3642 — Contracts: terms as two levers — the payment line per job, the standard terms editable (2026-09-20)

PR 4 of [`to-dos/contract-paper-lane/README.md`](../../to-dos/contract-paper-lane/README.md). The two questions that sized it were answered by the owner on 2026-09-20: Taunya's *"ability to update terms"* meant **both** the payment line and the legal paragraphs, and **any office staff** may edit the standard terms (the Book's existing rule — no permission change). One seed migration; no edge function.

## The problem it closes

Two things on the sweep were called terms. The **payment line** (`payment_terms_key`: half down · on completion · progress · custom) was per job but editable only in the full editor. The **legal paragraphs** were a dropdown with one option: prod had 0 customer-audience Contract Book documents, so the wording was `DEFAULT_JOB_CONTRACT_TERMS_PLAIN`, a source constant nobody in the office could change. The first-pass idea — an *Edit these terms* link — was rejected in the mock-up because it walked someone fixing one sentence for one homeowner into a shared document with no warning.

## Lever 1 — This job

The sweep pane's edit grid gains a **This job** heading and a **Payment** row: the four `PAYMENT_TERMS_PRESETS` as pressed-state buttons, and a sentence box when *Custom…* is on. `paneEdit` carries `paymentKey` / `paymentText`; `editedFields` folds them in; the existing debounced draft save and the preview iframe do the rest. Locked, like scope and amount, once the agreement is sent.

## Lever 2 — Standard terms

- **The seed** — [`20260920190000_seed_customer_standard_terms.sql`](../migrations/20260920190000_seed_customer_standard_terms.md): the constant, verbatim, as **Service agreement** (customer, plain, v. 2026-09-20) under a **Customer agreements** packet; skipped entirely when any customer document already exists. `jobContractTermsSeed.test.ts` holds the SQL text to the constant. The constant stays as the fallback.
- **The row** — *Standard terms · Service agreement · v. Sep 20 · Edit · the same wording on every agreement — an edit reaches all N here*. A picker appears only when the Book holds more than one customer document. With none (before the push) it reads *Built-in service agreement terms* and offers no Edit.
- **The door** — [`StandardTermsEditModal.tsx`](../../src/components/jobs/StandardTermsEditModal.tsx) on `ResponsiveModalShell`: an amber note first (`standardTermsReachLine` — every agreement sent from now on, the N still waiting included; sent and signed ones keep theirs; *to change one job only use This job*), the name, the wording. It saves through **`update_contract_book_entry`** — the Book's own write, so the name checks, the role gate and the version column are one rule — with today (company calendar) as the new `book_version_date`, passing the document's existing tags and canonical link through untouched. `standardTermsSaveBlocker` refuses a blank name, blank terms or no change.
- **After a save** the sweep re-reads its terms from the saved document and marks the selected job's **unsent draft** dirty so it is re-saved with the new wording (a draft row stores its body; sent rows are frozen by design). Other jobs' drafts pick the wording up the next time they are edited — prod had no unsent drafts on 2026-09-20.
- **The Contract window** shows the same row name and an *Edit standard terms* link under the picker, replacing the hint that only rendered when the Book had no customer documents (the to-do's "drop the zero-templates-only hint").

Not run live: the edit door needs the seeded row — after the push.
