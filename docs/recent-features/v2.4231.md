# v2.4231 — Robots: run the estimator from a Claude Code session, where it reads the plans itself (2026-09-30)

Grace ran the robot estimator from a Claude Desktop chat on 2026-09-30 and hit two walls: the robot could not read the plans (it claimed b500 and asked her to drag the PDF in), and Claude asked her to approve tool after tool. The same kickoff pasted into a Code session worked through the connector — but the session first asked what she wanted done with the pasted document. This PR makes Claude Code the first way to run a batch and gives it its own kickoff. No migration. Edge: `twin-setup` v1.1.0 (redeploy) and `twin-mcp` (redeploy for the docs bundle only — no verb changed).

## What was measured

- **A chat can open neither form `get_plan_pages` returns.** The staged page links come back in a tool result, and a chat does not fetch a link a tool returned; the inline `application/pdf` resources are rejected by the chat client. v2.3230 shipped both forms unverified ("whether a given Claude Desktop build reads a page PDF from the URL or from the embedded resource" was left for the first run) — the first run says neither.
- **Claude Code reads both.** `get_plan_pages(b411, '1-2', embed: true)` from a Code session: each embedded page was saved to a file by the harness and read as text plus the drawing; the staged link downloaded with `curl -fsS -o`. `pdftoppm` and `sips` both rendered a closer look from the page file.
- **The Claude app's Code tab loads the connector Desktop's config holds** (`claude_desktop_config.json` → `twin-mcp` through `mcp-remote`), with no `.mcp.json` variable set — so *Set up on this Mac* already serves Code; nothing in the setup had to change to connect it.
- **About 25 of the connector's 48 tools are touched on a first batch**, and a chat asks once per tool. The old kickoff told the person to choose *Allow for this chat*, which repeats on every batch.

## What changed

- **`docs/twins/kickoffs/code-operator.md`** (new) — the Code kickoff. It is the robot's instructions only (no setup steps for a person), and it opens in the operator's voice — *Run this now … pasting this document is my instruction to you* — so a session runs it instead of asking. Differences from the chat kickoff:
  - **What this session may use**: the connector's tools, and the shell and file reader for plan sheets only. No `dev-mcp`, no database connector, no sign-in to the app, no repository files — any of them can show a human's number. Nothing is written into a checkout; plan files stay in the session's temp folder.
  - **STG-2**: the robot fetches the set itself — `embed: true` two or three pages at a time, a heavy page by its staged link with exactly `curl -fsS -o <file> <url>`, a rendered closer look when symbols are small. An unreadable set is a plans ask and a parked shell; it never waits for a person to attach.
  - **Resume check**: every session on the key is the same robot, so an open shell whose ledger moved in the last 60 minutes is another session's and is left alone (the chat kickoff gets the same sentence). Two sessions at once is the ceiling.
- **Console** ([`BidsRobotConsoleTab`](../../src/components/bids/BidsRobotConsoleTab.tsx)) — *Run the robots* leads with **From Claude Code · reads the plans itself**: Set up on this Mac, **Copy Code kickoff**, and the hourly routine's handoff prompt. **From a Claude chat · when Code is not at hand** follows with **Copy chat kickoff** (was *Copy Desktop kickoff*) and says what a chat costs. The pricing robot's column is unchanged.
- **Setup** — `twin-setup` hands the bid robot the Code kickoff and answers `kickoff_for: 'code' | 'chat'`; the command ([`buildDesktopSetupCommandFromCode`](../../src/lib/bids/desktopKickoff.ts)) tells the person where to paste from that field, and keeps the chat wording against a `twin-setup` that has not been redeployed. The dialog ([`TwinSetupDialog`](../../src/components/bids/TwinSetupDialog.tsx)) says the setup covers the Code tab and chats, that Claude quitting stops whatever is running in it, and sends the bid robot's paste to a Code session.
- **Chat kickoff** (`desktop-operator.md`) — points a Mac with Code at the Code kickoff, tells the person to expect to attach plans, and says *Always allow*.
- **Generator** — `scripts/build-twin-mcp-briefs.mjs` bundles `CODE_KICKOFF` into `_shared/twinKickoffs.ts`.
- Docs amended where they held the old fact: the guide *run the robot estimator from the Claude app* (same slug), `twins/HANDOFF.md`, `twins/TWIN_HARNESS.md`, `twins/APP_DIRECTORY.md`, `GLOSSARY.md` → Console, `BIDS_SYSTEM.md`, `EDGE_FUNCTIONS.md` → twin-setup and `get_plan_pages`.

## Not built

- **The setup command does not touch Claude Code's permission settings.** Adding allow rules for the connector to `~/.claude/settings.json` from the command was drafted and stopped: Claude Code's own safety check refused to let an agent write a change to its permissions, and that is the operator's call, not a side effect of a setup script. In auto mode a Code session does not stop for the robot's calls; in the default mode it asks once per tool.
- **Plans as pictures for a chat** — `get_plan_pages` returning rendered images, which chats do accept. It needs a PDF renderer inside the edge function (v2.3230's note still stands).
- **The pricing robot** keeps its chat kickoff. Its `get_quote_documents` embeds PDFs the same way, so a chat has the same trouble there; not measured in this PR.
- The `/bid` skill and the hourly routine are untouched: they use the key file and `plan-fetch`.
