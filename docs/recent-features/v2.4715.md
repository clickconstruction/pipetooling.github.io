# v2.4715 — AIA G702-G703: a deleted application stays in the history (2026-10-06)

Third of the three PRs behind the owner's *build C* ([v2.4710](v2.4710.md) opened the window on the job's history, [v2.4714](v2.4714.md) named a change after the workbook went out). The mock-up's critique: Delete removed the row, and the delete-archive trigger that keeps a job's other rows for 90 days was not on `job_pay_applications`, so a history could silently lose its first entry. Migration `20261006235000_job_pay_applications_deleted.sql` ([doc](../migrations/20261006235000_job_pay_applications_deleted.md)); no edge function.

## The change

- **Soft delete.** `job_pay_applications.deleted_at` / `deleted_by`, stamped on the server by the replaced `job_pay_applications_stamp()` (a change to `deleted_at` stamps the delete or clears it on a restore and leaves the saved stamps alone, so the history does not read a delete as *saved again*). The unique rule moves to a partial index over the live rows, so a deleted application 1 does not block a new application 1, and a restore that would collide is refused.
- **IO** (`aiaPayApplicationsIo.ts`): `loadPayApplications` reads the live rows (`deleted_at IS NULL`); `loadDeletedPayApplications` the marked ones with the deleter's name; `deletePayApplication` marks the row, and removes it as before on a database without the column (PGRST204).
- **History** (`payApplicationHistory(apps, sent, deleted)`): the deleted applications follow the live ones in number order as lines with `deleted: true`, their workbooks still attached by `source_id`; the standing and the next number come from the live ones. `payApplicationDeletedWords`: *Deleted Sep 3 by Robert*.
- **Window and Documents tab**: a quiet muted line / row — number, name, period, *deleted*, payment due, who and when, the workbooks as file doors — with no Open. The Delete confirm says the application stays in the history.

## Not built

- **Restore.** The database allows it (clear `deleted_at`; the index refuses a collision) and the SQL bed covers it, but the window has no *Put it back* yet.

## The bed caught the runner

`scripts/pgtest-pay-applications.sh` re-applied the table's birth file as its "a second run changes nothing" check. That file's `CREATE OR REPLACE` of `job_pay_applications_stamp()` put the v2.4490 trigger back, so case 10's first assertion failed against the old trigger — the hazard `docs/MIGRATIONS.md` warns of, met in a test bed. The runner now re-applies the table's newest migration instead. Prod is not affected: `db push` never re-runs an applied file.
