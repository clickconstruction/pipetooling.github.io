# v2.4980 — My Time day editor: Escape acts on the day on screen (2026-10-08)

Client only. No migration, no edge function. Found chasing the render test's flake, *a clean day closes at once, from Close, the backdrop or Escape*, which failed with *expected spy to be called 3 times, but got 2 times*. It dropped #5031 from the merge queue and failed #5033's CI.

## What was wrong

The editor hears Escape through a capture-phase listener on the window. It was bound in a `useEffect` that depended on `closeTopmostSubFlow`, `discardConfirmOpen`, `requestDiscard` and `saving`. So every render that changed one of them bound it again, with that render's closures.

React runs a `useEffect` right away only after a render that a key or a click caused. The day's load renders from a promise, so its effects run later. Until they run, the window still holds the listener from the render before, and an Escape in that gap acts on the old state.

The test showed it under load, failing 1 run in 24, then 3 in 30, then 1 in 36. An instrumented copy logged the run:

- **The last bind** came 5.7 ms after mount, before the day loaded. That render still counted the day as dirty.
- **After the load** the footer read *Close* and there was no Save button.
- **Escape** opened *Discard unsaved changes?*, and the third close never came.
- **In the passing runs** a fresh bind landed after the load, before the press.

A person could hit it too, by pressing Escape in the moment after a day opens.

## What changed

- **One listener, bound once.** A `useLayoutEffect` with no dependencies adds it, and it calls `escapeKeyRef.current`.
- **The handler is written after every render.** A second layout effect stores the same handler as before in `escapeKeyRef.current`: `saving`, then `discardConfirmOpen`, then `closeTopmostSubFlow`, then `requestDiscard`. A layout effect runs in the same task as the render's commit, so no key can arrive between a render and its handler.
- `docs/MY_TIME_DAY_EDITOR_MODAL_ARCHITECTURE.md` (quirk 14, the z-index ladder) says so.

## #5025 and #5042 read it as a lost press

Both took the flake for a press made before the listener was bound. #5025 waited for the third close. #5042, merged as a stopgap so the queue stopped failing, pressed Escape inside `waitFor` until the close came.

The listener was bound, and it did answer: the instrumented run saw `defaultPrevented` set and the Discard question open. Waiting could not bring the close. Pressing again made the test pass with the bug in place. Press 1 opened the stale Discard question, press 2 closed it, and press 3 closed the window. The test now presses once and checks at once.

## Is this the best we can do?

- **A ref, not `useEffectEvent`.** React 18.3 has no `useEffectEvent`. A ref written in a layout effect is the same idea.
- **A layout effect, not a plain effect, for the bind too.** The first Escape after the editor mounts is heard as well.
- **The order of the closes is unchanged.** The sub-dialogs hear Escape with `onKeyDown` on their own elements. That runs after the window's capture listener whenever either was bound.

## Tests
