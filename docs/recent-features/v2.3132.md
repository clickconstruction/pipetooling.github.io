# v2.3132 — Stage Plan PR 5: the GC card in the company's voice (2026-09-08)

Fifth PR of the train in [`to-dos/stage-plan/`](../../to-dos/stage-plan/README.md). The owner's first rule: "The GC should never see that we have offered any of our work to a sub and should always think we're the one doing it." The v2.2933 card printed the sub's first name on three rows and an "Offered to a sub" chip; this PR replaces it. Client + two edge functions; no migration.

## One kernel, both sides

- The Stage Plan kernel moved to [`supabase/functions/_shared/stagePlan.ts`](../../supabase/functions/_shared/stagePlan.ts) (dependency-free: its two date helpers are inlined, the zone comes from `_shared/appTimeZone.ts`); [`src/lib/jobs/stagePlan.ts`](../../src/lib/jobs/stagePlan.ts) re-exports it, so the Bill tab, the Edit drawer and the portal run the same rules and the same 19 tests. `GcStep` gains `fixtureId`.
- [`_shared/gcStages.ts`](../../supabase/functions/_shared/gcStages.ts) rewritten: `loadGcStageInputs(admin, jobIds)` (six reads — fixtures with `stage_kind` / `shared_with_gc`, windows, orders **without** `display_name`, sheets with `progress_at` / `stage_changed_at`, invoices, payments — and a `byJob` slicer) and `gcPortalStages` → `{ view, askWindowId, askFixtureId }`. `buildGcStageEntries` / `gcStageLine` and the bundle logic are gone. Tests in `src/lib/subs/gcStages.test.ts` (4): the sequence, the ask window, *never a name / "offered" / money*.

## customer-portal

`stages[]` is now `{ jobId, jobLabel, jobAddress, view, askWindowId, askWindow, entries: [] }` per sharing job with something to show; `entries` stays empty one release so a stale client prints nothing. The sample GC (`?t=sample-gc`, Settings → What customers see) carries the mock-up's job through the same kernel ([`customerSampleFixtures.ts`](../../supabase/functions/_shared/customerSampleFixtures.ts) → `sampleGcStages`): Rough-in passed and paid, Top-out on site at 50%, Trim & final planned with the ask, Final inspection after it, a done change order under Also, a hidden one and a permit line that never show.

## submit-portal-request

A `stage_window` ask must land on the plan's **next** step — the function loads the job's inputs and checks `askWindowId` — else 400 *"Only the next stage can be moved. Call the office about the others."* The `offered_to_gc` requirement is gone (the eye is the rule).

## The page

- [`CustomerPortal.tsx`](../../src/pages/CustomerPortal.tsx) draws [`PortalStagesCard`](../../src/components/portal/PortalStagesCard.tsx) (PR 4's component) per job with `askSlot` → [`PortalStageAsk`](../../src/components/portal/PortalStageAsk.tsx), which now takes `{ windowId, window, asked }`, reads **Need other dates?**, and drops the "the sub is picking new days" line — the card's own next-step line says *we're picking new days inside the window*.
- [`portalPayload.ts`](../../src/lib/portal/portalPayload.ts): `PortalJobStages` = the view + ask window; the old `PortalStageEntry` shape (with `who`) is gone; a job with nothing to show or an old-shape payload parses to nothing (test: the old shape's name never survives).

## Docs

`docs/EDGE_FUNCTIONS.md` customer-portal + submit-portal-request sections. Guide *show a GC the stages you plan* (PR 4) already describes the card.

## Deploy

After merge: `bash scripts/deploy-functions.sh customer-portal submit-portal-request`, then `npm run check:edge-drift`. Client first (deploy.yml), then the functions — a new client against the old function shows no Stages card (old shape parses to nothing); the old client against the new function prints nothing (`entries: []`). Live check: `/portal?t=sample-gc` shows the card; a real GC link on a shared job shows no name; an ask from the next stage lands in dispatch, one from any other stage is refused.
