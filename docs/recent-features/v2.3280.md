# v2.3280 — "Their Word" PR 1: payment promises as an append-only record, and the one rule for kept / late / broken (2026-09-11)

Migration `20260911051414_job_payment_promises.sql` (see [`docs/migrations/20260911051414_job_payment_promises.md`](../migrations/20260911051414_job_payment_promises.md)); no edge function. Apply order: client first (the client only reads the new RPCs in PR 3), then `supabase db push`.

## Why

Owner, 2026-09-11, after the Done Right cheque-pickup analysis: the metric worth having is "when a customer says they have the money and will pay by a date, do they?" Prod showed the capture surfaces from August all empty — `job_promised_pay_dates` had one row ever (2026-08-21), `job_payment_chase_touches` and `gc_statement_round_marks` none — and the one table that does exist keeps ONE promise per job and overwrites it, so a re-promise erased the broken one. Lean four-PR plan (mock-up: https://claude.ai/code/artifact/b14f4981-2d20-445e-b84e-f1024f30d23c): 1 events + rule + guide (this), 2 capture where it's free, 3 reliability on the Billed row, 4 customer terms.

## What shipped

- **`job_payment_promises`** — append-only: `job_id`, `customer_id` (the payer, `COALESCE(gc_customer_id, customer_id)` snapshotted at promise time), `promised_date`, `said_by` (free text), `heard_by` (users; NULL = the customer named the date themselves), `channel` (phone · text · email · in_person · portal · backfill), `source` (office · customer), `note`, `voided_at/by`. The only update the table accepts is a void.
- **Legacy path keeps working and now logs:** `job_promised_pay_dates_log_promise_trg` (AFTER INSERT OR UPDATE on `job_promised_pay_dates`) writes an event for every `set_job_promised_pay_date` call — the modal's link and call mode's "promised" outcome — skipping same-date re-stamps. Clearing (NULL) deletes the latest-table row and leaves the event: a cleared promise was still made. The single pre-existing row is backfilled.
- **RPCs** (same gates as the promised-dates pair, now named: `can_write_payment_promises()` = dev / master / assistant-like, `can_read_payment_promises()` = + primary): `add_job_payment_promise(job, date, said_by, channel, note)` writes the event then upserts the latest table under a transaction-local flag (`app.promise_event_written`) so the trigger stays quiet — PR 2's "They said…" and backfill prompt call this; `void_job_payment_promise(id)`; `list_job_payment_promises()` (live events newest first, marker names joined); `list_payment_promise_records()` (per live promise: $ billed on the job as of the promise + every dated payment on the job — the kernel's inputs).
- **Kernel [`src/lib/jobs/paymentPromises.ts`](../../src/lib/jobs/paymentPromises.ts)** (+19 tests): `classifyPromises(records, todayYmd)` applies the one rule — **kept** = the job's billed-at-promise total reached a $1-tolerance zero balance by `promised + 3 business days` (`KEPT_GRACE_BUSINESS_DAYS`, weekends skipped, holidays not modeled); **late** = paid off after that, `daysLate` = paid-off day − promised day; **broken** = unpaid and either a newer promise exists on the same job (`rePromised`) or the date is `BROKEN_AFTER_DAYS` (= the chase loop's 7) behind today; **open** otherwise. Payments before the promise count toward the balance; a partial is never kept; a paid-off promise is judged by the money (late, not broken) even if it was re-promised. `buildCustomerPromiseRecords` rolls outcomes per customer (decided / kept / late / broken / open / keptRate / `usualSlipDays` = median slip over paid-off promises / rePromised / openBroken); `formatKeptRecord` → "keeps 3 of 7" / "kept 6 of 6"; `formatUsualSlip` → "slips ~9d". Parsers `parsePaymentPromisesRpc` / `parsePromiseRecordsRpc` are defensive like the chase ones.
- **Help guide** `know-whether-a-customer-keeps-their-word.md` (Billing & Money): what counts as a promise, the one rule with a worked example, who can do what, and a "where this shows up" section that the next PRs extend.
- Nothing on screen changes in this PR. The chip, the modal, call mode and the forecast read `job_promised_pay_dates` exactly as before.

## Verified

Migration replayed on a scratch Postgres 16 loaded from a `supabase db dump -s public` of prod (auth stubs): legacy mark → 1 event with the right payer/heard_by; same-date re-stamp → still 1; new date → 2; `add_job_payment_promise` → 3 events (not 4) and the latest table updated; void → 2 live of 3; clear → 0 latest rows, 3 events; a `helpers` account gets NULL from both lists and "Not allowed" from the writer.
