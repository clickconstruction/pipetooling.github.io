# v2.7346 — Job, task and report photos: a photo whose first send was cut off lands on the next try (punch list #338) (2026-11-15)

The bid photo fix of v2.7133, made in the three other photo sends that had the same upload. Taunya picked Build for the card on 2026-11-15. No migration and no edge function change.

## What was wrong

- `sendJobPhotoNote`, `sendTaskPhoto` and `sendReportPhoto` uploaded the shot with `upsert: true`. The `job-photo-notes`, `task-photos` and `report-photos` buckets have insert, select and delete policies and no update policy (migrations `20261102171500_job_photo_notes`, `20261106230000_task_cards_progress`, `20261029220000_report_photos`). An upsert onto an object that is already there takes the update path, and the project refuses it, as it was read to do for `bid-photos` on 2026-11-13.
- When it bites: the outbox's replay sends a kept shot again only after a try failed. When that try's upload had landed and its answer was lost, every later try was refused. `sendKeptPhotos` counts a refusal as a failed try, so the press waited, the bar turned red the next morning, and the photo never landed although its bytes were in the bucket. A tile's **Retry** met the same refusal.

## What changed

- Each of the three sends (`src/lib/photos/jobPhotoNotesIo.ts`, `taskPhotosIo.ts`, `reportPhotosIo.ts`) uploads with `upsert: false`. An upload refused because its object is already there (`bytesAlreadyThere`, `src/lib/photos/shotTiles.ts`) goes on to the row, which was already an upsert on the shot's id. The path carries the shot's own id, minted on the phone, so what is there is this shot. A first send is the same insert as before.
- A task photo sent with no kept id mints a new id each try, so its path is new each try and it never met the refusal. The kept shot of v2.6628 sends under its own id, and that is the one this fixes.

## Not changed

The counter ticket pages (`sendTicketPage`, `src/lib/tickets/ticketsIo.ts`) still upload as an upsert. Their bucket has an update policy for the file's owner, so the resend is likely allowed. Not walked.

The first two of each fail on the old send.

Not walked live before the merge: the dev server only reads, and the walk drops an answer on a real upload. The card stays as one line until a walk on the live site lands a ZZ Test photo once after a dropped answer.
