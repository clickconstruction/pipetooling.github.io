# v2.7289 — customerLang off portalI18n: the dev seat and quo-send stop uploading the portal translations (punch list #359, PR 2) (2026-11-14)

Infra only: no screen and no running code changes. The second cut on the #359 card, the first of the sliver chains in dev-mcp.

## Why

`lib/messages/customerLang.ts` imported `PORTAL_SPANISH_ON` and `type PortalLang` from `lib/gc/portalI18n.ts`, the portal's translations, 122 KB; `quickReplies/language.ts`, `quo/techSend.ts`, `bio/bio.ts` and `jobModeText.ts` imported the type alone. Deno erases the type imports, but `supabase functions deploy` uploads every file an import names, so dev-mcp carried the translations through `_shared/devMcpBill.ts` → `customerLang` for one constant and one type, and quo-send carried them five ways for the type. The portals say the schedule in two languages and keep the translations whatever this PR does.

## What changed

- **`src/lib/gc/portalLang.ts`**, new: `PortalLang`, `PORTAL_SPANISH_ON` and `portalShownLang`, moved word for word from `portalI18n.ts` with their comments. The gate and the function that reads it travel together, so the three are one file.
- **`src/lib/gc/portalI18n.ts`** imports the type from it and re-exports all three, so the forty-odd files in the app that import them from `portalI18n` import as before; nothing outside `src/lib` changed.
- **The five kernels** that took the type or the gate alone (`customerLang.ts`, `quickReplies/language.ts`, `quo/techSend.ts`, `bio/bio.ts`, `jobModeText.ts`) import from `portalLang`. `gc/bids.ts`, `gc/portal.ts` and the schedule kernels take `pt` and `pDate` too, so they keep importing `portalI18n`.
- **`QuickRepliesSpanish.render.test.tsx`** mocks the gate on `portalLang` now: it sets `PORTAL_SPANISH_ON` by a getter on the module `customerLang` reads it from, and that module moved.
- **The generator** carries `lib/gc/portalLang.ts` as an entry that exports nothing (the copy reached it through `portalI18n`'s re-export in any case; the entry says why the file is there). The copy regenerated: `portalLang.ts` in, `portalI18n.ts`, `customerLang.ts`, `language.ts`, `techSend.ts`, `bio.ts`, `jobModeText.ts` with their new import lines.
- **`edgeUploadGraph.test.ts`** holds it: dev-mcp and quo-send upload `portalLang.ts` and not `portalI18n.ts`; customer-portal uploads both, the switch through the file that re-exports it.

## Is this the best we can do?

- `portalShownLang` could have stayed in `portalI18n`; it reads the gate and nothing else, so it went with the gate. A reader that needs the shown language alone (`FileLinkPage`, `PortalGcPage`) still gets it from `portalI18n`.
- `customerLang.ts` still imports `quickReplies/language.ts` for `wordsFor`, a 20-line file: nothing to cut there.
- The next sliver chains in dev-mcp are `quo/textsSwitch.ts` → `quo/send.ts` for `type SendPurpose` (84 KB) and `overheadPartsAccountingBuckets.ts` → `overheadOfficePartsReads.ts` for `type OverheadPartsDetailLine` (74 KB), PRs 3 and 4 on the card.
