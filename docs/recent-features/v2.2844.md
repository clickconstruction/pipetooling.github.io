# v2.2844 — Superintendents see only the work orders on their own jobs (2026-09-05)

Journey map Phase 4, Tier-1 #4(b) — follow-up to v2.2836 (PR #2575, `20260905100000_project_access_assigned_superintendents`), which closed the project-level adoption leak. Drift sweep `_DRIFT-2` Tier-1 row #4 / Flag 1: `can_access_sub_work_order` (`20260904211244:70-105`, superseded by `20260905050035:73-95`) granted every `superintendent` **by role literal** SELECT on sheet- and job-anchored `step_commitments` rows, and `sc_update` (`:126,:133`) routes through the same helper — so every superintendent could read and edit every work order in the company that was not tied to a workflow step.

## Migration — `20260905120000_sub_work_orders_superintendent_scope.sql`

- `CREATE OR REPLACE FUNCTION public.can_access_sub_work_order(uuid, uuid, uuid)`: the sheet/job branch keeps the office list (`dev`, `master_technician`, `assistant`, `controller`, `estimator`) and replaces the bare `superintendent` literal with `u.role = 'superintendent' AND superintendent_can_access_sub_work_order(p_labor_job_id, p_job_id)`. Step-anchored rows still go through `can_access_project_via_step`.
- New `public.superintendent_can_access_sub_work_order(p_labor_job_id uuid, p_job_id uuid)` (`SECURITY DEFINER`, `row_security = off`, no role check of its own): job-anchored → **`superintendent_report_job_anchor_allowed(job_id)`** (the baseline reports-RLS superintendent job branch — strict project assignment via the 1-arg `can_access_project_row` OR `jobs_ledger_team_members`; the same anchor v2.2647's `superintendent_can_touch_job_thread` reuses); sheet-anchored without a `job_id` → the sheet's `project_id` under the strict `can_access_project_row`, or the `jobs_ledger` row whose `hcp_number` matches the sheet's `job_number` under the same job anchor.
- No policy text changes: `sc_select` / `sc_insert` / `sc_update` / `sc_delete` all call the helper, so tightening it scopes every verb (UPDATE included). Sub own-row branches untouched. Idempotent, additive-safe, two `CREATE OR REPLACE` statements. Full before/after, reader table, verify recipe and rollback in [`docs/migrations/20260905120000_sub_work_orders_superintendent_scope.md`](../migrations/20260905120000_sub_work_orders_superintendent_scope.md).

## Why this rule

The v2.2785 comment argued the sheet/job branch from "the Sub Labor tab audience", but that audience is the office set: the `people_labor_jobs` SELECT policy is dev/master_technician/assistant/estimator only (a superintendent cannot read a sheet), and `Jobs.tsx` hides the Work Orders tab from superintendents (`showSuperintendentExtraTabs = !isSuperintendent`). What a superintendent legitimately reaches is the **job window** (`JobFormEditFactRows.tsx:545` → `JobWorkOrderStrip` → `useJobWorkOrderCoverage`) for jobs they run, and the Dashboard unpriced-drafts count (`useUnpricedWorkOrders.ts`) — both now limited to their jobs. `/people` is not in `SUPERINTENDENT_PATHS`, so the Person Desk / Subs-row readers never ran for them; the sub portal edge functions read as service role and are unaffected.
