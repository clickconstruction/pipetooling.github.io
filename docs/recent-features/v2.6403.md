# v2.6403 — Find a file: a file deep inside a plan set now lands on its bid or job (2026-11-02)

Punch list #240, after the index check's first live run (v2.6364). It found most of the Shared Drive had no row, `--fill` gave them rows, and reading where those rows sat showed two faults, both fixed here, with the card's corrected counts. No migration; `drive-link` and the other functions that bundle what changed redeployed.

- **The walk climbs farther.** `WALK_MAX` goes from 8 to 16 in `_shared/fileIndexKernel.ts`. A file more than eight folders below its home ran out of climb, so its row carried no job or bid and its path started partway down. One plan export sat that deep, and rows from the same export within eight folders already sat on its bid. The limit stays, since a loop in the folders must not walk forever. `walkUp` caches each folder per request, so a deep file costs a few more Drive reads once. `src/lib/documents/fileIndexWalk.test.ts` holds a home nine folders up and the limit.
- **The walk lists as deep as it climbs.** `filesUnder` in `_shared/fileIndex.ts`, the index's lister, goes `WALK_MAX` folders down where it went three (the `seen` set still stops a loop, and two thousand files still caps a home). Inside the Shared Drive the check would catch a file past the old three, but a bid's folder outside it has no other way in. A home's listing costs one Drive list a folder, per round.
- **A row's home again.** `drive-link` `{ action: 'index_home', driveFileIds }`, up to 40 a call: each file's row is walked up from its folders as they stand and takes the job or bid, the folder kind and the path (`_shared/fileIndexRehome.ts`), with nothing read out of the file and nothing written to Drive → `{ homed, none, unanswered, failed }`. A pass skips a row that is current, so without this a row keeps the home it was first given, which also covers a folder linked to a job after its files were indexed. A dev's door (403 for the other roles). `npx vite-node scripts/file-index-check.ts --rehome [--pause 500]` reads every row on no job or bid, a thousand at a time, and walks them forty a call, counts only.
- **The fill outlives its sign-in.** `scripts/file-index-check.ts` signs in without refreshing, and a sign-in lasted about 70 minutes, so the first fill stopped partway with *Sign in first.* A 401 now signs in again, once a call. The check between rounds is asked again after a lost signal, the rate limit or the platform's own failure (`askAgainAfter`), never after the function's refusal in words, so one lost call does not end a fill of hundreds of files.
- **The card** holds the walk's and the fill's counts by reason, says what the walk could not reach and why, and records the owner's choice for new files: the sweep plus a reconcile step. It corrects two things the first version said. The sweep lists by Drive's modified time, and a file moved into the drive keeps its old one, so a file dropped in by hand is not always found within minutes. And a bid's folder outside the Shared Drive has rows in the index even though Drive's own search does not reach it.
- **Tests**: `fileIndexWalk.test.ts`; `fileIndexCheckKernel.test.ts` takes `askAgainAfter` and the rehome tally and words; `driveLink.test.ts` takes the new ask and its cap.
