# v2.3743 — Day book: the snapshot records each count the moment it resolves (2026-09-22)

A fix to v2.3736 (decision 6 of [`to-dos/day-book`](../../to-dos/day-book/README.md)), found on the first live row.

## What was wrong

The Dashboard's recorder marked the day as recorded after its first successful write. The Needs You card's counts resolve at different moments — the contract nudge lands before the bank-deposit count — so the first live row on prod carried `contracts: 110` and no `deposits` row: by the time the deposit count resolved, the day was already stamped and skipped.

## The change

- **[`dayBookQueueRecorder.ts`](../../src/lib/people/dayBookQueueRecorder.ts)** — the device remembers the *kinds* recorded today (`{ day, kinds }`, a new storage key), `planQueueRecord` returns only the resolved kinds not yet recorded, and `writeRecordedToday` merges the kinds just written. A new day starts over. Tests: a later count still lands; a fully recorded day writes nothing; the merge and the new-day reset; a throwing or corrupt store.
- **`DashboardPinnedQuickRow`** — the effect writes the kinds it sent; the RPC's upsert (per `(day, kind)`) already makes repeated writes harmless.

## Verified

- `dayBookQueueRecorder` (3), `releaseNotes`; typecheck, eslint.
- Live on the worktree dev server as the dev, after the fix: a reload of the Dashboard added today's `deposits` row beside the `contracts` row already there (read back through the app's own session).
