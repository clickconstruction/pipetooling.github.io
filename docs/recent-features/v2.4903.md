# v2.4903 — Labor: each set-aside row is kept once (2026-10-07)

Follow-up to PR 0b of punch list #73 (v2.4864, [`to-dos/bid-history`](../../to-dos/bid-history/README.md)), found on its live walk. Migration `20261008091000_labor_rows_unmatched_one_per_fixture.sql` ([doc](../migrations/20261008091000_labor_rows_unmatched_one_per_fixture.md)); no edge function.

## The race

The Bids page starts several Labor loads at once when the active version changes: the Labor effect re-runs on each dependency that moves, and a run in flight is not stopped. Each sync reads the rows, plans and writes. On ZZ Test, switching from To Plans to PEX in lieu of copper started four syncs, and each set WC, WH and ft of 2" PVC aside, so the set-aside table held 12 rows and the band listed every one four times. **ZZ Test was the only estimate touched** (read on prod: one estimate, 12 rows). Set-aside rows are in no total, so no number moved.

The take-back side could not inflate totals either: `cost_estimate_labor_rows` has been `UNIQUE (cost_estimate_id, fixture)` since the baseline, so a second sync's live insert is refused. The same constraint is why the **mint race, which is older than PR 0b**, never left a duplicate: concurrent syncs have always tried to mint the same rows, and every insert after the first failed quietly (prod, 2026-10-07: 7,296 live rows on 259 estimates, no name twice on one estimate).

## The change

- **One sync at a time per estimate** ([`laborSyncQueue.ts`](../../src/lib/bids/laborSyncQueue.ts) `oneLaborSyncAtATime`): `loadCostEstimateLaborRowsAndSync` queues behind the sync before it, which then re-reads what that one left. A failed sync never blocks the next.
- **Claim by delete** (`useBidPricingEngine`): setting a row aside deletes it first, returning it, and only the sync that got it back writes the copy; a refused delete writes none. Taking a row back deletes the set-aside row first, and a sync that gets nothing back mints nothing; a refused live write puts the set-aside row back. Two tabs can no longer move one row twice either.
- **The database's guard** (the migration): the copies are deleted (the oldest of each stays, so ZZ Test is clean with no hand SQL) and `UNIQUE (cost_estimate_id, fixture)` on the set-aside table, the live table's own key.
