# v2.3720 — Lien desk: the run mails one envelope per name and address (2026-09-22)

Punch list #16 (`to-dos/gc-on-notice/`), the residual PR 2 deferred: *one envelope for two notices to the same owner at the same address (1016 + 1031 in the mock-up) — the run lists an envelope per notice; merging is a run-modal change.* Built asking whether that was the best we could do: the same rule also collapses the GC's N copies into one envelope, and the packet prints in envelope order. Client only, no migration; the record is unchanged.

## What was wrong

`buildLienDeskRun` gives every notice two recipients and the run treated each as an envelope: a nine-job run for one GC was nine certified envelopes to one GC address with nine tracking numbers to type, two jobs at one property were two envelopes to one owner, and the packet printed notice by notice (note, owner copy, GC copy, note, owner copy, GC copy …), so the person at the post office collated it by hand.

## The change

- **[`runEnvelopes.ts`](../../src/lib/jobs/runEnvelopes.ts)** (7 tests) — `envelopeKey(name, address)`: one party at one address, case, punctuation and spacing ignored ("L.L.C." is "LLC"), empty when either is missing so blanks never merge. `runEnvelopes(notices)`: the envelopes in order of first appearance, each with its `contents` (notice, recipient, and where each sits in the notices), the first email on file inside, and the method and tracking of the first recipient. `runCopies` is the old count.
- **[`lienDeskRun.ts`](../../src/lib/jobs/lienDeskRun.ts)** — `runCoverSheetBlocks` lists one numbered line per envelope: who, how, the tracking blank, and what is inside (`envelopeContentsText`: one notice, or *2 notices: …; …*); the header paragraph counts envelopes and says *Notices to one name at one address share an envelope; its tracking number covers everything inside* when any do. `runPacketHtml` prints in envelope order: per envelope, per notice inside, the owner's copy behind its cover page (the run's letter or the note — the GC's copy carries neither, as the emailed copies and the preview already had it), then the job's invoices.
- **[`LienDeskRunModal.tsx`](../../src/components/jobs/LienDeskRunModal.tsx)** — the table is envelopes: a header row per envelope (*Envelope 2 · Original contractor Loberg Contracting*, the address, the email, *3 notices inside*) carrying the method select and the one tracking box, then a row per notice inside it (the job, the claim, *cover letter* / *cover note* on the owner's row, that recipient's problems in red, the months, *Copy for: …*). `setEnvelope` patches every recipient inside, so `recordLienDeskRun` writes the same send on each notice — the `job_lien_filings` rows are unchanged. An emailed envelope with several notices says *one email per notice*; the IO already sends each notice's PDF separately.
- **[`gcOnNotice.ts`](../../src/lib/jobs/gcOnNotice.ts)** / **[`useGcOnNoticeData.ts`](../../src/hooks/useGcOnNoticeData.ts)** — `GcNoticeJob.ownerKey` (the hook resolves the property the same way the run does) and `summary.envelopes` is what the run will mail: distinct owner keys across the ready rows, a job with no key counted alone, plus one to the GC; zero with nothing ready. The header above the four steps reads that number.
- Guide *send lien notices from the Lien desk*: the run section and the *Approve all* line.
