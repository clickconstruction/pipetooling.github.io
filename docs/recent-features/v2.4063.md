# v2.4063 — My Time day editor: the database can now save a whole day at once — `save_my_time_day` (2026-09-28)

Migration only; no client change, no edge function. PR 1 of 3 of the all-or-nothing save (punch list **#46** row 10; the MY_TIME_DAY_EDITOR_MODAL map, quirk 26). Nothing calls the function until PR 2.

## What shipped

- **[`20260928182140_save_my_time_day.sql`](../../supabase/migrations/20260928182140_save_my_time_day.sql)** — `save_my_time_day(p_subject_user_id, p_work_date, p_leader, p_writes)`: the day's inserts, note / time updates and `own_*` / `leader_*` split / replace RPCs, in order, in one transaction; any error rolls all back; one `people_hours` resync after an approved row's times change. `SECURITY INVOKER`, so today's RLS and RPC checks apply unchanged. Details and the permission reasoning: [`docs/migrations/20260928182140_save_my_time_day.md`](../migrations/20260928182140_save_my_time_day.md).
- **[`supabase/tests/my_time_day_save/`](../../supabase/tests/my_time_day_save/)** — the stand-in schema and the scenario the migration was tried against.

## Not changed

No week fence was added to direct writes (the design proposed one): the migration doc says why, and it waits for an owner call.

## Verified

- The migration applied twice to a throwaway Postgres 15 with the production `clock_sessions` RLS policies; the scenario ends `save_my_time_day PASSED` (ten steps, twelve expected refusals).
- The release-notes check; not yet pushed to the database — `supabase db push` runs after this PR is on main.
