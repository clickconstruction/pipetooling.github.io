# v2.7988 — Document builder: a place in the database for a builder's contents (2026-11-19)

Punch list #404, step 2 of ten, the first half: the table. One migration, `20261120032253_document_builders.sql`, alone. No client change and no edge function. The tab reads it in the PR after the push.

## Why

Step 1 (v2.7980) put the Sub NDA's flow in the Document builder tab, on contents that are a file in the client. The card's next steps need a builder's contents to be data: a dev types on them, publishes a numbered revision, and marks who read it. The second builder, a job's insurance requirements, needs the same four things. So they are one table, built once.

## What landed

- **`document_builders`**: one row a builder, keyed by its name in the client's registry. Its kind is `walked` or `filled`. It holds the draft being set up, the published copy everyone outside sees, that copy's revision with who published it and when, and the read mark.
- **A revision number names one set of words.** A trigger keeps three rules. A builder starts as a draft on revision 0. A revision goes up one at a time and only with its published copy. A published copy changes only with its revision.
- **The read mark** is a revision, a typed name and a day, whole or absent, and only the published revision can be marked. A builder is read when the mark's revision is the published one, so a new revision is unread again and nothing has to clear the mark.
- **Who did it is the caller**: who made a builder, published it, marked it and changed it last.
- **A dev alone** reads and writes it, by row security. Nobody signed out holds a grant.
- **The migration writes no words.** The first draft is loaded by a press in the app, which the next PR adds.

## What it does not do

- No screen reads the table yet, and step 1's flow still runs on the made-up paper in the client.
- It keeps the current published copy, not every past one. Nothing in the card reads an old revision's words: a send keeps the revision number a person opened, and a certificate keeps the asks it was checked against.
- A publish that races another is the client's to guard, by updating where the revision is still the one it read.

## Checks

- `supabase/tests/document_builders/20_scenario.sql`, the bed `document-builders` (`scripts/pgtest-document-builders.sh`, in `scripts/sql-beds.txt`, so CI runs it over the whole schema). It plays a dev through a first draft, a saved draft, two publishes, the read mark put on and taken off, and each refusal by its words. Then each of the other eight roles reads nothing and lands no write, a dev in training, a dev's twin and a dev who left are held by the fences, someone signed out is refused, and a dev deletes the builder.
- Docker was not running on the Mac that wrote this, so the bed did not run there. The migration was applied twice and the same scenario run on a throwaway local Postgres 15 with stub `users` and `auth` tables and the four fence functions' real bodies: 95 checks passed. That proves the SQL's logic. Its fit to the whole schema on Postgres 17 is CI's bed and the dry run at the push.
