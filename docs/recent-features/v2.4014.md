# v2.4014 — Takeoffs: "In N assemblies" counts every assembly (2026-09-28)

Client only; no migration, no edge function. The row-cap tripwire fired on a live pass on 2026-09-28 (dev account, prod data, Bids → Takeoffs on a Combined bid): `[row-cap] material_template_items returned exactly 1000 rows with no limit`, path `/rest/v1/material_template_items?select=template_id,item_type,part_id,nested_template_id,quantity`. The cap class and its fixes: `docs/TROUBLESHOOTING.md` → "[row-cap]".

## What was wrong

`BidsTakeoffTab.tsx`'s part-assembly index effect read `material_template_items` with no filter, no order and no range. PostgREST answered with an arbitrary 1,000 rows and a 200, and `buildPartAssemblyIndex` was built from that subset. What that does on the screen: the **In N assemblies** link under a part line counted too few (or did not show), and the Add assembly modal, filtered by a part, left out assemblies that hold it. An assembly whose nested assembly fell outside the page also showed the wrong quantity in "includes ‹part› ×N".

## The fix

- New [`src/lib/materials/assemblyItems.ts`](../../src/lib/materials/assemblyItems.ts) on the existing pager: `loadAllAssemblyItemLinks` (every row, `.order('id')`, `.range`), `loadAssemblyItemLinksForTemplates` (`.in('template_id', chunk)` in chunks of 150, paged per chunk), `loadLowestPriceByPartId` (`material_part_prices`, the same way), pure `partIdsOfAssemblyItems`. The three loaders throw on a page error.
- New [`src/lib/bids/partAssemblyIndexIo.ts`](../../src/lib/bids/partAssemblyIndexIo.ts): `loadPartAssemblyIndex(client)` builds the index from every row and resolves `null` when any page fails — never an index of the pages that did arrive. The effect keeps its fail-soft behavior: on `null` it leaves the index it has.
- **The whole table, not the loaded trade's assemblies.** Every reader of the index goes through `partAssemblyEntriesFor`, which keeps only assemblies in the loaded `materialTemplates`, so the *roots* could be bounded. The quantities cannot: the kernel follows `nested_template_id` into other assemblies' rows, and nothing holds a nested assembly to its parent's service type.
- [`useMaterialsAssemblies.loadAllTemplateItemsForStats`](../../src/hooks/useMaterialsAssemblies.ts) had the same shape one level down: `.in('template_id', <every assembly of the service type>)` with no range, then `material_part_prices` `.in('part_id', <every part in them>)` with no range. Both page now. The prices read is fixed in the same PR because paging the items lengthens its id list; left alone it would have been a longer URL over a read that was already short. On a failed read the hook does what it did: the stats and the price map go empty.

## Checked and left alone

- One assembly's items (`.eq('template_id', id)`): `useMaterialsAssemblies.loadTemplateItems`, `materialPOUtils.expandTemplate`, `TakeoffAssemblyAuthoringModals` (the existing-part lookup, the sequence read with `.limit(1)`, `loadEditTemplateItems`).
- `src/pages/Materials.tsx` 786–966: updates, inserts and deletes by id or by assembly; no read.
- `materialsByStageIo.loadAssemblyPartStageSplits`: the assemblies on one bid, and only rows with a remembered stage split.
- `useSettingsBackupExports`: already paged.

## Not in this PR

`fetchLowestPartPricesBatch` (`src/lib/materialPartCatalogPrice.ts`, the Takeoffs lowest-price batch) and `fetchPricesForParts` (`src/lib/materials/partPrices.ts`, chunks of 500) read `material_part_prices` by part id with no range. They are a different table and a money path with no tests; they get their own PR.
