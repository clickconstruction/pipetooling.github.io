# v2.5377 — Two more server functions pass their own type check again (2026-10-12)

A type-only fix to `gc-card-bill` and `plan-fetch`, two of the eight edge functions that v2.5359 left alone. Each carried the `ReturnType<typeof createClient>` fault that v2.5359 and v2.5376 fixed, and one more error where the checker could not see what a value really is. No migration and no screen. Nothing behaves differently.

- **The client**: `gc-card-bill`'s `Admin` and `plan-fetch`'s `recordProbe` typed the client as `ReturnType<typeof createClient>`. Under supabase-js 2.117.3 (what `esm.sh/@supabase/supabase-js@2` serves today) that is a client with no schema, `SupabaseClient<unknown, …, never, never, …>`. So writes and RPC arguments took `never`, and the service-role client could not be handed in. Both take `SupabaseClient` now, as v2.5359 did (15 of the 18 errors). What the errors flagged was read against `src/types/database.ts` and exists as written: the `customers` Stripe id columns, `gc_card_bill_begin(p_invoice_id)`, `gc_card_bill_undo(p_invoice_id)`, `gc_card_bill_finish(p_invoice_id, p_stripe_invoice_id, p_hosted_url, p_stripe_status, p_mode)` and the three `bids.plans_robot_*` columns.
- **Two reads that looked nullable are not**. Both errors went away with the client:
  - The portal door reads the job by `begun.jobId`, which `parseGcCardBillBegun` types `string | null`. It only gets there in the pending state, where `gc_card_bill_begin` returns the bill's `job_id`, and `jobs_ledger_invoices` holds that column `NOT NULL`.
  - The undo door reads `bill.stripe_mode` only after the guard that returns when `bill` gives no `stripe_invoice_id`.
- **`gc-card-bill`'s Stripe customer id** (1 error): `stripe.customers.create` comes back as `any` under `esm.sh/stripe@16.12.0?target=deno`. So `stripeCustomerId = created.id` widened the id back to its declared `string | null`, and `stripeCustomerFor`'s `Promise<string>` refused it. A customer Stripe makes always carries its `cus_…` id, so the line reads `created.id as string`.
- **`plan-fetch`'s merged PDF** (2 errors): both merges hand pdf-lib's bytes to `new Response`. `save()` is typed `Promise<Uint8Array>`, which TypeScript 5.7 and later read as `Uint8Array<ArrayBufferLike>`, a buffer that may be shared, and a `Response` body takes only a plain `ArrayBuffer`'s bytes. pdf-lib 1.17.1's `save()` returns `PDFWriter.serializeToBuffer()`, which fills a `new Uint8Array(size)` of its own, so the bytes are in a plain `ArrayBuffer`. Both sites read `bytes as Uint8Array<ArrayBuffer>`. A copy into a new buffer, as `_shared/fileSentCopy.ts`'s `ownBuffer` makes (v2.5348), would change the JavaScript and hold a merged set of up to 60 MB twice.
- **Checked**:
  - `deno check --no-lock --node-modules-dir=none` (deno 2.9.6, TypeScript 6.0.3) of the two went from 18 errors to 0 on `main`: `gc-card-bill` 9, `plan-fetch` 9.
  - Each `index.ts`, main's and this one, compiled by TypeScript's `transpileModule` with comments dropped, gives byte-identical JavaScript.
  - The tests that read these sources pass, `gcCardBill.test.ts` among them.
- **Deploy**: redeploy both once merged. The code that runs does not change, but until then `npm run check:edge-drift` and the Edge function drift workflow name them as behind `main`.
