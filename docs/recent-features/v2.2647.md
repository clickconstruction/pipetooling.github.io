# v2.2647 — Superintendents can read + post job thread notes (2026-09-02)

Field report (Abraham, superintendent): posting "Arrived 11am" from the job
activity panel failed with *new row violates row-level security policy for
table "jobs_ledger_thread_notes"* — despite being on the job's team.

Root cause: the baseline `jobs_ledger_thread_notes` SELECT/INSERT policies
have (1) an office branch whose team-member check lives inside an
`EXISTS (… FROM jobs_ledger …)` subquery evaluated under the caller's RLS —
and superintendents have no `jobs_ledger` SELECT policy, so the subquery is
empty for them even when they are team members — and (2) a field branch that
checks `jobs_ledger_team_members` / `job_schedule_blocks` directly but is
gated on `auth_uid_is_helpers_or_subcontractor()`. Superintendents fell
through both: the feed's system events still rendered (SECURITY DEFINER
`list_job_activity_events`), but plain notes were invisible and every insert
bounced. Verified against prod: Abraham is a `jobs_ledger_team_members` row
on the job (added 2026-08-14), not read-only, with no clock-session side-door.

Fix (migration `20260902165836_superintendent_thread_note_access.sql`,
DB-only, no client change): new SECURITY DEFINER helper
`superintendent_can_touch_job_thread(job_id)` — role superintendent AND
(`superintendent_report_job_anchor_allowed` (project access OR team member,
the v2.2599 reports branch) OR dispatch schedule assignee) — behind two new
additive permissive policies for SELECT and INSERT (author-only). Existing
policies and the restrictive fences are untouched, continuing the
v2.2634–v2.2637 superintendent field-parity series.
