# v2.2969 — Test-gap audit, pass 3: the physical invoice PDF and its three sibling kernels get their first tests (2026-09-06)

Follow-up to v2.2964, which named the invoice PDF builder next. Tests only — no kernel, client, migration or edge-function change.

## Why these four

`physicalInvoicePdf.ts` (643 lines) renders the customer-facing invoice PDF that Bill Customer emails and the Documents page reopens; `physicalInvoiceFixtureScaling.ts` splits a bill amount across fixture lines to the cent (and must stay in sync with the Stripe edge function's allocator); `physicalInvoiceFooter.ts` and `physicalInvoiceIssuer.ts` hold the org-wide legal footer presets and company identity. None had a colocated test.

## What shipped

- **`physicalInvoicePdf.test.ts`** (12 cases) — the renderer is a sequence of jsPDF draw calls, so the test replaces the loader with a **recording fake**: it captures every `text` call with its page, position, alignment, font size and weight, counts pages, and approximates wrapping deterministically. What is pinned: the detailed layout's header, uppercased meta labels (values keep their case), SERVICE ADDRESS / CONTACT / issuer / Memo blocks present only when their data is; Services merging its title into the column header while Materials gets a Description header; totals; the tail showing the tagline, else the company name; the payment-history card (absent without rows, a rounded 88 mm frame with rows, "Balance due" right-aligned vs "Paid in full"); pagination of an 80-line materials list with "-- k of n --" on every page and the brand line only on the last; long descriptions wrapping inside one row; the simple layout's label/value card, em-dash for a missing email, no tables, and the shared payment card; filename sanitisation and base64 round-trip.
- **`physicalInvoiceFixtureScaling.test.ts`** (11) — largest-remainder allocation (exact sum, tie order, zeros), the name-plus-scope description, and the draft builder: raw amounts when the fixtures already sum to the bill, proportional scaling flagged and exact to the cent, unnamed / zero-priced rows dropped and `sequence_order` honoured, missing count as one, null for nothing billable or a sub-cent target, a tiny target still summing exactly.
- **`physicalInvoiceFooter.test.ts`** (9) — the v2 parser (rejects non-v2 shapes, caps body and label lengths and the custom-preset count, drops blank labels, "standard" default → null) and the shipped-default getters a fresh browser resolves to (two builtins, opens on Standard, exact-match preset detection, None / label / Custom summary, the Settings draft).
- **`physicalInvoiceIssuer.test.ts`** (3) — the stored-JSON parser keeps only known string fields; the draft is all-empty before any fetch and returns a fresh copy each call.

One first-run expectation was wrong and the kernel right: with no tagline the company name is drawn three times (top-left, issuer block, tail), not two.

## Not done here

`physicalInvoiceDocument.ts` (the model builder) already had tests. The footer / issuer *save* paths are Supabase writes and stay untested by design. Next by weight: `scheduleDispatchAddBlockTimeline.ts` (393) and `estimateCustomerExperience.ts` (383).
