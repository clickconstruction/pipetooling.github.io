# v2.6803 — Dev gates: six doors the train opened whose code still served a dev alone (punch list #188) (2026-11-09)

The Dev gates train (v2.6753–v2.6767) moved each door to the role that owns it through `src/lib/doorRoles.ts`. The docs catch-up pass after #7330 (PR #7478) read every row against the code and found six doors open on screen whose code beneath still answered only a dev, so the person newly shown the press got nothing. Each was confirmed in the source against its row of `to-dos/dev-gates/README.md` and its fragment; none was a gate the owner chose to keep. One migration, three edge functions.

## What changed

- **Row 30, a clause change's approvers** (v2.6762 added the owner): `messages-notify` kept its own `APPROVER_ROLES = ['dev', 'controller']`, so the owner approved and was never told a change waited. The list is now `CLAUSE_APPROVER_ROLES` in `_shared/messagesTeams.ts` (dev, master_technician, controller); `access.test.ts` holds it to `GC_CLAUSE_APPROVE_TEAM`, which it already holds to `gc_clause_approve_team()`.
- **Row 48, Workflow → Projections** (v2.6760 gave the controller the bar): `useWorkflowProjections` read rows for dev and master only, and the delete policy on `workflow_projections` was the baseline's dev and master, so she saw an empty bar and a Delete that removed nothing. `canSeeProjections` (`src/lib/workflow/projectionEdit.ts`: the owner, a dev, the controller) is now the one gate of the bar (`Workflow.tsx`), the read (the hook, both places) and the Forecast's money column (`ProjectsForecastSpecificTab`). Migration `20261109150000_workflow_projections_controller_delete.sql` restates the delete policy as `is_master_or_dev() OR is_controller()`.
- **Row 62, Tally → Payroll rules** (v2.6761 gave the controller the window): `applyPayrollRules` and the auto-apply effect returned early unless `role === 'dev'`, though `bulk_apply_tally_payroll_rule_flags` admitted her. Both read `canEditPayrollRules`, now `canEditTallyPayrollRules` in `src/lib/tallyPayrollRules.ts`, the gate of the chip and the window that offer them.
- **Row 69, the Bridge** (v2.6763 opened the page to the owner): `bridge-sheet-email` refused anyone but a dev, and `bridge-weekly-sheet` mailed and dry-ran for devs alone, though the row says the weekly send *is for him*. `BRIDGE_ROLES` / `isBridgeRole` in `src/lib/bridge/weeklySend.ts` (dev, master_technician; held to `isOwnerOrDev` by its test) now gate **Email me this sheet**, the weekly send's recipients and the dry run. `bridge-sheet-email` joins the kernel copy's `IMPORTERS`. The card's words, the confirm, the email catalogs and the guide say *the owner and every dev*; the not-saved line names the owner beside a dev, as the switch's policy has since v2.6763.
- **Rows 27–28 (and row 24 of v2.6756), Settings → Contracts & terms**: the catalog marked every Settings editor `devOnly`, so the owner read *A dev edits this* on the estimate's terms he edits. A Settings door now carries `editors` (`'dev' | 'owner' | 'estimator' | 'office' | 'controller'`) and `settingsDoorOpens` reads `doorRoles.ts`: the estimate's terms and defaults are the owner's, the bid cover letter the estimators', invoice footers the controller's, test reports the office's. Everyone else reads who edits it (*The owner edits this: …*). The tab's audience has no estimator, so the cover letter's door opens for a dev and names the estimators to the rest. The test holds the two Jobs, bills and liens doors to `jobsBillingCardVisible` for every role, and the three Bids & materials doors to the gate the page mounts each block under.
- **Two titles**: *Draft bills on paid jobs* (the controller's since v2.6766) and *Bid Cover Letter Defaults* (the estimators' since v2.6764) drop "(dev)".
- **Guides**: *read the Bridge* (who gets the weekly email), *change the default bid cover letter text*, *see every contract side by side* (who edits which wording), *see the money flow on a workflow* (the controller).
- **Tests**: `projectionEdit.test.ts` (the predicate, its three readers, the migration's policy), `useWorkflowProjections.render.test.tsx` (the controller reads), `tallyPayrollRules.test.ts` (the predicate and the page's two gates), `weeklySend.test.ts` (the audience, the recipients, the two functions' gates), `access.test.ts` (the approver copy), `customerContractCatalog.test.ts` and `SettingsContractsTab.render.test.tsx` (each door's audience and words).
