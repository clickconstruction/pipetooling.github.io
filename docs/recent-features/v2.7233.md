# v2.7233 — The service worker's precache cap is 9 MiB: the main chunk passed 8 MiB (2026-11-13)

Infra, no screen. The deploy build ends with vite-plugin-pwa's `injectManifest`, which refuses any precached file over `maximumFileSizeToCacheInBytes`. The main chunk grew past the 8 MiB cap, and every deploy failed from 2026-11-14 02:20 UTC.

## What broke

- **The site's deploys.** The deploy for 6dc103663 (v2.7222 #8049 and v2.7220 #8047) built `assets/index-B0UZWb5i.js` at 8,393 kB, past 8 MiB (8,388.6 kB). The service worker's build then stopped with *Assets exceeding the limit … won't be precached* and exit 1. The deploy before it, for 0419a5517, built the same chunk at 8,367 kB. Nothing merged after 01:42 UTC reached the site.
- **Pull requests carried on.** CI's checks never run `vite build`, so the merge queue kept landing changes that could not deploy.

## The change

`maximumFileSizeToCacheInBytes: 9 * 1024 * 1024` in place of `8 * 1024 * 1024` in `vite.config.ts`, with the reason added to the comment above it, as that comment asks. The main chunk still enters the precache, as it did under 8 MiB, so the app opens with no signal as before. About 1 MiB is left for growth: about ten days at the pace since 2026-11-03 (7,348 kB then, 8,393 kB now). A regression like v2.4655's, which put every help guide in the main chunk (now ~3.1 MB), still trips it.

## Is this the best we can do?

No. The comment above the cap has said since 2026-10-20 that the main chunk is due a code-split pass: every public page is eager in `App.tsx`. That split is the real fix, and this raise only buys time for it. It is the owner's call and is not built here.

## Verified

`npm run build` passes locally with the new cap, and the deploy's *Verify build output* checks pass on its `dist/`.
