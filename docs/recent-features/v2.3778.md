# v2.3778 — The job-rename plan reads without writing (2026-09-24)

Found on the first real run of v2.3766's plan on prod, minutes after the push: `plan_job_names_from_work(false)` built a temp table, so it failed inside a read-only transaction — including the dev-mcp seat's `call_read`, the very door the migration doc pointed at. The same run listed **"Job total (migrated)"** eight times: the import's placeholder line, never the work. One migration, one kernel line.

## The change

- **[`20260924010000_job_name_plan_read_only.sql`](../migrations/20260924010000_job_name_plan_read_only.md)** — the plan is one `STABLE` SQL function, `job_names_from_work_plan()` (private: `service_role` only, the role check stays in the caller); `plan_job_names_from_work(p_apply)` returns it as is, or feeds it to the `UPDATE` and the activity `INSERT` in data-modifying CTEs. Same signature, same rows, no temp table. `specific_work_name()` refuses `job total`, `job total (migrated)` and any name ending in `(migrated)`.
- **[`jobNameFromWork.ts`](../../src/lib/estimates/jobNameFromWork.ts)** — the same two placeholders in `GENERIC_WORK_NAMES`, and `isSpecificWorkName` refuses a `(migrated)` suffix. Tested.

## What the plan says now

358 jobs (the eight migrated placeholders dropped from 366): 1 working, 3 billed, 1 waiting, 353 paid. The apply is still a separate, owner-approved step.
