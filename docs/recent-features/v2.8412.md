# v2.8412 — Supply house bills: every word on a bill becomes searchable (2026-11-23)

Punch list #431, PR 6 of seven. The owner asked what it takes to index supply house invoices so they become searchable, and chose the size that keeps each bill's whole text. The lines of a bill are already rows. This PR keeps the rest of the page: the ship-to, who ordered, a note. One edge function changes, `bill-lines-sweep`. The column it writes and the search that reads it shipped in v2.8406.

## Where the words are kept

`supply_papers.page_text`, on the paper itself, and not in the file index. The card first planned the file index. Three things changed that:

- **One file often holds several bills.** The file index keeps one row a file. A bill needs the words of its own pages, or a search for one bill's ship-to finds all nineteen bills scanned with it.
- **A bill is the office's to read.** The file index is read by the office and the estimators. The papers table already has the right policy, so the words take it with no new fence.
- **The reader is already there.** The bill sweep opens each bill's PDF and reads its text layer for the code check. Keeping the words costs one more pass over a file it already holds, and no model read.

The search by meaning and Documents → Search do not read bills as a result. Meaning is weak on bills, which are codes and numbers, and the three places the owner named for a bill search (a job's list, Materials and the app's own search) all read `search_supply_bills`. Putting bills in the file index as well stays open on the card.

## What changed

- **A paper keeps its own words.** After a paper and its lines are written, the sweep writes `page_text`: the text layer of the pages that are this paper (`paperPageText` in `_shared/billSweep.ts`). No pages on record is the whole file. At most 20,000 letters. The text is read a page at a time (`pageTextsOf`), each page shaped the way the whole text already is.
- **The write is its own.** A paper is never lost over its words. If the column is not on prod yet, the update is refused and logged and the paper stands, so the function may be deployed before or after the migration is pushed.
- **The bills on file are filled** by the same run, after the recheck (`fillPageText`): up to six files a run, every ten minutes, with no model read and so no cap. A file is opened once and every paper read from it takes its own pages. A file with no words to give (gone from Drive, too big, in the trash) leaves its papers an empty string, so it is not opened on every run. A file Drive is too busy to hand over waits.
- **A scan keeps no words.** Its text layer is empty, and the app has no OCR set up. Its lines, read by the model, are still found.
- The run's answer carries `pageText: { papers, files }`, and its line says how many papers took their words.

## What it costs

Nothing a month. No model reads: the words are the PDF's own text layer. About 300 files stand behind the bills on file, so the fill takes under ten hours of ten-minute runs by itself. The words are a few thousand letters a paper, a megabyte or two in all.
