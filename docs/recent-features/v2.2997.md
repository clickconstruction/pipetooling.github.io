# v2.2997 — Test-gap audit, pass 17: the schedule-block repository gets its first tests (2026-09-07)

The named kernel list closed at v2.2994; this pass restarts the train on the heaviest untested module in `src/lib` by line count. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`jobScheduleBlocks.ts` (655 lines) is the repository layer for `job_schedule_blocks`: twenty callers across Schedule, Dispatch, the Dashboard, the Calendar and People use it for every read and write of a scheduled block. Only its pure quick-pick builder had a test (`jobScheduleBlocksAssignPicks.test.ts`). The fetch and write wrappers — which filters and payloads reach PostgREST, how results and failures come back — had none.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Group-keyed reads and updates (legs, shared-group peers, group time sync) filter on `shared_block_group_id` alone, so bid-anchored legs are included; the job filter that once dropped them stays gone.
- The hub range read orders by assignee, then day, then start; the per-job and per-assignee range reads by day then start; the per-job read is capped at 101 rows and joins both the assignee and the scheduler (`creator`) names.
- Reads short-circuit without a query on no assignees or a blank assignee / day; the batched quick-pick read dedupes and trims assignee ids into one `IN` query and leaves assignees with no blocks out of the map.
- Every read failure comes back as an empty list (or map) plus the message; every write failure as the message. Nothing throws.
- `ensureSharedBlockGroupForRow` returns an existing group without writing, mints and patches a UUID onto a legacy solo row, and reports a missing row.
- The linked-group move passes a null job id through to the RPC as-is for bid-anchored groups.

## What shipped
