# v2.5536 — Messages: a webhook made in Quo's own settings is recognized (2026-10-14)

Found on the switch-on of 2026-10-14: the first webhook subscription was made in Quo's own settings (Settings → Webhooks, label ClickTooling), and every delivery answered 401. The function's log read `[quo-webhook] refused: missing headers` on each of the UI webhook's deliveries and test requests. The key on prod was the right one (the SHA-256 of `whsec_` plus the settings page's Signing secret equals the prod digest), so the fault was the check. Quo signs a webhook made through its versioned API (`Quo-Api-Version: 2026-03-30`) the Standard Webhooks way, which is all `verifySignature` knew. It signs one made in its settings the older OpenPhone way.

- **`src/lib/quo/webhook.ts`** `verifySignature`: when a delivery carries `openphone-signature` and no `webhook-signature`, it takes the older scheme. That is `hmac;1;<timestamp>;<base64>` entries, comma-separated, and HMAC-SHA256 over `<timestamp>.<body>`, keyed by the decoded base64 secret, with a `whsec_` prefix stripped if one was pasted. Quo's samples disagree on the body (raw bytes in Python, `JSON.stringify` in Node), so both the raw body and the JSON written out with no spaces are taken. The timestamp is in milliseconds (ten digits or fewer reads as seconds), and the window is the same five minutes either way. The delivery's id for `quo_webhook_claim` is the event's own `id`, which Quo keeps on every retry, else `legacy:<timestamp>`. A delivery carrying both header sets is read the newer way.
- **Tests**: `webhook.test.ts` gains six cases under *the older signature*. They cover the raw and compact bodies, the key with or without `whsec_`, several entries, seconds as well as milliseconds, another key, a changed body, another scheme or version, both windows, both header sets, and the id fallback. The thirteen Standard Webhooks cases are unchanged.
- **Edge copy**: `_shared/gcKernels/lib/quo/webhook.ts` is regenerated, and `quo-webhook` is redeployed.
- **Docs**: EDGE_FUNCTIONS → `quo-webhook` *Authentication* names both schemes.

What it found next: with the signature passing, Quo's test request answered `200 {"ignored":"API version v3, not 2026-03-30"}`. A webhook made in Quo's settings sends the older v3 event format, which `readQuoEvent` sets aside by design. So texts and calls come in through a webhook made with Quo's API (`Quo-Api-Version: 2026-03-30`). Cut 5 made one; the settings page does not list it, and its deliveries carry the Standard Webhooks headers, so the log's `bad signature` lines are its. The switch-on replaced its key on prod with the settings page's. The fix is to rotate that subscription's key (`POST https://api.quo.com/webhooks/{id}/rotate`, which returns the new `whsec_` key), set it as `QUO_WEBHOOK_SECRET`, and delete the settings-page webhook. Its v3 deliveries then fail the signature again, and Quo stops after its retries.

What does not change: the Standard Webhooks path, the events read (2026-03-30 only), the writes, and the answers.
