# v2.4686 — Database setup helpers are closed to outside calls (2026-10-06)

Migration only; no client change, no edge function. [`20261006160500_revoke_sweep_helpers_from_api.sql`](../../supabase/migrations/20261006160500_revoke_sweep_helpers_from_api.sql) revokes EXECUTE on `apply_read_only_write_blocks()`, `apply_read_only_stmt_blocks()` and `apply_digital_twin_write_blocks()` from `PUBLIC`, `anon` and `authenticated`. This is the follow-up flagged with v2.4604.

- **The exposure**: the three CREATE TABLE sweep helpers are `SECURITY DEFINER` in `public` with the default grants. So the anon key, which ships in the client bundle, could call them over `/rest/v1/rpc/` and run them as `postgres`. Before v2.4604 the twin fence helper rebuilt every policy on each call, so one anonymous request locked every RLS table. They slipped the 2026-09-06 RPC audit.
- **The fix**: nothing outside migrations calls them, so the API roles lose EXECUTE. The owner (`db push`) and `service_role` keep it, and `CREATE OR REPLACE` keeps the grants.
- **Guards**: an assertion fails the migration if the REVOKE did not take effect, since a non-owner REVOKE only warns. The file ends by calling all three helpers, so the push role provably still can.
- **Rehearsed** on Postgres 15.14 with a Supabase-like role layout in 24 checks ([details](../migrations/20261006160500_revoke_sweep_helpers_from_api.md)). [`ACCESS_CONTROL.md`](../ACCESS_CONTROL.md) → SECURITY DEFINER RPCs and the anon key records the revoke.

**Deploy**: `supabase db push` after merge. Then a `POST /rest/v1/rpc/apply_read_only_stmt_blocks` with the anon key should answer `401` with code `42501`.
