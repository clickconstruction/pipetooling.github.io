# v2.3117 — plan-fetch accepts Drive folder links (merge, cap, ?part=) (2026-09-07)

The robot plan-set door only served a bid whose `bids.plans_link` was a single Drive *file* link; estimators file plan sets as Drive *folders*, and the v2.3080 probe recorded every such bid as "unreadable by robots". plan-fetch now treats a folder as the plan set. Edge function only — no migration, no client change, no other function touched.

## What changed (all in `supabase/functions/plan-fetch/index.ts`)

- **`driveFolderIdFromUrl`** parses `https://drive.google.com/drive/folders/<id>` and `/drive/u/N/folders/<id>` (query/fragment tails tolerated). `driveFileIdFromUrl` and the whole file-link path are byte-for-byte unchanged.
- **`listFolderPdfs(token, folderId)`** — Drive v3 `files.list` with `q='<id>' in parents and trashed=false and mimeType='application/pdf'`, `fields=files(id,name,size,modifiedTime)`, `supportsAllDrives` + `includeItemsFromAllDrives`, paginated. Google-native docs and non-PDFs are ignored. The list is sorted by name with natural numeric collation (`A-1.2` before `A-1.10`), which is also the order `?part=` counts in.
- **Probe** (`?probe=1`, `?probe=all`): a folder is readable when the service account can list it and it holds ≥ 1 PDF → `plans_robot_readable = true`, note `folder · N PDFs, merged on fetch: a.pdf, b.pdf, …` (names capped at ~200 chars, `+N more`; a single PDF reads "streamed on fetch"). Zero PDFs → unreadable, `folder holds no PDF — upload the plan set`. Drive 403/404 on the listing (or, when the listing is empty, on the folder's own metadata — an unshared folder can list as empty) → the existing "not shared with the intake service account" / "no permission" wording. The single-file probe is unchanged.
- **Fetch** (folder link, after the twin assignment fence): the probe runs first and is recorded on the bid, as every fetch already did. Then:
  - one PDF → streamed exactly as a file link is (Content-Type/Length passed through, `<project>.pdf`);
  - several → fetched in name order and merged with pdf-lib 1.17.1 (`copyPages`) into one PDF, `Content-Disposition: <project> - plans (merged N).pdf`, `X-Plan-Parts: N`;
  - summed `size` > **60 MB** → not merged: the largest PDF streams with `X-Plan-Parts: N` and `X-Plan-Note: merged set exceeds 60 MB; streamed largest part only — stage_plan_pdf per part`;
  - a part pdf-lib cannot open (or a Drive hiccup mid-merge) falls back the same way with `X-Plan-Note: merge failed (…)` rather than making the set unreachable;
  - **`?part=<n>`** (1-based, name order; also `POST {part}`) streams one specific PDF (`<project> - <name> (part n of N).pdf`); out of range → 400 listing `1=a.pdf, 2=b.pdf, …`.
  - `Access-Control-Expose-Headers` names `Content-Disposition, X-Plan-Parts, X-Plan-Note` on folder responses only.
- Unreadable folder on fetch → 404 (empty) / 502 (not shared) with the probe note in the error, recorded on the bid.

## Not changed

File-link fetch bytes and headers; the `probe=all` sweep's selection/cap; auth and the assignment fence; the CT `import-takeoff` contract (it still receives one PDF per pull — for an over-cap folder it receives the largest part and the headers say so; `stage_plan_pdf` per `?part=` covers the rest).

## Deploy

`supabase functions deploy plan-fetch` (operator; `verify_jwt = false` stays). Pulls pdf-lib from esm.sh at bundle time.

## Docs
