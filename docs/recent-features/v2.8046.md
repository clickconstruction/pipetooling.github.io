# v2.8046 — Robots: a twin's seat that cannot be read now says why (2026-11-20)

`plan_twin_seat` on `dev-mcp` names the reason a TakeoffTooling seat could not be looked up. No new verb and no server version: the tool list and every count stand.

## Why

The first live run of `plan_twin_seat` (v2.7974) read *could not be read* for the TakeoffTooling seat of every bid robot, with the warning "tt-bridge answered 401" and nothing more. `tt-bridge` passes on whatever TakeoffTooling's `manage-user` answers. Its own refusals carry an `error` string. A reply from the other app, or from the gateway in front of it, may carry `message` or `msg` instead, and `ttSeatLookup` read `error` alone. The status hid the cause. The owner, 2026-11-20: "Yes, add it".

## What changed

- `ttSeatLookup` (`supabase/functions/_shared/devMcpTwinSeat.ts`) builds the reason from the status and the reply's own words: `error`, then `message`, then `msg`, trimmed and held to 300 characters. A reply with none reads as the status alone, as before.
- The reason now always leads with the status: `tt-bridge answered 500: TT_BRIDGE_SECRET not configured`, where a reply with an `error` read as the error alone.
- The plan hash is unmoved. The reason rides in `warnings`, which `planCommitment` leaves out.
- The apply already read both keys, through the server's `fnWords`.
