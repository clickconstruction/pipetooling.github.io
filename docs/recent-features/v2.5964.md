# v2.5964 — Nine more waiting lists say how long each row has waited (2026-10-27)

Punch list #184 sweep B, PR 2 (`to-dos/consistency-sweeps/README.md` → *B. Waiting lists*): the hand sites. The rule (Glossary → *Amber / red age*): a list of rows waiting on a person sorts oldest first and carries a fresh / amber / red chip at a threshold declared as a named constant in `src/lib/ageState.ts`. Seven new constants, one-line comment each: `UNLINKED_SHEET_AGE` 7 / 14, `PROSPECT_CALL_AGE` 7 / 30, `UNDATED_BILL_AGE` 3 / 7, `UNPRICED_PART_AGE` 3 / 7, `PRICE_MATRIX_PERSON_AGE` 1 / 3, `LEGAL_FIRM_ENTRY_AGE` 2 / 5, `LABEL_APPROVAL_AGE` 3 / 7. My Team reuses `HOURS_APPROVAL_AGE`; Sub money reads `dueState`. No migration, no edge function.

## Is this the best we can do?

Mostly. The thresholds are the plan's guesses beside the precedents; each is one constant. Three places could go further. Sub money first carried `dueState`'s red *N days late*; the review took it out, because on the sub's own screen it would read as the company admitting it is late, and the sub cannot act on it.nextRun`), one change in `subSheetDue`. The Legal desk's Needs You line still counts the firm's entries without the oldest's age; `buildFirmActivity` could carry it next. The Queue lens reads the 50 newest open price-matrix requests before it sorts them oldest first, so past 50 open asks the oldest would drop; that is a one-token flip in `usePriceMatrixRequests` if it ever happens. Unpriced Fixtures is a count, so its chip ages the oldest fixture rather than ordering rows; the list a person works is Jobs → Parts, a register. That tab (`usePartsLedgerData`) and the job cost snapshot (`fetchJobMaterialsCostSnapshot`) still read `list_tally_parts_with_po()` un-ranged, so past 1,000 visible tally rows they see only the newest 1,000; paging them is its own fix, outside this sweep.
