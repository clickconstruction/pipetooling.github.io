# v2.2876 — Bill Customer and New Estimate write nothing on open (2026-09-05)

Journey-map Phase 4, Tier-1 #14(d) ("Opening or picking mints a record"). Owner decision 17
(2026-09-05): **write only after an explicit user commit.** The code-only audit found two openers
that wrote on mount; this PR closes both. No migration, no edge-function change.

## Bill Customer (`SendRecordInvoiceModal.tsx`, kind `'job'`)

**Before.** Every `kind:'job'` opener (Dashboard Ready-to-Bill row, the three Pipeline board
doors, the job window's Bill tab) ran `ensure_single_ready_to_bill_invoice_for_job` in a mount
effect. That RPC INSERTs the primary Ready-to-Bill remainder draft, or UPDATEs an existing one to
the current remainder (+ flips `is_primary_rtb_bundle`), or DELETEs a never-sent $0 primary when
fully allocated. Only the INSERT was unwound on Cancel (v2.2464's `cleanupMintedPrimaryDraft`,
best-effort); the resize and the delete persisted. `kind:'invoice'` openers were clean.

**After.** The mount effect is gone. The modal derives its billing target from the job detail it
already fetches for the previews (`fetchJobWithDetailsById` → `jobs_ledger` row + `invoices`)
through a new pure kernel, **`src/lib/billing/proposedPrimaryRtbAmount.ts`**:

- `proposedPrimaryRtbAmount({ revenue, payments, otherOpenInvoices })` — THE remainder,
  `GREATEST(0, revenue − payments − Σ RTB+billed rows excluding the RTB primary)`, in cents.
- `planPrimaryRtbForBillCustomer(job, invoices)` — the RPC branch for branch, read-only:
  `{ kind:'bill', amount, invoiceId | null, wouldCreate }` or
  `{ kind:'blocked', reason, message }` with the RPC's verbatim error strings
  (`job_not_rtb`, `multiple_primary`, `no_remainder_partials`, `nothing_left`) plus
  `fully_allocated` — where the RPC would DELETE the $0 primary, the modal now just renders
  "Nothing left to bill for this job — every dollar is already on an invoice." and deletes nothing.
- 18 parity tests (`proposedPrimaryRtbAmount.test.ts`), including the job-978 shapes (stale
  $3,630 auto draft + $1,000 partial → resize to $2,630; fully allocated → blocked) and the
  Stripe-finalized primary that is never resized.

`ensuredInvoice` is now `{ jobId, id: string | null, amount }` — `id` is the existing RTB row the
RPC would adopt/resize, or `null` when it would INSERT on commit. Every consumer that scoped by id
(`fixturesForInvoiceBill`, `buildPhysicalInvoiceDetailFromJob`, the bill-to loader) already
handles null as "whole job". `ensureLoading` = detail fetch not settled; `ensureError` = plan
blocked (or the job failed to load).

**The RPC runs at commit, once, immediately before the write** — `ensurePrimaryRowForCommit(amountShown)`
inside `submitStripeInvoice` (before `create-stripe-invoice`), `confirmOutsideBill` (before the
HCP row UPDATE) and `submitPhysicalInvoiceEmail` (before `send-physical-invoice-email`). It
records the returned row as `committedPrimary` (the fallback "Send from Stripe" button and the
hazmat repoints use it), fires `onAfterEnsureSuccess` so openers refresh, and — new guard — if the
returned amount differs from the amount on screen (a payment landed, a partial was carved off
while the modal was open) it updates the amount and returns
*"The amount left to bill changed to $X since you opened this — review the bill, then send again."*
instead of billing the new number silently.

**Stripe preview.** `preview-stripe-invoice` strictly requires a `jobs_ledger_invoice_id` (it reads
the row for status, fixture scoping and bill-to). When the plan has a row id the live preview runs
exactly as before, on the planned amount. When it would INSERT (no row yet) the panel shows the
static draft line (`StripeBillPreSubmitPreview`'s idle state) with the hint *"Nothing is saved
until you send. Stripe's exact layout appears once the bill exists — the line below is what the
customer will see."* The ephemeral-Stripe-customer create+delete the preview performs is external
and transient; unchanged, noted. Follow-up if the no-row case turns out common: a job-level
preview mode in the edge function.

**Removed.** `cleanupMintedPrimaryDraft`, `mintedPrimaryDraftRef`, `openJobIdRef`, and
`src/lib/jobs/mintedPrimaryDraftCleanup.ts` (+ test) — nothing is minted on open, so there is
nothing to unwind. v2.2464's design note ("delete-on-cancel, not defer-create") is superseded by
decision 17.

**Smoke.** New `SendRecordInvoiceModal.render.test.tsx`: mount shows "RTB $2,630.00" from the
plan with zero ensure calls and zero `jobs_ledger_invoices` writes; HouseCall Pro → Save runs the
ensure exactly once, then one `update`, then `onSuccess`/`onClose`.

## New Estimate (`Estimates.tsx`)

**Before.** "New estimate", "New change order" and the Projects card's `?newEstimate=true` deep link
called `createDraft`, which INSERTed the `estimates` row and navigated to it. Walk away and the
empty row stayed — the reason the Pipeline's "Clean up empty drafts" sweep exists.

**Approach taken: mint on the button, self-delete on leave** (the plan's acceptable minimum).
Routing to `/estimates/new` with an unsaved virtual row was judged too invasive: `EstimateDetail`
is row-backed end to end — `load()` resolves by number/uuid, `saveDraft` UPDATEs by `row.id`,
autosave diffs against the hydrated row, and 27 effects key on `row.id`. Instead:

- `createDraft` navigates with `state: { freshEstimateDraft: true }` and records
  `estimate_draft_created` telemetry (`#button:estimate`, `#button:change_order`,
  `#deeplink:estimate`).
- `EstimateDetail` stamps `freshDraftRowIdRef` when it hydrates a draft under that marker, and
  `committedDraftRowIdRef` on any write (`saveDraft` — autosave, Save draft, the pre-send save —
  and `deleteDraft`).
- A leave hook keyed on `routeSegment` (its cleanup runs at a route change while state is still
  the OLD row's, and on unmount) asks the new kernel
  **`src/lib/estimateFreshDraftDiscard.ts`** — `shouldDiscardFreshEstimateDraftOnLeave({ fresh,
  everSaved, form })` = fresh ∧ ¬everSaved ∧ `isEmptyEstimateDraft(form)` over the LIVE form
  (`estimateDraftFormSnapshot`), not the stale hydrated row — and, when true, cancels any pending
  autosave and DELETEs the row (`.eq('status','draft')`, best-effort). 9 kernel tests.
- The deep link follows the same path (it still mints on mount — it has to land somewhere — but an
  untouched visit deletes the row on the way out).

`cleanUpEmptyDrafts` stays for legacy rows and for hard-reload / tab-close leaves (no JS runs);
its count should trend to zero.
