# v2.7748 — Estimates: saving a draft keeps the page up (2026-11-18)

Client only; no migration, no edge function. Punch list **#46** row 3 (`to-dos/decomposition-queue.md`): the first item under *What is left* on the Estimates map (`docs/ESTIMATES_TABS_ARCHITECTURE.md`), "A quiet reload — the owner's call". The owner sent the note to be worked on 2026-11-18. The cuts it unlocks are not in this PR.

## Before

A save that reloads ran `load()`, and `load()` set the page's `loading` flag, so `EstimateDetail` drew *Loading…* in place of the whole editor until the row and the customers had been read again. Three presses did it: **Save draft**, picking or clearing a customer (the customer-link autosave), and **Publish to bid room**'s save. Measured on the dev server against a ZZ draft on 2026-11-18, before the change:

- **Save draft**: the editor was gone 0.28 s after the press and back 0.40 s later. The page jumped from 789 px down to the top. Both open folds (*Customer experience*, *How to share a file…*) came back closed. Focus was on the page body.
- **Picking a customer**: the same blank, 0.31 s, and the cursor left the customer box.
- **Typing over a picked customer's name**: the first letter cleared the pick, which saved, which blanked the page. The box came back empty and the rest of the typing was lost.
- **Typed during the save**: anything typed between the press and the blank was overwritten when the row seeded the editor again.
- **A half-typed date**: the save left it out and said so, then the reload put the saved date back in the box. On a change order it put all four detail lines back.
- **With options**: the editor came back on the starred option, whichever one was being edited.
- **A read that failed after the write landed**: *Could not load estimate*, and the office was sent to the list.

## After

The same three presses read the row back with the page up (`reloadAfterSave` in `useEstimateDetailData`). The button says *Saving…* until the read lands. Nothing unmounts: the scroll position, the open folds, the box the cursor is in and every piece's own state stay.

What the editor holds afterwards is decided field by field by `reseedEstimateFormAfterSave` (`src/lib/estimates/estimateQuietReload.ts`) from three forms: the one the save wrote, the one on screen when the read lands, and the one the row would open as.

- **Not touched since the save**: the row's value arrives. That covers a trimmed title, the thirty-day date a cleared **Expires on** falls back to, the stub line of an estimate saved with no lines, and a value another person wrote.
- **Typed since the save**: the typing stays, and the autosave writes it about a second and a half later.
- **Both moved**: the typing stays and the next save writes over the row. A draft save has always written the whole form, so the last save wins, as before.
- **A date caught half typed**: the box keeps it. A change order's four detail lines stay with its date.
- **The screen's own four fields**: the option being edited stays the one being edited while it still exists. The Page preview's ticks stay. The lit good-through preset follows its date. The customer box keeps its text unless the read changed who the customer is.

Nothing is minted by the write. A line is a JSON row with no id, an option's key is made in the browser, and no trigger rewrites a draft's fields. So "what the server changed" is what opening the row changes, and the row's form is built by the code that opens a row.

**The autosave's baseline.** The blank used to reset it: the shared slice (`useJobFormAutosaveSlice`, also Edit Job's and Edit Bid's, not changed here) dropped its baseline while `loading` was true and took a new one from the seeded editor. The page no longer blanks, so the save hands the slice its baseline through the slice's own `markSavedNow`: for one commit the hook shows it the payload of the editor *as the read-back leaves it when nothing was typed*, then the screen's own. Typing newer than the save reads as unsaved against that and is saved next. A box typed back to what it held before the save reads as unsaved too, which it would not against the old baseline. With nothing typed, the screen equals the baseline and nothing is written a second time.

**A read-back that fails** after the write landed leaves the editor as typed and says *Saved. The page could not read the estimate back:* with the reason from `formatErrorMessage`. It no longer sends the office to the list. A row that is no longer a draft (somebody sent it) takes the whole seed without the blank, as the refresh after a send does.

## What did not change

- `load()` still blanks: the first open, the sent side's four presses, the read after **Publish to bid room** and after **Create job**. The refresh after a send was already quiet.
- The debounced autosave still skips the read-back.
- A save that fails still reads nothing and shows its reason.
- The payload: `estimateDraftPayloadOfForm` is the hook's old builder as a pure function, key for key in the same order. The autosave compares its JSON.

## What it allows, and one thing found on the walk

A section of the draft editor can now own what only it uses across a save. That is the map's next cut, not this one.

`EstimateDraftCustomerGate` still remounts what is inside it when a draft gains or loses its customer: it returns its children bare when a customer is picked and inside two wrappers when none is. The customer section sits outside the gate. Everything else in the editor sits inside it, so a piece that takes its own state loses it on that one change until the gate keeps one shape. Seen live: after clearing and picking a customer the Save draft button and the Terms box were new nodes.

After **Save draft** the cursor is on the page body, not on the button: the button is disabled while it saves, and a disabled button drops focus. The fields keep theirs.

## Tests

- `estimateQuietReload.test.ts`, 24 cases: the rule per field, the half-typed dates, the four screen fields, the baseline, the payload against the one builder, the row's form.
- `Estimates.render.test.tsx`, 9 new cases (33): the editor's nodes are the same nodes after a save, with the fold open and the box in hand; the row's values arrive; nothing is written twice; typing during the save stays and is saved next; a box typed back is saved; the edited option stays; text typed over a picked customer stays; a failed save says why through `formatErrorMessage` and reads nothing; a failed read-back stays on the estimate. Eight of them fail against the old `load()`; the ninth, the failed save, held before and holds now. Two fail with the baseline hand-off taken out.

## Verified

Walked on the dev server, signed in through `/dev-login`, on a ZZ draft made for the walk and deleted after it: picking a customer with the cursor in the box (no blank, same box, cursor kept), **Save draft** with two folds open (no blank, folds open, same Terms box, no second write in the three seconds after), adding a priced line and saving, **Save draft** pressed twice in a row (one write, one read, one *Saved*), typing in Terms while the read-back was held for 2.5 s (the typing stayed, the cursor stayed, the autosave wrote it 1.5 s after), typing over the picked customer's name (the box kept the text), and **Send to customer** after a save as far as the Tell sheet, which opened with the right address and total.

Not walked live: the send itself (this session was not allowed to press it; the page smoke sends a change order after a save against the recorder), a change order's save, options on the live page, **Publish to bid room**, and a failed read-back. Those stand on the tests.
