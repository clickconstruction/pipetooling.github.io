# v2.3036 — Test-gap audit, pass 46: the org's default Map view gets its first tests (2026-09-07)

Follow-up to v2.3035. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`mapDefaultViewSettings.ts` (138 lines) holds the org's default Map view — the centre, zoom and address the Map page opens on, set once in Settings by a dev: the stored JSON's validation, the `app_settings` read, upsert and delete, and the geocode-then-save flow through the `geocode-one` function. Three callers (the Settings block, the Map page and the office-address setting), no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- A stored view is accepted only when its latitude, longitude and zoom (4–18) are finite numbers in range and it carries a non-blank address label, which is trimmed; blanks, bad JSON, arrays and out-of-range values all read as "no view", and the historical Chicago fallback stays for callers with no row.
- Serialise and parse round-trip, and extra fields are dropped on the way out.
- The read looks the row up by its settings key and parses it; the upsert writes the serialised view under that key; the delete removes the key; a failed read or write throws.
- Saving from an address requires a non-blank address and a zoom in range before geocoding, geocodes the trimmed address, and saves the returned point with the typed label; a geocode refusal is translated with its detail, a transport failure and an unexpected payload each map to a message, and nothing is saved on any of them.
