# v2.4028 — Takeoffs and Materials: the lowest price is picked from every price on file (2026-09-28)

Client only; no migration, no edge function. The follow-up v2.4014 left under "Not in this PR": the reads of `material_part_prices` **across parts** that set no range. The cap class and its fixes: `docs/TROUBLESHOOTING.md` → "[row-cap]".

## What was wrong

PostgREST answers a read with no range with the first `max_rows` (1,000) rows and a 200. A part has one price row per supply house (`UNIQUE (part_id, supply_house_id)`), so a read by part id passes 1,000 rows at a few hundred parts. Three reads did:

| Read | Shape before | What a short read does |
| --- | --- | --- |
| `fetchLowestPartPricesBatch` (`src/lib/materialPartCatalogPrice.ts`) — the Takeoffs lowest-price map, `useTakeoffRoughLines`' fills and copies, `loadBundlePartLines` | one `.in('part_id', <every id>)`, no chunks, no order, no range | a part's lowest price row is past the cap: the line fills at a dearer price, or the part reads "No catalog price" |
| `fetchPricesForParts` (`src/lib/materials/partPrices.ts`) — Materials price lists | 500-id chunks, `.order('price')`, no range; the error ignored | a 500-part chunk at three supply houses is 1,500 rows: the dearest third of the rows is dropped, so parts lose supply houses |
| `loadBundleBreakdown` (`src/lib/bids/assemblyBundleBreakdown.ts`) — the bundle breakdown's à-la-carte totals | one `.in('part_id', <the assembly's parts>)`, no range; the error ignored | a supply house's total leaves parts out and its "missing" count is too high |

The third was found by the sweep this PR starts with (`grep -rn "from('material_part_prices')" src`); it was not on the list.

## The fix

- New `loadPartPriceRows(client, partIds, select, opts)` in [`src/lib/materials/partPrices.ts`](../../src/lib/materials/partPrices.ts), on `fetchAllRowsChunkedIn`: ids de-duplicated, `.in('part_id', chunk)` per chunk (150 unless told), a fresh query per page, `.order('id')` last, `.range(from, to)`. It throws on a page error. It is the one paged read of price rows across parts: `loadLowestPriceByPartId` (`assemblyItems.ts`, v2.4014) now calls it instead of holding its own copy of the query.
- `fetchLowestPartPricesBatch` calls it with `retry: true`: each **page** goes through `withSupabaseRetry` under the operation name it had (`fetch material part prices batch`), so a dropped connection re-reads that page and not the pages before it. It throws as it did, and on a failed later page it throws — it does not return a map of the pages that arrived. The pick is unchanged: lowest price, then lowest price id, whatever order the rows arrive in.
- `fetchPricesForParts` keeps its 500-id chunks (the v2.46 disk-IO wave) and pages inside each, ordered by price then id. It still never throws. A chunk whose read fails adds no prices, as before; that now holds for a failed second page too — the chunk is dropped whole, because its first page alone would give parts a price list with the cheapest rows and not the rest. Each part's prices are re-sorted ascending client-side, as before; rows at the same price now come in id order.
- `loadBundleBreakdown` reads its prices through the same loader. A failed read prices nothing, as before.

## Checked and left alone

- One part's prices (`.eq('part_id', id)`): `fetchLowestPartPrice`, `fetchPricesForPart`, `materialPOUtils.addExpandedPartsToPO` (`.limit(1)` per part), `PartPricesManager.loadPrices`, `TakeoffPartPricesModal`, `Materials.tsx` `loadAvailablePricesForPart` / `loadSupplyHouseOptionsForPart`.
- `useSupplyHouseEditor`: `.eq('supply_house_id', id).limit(1)` — an existence check.
- `partsCatalog.loadWholePartPricesCatalog`, `useSettingsBackupExports`: already paged.
- Writes by id (`PartFormModal`, `useSettingsCatalogs`, `Materials.tsx`).
- `material_parts` `.in('id', <an assembly's parts>)` in `loadBundleBreakdown` / `loadBundlePartLines` / `getTemplatePartsPreview`: one row per id, so it passes the cap only on an assembly of more than 1,000 parts. A different table; not in this PR.
