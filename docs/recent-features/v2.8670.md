# v2.8670 — The sign-in page can offer Continue with Google (2026-11-26)

Punch list #447, its sign-in page (piece 4), built the simple way the owner chose on 2026-11-26: no token hook and no per-person switch yet. Client only: no migration, no edge function. **Nothing shows until Google is switched on for the project in the Supabase dashboard**, which is a later step and the owner's.

## What was there

The sign-in page took an email and a password, and after two misses offered an emailed sign-in link. The project's Google provider is off.

## What changed

- **Continue with Google**, above the form, drawn only while the Auth server's public settings say Google is on (`GET /auth/v1/settings`, `external.google`). Unreadable settings read as off. So the provider switch in the dashboard is the company's switch: on shows the press, off takes it away, with no deploy.
- **The press** clears the caches, then calls `signInWithOAuth({ provider: 'google' })` with `prompt=select_account`. The page leaves for Google and loads again on the way back, so that load is the current build, as the hard reload after a password sign-in is.
- **It comes back to `/sign-in`**, carrying the address that was waiting (`googleRedirectTo`). Signed in, the sign-in route sends the person on, as it does for an emailed link. Refused, the page says why and takes the refusal out of the address.
- **The words** (`googleRefusalWords` in `src/lib/signInGoogle.ts`): no account behind that Google address (sign-ups are closed, so the Auth server refuses to make one), an account that is turned off, a sign-in stopped before it finished, and anything else in the server's own words.
- The client keeps the implicit flow, so the emailed links land as they did.

## Why this is enough to be safe

Every row rule reads the account's id and never how the session was opened. The Auth server links a Google sign-in to the one login whose address matches, so the id, the `users` row and the role are the same, and the password stays set. On 2026-11-26 that linking was seen for real on the shared project, on the same Auth version this project runs: a Google sign-in landed on an existing password account and made no second one. Sign-ups are closed here (`disable_signup`, and since the config fix of 2026-11-26 `supabase/config.toml` says so too), so a Google address that matches nobody gets no account.

## Not in this piece

The desk's *Ways in* row, removing a person's Google link, and taking that link off when a dev changes a person's address. They need a migration and are the next piece, and **Google should not be switched on before them**: until a link can be removed, an old Google account would keep opening a login after its address moved.
