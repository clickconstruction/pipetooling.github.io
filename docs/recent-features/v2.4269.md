# v2.4269 — A job's history shows when a payment was removed, not when it was added (2026-09-30)

Found on job 878 "Take 5- Seguin". Taunya applied a $13,680 Southern Post check on 9/21. It bounced, and she marked it returned on 9/24, which removed the payment. The history showed "Payment removed $13,680" at 9/21 15:06:44, the same instant as the add, so the 9/24 reversal was invisible. The cause: `jobs_ledger_payments_to_activity()` stamped both events with `coalesce(r.created_at, now())`, and on DELETE `r` is the old row. Migration only; no client change, no edge function.

## What shipped

- **Migration `20260930213000_payment_removed_when_removed.sql`** (`docs/migrations/20260930213000_payment_removed_when_removed.md`): a removal is stamped `now()`; an add keeps `created_at`. The removal's `(event_type, source_id)` dedupe is gone, and the add's dedupe now counts adds against removals, so a payment restored with the same id and removed again shows both times.
- **One-time correction**: 43 mis-dated removals on 28 jobs move to the payment's `deleted_records_archive.deleted_at`. On job 878 the $13,680 removal moves to 9/24 13:43:04. The 11 removals from before the archive began (2026-07-18) keep their stamp.
- **`npm run test:pg:payment-activity`**: a throwaway-Postgres bed (`supabase/tests/payment_activity/`) that reproduces the bug with the old body, then proves the correction, the new stamps, a restore, a same-transaction delete and re-insert, and the idempotent add.

## The $6,077.51 "phantom" removal

The second removal on job 878 (payment `241af1ce…`, added 9/29) was not a phantom. The payment was deleted at 2026-09-30 21:00:57 UTC and a new $6,077.51 payment from the same deposit was applied to job 650 "ATI Schertz" at 21:02:53: the check was moved to the right job. It looked instant only because of this bug. `apply_mercury_bank_payment_allocations` never deletes or re-inserts a payment, so there was no second code path to fix, and no removal event on prod points at a payment that still exists.

## Not run live

The migration was not run on prod before merge. The correction's predicate was counted read-only on prod (43 rows). Apply with `supabase db push` after merge.
