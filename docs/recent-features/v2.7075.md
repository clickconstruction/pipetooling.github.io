# v2.7075 — Materials on site: Add a part offers the names the job already has (2026-11-12)

Punch list #330, PR 2 of 5. The first site read had about a hundred typed part names and the same fitting under four spellings. The site's screen (v2.7074) folds only names whose words are the same, so the cheapest fold is the spelling that is never typed. This PR offers the names a job already holds at the two places a name is typed. No migration.

## What changed

- **The rules** (`src/lib/materials/onSiteNames.ts`), pure, 7 tests: `onHandNames` lists the names on hand in a job's live boxes, one per same-words key, as the spelling with the most pieces; `matchOnHandNames` offers a name when every word typed sits inside a word of it, both read through `sameWordsKey`, so `2 inch 90` finds `2" 90 pvc`, with the exact same words first; `onHandNameWords` says *94 in R12*.
- **The phone** (`AddPartSheet` in `TallyOnSiteTab.tsx`): as a person types, **Already on this job** lists up to six names above the parts book's hits, each with its count and boxes. A pick writes that exact name and id, so the new pieces land on the line the crew already counts. **Use “…” as typed** stays.
- **The office** (`JobsMaterialsTab.tsx`): the Part box of a delivery line carries the job's names as the browser's own suggestions.

## Where the build left the card

The card said *the names already on the site*. As built it is the names on **this job**: the phone holds one job's ledger, and reading the site's other jobs there would be more ledger reads on a phone in a metal building. On the first site read no part sat under two jobs.

## Checked

The kernel's tests and the phone sheet's render test: a typed plural finds the job's name, the pick adds to that line, and words no name holds offer nothing. Not walked on the live app, because adding a part writes a ledger row and prod is the only database.

Client only.
