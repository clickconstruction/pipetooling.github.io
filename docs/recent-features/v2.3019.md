# v2.3019 — Test-gap audit, pass 30: the person / user duplicate merger gets its first tests (2026-09-07)

Follow-up to v2.3018. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`mergePersonUserDuplicates.ts` (181 lines) finds the pay-config rows that name the same person twice — a roster person and a login sharing an email under different names, or a name and its role-suffixed twin like "Paige" and "Paige (Assistant)" — and merges one into the other: upsert the combined pay config under the login's name, delete the source row, cascade the rename through the pay tables, and rename the user. It runs from the People page and the Settings people directory. No test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- An email match is found from either side (the pay row under the person's name, or under the login's name), compared case-insensitively and trimmed, reported once per pair, and never when the two names already agree or no email links them.
- The role-suffix finder pairs a name with its `(Assistant | Master | Primary | Subcontractor | Estimator)` twin, shorter name first, once per pair; other parentheticals do not count.
- The merged row takes the login's values first and the person's as fallback, defaults when neither is configured, and carries the login's roster id when the roster resolves it uniquely; the source row is deleted by roster id when known, else by name; the cascade always runs; the user is renamed only when a user id is given.
- Blank or identical names are a no-op with no writes.
