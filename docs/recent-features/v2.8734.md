# v2.8734 — Messages: a search keeps its rows when a re-read behind it fails (2026-11-27)

Finding 323 of the fixing thread's ledger, from the simulator thread's second sitting of 2026-11-27, seen once: under Messages' search box a line read *The app was busy renewing your sign-in, so this did not load. Try again.*, and the search then found its rows. No card holds it. Client only. No migration, no edge function. Nothing owed after the merge.

**Read.** The search reads nothing itself. Its hits are worked out from the view the page already holds (`searchLines(host.view.messages, …)`). `useMessagesHost` keeps the view from the read before when a re-read fails, and sets `problem`. The search list let the problem win: with a problem it drew the problem where the hits go, though the held view could still be searched.

**The mend.** A kernel in `src/lib/messages/searchLines.ts`, `searchListShows(found, problem)`, says what the list draws. A failed read is the list's news only when no view is held. With a view held, the hits draw, or *No message has those words.* `Messages.tsx` reads it.

**The three other places the page hands `host.problem` down, read and left alone.**

- The people list, twice (`GcMessages`): it draws the problem only when it holds no view. With a view it draws its rows.
- The thread window (`ThreadWindow`): it draws the problem only when the person is not in the view it holds. With the person there it draws the thread.

So the search list was the one place a failed re-read covered rows already held.

**What this may not be.** The walk called the line red and met it right after the box took focus. The search list's line is grey, and it draws only once two letters are typed. On the Follow up pill, the queue's own panel stands directly under the box until then, and a failed re-read of the queue draws a red line there with the same words (`FollowUpPanel.tsx`, the `role="alert"` line over rows already drawn). That may be the line that was seen. It is not changed here. It belongs with the older finding that a stolen sign-in lock says *Try again* and offers nothing to press.

**Tests.** `searchLines.test.ts`: the kernel's six answers. `Messages.render.test.tsx`: a search holds its hits, the page reads again and that read fails, and the hits stay with no failure words in the list; and a first read that fails, with no view held, says so where the hits go, as before. The first case fails on the old condition.

**To see it live.** It cannot be staged by a press: it needs a re-read to fail while a search is open. Read the tests. If a walk meets the line again, it says its colour and whether two letters were typed yet.
