# v2.3630 — Submittal robot: either seat can take a task; a held read_schedule task opens the bid's plans (2026-09-19)

The submittal robot (v2.3544) was written for "estimator or pricer keys" — the brief ([`docs/twins/submittals.md`](../twins/submittals.md)), the tool descriptions and the v2.3544 fragment all say so — but two fences said otherwise. Two edge functions + one shared kernel; no migration, no client change.

## What was wrong

1. **The seat gate refused a pricer the four verbs.** `callTool` refuses a `twin_kind = 'pricer'` key any verb outside `PRICER_VERBS` / `SHARED_VERBS`; `get_submittal_guide`, `next_submittal_task`, `put_submittal_result` and `finish_submittal_task` were in neither.
2. **`read_schedule` could not read the plans — for either seat.** The task tells the robot to read with `get_plan_pages`, which (like `plan-fetch`, the door it fetches through) is fenced to bids the twin created or is assigned. A submittal is asked on the office's bid, which a person owns: a pricer owns no bids at all, and a bid robot owns only its shells. `file_cut_sheets` and `read_redlines` ride a signed link in the task and were unaffected.

## The change

- [`_shared/twinSeatGate.ts`](../../supabase/functions/_shared/twinSeatGate.ts) (new kernel): the verb sets (`PRICER_VERBS`, `SHARED_VERBS`, new `SUBMITTAL_VERBS`, `PRICER_TASK_FENCED_VERBS` = `get_plan_pages`), `seatGate(kind, verb)` → ok, or refused as `bid_verb` / `pricer_verb`, `pricerVerbList()` for the refusal message, and `twinMayReadPlans(twinUserId, bid, tasks)` — own/assigned, or a task on that bid that is `read_schedule`, `working` and claimed by this twin (`holdsPlanReadingTask`; the mirror of `pricerMayTouchBid`). A file kind, another twin's claim, another bid, or a task that has left `working` opens nothing.
- [`twin-mcp`](../../supabase/functions/twin-mcp/index.ts): the gate at the top of `callTool` is `seatGate`; the sets moved to the kernel. `get_plan_pages` fences with `twinMayReadPlans` over the twin's working tasks on the bid (`heldSubmittalTasks`). A pricer passes the gate for `get_plan_pages` only so that fence can decide — every other bid verb, `stage_plan_pdf` included, stays refused. The `read_schedule` task's `next` line names `get_plan_pages` alone. `serverInfo.version` 1.4.1 → **1.4.2** (it was not bumped for the submittal verbs).
- [`plan-fetch`](../../supabase/functions/plan-fetch/index.ts): the twin fence on a bid's plan set is the same `twinMayReadPlans` — `get_plan_pages` fetches through this door with the twin's token, so opening one without the other would still answer 403. The quote-source and probe paths are untouched.
- Brief `docs/twins/submittals.md` (→ `briefs.ts`): the `read_schedule` row names `get_plan_pages` and says the task opens the plans.

## Tests

`src/lib/twins/twinSeatGate.test.ts` (+7): the four verbs answer to either seat; shared verbs to both, pricing verbs to the pricer only; a pricer is still refused the bid verbs (`stage_plan_pdf`, `mint_session`, `paste_counts`, …) with `get_plan_pages` the one door; the pricer's verb list has no duplicates and every entry passes; plans open on an own/assigned bid with no task; only a working `read_schedule` task claimed by this twin on this bid opens another; the opening task is found among others.

## Deploy

`supabase functions deploy twin-mcp` and `supabase functions deploy plan-fetch` after merge — plan-fetch first is harmless (the fence only widens), twin-mcp alone would leave `get_plan_pages` answering plan-fetch's 403.
