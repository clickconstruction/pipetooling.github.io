# v2.6056 — Where files go: the settings and the kernel (punch list #211, PR 1) (2026-10-29)

Punch list #211, the owner's ask of 2026-10-29 once the app began making a job's Drive folders (#209, v2.6054): a Documents page where the office sets where folders are made and how they are named. The mock-up (`to-dos/where-files-go/mockup.html`, PR #6422) drew a third tab, **Where files go**, with three cards and two presses; the owner picked it. This is the first of three PRs: the settings, the pure kernel and the function verbs. The tab itself is PR 2; the bids' folder by the same pattern and the as-needed choice in the press are PR 3.

## What changed

- **Four `app_settings` keys** in `src/lib/appSettingsKeys.ts`: `drive_jobs_root_folder_id` (the root's Drive folder id; empty = the functions' `DRIVE_JOBS_FOLDER_ID` env), `drive_job_folder_pattern` and `drive_bid_folder_pattern` (JSON lists of pieces in order: a job's `number`, `name`, `customer`, `address`, `year`, shipping as `["number","name"]`; a bid's `project`, `number`, `customer`, `address`, `year`, shipping as `["project"]`), `drive_folders_made` (`upfront` or `as-needed`, shipping as upfront). No migration: the rows are written by the function below with the service role, so the office writes them without a key-scoped policy. The edge copy of the keys (`_shared/gcKernels/lib/appSettingsKeys.ts`) is regenerated; six functions bundle it through the kernels' copy (`bridge-weekly-sheet`, `customer-portal`, `drive-link`, `gc-trade-portal`, `messages-nudge-dispatch`, `photo-save`) and are redeployed with nothing that behaves differently.
- **The kernel** `supabase/functions/_shared/whereFilesGo.ts`, with no imports, re-exported by `src/lib/documents/folderName.ts` and tested by `folderName.test.ts`: `folderName(pattern, job)` (the pieces in order, each Drive-safe as v2.6054's press cleaned them, an empty piece skipped, joined by ` · `, capped at 120, `Job <id>` when every piece is empty), `bidFolderName`, the parsers (`parseJobFolderPattern`, `parseBidFolderPattern`, `parseFoldersMade`, each falling back on anything it cannot read), `driveSettingsFromRows` (the setting's root first, the env's second, and which), `driveFolderIdFromLinkOrId`, the fixed tree `JOB_FOLDER_TREE`, and `writeCheckWords`: *The app can write here.* or Drive's refusal naming the account to share with, the same words on the root card, on a job's folder and in the sweep's reason. The test holds the kernel's four key strings equal to the app's constants.
- **The reader** `supabase/functions/_shared/driveSettings.ts`: `readDriveSettings` / `jobsRootFolderId` through the service client, and `checkFolderWrite`: Drive's `capabilities.canAddChildren` on the folder (the reading v2.6054's `writable` and the photo sweep's 403 agree on; nothing is written by the check) with the folder's name, its path from the Shared Drive down, its owner or Shared Drive, and the count of folders inside.
- **Every maker reads the root there**: `job-drive-folders`, `drive-intake`, `gc-drive-access`, `file-submittal-package` and `submit-gc-trade-portal` (a trade's certificate) make their folders under the office's root, the env while the setting is empty; `drive-contract-scan` scans both roots when they differ, since a moved root leaves the older job folders behind. A maker with no root anywhere answers *The jobs root is not set yet. Set it on Documents → Where files go.* (503).
- **Three verbs on `job-drive-folders`** (`docs/EDGE_FUNCTIONS.md`): `{ check: { folder } }` runs the write check on a link or id; `{ settings: true }` answers the four settings, where the root came from and its live check; `{ set: { root?, job_pattern?, bid_pattern?, folders_made? } }` saves what is given, a new root only after the check passes (409 `root_unwritable` otherwise), the four office roles without the estimator. The press names the job's folder by the pattern (`customer_name`, `job_address` and the year of `created_at` in the app's calendar are the new pieces it reads).

## Decisions

- **The settings are written through the function, not a policy.** `app_settings` is dev-managed with key-scoped UPDATE policies per setting; the office (assistant, controller, master) would have needed a new policy and a migration. The function already validates the office roles and holds the service client, and writing there lets a new root be refused before it is saved. No migration.
- **The check is Drive's own answer, not a probe file.** Making and deleting a probe folder in a Shared Drive leaves a trashed item the service account cannot purge (content managers trash, only managers delete). `canAddChildren` is what caught job 972's hand-made folder in v2.6054, so the check and the press agree.
- **The names do not change for a job that has a folder.** The default pattern spells the same name v2.6054 made, with the same cleaning, so a second press finds the first press's folder; a changed pattern applies to folders made from then on, and nothing is moved or renamed.
- **A bid's pattern is stored now and honored in PR 3**, so the tab can show and save it with the job's; `drive-intake` keeps naming by `project_name` until then, which the default pattern equals.
