# v2.5458 — Messages: photos that come in go to the job's photos in Drive (2026-10-13)

Messages, cut 10's last item (GC Mode helper 2, directed by the lead session GC MODE): photos saved on arrival to the
job's photos, with the file agent copying and naming. This is PR 3 of five. It stacks on PR 1, the kernels (v2.5456,
#5625). It reads PR 2's table (v2.5457, #5626, migration `20261014070000_photo_saves.sql`).

- **`supabase/functions/_shared/driveJobFolder.ts`**, a job's Drive folder.
  - `jobFolder`, `childFolder`, `landingFolder` and `driveGet` are lifted word for word from drive-link, so the office's
    door and the sweep share one implementation (the lead's yes, 2026-10-13).
  - New: `photoFolderFor(job)`, the folder a job's photos land in, made as needed.
  - New: `freeName`, the first name the folder does not hold yet.
- **`_shared/driveLink.ts`**, the landing rule: `photoLanding(job, picturesFolderId)`.
  - A Pipeline job's photo goes to its own Customer Pictures folder (`jobs_ledger.job_pictures_link`) when that link is
    plainly a Drive folder (`driveFolderIdFromUrl`).
  - Anything else goes to Team only → Photos under the job's folder, which is `google_drive_link` for a Pipeline job
    (the lead, 2026-10-13).
  - `isImageFile` names the picture test `saveHalfFor` already made.
- **`drive-link`'s save**: a photo now goes to the job's photos instead of Team only → From email, named by day,
  sender and caption (`photoDriveName`, v2.5456). Any other file saves as before.
- **`photo-save`**, a new function: the file agent's sweep, on a cron with `X-Cron-Secret`.
  - It reads the ticks that are on (`photo_saves`), and for each the files that came in on its lines since the tick
    went on, kept by us and not in Drive.
  - `photosToSave` picks them, 20 a run, oldest first.
  - Each is uploaded to `photoFolderFor` under `photoDriveName`. The row keeps `drive_file_id`, written only where no
    save got there first.
  - A failure is said per file and tried again next run.
  - Its `cron.schedule` (every 5 minutes) rides its own migration after the lead deploys it.
- **`src/lib/photos/photoRows.ts`**, the sweep's read as the kernels take it.
  - `PHOTO_ROWS_SELECT` (each file with its line) and `PHOTO_SWITCHES_SELECT`.
  - `photoRowOf` and `photoNameInputOf`. An email's subject names a photo better than its body.
  - `senderOf` takes *Greg Paulk* from an email's *Greg Paulk <greg@…> to bids@*.
- **The edge copy** (`_shared/gcKernels/`, regenerated) takes the photo kernels, now 66 files. `photoName.ts` reads the
  day from `utils/dateUtils` (`calendarYmdInAppTzFromIso`) in place of `messages/thread.ts`'s `chicagoDay`: since #5537
  `thread.ts` imports types from `lineFiles.ts`, a file that runs code, which the copy refuses.
  - Its importers are `customer-portal`, `drive-link`, `gc-trade-portal`, `gmail-sync` and `photo-save`.
  - On a rebase conflict in the copy, regenerate with `npm run gen:edge-kernels`.
- **Deploys, the lead's**: `drive-link`, `photo-save` and `dev-mcp`, whose regenerated catalog
  (`supabase/functions/dev-mcp/catalog.ts`) names photo-save. Then the cron's migration. `config.toml` keeps photo-save's
  `verify_jwt = false`.
- **Docs**: `EDGE_FUNCTIONS.md` gains photo-save's section and TOC line, drive-link's save and status, and the copy's
  counts and importers.
