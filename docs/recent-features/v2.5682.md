# v2.5682 — Bids: taking the GC off hands the bid to the alternate (2026-10-20)

Wendi's report, punch list #136 (`to-dos/auto-promote-alternate-gc/`): "when taking the primary GC
off of a project in bids, I would like it to auto select the alternate GC as the primary." The
owner took the proposal's five defaults as written.

**The hazard underneath the ask:** four stores key "the bid's own GC" as `customer_id NULL`
(`bid_versions`, `bid_gcs`, `bid_proposal_rooms`; whole-bid notes via
`bids_submission_entries.gc_customer_id`), so a bare `bids.customer_id` swap — all change ▸ did —
silently re-attributed the departing GC's sent letters, dues and rooms to the new GC, and an
alternate picked as the new primary kept its stale recipient card.

- **Migration `20261020100000_promote_bid_gc.sql`** — RPC `promote_bid_gc(p_bid_id, p_new_gc_id,
  p_old_gc_stays)`, SECURITY INVOKER (RLS applies; the bids UPDATE runs first so a write fence
  rolls back the whole call). Atomically: own-GC versions **with a send** re-key to the departing
  GC (unsent drafts are the project's estimate and stay with the bid); the stepping-up GC's
  explicit rows become the bid's NULL-keyed rows (`bid_versions`, `bid_gcs` with a wholesale-merge
  when both rows exist, `bid_proposal_rooms` minding the partial unique open-room indexes — a
  leftover open own-room that cannot move closes rather than pass to the new GC); recipients fix
  up (the promoted GC's row deletes — the duplicate-card bug — and the departing GC gets a
  `version`/`manual` row when it stays or its packet keeps it visible); a fully-departed GC's
  `bid_gcs` row deletes so its due stops steering the bid's derived due (`recompute_bid_due` runs
  last); a **method-less whole-bid note** records the handoff, so last-contact does not move.
- **Edit Bid** (`BidFormModal`): the ★ Bid's GC card gains **×** (only while another GC is on the
  bid, same `canEdit` roles); the confirm (`PromoteBidGcModal`) names the successor, asks who
  steps up when 2+ alternates (recommended pick preselected: own-packet GC with the latest send —
  `recommendedSuccessor`), and offers **Keep as an alternate instead**. Alternate cards gain
  **make bid's GC ▸** (`BidGcRecipientsRow` `onMakePrimary`; old GC stays). The change ▸ dropdown
  leads with an **On this bid** group (one press, routed through the RPC; those GCs leave the
  all-customers list), and an outside pick or ＋ Add-new-customer in edit mode also routes through
  the RPC. On a saved bid, typing in the GC search no longer clears `gcCustomerId` — autosave
  could write `customer_id NULL` mid-search.
- **Kernel `promoteBidGc.ts`** (`canTakeOffBidGc`, `recommendedSuccessor`,
  `latestSendByGcFromVersions`, `promoteConfirmCopy`) with unit tests;
  `PromoteBidGcModal.render.test.tsx` smoke. Migration smoke-tested on a throwaway Postgres 15
  (idempotent; both the sent-packet handoff and the unsent full take-off scenarios asserted).
- **Docs**: help guide `bid-one-project-to-multiple-gcs` gains "When the lead GC drops out";
  `docs/migrations/20261020100000_promote_bid_gc.md`; PROJECT_DOCUMENTATION People-section line.

Deploy order: migration pushes first (a new RPC is invisible to old clients), client after.
Known corner, accepted in the to-do: a legacy builder-label primary has no customer id, so its
NULL-keyed state cannot re-key — its `bid_gcs` row drops and its open room closes rather than
pass to the new GC, and "Keep as an alternate" is not offered.
