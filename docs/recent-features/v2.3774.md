# v2.3774 — The Bank payments combo-chip smoke stops flaking under load (2026-09-23)

Test-only. One `.render.test.tsx`, no source change, no migration, no user-facing surface. Sister of [v2.3551](v2.3551.md), which fixed the close-out smoke in the same modal.

## Why

`src/components/jobs/BankPaymentsModalCombo.render.test.tsx` failed once in a full `npm test` run on 2026-09-23, on a branch that only touched estimates and job naming:

```
Unable to find role="button" and name /Fill 2 allocations: \$2,711\.50 915 \+ \$1,380\.00 880/
```

It then passed twice alone. A check that reddens on unrelated work gets ignored, which is how a real regression slips through.

## What it was — not what it looked like

The obvious diagnosis is a synchronous `getByRole` reading a render that has not happened yet, the v2.3551 shape. That is **not** this one: the chip lookup was already `await screen.findByRole(…)`. What expired was testing-library's **1 s default window** on that `findByRole`.

The chip is the end of a chain of mocked awaits inside `BankPaymentsModal`: the sorting-config fetch resolves → the deposit-list RPC resolves → the first deposit is selected → the exact bill combo is computed → `ArPayerMatches` paints the chip. On top of that, a role query with a regex name computes an accessible name for every button in the 2,000-line modal on every 50 ms poll. Measured on the 14-core machine:

| Condition | Test duration |
|---|---|
| file alone, 3 runs | 114–118 ms |
| file looped 25× while a full suite ran beside it | 115–473 ms |

Four-fold slowdown from one full suite's load; the failing run had the whole suite's transform + collect burst competing for the same cores, and 1 s was not enough. The link-guard smoke in the same modal (`BankPaymentsModalLinkGuard.render.test.tsx`) had already hit this in v2.3382 and waits 4 s for the same reason.

## The fix

One constant, `LOADED_SUITE_TIMEOUT_MS = 4000`, on both waits in the file: the chip's `findByRole` and the `waitFor` for the two allocation lines after the tap. **No assertion was weakened** — the chip still has to carry the exact accessible name, the two dollar totals, the "fills 2 allocation lines" hint, and the tap still has to produce exactly two lines with the right amounts and remove the chip. The file's header records the rule so the next case added here waits the same way.

## Verified

- The file alone, and looped 25× under a concurrent full suite: green every run before the change too (the flake needs a heavier moment than one full suite provides on 14 cores), and green every run after.
- The **full suite twice in a row** after the change, with the worktree given the `.env.local` the main checkout has (without it 67 files fail at import on the missing Supabase env pair, which is why the first load run here reported 102 failed files — none of them tests).
- Typecheck, lint, theme check clean.
