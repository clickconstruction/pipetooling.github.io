# v2.4121 — Walk me through it: the page scrolls under the tour (2026-09-29)

The owner, on Bids → Submittals: the walkthrough would not let the user scroll, and half the stages sat below the screen where they could not be reached.

**Cause.** `SpotlightTour` (v2.2021) dims the page with a `position: fixed; inset: 0` overlay. The app-wide body scroll lock (v2.2186, `BodyScrollLockSentinel` over `findBlockingOverlays`) treats any viewport-covering fixed layer as a modal and pins the body (`position: fixed; top: -<scrollY>px`). Pinned, the tour's own `scrollIntoView` on each stop's anchor moved nothing, and a wheel or a touch drag did nothing either — reproduced on BP398 from the dev server: `body` read `overflow: hidden; position: fixed; top: -88px`, no scrollable ancestor above the anchor, `scrollY` unchanged after a wheel. Every tour built on the component since 2026-08-23 (Pricing Workbench, Submittals v2.4067) walked its stops without the page following.

**Fix.** The overlay carries `data-page-scroll="allow"` — the lock's own opt-out valve — so the body stays free: each stop scrolls its anchor to the center as designed, and the wheel or a finger scrolls the page under the dim. Clicks on the page are still held by the overlay (a click on the dim closes the tour, as before).

**Tests.** New `SpotlightTour.render.test.tsx`: with every rect stubbed to the full viewport, `findBlockingOverlays` returns nothing for the rendered tour and returns the overlay once the attribute is removed — the attribute is the fix; plus Next/Back and the missing-anchor line.
