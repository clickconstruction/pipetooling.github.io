# v2.3229 — The dispatcher hands back a shell whose plans ask was answered "Attached — rerun", so the tap alone is enough (2026-09-10)

Migration `20260910123000_twin_question_acted_at.sql` (one nullable column); edge function `twin-mcp` v1.3.17 (redeploy).

## Why

v2.3223 made *Attached — rerun* on the robot needs sheet stamp the bid robot-requested, but `next_shadow` never hands out a bid that already has a shell, so the rerun still depended on the robot remembering to read `get_answers` and resume its own shell. Now the dispatcher does the remembering.

## What shipped

- **`next_shadow` resumes first** (`twin-mcp` v1.3.17): before any new claim it reads this twin's answered, un-acted questions (`twin_questions.acted_at IS NULL`, oldest answer first). A **plans** ask whose answer says rerun is resolved to the twin's shell — the ask's bid when that is the shell, else the twin's shell for that human bid — and, if the shell's run is still `open`, handed back as the run with `resumed: true`, the reference's current `plans_link`, the question and the answer, plus a `[pipeline STG-0 resume]` note on the shell's ledger. Every answered ask it reads is stamped `acted_at`, so a shell comes back once per answer; a non-rerun answer, a locked/scored/void shell, or no shell is consumed with nothing to resume. Best-effort: any error, including the column not yet applied, falls through to a normal claim.
- **Migration**: `twin_questions.acted_at timestamptz`, comment. Edge-only writes.
- **Docs**: the bid skill and the Desktop kickoff now say the dispatcher hands the shell back (resume from STG-2 as if freshly claimed); `EDGE_FUNCTIONS.md` paragraph; migration fragment; `database.ts` hand-adds the column.
