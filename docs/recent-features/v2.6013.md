# v2.6013 — The lens seals the frames a sealed screen opens inside it (2026-10-28)

Punch list #202, out of the live check of What everyone sees (#194). The seal (`src/lib/lens/seal.ts`) swapped storage, network, channels and sensors in the one window the lens named and in a tab opened from it, but not in a frame the screen itself put inside the page. What customers see is such a screen: its previews are nested iframes of the real app, and inside a sealed frame they ran on the origin's real storage, where the dev's session lives.

## The check

A development-mode build served by `vite preview` (`NODE_ENV=development vite build --mode development --outDir <dir>`, the service-worker files removed; the dev server cannot run 28 nested frames of ~1,000 modules each, Chrome gives `net::ERR_INSUFFICIENT_RESOURCES`), signed in through `dev-login`, Who → Dev, Where → What customers see, each preview scrolled into view inside the sealed frame. `performance.getEntriesByType('resource')` saw none of it: the 250-entry buffer fills with chunks before any Supabase call, so a `fetch` / `WebSocket` / `XMLHttpRequest` probe went onto each nested frame's initial window before it loaded (Chrome keeps that window for the first same-origin navigation).

Before the fix, all 28 page previews ran unsealed with the dev's real session in their storage, and each read `users` (7–104 times, every sibling's SIGNED_IN broadcast refetching the role row), `app_settings` and `service_types` with it; the signed contract preview called `list_my_contract_dashboard_prompts` 92 times; the two submittal previews and the trade partner's portal sent the real token to `get-submittal-room` and `gc-trade-portal`. The other sample functions were called on the anon key, as the headless check of 2026-10-27 had seen. No socket, no XHR. The full table is in the session notes.

## What changed

- **The seal names the frames a sealed window creates** (`installSeal`): `Element.prototype.setAttribute` and the `src` setter of `HTMLIFrameElement.prototype` give every same-origin `iframe` without a lens name the frame's own name with a fresh nonce the moment its address is set, which React does before inserting the element, so it boots sealed on that frame's memory and world. Chrome reads an iframe's name only as the frame is made (a name set on an inserted frame leaves `window.name` empty, which the first re-check showed on all 28 previews), so a frame that is already in the document when it gets its address, or arrives parsed with one (a `MutationObserver` on added nodes), is taken out and put back in its place under the name. A frame of another origin, or one drawn from `srcdoc` (the email and paper previews, sandboxed), is left alone.
- **A customer's sample page answers from the network** (`src/lib/lens/samplePage.ts`, `isSamplePage` / `isSampleToken`, pure): when the sealed frame's own address names a sample token (`?t=sample…`, `/pay/sample`, `/q/sample-done`, `/t/sample`), the seal hands the engine the real fetch as its `network` option, and the engine sends every `/functions/v1` call out whole with the anon key in place of whatever token the page put on it (`staffAwarePublicHeaders` would have sent the frame's invented session), reporting it as an ask answered by `network`. Chosen over having the world answer each sample function: the edge functions lay the fixture over today's Settings, which the world cannot reproduce without duplicating ten of them. The database, sign-in, files and every function on any other page stay in the world, and the state knob still rules the sample page (offline fails it, loading hangs it).
- **The lens's own customer frames** (Who, outside) are unchanged: unsealed on their sample tokens, `config: null`.
- `LensRequest.raw` carries the call as the page made it; `AskSummary.network` and the tab's count line ("N from the sample's own function").
- **Tests**: `seal.test.ts` (+2: the naming hook on added, srcdoc, cross-origin and late-`src` frames; the `network` option on a sample page alone, with `raw`), `lensEngine.network.test.ts` (+3: the pass-through's headers, method and body; the world on any other page; the state knob), `samplePage.test.ts` (+3, pinned to the fixture's tokens and every page What customers see previews), `sealFirst.test.ts` admits `samplePage` to the seal's imports, `lensTab.test.ts` counts `network`.
- **Docs**: the Glossary's *The lens's sealed frame*, the sealed-frame note in `ACCESS_CONTROL.md`, the guide *see every screen as every role*; the to-do deleted.

## Checked after the fix

The same check on the fixed build: every nested preview boots under a `pipetooling-lens:` name with `__lens` set, its storage holds the invented dev's session only, no frame makes a `/rest/v1/` or `/auth/v1/` request, each sample page's function call goes out once on the anon key, and every preview draws its sample.
