# v2.2464 — Bill Customer cancel-leak: a minted auto draft un-mints on close (2026-08-28)

Follow-up to v2.2446 (Taunya, job 978). The remaining door the confusing full-remainder "auto"
draft came through: **opening** Bill Customer with `kind:'job'` runs
`ensure_single_ready_to_bill_invoice_for_job`, which INSERTs the primary Ready-to-Bill remainder
bundle when absent — and cancelling the modal left that row behind permanently. That is how the
$3,630 auto draft got planted on job 978 before anyone billed anything.

**Design: delete-on-cancel, not defer-create.** Deferring the INSERT to submit time would cut
through the billing-target engine that all three channels (Stripe / HouseCall Pro / Physical) and
the Stripe preview read (`SEND_RECORD_INVOICE_MODAL_ARCHITECTURE.md` rates that region high-risk).
Instead the modal remembers when THIS open **minted** the row — the ensure RPC already reports
`created: true` — and on close deletes it again via the existing `delete_ready_to_bill_invoice`
RPC. No migration.

**The untouched-check** (new kernel `src/lib/jobs/mintedPrimaryDraftCleanup.ts`,
`isMintedPrimaryDraftStillUntouched`, unit-tested): before deleting, the row is re-fetched and
must still be a `ready_to_bill` primary with blank `stripe_invoice_id`, `stripe_invoice_status`,
`hosted_invoice_url`, `sent_to_customer_at`, `billed_at`, `external_send_channel`, and all four
`bill_to_*` fields, with zero `jobs_ledger_payments` referencing it. One check at close time
covers every success/mutation path without touching the three submit engines; on any doubt
(fetch error, payment-count error, any field set) the row is kept — a kept draft resizes or
deletes on the next remainder resync anyway.

**Wiring** (`SendRecordInvoiceModal.tsx`): `mintedPrimaryDraftRef` records
`{jobId, invoiceId}` when the ensure parse sees `created: true` (recorded BEFORE the
`cancelled` bail-out — the row exists server-side even if the effect run was cancelled, and that
path triggers an immediate cleanup for close-during-ensure). Cleanup fires on `open → false`, on
unmount (provider teardown / route change), and when the payload swaps to a different job while
open. `openJobIdRef` guards the fast close→reopen-same-job race: the reopen's ensure reuses the
same row (`created: false`), so a late cleanup from the first open must not delete it — the guard
bails while the modal is open for that job (the sync effect clears the ref in its cleanup,
declared before the unmount effect, so unmount cleanup still runs). After a successful delete the
opener's `onAfterEnsureSuccess` callback re-fires so lists drop the row.

Docs: BILLING_FLOWS ensure-keystone note + Open-Bill-Customer side-effect row updated;
architecture map notes the guard in the billing-target engine dossier.
