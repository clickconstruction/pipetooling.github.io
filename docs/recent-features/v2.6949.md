# v2.6949 — Small edits inside a section: the dev seat adds a line under a heading or swaps one run of text (2026-11-11)

Found 2026-11-11 by a session keeping notes in a long shared document. It had to put one new line on top of a "newest first" log and change one sentence in another section. The only way was `replace_section`, which meant sending each section whole, twice (once to plan, once to apply), most of it other sessions' words. A slip in the retyping would have been silent, because the plan's removed and added view is capped and only its character total could be checked. Other sessions were saving the same document minutes apart, and each collision meant reading and resending the section again. Nothing from that document is in this change: the tests run on a made-up one.

## What changed

- **Two more ops** on `plan_person_doc` → `apply_person_doc` and `plan_matter_narrative` → `apply_matter_narrative`, beside `replace_section`, `insert_after` and `append`, under the same rules (at most 20 ops a call, in order, each against the text the one before it left):
  - `prepend_section { heading, markdown }` sets new lines straight under the heading, above the section's first line of words. The blank line under the heading stays where it is, and a section stored with none keeps none. Markdown that ends with an empty line leaves one blank line between the new lines and the old; without it the new lines sit on the old ones, as a list wants. A heading with nothing under it takes the lines as its section.
  - `replace_text { heading, find, replace }` swaps one exact run of text inside the named section (its subsections included, its heading line not). It is refused, in words that name the count, when the run occurs 0 times there (the words say where else in the document it stands) or more than once (the words name the lines). Overlapping reads count, `''` as `replace` takes the run out, and a run may cross a line break.
- **Where it is worked out.** The section grammar is plpgsql: `hr_doc_apply_ops` (20261107100000) for the matter's narrative and an inlined copy in `dev_person_doc_write` (20261108193000). Neither is touched and there is no migration. `_shared/devMcpDocEdits.ts` (new, pure) handles a call that carries a small edit in the function: `prepareDocEdits` reads the text and its stamp with one GET as the dev (`person_documents`, `person_files` or `legal_matters`), `applyDocOps` applies every op of the call (the three section ops ported with the database's own joins, so a mixed call works), and the arguments go on to the same RPC as the whole `markdown` with `expect_updated_at` set to the stamp just read. A call with no small edit travels as before.
- **The rules that stay.** The plan hash covers the payload, now the whole text and the stamp, and the RPC's reply with the document's `updated_at`: a save by anyone between plan and apply changes both, and the apply is refused. The RPC itself refuses a save that lands between the function's read and its write, through `expect_updated_at`. The caller's own `expect_updated_at` still refuses a stale plan, the dev is still the author, and the prior version is still archived.
- **The plan.** `changes` holds one line an op, in order. `prepend_section`: the heading, `at_line`, `added_lines`, `added` whole and `above`, the line it now sits on. `replace_text`: the heading, `line`, `removed` and `added` whole with their lengths, and `reads`, the line as it reads after. The section ops keep the database's 6,000-character cap. `worked_out` says the text was read on the server and at which stamp.
- **The extra line break `replace_section` added.** The op writes one blank line under the heading and one before the next heading, and trims only the end of the markdown it is sent. The lines under a heading, copied from a section as `get_person_document` reads it, start with the blank line under that heading, so the op wrote two: one line and one character more than the edit. The join is in SQL and is left alone; `writeRpcBody` now drops the empty lines at the head of a section op's markdown (`sectionOpsForRpc`), so a section sent back as it was read lands exactly. Two cases stay with the SQL join: a section stored without a blank line under its heading or before the next heading still gains them on a `replace_section`, and the last section of a document that ends with a line break loses that one break (one character and one line fewer; found in the live check below). The two small edits never change a section's framing.
- **`supabase/functions/dev-mcp/index.ts`**: server 0.69.0; the two planners' descriptions and schemas name the ops; the server's instructions say a document can be edited by a line or a run of text.
- **Docs**: the two rows in `docs/dev-mcp/README.md`, `docs/HR_FILES.md`'s line on the documents' door, `docs/EDGE_FUNCTIONS.md` → dev-mcp.

## Live check (2026-11-11, server 0.69.0, plans only, nothing applied)

On two made-up documents of a ZZ test person. `prepend_section` on the last section of a 177,592-character document: 47 characters sent, the plan reads 177,640 characters and one line more, `at_line` under the heading's blank line. `replace_text` on a 307-character note: a 32-character run for a 42-character one, the plan reads 317 characters and the same 12 lines. A run that stands three times in the section is refused with the count. Both ops in one call: the totals move by the two edits alone. `replace_section` with a middle section sent back as read is refused as *nothing changes*; with the last section it drops the document's final line break, the case named above.

## Not in this change

`plan_matter_document` takes no ops and is unchanged. Making `replace_section` keep a section's stored framing would be a change to the two SQL functions, which is a migration of its own.
