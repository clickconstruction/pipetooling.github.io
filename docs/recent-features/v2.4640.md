# v2.4640 — Legal portal: every act from the firm carries a date and a name (2026-10-05)

Punch list #85, item 18, PR 1 of 2 (lane D). Four of the five things a firm needs before it records its billing in someone else's system. No migration; PR 2 adds the void (undo with a reason) and the unique index behind the one-time key.

## What changed

- **The guards in one shared kernel**: `supabase/functions/_shared/legalPortalActs.ts` — `legalActDateProblem`, `isLegalClientId`, `LEGAL_ACTS_PER_MATTER_PER_HOUR` (60), `legalRateLimitMessage`, `recordedByOf`. `submit-legal-portal` and the tests read it.
- **(c) A date the firm sets.** The fee, step and payment forms carry a date field (today by default, never after today). `submit-legal-portal` already stored `occurredOn`; it now refuses a date in the future or more than three years back, with a message.
- **(b) Recorded by.** A *Recorded by* picker above the firm's acts lists the people on the firm's Notifications page (`legal_firm_recipients`); the pick is remembered in that browser (`localStorage`, try/catch, falls back to *the firm*). Every matter act sends `recordedById`; the function checks it is a live person on that firm's list and stores `meta.recordedBy = { id, name }`. The firm's and the desk's fee and step tables gain a *By* column (`entryRecordedByWords`), and the conversation names the person (*Dana Reyes asked*, *Dana Reyes at the firm asked*).
- **(d) One save per act.** The page sends a `clientId` (a uuid) with every matter act and keeps it until the act saves, so a retry after a dropped connection reuses it. The function answers an existing entry with the same `meta.clientId` with `{ ok, entryId, duplicate: true }` and writes nothing. A same-instant race still gets through until PR 2's unique index.
- **(e) A per-matter limit.** 60 portal acts per matter per hour (30 per firm before). The refusal names the matter and the time the limit lifts, in the company's zone.
- Docs: the guide *share your attorney their portal*, EDGE_FUNCTIONS (`submit-legal-portal`).

**Deploy**: client (CI on merge), then `supabase functions deploy submit-legal-portal`. Order is free: an old function ignores the new fields, and a new function treats a missing field as before.

- **Integration pass (review fixes).** A `recordedById` that names nobody live on that firm's list is refused with 400 *Pick who recorded this from the list.*, never saved as *the firm*. The default date follows the page across midnight: when the payload's `preparedOn` changes, a date nobody changed moves with it, so a page left open overnight never defaults to yesterday. The guide says the name is the firm's own word for who did it; the portal has no sign-in, so it proves nothing on its own.

## Is this the best we can do?

- *Typed name, or picked?* Picked from the firm's own list, so the name is one the firm vouched for. An empty list still saves, as *the firm*. Remembered per browser, so it is one pick per person, not per act.
- *A key per click, or per act?* Per act, kept until it saves. A key per click would not stop the real duplicate: a timeout after the server saved, then a second press.
- *Is the pre-check enough?* Not alone: two requests in the same instant can both pass it. PR 2's unique index on `(matter_id, meta->>'clientId')` closes that, and the function then reads the conflict as a duplicate.
- *Why per matter?* The limit guards against a runaway script; a real month of costs lands on one matter, and the per-firm cap punished every other matter.
- *Undo now?* It needs columns (`voided_at`, `void_reason`, who), so it is PR 2, with the RPC for the office's side.
