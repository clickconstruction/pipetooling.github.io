# v2.8371 — Payments: the older Stripe payments made in the evening sit on the day they were made (2026-11-23)

Punch list #422, the step after v2.8335, on the owner's yes the same day. Migration `20261123162010_stripe_paid_day_older_rows.sql`. Data only: no table, no function, no edge function, no client change.

## What was wrong

v2.8335 made `mark_invoice_paid_from_stripe` file a customer's Stripe payment on the company's day instead of the UTC date, and left the rows already written alone. Read on prod, read only and with no amounts: six Stripe rows sat a day late, each written between 6 PM and midnight Central. Three were Sunday-night payments filed on a Monday.

## What changed

- The six rows' `paid_on` moves back a day, to the company's date of the moment each was written.
- A row moves only when it carries every mark of the old function's own write: on a bill, the note *Stripe*, no payment type, number or recorder, a day that is the UTC date and not the company's, and written before 2026-11-23. The same six match this rule and the looser count.
- The update refuses to move more than six, so a row nobody has read is never moved. A second run moves nothing.

## What did not change

- No amount, bill or job total. No trigger on the payments table reads `paid_on`, and none writes a line on an update, so a job's trail gains nothing. The plan in the card said an update would write a history line; reading the triggers showed it does not, and the card and the v2.8335 migration note are amended.
- A paper or an email already sent keeps the day it said.

## Tests

- The SQL bed `stripe-paid-day` gains `supabase/tests/stripe_paid_day/30_older_rows.sql`, run in phases around the migration itself: three late rows move back a day (one into the month before), nine rows that differ in one mark each or were on their day stay, no amount, recorder or job total changes, a second run moves nothing, and seven more late rows than were read are refused whole.
