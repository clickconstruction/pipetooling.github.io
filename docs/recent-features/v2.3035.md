# v2.3035 — Test-gap audit, pass 45: the Customer Pictures dispatch request gets its first tests (2026-09-07)

Follow-up to v2.3034. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`linkJobPicturesDispatchRequest.ts` (139 lines) is the "Send to Dispatch: add a Customer Pictures folder" action on the Dashboard and Dispatch Mode's My Schedule: it checks for an open request and the job's current link, files the request, notifies Dispatch, and retires a request that the job's link has made unclosable. The decision kernel (`picturesDispatchRequests`) was tested; the action around it was not.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- A signed-out user is told to sign in; a blank job id does nothing.
- The action reads the job's open `link_job_pictures` request and its pictures link together, then files a request titled "Add a Customer Pictures folder for HCP <n> - <name>" with a reference summary of "HCP <n> | <name> - <address>", both shrinking when the HCP or address is missing and "Job" standing in for a blank name; it then pings the notify function and the dispatch-requests-changed event and toasts success.
- An open request already on file means no new one, just a note. A job that already has its pictures link refuses the request and, when an orphaned open request exists, closes it with the self-heal note by id while it is still open; a viewer who lacks update rights has that failure logged, never shown.
- An insert that returns no id and a failed read each surface as an error toast.

## What shipped

- **`linkJobPicturesDispatchRequest.test.ts`** (7) — a recording Supabase stand-in with the edge invoke as a spy, the changed-event helper as a spy, fake time, the real decision kernel for the messages. Covers the gates, the full file path, the shrunken title, the already-open and already-linked outcomes with the orphan close, the logged-not-surfaced close failure, and the two error toasts.
