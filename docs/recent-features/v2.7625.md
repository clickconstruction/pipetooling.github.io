# v2.7625 — Documents: the Agreements tab lists GC projects' papers too (2026-11-17)

Punch list #376, PR 5 of five: GC mode's kinds. One migration, `20261117210000_agreements_on_file_gc.sql` (its page in `docs/migrations/`), the bed's new lines, and the rules and the tab learning three kinds. With this the card's train is whole.

## What is new

- **Three more kinds in `agreements_on_file`**: `owner_contract` (our contract with the owner, one line per GC project, its newest send), `sow` (a trade's statement of work, once sent) and `company_agreement` (a trade company's agreement).
- **In `agreementsLedger.ts`**: the `gc` group and its **GC projects** chip, the tags *Owner contract*, *Statement of work* and *Trade company*, the names, and the state words in GC mode's own terms: *waiting on their signature*, *late, asked to sign by Fri Nov 6* once the sign-by day passed (`weekdayDate` from `gc/words.ts`), *signed ✓*, *cancelled*. A trade company's agreement reads as a person's does.
- **The door**: a GC project's paper is a link to `/gc`. GC mode has no address that opens one project, so the line opens the page. A trade company's signed agreement opens its signed record, as a person's does.
- **The line**: a GC project is not a job, so its name sits where the job's would, as words and not a link.

## Choices worth knowing

- **The chip shows to everyone with the tab.** The plan said only the roles that read GC mode's money. But an assistant does read a trade company's agreement, so hiding the chip from them would hide a row they may open. The rows stay each table's own: under the chip a dev sees all three, the owner and the controller the statements of work and the company papers, an assistant the company papers alone. The bed asserts each.
- **One line per project for the owner contract.** A reminder or a new price is a new send; listing each would read as several contracts.
- **No amount.** The view leaves `worth`, `total` and `price` out, and the bed asserts the keys of `facts`.
- **The bed's runner re-applies the newest view.** Re-applying the first migration after the second would put the older view back.
