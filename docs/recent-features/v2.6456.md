# v2.6456 — Materials on site: a new cage or box records who added it, and the dev seat names the job the way the app does (2026-11-03)

Punch list #209. Three small fixes the dev seat's work on Materials on site turned up (v2.6367, `MATERIALS_ON_SITE_ARCHITECTURE.md`). The owner said yes to building all three as one PR on 2026-11-03.

## What changed

- **Migration `20261103143000_on_site_small_fixes.sql`** ([`docs/migrations/20261103143000_on_site_small_fixes.md`](../migrations/20261103143000_on_site_small_fixes.md)):
  - **`on_site_fill_created_by()`**, a `BEFORE INSERT` trigger on `job_containers` and `job_places`, sets `created_by` from `auth.uid()` when the insert leaves it null. Both screens call the store without the user and the store sends `created_by: null`, so all 100 containers on prod read null. A column default skips an explicit null, so it would not have helped. The trigger covers every client at once, the cached ones on crews' phones too.
  - **`on_site_line_on_hand`'s part arguments default to null**, so the dev seat's `call_read`, a GET that cannot send a null, reads a typed-name line with `p_part_name` alone. Before, it could reach only parts-book lines.
  - **`dev_on_site_write` builds the job's label as `formatJobLedgerNumberLabel` does** (`JP972`, `J1085` with no service type), where it said `972`. Re-stated whole from `20261102100000`; only the job lookup changed.
- **Tests**: `src/lib/devMcp/devMcpWrites.test.ts` holds the wrapper's rules on its newest definition (`newestDefinition`), so a later re-statement must keep them, and checks the trigger, the defaults and the label rule against the app's own `formatJobLedgerNumberLabel`.
- **Docs**: the architecture note (the live reading, the store's writes, the gap closed), the migration doc, this fragment and the release note.

## Decisions (the owner's rule: the recommended default, named)

- **A trigger, not a client change.** Passing the user at the five call sites would leave every cached phone writing null until it reloads. The trigger fixes all of them on the push.
- **No backfill.** Nothing recorded who made the 100 earlier containers; guessing from the first ledger row would write a name that may be wrong.

## Deploy

Merge, then `supabase db push`. No function changes.

## Verified

A throwaway Postgres 15 ran the earlier migration and this one twice, then every earlier case and refusal, which all passed on the re-stated wrapper. Then the new cases: the labels `JP972` and `J1085`, a refusal naming `JP972`, and the trigger filling a null or missing `created_by`, keeping a given one and leaving it null with no user. The on-hand read took one part argument by name.
