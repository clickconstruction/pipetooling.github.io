# v2.3701 — People spine, PR 3: Hire — one form, born linked (2026-09-21)

PR 3 of the People spine train ([`to-dos/people-spine/README.md`](../../to-dos/people-spine/README.md); PR 1 = v2.3698, PR 2 = v2.3700). The train's first write moment. Edge functions `invite-user` and `create-user` changed and were deployed before merge (`create-user` keeps `verify_jwt = false`); no migration.

## What was wrong

A new person was four jobs on four screens: the invite (Active Accounts), the roster row (People → Users or the first Employment-tab date save), the wage (People pay config), the workday template (Settings → Your account → All salaried users). Nothing tied them together, so a person could be any subset — an account with no roster row, a roster row with no pay, a pay row with Salary ticked and no wage (the Training Helper). `invite-user` / `create-user` wrote `users` only; the `people` row came later, from whoever noticed the desk's *no roster row* gap.

## The change

- **[`_shared/rosterRow.ts`](../../supabase/functions/_shared/rosterRow.ts)** — `ensureLinkedRosterRow`: after the `users` upsert, the roster row is found (already linked), linked (an unlinked, unarchived row with the same email, else one with exactly that name) or created, owned by the calling dev, with the optional `start_date`. `rosterKindForRole` maps `helpers → helper`, `subcontractor → sub`, `dev → none`. Fail-soft: a roster problem is logged and reported as `person_id: null`, never a failed invite. Fixtures get none: `is_sample`, `skip_roster_row` (the twin minter passes it), anything on `*.pipetooling.local`, and the Hiring board's Try-out door, which keeps its own roster path.
- **`invite-user`** — accepts `start_date`; the response carries `user_id`, `person_id`, `roster_row` (`existing | by_email | by_name | created | skipped`). **`create-user`** — accepts `start_date` and `skip_roster_row`; the user response carries `person_id` and `roster_row`. Docs: [`EDGE_FUNCTIONS.md`](../EDGE_FUNCTIONS.md).
- **[`hireWrites.ts`](../../src/lib/people/hireWrites.ts)** — `hirePlan` (pure: the ordered steps this hire needs and the problems that stop it — no name, invite without email or without dev, a paid kind with no wage, a salaried hire without a login, a bad date; six tests), `findNameCollision` (pay is name-keyed), and one function per write: `inviteHire`, `createRosterRow`, `upsertPayConfigRow`, `saveSalaryTemplate` (one continuous 8-hour block, weekdays, then today's sync), `assignPacketToPerson` (loads what `materializePacketForPerson` needs).
- **[`HirePersonModal`](../../src/components/people/HirePersonModal.tsx)** — the form (name, kind, email + *Send the invite* + *Start in training mode* for a dev, start date, wage + *Salaried* + workday start, packet) and the run: steps in order with a dot per state, the failure reason on its line, **Retry** from that step, **Open their desk** when every step is green. Nothing is written before Hire is pressed; a name collision is refused first. The form says what it cannot promise: each step is its own write.
- **Users tab** — `+ Hire` (blue) beside a now-secondary `+ Add to roster` ("a roster row only — no login, no pay"), wide and phone toolbars; `onOpenHire` prop, the modal mounted by `People.tsx`.
- Guide *hire someone*; *open a person's desk* points at it for someone already on the roster.
