# v2.6332 — Search every file deeply, PR 2: the dev seat's door to the file index, and a read that stays inside the platform's limit (2026-11-02)

Punch list #240's second PR: three dev-mcp verbs (server 0.15.0) so a Claude agent with a dev key runs the one-time backfill of `file_index` and reads where it stands. Migration `20261102050300_dev_file_index_status.sql` (`docs/migrations/20261102050300_dev_file_index_status.md`, with `file_index.pages_read`); `dev-mcp`, `drive-link` and `file-index-sweep` redeployed after the push, since the shared pass changed.

- **`read_file_index_status`**: one GET of `dev_file_index_status()` as the dev (SECURITY DEFINER, `is_dev()` inside, as the health RPCs): rows, rows with text, counts by source, by why and by folder, the jobs and bids with rows, the live and paid jobs with a Drive folder and how many have none yet, the newest indexed stamp, the oldest recheck and the sweep's last look; `statusReading` opens the reply with one line.
- **`plan_index_backfill { plan: { scope: live | paid | job, job_id?, limit?, retry?, after_job? } }`**: the jobs the scope walks, read as the service role from `jobs_ledger` (a Drive folder set; live = not Paid in Full, oldest first; paid = newest first; job = one by id) in the one order `created_at` then `id` (a job number ties on `''` for every click-only job, 125 of the 282 with a folder, and a tie would place the cursor differently on every read), at most 500 a plan — the plan's own `after_job` starts the list after that job (`backfillAfterFilter`: strictly after on the stamp, or the same stamp and a greater id), for the next 500 or to go on past a job that left the scope, and the reply says `may_be_more` with the `last_job` to plan after — which already have rows (the ids per hundred jobs, a thousand rows a page), the sweep's last look, the reads to expect and the how; the `plan_hash` is a sha256 over the scope, the switches, the start and the job ids in order, so a job joining or leaving the scope refuses the apply. Nothing is read from Drive, nothing written.
- **`apply_index_backfill { plan, plan_hash, after_job?, batch? }`**: the plan recomputed and its hash checked on every call; the job after the cursor (`nextBackfillJob`; none to start at the first); its files listed through `jobFilesToIndex` (lifted into `_shared/fileIndex.ts` from drive-link's `index_job`, which reads it too now: the folder tree three levels deep and a Pipeline job's plans and pictures links); the one index pass over the next `batch` (25, at most 40) files, as the service role into `file_index`, never into Drive; the answer `backfillApplyReply`: `indexed`, `held` with the reason, `skipped_current`, `remaining`, `job_done`, `next_after`, `jobs_done`, `jobs_left` and the next step in words. A job whose folder Drive refuses (a 404 on one the account cannot open, a hold) is passed over with its reason (`backfillJobPassedReply`, `job_passed`) and the cursor moves on, so one bad folder never strands the loop; an `after_job` the plan does not hold is refused with the way on (`cursorLostWords`: plan again with that job as the plan's `after_job`), never a silent start over that would walk the first jobs twice. The one-apply-per-plan rule does not hold it: an apply runs as often as files remain. Refused through `view_as` like every write.
- **Kernel** `_shared/devMcpIndexBackfill.ts` (no imports), tested from `src/lib/devMcp/devMcpIndexBackfill.test.ts`: the plan's shape, the jobs query by scope, the start's filter, the commitment, the cursor and its loss, the batch cap, the replies, the passed-over job and the status line.
- **The shared pass, hardened in review before the push** (`_shared/fileIndexKernel.ts`, `fileIndex.ts`, `fileHomes.ts`; `drive-link` and `file-index-sweep` run it too, so both redeploy): a `retry` takes a held row only when its last check is an hour old (`RETRY_HOLD_MS`, `retryDue`; `KnownRow` carries `checked_at`), so a loop with `retry` that holds the same slow file again moves past it instead of taking it first on every call forever; a parent folder Drive refuses on the walk up writes the file's row held as `error` with no home, so the pass moves on and the row says why, instead of the same file failing first with no row on every call; `folderHomes` reads every linked job and bid a thousand rows a page (`allRows`), since PostgREST caps one answer at a thousand rows whatever the limit asks and a job past the cap would have homed its files to no job for good.
- **The agent's loop**, as the card orders it: `read_file_index_status` → `plan_index_backfill { scope: 'live' }` → `apply_index_backfill` with the same plan and hash, the same `after_job` while `remaining` is above 0, then `next_after`, a few seconds between calls → `plan_index_backfill { scope: 'paid' }` the same way → `read_file_index_status` → the counts and the held files into the card's *Where it stands*.
- **The tally's words**: *Index this job's files* and the sweep's line say how many of the indexed files have their words (`indexPassWords`: *Indexed 9 files, 2 with their words, 7 held.*), since a held row is indexed too and *Indexed 9 files, 7 held* read as a contradiction on the first live press.
- **The read stays inside the platform's limit.** The first whole run over prod (the backfill through `index_job`, 2,618 rows) held 620 PDFs as `big` under the 8 MB and 40 page caps and left 51 as `reading`: the platform kills a request at about 2 s of CPU, and any file in flight when forty files' parsing added up to that was left stamped, 24 of the 51 under 4 MB. A kill also takes the office's other requests in that worker. Measured in Deno on made-up sets with deflated drawing streams: parsing costs about 17 ms of CPU per megabyte of a sheet's drawing here (three times that is a fair guess on the platform), so a dense sheet costs what a whole small file does, and the cost follows the drawing and never the file's size. So `pdfPagesText` (`_shared/fileIndexKernel.ts`, pure, tested with a made-up document and clock) reads a page at a time in the shape unpdf merges (the same text to the byte on a file read whole) until `PDF_READ_BUDGET_MS` (800) is spent or the text cap is reached, always the first page, and `passMayTake` lets a request start a file only when its expected cost fits `PASS_READ_BUDGET_MS` (1,200) and its bytes fit `PASS_READ_MAX_BYTES` (60 MB), the first file always; the rest is `remaining` for the next call. `ctx.spend` is shared by every read in a request, the clock counts pdf.js's load and open, and the clock is checked between pages and never inside one: cancelling pdf.js's text stream throws an uncaught rejection from its message handler, which crashed the test process and would crash a worker. With the budget doing the work, `TEXT_PDF_MAX_BYTES` is 50 MB and `TEXT_PDF_MAX_PAGES` 1,000, so a long written spec is read through and a plan set as far as its time goes; `file_index.pages_read` keeps how far (`read_in_part` in the status). Each document is freed after its read (`loadingTask.destroy`, since `pdf.destroy` is not on this build). A search's ten excerpts read at once, so they keep v2.6306's caps under `EXCERPT_PDF_LIMITS` (8 MB, 40 pages, 300 ms each, one shared clock), and a hit whose words sit past the pages read says too big rather than a kind we do not read.
