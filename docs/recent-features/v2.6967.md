# v2.6967 — The dev seat writes a bid's count rows: plan_bid_counts and apply_bid_counts (2026-11-11)

PR 2 of the bid train (`to-dos/mcp-servers.md` → The bid train). The owner, 2026-11-11: "fill out all of the line items for counts, takeoffs, labor, pricing." He gave the go on the map's order the same day. A bid entered from a paper proposal needs its Count Sheet before its takeoff, its labor and its prices, since all three hang on the count rows.

## What was added

One plan → apply pair on `dev-mcp` (eighty-nine write verbs). No wrapper RPC and no migration: the rows are the ones `BidsCountsTab` writes, as the dev under the table's RLS.

- **`plan_bid_counts` / `apply_bid_counts`** (`supabase/functions/_shared/devMcpBidCounts.ts`): `counts = { bid_id, rows?, remove?, version_id? }`, up to 200 rows a call.
- **Add** is the Count Sheet's quick add: the bid's active version (`pickActiveVersion`), after the bid's last row, the unit read off the name when left out (`classifyCountRowUnit`), the insert tagged `counts-import` so the bid's History reads the rows as one action.
- **Change** is the sheet's inline edit, in the fields the ask names: count, unit, page, group.
- **Remove** is the row's delete. The plan names the takeoff lines and prices the database deletes with the row.
- **Alternates**: `alternate: true` joins the row's group to `bids.alternate_group_tags`. Nothing here takes one off.
- **Held, not refused**: a row with a fault is listed with its reason and the rest goes on. A plan with nothing ready is refused.

## The key is the sheet's rule

`bids_count_rows` has no unique key. The Count Sheet keeps one row a fixture in a scope, where a scope is the base bid or one alternate group (`findDuplicateFixture`, v2.4188). Its quick add refuses a second row and its rename offers a merge, because a duplicate forks the takeoff assignment and the labor rows are keyed by the fixture's name. The verb follows it: the same fixture twice in the base bid is held, and an area is the row's group, not a second row. Where an import left several rows wearing one fixture, the ask's group picks one, or the row is held.

## One way to shape a row

A row off the wire is shaped by the app's own kernels, read from the kernel copy: the `[Group] ` prefix lifted off the name (`COUNT_GROUP_PREFIX_RE`), the units (`COUNT_UNITS`), the lengths. twin-mcp's `paste_counts` carries the same shaping inline. The new test holds twin-mcp's prefix, unit list and lengths to these, so the two seats cannot drift. Moving `paste_counts` onto the shared kernel is its own PR, since it puts twin-mcp among the kernel copy's importers and needs a twin-mcp deploy.

## What the screen does that the verb does not

A note on a row (the sheet has none). The CountTooling import and its sources. The drag order. A rename. Taking an alternate off the bid. Merging two rows.

## Server changes beside the verbs

`restRows` in `dev-mcp/index.ts` takes `DELETE` and extra request headers. Four files join the kernel copy off its index: `lib/bids/countSheet.ts`, `countRowUnit.ts`, `parseCountsImportText.ts` and `pickActiveVersion.ts`. The index's header comment lists them, so the functions that import the index read as changed until deployed again.
