# v2.2838 — Auto-create-job guard: dedupes hand-typed twins, skips change orders (2026-09-05)

**Why.** Journey-map Tier-1 #9 (C76; J15-F2, J16-F5). v2.2743's "Create jobs automatically" switch (off by default) deduped only through `jobs_ledger.bid_id`, a column **no job had ever carried** (0 of 815 in prod), while ≥10 of the 24 recent wins were re-typed into New Job by hand — same customer, same name, same cents. Flipping the switch would have minted a twin for every hand-typed win. It also never looked at `estimates.doc_kind`, so a signed change order — which is *applied* to a job through `apply_estimate_to_job` (never executed in prod; 0 accepted COs ever) — would have opened a brand-new job. `accept-estimate` calls the notifier with `kind: 'estimate'` for every doc kind, so the bridged-CO path was live.

**What.**
- **Pure kernel** `supabase/functions/_shared/autoCreateJobGuard.ts` (app twin `src/lib/estimates/autoCreateJobGuard.ts`, byte-parity tested) — `decideAutoCreateJob({ estimate, candidateJobs, now, switchOn })` → `{ create, reason, matchedJobId, via }`. First match wins:

  | Condition | Decision | `reason` / `via` | Letter shows |
  |---|---|---|---|
  | switch off | skip | `switch_off` (linked job surfaced if any) | linked job, else Create the job |
  | `estimates.job_ledger_id` set | skip | `already_linked` / `estimate_link` | Open job J#### |
  | `doc_kind = 'change_order'` (unlinked) | skip | `change_order` | Create the job → opens **Apply change order** |
  | a `jobs_ledger` row carries the estimate's `bid_id` | skip, **link it** (RPC, v2.2743 behaviour) | `already_linked` / `bid_link` | Open job J#### |
  | same customer (`customer_id` or `gc_customer_id`) + folded name (trim, collapse whitespace, lowercase) + revenue within ±1% or ±$1 + created in the last 90 days | skip, no write | `duplicate_by_name_value` | Create the job (link the twin there) |
  | otherwise | **create** via `auto_create_job_from_signed_estimate` | `no_existing_job` | Open job J#### |

- **Edge side** (`_shared/signedAgreementNotify.ts`): loads the estimate (`doc_kind, job_ledger_id, bid_id, customer_id, title, total_cents`), then a bounded candidate set — jobs on the bid (≤50) plus the customer's jobs from the last 90 days (≤200) — runs the kernel, and logs **one structured line per decision**: `{"event":"signed_agreement_auto_create_decision", kind, estimate_id, estimate_number, doc_kind, outcome: create|skip, skipped_reason, matched_job_id, via, candidates}` (Supabase function logs for `accept-estimate` / `sign-bid-room`). Never calls `apply_estimate_to_job` automatically — the office picks the job and owns the revenue move.
- **SQL safety net** — migration `20260905110000_auto_create_job_guard` (`CREATE OR REPLACE`, same signature/return): `auto_create_job_from_signed_estimate` now RAISES for `doc_kind = 'change_order'` (`check_violation`) and for a same-customer/name/value job created in the last 90 days (`unique_violation`, names the J#), so the rules hold for any caller that skipped the kernel (an older edge deploy, a hand RPC). On a real create it inserts `job_activity_events` (`event_type = 'job_auto_created_from_estimate'`, summary "Job opened automatically from signed estimate #N" / "…bid room proposal #N", `detail.source_id = estimate id`, non-financial; best-effort). The client registers the type in `src/lib/jobActivityEvent.ts` (tag **Opened**, status bucket) — unregistered types are dropped by `jobActivityEventsFromRpc`, so without this the row would never show in Job activity.
- **Tests** `src/lib/estimates/autoCreateJobGuard.test.ts` (16): exact bid link, estimate link, name+value twin inside the window (incl. GC-customer column and whitespace/case folding), twin outside the window → create, different customer → create, value outside tolerance → create, change order → skip (even with a bid twin), switch off → skip, `bid_proposal` treated as estimate, tolerance edges, twin parity.
- **Help guide** `get-notified-when-a-bid-or-estimate-is-signed` states both rules in plain words.

**Deploy order (either order is safe).** New edge + old SQL: identical guard in TS; SQL still creates on the create path. Old edge + new SQL: a twin or CO raises in SQL → `console.error` → letter offers Create the job. Both tracks are manual: `supabase db push`, then `supabase functions deploy accept-estimate sign-bid-room`. The switches are `app_settings` keys `signed_agreements_auto_create_job_estimates` and `signed_agreements_auto_create_job_bids` (`value_text` of `1`/`true`/`on` = on; absent/unset = off; both shipped off in v2.2743). Read both before deploying — if either is on, the guard is not protecting prod until both tracks land — and do not flip either until they have.

**Not changed / follow-ups.** The letter does not yet name the matched twin on a `duplicate_by_name_value` skip (it says "No job yet — automatic creation did not run for this one"); the `matched_job_id` is in the decision log. `accept-estimate`'s `alreadyAccepted` short-circuit and the bid-room CO signature path (which never called the notifier) are untouched.
