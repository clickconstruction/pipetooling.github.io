# v2.2837 — Sign-in doors: `users` read needs a session, `/accept-invite` arms only from the invite, `/sign-up` removed (2026-09-05)

Journey-map Phase 4, Tier-1 #1 ("Sign-in doors left open", J24-F1/F4/N1/N3). Three parts, one PR.

## (b) `public.users` SELECT requires a signed-in user — migration `20260905090000_users_select_requires_session.sql`

- **Before**: `"Users can select users"` (baseline `20250101000000_baseline.sql:38461`, controller widening via the `pg_policies` rewrite in `20260714213000_controller_capabilities.sql`) keyed most disjuncts on the **row's** role (`role = 'assistant'`, `'estimator'`, `'primary'`, `'helpers'/'subcontractor'`, `'superintendent'`) with no `auth.uid()` term and no `TO authenticated`. Every non-archived row of those roles was readable with the anon key alone — the key that ships in the JS bundle (J24-N1, live-proved 2026-09-04).
- **After**: same policy name, same disjunct list verbatim (controller included), wrapped in `FOR SELECT TO authenticated USING ((SELECT auth.uid()) IS NOT NULL AND (…))`. No signed-in role loses a row it could read; anonymous callers get zero rows.
- **Anon-reader enumeration** (nothing legitimate breaks): every edge function that touches `users` does so with the service-role client or with an anon client that forwards the caller's JWT (user-scoped, `auth.uid()` set); the public pages (`/portal`, `/sub`, `/bid-room`, `/contract/*`, `/estimate/*`, `/q/:token`, `/hazmat-notice`, `/task`) reach `users` only via SECURITY DEFINER RPCs (`get_hazmat_notice_by_token`, `create_hazmat_fee_incident`, `list_my_contract_dashboard_prompts`) or edge functions; `useAuth` reads the caller's own row by session uid. The only anon-dependent reader was `SignUp.tsx`'s pre-auth duplicate-name check — deleted in (a).
- Docs: `docs/migrations/20260905090000_users_select_requires_session.md`, `ACCESS_CONTROL.md` → Access Control Mechanisms.

## (c) `/accept-invite` arms only via the invite — `src/lib/acceptInviteState.ts` (tested)

- **Before**: `getSession()` truthy ⇒ set-password form; `handleSubmit` ran `supabase.auth.updateUser({ password })` unconditionally. supabase-js consumes the invite hash and clears it, so the history entry left behind is bare `/accept-invite` — revisiting it (history, autocomplete, typed) with any live session armed a silent password reset of *that* account (J24-F1). Meanwhile a hire whose invite session was live but who re-clicked the (now dead) email link got "invalid or expired" because the error-hash early return pre-empted the session check (J24-N3).
- **Mechanism**: `main.tsx` calls `markInvitePendingFromHash(window.location.hash, sessionStorage)` synchronously at module-body time — before supabase-js's async `_initialize` consumes the hash — and sets `sessionStorage.accept_invite_pending = '1'` when the hash is `type=invite` (or `type=signup`) with an `access_token`. `AcceptInvite.tsx` computes `resolveAcceptInviteState({ hasSession, inviteHashPresent, pendingInviteFlag, errorHash })` → `'set-password' | 'already-set-up' | 'invalid-link' | 'loading'` (decision table in the kernel's doc comment). `updateUser` is reachable only from `'set-password'`; the flag clears on success. `'already-set-up'` renders "You're already set up" with **Sign in** (→ `/dashboard`) and **Not you? Sign out** (signs out → `/sign-in`).
- **Error hash + pending flag** now resolves to set-password when a session exists (the live session *is* the invite session) — J24-N3 closed in the same conditional.
- **Telemetry**: `recordNavClick(userId, null, 'accept_invite_blocked_already_set_up', '/accept-invite')` fires (fire-and-forget, `ui_nav_clicks`) whenever the blocked view renders — the journey map's requested counter.
- Tests: `src/lib/acceptInviteState.test.ts` — every row of the truth table, hash parsing (invite/signup/recovery/error/empty), storage helpers incl. null and throwing storage.

## (a) `/sign-up` route and `src/pages/SignUp.tsx` removed

- Linked from nowhere (grep: only `App.tsx` imported it). It self-provisioned a `helpers` account via `handle_new_user`'s fallback (J24-F4) and its duplicate-name check depended on the anon `users` leak. `handle_new_user` is untouched — invited users still get their row.
- Server-side, Will closed self-signup in the Supabase dashboard on 2026-09-03 (`disable_signup`); the route removal is the client-side cleanup.
- Docs: `PROJECT_DOCUMENTATION.md` public-route list / auth flow / file tree; help guides `add-someone-to-the-roster.md`, `onboard-a-new-subcontractor.md`.

## Verify

1. **Anon read refused**: `curl -s "$SUPABASE_URL/rest/v1/users?select=id,name&limit=5" -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY"` → `[]` (RLS filters to nothing; before the migration this returned real rows). Signed in as any role, the same call with the user's JWT returns the same rows it did before.
2. **Bare `/accept-invite` no longer arms**: sign in (dev-login is fine), then open `/accept-invite` with no hash → "You're already set up" + Sign in + Not you? Sign out; no password inputs in the DOM. `ui_nav_clicks` gains a row with `control = 'accept_invite_blocked_already_set_up'`.
3. **Genuine invite still works**: People → Users → Add to roster with *Also invite them to sign in* → open the email link → "Welcome to ClickTooling" set-password form → set → lands on `/`. Re-open bare `/accept-invite` in the same tab afterwards → "You're already set up".
4. `/sign-up` → the app's not-found handling (no "Create an account" page).
