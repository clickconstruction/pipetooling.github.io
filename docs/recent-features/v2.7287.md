# v2.7287 — The theme check reads a colour inside a template string (2026-11-14)

A sweep, the one v2.7149 left. The theme check could not read a colour written inside a template string, such as `` border: `1px solid ${active ? '#2563eb' : '#d1d5db'}` ``. It reads them now, and the 19 it found are on tokens.

## The gap

v2.7149 taught `scripts/lib/themeTokenize.mjs` to read a ternary whatever its other side is, and listed what was still outside the check: 16 borders inside a template string, 17 backgrounds held in a `const` or handed to a helper, 3 text colours through a helper. The owner asked the same day whether the open supply house's row was fixed in dark (it was, v2.7143) and then for the rest of the sweep.

## The change to the check

- `templateBranches(src, from)` reads a style value that is a template string: each `${…}` expression goes through `ternaryBranches`, so a ternary, a nested ternary and a `??` fallback inside it count and a string handed to a call does not, and the string's own text between expressions is read for a hex of its own (`` `${w}px solid #e5e7eb` ``). A text run comes back with `raw: true`, since it has no quotes to keep. An unterminated string reads as nothing.
- `rewriteTernaries` tries `ternaryBranches` first and `templateBranches` when the value starts with a backtick. The prop still decides the table, so a `boxShadow` template is left alone and a `background` template reads the background table.
- `src/lib/themeTokenize.test.ts` gains eight cases for the template string, and the old "a template string needs a person" case is gone.
