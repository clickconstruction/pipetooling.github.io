# v2.4817 — Scheduled emails: the five cron callers keep the gateway check off (2026-10-07)

Config and docs only; the fix itself was a redeploy, done before this PR. Closes the outage [v2.4738](v2.4738.md) listed under *Open when this merged*.

## What happened

pg_cron calls each dispatcher with `X-Cron-Secret` and no JWT, and each function checks the secret in its handler. A plain `supabase functions deploy` turns the gateway's JWT check on for any function with no `[functions.<name>] verify_jwt = false` block in `config.toml`, and the gateway then refuses the cron call with `UNAUTHORIZED_NO_AUTH_HEADER` before the handler runs.

- `crew-day-email-dispatch`, `money-waiting-email-dispatch`, `schedule-share-dispatch` and `statement-round-email-dispatch` never had a block. A plain deploy on 2026-10-06 at 06:29 UTC turned their check on.
- `[functions.auto-send-test-reports]` lost its `verify_jwt = false` line in v2.3319's merge (621ee92b1), so its 2026-10-06 13:08 UTC deploy did the same.

From then until 2026-10-07 17:57 UTC none of the five ran: no crew day emails, Money waiting emails, recurring schedule shares, GC statement-round emails or automatic test reports. `net._http_response` held 270 gateway refusals between 12:00 and 17:57 UTC on 2026-10-07 alone.

## The fix

- 2026-10-07 17:57 UTC: the five redeployed from `origin/main` (1dd1a1c23) with `bash scripts/deploy-functions.sh`, which always passes `--no-verify-jwt`. `supabase functions list` reads `verify_jwt=false` for all five.
- Checked live: a POST with no headers now gets each handler's own 401 (`Unauthorized`, or `Missing authorization` from `schedule-share-dispatch`'s instant path), not the gateway's. No gateway refusal has been logged since 17:58 UTC. One held Money waiting request went out on the next tick, and no request queue has anything past due.
- The same sitting deployed the other 45 functions `npm run check:edge-drift` named: `close-held-stripe-marks` (v2.4801, never deployed, though its cron was scheduled) and 44 behind on `_shared/sentCopyEmail.ts` (v2.4750), `_shared/customerSampleFixtures.ts` (v2.4755 / v2.4771), `dev-mcp`'s catalog and the two Stripe functions of v2.4803. Before the deploy only `merge-users` and the five had the gateway check on in prod, so the script's `--no-verify-jwt` changed nothing else. The drift check after: all 138 functions deployed and current.

## This PR

- `supabase/config.toml`: `verify_jwt = false` under `[functions.auto-send-test-reports]`, and blocks for the other four, so a plain deploy keeps the check off.
- `docs/EDGE_FUNCTIONS.md` → Overview: `merge-users` is the one function on the gateway default; the sentence that named `schedule-share-dispatch` as the second was what the outage proved wrong. A pg_cron caller needs the block.

## Not done

- Nothing stops a new cron-called function from shipping without its block. A test that reads each `cron.schedule` call's URL and headers and asks `config.toml` for the block would catch it.
- The emails missed on 2026-10-06 and the morning of 2026-10-07 were not looked for one by one. After the fix no request queue (`crew_day_email_requests`, `money_waiting_email_requests`, `statement_round_email_requests`) had anything past due; whether a recurring schedule share or test report skipped a day was not checked.
