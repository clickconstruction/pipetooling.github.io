# v2.6893 — Permits: the reads' pairing made index-driven (punch list #307) (2026-11-10)

The read back (v2.6873) was held the night it shipped, before its first run (`docs/recent-features/v2.6886.md`): the Permits reads took 2 to 3 seconds each on ten weeks of rows. Two things made them slow. This fixes the first; the hold stays until the second is pushed too.

## What changed

- **Migration `20261111003750_permit_reads_indexed.sql`** (`docs/migrations/20261111003750_permit_reads_indexed.md`): `research_permits`, `research_permits_v2` and `research_builders` replaced in place. The pairing of a building permit with its plumbing permits, by number or by address, is two indexed joins in place of one `OR` that compared every building permit in a city with every plumbing one; Builders' bids with a name likewise. Same shape, same rows.
- **`scripts/pgtest-permit-skim.sh`**: the bed re-applied the skim's migration last, which put the first bodies of the reads back, so later rewrites were never probed. It runs `*_permit_history.sql` and this migration again after it.
- **`nameAnswers.ts`**: a sentence that ends on a customer's name ends once. Seen on the first live walk, where a name ending in *Assoc.* drew two full stops in the name question.
- Card #307.

## How it was proven, and what it measured

Read only, on prod: each rewritten body beside the live function with the same arguments, `EXCEPT` both ways, in all five cities and three windows. One row differed on the first pass, a plumber picked between two plumbing permits filed the same day; that pick was already left to chance, so it has a tiebreak now and the comparison is clean.

As the database owner the reads went from 1 to 3 seconds to 40 to 70 ms. That is not what a person meets: timed as a signed-in dev they went from 2 to 3 seconds to 0.7 to 1.4. The difference is the access rule, `user_can_research_permits()`, which the tables' policies call bare and Postgres therefore asks for every row. The Permits session measured the same thing from the other side and owns that fix, a migration of its own that touches policies only (`*_permit_policies_once.sql`).

## The read back stays held

A read back adds about 7,000 San Antonio rows a step, and every row pays the access rule. So `HISTORY_HELD` and the empty `HISTORY_CITIES` stand until both migrations are pushed and the reads are timed as a signed-in user.
