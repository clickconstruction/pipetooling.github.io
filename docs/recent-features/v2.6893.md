# v2.6893 — Permits: the reads' pairing made index-driven, and the read back turned on again (punch list #307) (2026-11-10)

The read back (v2.6873) was held the night it shipped, before its first run (`docs/recent-features/v2.6886.md`): the Permits reads took 2 to 3 seconds each on ten weeks of rows. Two things made them slow. This fixes one, the Permits session fixed the other the same night, and with both the hold is lifted.

## What changed

- **Migration `20261111003750_permit_reads_indexed.sql`** (`docs/migrations/20261111003750_permit_reads_indexed.md`): `research_permits`, `research_permits_v2` and `research_builders` replaced in place. The pairing of a building permit with its plumbing permits, by number or by address, is two indexed joins in place of one `OR` that compared every building permit in a city with every plumbing one; Builders' bids with a name likewise. Same shape, same rows.
- **The hold lifted**: `HISTORY_CITIES` is San Antonio again, so Builders draws **Read back to …**; `permit-pull` no longer refuses a read back (`HISTORY_HELD` is gone). `historyAsk` keeps the list it can be handed, so its steps are tested whatever cities are open.
- **`scripts/pgtest-permit-skim.sh`**: the bed re-applied the skim's migration last, which put the first bodies of the reads back, so later rewrites were never probed. It runs `*_permit_history.sql` and this migration again after it.
- **`nameAnswers.ts`**: a sentence that ends on a customer's name ends once. Seen on the first live walk, where a name ending in *Assoc.* drew two full stops in the name question.
- Guide `research-permits-for-work-to-bid` names the press again; card #307.

## How it was proven, and what it measured

Read only, on prod: each rewritten body beside the live function with the same arguments, `EXCEPT` both ways, in all five cities and three windows. One row differed on the first pass, a plumber picked between two plumbing permits filed the same day; that pick was already left to chance, so it has a tiebreak now and the comparison is clean.

The first timings were taken as the database owner and read 40 to 70 ms. That is not what a person meets: as a signed-in dev the rewritten reads still took 0.7 to 1.4 seconds, because the tables' policies called `user_can_research_permits()` bare and Postgres asked it for every row. The Permits session had measured the same thing from the other side and fixed it in `20261111013000_permit_policies_once.sql` (policies only, pushed first). Signed in, with both: 45 to 70 ms, from 2 to 3 seconds. The table is in the migration's doc.
