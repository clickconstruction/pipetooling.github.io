# v2.6299 — The job window shows what is in the job's Drive folders (2026-11-02)

The owner's ask of 2026-11-01, the evening the folder tree went live (v2.6284–v2.6288, punch list #236): "when we link these folders for a user in the edit job modal, we should show what is in those folders … so a user knows what exists before they go looking for it", with the worry "I just don't know how to handle someone moving a file into that folder and the system not knowing about it." The answer built here: the app does not have to know; it looks. Drive is the record of what a folder holds, and the app records only what it put there itself.

- **The section** (`JobDocumentsFolderFiles.tsx`, between **Job folders** and **Photos** on the job window's Documents tab): the five folders of the tree (`JOB_FOLDER_TREE`) and the job folder's own loose files, each a block with its name, its count (`sectionCountWords`: *3 files*, *100 or more files*, *Empty*), **Open in Drive ↗**, and its newest rows: the file's name as the door to it, *Nov 1 · 2.1 MB · Dana Example* (`fileMetaWords`), and a chip for where it came from. Five rows a folder, then *and N more in Drive · Open the folder* (`moreWords`, `SHOW_FIRST`). An empty folder draws `EmptyState` with *Nothing in Plans yet. Drop a file in the folder and it shows here.*; a folder not made yet (the as-needed choice on Where files go) says *Plans is not made yet. The app makes it when something first lands in it.* (`sectionEmptyWords`). A held job (`jobs_ledger.drive_folder_hold`) shows the hold's words instead. A job with no folder link draws nothing: the Job folders section above already says so and offers the press. A read that fails says why with Try again (`formatErrorMessage`, `filesReadFailedWords`).
- **Where a file came from** (`fromWords`): the function names a file the app filed itself by matching Drive ids against `uploaded_photos` (every photo view, with its `source`: *a report photo*, *a Tally photo*, *a checklist photo*, *a photo from a text or an email*) and `drive_links` (*a file the app linked*); everything else is *Added in Drive*. Nothing new is stored, so there is no index to drift and nothing for a hand-dropped file to be missing from.
- **The read** (`job-photos`' new `files` action, `jobFolderFilesIo.ts`): the job's row gives the job folder, the pictures and plans links and the hold; `Team only › Photos` and `Sent by us` are found by name under the job folder (`childFolder`); each folder is listed live (`files.list`, newest first, folders inside skipped, 100 a folder with `more` past it, `webViewLink` and `lastModifyingUser`). Same gate as the photo strip: anyone who may stamp the job's stages (`can_report_stage_progress`). The answer is parsed defensively (`jobFolderFilesFromAnswer`): an unknown shape reads as empty, never throws.
- **Deploy** `job-photos` after the merge. `set-where-a-jobs-files-go` gains the section; `jobFolderFiles.test.ts` and the section's render smoke hold the words and the states.
- **Left for a second pass**: an *Add a file* press per folder that uploads through the app (so new files carry a record), and, when a feature needs search or "new since you looked", one `changes.list` cursor on the shared drive into a light index. The listing stays live either way.
