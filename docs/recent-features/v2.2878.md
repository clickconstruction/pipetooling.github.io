# v2.2878 — Stripe receipts link back to the customer's statement, and the portal refreshes itself after a payment (2026-09-05)

Journey-map Phase 4, Tier-2 #38 (J22-F3, "after paying, the customer is stranded on Stripe's receipt"): no link back to the portal, stale totals until reload.

## Stripe has no return URL for invoices — the footer is the return path

Verified against the Stripe API reference for the pinned `2024-06-20` version: the Invoice object takes no `return_url` / `success_url` (those are Checkout Session and Payment Link fields) and the hosted invoice page has no post-payment redirect. The only field that renders on the hosted page, the PDF and the receipt is `footer`, so the portal link rides there.

- `supabase/functions/_shared/stripeInvoiceFooterPortalLink.ts` — `stripeInvoiceFooter(customFooter, portalUrl)`: no portal → the custom footer as typed (`null` when blank, Stripe's account default); portal and no custom footer → just `See your updated statement any time at <url>`; both → the custom footer keeps priority and the line is appended after a blank line **only while the total stays within `STRIPE_INVOICE_FOOTER_MAX_CHARS` (5000)** — over the cap the office's footer wins untouched, never truncated.
- `supabase/functions/_shared/customerPortalReturnUrl.ts` — `resolvePortalReturnUrl(links, slug, appOrigin)` reads the same two tables as the globe modal and the GC statement email (`customer_portal_links`, `customer_portal_slugs`), in the order the *invoice* needs: the main `all` link first (short `my.clickplumbing.com/<slug>` when saved, else its token URL — the only view guaranteed to list a bill on the customer's own job), then a GC-scoped link, else `null` (portal off / never minted → no line). Every URL carries `?paid=1`; the Cloudflare worker forwards the query string. `loadPortalReturnUrl(admin, customerId, appOrigin)` is the never-throws DB wrapper.
- `create-stripe-invoice/index.ts` resolves the URL after the customer row loads — **skipped when `bill_to_email` is set** (an alternate payer is not the portal holder and must not be handed the customer's key) — and passes `stripeInvoiceFooter(...)` to `invoices.create` and into `jobs_ledger_invoices.stripe_invoice_footer`, so the stored footer matches what Stripe rendered. `APP_ORIGIN` (else `https://clicktooling.com`) is the domain-cutover flip point.

## The portal lands fresh

`src/pages/CustomerPortal.tsx`:

- The load is now a `load(reason, gen)` callback. `?paid=1` landings fetch with `return=stripe`; a return to the tab after a **PAY ONLINE click from this page** (delegated listener on `a[data-bill-pay]`; idle tab switches never refetch) fetches with `return=refresh`. When the bill is still open (webhook latency), it looks again at +6 s and +20 s, then stops — bounded, since every fetch is a portal load.
- `src/lib/portal/portalPaidFlip.ts` — `snapshotPortalBills` / `paidFlipDetected(before, after)`: true only when the balance dropped **and** a bill from `before` (keyed by pay URL, else job label + billed date) is gone or smaller. Snapshots persist in `localStorage` (`pt-portal-snapshot:<token|slug>`) so a receipt-footer landing in a fresh tab can compare against what the statement showed before the payment. A refetch that fails leaves the statement on screen. Sample mode never persists.
- Banner: `[data-portal-paid-banner]`, screen-only, `PAPER_GREEN` rule — "**Payment received** — statement updated." No new writes anywhere.

## Telemetry — `portal_return_from_stripe`

`customer-portal/index.ts` reads `return` and logs one structured `portal_return_from_stripe` line (`customer_id`, `audience`, `via`) when it is `stripe`; the existing `portal_statement_rendered` line gains `return_from`. Function-log path, like J21-F1's statement line — `public_page_views.via` is CHECK-limited to `token`/`slug`, so no row shape changes and no migration. Refetches do still append a `public_page_views` row each (≤3 per return); #37's view-counting work can skip `return=refresh` when it lands.
