# v2.3773 — Travel times remembered: a repeat press is free (2026-09-23)

The follow-up v2.3764 named: a cache so the second day's *Travel times* press costs no Routes call. Done in the edge function, so every caller benefits and the client changes not at all. One migration, one function redeploy.

## What shipped

- **`public.driving_distance_cache`** ([`20260923230000_driving_distance_cache.sql`](../migrations/20260923230000_driving_distance_cache.md)): one row per origin → destination pair keyed by the two points to five decimals (about a metre), `distance_meters`, nullable `duration_seconds`, `source`, `computed_at`. RLS on with **no policies** — the function's service-role client is the only reader and writer, the same shape as `job_travel_times`. Both read-only blocks applied.
- **[`driving-distance`](../../supabase/functions/driving-distance/index.ts)** looks the pair up first (a hit answers even when the Routes key is missing or the API is off), routes on a miss, and upserts the answer; 30-day TTL, a stale row is re-routed and overwritten. A hit carries `cached: true` (`DrivingDistanceResponse` in [`bidDistanceToOffice.ts`](../../src/lib/bidDistanceToOffice.ts)). The cache is best effort: no table yet, no service key, or a failed write is a miss, never an error. Docs: [`EDGE_FUNCTIONS.md`](../EDGE_FUNCTIONS.md#driving-distance).
- The clocked-in map's page memo ([`clockedInMapTravel.ts`](../../src/lib/clockedInMapTravel.ts)) stays: it saves the call itself within a page; the table saves the Routes cost across days and across people. Why not the client? Writes from the browser would need a policy and a read-only-user block for a table nobody reads on screen; the function already holds the answer at the moment it is worth keeping.

## Deploy order

1. Merge; `supabase db push` (the table).
2. `supabase functions deploy driving-distance` — this deploy also carries v2.3764's `seconds` (not yet deployed when this was written), so the map's minutes and the cache arrive together.

## Verified

- Typecheck, lint; the release-note suite. The function is Deno (no unit test here); the cache path was read against `travel-time-batch`'s, which has run in prod since v2.2xxx with the same service-role pattern.
- Live: after the push and the deploy — two presses on clicktooling.com, the second answering with `cached: true` in the network log.
