# v2.7452 — The morning run reads a bill's own due day and terms in days (2026-11-16)

Punch list #341, the card's *Left for a deploy* line. PRs 4 and 5 of the train gave a bill a due day of its own (v2.7341, `invoice_due_days`) and a Pay calendar a second shape, a number of days after the bill (v2.7343, `payer_pay_calendars.days_after`). Every screen reads both. The morning run, `messages-nudge-dispatch`, read neither: both fragments said so, a docs pass found it still open, and the owner asked for it on 2026-11-16.

## What was wrong

- **Terms in days.** The run selected the calendars with `PIPELINE_SELECTS.payCalendars`, a column list written before `days_after`. A row of the second shape reached `parsePayCalendarRow` with no number, read as no calendar at all, and the Paid round fell back to the payer's pace.
- **A bill's own day.** The run never read `invoice_due_days`, so such a bill's Paid round was due on its calendar's day, or the pace's.

The kernel copy on the edge already knew both (`calendarSourceFor`'s `from: 'bill'`, `PayCalendar.daysAfter`). Only the reads were missing. Both tables are empty on prod, so no reminder has gone on a wrong day.

## What changed

- **`PIPELINE_SELECTS`** (`src/lib/flows/residentialRows.ts`): `payCalendars` gains `days_after`, and `billDueDays` is new (`invoice_id, due_on, clause, words, marked_at`).
- **`payTermRowsOf`**, same file: the stored rows of both tables as the rows `indexPayCalendars` takes, the calendars and then each bill's own day, which is how `loadPayCalendars` hands them to a screen. A half that was not read is null and is left out.
- **`_shared/payTermsRead.ts`**, new: `readPayTerms(admin, invoiceIds, warn)` is the function's read, moved out of `index.ts` (`readPayCalendars` there until now) so vitest runs it as it stands. It reads the calendars whole, the own days of the bills the morning read, and their accepted days when a calendar could count from one.
- **Soft, each alone.** A read that fails logs why and leaves that half null. A bill's own day stands without the calendars, the calendars stand without the days, and with neither the round keeps the pace's day. The morning goes on.

## Not changed

- **The client.** No screen selects with `PIPELINE_SELECTS.payCalendars`: the step card and Follow up's nudges read through `loadPayCalendars` (`payCalendarIo.ts`), which has held `days_after` and the own days since v2.7343 and v2.7341. So the short column list was the function's gap alone.
- A bill with neither, on every morning. With nothing stored the run reads what it read before.
- One difference from the client is on purpose. A screen whose calendar read fails drops the own days with it, since `loadPayCalendars` is one read to its caller. The run keeps whichever half it could read.

## Deploy

**No migration, and no deploy with the merge.** The function is deployed only on Taunya's go that names it: `supabase functions deploy messages-nudge-dispatch`, from a checkout equal to `origin/main`, then a check that it boots. Until then the morning run reads neither, as before, and the card says merged, not deployed. The copy's `residentialRows.ts` changed, and `npm run check:edge-drift` names this function alone as behind: no other function's bundle reaches that file. The function was last deployed on 2026-11-15, after v2.7343, so the kernels it runs already know both shapes and this deploy brings only the reads.

## Is this the best we can do?

- **Proved in tests alone.** Prod holds no calendar and no bill's own day, and none was set to test this, so no live run is claimed. The first real calendars are the live walk, as the card says.
- **The pager is written twice.** `payTermsRead.ts` carries its own page loop, ten lines the function also holds. Sharing it means moving the function's other reads, which this PR leaves alone.
- **The run reads every calendar, the screens' way.** At a few dozen rows that is right. If the table ever grows past a page the loop already pages it.

## Checked

`morningRunPayTerms.test.ts` (new, 10) runs `readPayTerms` over one made-up database and reads the same rows through the screen's loaders and the Pipeline's own call of `billedPayModel`. The two due days are equal for a bill on 45 days (billed Oct 9, due Nov 23), for a bill with its own day (Feb 15), and from an accepted day (Nov 28). It holds the selects, the accepted-day gate, and each read failing alone. Dropping `days_after` from the select fails six of the ten. `residentialLoad.payCalendar.test.ts` gains one for `payTermRowsOf` and holds the new column lists. `npm run check:edge-bundles` links all 192 functions.

The select strings were read against prod through the dev seat, reads only: both answer with no rows and no refusal, so the column and the table are there.
