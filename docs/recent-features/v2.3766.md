# v2.3766 — A job made from an estimate is named for the work too (2026-09-23)

The follow-up to v2.3748 (a job named for the customer instead of "Estimate for …"). Grace: *"What should we name a second job at the same house?"* — and *"I would like to also potentially backfill many of our jobs with just a name."* The office's own hand-typed names on prod answer the first: the work, sometimes with the last name in front ("Berg AirBnb- Door Repair", "Montolongo- Pretest", "Carter- Post", "Gas Line"). One kernel, one migration with two functions.

## The rule

When the estimate's title is still the app default and the linked customer has a name (v2.3748), the job is **"<customer> — <work>"** when the estimate has **exactly one line** whose name is **specific**: after whitespace folding, trailing periods dropped and the first letter capitalised, at most 60 characters and not a generic service word (`item`, `service`, `service visit`, `custom service visit`, `service call`, `trip charge`, `labor`, `materials`, `misc`, `miscellaneous`; case-insensitive). The line's name is `line_item`, falling back to `description` — the same order the Specific Work mapping uses. Several lines, no lines or a generic line give the customer's name alone; a guess from a list of lines ("1st Draw- Installation of customer provided i…") reads worse than the plain name. A typed title is kept, as before.

## The change

- **[`jobNameFromWork.ts`](../../src/lib/estimates/jobNameFromWork.ts)** (new) — `GENERIC_WORK_NAMES`, `WORK_NAME_MAX_CHARS`, `isSpecificWorkName`, `tidyWorkName` (whitespace folded, trailing periods dropped, first letter capitalised), `specificWorkFromLines(lines)`, `jobNameForCustomerAndWork(customer, work)`. Tested.
- **[`jobFromEstimateDefaults.ts`](../../src/lib/jobFromEstimateDefaults.ts)** — `defaultJobFieldsFromEstimate` reads `line_items_snapshot` and joins customer and work. The Create job window's late customer-name read goes through the same kernel. One more render case.
- **[`20260923220000_job_name_from_estimate_line.sql`](../migrations/20260923220000_job_name_from_estimate_line.md)** —
  - `auto_create_job_from_signed_estimate` re-created (the v2.3748 body) with the line rule in SQL.
  - **`plan_job_names_from_work(p_apply boolean DEFAULT false)`** — the backfill, as a plan first. Returns one row per job whose name is just the customer's name (whitespace/case-folded) or still "Estimate for …", that has **exactly one** Specific Work line (`jobs_ledger_fixtures`) naming the work by the rule above: `job_id`, `hcp_number`, `old_name`, `new_name`, `work`. Dev or controller only. With `p_apply = true` it renames those jobs and writes one `job_activity_events` row each (`job_renamed_from_work`, with the old and new name in `detail`), and returns the rows it changed. Re-runnable: a renamed job no longer matches, so a second apply is a no-op. Over the dev-mcp seat `call_read` runs it as a GET, so the database itself refuses an apply from there.

## Not changed

- The Job address fallback from v2.3748's notes is still open.
