# v2.6369 — Find a file shows our index's hits at once, and Drive's search fills in behind them (2026-11-02)

v2.6319 asked our index and Drive's search together and merged the two (`driveBehindIndex`), so a hit from the index never hid a file the index had not read yet. It waited for both before it drew anything, so the index's answer, about 130 ms for the RPC, took the seconds Drive's search and its excerpts take.

- **`findAFileIo.searchJobFiles(words, onFirst?)`**: Drive is asked at once and not awaited first; the index's hits go to `onFirst` the moment they come; the answer is the index's hits with Drive's behind them, as before. An index with nothing calls nothing first, and Drive refusing still costs the floor alone. Pinned in the new `findAFileIo.test.ts`.
- **The box**: `FindAFile` draws the first hits with a quiet line (*Drive's search is still looking…*, `data-find-filling`), and the answer replaces them and the line. `seq` guards both, so words typed since never hear an older search. Two new cases in `FindAFile.render.test.tsx`.
- **Guide**: *What the search reads* says the index's hits show first and Drive's follow a moment later.

No function or migration changes.
