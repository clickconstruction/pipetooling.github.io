# v2.5962 — A crew screen that cannot load says why and offers Retry (2026-10-26)

Punch list #184, sweep D, PR 3, part 1 of 2: the crew and phone loads with no Retry (`to-dos/consistency-sweeps/README.md` → D, pattern P4). The rule: a load failure a person meets on a crew or phone surface names its reason and offers Retry, and a lost signal reads again by itself when the signal comes back. Every site below is wired the way v2.2861 wired the Dispatch Mode schedule: the error state is the `{ kind, message }` failure (`OfflineRecoveryLastError`), `OfflineRetryPanel` draws it, Retry re-runs the exact read, and the panel is `idempotent` because a read is safe to repeat. Built on v2.5935 (the error codemod). No migration, no edge function.

## The kernel

- `recoveryFailureFromError` (`src/lib/offlineRecoveryState.ts`) formats every value with `formatErrorMessage`. Since v2.5935 the formatter reads a plain-object Supabase result error by its code with the screen's own sentence leading, so the PostgREST formatter is no longer needed: its `Code:` and `Details:` lines ran together on the panel's one paragraph. A refused direct read now reads *Couldn't load your requests. You don't have access to this record.*; any other server reason reads *Couldn't load your requests: <reason>*.
- Two fetchers carry the class beside the sentence, as `fetchDispatchModeDayBlocks` has since v2.2861: `fetchJobsLedgerWithDetailsForStages` / `fetchJobsLedgerStagesPrimary` fail as `FetchJobsLedgerFailure` (`{ ok: false, error, errorKind }`), and `fetchCustomerSummaryActivity` returns `errorKind`.
- The formatter words a `DatabaseError` by its operation name, *Couldn't load <subject>: <reason>* and *You don't have access to this <subject>.*, so a read named after a component or a table printed as words (*Failed to TallyClockWindowAllocateModal clock_sessions: …*). The reads on the wired surfaces are renamed to singular subjects: `load customer list`, `load crew`, `load clock history`, `load clock session`, `load schedule`, `load job`, `load job activity`, `load crew day`, `load cost estimate`, `load transaction list`.
- `trainingReadError` (`src/lib/training/trainingIo.ts`): the two training reads threw `new Error(message)`, which kept a lost signal (by its fetch signature) but dropped a refusal's code. The Error now keeps the code.
- `crewDayRefusalSentence` (`src/lib/crewDay.ts`): the Crew Day RPC answers its own refusal as `{ error: '<code>' }`; `forbidden` and `not_authenticated` read *You don't have access to this crew day.*, anything else *Couldn't load this day.*

## Is this the best we can do?

Close. Four things are left on purpose:

- A server failure on a read still has no Retry: the kernel's rule, pinned by its tests, is that a refusal does not heal. A transient one does (a 5xx, a pool timeout). Offering a tap Retry on an idempotent read when `isRetryableError` says trying again can help is one branch in `offlineRecoveryState`, left for the owner's call.
- The offline sentence says *nothing was saved* on a read too. It is the shared `OFFLINE_ERROR_MESSAGE` that hundreds of sites and tests read; a sentence for reads would be more exact.
- Operation names as words are a kernel limit: a plural subject reads *this customers*, so these reads got singular ones. Letting the screen's own sentence lead a `DatabaseError`, as v2.5935 did for a plain object, would retire op names as words everywhere.
- A `FunctionsFetchError` is a lost signal that `errorKindOf` does not know, so every edge-function read on a dead signal reads *Failed to send a request to the Edge Function*. One class check in `errorHandling.ts` fixes it for every caller.
