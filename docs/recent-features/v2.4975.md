# v2.4975 — Map: a pin that lands in another country is not kept (2026-10-08)

Five edge functions change (**redeploy after merge**): `geocode-one`, `geocode-address-batch`, `court-precinct-nightly`, `owner-confirm-nightly` and `property-lookup`. No migration, no client change. Found on the read for punch list #95's close-out ([v2.4790](v2.4790.md), *The first night*).

## What was wrong

No geocoder was held to the country. OpenStreetMap, which `geocode-one` and `geocode-address-batch` ask first, and Google both search the whole world, and every function stored whatever point came back.

On 2026-10-08 `address_geocodes` held ten points outside the lower 48, in Europe, Russia, Iceland, Brazil, Australia and India. Each was written alone, not by a night's run, for a short key of 3 to 14 characters. Nine sit under no property record.

One does. A property record's twelve-character address was cached on 2026-09-14 at 26.7813, 91.9274, in Assam, India. The Census has no county there, so the record never got one, and no drawn court area holds it. The precinct night read the cached point every run and could not fix it.

## What changed

- **One box, in [`_shared/usPointBox.ts`](../../supabase/functions/_shared/usPointBox.ts).** `inUsPointBox(lat, lng)` keeps lat 24–50 and lng −125 to −66, edges included. `refusePointOutsideUs` logs the geocoder's raw answer (`console.warn`, up to 2,000 characters) and returns the line the miss carries: *Google placed it outside the lower 48 (26.7813, 91.9274)*.
- **The shared geocoders call such a point a miss.** `geocodeWithGoogle` and `geocodeWithCensus` answer `not_found` with that line. So all five functions stop storing it and ask the next geocoder. A Census answer in Alaska, Hawaii or a territory is a miss too.
- **OpenStreetMap's answer** in `geocode-one` and `geocode-address-batch` goes through the same box before it is stored.
- **A cached point outside the box reads as none** at every cache read in the five functions. The precinct night lists the address as unplaced and geocodes it again. A good answer overwrites the row through the upsert on `address_normalized`. A miss leaves the row alone and counts in `geocodeMisses`. Nothing edits the cache by hand.
- **The miss names its reason.** The `detail` from `geocode-one` and the batch carries the refusal, which the Map page shows after *Address not found —*.

## Is this the best we can do?

- **A box, not the country's outline.** A point just south of the border passes; Monterrey is inside the box. The guard is for answers on another continent. A wrong pin inside the US is still fixed with *Not right? Pin from Google*.
- **The searches are not restricted to the US** (`countrycodes=us` for OpenStreetMap, `components=country:US` for Google). That would change every lookup's answer, not only the wrong ones, so it waits until the misses show it is needed.
- **The Map page and the job form read `address_geocodes` directly**, so they show a cached wrong point until a lookup replaces it. The Assam record is asked again at the next night's run (06:20 UTC). If both geocoders miss again, the row stays and the night keeps reading it as no point.
