# v2.4897 — Map buttons show only for people the Map opens for (2026-10-07)

Found by the help-guides freshness pass (punch list #91) and listed in [v2.4893](v2.4893.md). Punchlist asked for its own PR. The question was which side is wrong: if the superintendent may open the Map, the route gate is; if not, the door is.

## Which was wrong: the door

`docs/ACCESS_CONTROL.md`'s matrix has **Map** (`/map`) ❌ for superintendent, primary and sub. Its footnote says they are redirected away. `SUPERINTENDENT_PATHS` agrees (`src/lib/layoutRouteAccess.ts`). So the route was right. The doors were wrong. A superintendent keeps Bids → **Followup → By builder** (`bidsTabAccess.ts`), whose **Bid map** button navigated to `/map?builder=…` and bounced back. A field lead or superintendent who sees the Dashboard's **Who's in** strip could also open its map. That map's *Open the full map ›* bounced the same way.

## What shipped

- **`BidsBuilderReviewTab.tsx`** takes a required `canOpenMap`. `Bids.tsx` passes `isPathAllowedForRole(myRole, '/map', false)`, the route's own rule, so the button can never disagree with the route.
- **`ClockedInMapModal.tsx`** takes a required `canOpenFullMap`. `DashboardTeamActiveClockStrip.tsx` passes the same rule for the viewer, and the link shows only then.
- **`docs/ACCESS_CONTROL.md`**: the Map footnote names both doors and the rule they read.

The Layout nav (`canShowMapNav`) and the phone dock already matched the route, so they are unchanged.

## Tests

- `layoutRouteAccess.test.ts`: `/map` per role. Dev, leader, assistant, controller and estimator open it. Superintendent, primary, subcontractor and helper are bounced.
- `BidsBuilderReviewTab.render.test.tsx` (new): per role, **Bid map** shows exactly where `/map` opens. The superintendent case fails with the gate removed.
- `ClockedInMapModal.render.test.tsx`: the link shows with the rule true and hides with it false.
- The Who's in strip suite, the release-notes test, lint and typecheck.
