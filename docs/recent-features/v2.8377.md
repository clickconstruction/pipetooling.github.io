# v2.8377 — A window that cannot load keeps the page behind it, and fifteen routes offer Reload (2026-11-23)

Punch list #85, two of the three faults v2.8327 left (`docs/recent-features/v2.8327.md`, *What is left*). The owner approved all three in chat on 2026-11-23 after reading a before and after page. The third, a customer's second **Try again**, is v2.8379. Client only: no migration and no edge function.

Both faults show in the same two rare cases. The phone is offline, or a recovery reload ran inside the last minute, so the one guarded reload (`chunkLoadRecovery`) is refused and Vite's import really throws.

## 1. A window whose load fails keeps the page behind it

**Before.** The on-demand windows (`lazyWindow`) sat in a `Suspense` with no boundary of their own. A failed load reached the boundary around the routes (`RouteChunkBoundary`), which drew *This page could not load — the app may have just been updated.* in place of the whole signed-in app. The office pressed one job on the Jobs list and lost the list.

**After.** Only the window gives up. Its host closes it, one line says so, and the page behind stays as it was:

> The job could not open. Check your signal, then press it again.

The line is a warning toast, eight seconds, at the foot on a phone and in the corner on a desk. It names the window (`WINDOW_NAMES`) and the next press, since a toast has no press of its own. It is a warning and not an error line, so it carries no **Tell the dev** press: a lost signal is not a fault to report.

| Host | Window | The line names |
|---|---|---|
| `JobDetailModalContext` | `JobWindowModal`, `DetailJobModal` | The job |
| `JobFormModalContext` | `JobFormModal` | The job form |
| `BidPreviewModalContext` | `BidPreviewModal` | The bid |
| `CustomerProfileModalContext` | `CustomerProfileModal` | The customer |
| `EditCustomerModal` | `EditCustomerForm` | The customer form |
| `UserReviewModalOnDemand` (`OnDemandWindow`) | `UserReviewModal` | The review |
| `PersonDeskDrawerOnDemand` (`OnDemandWindow`) | `PersonDeskDrawer` | The desk |
| `PaintedMapHost` | `PaintAMapStartSheet`, `PaintedMapWindow` | The map |

Ten windows in eight hosts. The reader's count was seven hosts: `PaintedMapHost` had a `Suspense` and no boundary, so it is the eighth.

### How it is built

- **`src/lib/windowLoad.ts`**, the kernel. `windowLoadView(error, reloadOnItsWay)` answers `window`, `updating`, `gave-up` or `broken`. `windowLostWords(what)` writes the line.
- **`src/components/WindowLoadBoundary.tsx`**, one shared boundary. A lost chunk with no reload coming is `gave-up`: it calls the host's `onGaveUp`, says the line through the toasts, and draws nothing until its host unmounts it or `resetKey` changes. A host that could not close its window is therefore never asked again by a render alone.
- **It starts no reload.** In the built app every dynamic import passes through Vite's preload helper (`baseModule().catch(handlePreloadError)`), so `main.tsx`'s `vite:preloadError` handler has already had its guarded try before a boundary hears of the failure. What reaches the window's boundary is what that try refused.
- **While a recovery reload is on its way** (`updating`), the boundary draws the small `WindowOpening` note with *Updating app…* and closes nothing. The page behind stays until the reload comes. Before, the routes' boundary drew *Updating app…* in place of the app.
- **An ordinary crash in a window** (`broken`) is thrown on to the boundary above, as before. This change is about a load that fails, not about a window that breaks.
- **`OnDemandWindow`** takes `what` and `onGaveUp`. A window that gave up is unmounted, and it stays unmounted until its host has closed it once, so the next open is a new ask.
- **`PaintedMapHost`** holds each of its windows in the boundary inside the body (`heldMapWindow`), not around it. The body also draws the kept walk's offer and the places that wait for a signal, and a boundary around the whole body would have taken those away with the window. A caller that asked for a new map by the door still hears that its window closed.
- **The person's desk** closes with the way back kept, so People → Users still offers *Back to the desk* after a load that failed.

`lazyWindow` keeps a failed load for two seconds (`FAILED_LOAD_HELD_MS`, v2.8327). A second press inside that time gets the same line with no new ask. A press after it asks afresh.

## 2. Fifteen routes offer Reload

**Before.** Fifteen routes in the Layout wrapped a lazy page in the plain `ErrorBoundary`: `bills-sent`, `in-kind`, `projects-board`, `quickfill`, `bridge`, `gc`, `messages`, `training/:slug`, `moneyfill`, `partnerships`, `my-statement`, `logbook/:userId`, `my-logbook`, `first-looks` and `first-look/:id`. That boundary caught a page whose code did not come and drew *Something went wrong. Please refresh the page or try again later.* in small red words, with nothing to press. It also swallowed a first lost chunk, so the one guarded reload never ran for these pages from a boundary.

**After.** Those routes use `RoutePageBoundary` (`src/components/RoutePageBoundary.tsx`), which is `ErrorBoundary` with `chunkLoadsGoUp`. A lost chunk, or any error while a recovery reload is on its way (`errorIsForChunkBoundary` in `chunkLoadRecovery.ts`), is thrown on to the Layout's `RouteChunkBoundary`. That one reloads once, draws *Updating app…*, and when the reload is spent or the phone is offline draws the words and **Reload** press every other page has. An ordinary page crash is still caught by the page's own boundary, with the words it had.

## The guards

- `windowLoad.test.ts` walks `src` for every file that holds a window through `lazyWindow(() => import(…))` and fails a PR whose host has neither `<WindowLoadBoundary>` nor `<OnDemandWindow>`. The failure names the file and the fix.
- `lazyRoutesInPlainErrorBoundary` (`src/lib/lazyRouteBoundaries.ts`) reads every route in `App.tsx`, inside the Layout and out of it, and names one whose element puts a lazy page inside the plain `<ErrorBoundary>`. `lazyRouteBoundaries.test.ts` fails on it and says to use `<RoutePageBoundary>`.

## Seen

On 2026-11-23, on a throwaway harness page on the dev server (never committed), with a headless browser at 390 by 844 and 1,280 by 800, in light and in dark. No live page was opened and nobody signed in.

- **A window.** A Jobs list of three made-up rows. A press on a row drew *Opening the job…*, the import was refused with a lost-chunk error, and the list stayed with the amber line over it: at the foot on the phone, in the corner on the desk. Nothing was wider than the screen.
- **A route, before.** A lazy page inside the plain `ErrorBoundary` under the Layout's chunk boundary, inside a minute of a recovery reload: the small red sentence and no press.
- **A route, after.** The same page inside `RoutePageBoundary`: *This page could not load — the app may have just been updated.*, **Reload**, *Still stuck? Fix app*.

## Not proved

- No signed-in page was opened. The eight hosts rest on the typecheck, the guard that reads each host's source, and the render smokes below. Of the hosts, only `PaintedMapHost` has a smoke that loses its real window's chunk.
- The production build's own failure (a chunk refused by the network) was not forced in a built app. The smokes reject the import with the error text a browser gives.
