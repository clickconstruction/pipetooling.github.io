# v2.5263 — Messages: the database behind the customer's page (2026-10-12)

Cut 8 of the Messages build (`to-dos/gc-mode/messages/BUILD_PLAN.md` on `spike/gc-mode`), its own SQL, by GC Reviews helper 8, directed by GC Review. It sits on #5429 (v2.5252, the kernels), whose word table it seeds from. One migration, `20261012130000_portal_customer_page.sql` (`docs/migrations/20261012130000_portal_customer_page.md`). Draft until the lead's go; not pushed to prod. Dev only.

- **A view per paper**: `public_page_views` gains `paper_kind` and `paper_id`, written under a surface of their own, `portal_paper`.
  - Every reader of the table (the globe's "Opened N times", `usage_customer_views`, `journey_health_counts`) counts `surface = 'portal'` rows as page loads. A paper row there would inflate all three, so the existing table's grain is right and the surface is new. Each open is a row, with who opened it, as for the page.
  - `customer_portal_views(customer_ids)` reads it back for the office team: the page and each paper, with first and last outside open and the count. These are the opens `PaperView.viewedAt` and `portalWords(lastOpenedAt, …)` take.
- **`customer_page_words`**: every sentence of the customer's page in English and Spanish, 144 rows from `customerPageWordRows()`.
  - The rows are the page's own keys (the trade partner's six left out) and each customer paper's words as `paper.<id>.<field>`.
  - The office team edits `en` and `es` only. An edit keeps the sentence's `{blanks}` and is stamped with who and when by a trigger.
  - The seed follows the code only where nobody edited. `scripts/customer-page-words-sql.ts` writes the seed block, and `customerPageWords.test.ts` fails when the newest block and the code differ.
- **Three switches per job** on `gc_projects`: `portal_photos_on`, `portal_forecast_on` and `portal_spanish_on`, all off. Spanish stays off until a native speaker reads it.
- **Left out on purpose**: the portal's write that lands a customer's note in the thread, which waits on cut 1's `messages` table. The `customer-portal` reads and writes, and the screens, come with the page.
- **Tests**:
  - The new SQL bed `portal-customer-page` (`scripts/pgtest-portal-customer-page.sh`, `supabase/tests/portal_customer_page/20_scenario.sql`, a line in `scripts/sql-beds.txt`) seeds the words, edits them, re-runs the migration mid-scenario and reads paper views back. The SQL beds workflow runs it on the PR, since no local session reaches Docker.
  - `customerPageWords.test.ts` (4): the seed against the code, a block read back, the table's rules on every sentence, and which keys are in.
