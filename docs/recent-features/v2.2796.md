# v2.2796 — Audits: unpriced audits read "Robot still working", the seal pairs from shadow runs, count rows page (2026-09-04)

Follow-up to v2.2795 (Wendi's audit pass). Two things the pass exposed in the Audits tab itself, plus a row-cap hazard found while fixing them. Client only — no migration, no edge functions.

## Unpriced audits (the "draft $0 · −100% vs ours" cards)

The tab prices a robot bid from its PipeTooling count rows × book assignments (`computeAuditDraftTotal`). The BT-16..19 slate (b422, b424–b429) opened audits whose estimates lived only in CountTooling and the lock notes, so seven pending cards read *draft $0 · −100% vs ours*, fed −100% into the "recent runs" strip, and one drew "we will not do this for free wtf" on a bid that was never $0.

- Kernel [`bidAudits.ts`](../../src/lib/bids/bidAudits.ts): `isUnpricedAudit(draft)` (loaded, zero active rows), `countWorkablePendingAudits(audits, sealed, unpriced)`. +3 tests.
- [`BidsAuditsTab.tsx`](../../src/components/bids/BidsAuditsTab.tsx): an unpriced pending audit renders with a gray **Robot still working** chip and *no counts in PipeTooling yet* where the draft total sat; no delta on the row or the strip; it never auto-expands. Opened by hand, the card shows a dashed notice (questions are still answerable; hold the verdicts until the rows land) and the comparison strip shows "—" / *no rows yet*.
- [`useBidAuditsPendingCount.ts`](../../src/hooks/useBidAuditsPendingCount.ts) (Audits tab badge + the Dashboard Needs-you item): one HEAD count per pending bid on `bids_count_rows`; zero-row bids drop out of the pending number. Best-effort like the seal check.
- Help guide `audit-a-robot-bid` gains the row's meaning.

## Seal pairing from shadow runs

The sealed-shadow hold (v2.2553) keyed only on `bids.twin_source_bid_id`; `open_shadow` has stamped it since v2.2543, but b418 and b419 were opened minutes before that deploy and never got it, so b418 (Take 5 Brownsville — live, unsent) was audited in the open on 2026-09-04. `pairTwinReferences(twins, shadowRuns)` now takes the reference from the staff RPC `list_shadow_runs()` (bid numbers, sealed money NULL — the direct table select is RLS-closed since v2.2544) when the stamp is missing; the stamp wins when both exist. The tab resolves a number-only pairing with one extra `bids` read by `bid_number`; the badge hook uses the run's `reference_sent_at` directly. b419 (MPH LIVSTE) seals immediately. Backtests have no run row, so the six-row data backfill in the v2.2795 fragment is still worth running for b411–b414's "vs ours" strip.

## Count rows page

The tab loaded `bids_count_rows` and `bid_pricing_assignments` for every open audit with one un-limited `.in()` — 15 open audits × ~60 rows was already near PostgREST's silent 1,000-row cap (the v2.2755/2756 class); a truncated load would price the newest audits at $0 for a different reason. Both loads use `fetchAllRowsChunkedIn` with a stable order now.

Verified live as dev on a worktree dev server (port 5199), Bids → Audits: the seven BT-16..19 cards render as gray **Robot still working** rows with *no counts in PipeTooling yet* and no delta; b419 shows the 🔒 "opens after we send b396" row; the Robots pill reads **9 audits pending** (17 pending − 7 unpriced − 1 sealed); b410 auto-expands with its real draft ($174,930, −17.0%); a fetch probe over a tab remount recorded no non-2xx response.
