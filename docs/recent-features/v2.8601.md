# v2.8601 — Papers before a job opens: declining a GC's proposal needs a reason (2026-11-25)

Punch list #389, a mend to step 6 (v2.8553). Finding 125 of the run of 2026-11-25, read in the code by the docs pass and briefed by the fixing thread. The owner's answer of 2026-11-25, asked whether a decline of a GC's proposal must carry a reason: yes, in the client alone. No migration, no edge function.

**Read.** On a job's Documents tab, **Decline…** on a GC's proposal opens a window that asks why, *for the GC to read*. `JobPaperProposalCard.tsx` sent `typed.trim() || undefined`, so an empty box declined with no reason. `job_paper_proposal_decide` stores `decline_why` as null when nothing came. The guide tells the office to type why, and the GC's page reads the reason back.

**The mend.**

- `usePromptDialog` takes `required: true` (`ConfirmDialogContext.tsx`). While the box is empty or holds spaces alone, the confirm press is disabled and drawn as a dead press (`deadPress.ts`), and Enter does nothing. The box carries `aria-required`. A prompt that does not ask for it is unchanged: it still answers an empty string.
- `declineWhy` (`lib/contracts/jobPaperProposal.ts`) is the reason as it is sent: the typed words with the spaces at their ends cut, or null. The card sends no decline on null, so the rule holds even if the window is ever changed.
- The guide's step says the button stays grey until a reason is typed.

## What did not change

- The database function still takes a decline with no reason. The rule is the client's alone, as the owner chose. A proposal declined before this with no reason keeps its empty reason.
- **Take it**, the words of the window, and what the GC's page shows.
