# v2.7704 — Signed contracts: a job whose Drive folder is gone says so, and a voided copy is found by its new name at once (2026-11-17)

Punch list #377, two small finds from the walk on prod, fixed on the owner's word (*Yes, fix both*).

## A job folder Drive no longer has

The walk pointed a ZZ Test job's Drive link at a folder that does not exist. The paper was held, as it should be, but the hold was `drive_refused` and its words were Drive's: *Folder create failed (404): File not found*. No door, and nothing a person could act on.

- `keptJobFolderWhy` (`supabase/functions/_shared/jobContractDrive.ts`): the state of the folder a job's link names, as Drive answers it, to the reason it cannot take a paper. No such folder reads *This job's Drive folder is gone. Put the right link on the job's Edit tab and the paper files itself.* A folder in the trash reads *This job's Drive folder is in Drive's trash. Put it back in Drive and the paper files itself.* Both pass the plain-words rules.
- `job-contract-drive` reads the folder once (`driveFileState`) before the first write when the job keeps a link, and holds the paper as `job_folder` with that reason. The hold then carries the door it already had, **Open the job's Edit tab**, and **Try again**.
- One more Drive read per filing from the stored file. An adopted paper never reaches it.

## A voided copy's new name

`markVoidedCopy` renamed the copy and left the file index to learn the name on its next ten-minute run, so Find a file showed the old name with a *Voided contract* chip for that long. It now hands the file to the index right after the rename (`drive.index`), as a filing does. The hand-off failing changes nothing: the row is still marked and the index sweep is the net.
