# v2.8252 — Permits, Market: the read learns a job's first plumbing permit day (2026-11-21)

Punch list #405 ([the card](../../to-dos/permits-market-page/README.md)), the line *Austin's clock runs to a job's newest plumbing permit* on its *Seen while building, not done* list. Taunya said to build it on 2026-11-21. This is step one of two: the database's part, shipped alone so the clock's change can follow once it is pushed.

## What was wrong

Market's clock in Austin runs from a building permit to the plumber's permit. The read behind it keeps one plumbing day per job, the newest. A job with two plumbing permits was measured to its later one, so the clock read long.

## What this adds

Migration [`20261122032000`](../migrations/20261122032000_permit_first_plumbing_day.md) adds `research_permits_v4`. It is `research_permits_v3` with one column more, `plumber_first_permit_on`: the day of the earliest plumbing permit that counts for the job. It pairs a plumbing permit with a job as `research_permits` does, so the day is set on exactly the rows that carry the newest day and is never later.

Nothing on screen changes with this PR. No client reads v4 yet.

## What the clock will read

Read on prod, counts only: of 300 Austin jobs with a plumbing permit in the last year, 54 have more than one and 26 have a first day earlier than the newest. The clock's quarter marks move from 1, 7 and 16 days to 1, 6 and 15.

## Tests

The permit skim bed (`npm run test:pg:permit-skim`) holds the new read: a job with two plumbing permits says both days, one from outside the thirty days is never read, v4 less its column equals v3, and anon cannot run it. The bed's runner applies the new file a second time, which must change nothing.

## The card

Not marked yet. The line is marked fixed when the clock reads the new day.
