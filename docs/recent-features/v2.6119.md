# v2.6119 — Calls ahead of their migration: CI says push right after the merge, and the deploy holds until the push (2026-10-30)

No migration. The guard for the hazard `CLAUDE.md` → Deploy model's bullet 1 only half named: the client deploys to GitHub Pages on every merge (`deploy.yml`), a migration waits for a hand `supabase db push`, so a client that calls a function, table or view that only a still-pending migration creates is broken on prod from the deploy until the push.

## The incident

On 2026-10-30 #6473 (punch list #163 PR 2, v2.6099) merged at 4:46 AM CDT through the merge queue and `deploy.yml` published the client at 4:57 AM. Every clock in and clock out now went through the new `land_field_press` RPC, whose migration `20261029230000_field_presses.sql` was still pending (the morning's `scripts/db-push.sh` had run at 3:50 AM, before the merge). PostgREST answers a missing function with a 404 (`PGRST202`), which the client classes as a refusal, not a lost signal, so every clock press on prod was refused until the push. The "Migration drift" run on that commit printed "3 pending (push soon)" and passed: its `STRICT_PENDING` is for the daily cron, and the deploy never looked. The migration doc had said "client first is fine", reasoning only about queued presses.

## What changed

- **`src/lib/callsAhead.ts`** — three pure pieces, tested in `callsAhead.test.ts`. `schemaCallsIn(source, file)` reads the names a TypeScript source calls through `.rpc('name')` and `.from('name')` by the compiler's own parse (a literal, through an `as never` cast or a template with no substitutions; a name in a comment is not a call; `storage.from('bucket')` and a constructor's `Array.from(…)` are not reads of a table). `namesCreatedIn(sql)` reads the functions, tables and views a migration creates, quoted or schema-qualified, with the SQL's comments stripped first. `callsAhead(calls, pending, applied)` pairs them: a call is ahead when a pending migration creates its name and no applied one does, so a `CREATE OR REPLACE` of a function prod already has (the old body answers, never a 404) is not listed.
- **`scripts/check-calls-ahead.ts`** (`npm run check:calls-ahead`), two modes:
  - On a pull request (the checks job in `ci.yml`, no flag): the calls on the lines the change wrote whose name a migration the change *adds* creates, and no older migration does. Each is a `::warning` on its line, the step summary says what to do, and the PR gets the label **push right after the merge** (the job now carries `pull-requests: write` for it; when the token cannot label, a warning says so and the annotations stand). It never fails: the migration cannot be pushed before it is on main, so the PR is right to carry both. `--base <ref> --head <ref>` compare any two commits through git; on #6473 it lists `src/lib/offline/landFieldPress.ts:67 calls the function land_field_press, which only supabase/migrations/20261029230000_field_presses.sql creates`.
  - `--prod` (the build job in `deploy.yml`, right after `npm ci`): every call in src against the migrations the prod ledger has not applied, read with the same Management API query as `check-migration-drift.mjs` (`SUPABASE_ACCESS_TOKEN`). A call ahead of its migration fails the build with a `::error` naming the call, the migration and the fix, so the site keeps the old client. No token, or the API down: a warning, and the build goes on — a blip at Supabase must not hold every deploy. `--ledger <file>` reads the applied versions from a file (one per line) for a dry run.
- **`scripts/db-push.sh`** — after the push and the drift check, when the newest deploy of main failed, re-runs it (`gh workflow run deploy.yml --ref main`), so a held deploy lands the moment the migration does.
- **`CLAUDE.md`** → Deploy model, bullet 1, amended in place with the opposite case: client first when the migration changes behavior the old client would misread; push right after the merge, before the Pages deploy finishes, and arm that PR only when the person who pushes is at hand, when the client calls what only the migration creates. `docs/MIGRATIONS.md`'s sequencing sentence says the same.

## What it does not read

- A column: a client that selects a column only a pending migration adds gets a `42703` from PostgREST, and nothing here reads select strings. The same for a function prod has whose pending `CREATE OR REPLACE` teaches it a new kind the client now sends (the #163 train's PR 3, `20261030040000_field_presses_notes_reports.sql`, is exactly this: the old body refuses the new kinds with a `P0001`). Both still need the migration doc's "push right after the merge" line and an arming hand that reads it.
- A name held in a variable (`supabase.rpc(fn as never, …)`), and a call made from an edge function or a Worker.
- A held deploy holds every merge's client, not only the one that calls ahead; the push releases them all. That is the trade: a few merges wait on a push that was due anyway, against every crew's clock refused for hours.

## Verify

`npm test -- callsAhead` (10 tests). `npx vite-node scripts/check-calls-ahead.ts --base b21e60694~1 --head b21e60694` prints the #6473 finding and exits 0; with a ledger file that lacks `20261029230000`, `npx vite-node scripts/check-calls-ahead.ts --prod --ledger <file>` names the same call and exits 1, and with every version listed it exits 0. `npm run check:calls-ahead` on a branch that adds no migration says so and exits 0.
