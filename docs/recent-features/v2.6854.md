# v2.6854 — The ground under photos on a bid (punch list #306, PR 1) (2026-11-10)

Punch list #306's first PR, on the owner's go of 2026-11-10 (*Yes, C and PR 1*). The owner's ask: a photos icon in the Bid Board's Links column that is always in its place, grey until the bid has photos, with upload tools and the photos kept in Google Drive and managed in the app, the way a job's are. This PR is the table and the bucket alone, so both can be on `main` and pushed before anything that reads them merges. PR 2 is the Drive leg (the `bid-photos` function and the sweep's tenth source), PR 3 the icon and its window.

## What changed

- **The migration** `20261110195527_bid_photos.sql` (`docs/migrations/20261110195527_bid_photos.md`): the `bid_photos` table, a job photo's shape keyed on the bid, with `added_at` (null while a pick waits on the press that adds it), `fail_why` (why the sweep could not file it yet) and `removed_at` (a removal is a stamp, the row stays for an Undo); a unique index on `drive_file_id`, so a picture adopted from the Drive folder is one row; and the private `bid-photos` bucket, 2 MB a file, images only, objects `<bid_id>/<photo_id>.jpg`.
- **The gate is the bid's own**, read through `bids` under the caller's RLS and not through `can_access_bid_for_pricing`, which lets any primary through. Whoever reads a bid reads its photos and adds one as themselves; a primary only on the bids they estimate, manage or made; the adder and the office change a photo; only an un-added shot of one's own is deleted. The bucket's policies read the bid from the path's first folder the same way, and a path that is not a bid's is refused without a cast error.
- **The bed** `npm run test:pg:bid-photos` (`scripts/pgtest-bid-photos.sh`, in `scripts/sql-beds.txt`): every migration, this one twice, then the gate walked as nine accounts on the table and the bucket.
- **`docs/ACCESS_CONTROL.md`**: the `bid_photos` line beside `bid_plan_sets`.

## Decisions

- **A photo goes into the app first and the sweep files it**, as a job photo does, so a bid folder the app cannot write to costs a delay and never a photo. Most hand-made plumbing bid folders sit in a personal Drive today (card #240, call 4).
- **No column on `bids`.** The board's count reads the table, so a count stamp never fires a bid's own triggers or its realtime.
- **The update rule follows the card's pick for call 6** (the adder and the office). The owner has not answered it. A different answer is one policy, changed with PR 4.
- **The `photo-save` cron is not touched here.** Its guard gains a clause for a waiting `bid_photos` row with PR 2, when the sweep can file one.
