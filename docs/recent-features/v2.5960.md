# v2.5960 — What everyone sees, part 1: a sealed frame draws the app on invented data (2026-10-26)

Punch list #194, PR 2 ([`to-dos/experiences-lens/`](../../to-dos/experiences-lens/README.md)). The owner's long-term ask is every experience a user can have, live, on test data, so a theme or style change shows on all of them before it ships. This PR is the seam everything else stands on. The Settings tab comes next.

- **The seal** ([`src/lib/lens/seal.ts`](../../src/lib/lens/seal.ts)), the first import in `main.tsx` (`sealFirst.test.ts` pins it). Without the lens's frame name, `pipetooling-lens:{as, mood, theme}`, it returns after one string check. With it, before any other module runs, it does six things:
  - `localStorage` and `sessionStorage` become memory stores ([`memoryStorage.ts`](../../src/lib/lens/memoryStorage.ts)), seeded with the person's invented session (`lensAuth.ts`, a token signed by nobody) and the frame's `themeOverride`.
  - `fetch` to the Supabase address goes to the world.
  - The realtime socket becomes [`QuietSocket`](../../src/lib/lens/quietSocket.ts), which echoes a join's `postgres_changes` bindings and answers heartbeats.
  - IndexedDB and the cache store are hidden, since the Pipeline board's snapshot and a hard reload would reach the real ones.
  - `BroadcastChannel`, `navigator.locks` and `document.cookie` become the frame's own ([`frameChannels.ts`](../../src/lib/lens/frameChannels.ts)), and no real `storage` event reaches it. supabase-js's auth client opens a BroadcastChannel named after its storage key in every window, so without this a frame announced its invented session to the dev's own window. The browser check caught it: the dev's Settings page took on the invented person and its fake token was refused with a 401.
  - Location, notifications and `onLine` answer from the state.
  - `window.open` and `target` links pass the name on.

  A small mark reads *Lens · invented data · Estimator*. `seal.test.ts` runs each of these on a fresh jsdom window.
- **The world's front door** (`src/lib/lens/answer/`): [`postgrest.ts`](../../src/lib/lens/answer/postgrest.ts), [`select.ts`](../../src/lib/lens/answer/select.ts) and [`filters.ts`](../../src/lib/lens/answer/filters.ts) answer the request the real client built.
  - **Reads:** filters with SQL's three-valued logic, logical trees, JSON paths and containment, embeds along the foreign keys (to-one, to-many, through a junction, `!inner`, hints, aliases, spreads, counts), orders, ranges, exact and head counts, and `single` and `maybeSingle`.
  - **Writes:** insert, upsert, update and delete change the frame's copy only. Training mode refuses with the database's own *Read-only (training) mode: changes are blocked.*, except clock punches.
  - **Errors** carry PostgREST's codes (PGRST116, PGRST200, PGRST205, 42703, 23505).
  - **The engine** ([`lensEngine.ts`](../../src/lib/lens/answer/lensEngine.ts)) routes `rest`, `auth`, `storage` and `functions`. An RPC with no handler answers by its return kind: no rows for a set, null for a scalar, nothing for void, and an error (`LENS`) for an object, which a caller would read fields from. It applies the state knob: empty, loading, slow, failing, offline and training mode are answers, not code in pages. Every request is reported as an ask on `window.__lens.asks`.
  - **Tests:** `postgrest.client.test.ts` (23) builds every request with the real `@supabase/supabase-js` client.
- **The schema map** comes from `src/types/database.ts` at build time, through `scripts/lens/lensSchema.ts` and the `virtual:lens-schema` plugin in `vite.config.ts`. It holds every table's columns and foreign keys and every RPC's return kind. No generated file exists to fall out of step. The engine and the map are their own chunk (`lensEngine-*.js`), loaded only by a sealed frame, and `globIgnores` keeps the service worker from precaching it.
- **The world** ([`world/lensWorld.ts`](../../src/lib/lens/world/lensWorld.ts)) has one invented person per role ([`lensPeople.ts`](../../src/lib/lens/lensPeople.ts), fixed ids). Its customers are the customer pages' own sample people. It holds five jobs, one at each Pipeline status, typed by `database.ts`. Empty keeps only the person's row, the settings and the trades.

**Checked:**
- The lens's suites pass: 55 tests in 10 files.
- The real app was booted sealed in Chrome as seven roles, at 375, 768 and 1280, light and dark, and on the Jobs page in every state. Every request was answered in the page, and **none reached the Supabase host**.
- The dashboard's receivables, unbilled work and contract warnings computed from the invented jobs through the app's own kernels.
- The failing state found two real loaders that throw uncaught when a read fails: *Failed to load team labor crew days* and *Failed to list users banking attribution*. That is follow-up work for #184.
- Still answered with an error until the world fills them: object-returning RPCs such as `get_my_partner_summary`, `list_paid_claims`, `get_crew_day_payload` and `get_billed_customer_pay_speeds`, and the `geocode-address-batch` and `get-mercury-account-balances` functions.
