# v2.7154 — The dev seat reads a Drive folder and files a bid's sent paper from Drive: read_drive_folder, plan_bid_submission and apply_bid_submission (2026-11-13)

Punch list #339, pair 6 of the bid train (`to-dos/mcp-servers.md` → The bid train; the pickup card is #317). The owner, 2026-11-11, on old proposal files copied into company Drive, a folder a bid: "connected to their bids where a user links the submissions" and "if we don't have dev verbs to support this, we should add those too". No migration. `dev-mcp` is server 0.82.0 with 145 tools.

## Why

The seat could set a bid's submission link (`plan_bid_update`, v2.6945) and nothing more: it could not list a Drive folder, make a bid's project folder or put a file in it. The session working the real case, 35 proposal files for 14 bids, read Drive through a browser and left its links in bid notes.

## What was added

- **`read_drive_folder { folder | file, page? }`** lists a Drive folder (100 entries a reply, folders first, `next_page` reads on) or answers one file's facts with the folders above it and who it is shared with. It reads through the intake service account on a token minted with `drive.readonly`, through a door that only GETs (`driveGetWith`), and never reads a file's bytes. Each entry says whether the company's Shared Drive, the one that holds the jobs root, holds it. A folder or a file the account cannot open is refused in words that name the share that fixes it. A dev's own key alone: refused under `view_as`, since the service account sees more than any one person.
- **`plan_bid_submission` / `apply_bid_submission`** take `submission = { bid, drive_file_id | drive_url, replace? }`, one paper a call. `bid` is an id or text that finds one bid ("b398"), as `plan_activity_note` names one.
  - **The project folder**: made at the apply through `bid-photos`' `make` as the dev when the bid has none, the Files window's own press, which writes `bids.drive_link` itself. The plan names the folder it will get, by the office's bid pattern.
  - **Where the paper lands**: Team only › Sent by us of that folder (`JOB_FOLDER_TREE.sentByUs`, `landingPath('sent')`). No Submission folder was invented.
  - **The copy**: a file already in the company's Shared Drive is copied with Drive's own `files.copy` by the service account, so its size is no limit and no byte passes through the function. A file elsewhere is read on the server, checked against the plan's size and Drive's sha256, and put through `drive-link`'s `put` with `where: 'sent'` as the dev, 10 MB at most. A file whose bytes are already in Sent by us is not copied again: only the link is written.
  - **The link**: `bids.bid_submission_link` set to the filed copy by the Files window's own PATCH, held to the link the plan read, so a link someone set while the paper was being filed is never written over.
  - **The note**: one line on the bid's Notes, the row `plan_activity_note` writes, after the link. A note that fails never undoes the rest.
- **The kernel** is `supabase/functions/_shared/devMcpBidSubmission.ts`. Its reads come in through the seat's `Reader` (the bid, the prefixes and `app_settings`, as the dev under RLS) and `DriveGet`, so the tests stand in for the database and for Drive.

## The plan and the hash

The plan writes nothing, in the app or in Drive: it reads Drive on the read-only token, and the full `drive` token is minted in the copy alone, after the hash matched. It commits to the bid, the link it carries, the project folder as it stands, the file's name, size, md5 and sha256, and what Sent by us already holds. It commits to no clock: the note is stamped when the apply writes it. A file changed, renamed or trashed since, a link set since, a folder made since or a paper filed since each refuse the apply.

## What is refused, each in its own words

A bid that already has a submission link unless `replace: true`, with the link named; a bid already linked to this paper; a file in the trash; a folder; a shortcut; a Google Doc, Sheet or Slides (download it as a PDF); a file the service account cannot open; a project folder link that is not a folder, cannot be opened or added to, or sits in a personal Drive (`bidFolderHoldWords`, without its line about photos); a bid with no folder while no jobs root is set; a file outside the Shared Drive that is over 10 MB, empty, or that Drive will not hand over; a copy Drive forbids. A second apply of a plan that landed is refused from the call log, before the hash.

## What it does not do

It logs no contact with its method (the Bid Board's Log contact has no verb yet). It does not set the sent date, who the bid went to or the outcome: that is `plan_bid_update`. It neither moves nor removes the original, and it tells nobody.

## One call left with the owner

`bid_submission_link` holds one link and a bid can hold several papers (a revision, a second option). As built, each paper is filed in Sent by us and the newest filed keeps the link; the plan says so and names the papers already there. Whether the link should be the Sent by us folder once a bid holds more than one is the owner's to say.
