# v2.8256 — Permits: a San Antonio application learns the day its permit was issued (2026-11-21)

Punch list #405 ([the card](../../to-dos/permits-market-page/README.md)), found while building the line *San Antonio's clock reads short* on its *Seen while building, not done* list. Taunya said to build that line on 2026-11-21. The clock is to say how many applications still wait, and the stored rows could not be trusted to say it.

## What was wrong

San Antonio publishes its applications as one feed. A row is filed on one day and takes its permit's issued day weeks later: the middle wait is 50 days. `permit-pull` read that feed by filing day, from ten days before the newest filing day it held. So an application was read for about ten days after it was filed and never again.

- An application that got its permit after that kept reading as still waiting.
- Market's clock, application to permit, counts only applications that carry both days. Every application read by the nightly pull would have stayed off it. The clock stood on the rows read back as history in November, and would have run dry as they aged out of its twelve months.

Read on prod on 2026-11-21, counts only: of 1,833 commercial applications filed in a year, 824 read as waiting, and 714 of those had last been read on the first two days of the feed. The city's own feed that day said 1,854 filed and 1,042 with a permit, against 1,833 and 1,009 held. So some thirty applications had taken their permit without the app hearing of it. The gap was small because the app had read the feed for only twelve days. It would have grown every week.

## The fix

`permit-pull` reads a feed of applications a second time in the same run, by the day each row's permit was issued.

- A reader says it can be read that way with `issuedPageUrl`. San Antonio's applications feed has it. The page query is the one `feedPageSql` already writes, with the feed's date column set to `DATE ISSUED`.
- `feedPasses` in `_shared/permitCities.ts` lists a feed's readings: one for every feed, two for a feed with `issuedPageUrl`, and one on a read back as history.
- The second reading starts ten days before the newest issued day held on that feed's rows. It keeps the same kinds of permit and upserts on the same key.
- A row read again keeps its `backfilled` flag and the day it was first seen. Only the columns the feed sends change.
- The feed's answer says where the second reading started (`issuedSince`). `permit_pulls.since` stays the first reading's day, so where a city's records start does not move.

The second reading is small: the city's feed held 114 rows of the kept kinds issued in the first two weeks of November.

## Tests

`permitCities.test.ts`: San Antonio's applications feed has two readings and its issued feed one; the second reading's query asks the applications feed by `DATE ISSUED`, oldest first, and keeps the same kinds of permit as the first; a read back as history makes one reading; no other city's feed is read twice.

The second reading's first page, as the pull builds it, was asked of the city's feed by hand on 2026-11-21. It answered 101 rows issued from 2026-11-03 to 2026-11-13, each with its issued day, 48 of them commercial applications. The pull itself has no run test and was not run from this branch.

## Deploy

`supabase functions deploy permit-pull` once this is on main. The first nightly run after the deploy starts its second reading ten days before the newest issued day held. That day is 2026-11-03, and the oldest read of any row is 2026-11-09, so the run catches up by itself. The proof is that the app's count of applications with a permit then matches the city's.

`permit-lookup` bundles the same shared file and will read as behind on the edge drift check. Its behaviour does not change.
