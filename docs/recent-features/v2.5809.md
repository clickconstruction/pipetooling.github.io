# v2.5809 — Prospects → Subs: drag a card to pin it, and Call first · Normal · Later on every sub (2026-10-24)

Punch list #153, PR 3 of 4 (`to-dos/subs-bench-board/`), on PR 2's v2.5808. The owner's words: "we can rank the responsiveness of people or the priority of people". The board stores the two things only a person knows and computes the rest.

- **The migration** [`20261024010000_prospect_trade_ranks.sql`](../migrations/20261024010000_prospect_trade_ranks.md): `prospect_trade_ranks` (one row a company a trade: a pin at `rank_order`, dense among the column's pins; no row means the card flows) and `prospects.priority` (1 Call first, NULL Normal, 3 Later), both behind `user_has_prospects_staff_access()`, the three fences applied. Pushed with `supabase db push` before the client deploy (additive; the old client ignores both), the types regenerated in the same PR.
- **The kernel** ([`subsRanks.ts`](../../src/lib/prospects/subsRanks.ts), [tested](../../src/lib/prospects/subsRanks.test.ts)): `pinsByTrade` reads the rows case-blind by trade, `pinAfterDrop` puts the dragged card where it landed among the pins (a drop below them pins it last among them, since pins sit first and the flow keeps its own order), `unpin` lets it flow, `rankWrites` says what to upsert dense from one and what to delete. `orderColumn` (v2.5808) already put pins first and the priority over the record.
- **The board** ([`SubsBoard.tsx`](../../src/components/prospects/SubsBoard.tsx)): dnd-kit's `DndContext` over the columns and a `SortableContext` a column; a card's sortable id carries its trade, since a sub sits in two columns; the handle ⠿ draws when the page passes `onDrop`; the *pinned* chip is a press when `onUnpin` is passed; the priority picker (Call first · Normal · Later, `PRIORITY_CHOICES`) draws under `onPriority`.
- **The page** ([`Prospects.tsx`](../../src/pages/Prospects.tsx)): `laneRanks` / `lanePins` read by `loadLaneRanks` with the board's extras and on By rank, `dropOnBoard` → `writePins` (paint first, write dense, reload the truth on a refusal), `unpinOnBoard`, `savePriority` patching every cache; `PROSPECT_COLUMNS` carries `priority`; the deck's utility row shows the three priority presses on Subs where the warmth flame stood (decision 7: warmth retires on Subs); By rank reads the filtered trade's pins.
- **Guide**: *find subs for the bench* § Pin a card and set a priority. **Docs**: `ACCESS_CONTROL.md`'s Prospects bullet, the Prospects map, the Glossary.

## Is this the best we can do?

- Two stored facts, both the office's own words; the record and the order stay computed, so the board and the bench never disagree.
- A pin is per trade, so dragging a sub up for Fire sprinkler never moves it in Sitework.
- Checked live as the dev with the ZZ sub: the drag pinning it to #1 with the chip, the unpin, Later sinking it to the foot, Call first on the deck's card.
