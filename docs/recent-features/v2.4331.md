# v2.4331 — Submittals: Split keeps a row's parts (2026-10-01)

Found while building the draft refresh (the parts train after v2.4319): a batch insert to PostgREST fills a field that one row of the batch leaves out with NULL, not the column's default. **Split** on a row with parts inserts the first tag's carried parts (with their `procure_key`) in one batch with the other tags' copies (no key), so the copies sent `procure_key = NULL` and the insert failed on the NOT NULL. The rows had already split by then, so the new rows came out with no parts. The same shape mix would hit any later caller that batches parts with and without a call (`decision_source` is NOT NULL too).

## What changed
- `insertItemParts` (`src/lib/submittals/itemPartsIo.ts`) sends one shape per batch: `partInsertBatches` groups the rows by the fields they set (a field set to `undefined` counts as left out), then 200 at a time. Every caller is covered without changing its rows.

## Tests
- `src/lib/submittals/itemPartsIo.test.ts`: a split's carried part and copies land in separate batches; `undefined` is a left-out field; one shape still pages at 200.
