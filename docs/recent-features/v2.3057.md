# v2.3057 — Controller and the clock: verified, no gap (2026-09-07)

Docs only. No client behaviour, migration or edge-function change.

## The question

The owner-decisions list carried, since v2.2962: "Jobs → Team lets dev + controller act on chips, but the `clock_sessions` UPDATE policy (2026-06-05) passes only dev, team leads, pay-approved masters and their adopted assistants — add `is_controller()` to that policy, or leave controllers to People → Hours?"

## What the migration history says

- `20260605202851` created `clock_sessions select access` / `update access` naming `is_pay_approved_master()`.
- `20260714213000` (controller capabilities) redefined `has_payroll_access()` as `is_pay_approved_master() OR is_controller()`.
- `20260714230000` (controller payroll capability sweep) rewrote **every** policy and function body that named `is_pay_approved_master` to `has_payroll_access`, from `pg_policies`, and raised if any remained. The two `clock_sessions` policies were among them.
- No migration after the sweep recreates either `clock_sessions` permissive policy (only the read-only restrictive pair, v2.1066, and triggers).

So a controller has passed the clock-sessions select and update policies since 2026-07-14. The v2.2962 caveat was read from the 2026-06-05 file text, which the sweep made stale in the live database — the same "the file is not the policy" trap as the dynamic role sweep of 2026-09-06.

## What changed

- The decision line is retired and the answer recorded in the same file.
- `docs/ACCESS_CONTROL.md` Team-tab line now says how a controller passes and why the earlier caveat was wrong.
- The `partialLinkMessage` comment in `linkClockSessionsToPick.ts` no longer names controllers as the example refusal (team leads off-roster and assistants without pay access remain).
