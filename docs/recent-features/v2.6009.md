# v2.6009 — Honest and fast, PR 1: the slow strip and the auth gate's hold (2026-10-28)

Punch list #183 ([`to-dos/honest-and-fast/README.md`](../../to-dos/honest-and-fast/README.md)), the first of five PRs, shipped alone. During a database freeze every live read hangs, so a daily screen showed a spinner, two grey bars or a blank, and a person could not tell a freeze from a dead app; a cold open offered the cache-repair page at 5 s and fell through to sign-in at 8 s, so a freeze read as being signed out. The owner's line, from his holistic look of 2026-10-26: *"a plain line when the database is slow."*

## What changed

- **The kernel** [`src/lib/appHealth.ts`](../../src/lib/appHealth.ts) (+59 tests): one store, the subscribe shape of `unsavedWork.ts`, fed by a third fetch wrapper on the Supabase client (`wrapFetchReportingHealth`, outermost in `supabase.ts`) that reports every `/rest/v1/` and `/auth/v1/` request's start and end — a function call or a file upload has its own clock and is not watched. Four states: **fine**; **slow** when something has waited 4 s and nothing landed in those 4 s, or a response in the last 30 s carried a freeze code (`57014` the statement timeout, `57P03`, `53xxx`, `08xxx`, `PGRST000`–`003`, or HTTP 502/503/504/522/524, read out of the error body); **unreachable** on a fetch-layer failure while the browser says online with nothing landing for 4 s, or 20 s waiting with no answer of any kind; **offline** on `navigator.onLine`, #163's state held here so one strip owns the words. A freeze-coded response is an *answer* (the server spoke, so a pileup stays slow and never turns red) but not a *landing* (it never clears slow). A landing clears both. The strip holds 3 s once shown. `nextChangeAt` tells a reader the next instant the reading could change with no new event, so `useAppHealth` sets one timer instead of polling; `resumed()` on `visibilitychange` / `pageshow` restarts the waits, so a throttled background tab never paints a stale strip on return.
- **The strip** [`AppHealthStrip.tsx`](../../src/components/AppHealthStrip.tsx) (+ render smoke): the first row inside `.appNavChrome` in `Layout.tsx`, in flow above the nav so it pushes the nav down a line rather than covering it (no new fixed layer, so `check:window-z` and `check:status-bar` see nothing). While it shows it takes the iPhone status-bar padding on itself and the nav keeps its plain padding (`.appNavChrome:has(.appHealthStrip) > .appNav` in `index.css`). Amber *The app is slow right now.*; red *Could not reach the app.* with **Retry**, which reloads the page (the shell is precached, and a per-page retry would need every page to expose its reads); grey *No signal.*; a dev's screen adds *Run /db-freeze before anyone restarts.* once the trouble is a minute old. It is the strip #163's waiting bar will use — the health words first, the queue's count and door after — so a phone never carries two bars. *Nothing you pressed is lost.* waits on #163's queue; *The page you see was read at 7:52 AM.* on PR 2's stamp.
- **The auth gate** (`useAuth.ts`, `App.tsx`): the 8 s `getSession` watchdog and the 4 s role-gate watchdog hold while the kernel says slow or unreachable, looking again every 2 s, so a freeze no longer lands a cold open on sign-in or on a role-less app; a wedged auth lock makes no request, so the kernel stays fine and both give up as before. A role read the freeze failed (its statement timeout, or any refusal while the app is slow) is read again every 5 s instead of settling a null role for the session. Past 5 s the gate's screen reads *The app is slow right now. Keep this open.* while the kernel holds and offers no cache-repair link; the link stays for the case where no request could start.
- **Guide** *know what to do when the app is slow* (`src/content/help/know-what-to-do-when-the-app-is-slow.md`), for every role.
- **Docs**: `PROJECT_DOCUMENTATION.md` (Layout), `GLOSSARY.md` (UI/UX Terms), `DB_FREEZE_RUNBOOK.md` (the signature), the to-do's status.
