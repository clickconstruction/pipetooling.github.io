# v2.7705 — Lien notices: a mail number for each envelope when you record a notice already mailed (2026-11-17)

## Why

The owner scanned the divider pages of a notice run, each with its certified mail number written in by hand, and found the desk's record wrong. A § 53.056 notice goes to two recipients, the owner of record and the original contractor. Each envelope has its own certified label. The Lien desk's *Already mailed? Record it…* form had one **Tracking** box, and `byHandSends` wrote that one number on every recipient's send, so a notice recorded by hand carried one envelope's number on both.

The divider page also asked for "20 digits from the certified label", and the hint under a number box said a certified number has 20. The labels the office buys at the counter carry 22, which `trackingShape` already accepted.

The dev seat's `plan_notice_numbers` (v2.7687) corrects a notice after the fact. This change fixes the form.

## What changed

- **`src/lib/jobs/lienNoticeByHand.ts`** (the form's kernel, mirrored for the dev seat):
  - `ByHandInput.trackingBy?: { owner?, original_contractor? }` holds each envelope's own number. When it is given and the method is certified mail or a courier it rules: a recipient it does not name has no number, and `tracking` is not read.
  - `byHandSends` writes each send through `byHandTrackingFor`, so each recipient's send carries its own envelope's number. `byHandFilingPayloads` is unchanged and inherits it on every covered job.
  - `byHandNumberBoxes` says which recipients get a box of their own: everyone the paper went to, when a carrier took it. Mail, email and hand delivery get none and keep the one box.
  - `byHandNumberShape`, `byHandSameNumberTwice` and `byHandNumberNotes` are what the form says about the numbers. None of them is in `byHandProblems`: a wrong length or a repeated number never stops the record, as in the run window, since the post office may hand a number back later and an owner who is also the contractor at one address gets one envelope.
- **`src/lib/jobs/lienSendTracking.ts`**: `trackingShape` and `TrackingShape` moved here from `lienDeskRun.ts`, which re-exports them, so the by-hand kernel and its mirror reach the rule without the run's kernel. The copy under `_shared/gcKernels/` already held this file, so the copy gains no file and its index does not change: `dev-mcp` is the only function whose bundle moves. The wrong-length hint now reads *a certified number has 20 or 22* (`CERTIFIED_DIGITS_WORDS`). `trackedMethod` is exported.
- **`src/components/jobs/LienNoticeByHandPane.tsx`**: the recipients' ticks moved above the number. Certified mail or a courier draws one box for each recipient ticked, named *Tracking — owner of record* and *Tracking — original contractor* when there are two and *Tracking* when there is one. Each number is kept under its own recipient, so unticking one never moves a number to the other. A certified number shows the run window's hint as it is typed, and one number in both boxes shows an amber line. Both layouts (the box and the phone's sheet) share the state.
- **`src/lib/jobs/lienRunPaper.ts`**: the TRACKING NUMBER box on the run's checklist sheet and on each divider page is captioned *20 or 22 digits from the certified label*.
- **`supabase/functions/_shared/devMcpNoticeByHand.ts`** (server 0.101.0): `plan_notice_by_hand` takes `tracking_by: { owner?, original_contractor? }` beside `tracking`. It is refused with `tracking`, with a method that is not a carrier, and when it names a recipient `to` leaves out. `tracking` alone still writes one number on every send, and for two carrier envelopes the plan says so under `check_the_numbers`. The already-recorded check reads either form. The key is left off the payload when not given, so a plan with one number hashes as it did.
- The guide *send lien notices from the Lien desk* says how to type the two numbers, and says 20 or 22 digits.

## Not changed

No live record. The notices recorded before this keep the sends they have. `plan_notice_numbers` is the door for those.

## Deploy

`supabase functions deploy dev-mcp` from `main` after the merge. `whoami` answers 0.101.0. No migration.
