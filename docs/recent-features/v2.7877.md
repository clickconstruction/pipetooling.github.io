# v2.7877 — Painted maps: Text it from my phone… opens Messages the moment you press (2026-11-18)

Punch list #394, step 3, on the owner's word the same evening as the walk: *Build all the steps and let me know when it is all live.*

## Why

The walk on an iPhone (v2.7863) showed Safari does not refuse to open Messages after the wait for a link. It asks first: *Open this page in “Messages”?* With a link already out, the same press opens Messages at once. The difference is whether the address is handed over inside the press. So the phone now knows the address at the press.

## What changed

- **The phone picks the link's code** (`pickPaintedMapLinkCode`): ten letters from the same alphabet, from the phone's own random source. The address is known before the server has answered.
- **The press sends the ask, then opens Messages, both inside the press.** `registerPaintedMapLink` is not an `async` function on purpose: with the session at hand the ask is on its way before it returns, and it is sent with `keepalive` so it finishes after the page is left. A lost signal gets one more try for the same code.
- **The sheet asks first whether a link can be made** (`desk.can`, `canMakePaintedMapLink`), on opening, on a phone alone. Nothing is written. Only on a yes is a text handed over at once, so a text is not written around a link the server would refuse: a training account, a map with nothing on it, twenty links out. That ask also reads the session, which is what puts it at hand for the press.
- **Without that yes the sheet works as it did:** the link is made first, then Messages, with *The link is ready. Press Open Messages.* if the phone opens nothing.
- **If the link is refused or lost after the text is written,** the sheet says the reason and *The link in that text will not open. Do not send it.* Those words stay when the page is left and come back to.
- **Every other press makes its link the same way,** with the phone's code, and waits for the server before it acts, as before.

## The function

`painted-map-link`, redeployed after this merge:

- `desk.mint` with a `code` keeps that code's hash and answers `{ ok, kept: true, endsOn }`, never the code. A code that is not ten letters of the alphabet is refused, not replaced. The same caller asking twice for the same code on the same map gets the same answer. A code another link holds is 409.
- `desk.can` runs every refusal a mint would give and writes nothing.
- `desk.mint` with no code is unchanged, so the client that was live before this one keeps working across the deploy.

**Either order is safe.** A new client on the old function gets *That did not go through* to `desk.can`, so it never uses the instant path, and the old function's own code is taken as the link. An old client on the new function sends no code.
