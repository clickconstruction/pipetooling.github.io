# v2.8681 — Jobs: a ZZ test job a developer deletes takes its Drive folder to the trash (2026-11-26)

Punch list #443, row 18. An edge function and the client. No migration. **Owed after the merge: one deploy, `job-drive-folders`.** Until it is deployed the app asks, the old function answers that it read no job, and the toast says the take-back is not known yet: the job is deleted as before and its folder stays as before.

## The press nothing took back

**Create Job**, on any new job. The form asks `job-drive-folders` for the folders as it saves, and a sweep every ten minutes makes them for a live job that has none: the customer's folder under the jobs root, the job's own folder under it, and the folders inside. **Delete** on the job took the job and left every folder. Two ZZ Test jobs a walk made and deleted on 2026-11-26 left theirs for a person to remove by hand.

## What was read first

- **The delete is the client's.** `JobFormModal.deleteJob` sends one delete on `jobs_ledger`. No function is called and nothing touches Drive. The two migrate-and-delete paths go through their own database functions.
- **The job is still known after it is gone.** A `BEFORE DELETE` trigger copies the whole row into `deleted_records_archive` (`row_data`), kept 90 days, which is what Recently deleted restores from. So the server still holds the job's name, its customer's name and its Drive link.
- **The function never removed anything.** `FolderTree.placeJob` (`_shared/jobFolders.ts`) finds, makes, moves and renames. A job made from a bid takes the bid's own folder: it is moved under the customer and its link is written on the job.

## What changed

- `supabase/functions/_shared/deletedJobFolderTrash.ts`, the rule, pure, read by the function and by the app's tests. One function a stage: the caller, the job, the link, the folder, what still keeps it, what it holds.
- `supabase/functions/job-drive-folders/index.ts` carries a sixth body, `{ trash: { job_id } }`. It reads the facts, asks the rule, and makes the one write: `trashed: true` on the folder, with a note in the folder's description that says why it is in the trash and which job it was. It never calls Drive's delete. The write is the one `drive-link` has made since v2.7699 for a file taken off a job, so its shape is already live.
- `src/lib/jobs/deletedJobFolderOffer.ts`, the app's half, pure: who is offered it, the Delete window's line, the function's answer as the app reads it, the toast.
- `src/lib/jobs/jobDriveFoldersIo.ts`: `trashDeletedJobFolder(jobId)` and `afterDeleteJobFolder(jobId, job, role)`, which never throws.
- `JobFormModal.tsx` asks after a delete that went through, and `JobFormDeleteMigrateModals.tsx` draws the line in the Delete window.

## The order: the delete first, the folder after

The app deletes the job, then asks the function with the job's id alone. The function reads the job from Deleted records, so nothing the caller says decides which folder goes. A job that still stands is refused, so a folder can never be in the trash under a job that is still there. A delete that fails asks nothing.

## Who, and which job

- A dev alone. The function checks the role itself, after its own gates for a training account, a digital twin and an archived caller. The app asks only for a dev.
- A ZZ-named job alone, by the app's one rule, `isZzTestJob`: its own name or its customer's starts with ZZ. The function reads the names from the kept copy.
- Everyone else's delete, and every real job's, is as it was: no line, no call, no toast.

## What happens to a folder that holds a file a person added

**It stays, and the toast counts the files.** Before the write the function reads everything the folder holds, folder by folder. A file last changed by any account but the app's own was put there, or changed, by hand. One such file keeps the whole folder: *A person added or changed 2 files in this folder by hand. It stays. Move them out, or trash it in Drive.* Folders are not counted, since an empty folder holds nothing.

- The app's own account is the service account. Drive says so itself for each file (`lastModifyingUser.me`), or names the account. When Drive says neither, the file counts as a person's.
- A file the app put there under the upload account some functions use (`DRIVE_IMPERSONATE_USER`) counts as a person's too, so that folder stays. That errs toward keeping.
- A folder too large to read whole stays: past 60 folders read or 2,000 things counted.

## What happens when the folder is already gone

**Nothing, said plainly, and it is not an error.** Each of these answers as a success and writes nothing, so a second ask on the same job is safe:

- The job kept no Drive link, or a link that is no folder's: *This job had no Drive folder on record. Nothing went to the trash.*
- Drive no longer shows the folder: *Its Drive folder is already gone, or the app can no longer open it. Nothing went to the trash.*
- The folder is already in the trash: *Its Drive folder is already in Drive's trash.*

## What else keeps a folder

- **A record still keeps it.** A live bid, another live job or a customer whose link names the folder: *1 bid still keeps this folder. It stays.* This is the job made from a bid.
- **It is not a job's folder.** The jobs root, or a folder straight under it, which is a customer's or *No customer yet*.
- **It is somewhere else.** A folder in a My Drive, or one that does not sit under a folder of the root.
- **Drive will not let the app.** The answer names the app's account to make a content manager of the Shared Drive.
- **The job still stands**, or Deleted records keeps no copy of it, or it was not named ZZ.

## What is not built

- **The customer's folder stays, empty or not.** The card's row asked for it to go when it is left empty. The customer is usually still there when its job is deleted, and its link names that folder: a folder in the trash under a live customer would take the next job's folders with it. It belongs with a ZZ customer's own delete, which is not built.
- **Migrate and delete** leaves the folder, on both paths. That press moves a job's work onto another record, and its files may be wanted there.
- **No put-back in the app.** A job brought back from Recently deleted keeps its link to a folder in the trash. A manager of the Shared Drive restores the folder in Drive, within 30 days.
- **No press for a job deleted earlier.** The two folder trees a walk left on 2026-11-26 belong to jobs deleted before this was built, and the app asks only at the moment of a delete. The function could take them: it reads Deleted records, which keeps a job 90 days. No screen asks it to. A line on a deleted job in Recently deleted would be the place.
- **The names beside an older file.** `src/lib/jobs/jobFolderTrash.ts` is v2.7699's, a file taken off a job. These files are named `deletedJobFolder…` to stand apart from it.

**One thing the reference does not settle.** It says `lastModifyingUser` is filled only when the last change was made by a signed-in user, and does not say whether the app's service account counts as one. If Drive leaves it empty for the app's own uploads, every file counts as a person's, and a test job's folder that holds a photo stays. A folder that holds only the app's five folders goes either way, since folders are not counted. That is the shape of what the walks left. The first press on a folder with an app-filed photo in it settles this.
