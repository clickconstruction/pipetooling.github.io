# v2.6390 — A bid marked lost with every GC now leaves Not yet won or lost, even with a same-letter GC on it (2026-11-02)

Grace, through the owner, 2026-11-02: *I am trying to clear out bids I have followed up on and we lost. I marked lost on everything but it is not clearing off the bid board.* The bid is BP391, RBFCU Potranco San Antonio, open on the Edit tab with three GC cards all reading lost and the pile row still counting it under Pending.

## The cause, with the rows

`bids.outcome` was NULL while all three `bid_versions` rows read `lost` (Structura, the bid's own GC, `gc_lost` on 2026-11-02; PlanHub and the Wrenman Commercial version, both `price` on 2026-10-27 and both on PlanHub's customer id). Each version had a `bid_version_sends` row dated 2026-09-01. `bid_gc_recipients` held two GCs: PlanHub (source `version`) and **Wrenman Commercial on its own customer id with no version of its own** (source `manual`). `groupVersionsByGc` turns that second recipient into a **shared-letter packet** carrying the bid's sent date and no outcome, and `rollUpOutcome` counted it as a sent packet with no answer — so the all-lost rule never fired, `setGcPacketOutcome` never wrote `bids.outcome = 'lost'`, and the board's pile rule (`getSubmissionSectionKey`, which reads the bid's column) kept the bid in *Not yet won or lost*. The shared-letter card offers no Won / Lost… of its own (its answer *is* the bid's), so Grace had no press left that could move it: the GC whose answer is tracked with the bid was holding the bid's answer.

## The fix

- `rollUpOutcome` (`src/lib/bids/gcPackets.ts`) skips a shared-letter packet with **no answer of its own**: unanswered, it rides the bid and is not a GC still waiting, as `perGcSentSummary`, `resolveWinningPacket` and the Won cascade already treated it. An answer set on a shared-letter packet (the writer's in-memory `packetsAfter`; no card offers it today) is the bid's answer and counts as before — the first push dropped it and `gcPacketOutcome.test.ts` caught it. The bid room's `roomRollUpOutcome` (`supabase/functions/_shared/bidRoomOutcome.ts`) mirrors it; `bidRoomOutcomeParity.test.ts` holds both to the same answers, shared-letter cases included.
- `archiveFromBoardBlockedReason` (`src/lib/workingBoardArchiveEligibility.ts`) takes the bid's packets (`gcPacketsByBid[bid]` from `Bids.tsx`, both call sites). On a sent bid with real packets the words name each GC's card in the Sent panel — the Win / Loss segment the old words pointed at is locked on a per-GC bid. When every real GC has said no but the bid still reads open, the words say the bid belongs in Lost and name the press that rolls it up (*↩ waiting*, then *Lost…*, on one card). A sent bid that is already Won, Lost or Started says it is off the working piles and there is nothing to archive, in place of *set Win / Loss to Lost instead* on a bid that was Lost already.
- Guides *read the bid board* and *bid one project to multiple GCs* say a same-letter GC never holds the bid open; `GLOSSARY.md` (bid versions entry), `docs/BIDS_SYSTEM.md`, `docs/PER_GC_BID_PLAN.md` and `docs/BIDS_BOARD_FORM_ARCHITECTURE.md` carry the amended rule.
- Tests: `gcPackets.test.ts` (+4: BP391's exact shape through `groupVersionsByGc`, the roll-up to Lost and the pile rule filing it under Lost, a shared-letter GC alone deciding nothing either way, a real GC still waiting holding the bid open), `bidRoomOutcomeParity.test.ts` (+2 cases, +1 test), `workingBoardArchiveEligibility.test.ts` (+4, and the sent-and-lost test now holds the full new sentence).

## The pile, counted

A dev-mcp read of every open sent bid (`outcome` NULL, `bid_date_sent` set, not adopted) found 128 across all trades, 102 of them Plumbing — the board's *Pending 102*. Of those 128, **exactly one has any lost version at all: BP391.** No other Pending bid moves with this fix, and no bulk rewrite is needed.

## What moves BP391 (the owner's call)

The fix changes the next write, not the stored column: BP391's `bids.outcome` stays NULL until a GC's answer is set again. Either press *↩ waiting* and then *Lost…* (GC lost the project) on the Structura card once the deploy is live, which re-writes the same rows and rolls the bid up, or run this one-row statement:

```sql
-- BP391 only: every real packet is lost (gc_lost / price / price) and bids.outcome is still NULL.
UPDATE public.bids
   SET outcome = 'lost'
 WHERE id = '2b32fad5-152c-4124-9f90-74b10057c473'
   AND outcome IS NULL
   AND bid_date_sent IS NOT NULL;
```

The census the owner can repeat (expected: one row, BP391):

```sql
WITH packet AS (
  SELECT v.bid_id, v.customer_id,
         (array_remove(array_agg(v.outcome ORDER BY v.sort_order), NULL))[1] AS outcome,
         bool_or(EXISTS (SELECT 1 FROM public.bid_version_sends s WHERE s.bid_version_id = v.id)) AS sent
    FROM public.bid_versions v
   GROUP BY v.bid_id, v.customer_id
), rolled AS (
  SELECT bid_id,
         bool_or(outcome = 'won') AS any_won,
         count(*) FILTER (WHERE sent OR outcome IS NOT NULL) AS counted,
         count(*) FILTER (WHERE (sent OR outcome IS NOT NULL) AND outcome = 'lost') AS counted_lost
    FROM packet GROUP BY bid_id
)
SELECT b.id, b.bid_number, b.project_name
  FROM public.bids b JOIN rolled r ON r.bid_id = b.id
 WHERE b.outcome IS NULL AND b.bid_date_sent IS NOT NULL AND b.adopted_into_bid_id IS NULL
   AND NOT r.any_won AND r.counted > 0 AND r.counted = r.counted_lost;
```
