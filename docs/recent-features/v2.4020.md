# v2.4020 — The bill email comes from us, with a QR code and a short address to the customer's statement (2026-09-28)

The statement link on a Stripe invoice read `https://clicktooling.com/portal?t=<64 hex>&paid=1` for every customer without a saved short address, and the owner asked for a QR code instead. Stripe's invoice email, hosted page and PDF take no image (the `footer` is text; `custom_fields` are text), so the code cannot sit on anything Stripe draws. The email is the one surface we can own: `send-stripe-invoice` now sends it.

## The email — `_shared/stripeBillEmail.ts`

`buildStripeBillEmail(input)` → `{ subject, text, html }`, pure. Letterhead bar, greeting with the service address, *Invoice #…*, the amount, the due date, **Pay now**, the PDF line, and — when the payer has a portal — a cream card: the QR code (120 px, linked) beside **Your account, any time**, the address in words, and one line of what it is.

- **Pay now is `payLinkAddress(APP_ORIGIN, <jobs_ledger_invoices.id>)`** — the `/pay/<id>` page (v2.3754), which asks Stripe for the current hosted link at click time. The email never carries `hosted_invoice_url`, which expires 30 days after the due date.
- **The service address, never the job name or number.** The portal's rule for what a customer reads; the copy email (to the payer's own people) keeps its job label.
- **The address in words** comes from `portalAddressInWords`: scheme and trailing slash dropped, `null` for an address with a query (a token link, whose key is the query) or one past 48 characters — the link then reads *Open your statement*. The code still carries the full address.
- **The code is an inline attachment**, `content_id: 'portal-qr'`, read as `<img src="cid:portal-qr">`. Mail clients do not draw SVG and strip data URLs; Resend's note that some webmail rejects inline images is why the address is always printed beside it and the card stands without the image.
- **`testIntendedFor`** prefixes the subject with `[Test]` and puts one banner line above the letterhead naming the address the email did not go to.

## The code — `_shared/qrMatrix.ts` and `_shared/qrPng.ts`

Both dependency-free, so the Deno function and vitest share them and a bill never waits on a package fetch.

- `qrMatrix(text)` — byte mode, level M, versions 1–10 (213 bytes; a short address is about 45, the token address 98), `null` past that. Laid out the way Project Nayuki's generator (MIT) does it, which is the encoder inside `qrcode.react`. **`qrMatrix.test.ts` holds it to `qrcode.react` module for module**: the short address, the token address, the longest text of every version 1–10, and non-ASCII text. The reference is read back out of the `<path>` `QRCodeSVG` renders with `boostLevel: false`.
- `qrPngBytes(modules, { scale, quiet })` — one bit per pixel, greyscale, stored deflate blocks (no compressor), 8 px a module and the spec's four-module quiet zone by default: a short address is a 33-module code, 328 px and about 14 KB; the token address is 41 modules, 392 px and about 20 KB. `qrPng.test.ts` reads the file back with its own CRC arithmetic and Node's `inflateSync`, pixel by pixel, including an image large enough to span several stored blocks.

## The short address — `_shared/portalShortAddress.ts`

`ensurePortalShortAddress(admin, customerId, createdBy)` returns the saved slug, or assigns one when the customer's main (`all`) link is live and no slug is saved; `null` otherwise, and it never throws.

- The slug is the globe's own default: `suggestSlugFromName(name)` + `appendRandomTail`. A name a slug cannot keep becomes `account-<tail>-<tail>`. The random source is `crypto.getRandomValues` — the tail is what keeps a statement private.
- Inserted with `locked_at = now()` and two `customer_portal_slug_events` rows (`created`, `locked`), `created_by` the signed-in sender: an address that has gone out on a bill is shared.
- A taken address (unique violation, or a sub holding it — `sub_portal_slugs` shares the printed namespace) tries the next tail, five in all. A concurrent send that assigned one first wins; its slug is returned.
- The slug kernel moved to `_shared/portalSlug.ts`; `src/lib/portal/portalSlug.ts` re-exports it.

Called from **`send-stripe-invoice`** (the payer, from `payerCustomerId(effectiveInvoiceParty(…))`) and from **`create-stripe-invoice`** (before `loadPortalReturnUrl`, so the invoice footer reads the short address too). Both skip it on a test-mode bill and on a typed bill-to.

## Who sends — `_shared/billEmailPlan.ts`

`planBillEmail({ sender, hasResendKey, stripeMode, customerEmail, callerEmail })`:

| Case | Plan |
|---|---|
| `BILL_EMAIL_SENDER=stripe` | Stripe, `configured` |
| no `RESEND_API_KEY` | Stripe, `no_resend_key` |
| test mode, the caller has an address | ours, to the caller, `testIntendedFor` the customer |
| test mode, no caller address | Stripe, `test_without_sender` (Stripe delivers nothing in test mode) |
| live | ours, to the customer |

When ours is planned and Resend refuses it (or anything in the build throws), the function calls `stripe.invoices.sendInvoice` exactly as before and answers `fallback_reason: 'send_failed'`. The response gains `sent_by`, `delivered_to`, and optionally `fallback_reason` / `test_redirected`; `src/lib/billing/billEmailOutcome.ts` turns them into the toast and the green line, and reads an answer with no `sent_by` as Stripe's — so this client works against the function before and after it is redeployed.

The invoice PDF is fetched from `invoice_pdf` (10 s, 8 MB, must begin `%PDF`) and attached; when it cannot be, the email links it instead. Logged to `email_send_log` as `stripe_bill`. Reply-To is the sender, as on the copies. The copies themselves are unchanged.

## The app

- `StripeInvoiceSendFromStripeButton` — the confirm reads *Email this invoice?*, says where the email goes and that paying is on Stripe (test mode: that it comes to you), and the button is *Yes, send it*. The green line is the outcome's own sentence and survives a remount in `sessionStorage`.
- `CollectPaymentModal`, `SendRecordInvoiceModal` — the three labels that said Stripe emails the customer.
- Settings → What customers see: the homeowner's **Bill email** step renders (`SampleEmailId 'bill-email'`, `buildSampleBillEmail`) — the send function's builder and QR code over the sample job, the code inlined as a data URL since a browser cannot load `cid:`. `EMAIL_CATALOG` gains `stripe_bill`.

## Not changed

No migration. The `stripe` tag on the button stays: it is still a Stripe bill. Bills already sent keep the footer they were created with. Stripe's own account-level emails (receipts, reminders) are whatever the Stripe Dashboard says; `docs/BILLING_FLOWS.md` lists them as off.
