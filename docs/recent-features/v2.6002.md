# v2.6002 — Lien waivers kept on a bid read right on every job surface; types regenerated (2026-10-27)

v2.5958 (#6296) let a waiver live on a bid (`job_lien_releases.bid_id`, `job_id` nullable, exactly one set) and v2.5985 (#6322) added `notary_copy_path`; both migrations reached prod without a types regen, so main's `src/types/database.ts` still read `job_id` as a string. A fresh regen (PR #6347, closed unmerged) showed eleven TypeScript errors across five job surfaces that indexed, filtered and emailed by `job_id` as if every waiver had a job. This change makes each of those surfaces say what it does with a bid's waiver — reads the job rows, leaves the bid's where it is — and ships the regen with it.

## What changed

- **Kernel** ([`lienReleaseTracking.ts`](../../src/lib/jobs/lienReleaseTracking.ts)): `JobScopedLienReleaseRow` (a row kept on a job), `isJobScopedLienRelease` (the guard) and `lienReleasesOnJobs` (the filter that leaves a bid's waiver out on purpose, order kept). `owedLienReleasesByJob` groups the job rows only: a bid's waiver has no bills behind it, so nothing clears it and no unconditional follow-up is owed from the Dashboard's count or its queue.
- **Lanes** ([`lienReleaseInboxLanes.ts`](../../src/lib/jobs/lienReleaseInboxLanes.ts)): `LienInboxFetchedRow` is what the hook reads (its job joined, null on a bid's); `LienInboxRow`, a lane row, is a job's. `splitLienSignatureLanes` keeps the job rows: the lanes are a job's signing loop (asked for → signed → sent to the job's payor), and a bid's waiver is signed at the estimator's screen with the leader's code and goes out from the bid's own Lien Release tab, so it takes no lane whoever its signer is. `useLienSignatureLanes` and `useLienReleasesOwedNudge` also ask the database for job rows only (`job_id IS NOT NULL`).
- **Surfaces**: `DashboardLienWaiversToSignModal` and `LienSignatureInboxSection` take lane rows, so the recipient lookup, the payor map and the send read a job id that is one; `Documents` builds its per-job map through `lienReleasesOnJobs` (its query already asked by job, so no bid row ever answered — the guard now says so in the type).
- **Generated**: `src/types/database.ts` regenerated from prod (`bid_id`, nullable `job_id`, `notary_copy_path`, the `job_lien_releases_bid_id_fkey` relationship, and the `extend_estimate_good_through` RPC from v2.5992) and `supabase/functions/dev-mcp/catalog.ts` rebuilt from it. **Deploy `dev-mcp` after merge** so the seat's catalog matches. `Estimates.tsx` still reaches the new RPC through its cast, like `record_estimate_decline`; that is its own change.
