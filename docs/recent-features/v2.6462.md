# v2.6462 — A stopped crew's check reads as a stage check at the top of the Dispatch inbox (2026-11-03)

Punch list #245 (`to-dos/stage-check-to-dispatch/README.md`), a fix to PR 1 (v2.6360). Found reading the inbox during PR 1's live walk on prod, 2026-11-03: a check sent with *Can't do it* is `priority = 'high'`, and `DispatchInboxSection` drew every open high row as `CustomerWaitingRequestCard`. That card is a portal customer's. It named the row *A customer*, wore a *Portal* chip, offered *Reach them at* with no number and *Nobody has called yet*, and dropped the *Stage check* tag; the two doors still drew in the action column. No migration, no edge function.

## What changed

- **The row** (`DispatchInboxSection.tsx`): the card draws only for a waiting row that is not a stage check (`waiting && !stageCheck`). A waiting stage check draws the same row as at normal priority, the tag, the built title and both doors, under **`StageCheckWaitingLine`** (new, `src/components/stageChecklists/`): a red dot and *Can't do it · waiting 4 min*, ticking every 30 seconds through `useIntervalNowMs`, red-700 once the wait passes `CUSTOMER_WAITING_RED_MINUTES` as the card's header does.
- **The words** (`stageCheckWaiting` in `stageCheckDispatch.ts`): the request's own reason off `pending_payload.stage_check.reason` and `describeWait`'s label, so a *Need a part* check Dispatch raised reads *Need a part · waiting 1 h 5 min*, and an unknown reason reads *Waiting 4 min*.
- **Lower priority**: the card's *Lower priority ▾* had no home on the row, so the thread's header carries **Lower priority** where *Raise priority* sits on a normal row (`STAGE_CHECK_WORDS.lower`), opening the same `RequestPrioritySheet`.
- The guide *send a check to Dispatch* names the red line in its inbox paragraph. `GLOSSARY.md` → Stage check, and the card's call 3 and *Where it stands*, say the same.

## Decisions

- **The priority stays high.** The card's design is that a stopped crew leads the inbox: sorted first and counted on the badge. Only the drawing changes.
- **A stage check never draws as the portal card**, whether sent high or raised by hand. The card's name, number and Call are a customer's; a stage check's facts are the stage, the check and the job.

## Left for later

The app-wide *Customer waiting* banner (`CustomerWaitingContext` into `buildCustomerWaitingBanner`) still reads every open high dispatch row, so a *Can't do it* check raises it, named *A customer* (`nameOf` reads only a portal payload). Whether a stopped crew should raise the team banner at all is the owner's call. Any request Dispatch raises by hand reads the same way today.
