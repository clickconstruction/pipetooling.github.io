## The script — [`scripts/pay-backfill.ts`](../../scripts/pay-backfill.ts)

`npm run pay:backfill -- [--csv <export>] [--person <name>] [--out plan.md] [--record-review] [--apply]`. Signs in as the owner through the `dev-login` function with the secret in `.env.local`, so every write is an ordinary authenticated call. Dry run by default; the plan prints as Markdown. With `--apply`: import new rows the way the reconcile modal does, then link · correct within $5 · split · file lanes through `link_pay_send` / `split_pay_payment` / `set_cashapp_lane`; with `--record-review`, the pay/advance sends nobody recorded go through `record_pay_send`. Idempotent on the send, so re-running is safe.

## The kernel — [`backfillPlan.ts`](../../src/lib/cashapp/backfillPlan.ts)

`buildBackfillPlan({ sends, payments, mercury, … })` runs the reconcile matcher (rules a–c, e) and adds four rules: **near** (within `PAY_SEND_AUTOCORRECT_USD`, link and correct the amount to the send), **memo-split** (a payment whose memo lists the sends that made it up becomes one row per send when they sum), **memo-group** (a memo naming a send bigger than the row — "1200 sent" on five rows — links every row naming it) and **memo-fill** (a memo naming part of a payment is completed by one unmatched send of exactly the gap, Cash App or Mercury). Mercury sends match by amount for the alias-resolved person, preferring a memo that says Mercury; a send inside the first week of records is left for a person, since it pays the week before. A payment is consumed once across every rule; a send a payment already carries is skipped; a send backing two rows on one report, or memo sends that do not sum, is left for a person with the reason. `renderBackfillPlan` is the Markdown. 10 tests.
