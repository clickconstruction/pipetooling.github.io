# v2.2980 — Test-gap audit, pass 9: the per-GC outcome writer gets its first tests, and they catch a date-format hazard (2026-09-06)

Follow-up to v2.2979, which named `bids/gcPacketOutcome.ts` next. One small kernel fix plus tests; no client, migration or edge-function change.

## Why this one

`bids/gcPacketOutcome.ts` (256 lines) is the write orchestrator behind marking a GC packet Won / Lost / waiting (Bids by GC, v2.2162): it snapshots the rows a win will touch, writes the winner, auto-loses the sent-but-unanswered siblings, rolls the bid outcome up, writes the Win/Loss note and a telemetry row — and "↩ waiting" on the winner undoes the whole cascade. Its decision kernels (`wonCascade`, `gcPackets`, `updateGuard`) were tested; the sequence of writes around them was not. Seven surfaces call it.

## What the tests found

`outcome_at` was built with `new Intl.DateTimeFormat('en-CA', …).format(...)`, expecting `YYYY-MM-DD`. On Node 20 / ICU 72 that renders `09/06/2026`, and the string went straight into a date column. Browsers format `en-CA` correctly, which is why prod never saw it — but the repo already knew this class (`denverCalendarDayKey` in `dateUtils.ts` exists precisely because "runtimes whose 'en-CA' falls back to MM/DD/YYYY ordering", and `checklistDueDates.ts` / `payStubPayments.ts` carry the same warning). `todayYmd()` now calls `denverCalendarDayKey`, the parts-based formatter, so the value is the same on every ICU build.

**Deferred**: 119 more `toLocaleDateString('en-CA')` / `en-CA .format()` call sites remain across components and pages — a mechanical sweep (merge alone, per `CLAUDE.md`), recorded in `to-dos/engineering-hygiene.md`.

## What shipped

**`bids/gcPacketOutcome.test.ts`** (14) — through the recording chainable Supabase stand-in, with the decision kernels real, asserting the write sequence (table, patch, `in` ids, `eq` filters) for each path:

- **Lost**: one packet write with today's date, the bid left alone while another packet still waits, telemetry with an actor and none without; the last sent packet lost rolls the bid to Lost unless the bid is already decided; clearing a lost packet resets date and reason with no cascade; a failed write returns its message and stops.
- **Won**: reads the rows the cascade will touch first (the winner and the sent-unanswered sibling — never the unsent or shared-letter ones), then winner → siblings (no `loss_category`, so "GC lost the project" is inferred) → bid → note, with the exact note text; a win over a hand-set Lost says "bid Lost → Won"; a bid already Started is not rolled; a bid update that touches no rows (RLS) is reported after the packets landed; a note that fails to insert costs only the note; a shared-letter target gets no `gc_customer_id`; the session snapshot is kept for undo with `bidOutcomeWritten` set.
- **Undo**: with this session's snapshot — clear the winner, restore the siblings in one write per prior state, un-roll only a bid that still reads Won, write the undo note, clear the snapshot; a bid changed by hand since the win is left alone; without a snapshot (a reload) the rows are read *before* the winner is cleared and the cascade inferred; a snapshot taken for a different packet of the same bid is not reused.
- **Loss category**: empty packet refused, category with and without note, error passthrough.

## Verify

`npx vitest run src/lib/bids/gcPacketOutcome.test.ts` → 14 passed. Mark a GC packet Won on the Bid Board: `bid_versions.outcome_at` reads `2026-09-06`, as before in the browser.
