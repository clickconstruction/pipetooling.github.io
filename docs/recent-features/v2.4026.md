# v2.4026 — Bids page smoke: a click waits for the page's first load (2026-09-28)

Tests only; no app code. CI on `main` failed once on v2.4018's commit: `Bids.render.test.tsx` → *the Day book's params stay while the Day book is open and leave the URL when another tab is clicked* — `expected 'day-book' to be 'estimators'`. The same test had passed on the PR and in the merge queue.

## What was wrong

The case clicked a tab the moment the Day book had written its week into the URL. The page's first load of bids could still be in flight; when it lands, the router re-applies the URL's `?tab=`. The smoke's router ran with `v7_startTransition: true`, which holds a URL change back as a low-priority update — so for a moment after the click the page's tab said Estimators while the URL still said Day book, and a load landing in that moment put the tab back. The app's own router runs with the flag **off** (`src/main.tsx`, on purpose), so the window is the test's, not the app's.

This is the pattern the render harness's header warns about (`src/test/renderSmokeMocks.tsx`, v2.3852): assert on something the data load produces before a click, never click on the line after a `waitFor` on something else.

## What changed

- `pageAtRest()` in the smoke: waits until the stub has served the page's bids read, then `settle()`. The three cases that click call it before each click.
- The smoke's router runs with `v7_startTransition: false`, like the app's.
