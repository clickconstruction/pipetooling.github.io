# v2.4399 — A page no longer stays frozen after a window closes (2026-10-02)

Client only: no migration, no edge function. PR 1 of 4 on the owner's ask (2026-10-02): "stop background scroll on all modals across the app". The app-wide lock has existed since [v2.2186](v2.2186.md); the ask became a hunt for where it still fails. Three gaps were measured on the dev server. This PR closes the first; the other two (a window that stops above the bottom bar goes unlocked on a short screen; public pages have no lock) are PRs 2 and 3, and PR 4 is the proof in CI.

## What was wrong

Reproduced on People → Employment → **Pay history** at 375 px: scroll the page to 300, open the window, close it — `body` kept `overflow: hidden` with no window open, and the page could not scroll until a refresh. This is the cause [v2.2394](v2.2394.md) could not find behind "can not scroll down" (it added the watchdog instead, which never fired here: the sentinel believed it had released).

Two writers were saving and restoring the same inline styles around each other:

1. The window's own effect ran first (React flushes a click's effects inside the commit): it saved `body.style.overflow` (`''`) and wrote `hidden`.
2. The sentinel's recompute ran a frame later: `acquireBodyScrollLock` saved the body's styles — now `overflow: hidden` — as "the styles before", and pinned the body.
3. On close, the window's cleanup put `''` back; a frame later the lock's release restored what it had saved: `hidden`, for good.

When the open came after an `await` (effects flush after the frame) the order flipped and nothing stuck, which is why it looked random. Nine places had such an effect: `UserReviewModal`, `PeoplePayStubsTab` (Upcoming payroll), `CashAppReconcileModal`, `EmploymentMonthScheduleModal`, `EmploymentPayHistoryModal`, `ProjectsForecastSpecificStageModal`, `ProjectsForecastAlignStagesModal`, the two public ones `EstimateAcceptBody` and `SubPortalGuide` (overflow only, which does not hold on an iPhone), and `ClockInOutButton`'s Update Focus / Clock Out review / Tally effect, which wrote the whole fixed-body recipe (v2.2186 retired the Clock In copy and missed this one; with it the lock restored a fixed body — not walked live, it writes clock data).

## What changed

- **The lock is a class, not body styles** ([`bodyScrollLock.ts`](../../src/lib/bodyScrollLock.ts), [`index.css`](../../src/index.css)): `acquireBodyScrollLock(root, win, scrollbarWidth)` now takes `document.documentElement`, sets `--scroll-lock-top` / `--scroll-lock-pad` on it and adds `scroll-locked`; the rule `html.scroll-locked body { position: fixed; overflow: hidden; top: var(--scroll-lock-top) … }` (`!important`) pins the body. The kernel reads and restores no style, so no other writer can strand it — and a style written straight onto the body cannot undo the lock while it is held. Still reference-counted, still restores the scroll offset on the last release.
- **The nine effects are gone**: each is `useBodyScrollLock(<open>)` ([`useBodyScrollLock.ts`](../../src/hooks/useBodyScrollLock.ts)). The two public pages get the iPhone-safe lock for the first time.
- **Nothing open, nothing frozen** ([`BodyScrollLockSentinel`](../../src/components/BodyScrollLockSentinel.tsx)): when no blocking overlay is on screen and no lock is held, the recompute calls `healStrayScrollLock` — it lifts a class left behind and clears `overflow: hidden` / `position: fixed` written on the body's inline styles (a library can still do that), and warns in the console. A wheel, touch drag or key on such a page triggers the check, as it already did for a held lock.
- **Lint forbids the pattern** ([`eslint.config.js`](../../eslint.config.js)): `no-restricted-syntax` errors on an assignment to `document.body.style.overflow` / `overflowY` / `position` (or `documentElement`), with the hook named in the message.

## Tests

- [`bodyScrollLock.test.ts`](../../src/lib/bodyScrollLock.test.ts) rewritten for the class (13 cases): the stack, the offset kept when a second lock stacks on a pinned page, the scrollbar pad, double release, **the stranding order above as a regression**, and `healStrayScrollLock` (overflow, fixed body, a class left behind, refuses while held, leaves `overflow: auto` alone).
- `JobsStagesThreadPanel.render.test.tsx` reads the class instead of `body.style.overflow`.

## Verified live

Dev server, 375 × 812, production data, read-only. Pay history: open at scroll 300 → `<html class="scroll-locked" style="--scroll-lock-top: -300px">`, body computed `position: fixed; top: -300px`, no inline style on the body; Escape → class and variables gone, body `static` / `visible`, `scrollY` 300. Before the change the same walk left `body style="overflow: hidden;"`. A stray `document.body.style.overflow = 'hidden'` typed into the console with nothing open was cleared within a frame, with the warning.
