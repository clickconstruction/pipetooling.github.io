# v2.8657 — People, Users: a developer sees each person's seat on CountTooling and TakeoffTooling (2026-11-26)

The second PipeTooling piece of the accounts train (one staff account across PipeTooling, CountTooling and TakeoffTooling, managed from People). Client only: no migration, no edge function. It reads and writes nothing.

## What was there

PipeTooling is the record of people, and a dev issues a CountTooling seat from the person's desk (`users.counttooling_user_id`, v2.2434). The only place that set PipeTooling's people beside another site's accounts was the Monday audit email (`ct-roster-audit`), and it covers CountTooling alone. Nothing on a screen said who holds a seat where.

## What changed

- **A fourth lens on People → Users, Sites, for a dev.** `usersTabLens.ts` gains `sites`; `usersTabLensesFor` and `resolveUsersTabLens` take `isDev`, so anyone else who opens `?lens=sites` lands on Contact. A phone shows Contact only, as before.
- **Two cells a row, one a site** (`UsersTabSiteCells.tsx`): *no seat*, *active* or *retired*, then what is worth saying: the role there (CountTooling's admin, TakeoffTooling's `admin` or `dev`), *twin* for a robot's seat, the last sign-in where the roster carries it (TakeoffTooling's does, CountTooling's does not), *by address* when the row holds no id for the site, *address differs* when the linked account holds another address, and *link gone* when the row's id matches no account.
- **The matching is a kernel** (`src/lib/people/siteAccounts.ts`, tested in `siteAccounts.test.ts`): by `counttooling_user_id` where the row holds one, by address otherwise, with the robots' fleet domains folded into one as `_shared/ctRosterDiff.ts` does. TakeoffTooling has no id column here, so it is always by address.
- **A line above the list, one sentence a site**: how many of the site's accounts match nobody here, its count drawn as a value. A site that could not be read says why, with **Read again**, and the other site still shows.
- **The reads** (`siteAccountsIo.ts`, `useSiteAccounts.ts`): `roster` over `ct-bridge` and over `tt-bridge`, and the `users` rows with their CountTooling id. Each runs on its own, only while the lens is open, only for a dev.

## What it needs

`ct-bridge` has forwarded `roster` since v2.2435, so CountTooling reads at once. TakeoffTooling reads once `tt-bridge` forwards `roster` (v2.8655) **and that function is deployed**. Until then its column shows a dash and the line above says *TakeoffTooling could not be read*, with the proxy's reason.

`npm run typecheck`, `npm run lint`, the kernel's tests, a render smoke of the cells and the line (`UsersTabSiteCells.render.test.tsx`), the People components' tests, and `npm run build`. **Not seen against the live rosters**: that needs a signed-in dev on the deployed app.
