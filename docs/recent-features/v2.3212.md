# v2.3212 — Plans asks leave Standing rulings for the bid's robot needs sheet: ask_question `kind`, shell→source routing, Edit bid + intake address beside the taps (2026-09-10)

Migration `20260910003115_twin_question_kind.sql` (one nullable column); edge function `twin-mcp` v1.3.16 (redeploy). Third layer of the "questions a person can process" work (v2.3210 was the door + the taps).

## Why

Two of the three cards on the Standing rulings panel were "the file on the bid is the electrical set — attach the plumbing sheets?" That is a task on one bid, fixed on the Edit form or by sharing the right file, not a doctrine the estimator rules on for every robot. Mixed in with real rulings it costs the same reading for none of the leverage, and the place where the fix lives — the amber robot icon's needs sheet — never heard about it, because the robot asked on its ZZ shell, not on the human bid.

## What shipped

- **Kind** (`supabase/functions/_shared/twinQuestionKind.ts`, shared Deno + client): `'decision' | 'plans'`. The robot names it on `ask_question`; omitted, `classifyTwinQuestionKind` reads the text (attach/share/upload … plans/sheets/drawing set; "wrong set"/"is the electrical set"; "the file on this bid"; "no plumbing sheets"; "can't open the plans"). `effectiveTwinQuestionKind(row)` = column when present, else text, so history classifies the same everywhere. Tests feed it the two real asks from the panel and four judgments.
- **twin-mcp v1.3.16**: `kind` in the schema and description; a plans ask with no `choices` gets the standard three taps (`Attached — rerun` / `Use what is on the bid` / `Skip this bid`) so it passes the v2.3210 shape gate without the robot typing labels; insert writes `kind` (retry ladder: kind → choices/recommended → audience); the success line names the lane and warns when a plans ask has no `bid`. `get_answers` returns `kind`. Briefs regenerated.
- **Migration**: `twin_questions.kind text` with a CHECK (`decision | plans | NULL`), comment. Edge-only writes.
- **Standing rulings** (`standingRulings.ts`, `BidsAuditsTab.tsx`): plans asks are pulled out of the rulings and the header count and exposed as `plansAsks`; the panel shows one pointer line — *One bid needs a different plan set — not a ruling, a fix on the bid: b378* — one link per HUMAN bid (a shell's ask resolves to its source through the same pairing the "ours b214" links use), opening `/bids?tab=bid-board&bidId=<human>&robot=needs` in a new tab.
- **Bids page** (`Bids.tsx`): the board's open-question loader now selects `*` (choices, recommended, kind ride along) and keys a plans ask filed on a ZZ shell to the shell's `twin_source_bid_id`, so the amber icon lands on the estimator's row; other questions stay where they were asked. `robot=needs` deep link opens the needs sheet once the bid is in hand and drops the flag. `robotRowState` gets `plansAsks` and titles the icon *Robot needs a different plan set on X — click to fix*.
- **Robot needs sheet** (`RobotNeedsSheet.tsx`): a plans ask renders in the blocking list — *Robot needs a different plan set*, the robot's words, the fix line, **Copy intake address** and **Edit bid** beside it, and its taps underneath (★ pick first, *Something else…* for the box). Every other question on the sheet also gets the v2.3210 tap buttons now. A plans ask filed before the door (no stored choices — the two real ones on the panel today) gets the same three taps from the sheet itself, so nothing waits on a robot re-ask. The subline says *It stops here until these are fixed* when a plans ask is present.
- **Docs**: bid skill STG-2, estimator brief §9, Desktop kickoff STG-2, EDGE_FUNCTIONS, migration fragment, help guides `audit-a-robot-bid` (new step 5) and `let-the-robots-shadow-a-bid` (amber icon). `database.ts` hand-adds `kind`.
