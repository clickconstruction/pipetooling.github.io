# v2.4162 — New Bid: Plans sit under the name — the folder to open, the name to copy, and Find fills the link in (2026-09-29)

The owner's audit question, "do we make it easy for an estimator to load in what a robot needs?", answered on the live Robot Board: 6 of 12 unsent bids needed a person and all six were *No plans link*; the Job Plans field was the 14th of 26 on the form; the line under it said "a Drive file or folder the intake account can open" and the share step was taught only after a failed probe. The mock-up (Claude artifact `FR171snJmaS53BgYRGrH8a`, the After row) and the owner's two rulings: plans are **always a Drive link, never an upload**, and the estimator makes the folder — the app **gives them the name to copy**. PR 1 of 2.

- **`lib/bids/bidPlansFolder.ts`**: the three division bid folders (plumbing · electrical · HVAC — the ids the form has linked beside Project Folder), `divisionBidFolderFor(serviceTypeName)`, `bidPlansFolderName` = `jobFolderName` (the project name — one rule with the folder drive-intake makes for the job), `findFolderWords`.
- **`plan-fetch` gains `find_folder`** (staff JWT): `POST { find_folder: { parent_id, name } }` → the child folder of the division folder named exactly `name`, with its link and PDF count, or `found: false`. `findChildFolder` is one Drive `files.list` by parent + name + folder mime, shared drives included. **Deploy** `supabase functions deploy plan-fetch` after merge; before the deploy the form's Find reads "Could not look just now" and the pasted-link path still works.
