# v2.7186 — The dev seat links a bid with several sent papers to its Sent by us folder (2026-11-13)

Punch list #339, the one design call the pair left open. The column `bids.bid_submission_link` holds one link and a bid can hold several papers, a revision or a second option. v2.7154 filed each in Team only › Sent by us and moved the link to the newest. Asked on 2026-11-13 whether the link should be the folder once a bid holds several, the owner said: "Use the folder". `dev-mcp` is server 0.83.0. No migration, no new verb.

## What changed

- **Which link** (`bidSubmissionDryRun` in `supabase/functions/_shared/devMcpBidSubmission.ts`): the paper while Sent by us holds it alone, the Sent by us folder once it holds more. The plan says which under `link.is` (`paper` or `folder`), and for a folder it states the link whole, since the folder already exists.
- **`replace: true` asks less.** A link that already points into the bid's own Sent by us, a paper there or the folder, moves without it, since nothing is lost. A link to anywhere else, one a person pasted, still needs it, and the refusal names the link.
- **A bid that already carries its folder** takes another paper with no write to its row: the apply files the paper, leaves the link and writes the note. A folder link a person pasted with a query on the end reads as the same folder.
- **A bid left on one paper by 0.82.0** moves to the folder the next time any of its papers is planned: nothing is copied and only the link and the note are written.
- **The note** says which: "…beside 2 other papers. The bid's submission link is that folder."
- **A folder too long to read whole** (over 100 papers) counts as several.

## What to know

Sent by us is the app's home for everything sent, not for bid papers alone. On a bid that shares its project folder with a job, the folder link shows that job's sent papers too, an hours statement for one. The README row says so.
