## What was open

v2.8632 drew **The bank confirmed the funds** for a dev, a leader and a controller alone, and v2.8735 did the same for **Release it anyway…** on a check that has not cleared. The screen alone held both. A release is an insert on `job_lien_filings` and the confirmation an update of its `fields`, and the table's policies pass the whole office. An assistant with a request written by hand could do either.

## What changed

- **Migration `20261127164654_lien_early_on_check_three_roles.sql`.** One `BEFORE INSERT OR UPDATE` trigger, `job_lien_filings_early_on_check_guard`. For a signed-in caller who is not a dev, a leader or a controller it refuses a `release_of_record` row that gains `releasedBeforeClearedReason`, and any row whose `fields.fundsConfirmed` is set, changed or taken off. Its page: [`docs/migrations/20261127164654_lien_early_on_check_three_roles.md`](../migrations/20261127164654_lien_early_on_check_three_roles.md).
- **A new bed**, `npm run test:pg:lien-early-on-check`, listed in `scripts/sql-beds.txt`.

## What stays

Every other write of the table, for every role the policies pass. No policy, grant, column or row is changed. A write with no sign-in behind it passes, so the mail refresh still stamps a lien's sends.

## What it does not do

It does not tell an early release from an ordinary one by itself: the database reads no bank row. A hand-written release that leaves the reason out is an ordinary release to it. The screen knows a check has not cleared; the database now makes sure the two things the screen writes then are the three roles' alone.
