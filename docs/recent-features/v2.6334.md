# v2.6334 — In the folders: a file the app put there says From the app (2026-11-01)

Found live on 2026-11-01, the first time the Documents tab's **Add a file** (v2.6303) ran on a test job: the file landed in the job's Plans folder, and **In the folders** (v2.6299) then listed it as *Added in Drive · Nov 1 · 1 KB · drive-intake@….iam.gserviceaccount.com*, the grey chip of a hand in Drive and the app's own Drive account where a person's name goes. Client only, no migration, no deploy.

- **Why.** `fromWords` read *From the app* only for a file `job-photos`' `files` action matched to the app's own record (`uploaded_photos`, `drive_links`), and `drive-link`'s `put` writes neither. `fileMetaWords` printed `by`, which the action takes from Drive's `lastModifyingUser` (the display name, else the address), and Drive names a service account by its address.
- **The fix** (`src/lib/jobs/jobFolderFiles.ts`): `byTheApp(by)` is true for an address ending in `.iam.gserviceaccount.com`, the app's own Drive account. `fromWords` keeps the record's kinds first (*a report photo*, *a file the app linked*), then reads such a file as *From the app · a file the app put there* in the blue chip; `fileMetaWords` leaves the address out (*Nov 1 · 1 KB*). Anything else the account wrote with no record of its own reads the same way.
- **Limit.** Drive names the last hand on a file, not the first: a person's file the app's account changed last reads as the app's, and a recordless app file a person changed last reads as *Added in Drive* with their name. A record for each `put` (the follow-up v2.6303 named) would make it exact.
- Tests: `jobFolderFiles.test.ts` (the address read case-blind and trimmed, a name or a person's address not; the record's kinds still first; the meta line without it) and the section's render smoke (a Plans row with the blue chip, *Nov 1 · 1 KB* and no address anywhere, a person's file still *Added in Drive*; it fails on the old kernel). The guide `set-where-a-jobs-files-go` names the new chip.
