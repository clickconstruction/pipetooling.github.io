# v2.6254 — check:calls-ahead labels the pull request it flags (2026-10-31)

Since v2.6119, `npm run check:calls-ahead` has warned on a pull request whose client calls what only its own migration creates, and was meant to put the label *push right after the merge* on it. No PR ever carried the label. The step's `gh label create` sent a 110-character description, GitHub caps a label's description at 100 (`Validation Failed: description is too long (maximum is 100 characters)`), and the warning showed only the command line, so the cause stayed hidden. Found reading #6635's checks log (punch list #222, 2026-10-31).

- **`src/lib/callsAhead.ts`** — the label's color and a 76-character description (`CALLS_AHEAD_LABEL_DESCRIPTION`) beside `GITHUB_LABEL_DESCRIPTION_MAX`; `callsAheadLabelCalls` builds the three REST calls (read the label, make it when the repo lacks it, add it to the PR); `labelAlreadyExists` lets a run that lost the race to make the label carry on to the add; `ghFailureWords` gives GitHub's own message and field errors. Tests in `callsAhead.test.ts`, one holding the description under the cap.
- **`scripts/check-calls-ahead.ts`** — labels through `gh api` in place of `gh label create --force` and `gh pr edit`, which fails quietly in this repo, and the warning carries GitHub's reason.
- **No permission change.** GitHub's permissions table for apps lists every label endpoint under both the Issues and the Pull requests permission, so the checks job's `pull-requests: write` covers all three calls. The deploy hold in `deploy.yml` (`check:calls-ahead -- --prod`) is unchanged.
- Checked against GitHub with requests that cannot create anything, each sent with a deliberately invalid color: the old description drew the length error, the new one only the color error. The first pull request that calls ahead after this merges makes the label and carries it.
