# v2.2881 — Three statement lanes, one shared view: the office sees every scheduled send; duplicates within a window are skipped; each GC shows what went out and by which lane (2026-09-05)

Journey-map Tier-2 #45 ("Three statement lanes, no shared view", C31 — J20-F5, F10, N1). Ships after #11 (v2.2842, `gc_review_week_status` counts round marks) and #46 (v2.2874, `gcStatementSendGuard`, pay line, dispatcher parity).

## 1. The "Scheduled statement sends" box is the office's, not the requester's (J20-F5)

`gc_statement_email_requests` SELECT was `requested_by = auth.uid() OR is_dev()` (20260806233713), while the client read unfiltered and titled the result *the* scheduled-sends list. An assistant running the Wednesday round saw **no box at all** while two weekly chains ran; only the dev who created a chain could see it existed or cancel it.

- **Migration `20260905190000_gc_statement_requests_office_read.sql`**: the SELECT policy becomes `requested_by = auth.uid() OR is_dev() OR is_assistant() OR role IN ('master_technician','primary')` — the GC Review cohort, the same predicate the table's INSERT policy already names. **Cancel stays owner-only**: the DELETE policy ("Creators cancel own unsent …", requester-or-dev) is untouched and there is still no client UPDATE policy (verified by reading the migration that created them; nothing here re-declares them).
- **Client**: `listMyPendingGcStatementSends` → `listPendingStatementRequests` (its old name would now lie), selecting `requested_by`; `PendingGcStatementSend.requested_by` is required. New `canCancelStatementRequest(row, { id, isDev })` mirrors the RLS DELETE rule so the button never promises what the row refuses. In `JobsGcReviewModal`'s box every row renders for every office role; the **Cancel** button shows only to the requester or a dev, otherwise a muted `by <name>` with a hover explaining who can cancel. Standing whole-report groups follow the same rule across all their chain rows.

## 2. Send-time dedupe in both lanes (J20-F5 "no send-time dedupe in EITHER edge fn")

Neither `send-gc-statement-email` nor `gc-statement-email-dispatch` looked before it sent; the dispatcher's only skip was nothing-outstanding.

- **Shared kernel** `supabase/functions/_shared/gcStatementSendDedupe.ts` (client twin `src/lib/gcStatementSendDedupe.ts` re-exports it — one rule, no mirror): `findDuplicateStatementSend(recent, candidate, windowMs, now)` / `isDuplicateStatementSend(...)`, `statementEntityKey` (GC customer id when known; `development:<name>` / `all:<name>` otherwise — the audit table has no development id), `describeDuplicateStatementSkip` ("skipped: duplicate — Knight Contracting already went to ap@knight.com 4 minutes ago"), `dedupeSinceIso`. Identity is **(entity, recipient), lane-agnostic** — the cross-lane double send is exactly the one being prevented.
- **Windows** (`GC_STATEMENT_DEDUPE_WINDOW_MS`): **attended 10 min** for Draft Message (double-click, slow-response retry, two people within minutes; anything older is the sender's call, informed by "What went out"); **unattended 12 h** for the cron dispatcher (a scheduled statement landing the same half-day as one the GC already got, by any lane).
- **`send-gc-statement-email`**: reads the last 20 `gc_statement_emails` rows to that address inside the window (service role), and on a match answers **200 `{ success: false, skipped: 'duplicate', error: <reason> }`** — the existing client already surfaces `error` strings in the dialog, so no transport change was needed. Audit-read failures fail open (the send proceeds).
- **`gc-statement-email-dispatch`**: same read per row; on a match stamps the request `sent_at = now(), error = 'skipped: duplicate — …'`, advances the weekly chain, and counts it in a new `duplicates` field of the run summary. Fails open the same way.
- **Tests**: `src/lib/gcStatementSendDedupe.test.ts` — 15 cases: both windows, other recipient/GC, case-insensitive address, whole-report and development keys, newest-match selection, garbage/future timestamps, zero window, skip sentence, and a twin-agreement block asserting the client export *is* the edge module.

## 3. "What went out" — one per-GC list across all three lanes (J20-F10)

`gc_statement_emails` had exactly two readers, both latest-only (the last-sent pill and the Customer Hub profile); a dev-only per-send list existed at Settings → Notifications (`SettingsRecentEmailsSent`, v2.2656 `email_type`). The v2.2761 send-history modal listed only round marks, with a footnote about the latest app send.

- **Migration (same file)**: additive policy `email_send_log_statement_office_select` — the GC Review cohort may read `email_send_log` rows whose `email_type IN ('gc_statement_manual','gc_statement_scheduled')`. Nothing else in the org-wide log opens up; the dev-only policy stays.
- **Kernel** `src/lib/jobs/gcStatementSendHistory.ts`: `buildGcStatementSendHistory({ marks, emails, log }, limit)` merges `gc_statement_round_marks` (sent + contacted; skips excluded) with the GC's `gc_statement_emails` rows, joining `email_send_log` by `resend_email_id` for the **lane** (`laneForEmailType`: `gc_statement_manual` → Draft Message, `gc_statement_scheduled` → Scheduled send, anything else/no row → App email) and the **delivery status** (`emailLogStatusChip` on `last_event`, reused from `emailSendLog.ts`). Newest first, latest N (60). `summarizeStatementLanes` writes the one-line count ("1 personal · 1 by Draft Message · 1 scheduled"). 5 tests in `gcStatementSendHistory.test.ts`.
- **IO** `src/lib/gcStatementSendHistoryIo.ts`: `listGcStatementAppSends(gcId)` + `listGcStatementSendLog(resendIds)` — both fail soft to empty, so a client ahead of the push sees "App email" with no status rather than an error.
- **UI** `GcStatementSendHistoryModal` (opens from the last-sent pill, the temperature pill, and the Temperature board): columns **When · What · Lane · Who · Details** — marks show `Personal · text` with temperature / pays-by / note; app sends show `to ap@knight.com +1 · $12,345.50` and a Delivered / Bounced / Sent chip. The `appLastSentAt` prop and its footnote are gone — the app sends are rows now.

## 4. Telemetry — `gc_statement_sent{lane}` now has the lane on the log row

Both functions now pass `emailType` to `logEmailSendBestEffort` (`gc_statement_manual` / `gc_statement_scheduled`, the catalog ids `emailCatalog.ts` already listed as each sender's) — previously neither stamped it, so the catalog's per-type counts for the two GC-statement rows were zero and the lane was unrecoverable per send. No new column. Query for a week:

```sql
select coalesce(l.email_type, 'app_email:unstamped') as lane, count(*)
  from gc_statement_emails e
  left join email_send_log l on l.resend_email_id = e.resend_email_id
 where (e.sent_at at time zone 'America/Chicago')::date >= :week_start
 group by 1
union all
select 'round_mark:' || coalesce(channel, 'unknown'), count(*)
  from gc_statement_round_marks
 where week_start = :week_start and action = 'sent' group by channel;
```
