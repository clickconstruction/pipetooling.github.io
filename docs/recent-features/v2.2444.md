# v2.2444 — The price book drawer can reach the bid you have open (2026-08-28)

Wendi: *"changed both versions of water to 13 and it isnt coming up when im trying to add
it in."* Both edits saved. Neither could ever have reached a bid.

**What was happening.** A bid does not price from a price book — `clone_price_book_version_to_bid`
gives it a frozen **copy**, and the copy keeps the source's name (v2.2123). So the Workbench chip
("WENDI · 111 entries", the bid's copy) opens a drawer titled "Price book — WENDI" (the shared
template), and nothing distinguishes them. The assign dropdowns search `priceBookEntries` (the
copy); the drawer's ✎ and **Add entry** write `templateEntries` (the template). Verified in prod:
`Ft of Water Line` exists in 41 versions and exactly one — the WENDI template — holds $13; the 40
bid-owned copies still hold $12. `feet of water line`: 1 template at $13, 25 copies at $12.

v2.2398 diagnosed half of this ("an entry added there never appeared back in the dropdown") and
fixed only the **add** path, by giving the assign dropdown its own door into the bid's copy. The
**edit** path was left pointing at the template, with no door back.

**The door back** (`src/lib/bids/bookEditBidOffer.ts` + 10 unit tests). After any save to the
shared book with a bid open, `planBookEditBidOffer` compares the saved entry against the bid's
copy and returns one of three answers: *update* (the copy holds this fixture at different prices —
stage prices count, not just the total), *add* (the copy has never heard of it), or null (no bid
open, or the copy already agrees — the common case, so the banner stays meaningful). The drawer
renders the offer under its header: **Use $13.00 on this bid** / **Add it to this bid too**, beside
**Leave this bid alone**. Applying writes the four prices into the copy's own entry — assignments
already point at that entry id, so every assigned row re-prices with no re-assigning — or inserts
the entry so it starts surfacing in the `assign…` searches. Never automatic, per owner decision:
the freeze is what stops a sent bid re-pricing because someone tidied the book.

**Saying it in the drawer, always.** The "Browsing only — the bid still prices from its ★ book"
caption rendered *only* when the selected book differed from the bid's — so on the bid's own book,
the case where you are most likely to edit and expect it to take, nothing explained the freeze. A
permanent line now names the copy for every book: *"Edits here change the shared book. This bid
prices from **WENDI**, its own copy taken when the bid started."*

**Severed lineage, resolved by name** (`resolvePriceBookTemplateRoot`, +9 tests).
`price_book_versions.source_version_id` is `ON DELETE SET NULL` (`20260610120000`), so deleting a
scenario orphans every copy taken from it. BP384's two "WENDI" pricings had `source_version_id =
null` (created 2026-08-27, 111 entries + 16 assignments each) and resolved to no template, which:
sent the drawer to the first template alphabetically — **Default**, which is why Wendi edited a
water line there too; dropped the ★ "Feeding this bid" marker from every book; and made
**Use WENDI on this bid** miss the copy the bid already had, so it would have cloned a *third*
WENDI scenario carrying none of her 16 assignments. Cloning preserves the name, so the name is the
surviving evidence: when the `source_version_id` chain dead-ends (or cycles), the resolver now
matches the pricing's name against the templates, case- and whitespace-insensitively, and accepts
it **only** when exactly one template matches. A live lineage always wins; callers that don't pass
`templates` keep the old null.

No migration, no data backfill — owner's call: sent and in-flight bids keep the prices they were
built with, and estimators carry changes across per bid with the new door.
