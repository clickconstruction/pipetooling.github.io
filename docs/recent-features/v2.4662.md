# v2.4662 — Legal portal: an email to the law firm that fails is tried again and shown (2026-10-05)

Item 26 of punch list #85 ([`to-dos/legal-portal-firm-ready/`](../../to-dos/legal-portal-firm-ready/README.md)). **One migration** ([`20261006055407_legal_notify_per_recipient`](../migrations/20261006055407_legal_notify_per_recipient.md), four additive columns, not pushed here) and **three functions to redeploy after it**: `legal-notify-dispatch`, `submit-legal-portal`, `legal-portal`. Mockup: `mockup-26-send-retries.html` beside the card (the real now-email builder and the real token kernel).

## The defects

- **Failures were final and silent.** The dispatcher's "now" lane stamped `sent_now_at` after its loop whether Resend took each email or not. A refused *New account referred* was never retried, and the failure went only to the cron log.
- **Older stop links died.** `unsubscribeLink` minted a fresh token and overwrote the person's stored hash on every email, so *Stop these emails to you* in any email but the newest answered *That link has expired*.
- **The cron secret** was compared with `!==`, which returns at the first differing byte.

## What changed

- **A per-person ledger** on each queue event, `legal_notification_queue.sent_to`, with the rules in [`_shared/legalNotifyLedger.ts`](../../supabase/functions/_shared/legalNotifyLedger.ts) (client door `src/lib/legal/legalNotifyLedger.ts`): `legalNotifyDue` freezes the people who were to hear the event on its first tick and returns who is due; `legalNotifyRecord` stamps `at` on success or counts the try, the error and its time, giving up at `LEGAL_NOTIFY_MAX_TRIES` (12, an hour of ticks); a frozen person who stopped, was removed or moved to the digest is `skipped`; `legalNotifyDone` says when to stamp `sent_now_at`. Someone who confirms during the retry hour is not sent the old event (the v2.3325 rule).
- **The person's standing**: every send (now, digest, and the confirmation in `submit-legal-portal`) sets or clears `legal_firm_recipients.send_failed_since` / `send_error` (`legalRecipientSendPatch` keeps the first failure's time).
- **Shown on the desk** ([`LegalDeskModal.tsx`](../../src/components/jobs/legal/LegalDeskModal.tsx)): **✉ Firm's emails · 1 not reaching** on the header button; in the modal, the status pill *not reaching* and a red line under the name, *Could not reach bo@… since 2026-10-05: The to address is invalid. The queue tries each email again every five minutes, for an hour.*
- **Shown on the portal** ([`LegalPortal.tsx`](../../src/pages/LegalPortal.tsx)): `legal-portal` returns each person's `failingSince` (the company-zone day), parsed by `legalPortalPayload.ts`; the person's card carries *Our emails to bo@… have not gone through since 2026-10-05. We try each one again for an hour. If the address is wrong, press Stop emails to this person and add the right one.* Not shown while the person is stopped. The firm is not shown the mail service's words.
- **Stop links minted once**: `legalUnsubscribeToken` is an HMAC of the person's id and `unsubscribe_salt` under the service key. The same token rides every email; only its SHA-256 is stored, written when missing or stale. `recipient_resume` (turning emails back on) sets a new salt, the one rotation, so a stop link in an old forwarded email no longer pauses them. The first email after the deploy writes each person's new hash once, so stop links in emails sent before the deploy stop working one last time.
- **Cron secret**: `constantTimeEqual` (every byte and the length).
- **Deploy-order safe**: a queue row without `sent_to` (function deployed before the push) is stamped after one pass, as before, so nothing re-sends every five minutes; the failure and salt writes are separate updates that cannot hold back a stamp or a resume; `legal-portal` reads recipients with `*`.
- Docs: `EDGE_FUNCTIONS.md` notes on the three functions (and the dispatcher's *Purpose* amended), the migration page; the guide *manage who at the law firm gets emails* gains the retry and the *not reaching* status.

## Is this the best we can do?

- **A jsonb ledger on the event, or a table of sends?** The jsonb column. It lives and dies with its event and needs no new RLS or training-mode fences. The person's standing is two plain columns. A send history already exists: the filed copies in `sent_documents`.
- **How many tries?** Twelve, one per tick. An hour rides out a mail-service blip and calls a dead address dead the same hour. The person's line stays until an email gets through, so a given-up event is still visible.
- **Who gets a retried event?** Only the people who were to hear it when it happened (the ledger is frozen on the first tick).
- **What if the function goes out before the migration?** It notices and behaves as before, never re-sending; the portal never breaks on the missing columns.
- **Why rotate the stop link at all?** Only on turning emails back on, so an old forwarded email cannot pause the person again. Otherwise every email's link works forever.
- **Should the firm see the mail service's error?** No. The office does, for diagnosis. The firm is told what to do. Refined after the first draw: the firm's line first said only *add the right one*, which left the bad address tried on every event; it now says to stop it first.
- **Digests?** A failed digest was already retried each tick that day (it is not stamped). It now also marks the person, and is not capped: the line says the address is failing.
- **Bounces after acceptance** (Resend takes the email, then the receiving server bounces it) are not caught: that needs the Resend webhook's events, a separate pass.

## Known limits

- **Overlapping cron ticks can double-send.** Two ticks that run at once both read the same due rows before either stamps `sent_to`, so a person can get one event twice. The fix is to claim rows through an RPC with `FOR UPDATE SKIP LOCKED`; later.
- **`limit(50)` can hold back new events.** The now lane reads 50 unfinished rows per firm, oldest first; while 50 are still retrying, a new event waits behind them until they finish or give up.

## Integration pass (review fixes)

- The not-reaching line says what is really tried again (`legalNotReachingLine`, now told `confirmed` and `mode`): a confirmation is never retried by the queue, so an unconfirmed person's line says *press Resend the confirmation* with no *for an hour*; a digest is retried each tick for the rest of its day; an event email every five minutes for an hour. The desk's line says the same per case.
- The stop link's key is `LEGAL_UNSUBSCRIBE_SECRET`, falling back to the service key (`legalUnsubscribeSecret`); with both empty the email goes with no stop link and the function logs it (fail closed: the footer says to reply to stop). Setting the secret later re-mints each person's link at their next email; links in older emails then stop working once.
- `legalNotifyDispatch.run.test.ts`'s fake client answers `rpc` like a missing function, so it survives item 22 (#4639) adding `admin.rpc('legal_portal_link_token')` in either merge order.
