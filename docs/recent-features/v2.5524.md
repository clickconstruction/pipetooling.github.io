# v2.5524 — Messages: a test keeps the sort card to one in a thread (2026-10-14)

The lead's ask after the prod walk: the thread window drew the New lane's sort card twice on open, and one more on each
re-render. The unknown ZZ number showed three *Who is this?* cards after a press on Someone else and typing in its
window. The ZZ customer showed two *Who has it?* cards. No migration, no edge function, no change to the app's code.

- **The cause** was two siblings in the thread column with one key. The sort card (`useNewLaneThreadSlots` →
  `<NewLaneSlot key={c.id}>`, the `aboveLines` slot) and the reply box (`<ReplyBox key={c.id}>`, the `box` slot) both
  keyed bare `c.id`. React warns *Encountered two children with the same key … Non-unique keys may cause children to be
  duplicated and/or omitted*, and it kept an extra card on each re-render.
- **The fix was already on main**: v2.5516 (#5696, merged 05:20Z and deployed in `ab18ae92d`) gave every slot its own
  prefix (`new-lane:`, `reply:`, `flow:`). This PR adds no code.
- **`ThreadWindow.sortCard.render.test.tsx`** (new) draws the thread window with its own slots (`useThreadSlots`, no
  smoke slots). It uses the spine's number nobody has named, a fake card io in New with *Who is this?*, and an assistant
  signed in. It counts one card on open and one after two re-renders with a fresh view, as a re-read hands it, and one
  *Who is this?* heading.
- **Proof it bites**: with the two files as they were before #5696, the smoke fails, with React's duplicate-key warning
  for `c-unknown` and more than one card. With main it passes.
