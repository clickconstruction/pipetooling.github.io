# v2.4598 — Bids: every change is now kept, with who made it (2026-10-05)

Punch list #73, PR 1 ([`to-dos/bid-history`](../../to-dos/bid-history/README.md)): capture. Wendi lost work on a SpaceX bid and nothing could say what the bid had said before, or who changed it: an edit overwrote, a delete was kept for a dev for 90 days. This PR records every value anyone enters on a bid, in a ledger written by a database trigger, so no save path can miss it. Capture only: nothing reads it until PR 2 (the pane), and every day before this push is a day with no history.

## The change

Two migrations, no client change, no edge function.

- [`20261005215057_bid_changes`](../migrations/20261005215057_bid_changes.md): the `bid_changes` table (one row per insert, real change or delete, with the row's name, its count row and its version at write time), its RLS (whoever can read the bid; a dev also after the bid is deleted; no client writes), `record_bid_change()`, the lists `bid_changes_tables()` and `bid_changes_bid_columns()`, and a three-year pg_cron purge.
- [`20261005215059_bid_changes_triggers`](../migrations/20261005215059_bid_changes_triggers.md): the trigger on the seventeen tables, alone in its file, so the write locks on the bid tables are held for seventeen catalog inserts. Its doc carries the deploy note.

What the to-do got wrong, and the PR does instead: the list names 18 tables (`bids_takeoff_template_mappings` is By Stage's and dropped, so 17); the reader's "an earlier Lav-1" fallback needs the version, so every row carries `bid_version_id`; a `bids` row has no label (one row can carry several columns, so the column words belong to the reader); the RLS is the bid's own read rule, not `bidsTabOpenFor` (a per-tab role gate) and not a service-type limit the bids policy does not have.

## Design calls

- **Row trigger, not statement triggers.** Measured on a scratch Postgres 15 (numbers in the ledger's doc): the ledger adds about 0.1 ms per row written, and a 300-row copy goes from 33 ms to about 250 ms. A statement-level design cut a 300-row copy from 2,103 subtransactions to 308, but that is still past the 64-subtransaction cache, and it was 3–7 times slower on every single-row statement. With copies looping under concurrent readers, read throughput was the same with and without the subtransactions.
- **Children of a removed parent** take their fixture, version or bid from the delete archive's `BEFORE DELETE` snapshot: a child's AFTER trigger runs after its parent is gone. A row is never written without its bid. A deleted bid writes one row (its own) and the archive keeps the bundle.
- **No foreign key on `bid_id`**: a deleted bid's history stays (dev-readable), and comes back into view if the bid is put back from *Recently deleted*.
- **48 `bids` columns**, everything Edit Bid saves plus the Pricing, Cover Letter and SOV picks, under `UPDATE OF`, so robot, follow-up and board writes never call the trigger. History cannot be filled in later, so capture is wide and PR 2's reader chooses.
- **No `apply_digital_twin_write_blocks()`**: the ledger has no client write to fence, and that helper takes ACCESS EXCLUSIVE on every RLS table (a task chip proposes making it incremental).

## Tests

- `src/lib/bids/bidChangesCapture.test.ts`: the two lists against the generated types (seventeen real tables, `bids` last, 48 real `bids` columns, no stamp or robot column), every column the function reads by name pinned to its table, and every table it branches on one of the seventeen. A rename would otherwise turn capture off silently. Checked by breaking a list entry, a key, a branch name and a column in the types: each fails.
- `npm run test:pg:bid-changes` (new, `scripts/pgtest-bid-changes.sh` + `supabase/tests/bid_changes/20_scenario.sql`): the Supabase 17.6 image with every migration, both files re-run, then 33 assertions. They cover an insert, an update and a delete on every one of the seventeen tables, and a last check that every table recorded something. They also cover a new bid; a notes edit next to an unkept column; a price typed three times; a reorder; what hangs on a count row; labor, costs, SOV, schedule, a version; a fixture removed; a version deleted; a cost estimate removed; the ledger renamed and refusing (each save still lands); a trainee refused; who reads it; a real copy; a bid deleted; a write with no author.
- **Not run on the full schema.** Docker was not available to the authoring session, so the scenario ran against a stub of the seventeen tables on Postgres 15 (all 33 pass). The PR merges only after the bed has run green, since a merged migration is pushed by the next `db push` from any session.
