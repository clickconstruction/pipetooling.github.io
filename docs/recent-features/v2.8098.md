# v2.8098 — The main chunk's split, step 1: the three job windows load on demand (2026-11-20)

The service worker's precache has a cap for one file (`maximumFileSizeToCacheInBytes` in `vite.config.ts`), and the app's main chunk has crossed it four times: 7, 8, 9 and 10 MiB. Each time every deploy build failed, with no error line, until the cap was raised. On 2026-11-20 merges did not go live from 13:37 to 15:48 UTC. This is the first cut of the split the cap's comment has asked for since October. No migration and no function.

## Measured

| | Main chunk | |
|---|---|---|
| Live site, 2026-11-20 (before) | 9,465,107 bytes | read from the deployed `assets/index-*.js` |
| This change, `vite build` on the branch | 5,671,756 bytes | 40% smaller, 3.8 MB out |

The build's precache step passed. The largest precached files are now the main chunk and the Settings page's chunk (5,603,956 bytes, unchanged). The cap stays at 10 MiB in this change and comes down once the next cuts are in.

## What changed

- **Why they were in.** `JobDetailModalProvider` and `JobFormModalProvider` are mounted in `App.tsx` for everyone signed in, and each imported its window. So the Job window, the read-only Job Detail pane, the job form and everything those read (the lien paper, billing, costs, documents) sat in the entry's chunk whether or not anyone opened a job.
- **On demand.** Both providers now hold their windows through `lazyWindow` (`src/lib/lazyWindow.ts`), with a `Suspense` around the window alone. They import the windows' types only.
- **A first open stays quick.** The service worker precaches every chunk, so an installed app reads the window from the device. And `useWarmWindows` loads the window for this person's role once the page is idle (`warmWhenIdle`: the browser's idle callback, a three second timer where there is none), one window per idle moment. The Job window imports the job form, so warming it brings the form.
- **While it loads.** `WindowOpening` is a small note in the middle of the screen, *Opening the job…*. It waits a quarter second before it shows, takes no press and is not a window. A chunk that fails to load is caught by the `RouteChunkBoundary` around the routes, which reloads once as it does for a page.
- **The guard.** `src/lib/entryGraph.ts` walks the entry's static imports from the source, with no build, and `entryGraph.repo.test.ts` runs in PR CI: none of `ON_DEMAND_WINDOWS` may be reachable from `src/main.tsx`, and the eager source must stay under `ENTRY_SOURCE_BUDGET_BYTES` (16 MB; it is 14.1 MB, which built the 5.67 MB chunk). A PR that puts a window back, or grows what every visit loads, fails with the chain of imports that did it. Until now the first word of it was a deploy failing for everyone.

## Seen on the dev server

- The app shell and the Dashboard loaded with no request for any of the three windows.
- A job opened from the Dashboard's Assigned Jobs 155 ms after the press, with every tab, and no request for the window at the press: the idle warm-up had loaded it.
- **New Job** on Jobs opened the form. Pressed in the first second, while the jobs list is still loading, it does nothing but toast, as before this change (`openNew` in `Jobs.tsx`).

## What is left

By the import trace, after this change the heaviest things still eager are the Legal portal page, the person desk, the user review window, the bid preview and the painted map host in `Layout.tsx` and the providers, and the other public pages in `App.tsx`. The Settings chunk, at 5.6 MB, is the next file near the cap.
