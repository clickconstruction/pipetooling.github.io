# v2.4963 — Bids: History shows every change on a long bid (2026-10-08)

Punch list #73, the row-cap fix ([`docs/TROUBLESHOOTING.md`](../TROUBLESHOOTING.md) `[row-cap]`). Found on PR 4's live check: `list_bid_history` returned exactly 1,000 rows for a dev on ZZ Test, whose history is mostly the delete archive. PostgREST's cap had cut the oldest changes without an error. A non-dev would meet it once a bid passes 1,000 ledger rows. `latest_bid_cell_history` can reach it on a very large bid. Migration `20261009180000_bid_history_paged.sql` ([doc](../migrations/20261009180000_bid_history_paged.md)); no edge function.

## The change

- **A total order** on both functions, so a page read with `.range()` never shuffles. `list_bid_history` breaks ties on the archive row's id, since a cascade removes many rows at once. Its own 2,000-row default cap is gone.
- **The window reads a page at a time** (`loadBidHistory(bidId, from)`, `BID_HISTORY_PAGE` = 1,000). While a full page says older rows remain, the count reads *so far* and a **Show older changes** button sits at the bottom. A row repeated at a page's edge by a new change is shown once. After a Put back, the window reads again as many pages as it had shown.
- **The cells read everything**: `loadBidCellHistory` pages with `fetchAllRows` until a short page.
- `makeFakeRowCapSupabase` gains `rpc()`, which reads as the table `rpc:<name>`, so RPC paging can be tested with it.

## Tests

- `loadBidHistory.test.ts`: the reader pages by range (`[0, 999]`, then `[1000, 1999]`) and throws a failed read; the cells' read pages until a short page.
- `BidHistoryWindow.render.test.tsx`: a 1,001-change bid shows *1,000 changes so far* and *Older changes are not shown yet*; *Show older changes* reads from row 1,000 and then shows all 1,001.
- The migration's stub runs are in its doc.
