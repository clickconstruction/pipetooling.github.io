# v2.6109 — The Bid Board's tools row fits a 320 px phone (2026-10-29)

Fix, no migration, no edge function. Found on 2026-10-29 by v2.6065's live check (PR #6439): at 320 the Health section's band stayed inside its 288 px column, but `document.documentElement.scrollWidth` read 349, because the board's tools row ran 30 px past the window. v2.5977 had cleared the board's sideways scroll at 375, and `e2e/viewport-smoke.spec.ts` measured the board at 375 only.

## Cause

The tools row (`BidsBidBoardTab.tsx`, the first thing under the tab's heading) is one `nowrap` flex row: the search input (`flex: 1 1 auto`, `min-width: 0`), the development filter (`flex-shrink: 0`, capped at 7.5rem on a phone) and a `flex-shrink: 0` group of four presses: Marked bids, Archived, Reply book, Customer review. The search is the only part that shrinks, and it stops at its own 18 px of border and padding. The fixed parts come to 334 px with their gaps (18 + 8 + 120 + 8 + 180), so the row fits only in a column 334 px wide or wider, a screen 366 px or wider. At 375 the search draws 27 px wide and the row fits; at 320 the column is 288 px and the group ran 170–350, past the window.

## Fix

- **`lib/bidBoardToolsRow.ts`** (new): `BID_BOARD_TOOLS_WRAP_MQ` is `(max-width: 365px)`, the widest screen whose column cannot hold the row. `bidBoardToolsRowLayout(wrap)` gives the row's `flex-wrap`, the search's `flex` and the group's `margin-left`. Under the query the row wraps, the search takes a `9rem` basis so it shares the first line with the filter (144 + 8 + 120 = 272 px in a 288 px column, then grows to 160) and the group drops to its own line, `margin-left: auto` keeping it at the right edge where it sits on every other width. Over the query the three values are what they were (`nowrap`, `1 1 auto`, none).
- **`BidsBidBoardTab.tsx`** reads the query with `useMatchMedia` and puts the three values on the row, the input and the group. Nothing else in the row changes; the four presses keep their widths.
- **`e2e/viewport-smoke.spec.ts`** adds one test at 320 × 740 for `/bids?tab=bid-board`, with the same network-quiet wait as the 375 entry. 375 never runs the wrap, so the width is the only way the smoke exercises it.
- **Docs**: `BIDS_BOARD_FORM_ARCHITECTURE.md` (B13, B14, the toolbar paragraph, the e2e line), `E2E_SMOKE.md`.

## Tests

- `bidBoardToolsRow.test.ts` (new, 3): the query stops at 365; the wrapped layout's three values; the one-line layout's three values. jsdom cannot measure a flex line, so the structure is pinned and the smoke measures the page.

## Verified

Dev server from the worktree, the estimator twin, Bid Board → Plumbing, the row measured with `getBoundingClientRect`; `scrollWidth` against `innerWidth`; every element outside an `overflow-x` box checked against the window's right edge. Before and after:

| Width | Column | Row | Search | Filter | Group | scrollWidth = innerWidth | Past the window |
|---|---|---|---|---|---|---|---|
| 320 before | 16–304 | one line | 18 px | 120 px | 170–350 (180 px) | no: 349 in 320 | the group, 46 px |
| 320 after | 16–304 | two lines | 160 px, line 1 | 120 px, line 1 | 124–304 (180 px), line 2 | yes: 320 | none |
| 375 before and after | 16–359 | one line | 27 px | 120 px | 179–359 (180 px) | yes: 375 | none |
| 1,280 before and after | 56–1,224 | one line | 530 px | 182 px | 784–1,224 (440 px) | yes: 1,280 | none |

At 375 and 1,280 every number is the same before and after, so v2.5977's one-line draw at 375 holds.

## Left as is

- The Archived press keeps `0.5rem 1rem` padding on a phone where its neighbours use `0.6rem`; 13 px that would not have brought the row inside 288 px on its own.
- A 340 px column (a screen between 366 and 375 wide, if one existed) still draws the search under 30 px wide on one line, as it did at 375 before this.
