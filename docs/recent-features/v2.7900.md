# v2.7900 — Robots: an assistant can list a robot's keys and revoke one (2026-11-19)

Three verbs on `dev-mcp` (server 0.107.0, 131 write verbs, 78 naming no RPC, 182 tools): **`read_twin_keys`**, and **`plan_twin_key_revoke`** → **`apply_twin_key_revoke`**. The owner, 2026-11-19: "build the next gap: revoke a twin key."

## Why

The seat could mint a twin's key with `mint_twin_setup_code`. It could not see a key or take one back. Both were presses on Settings → System → Digital twins, and `read_rows` refuses `twin_credentials` outright.

## The list

`read_twin_keys { twin? }` is a read, for devs only.

- Each twin answers with its live keys: `key_id`, `label`, `made_at`, `last_used_at`, `last_seen_at`, and whether its rounds are stopped.
- Its revoked keys are counted, and the newest five are named.
- `twin` narrows the list to one twin, by its users.id or its fleet address.

## The revoke

- `revoke = { twin, label }` cuts off every live key of that twin wearing the label. A label is the name a machine's key was given when it was minted.
- `revoke = { twin, key_id }` cuts off one key.
- The plan reads the twin and its keys as the dev. It answers the keys it would revoke and the live keys that stay. It says when no live key would be left.
- The plan hash commits to the keys as they read. A key revoked or minted since the plan refuses the apply.
- Apply is the panel's own write (`DigitalTwinsPanel.revokeToken`): `revoked_at` on each key's `twin_credentials` row, as the dev under the table's dev-only RLS. It is one key a write, and each is reported done or held.
- Refused in words: no such twin, no such key, a key already revoked, and both or neither of `label` and `key_id`. A refusal names the labels that are live.

There is no undo, as in the panel. A new key is `mint_twin_setup_code`.

## What never crosses the door

`twin_credentials` stays in `DENIED_TABLES`, so `read_rows` and embeds still refuse it. The three verbs read it through one fixed column list, `TWIN_KEY_SELECT`, which never names `token_hash`. The PATCH asks for `id` alone. A key or its hash is never in a reply or a log line.

## What it leaves alone

- The copies of a key's hash that CountTooling and TakeoffTooling hold. The panel does not touch them either. Every seat call resolves the PipeTooling row first, so a revoked key is refused there.
- Stopping a Mac's rounds, the rung, the calibration standard and Archive. They stay presses in the panel.
