# v2.7642 — Drive uploads: a busy Drive is named as busy, with its own words (2026-11-17)

The follow-up to v2.7635, on the owner's yes the same day. That change made `drive-link` name the reason of a failed upload. This one fixes the helper underneath, so the reason is there to name.

**What happened on 2026-11-17.** A receipt photo on the Lien desk failed and the screen said `failed`. The function's log held the cause: `uploadBytes` threw `SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON`. Drive had answered the upload with a web page, which Google's front door sends when it is busy or a gateway failed. `_shared/driveUpload.ts` read every answer with a bare `res.json()`, so the page threw before the helper could look at the status.

**The read.** Three pure pieces in `_shared/driveUpload.ts`:
- `driveAnswerOf(text)` answers the JSON body, or an empty body with `unread: true` and the page's own title.
- `drivePageTitle(text)` reads `<title>` as a person would: entities decoded, line breaks folded, Google's trailing `!!1` dropped, 120 characters at most. *Error 502 (Server Error)*.
- `driveAnswerWords(answer)` picks the reason: Drive's `error.message`, Google's `error_description`, a bare `error` string, the page's title, or `unknown`.

**Where it is used.** `googleAccessToken`, `findOrCreateFolder`'s create, `uploadBytes`, `startResumableUpload`, `putResumablePiece` and `resumableStatus` throw the sentences they always threw, with the status kept: `Upload failed (502): Error 502 (Server Error)`. The three calls for an upload in pieces already caught the bad read; they now keep the title too.

**A page is never an empty list.** `findOrCreateFolder`'s look and `findExistingFile` read their list through `readDriveList`, which throws `Drive answered <status>` on a page. Both threw before, by accident of the bad read; the throw is now deliberate and named, so a later tidy-up cannot turn a page into "no such folder" and make a second one. A JSON answer, an error included, reads exactly as it did.

**With v2.7635.** `drive-link`'s reader (`driveFailureOf`) already knows these shapes: `Upload failed (502): …` becomes *Drive did not take the file. Drive said: Error 502 (Server Error)*, and the status decides whether **Try again** is offered. A page with a 413 no longer offers a second try that cannot help.

**Not changed.** `uploadFromUrl`'s read of a file's name (`metaRes.json()` after `metaRes.ok`) and the other Drive helpers (`driveJobFolder.ts`, `fileIndex.ts`), which have their own reads.

**Tests.** `src/lib/documents/driveUploadAnswer.test.ts`: the three pure pieces, `uploadBytes` against a page, a JSON refusal and a success, both list reads against a page, and `googleAccessToken` with a made-up key against a refusal, a page and a success. The 97 test files that reach the Drive helpers pass unchanged.

**Deploy.** The seventeen functions that reach the helper: `bid-photos`, `bid-plan-set-files`, `bill-lines-sweep`, `dev-mcp`, `drive-contract-scan`, `drive-intake`, `drive-link`, `file-index-sweep`, `file-submittal-package`, `gc-drive-access`, `hr-evidence-drive`, `job-drive-folders`, `job-photos`, `messages-email`, `photo-save`, `plan-set-files`, `submit-gc-trade-portal`. No migration. A function left behind keeps the old crash and nothing else.
