# v2.8301 — Documents → Photos: the list reads again on All and on Texts & email (2026-11-22)

Found on the live walk of v2.8215 (punch list #306, PR 9). One migration on a view. No client change, no edge function.

## What was wrong

Documents → Photos answered *The photos did not read: canceling statement due to statement timeout* on **All**, its first screen, and on **Texts & email**. The other chips read. It was older than the walk: the gateway's log shows the same read failing on 2026-11-17 and 2026-11-18.

The view `uploaded_photos` finds the job behind a text's picture with a join written as `j.id = COALESCE(m.jobs_ledger_id, gp.billing_job_id)`. Postgres uses a join clause as an index condition on a table with row policies only when it can prove the clause leaks nothing. It does not prove that of a `COALESCE`. So every job was walked under `jobs_ledger`'s policies, once per picture: 111 pictures at about 170 ms a walk. The branch ran 14 seconds as a dev and the whole list 29 seconds as an assistant, against the 8 second limit.

## What changed

- **The join is a `CASE`** ([`20261122063000_uploaded_photos_message_job_join.sql`](../../supabase/migrations/20261122063000_uploaded_photos_message_job_join.sql), [its doc](../migrations/20261122063000_uploaded_photos_message_job_join.md)): the line's own job when it names one, the project's billing job when it does not. The same job, found by its key. The rest of the view is word for word what `20261121222237` wrote.
- **The rule has a home**: `docs/MIGRATIONS.md`, Key Principles. A join onto a table with row policies is a plain equality or a `CASE`, never a `COALESCE`.
- **The bed holds it**: `bid-photos` asserts that a text on a job and a text on a project both name the job, and that the plan finds the job by its key.

## Checked

- On prod, read-only, with the new `SELECT` in place of the view: the old and the new branch hand back the same 111 rows; the branch runs in 31 ms; the whole list runs in 133 to 407 ms as each of nine roles.
- Not run here: the SQL bed, which needs Docker. It runs on the PR.

## After the merge

`supabase db push`, then the list is walked on the live app. Until the push the list keeps timing out, as it does today.

## Left

- The Photos tab keeps a failed read's red line on screen after a later read succeeds, and a slow read can land over a newer one. Its `load` does not check that it is still the newest ask. Not changed here.
- Two other `security_invoker` views join through a `COALESCE`: `agreements_on_file` and `people_hours_recorded`. Neither was measured.
