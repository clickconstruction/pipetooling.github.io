# v2.4044 — GC Review and the portal: under each bill, what paid it (2026-09-28)

Client only; no migration, no edge function. PR 2 of "Where the checks went" (after [v2.4043](v2.4043.md), the kernel). The first shape of the GC's question — *"did you get our check for Oak Ridge?"* — answered before it is asked.

## What shipped

- **`GcReviewRow.paidBy`** (`src/lib/gcReviewRollup.ts`) — every statement row now carries `billPaidByWords(job, invoice)` from the kernel: *paid in full by #48102 on Sep 10* · *$12,000.00 paid by #48211 on Sep 24 · $1,333.00 still open* (with *, the retainage you hold* when what is left is within the job's recorded `lien_retainage_held`) · *nothing applied yet* · for a job balance with no bill, *paid $21,750.00 so far by …*. The board rows already embed each job's payments and invoices, so nothing new is read.
- **The printed statement** (`gcStatementReport.ts`) — the line under the job, small and grey.
- **The bill lines** (`GcBillLines.tsx`: the certify checklist and the call sheet) — the line under each bill, in both the full and the compact layout.
- **The portal** (`CustomerPortal.tsx` → `portalBillPaidByWords` in `lib/portal/portalJobGroups.ts`) — the same line under each open bill, from the per-bill payments the payload already carries. The portal's method label is the raw `payment_type` (*check*), not the number — the number reaches the portal in PR 5 with the edge function change.
- Guides: *run your weekly GC statement round* (the opened row), *share a customer their portal* (what a job section shows).

## Not in this PR

- **The statement email** keeps its rows as they were. Its server lane renders from `get_gc_statement_email_payload` and the parity test pins the two renders byte for byte, so the line reaches the email with the RPC change, as its own PR after the train.
