# v2.2843 — Error classification by class: "No connection" only when the connection failed (2026-09-05)

Journey-map Tier-1 #6(a) (J18-N1 systemic, J18-F1 loudest instance, J2-F3 the genuine offline path). Two message-text mechanisms in the error plumbing combined to report almost every database error as an outage:

1. **The prefix contained the offline token.** `checkSupabaseError` built every `DatabaseError` message as `Failed to <operationName>: <server message>`. For an operation named `fetch…` — **~100 distinct `'fetch…'` operation-name strings in `src/`** (`fetchScheduleJobContext`, `fetch bid for preview`, `fetch common jobs`, …) — that prefix contains the literal `failed to fetch`, which `isNetworkFetchErrorMessage` (`src/lib/networkErrorMessage.ts`) treated as Chrome's no-signal signature. So a `22P02` (bad uuid), a `42501` (RLS refusal) or a missing column from any of those reads rendered `OFFLINE_ERROR_MESSAGE` ("No connection — … nothing was saved. Check your signal") through **~555 `formatErrorMessage` + 16 `formatPostgrestOrUnknownError` call sites**.
2. **The retry token was `'fetch'`.** `isRetryableError` matched the bare word `fetch` in the message, so the same permanent failures were retried 4× (the "Operation failed (attempt 1/4)…" console loop in F1) before the fake offline page appeared.

Live specimen (J18-F1): clicking a bid block's time range on the week grid opens `?jobId=bid:<uuid>`; the loaders feed that raw into uuid `.eq()` filters → `22P02` → ×4 retries × 2 loaders → "No connection" + empty roster.

## The `kind` model

`DatabaseError` now carries structure, decided by **class, never by message text**:

| `kind` | Evidence | Rendered | Retried |
| --- | --- | --- | --- |
| `network` | supabase-js result with `code: ''` and `status: 0` (how postgrest-js reports a rejected `fetch`), or a raw `TypeError` carrying a fetch-layer signature (`isFetchLayerTypeError`) | `OFFLINE_ERROR_MESSAGE` | yes |
| `server` | any PostgREST/Postgres `code`, or an HTTP status ≥ 400 with no body code (Cloudflare 522 etc.) | sentence by code family (below) | only transient codes (`40001`, `40P01`, `53xxx`, `57P03`, `08xxx`, `PGRST000-003`) or, with no code, 408 / 429 / 5xx. **Never** `22P02`, `42501`, `PGRST116`, `23xxx`, other 4xx. `57014` (statement timeout) stays non-retryable — pre-existing rule kept |
| `unknown` | no code, no status, no fetch signature (a bare `new DatabaseError('…')`) | the message as-is | old message tokens (`network`, `connection`, `timeout`, `deadlock`, …) **minus the bare `fetch` token** |

Also preserved on the object: `code`, `status`, `operationName`, `serverMessage` (the server's message before the prefix). `.message` is unchanged (`Failed to <op>: <server message>`) so console output and the existing `/Failed to load stuff: boom/`-style tests hold; the user-facing sentence comes from `formatErrorMessage` / `formatPostgrestOrUnknownError`.

New exports in `src/utils/errorHandling.ts`: `classifyResultError`, `databaseErrorFromResult` (the factory `checkSupabaseError`, `executeDeleteChain` and `supabasePaging.fetchAllRows` now use), `describeClassifiedError`, `humanizeOperationName`, `operationSubject`, and `isRetryableError` (now exported for tests). `SupabaseClientResult` / `checkSupabaseError` accept the awaited builder's `status` so the class is decided from it; the 3-arg `new DatabaseError(message, code, details)` signature still works (39 direct constructions untouched — they classify from `code`).

## Code → sentence

| Code | Sentence |
| --- | --- |
| `42501` (insufficient_privilege / RLS) | read: **"You don't have access to this <subject>."** (`fetchScheduleJobContext` → "…this schedule job context.") · write: **"You don't have permission to <op words>."** · no operation: "…this record." |
| `22P02` (invalid uuid text), `PGRST116` (`.single()` found no row) | **"This link points to something that doesn't exist any more."** |
| any other code, read op (`fetch`/`load`/`get`/`list`/`read`/`query`/`count`/`select`) | **"Couldn't load <subject>: <server message>"** |
| any other code, write op | **"Failed to <op words>: <server message>"** (camelCase and underscores → words) |
| `kind: 'network'` | `OFFLINE_ERROR_MESSAGE` (unchanged copy) |

`formatPostgrestOrUnknownError` leads with the same sentence, then its existing `Code:` / `Details:` / `Hint:` lines; a network-kind error returns the offline copy alone (no stack in `Details`).

## The text kernel is now a last resort

`isNetworkFetchErrorMessage` keeps the per-engine tokens (`load failed`, `networkerror`, `fetch failed`, …) but Chrome's `failed to fetch` must now end the sentence (`/failed to fetch(?=\s*$|[.,;:)\]\n])/`): `TypeError: Failed to fetch` and `Failed to insert X: TypeError: Failed to fetch` match; `Failed to fetchScheduleJobContext: …` and `Failed to fetch bid for preview: …` do not. It is consulted only for inputs with no structure at all (bare strings, plain `Error`s without a `code`). **Legacy behaviour documented:** `formatErrorMessage('TypeError: Failed to fetch')` → offline copy; `formatErrorMessage('Failed to fetchScheduleJobContext: invalid input syntax…')` → shown as-is; a `new DatabaseError('Failed to fetchFoo: boom')` with no code is `unknown`, shown as-is, not retried; a `new DatabaseError('TypeError: Failed to fetch')` (raw engine message, as `salaryScheduleSync` passes) is `network`.

## Telemetry (console-only, follow-up hook)

`src/lib/errorClassTelemetry.ts` — same shape as the row-cap tripwire (v2.2756): `reportErrorClass` writes one `console.warn` line `[error-class] <kind> <code|-> <operation|->` per (kind, code, operation) per page load, at the moment a `DatabaseError` (or fetch-layer `TypeError`) is rendered by either formatter. No sink yet. **Follow-up:** a real `error_shown{class, operation}` event — `errorClassKey` is its natural identity — so the two classes can be counted in production instead of inferred from support screenshots.
