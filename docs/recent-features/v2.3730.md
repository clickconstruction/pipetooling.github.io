# v2.3730 — dev-mcp 0.4.1: one apply per plan (2026-09-22)

Found by the live pass of [v2.3722](./v2.3722.md)'s verify list, run the same day with a temporary dev key the owner issued. Function only; no migration.

## What the live run found

Everything in the list held — wrong hash and changed payload both *Nothing written*, the batch row names the dev, revert cleans up, `view_as` refuses every write verb, the HR wrapper's gate answers — except step 6, added on the spot: **the same plan applied twice with the same hash landed twice**. The hash re-derives the dry run, and a thread note (or an HR entry) has no before-state, so the second dry run is identical to the first. An allocation would not replay (its before image changes once it exists); a note or an HR entry would.

## The change

- **[`dev-mcp/index.ts`](../../supabase/functions/dev-mcp/index.ts)** 0.4.1 — `priorApply(admin, verb, hash)`: before the real POST, the apply branch asks `dev_mcp_calls` (service role, the log the function itself writes) for an ok `apply_*` whose logged `args->>plan_hash` is this hash — any dev's key — and refuses with the earlier target and time. For `apply_cost_batch`, a batch since reverted does not count, so a wrong batch can be reverted and the same plan applied again on purpose. `runVerb` takes the lookup as a hook; `view_as` never reaches it.
- **[`devMcpWrites.ts`](../../supabase/functions/_shared/devMcpWrites.ts)** — `alreadyApplied(verb, prior)`, the refusal sentence; the plan reply's `next` says *one apply per plan*.
- Docs: `dev-mcp/README.md`, `EDGE_FUNCTIONS.md` → dev-mcp. The to-do's PR 6 section gets the live results in the docs-only PR that follows #3569 (the same file is queued there).
