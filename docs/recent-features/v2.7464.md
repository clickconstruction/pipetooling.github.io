# v2.7464 — Plans: Change the link on a set that is already saved (2026-11-16)

The app half of the saved-set link change; the dev seat's half is v2.7458. An inventory of one development on 2026-11-16 found saved sets whose `plan_sets.link` points at a file the company does not own, while the company's Shared Drive holds its own copy. The Plans section could add a set, switch a part, edit what changed and remove a set, and nothing could move a saved set's link. Removing and adding the row again would break `replaces_set_id` chains and a part's `current_set_id`. Proposed from the inventory; the owner has not asked for it yet. No migration.

## What landed

- **Kernel, `src/lib/plans/planSets.ts`.** `LINK_PRESS` (*Change the link*, *Set the link*, *Save the link*), `linkPressWords(set)` (the press a row offers: *Set the link* while the set has none), `linkChangeProblem(current, draft)` (empty, not `https://`, over the column's 2,000 characters, or the link the set already has) and `linkChangeNote(isCurrent)` (the line under the box).
- **The write, `planSetsIo.updateLink(setId, link)`.** One update on the row's own id: the link, and the file facts read behind the old link (`file_name`, `file_size`, `file_count`, `checked_at`, `check_note`) set to null. It asks the row back, so an update that RLS lets through no row is an error (*This set is not yours to change.*) and not a silent save.
- **The box, `src/components/plans/PlanSetLinkEditor.tsx`.** Opens with the link the set has, says what the save moves, names a pasted link's problem, and keeps **Save the link** dead until the link is a new one.
- **The job window's Plans section (`JobPlansSection.tsx`).** The press on the set under *Building from*, on each older set and on each as-built, for the five office roles that add a set. Saving the current set's link tells the window through `onPlansLinkChanged`, as a switch does.
- **The Development page's Plans look (`DevelopmentPartsCard.tsx`).** The same press beside *Open ↗* on a part's current set, each older set and each as-built, through a new `SitePlansWrites.changeLink` that `DevelopmentPage.tsx` wires to the io with the page's own toast on a failure.
- **No mirror call, no migration.** `plan_sets_mirror_on_change` fires `AFTER UPDATE OF link` and writes the part's current set's link onto every job naming the part, and `plan_sets_update` already passes for `plan_part_can_write`. `planSetLink.test.ts` pins both.
- **Guides**: *keep the plans on a job* gains **Change the link of a set**; *see everything on a development* names the press. The glossary's *Plan sets by part* sentence is amended in place.
