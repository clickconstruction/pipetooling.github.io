# v2.6194 — A copied bid keeps each row's plan tag (2026-10-30)

A prod data-loss gap the merge-ledger session found on 2026-10-31 through the copy guard, fixed in one migration, `20261031000000_bid_copies_carry_plan_tag`. The four SQL functions that copy or move a bid's takeoff — `create_bid_version`, the `clone_count_rows_to_bid_version` it calls, `duplicate_bid_to_service_type` and `adopt_bid_as_version` — name their columns one by one, so a column added to `bids_count_rows` later is silently left out of every copy. That is the incident behind the guard, `src/lib/bids/bidCopySql.test.ts` (v2.4388, punch list #78), which pins each function's newest body to the generated types.

## The gap

Two migrations merged on 2026-10-30 without touching the copies. `20261030200000_bid_plan_sets` (#6560, v2.6169) added `bid_plan_sets`, a table keyed by bid alone, which the guard does not watch and no copy carries (a follow-up below). `20261030230000_robot_fixtures` (#6581, v2.6180, punch list #221) added `bids_count_rows.plan_tag` — the robot's tag (*WC-1*) on a row its fixtures landed, drawn as the chip beside the name — and `bid_fixture_pulls` / `bid_fixture_pull_rows`, the robot's record of what it read; the guard sees the pull rows as a table hanging off a count row (they carry `count_row_id` and `bid_id`). Both are applied on prod. From the robot-fixtures push until this migration is pushed, a new version and a duplicate drop every row's `plan_tag`; an adopt moves rows whole and drops nothing. The guard reads `database.ts`, so it went red only with the types chore that followed the push, #6593 (six failures), which the merge-ledger session held until this fix.

**What was lost on prod: nothing, as far as the dev seat can read.** #6581 merged at 2026-10-31 02:16 UTC and the push came after it. The newest bid on prod was made at 2026-10-30 20:42 UTC (three human bids and their three ZZ shadow shells, all plumbing, none a copy); no bid version with a source version and no adopt was made on 2026-10-30 or since, read at about 03:00 UTC on 10-31. `plan_tag` has one writer, `take_robot_fixtures`, whose window is PR 3 of #221 (#6591, unmerged), so no tagged row existed to lose either. The deployed dev-mcp's catalog predates the push and refuses `plan_tag` and the pull tables by name, so those two counts wait for the catalog that #6593 ships.

## What changed

- **Migration** (`docs/migrations/20261031000000_bid_copies_carry_plan_tag.md`): `clone_count_rows_to_bid_version` and `duplicate_bid_to_service_type` redefined with `plan_tag` added to the copy's SELECT and INSERT and nothing else changed, both bodies as `20261020020000_bid_count_row_marks` left them. No table, so no fences.
- **The robot's pull rows stay with the bid the robot read, on every copy**, and the guard lists `bid_fixture_pull_rows` beside `bid_changes` as the robot's record, not a row on a count row. A pull is one read of one bid's plans on one run (the bid, the shell, the run, the set it read); a pull row's `count_row_id` only remembers which row of hers the take landed as. A new version clones her rows with their `plan_tag` and the robot's share, so the shade and the chip survive, while the take stays recorded once, on the version she took it on (`taken_version_id`), the way the fixtures score reads it; two pull rows for one fixture found once would count it twice. A duplicate is a new bid with no run and already leaves the count sources behind (v2.5517): a pull there would describe another bid's read. An adopt leaves the pull on the adopted bid with its run, where `robot_progress()` reads it, still pointing at the moved row.
- **Guard**: `bidCopySql.test.ts` names the table in its exemption with the reason and checks the types still carry it. Green against #6593's `database.ts` (46 tests).
- **Bed** `supabase/tests/bid_copies/20_scenario.sql`: a `copt.robot_read` seeds one pull and one taken row wearing its tag on two of the bed's bids, and the scenario holds the new version's tags with one pull row still on the first version's row, the duplicate's tags with no pull of its own, and the adopt's pull staying on the adopted bid pointing at the moved row.
- **Docs**: `BIDS_SYSTEM.md` (what a copy takes, the row's marks line).
