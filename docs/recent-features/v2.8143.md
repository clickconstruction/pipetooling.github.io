# v2.8143 — Document builder: a draft has a number in the database (2026-11-20)

Punch list #404. A migration alone, the ground for two faults the review of 2026-11-20 found and did not fix. The client that names the number comes after the push.

## Why

A builder's draft and a job's sheet's draft are saved a moment after the typing rests. A save named nothing it was loaded at (`saveBuilderDraft`, `saveSheetDraft`). A publish named the revision, and nothing else.

So a tab left open could write its old draft over a newer one. The reply carried the row's newer revision back to that tab, and its publish then named that revision and put the old words out as the next one. And the usual's publish to every job wrote each job's draft from the page as it was loaded: a draft a teammate had saved since does not move the job's revision, so nothing refused it.

## What it adds

`20261120160000_document_builder_draft_no.sql`:

- `document_builders.draft_no` and `document_builder_sheets.draft_no`, an integer that goes up one each time the row's draft or its revision changes.
- Each table's stamp sets it from the row as it was, whatever the client sent. The two stamps are replaced in place and nothing else in them changes: a script held each new body against the old one, and the only lines that differ are the number's.
- A read mark does not move the number, and neither does a draft saved as it already reads.

A save or a publish will name the number its page read, `WHERE draft_no = n`, and land on no row when the row moved on. The page then reads the row to say why.

**The number and not the row's `updated_at`.** The stamp sets `updated_at` to the transaction's time, which is one value for a whole bed scenario, so no bed could hold the rule. A read mark also moves it. The number is exact, and a bed can read it.

**A filter and not a refusal raised by the stamp.** A stamp cannot see what a write's `WHERE` named. It could refuse a number sent in the write itself, but a page on the old client sends none, and must keep saving until it is reloaded. So the guard is the same shape the publish already had on `revision`.

## Tests

Section 4b of `supabase/tests/document_builders/20_scenario.sql` and section 2b of `supabase/tests/document_builder_sheets/20_scenario.sql`: two pages read a row at one number, the first save lands, and the second save and a publish from the page that fell behind land on no row. A number sent by the client, a draft saved as it reads, a read mark and its taking off do not move the number. A publish does.

Docker is not running on this Mac, so CI's `sql-beds` job was the beds' first run.

Each bed's script applied its table's migration a second time, to prove that changes nothing. That would now put the old stamp back, so each script applies the table's migration and then this one.
