# v2.7947 — Robots: an assistant's plans count the robots' scored bids (2026-11-19)

A fix to three `dev-mcp` plans shipped the same day in v2.7928, v2.7934 and v2.7939 (server 0.112.0, no new verb).

## What was wrong

The first live dry runs after the deploy answered counts that did not match the Robots board.

- `plan_calibration_standard` said no scored shadow run named the person as teacher. The board listed 22 scored runs, 2 of them the standard's and 20 another estimator's.
- `plan_robot_book_price` answered `locked_robot_bids: 0` for a price 18 bids read.
- `plan_bid_update` named the axes in use without the runs' own.

No apply was run on any of them.

## Why

All three read `twin_shadow_runs` over REST as the dev. That table has had no read policy for a signed-in person since migration `20260901010000`. Staff read the runs through `list_shadow_runs()`, which keeps the money null until a run is scored. A direct read is not refused. It answers no rows and no error, so each plan counted zero and said so with confidence.

The unit tests passed because they ran over made-up rows. Only a read against the real policy showed it.

## The fix

Every read of the runs in the seat goes through `rpc/list_shadow_runs` (`SHADOW_RUNS_READ` in `_shared/devMcpShadowRuns.ts`).

- The RPC gives a run's `teacher_name` and never the teacher's id. A person's runs are the ones that carry their name, whatever its case or padding (`calibrationRunsOf`). The reply says `matched_by`. A person with no name reads as unknown, never as none.
- The RPC gives a run's `shadow_bid_number` and never the bid's id. A locked robot bid is matched by its number.
- A refused read of the runs is `null`. The robot book plan then warns that locked robot bids are not counted, and answers `locked_robot_bids: null`.

## The guard

`src/lib/devMcp/devMcpShadowRuns.test.ts` holds three things.

- The columns the plans ask of the RPC are ones its generated type answers.
- No `devMcp*` kernel and no branch of the server reads `twin_shadow_runs` itself.
- No migration after `20260901010000` gives the table a read policy. If one does, the test fails and the reason is revisited.

- `supabase/functions/_shared/devMcpCalibrationStandard.ts`, `devMcpRobotBookPrice.ts`, `devMcpBidUpdate.ts`.
