# v2.2462 — Estimate Options, Phase 3: read-backs (2026-08-28)

Phase 3 of 3 (plan in v2.2457, customer flow in v2.2460). The office learns what the
customer did with the choice:

- **Activity feed knows the deliberation.** New public edge function
  `log-estimate-option-view` (token-validated like `get-estimate-for-customer`; always
  200, drops invalid input silently) appends `option_viewed` events with the option's
  key/name; the acceptance page fires it on every card pick, fire-and-forget. The detail
  page's Customer activity renders "Viewed option — Tankless upgrade · <ip> — <time>".
  Migration `20260828193012` widens the two `estimate_customer_events` CHECK constraints.
- **The acceptance record says what was chosen of what was offered**: "Accepted
  “Replace 50-gal” · $3,400.00 (of 3 offered)" with the unchosen options listed greyed
  beneath — the record shows what was sold AND what was passed on.
- **List rows badge the choice in flight**: Pipeline and Ledger money cells append
  "· 3 options" (muted) on multi-option estimates until acceptance, via a cheap
  keyed-entry counter (no full normalization in 200-row renders).

Deliberately NOT done — the CX override key for the picker heading (planned in v2.2457's
Phase 2 list): `parseEstimateCustomerExperienceSnapshot` is strict — a new required key
would null out the frozen `customer_experience_sent` snapshot of every previously-sent
estimate, silently swapping their locked copy for live-resolved strings. The heading
stays fixed ("Choose your option"); if someone actually needs to reword it, it can join
the CX system with an optional-key parse the way `accept_page_footer` did.

**Deploy after merge**: `supabase db push` (constraints migration), then
`supabase functions deploy log-estimate-option-view`.
