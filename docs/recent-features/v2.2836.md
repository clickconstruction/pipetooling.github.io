# v2.2836 — Superintendents see only their assigned projects: RLS adoption branch removed; primary Workflow route dropped (2026-09-05)

Journey map J31 (private repo, Tier-1 #4 — N1/N2/N4/N7, D3). Live on 2026-09-04: `projects` = 3, `project_superintendents` = 1 row, `master_superintendents` = 4 rows (3 masters × 2 superintendents); the walked superintendent was assigned to at most 1 project and saw all 3, with every step's **Line Items For Office** readable and writable.

**Mechanism.** The `projects` SELECT policy calls the **3-arg** `can_access_project_row(id, master_user_id, customer_id)`, which returned true on a `master_superintendents` adoption row *before* it ever reached the assignment check. The 2026-06-23 `superintendent_assigned_only` migration had rewritten only the **1-arg** overload. v2.921's `sync_company_access_grants()` then made adoption universal (every live dev/master × every live superintendent), so the untouched branch granted every project. The same adoption grant reached `project_workflows` (via `can_access_project` → `master_adopted_current_user`), `workflow_step_line_items` CRUD and the signed sub work orders `step_commitments` (via `can_access_project_via_step`), and step actions (`can_access_step_for_action`).

**Migration** [`20260905100000_project_access_assigned_superintendents.sql`](../migrations/20260905100000_project_access_assigned_superintendents.md) — `CREATE OR REPLACE` of four helpers, no table/policy/grant changes:

- `can_access_project_row(uuid, uuid, uuid)` — `IF user_role_val = 'superintendent' THEN RETURN user_assigned_to_project_as_superintendent(project_id_param)` placed before every adoption check (mirrors the 1-arg overload); the two `master_superintendents` `EXISTS` branches removed.
- `can_access_project(uuid)`, `can_access_project_via_step(uuid)`, `can_access_step_for_action(uuid)` — adoption (`master_adopted_current_user`) now consulted only when `user_role_val IS DISTINCT FROM 'superintendent'`; superintendents take `can_access_project_row(project_id)` (strict) instead.
- **Left alone, deliberately:** `master_adopted_current_user()` body (the `users` SELECT policy relies on its superintendent branch so a superintendent can see the masters who adopted them — only its COMMENT is corrected); the `master_superintendents` table and `sync_company_access_grants()` (dashboards, dispatch/schedule RLS, bids helpers, people RLS, tag org, feedback still read it); `can_access_project_row_for_user()` (schedule-email cron path whose callers grant superintendents via their own direct adoption checks — dispatch is company-wide by design); `can_access_project_via_workflow()` (no adoption branch of its own; fixed through `can_access_project`).
- dev / master / assistant-like / primary / owner / customer-side branches byte-for-byte unchanged.

**Primary route (D3 subtraction).** `/workflows` removed from `PRIMARY_PATHS` in [`layoutRouteAccess.ts`](../../src/lib/layoutRouteAccess.ts); [`layoutRouteAccess.test.ts`](../../src/lib/layoutRouteAccess.test.ts) now asserts `/workflows/abc` → false for primaries. The `project_workflow_steps` SELECT policy has no primary branch (dev | master | assistant+via_workflow | superintendent+via_workflow | helpers/sub+`step_assignee_matches_user`), so a primary's Workflow page always rendered "No steps assigned to you" — and no link in the app produced the URL. The alternative (a `role='primary' AND step_assignee_matches_user(...)` branch on the steps SELECT) was not taken: no door exists, no primary is assigned a step in prod, and adding a grant to fix a dead grant widens the surface this PR is narrowing.

**Docs:** `ACCESS_CONTROL.md` (superintendent "assigned projects only" claims now true in code; primary Workflow row/redirect list), `WORKFLOW_PAGE_ARCHITECTURE.md` (`master_superintendents` is a roster scope for the assign picker, not a project grant), help guides `see-project-status-at-a-glance` + `start-here-as-a-superintendent` say "the projects you're assigned to" explicitly.

**Verify after `db push`** (recipe in the migration doc): as a superintendent `select count(*) from projects` = their `project_superintendents` row count; `project_workflows` / `project_workflow_steps` / `workflow_step_line_items` / step-anchored `step_commitments` limited to those projects; as dev, counts unchanged.
