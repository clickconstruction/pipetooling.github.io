# v2.3031 — Test-gap audit, pass 41: emailing a signed lien release gets its first tests (2026-09-07)

Follow-up to v2.3030. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`sendLienReleaseEmail.ts` (148 lines) is the "ready to send" lane's primary action on the lien signature inbox: it emails a signed release to the job's customer with the PDF attached — the exact bytes stored at signing when the bucket has them, else a regeneration with the typed signature — through the `send-lien-release-email` edge function, which validates the recipient, sends and stamps the row. One caller, no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Only a signed, unvoided release can be emailed; the job needs a customer email; the caller needs a session. Each refusal names itself and nothing is sent.
- The stored signed PDF is preferred and sent byte-for-byte; when nothing is stored or the download fails, the PDF is regenerated with the typed signature and audit line (no signature block without a printed name), and an unknown form type falls back to conditional progress.
- A PDF over the size cap is refused before the send.
- The email is the plain, formal built-in unless a dev-saved wording override exists; the attachment is named `lien-release-<form>-<job number>.pdf` from the HCP number, else the Click number, else "job".
- The payload carries the release and job ids, the trimmed recipient, subject, text and HTML, the base64 PDF and the filename, with the caller's bearer token; the edge function's own error, a bare error, a body error and a thrown request each map to a message, with "Send release email failed" for anything unnamed.
