# v2.6904 — A scanned box stays open through a reload: the Tally's address keeps the box (punch list #209) (2026-11-10)

Found on the walk for v2.6900 (the empty page after a scan): a signed-in scan of a box label opened the cage, the new service worker reached waiting four seconds later, the first-paint reload fired, and the page came back at `/tally?tab=on-site` with no cage.

## Why

`BoxCode` sends a signed-in scan to `/tally?tab=on-site&job=<id>&container=<id>`. `JobTally` read `job` and `container` once, when its jobs had loaded, and took both off the address with a `replace`. Any reload after that reopened On site on the box list. Three reloads land there: `UpdatePrompt`'s first-paint reload when a new worker finishes installing, its 4 second fallback in `applyUpdate`, and a chunk recovery (`hardReloadFromRoot` saves `pathname + search` and restores it). After a client deploy, a phone one build behind met the first on its next scan.

## What changed

- **Kernel `src/lib/materials/onSiteAddress.ts`**: `readOnSiteAddress`, `withOnSiteBox` and `onSiteAddressStep`. The step compares the address with the one this page last read or wrote. An address moved by someone else (the first load, a scan, a door in Go anywhere, Back) is read when it names a job. Otherwise the screen wins: the address carries `job` and `container` while a box's screen is open on the On site tab and neither when it is not, and it is written only when it says something else. Nothing is read or written before the jobs load.
- **Hook `src/hooks/useOnSiteAddress.ts`**: runs the step for `JobTally`. It holds the asked box with a sequence number that goes up on every read, hears from the tab which box is open, and `pickJob` forgets the asked box when the person chooses another job. The sequence number is a dependency of the step's effect, so the step runs once more after a read that changed nothing else (a link to the job already chosen) and the address settles.
- **`TallyOnSiteTab`**: two optional props. `onOpenContainer` reports the box on screen (its count walk included), null on the list. `askSeq` joins the dependencies of the effect that opens the asked box, so a box asked for a second time opens again.
- **`JobTally`**: the read-once-and-strip effect is gone; both job pickers go through `pickJob`.

Writes are `replace`, as before, so the Tally adds no history entry of its own: Back from another page returns to the entry that names the box.

## Two older faults this closes

- After a scan, choosing another job drew *That container is not on this job any more.*, because the asked box outlived the job it was on.
- A second link to the box that was asked for and then left did not open it, because the asked id had not changed.

## What it does not change

- `BoxPublicPage`, `RouteChunkBoundary` and `src/lib/chunkLoadRecovery.ts` are untouched. `UpdatePrompt` still reloads when it did.
- A reload during a count walk comes back to the box, not to the line the walk was on.

## Tests

- `src/lib/materials/onSiteAddress.test.ts`: the step's cases, and a source check that `JobTally` reads and writes `job` and `container` only through the hook.
- `src/components/tally/TallyOnSiteTab.address.render.test.tsx`: the real tab over the hook at a scan's address. The address keeps the job and the box once the jobs load, a second load of that address opens the same box, leaving takes them off, a pressed box goes on, a link that names only a job is read and taken off, and the two older faults. With the old rule in the kernel three of its six cases fail.
