# v2.2011 — Pricing Workbench: target total is the whole-bid total; preview clears on scenario switch (2026-08-21)

Two confirmed behavior bugs found reviewing scenario/version UX on BP298, plus a target-input UX fix. Client-only — no migration.

**Solver** ([`pricingWorkbenchSolver.ts`](../../src/lib/bids/pricingWorkbenchSolver.ts)): `solveWorkbenchPrices` subtracted held (locked / onlyUnpriced-held) rows' revenue from the target but NOT the existing revenue on priced uncosted rows (`rowCost <= 0` with a `unitPrice`) — that revenue rode on top of the solve, so typing a 150,000 target on BP298 produced a $240,396.77 bid (~$90k of no-cost-row revenue overshooting). Now a `uncostedRevenue` sum comes out of the target alongside `heldRevenue` in both target-total and target-margin modes, so the typed number (and the slider margin) is the whole-bid result. 3 new kernel tests in [`pricingWorkbenchSolver.test.ts`](../../src/lib/bids/pricingWorkbenchSolver.test.ts) cover priced-uncosted with target total, the locked + priced-uncosted + free mix (no double-count), and margin mode.

**Scenario switch clears the preview** ([`BidsPricingTab.tsx`](../../src/components/bids/BidsPricingTab.tsx)): `wbPreview` (solver preview keyed by count-row id — counts are shared across scenarios) survived `handlePricingVersionChange`, so a solve previewed on one scenario carried onto another and Apply wrote it there. The handler now clears the preview first.

**Target input UX**: the target total no longer self-clears after solving (the typed number stays for tweaking/re-solving), and a success toast echoes the exact total the preview lands at (`Preview lands at $… total.`).
