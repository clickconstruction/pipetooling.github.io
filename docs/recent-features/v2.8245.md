# v2.8245 — Job Mode: Is it as told? says when the app could not read the list (2026-11-21)

Punch list #382, call D from the audit of PR 10 (v2.8110), on Taunya's word of 2026-11-21. Client only: `JobModeArrivalCheck.tsx` and one word line in `lib/startChecks/arrival.ts`. No migration, no edge function.

## The gap

PR 10's own fourth default was that a first read that fails is silent. That was right for a lost signal: the card is an extra on the way in, most jobs have nothing to ask, and the card reads again by itself when the signal is back.

It was silent for a refusal too. When the database answers the read with an error, the fault is ours and not the site's. The crew was asked nothing and nobody knew a question was missing. `CLAUDE.md` asks a failed read on a crew screen to draw its failure, with no Retry for a refusal.

## The fix

The card keeps a first read's failure only when its kind is `server`, the class `errorKindOf` gives an error the database answered with. It then draws the heading, the failure on `OfflineRetryPanel` with its reason, and *Keep working either way.* A refusal gets no Retry there.

- A first read lost to the signal, kind `network`, draws nothing, as before.
- A read that lands takes the words away, and shows the card when there is something to ask.
- A later read that fails, of either kind, still keeps the card that is up with its Nos.

## Checked

`JobModeArrivalCheck.render.test.tsx` has three new tests: a refused first read says so with its reason and no Retry, and a read that lands takes it away; a first read lost to the signal stays silent; a later refused read keeps the card. Every Job Mode test passes, 162 in 28 files. The guide *say whether a site is as we were told* has a section for it.
