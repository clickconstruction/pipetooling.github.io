# v2.7119 — ZZ test estimates no longer count in the Bridge's won rate (punch list #334, PR 3) (2026-11-13)

PR 3 of the Bridge train (card #334, `to-dos/bridge-pulse/`), on PR 2 in stack A. Reading the estimates behind the won rate, the owner saw test estimates among them. Eight were inside the rate. Those eight rows were deleted on 2026-11-12 (v2.7051), so the rate does not move on this merge. The rule keeps the next test out.

## What changed

- **`isZzEstimate({ title, customerName })`** (`src/lib/bridge/loadEstimateWins.ts`): a test estimate by the ZZ convention. Its customer's name is a ZZ name (`isZzTestName`), or its title is once the usual opening *Estimate for* is taken off. The title alone would miss one whose title was typed over; the customer alone would miss one sent to an email with no customer row.
- **`loadEstimatesSent` takes `zzTestJobIds`**, read as the bids' loader reads it: a set stands for the viewer's switch and leaves the ZZ test estimates out, null (or nothing) keeps them. The read asks for two more fields, `title` and `customers(name)`.
- **The page** (`Bridge.tsx`): the estimates' read is handed the viewer's ZZ switch alone (`readZzSwitchIds`, PR 2), not the ids of the jobs the Bridge leaves out. So a dev who shows ZZ tests keeps them in the rate whatever the left-out list names.
- **The Monday email** (`sheetReads.ts`): hands the loader the same ids it hands every other read, so the email's won rate follows the rule. The email always leaves ZZ tests out.

## Left, on purpose

- The count of asks (`loadDemandPace.ts`) and the Market and Sales windows' own lists (`loadMarketDesk.ts`, `loadSalesDesk.ts`) still read every estimate. Their header comments say so. Only the won rate was the owner's ask.
- The ids, numbers and names on each estimate are PR 4's.

## Deploy

`loadEstimateWins.ts`, `sheetReads.ts` and `zzTestJobs.ts` (a comment) are copied to the edge functions; `npm run gen:edge-kernels` ran. After the merge, deploy `bridge-weekly-sheet` and whatever else `npm run check:edge-drift` names. No migration.

## Tests

`loadEstimateWins.test.ts` (new, 5): the rule by the customer's name, by the title with its opening taken off, a real estimate left alone, and the loader over a stand-in database: the ZZ rows leave for a viewer who hides tests and stay for a dev who shows them or when no switch is handed in.

## Verify

Walked on a dev server as a dev on production data, in headless Chrome, at 375, 768 and 1400 wide, every write refused. The estimates' read answered 200 with its two new fields, every estimate carried its customer's name, the rule matched none of today's rows, and the pipe's estimates line drew the same won rate as before the change.
