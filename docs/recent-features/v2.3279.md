# v2.3279 — Discount row: a dollar amount above the work is clamped, so Job Total never reads work − typed (2026-09-11)

Client only — no migration. Found on the first owner-driven live pass of the discount tools (2026-09-11): type `9000` into a discount row on a $5,000 job and the row said "Can't exceed $5,000.00 … Kept at $5,000.00" while the footer read **$5,000.00 work − $5,000.00 discount · Job Total: $-4,000.00**.

## Why

`syncDiscountRows` (v2.3252) deliberately kept a typed dollar amount above the basis *as typed* in state so the row could show the cap message, and only capped on the autosave write. Every count × price reader in the form — `revenueDollarsFromFixtures`, the pipeline card's bid figure, the segments coverage — trusted the stored price and summed the overage. The DB row was right; the screen was wrong until the next re-hydrate.

## What shipped

- **Kernel** ([`discountLine.ts`](../../supabase/functions/_shared/discountLine.ts)): `syncDiscountRows` always writes the derived, capped price. The stored `line_unit_price` is the true amount everywhere, which was the point of storing the signed amount in the first place. `discountExceedsBasis` stays for rows that predate the clamp.
- **Row** ([`JobFormDiscountRow.tsx`](../../src/components/jobs/JobFormDiscountRow.tsx)): the smart field remembers what was typed (`typedDollars`) and shows the cap message from that — same wording, same place — and asks the form for the capped price directly, so the message survives the clamp. Swapping to percent clears it.
- **Tests**: the kernel test now asserts the clamp and that `work − discount` is exactly the Job Total after a $40,000 entry on job 892; the render test types `40000` into the field, expects the capped update and the message, then `500` clears it.

## Not changed

Bill Customer's *Take off* strip and *Make the Job Total* already went through `planBillDiscount` / `applyTargetJobTotal`, which cap (or refuse as unreachable) before anything is stored.
