# v2.8482 — The type check's heap is sized from the machine, and a heap death says it is no verdict (2026-11-24)

Infra, no screen. No migration, no edge function. The whole-program TypeScript check had grown to need all of the fixed 12,288 MB heap it was given on 2026-11-13 (v2.7134). This measures how much room was left, gives the check the room each machine has, and makes a check that dies of its heap say so in words. The lasting fix is punch list #434.

## What the numbers say

- **The check needs 12.0 to 12.3 GB today, on both machines.** With room and a collection forced at the end it holds 12,334 MB. The old cap was 12,288.
- **There was no headroom left.** Under 12,288 MB a cold `tsc -p` died on the runner and on the Mac. The deploy's cold `tsc -b` and the old-build-info run finished inside the last 230 to 300 MB, with V8 collecting back to back. Which of them lives is chance. The cold check runs on every deploy, and on any pull request that changes the lockfile, `tsconfig.json` or the eslint config, because that changes the cache key.
- **An old build-info file does not cost memory.** Six days old, it needs what a cold run needs (11,993 against 12,054 live at the same cap). The two deaths a session saw with an old file in a reused worktree were the same edge, not the file. So the wrapper does not delete old build-info files.
- **A warm cache is cheap.** One merge old, the check takes 23 seconds and 4.2 GB. That is what almost every pull request runs.
- **A runner has room for a bigger cap, but not much.** 13,312 and 14,336 MB both passed there with nothing swapped. The process holds about 265 MB over its cap when the heap is full, and the runner's other processes hold 1,000 to 1,250 MB, so a 15,700 MB runner has about 14,100 MB to give at the very most, with nothing to spare.
- **Room makes it faster.** The cold check took 13 minutes at the edge and 7 with room, because at the edge it spends its time collecting.
- **The program grows about 190 MB a day.** It died at about 10,050 MB on 2026-11-13 and needs about 12,200 now. Six days added 881 merges and about 222,000 lines under `src`, and each line of the program costs about 4.7 KB of heap.

## The change

- **The heap is sized from the machine** (`scripts/lib/typecheckHeap.mjs`, `heapCapMb`): 85% of its memory in 256 MB steps, never under 12,288 MB (the old cap) and never over 16,384 MB. A 15,700 MB runner gets 13,312, a 15,983 MB runner 13,568, a 16 GB Mac 13,824, and any machine from 20 GB up gets 16,384. The ceiling keeps two checks at once inside a 48 GB Mac, since the build's `tsc -b` takes no lock. `TYPECHECK_HEAP_MB=<n>` is the cap whatever the machine has.
- **One runner for both tsc runs** (`scripts/lib/runTsc.mjs`). `npm run typecheck` (`scripts/typecheck-queued.mjs`) and the build's `tsc -b` (new `scripts/tsc-build.mjs`, which `npm run build` and `npm run analyze` now call) take the same heap, so the two cannot drift apart. `vite build` keeps its 8 GB. CI checks what it checked before.
- **Each run says its heap first**: `typecheck: tsc has a 13312 MB heap on this machine's 15701 MB.` A CI log now shows which cap a run had.
- **A death is said in words.** A tsc that runs out of heap prints V8's trace and no `error TS` line, so through `| tail` or a grep for `error TS` it read as clean. The runner watches stderr for V8's line and ends with one line of its own: `typecheck: NO VERDICT. tsc ran out of its 12288 MB heap and stopped before it finished. No "error TS" line above does not mean the code is clean. Run it again, with TYPECHECK_HEAP_MB set higher if this machine has the memory.` A kill (how a machine out of memory stops a process) and any other signal get their own line. The line holds the words `error TS`, so a grep for them over the whole output finds it.
- **The exit code** is tsc's own, or 128 + n when a signal ended it: 134 for a heap death, 137 for a kill. It was 1 for every signal.

## Is this the best we can do?

No. It gives a runner about 1.0 to 1.3 GB over today's need, which is five to seven days at the pace above, and a 48 GB Mac about 4 GB, which is three weeks. A runner has little more to give. The lasting fix is to check the program in parts that each fit, and it was measured here on a runner, cold, a collection forced at the end:

| Program | Files | In use at the end | Peak | Wall |
|---|---|---|---|---|
| the whole of `src`, as today | 21,677 | 12,334 | 12,606 | 7:17 |
| `src` without its tests | 15,539 | 8,072 | 9,061 | 5:02 |
| the tests under `src/lib` and what they import | 9,647 | 6,524 | 7,133 | 1:22 |
| the tests outside `src/lib` and what they import | 10,344 | 8,578 | 9,085 | 6:37 |
| the whole of `src` with `incremental` off, cap 12,288 | 21,677 | 12,305 | 12,470 | 12:21 |

Three programs by plain `include` lists, with no project references, leave the largest at 8.6 GB. Turning `incremental` off saves nothing. Punch list #434 holds these numbers and the plan, and it is not built here.
