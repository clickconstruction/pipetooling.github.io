# v2.8730 — HR files: a correction link is written through the HR door (2026-11-27)

Punch list #315, the audit's leak, the correction links' half. The client alone: no migration, no edge function, no deploy. The person's pick of 2026-11-27, asked *through the door, or the guard asks first?*: **A, the door**.

## Why

`person_file_amendments` has a guard that answers before its row policy, so an insert sent straight at the table by anyone signed in learns where an id stands. v2.8727 closes that for a caller with no sign-in. For a signed-in caller it can only be closed by revoking INSERT and UPDATE from the signed-in role, and the HR tab used both: **Add entry** inserted one row a link, and the ✕ on a link updated its withdrawal stamps. The tab had to stop writing the table first.

## What changed

- **`src/lib/people/personAmendmentsIo.ts`.** `addAmendments` and `withdrawAmendment` call `dev_hr_entry_write` with `p_dry_run: false`. That function is the dev-gated definer the dev seat's `plan_hr_entry` and `apply_hr_entry` use, live since `20261112050000`. It carries a link between two things already on the file as `amendments[]` and a withdrawal as `withdraw_amendments[]`. The read is unchanged: the tab still selects the table as the signed-in dev.
- **`src/lib/people/personAmendmentsDoor.ts`**, new and pure: the two payloads, the 200 character hold on a reason, and the one refusal that means a link is already off.
- **`PersonFilePanel.tsx`**: the two call sites. A withdrawal now names the file, which the door asks for.
- `docs/HR_FILES.md` says where the link is written.

## What reads the same and what differs

- The guard is the same guard, so every refusal of a bad pair reads in the same words: *that link already stands*, *both ends of a link belong to the one person's file*, and the rest.
- Several links from one entry land together or not at all, as the one insert did.
- **Who made a link** comes from the sign-in inside the door, not from the client. The row also carries the dev's name as `author_label`, which the tab's insert left empty. Nothing reads that column on the tab.
- **A link that someone else already took off.** The old update changed no row and said the link was off. The door raises *no live link*. The tab reads that one refusal as done, so the person sees what they saw before and the reload shows the truth. Every other refusal is shown with its reason.
- A person who is not a dev is refused by the door with *devs only*. Before, the row policy refused them.

## Order

Nothing is owed after the merge. The door has been on prod since 2026-11-12, so the new client works the moment it is served. The second step is its own migration: revoke INSERT and UPDATE on the links from the signed-in role. It is pushed only once this client is live, because a tab left open on the old client would be refused a link until it reloads.
