# v2.5486 — Messages: the code reads the new kinds of contact through the database's own types (2026-10-13)

Residential R0's type tidy, on the lead's regen #5657 (`database.ts` after `20261013180000`, `20261014005000` and
`20261014050000`). No migration, no edge function, nothing on screen.

- **`contacts/load.ts`**: `NewRecordColumns`, the four id columns R0 added to `contacts` (`prospect_id`,
  `supply_house_id`, `supply_house_contact_id`, `team_prospect_id`), is now `Partial<Pick<Tables<'contacts'>, …>>`, so
  a renamed or retyped column fails the type check. Before, it was a hand-written `Partial<Record<…, string | null>>`
  that matched nothing. They stay optional because no fetcher selects them yet: `CONTACT_COLS` in
  `messages/messagesIo.ts` and `CONTACT_COLUMNS` in `followUp/followUpIo.ts` still read the nine pre-R0 columns, and
  neither loads `prospects`, `supply_houses`, `supply_house_contacts` or `team_prospects` for names. That read is R0's
  PR 4, cut once the open PRs on those two files land.
- **`contactForCustomer`** (`messages/messagesIo.ts`) calls `supabase.rpc('contact_for_customer', { p_customer_id })`
  typed, without the file's `rpc` helper's `as never` and the `as unknown as string` after it. A wrong argument name
  now fails the type check. The rest of the file's `as never` casts on the spine's tables, typed since #5482, are a
  later sweep of their own.
- **Proof**: a planted `p_customer` argument and a planted `prospect_idx` column each fail the narrow type check, and
  both went through before. Tests unchanged: `contacts` 2 files, `messagesIo.test.ts` and `followUp` pass, 208 in all.
