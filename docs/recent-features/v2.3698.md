# v2.3698 — People spine, PR 1: the roster view — pay lists take one answer to "who is a person", and the salary jobs stop for archived accounts (2026-09-21)

PR 1 of the People spine train ([`to-dos/people-spine/README.md`](../../to-dos/people-spine/README.md)). Born from the same-day clean-up of the Training Helper — a Tier 5 test account (`users` row + an unlinked `people` row + a `people_pay_config` row with Salary ticked and no wage) that put 40.00 h / $0.00 into the Hours grid, Draft Payroll ("No hours 40.00 $0.00"), the Earlier-weeks scan (11 of its 16 rows), the team labor total and eight $0 pay reports across nine weeks. The owner: *"things are a little disjoint with the active accounts separate from the people person area and the pay, payroll, people, pay config, also separate"*, then, on the plan, *"let's build it all"*. Migration `20260922001000_roster_people_view.sql` (db push after merge; a `gen-types` regen PR follows, dropping the one `as never` cast).

## What was wrong

Every roster, picker, pay list and email fan-out answered "who is a person" for itself — `archived_at`, `is_digital_twin`, `is_sample`, `role = 'dev'`, in every combination (a census on 2026-09-21: ~175 client files read `users` / `people`; 19 go through `activeUsersQuery`; 13 edge functions carry `eq('is_sample', false)` by hand). The pay lists answered it wrong: they took every `people_pay_config` row minus the archived *account names* from `get_archived_user_names()`, so a non-person with a pay row was a person to them. And the salary machinery never looked at `archived_at` at all: `salary_sync_one_user_clock_sessions` kept materializing schedule sessions for a departed salaried person as long as a template row survived, and the 30-minute `auto_approve_salary_clock_sessions` cron approved them into `people_hours`.

## The change

- **[`20260922001000_roster_people_view.sql`](../migrations/20260922001000_roster_people_view.md)** — `public.roster_people`: one row per human (the `users` row, the `people` row, or the pair linked by `people.account_user_id`), with `account_kind` (person | external | sample | twin — derived from `is_digital_twin` / `is_sample`, so no write path changes), `is_archived` (either half), `is_dev`, and two rollups: **`is_pay_roster`** (a real person with neither half archived — devs included, they are paid people) and **`is_active_roster`** (`is_pay_roster` and not a dev — the crew-picker rule `activeRoster.ts` states in TypeScript). Names, roles, kinds, flags and employment dates only; contact columns stay behind the `users` / `people` policies. Owner rights, so every signed-in viewer sees the same roster (the Hours grid must not differ by viewer — J7-6); `WHERE auth.uid() IS NOT NULL`, anon revoked. Ids CASE-wrapped (the v2.2995 trick) so PostgREST does not relate every `users` / `people` FK through the view. Same migration: the three salary functions rewritten from their newest definitions — the per-user sync deletes the day's unapproved auto sessions and returns for an archived account, the daily loop joins `users` and skips archived, the cron's session query adds `u.archived_at IS NULL`.
- **[`rosterPeople.ts`](../../src/lib/people/rosterPeople.ts)** — `fetchRosterPeople`, `buildPayRosterIndex` (by `person_id` and by trimmed `pay_name`; a live row wins a name collision), `isPayRosterRow` (matched → the view's verdict; matched nowhere → shown, an orphan pay row is a data question, never hidden money; no index yet → shown, a slow load never blanks a grid), `payRosterNames`. Six tests, one of them the Training Helper.
- **[`hoursGridRoster.ts`](../../src/lib/people/hoursGridRoster.ts)** — `buildHoursGridRoster` applies both exclusions: the archived account names (`get_archived_user_names()`, the pre-v2.3698 rule — kept because it needs no view and the client can deploy before the push) and the `payRoster` verdict on top; `payConfigRowsForRoster` turns the pay-config map into the row list. Found on the live walk of this branch: with the view not yet in prod and the archived set dropped, every archived account came back onto the grid (71.40 h instead of 49.85) — so rule 1 stays. Tests: the J7-6 case, the sample / twin case, an archived roster row that only the view can see.
- **Readers switched** — People → Hours / Draft Payroll / Earlier weeks / cost matrix (`People.tsx`: `loadRosterPeople` in the hours-tab and review-tab load cycles, `payRoster` state), `useWeeklyTeamLaborTotal` (the Dashboard Internal Team card; a fetch failure means no verdict, never a $0 card), Quickfill `HoursSection` (`payRosterNamesInOrder` for the grid and the row mover), `PeopleReviewTab` (`payRoster` prop beside `archivedUserNames`). The fetch does not retry: a missing view is not a blip. Offsets, Contracts and the Teams member filter still take `get_archived_user_names()` — PR 6 swaps them and drops the RPC.

## Verified

- Migration applied twice on a throwaway Postgres 15 with stub tables; one of each account kind inserted (a linked person, a sample, a twin, an archived account, a dev, an external roster row, an archived roster row, the Training Helper pair) — 9 rows classified as designed; the per-user sync for an archived account with a template and one unapproved auto session left 0 sessions; the daily loop skipped it; the view returns 0 rows without a session.
- Live on the branch's worktree server against prod (the view not yet pushed): the Hours grid lists the same 18 people as production, no Training Helper, the week total matching the live app at the same moment; the first walk, before the archived-name rule was restored, had shown 26 names (every archived account back) — the regression the kept rule closes.
- `npm test` (kernel suites) and `npm run typecheck` / `lint` green.
