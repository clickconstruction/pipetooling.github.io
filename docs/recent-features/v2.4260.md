# v2.4260 — GC statement email: the payments we have received, and where each went (2026-09-30)

Punch list #71, PR 2 of 2 — the block the mock-up drew under the total. Follows [v2.4255](v2.4255.md) (the statement one property at a time). **Client + edge function `gc-statement-email-dispatch` (redeploy). No migration.**

## What the GC reads

Under **Total owed**, a block headed **Payments we have received**: *2 payments since Aug 31, 2026, newest first. If one you sent is missing, reply and we will find it.* Then one line per check — *Sep 22 · Check #4402 to 1780 FM 1343 · Job 372 · $17,600.00*. A check that paid a job off says so: *to 1875 Co Rd 777 · Job 868, now paid in full* — the case the statement's own rows cannot see, and the bookkeeper's first question. When none came: *No payments received since Aug 31, 2026. If you sent one, reply and we will find it.*

## Where it lives

- **The kernel moved to `_shared`**: [`supabase/functions/_shared/gcChecksApplied.ts`](../../supabase/functions/_shared/gcChecksApplied.ts) is "Where the checks went" (v2.4043) verbatim, so the dispatcher can fold a GC's payments the way Find a check and the printed sheet do; [`src/lib/jobs/gcChecksApplied.ts`](../../src/lib/jobs/gcChecksApplied.ts) re-exports it and keeps the 16 tests. The one client-only import it had (`effectiveJobLedgerNumber`) is the HCP-else-Click rule, written out.
- [`_shared/gcStatementByProperty.ts`](../../supabase/functions/_shared/gcStatementByProperty.ts): `StatementReceivedIn`, `statementReceivedFromChecks(checks, jobsById)` (the kernel's folded checks → the block's rows, where = street · Job N per job), `statementReceivedIntro`, `STATEMENT_RECEIVED_DAYS = 30`, and the block in HTML and text. `received` undefined prints no block; an empty list prints the block saying none came.
- Client: [`gcStatementEmail.ts`](../../src/lib/jobsDocuments/gcStatementEmail.ts) `gcStatementReceived(inputs, gcId, todayYmd)` over the rows `fetchGcChecksInputs` reads; the new hook [`useGcStatementReceived`](../../src/hooks/useGcStatementReceived.ts) reads them once per GC the moment a row is opened or Draft Message opens, and hands a snapshot to Preview and Copy and a promise to Send (a statement sent a moment after the dialog opened still carries the block; a failed read sends without it).
- Dispatcher: `receivedFor(admin, gcId, todayYmd)` in `index.ts` reads the same rows with the service role (jobs the GC pays on, their bills and payments, the payment moves; deposit dates are not needed for the block) and passes the rows through `render.ts` `GcStatementRenderExtras`. A GC's statement only — a development has no one payer to read.
- `gcStatementEmailParity.test.ts` hands both lanes one `received` list and pins the output; `gcStatementByProperty.test.ts` builds the list from the kernel over three jobs (one paid off in the window, one older, one the owner pays).

## Decided here

- **Thirty days**, counted back from the statement's day on the company calendar. "Since the last statement we sent you" would never show a check twice; it can replace the constant if the office prefers it.
- **The block prints even when empty.** A bookkeeper who mailed a check reads *No payments received since…* and replies; silence would read as "they got it".
- **Copy for email carries the block once the GC's checks are read** — they start loading as the row opens, so by the time Share → Copy is reached they are there. A copy pressed before that pastes the statement without the block.
