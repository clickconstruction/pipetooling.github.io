# v2.3628 — Prospects access: an estimator can no longer grant it to themselves (2026-09-19)

`users.estimator_prospects_access` was never one of the columns `users_guard_privileged_columns()` watches. "Users can update own profile" is row-scoped (`auth.uid() = id`) and has no column list, so an estimator could PATCH their own `users` row to `estimator_prospects_access = true`; `user_has_prospects_staff_access()` (20260906010000) then returned true for them and the Prospects tables opened. Whether anyone ever did was not checked here — a dev can read the current grants on Settings → Active accounts. Migration only; no client change, no edge function.

## Who may set it — checked before writing the rule

The flag has one writer: `updateUserProfile` in [`useActiveAccountsManagement.ts`](../../src/hooks/useActiveAccountsManagement.ts), behind the Edit row of `ActiveAccountsPanel`. That panel mounts in two places and opens from three doors, all dev-only in the client:

- Settings → People & accounts — `myRole === 'dev'` around `SettingsPeopleTab`.
- People → Manage accounts — `onOpenActiveAccounts` is passed only when `isDev`.
- Person Desk → Access & account → *Manage account…* — `canEditAccount(viewer)` = dev and not in training mode.

No edge function writes it. Masters, assistants and controllers can UPDATE other users' rows under RLS ("Masters assistants devs can update user notes") but have no screen for this flag, so the rule is **dev-only** — the same rule as its sibling `team_prospects_access`. If the office is ever given this switch, widen the guard in the same PR that adds the screen.

## The change

[`20260920050000_guard_estimator_prospects_access.sql`](../../supabase/migrations/20260920050000_guard_estimator_prospects_access.sql) ([migration doc](../migrations/20260920050000_guard_estimator_prospects_access.md)): the function is rewritten with one more check — `NEW.estimator_prospects_access IS DISTINCT FROM OLD.… AND v_role IS DISTINCT FROM 'dev'` → `P0001 Only a dev can change an estimator's Prospects access` — and the column joins the trigger's `BEFORE UPDATE OF` list.

The body was copied from the newest definition, `20260920033000_helper_trial.sql` (v2.3627), and diffed against it mechanically: the only difference is the five added lines. That matters because the 20260903191916 rewrite started from a stale body and silently dropped the `team_prospects_access` guard, which v2.3627 had to restore. This migration is numbered after v2.3627's and cannot apply without it (it names `trial_prospect_id`).

The check compares old and new, so the dev Edit form — which sends the flag on every estimator save, changed or not — is unaffected, and an estimator saving their own profile (name, phone) never trips it.
