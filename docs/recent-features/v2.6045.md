# v2.6045 — Materials on site: the photo sweep files a box's photo in Drive (2026-10-29)

Punch list #209, PR 4 of 4, stacked on v2.6043 (the office). The three-tap photo flow of the On site tab (v2.6041) sends a shrunk shot to the `box-photos` bucket with a row in `job_box_photos`; this PR is the half that moves it into Drive.

## What changed

- **`photo-save`** (`supabase/functions/photo-save/index.ts`) gains a second source after its Messages pass: up to twenty `job_box_photos` rows with a `storage_path`, no `filed_at` and no `fail_why`, oldest first. Each is copied into the job's photo folder (`photoFolderFor`, the same place a texted-in photo lands: Team only › Photos under the job's Drive folder, or a Pipeline job's own Customer Pictures folder) under the row's own `file_name`, with *(2)* when the folder already holds the name; the row keeps `drive_file_id`, `filed_at` and `status = filed`, and the bucket copy is deleted, so the app keeps no lasting copy. A job with no Drive folder, or a copy that fails, is reported in the response and tried again next run. The response gains `boxes: { saved, failed }`.
- **Migration `20261029020000_photo_save_cron_box_photos.sql`** (`docs/migrations/20261029020000_photo_save_cron_box_photos.md`): the cron also calls while a box photo waits, not only while a Messages tick is on.
- **Docs**: `docs/EDGE_FUNCTIONS.md` → photo-save, the release note and this fragment.

## Deploy

1. After v2.6039's migration is applied: `supabase functions deploy photo-save` (from the main checkout, `npm run check:edge-drift` before and after).
2. `supabase db push` for the cron migration.
3. Watch one run: a photo taken on the On site tab reads "in the job's folder" within five minutes and the file is in the job's Photos folder.

## Left

A `fail_why` the office can read and clear on the materials page (today a failure is only in the run's response and the photo is retried), and the Drive thumbnail on the office panel once the bucket copy is gone.
