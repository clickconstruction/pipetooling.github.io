# v2.8114 — Permits: one Austin builder is one name (2026-11-20)

The first thing on the list *Seen while building, not done* of punch list #405 ([the card](../../to-dos/permits-market-page/README.md)). The owner's call on 2026-11-20: fix the mark now.

## What was wrong

Austin's feed writes the city's mark for a contractor's main account into the name itself. It comes in many spellings: one to five asterisks, the word `MAIN` or `Main`, then none to five asterisks, glued to the name or after a space, and sometimes the word in brackets, `(MAIN)` or `(Main GC account)`. `permitRowFromAustin` kept the name as it came, so the mark went into `permits.contact` and into the key made from it.

- **A name with a comma keyed to `main`.** `contactParts` splits a contact line at its commas. On `Name, Inc.**MAIN**` the tail no longer read as a company suffix, so the tail was taken as the company and `builderKeyOf` keyed it `main`. Every such contractor shared that key: one row on Builders and on the call list for many companies.
- **A name without a comma kept the mark in its key.** The same company with the mark and without it were two builders, each with part of its permits.
- **The plumbing permits carried it too**, and the reads that tie a plumbing permit to a building permit compare the two keys.

No other city writes the mark.

## What changed

- `austinName` in `supabase/functions/_shared/permitCities.ts` takes the mark off a name as it is read, by the one pattern `AUSTIN_MAIN_MARK`, wherever in the name it sits, and reads a name that was nothing but the mark as no name. `permitRowFromAustin` reads each of its four name fields through it, so `contact` is clean and `builder_key` is the company's own. `raw` keeps the feed's text.
- The pattern asks for asterisks before the word or brackets around it. A name that only holds the word (*Main Street Builders*, *Home Maintenance*) is left alone.
- Migration [`20261120110000_permit_austin_main_mark`](../migrations/20261120110000_permit_austin_main_mark.md) is the one-off for the Austin rows already stored, building and plumbing: the same pattern cleans `contact` and the key goes back to null, which `permit-pull`'s key pass fills on its next run.

## Why the key is not written in SQL

The key is made in TypeScript: `builderKeyOf` splits the person from the company first, and the database has no twin of that split. A second copy in SQL would be a second rule to keep true. `permit-pull` already fills any row with a contact and no key through `permit_set_builder_keys`, 500 a round and 12 rounds a run, so the migration hands the marked rows back to it. A read of the whole city again through the pull was the other way. It was not taken because it rewrites every row's `pulled_at` and its point, and it depends on what the feed sends that day.

## Order of the deploy

1. `permit-pull` first, so no pull can write the mark back.
2. The migration.
3. One **Pull now** on Austin, which runs the key pass. Between 2 and 3 the marked rows have no key and are off Builders.

## Checked

- `src/lib/research/permitCities.test.ts`: every spelling seen in the feed, with made-up names, glued on and after a space; the mark in the middle of a name; names that only hold the word; a name that was only the mark; the comma case keying to the company; the plumbing permit keying with the building permit; and the migration holding the same pattern as the function.
- The migration was run twice on a local Postgres with made-up rows: the second run changes nothing, and another city's row with the same mark is left alone.
- Before the push, a read of `builders`, `builder_marks`, `builder_customer_answers` and `builder_call_answers` for any row on a marked Austin key.
