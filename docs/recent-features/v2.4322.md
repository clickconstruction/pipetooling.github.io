# v2.4322 — Submittals: the GC calls each part (2026-10-01)

PR 2 of the parts train (PR 1: v2.4319, the parts on a row). Grace, on the canvas's "is this the best we can do" row: once parts are bought separately, one call per fixture holds back a part needed early (a carrier at Rough In) while another part (the 1.28 gpf flush valve on SpaceX) is resubmitted. So the GC calls each part, with Approve all as one tap, and the row's call is the roll-up every older reader keeps reading. Mock-up: https://claude.ai/artifact/JtoZEiwKP7zbABzXEy7hH8 (*Best B*).

## What changed

- **The room's payload** ([`_shared/submittalRoomPayload.ts`](../../supabase/functions/_shared/submittalRoomPayload.ts)): `RoomPartSource`, `RoomPart`, `roomPartsFrom` (the parts the GC sees, model first, `carried` when an approval came forward), `roomRowFrom(item, parts)` / `roomRowsFrom(items, partsByItem)` put `parts` on a row that has them. `splitPartLabel` lives here now; `itemParts.ts` re-exports it so the office and the GC read a label the same way. **`rollUpPartDecisions`** is the one rule for a row's call from its parts: a part sent back sends the row back at once (Reject over Revise), every part approved approves it, otherwise open; the note names the parts that carry one; the name and time are the latest call's.
- **`get-submittal-room`** reads the parts (`on_submittal = true`); **`submit-submittal-review`** `decide` takes `partId` (`parseDecideBody`), plans where each call lands (`planDecideWrites` in `_shared/submittalReviewActions.ts`: the part named; every part the GC sees for a call on the row; the row itself when it has no parts), writes the parts, then the rows' roll-up. A missing table reads as no parts in both.
- **The GC's card** (`RoomRowCard`): a row with parts lists each with its own Approve / Revise / Reject, a part approved on the last revision says so and asks nothing, *N parts · 1 approved · 2 to go*, and **Approve all N** for the parts still open. The page keys a pending call by row and part (`pendingKey`), names the part in the note box, posts `partId`, and folds the calls into the page the way the office will read them (`foldPending`). *See what the GC sees* draws the same.
- **The office**: each part shows its call on the row (`SubmittalPartsCell`), *Their call* adds *2 approved · 1 revise · 1 to go* (`partCallsLine`) and shows as soon as any part has a call. A call entered in Edit lands on the parts ticked (all the GC sees to start; `EnteredChoice.partIds`); **They approved all of it…** approves a row's parts still open; the robot's redline marks land on a row's parts; *clear it* clears the parts' entered calls. All through `enterCallOnParts` / `clearEnteredCallsOnParts` / `writeRowCallFromParts` in `itemPartsIo.ts`.
- **Resubmit**: *Rev N+1 from the rows sent back* carries a row's approved parts with their approval, marked `carried` (`carryPartInsert(…, keepApproval)`); only the parts sent back start blank. A plain New revision still starts every call blank.
