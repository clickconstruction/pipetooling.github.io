# v2.3017 — Test-gap audit, pass 28: the My Time cluster persist routing gets its first tests (2026-09-07)

Follow-up to v2.3015. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`persistMyTimeClusterForSegmentAssign.ts` (188 lines) runs the same multi-segment persistence as Dashboard My Time Save for one cluster and hands back a `clock_sessions.id` per editor segment, so the day editor and the schedule-proportions apply can assign each segment afterwards. It chooses between four writes: the single-session split RPC, the cluster split RPC, per-row in-place updates, and the replace-mixed RPC. The predicates it branches on (`myTimeDayTimeline`, `myTimeDaySavePlan`) have seven suites between them; the routing itself had none.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- Fewer than two segments is refused before any write.
- One row: the split RPC, with job and bid stripped from the payloads (those RPCs take times and notes only), and exactly one id per segment or the save fails.
- A homogeneous cluster (same job or bid, same origin and salary segment) is re-split as one with the cluster RPC; nothing is written row by row.
- A mixed cluster with one segment per row, in order, updates each row in place: notes only when the segment's times still match the row within a second, times too when a boundary moved. A mixed cluster whose segments each sit inside one row splits the rows that hold several segments and updates the rest.
- Segments that straddle rows replace the cluster as a whole, with each segment carrying its own job allocation; rows that differ in origin cannot be merged and fail with the user-facing message before any RPC runs.
- Every RPC result is checked for one id per segment.

## What shipped

- **`persistMyTimeClusterForSegmentAssign.test.ts`** (7) — the three RPCs as spies returning one id per segment, a recording Supabase stand-in for the in-place updates. Covers each of the four routes, the notes-only versus times update, the id-count guards on all three RPCs, and the origin-mismatch refusal.
