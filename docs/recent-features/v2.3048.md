# v2.3048 — Test-gap audit, pass 47: opening the Mercury allocations modal from a job gets its first tests (2026-09-07)

Pass 47 of the test-gap audit, renumbered from v2.3037 after a version race. Tests only; no kernel, client, migration or edge-function change.

## Why this one

`mercuryAllocModalData.ts` loads everything the Mercury transaction allocations modal needs when it is opened from a job: the full transaction row, its current job splits and attribution, the labels of the split jobs, the legacy person's name when only a person is attributed, and the account and card nicknames. One caller (the jobs Mercury allocations hook), no test.

## What the tests found

Nothing wrong. Contracts now pinned that were only implied:

- The full row, the splits, the attribution and the nickname maps are read together; the labels for the split jobs come after, in one `IN` read over every job seen in the split rows.
- Only this transaction's splits become initial allocations; a blank note is left off; the first attribution for this transaction sets the initial person and user.
- The legacy person lookup runs only when a person is attributed without a user, and a missing person reads as no name.
- Job labels read "HCP · name", falling back to the job id when both are blank; card nicknames are keyed by lower-cased card id.
- A transaction that is missing or invisible throws a named error; a failed nickname read fails soft to empty maps; a failed label read throws.

## What shipped

- **`mercuryAllocModalData.test.ts`** (3) — a recording Supabase stand-in routed by table with the two relation fetchers as spies. Covers the full happy path with its reads and mapping, the legacy-person path with and without a row, and the three failure shapes.
