# v2.5108 — Workflow: a refused change shows above the page instead of replacing it (2026-10-09)

Client only; no migration, no edge function. **A behaviour change on purpose.** An action's error used to replace the Workflow page, and now it shows in a banner above the page. Punch list **#21** (`to-dos/decomposition-residuals.md`), the Workflow page's leftovers: the second of the two behaviours the decomposition move pinned but did not change ([`docs/WORKFLOW_PAGE_ARCHITECTURE.md`](../WORKFLOW_PAGE_ARCHITECTURE.md), quirk 21). It follows v2.5103, whose refused projection delete reached the same `setError`.

## Why

The page returned `if (error) return <p>{error}</p>` before drawing anything. Every `setError` therefore left only the message until a reload. That covered a refused credit invoice, a failed line-item save, a sub work order's `onError`, a superintendent add, a refused Approve and, since v2.5103, a refused projection delete. The v2.4077 move kept the early return, so the fix could be its own PR.

## The split

`error` held two kinds of failure, and a banner is right for only one of them.

- **A load that leaves nothing to draw** goes to the new `loadError` in `useWorkflowStepsEngine`. That covers the first project read, the workflow read or create (`ensureWorkflow`), the first steps read and a subcontractor with no step here. These still replace the page, exactly as before. A banner would draw the page shell for a denied subcontractor: the title, Edit Project and an empty list. It would also offer *create from template* on a workflow whose steps failed to load.
- **Everything else stays in `error`**, and the page draws it in the banner. That covers the writes, the staggered line-item and projection reads, and the windows' and panels' `onError`.
- **A re-read once the steps are drawn** also goes to `error`. Every write ends in `refreshSteps()`, which runs `loadSteps`, and Edit Project's save re-reads the project. A failed re-read after a write that landed must not replace the page. A ref, `stepsDrawn`, is set by the first steps read that succeeds and cleared when the project changes. After that, a failed project or steps read keeps the last steps and shows in the banner. The PUNCHLIST review caught this. A subcontractor whose re-read finds no step of theirs still gets the page replaced, as before.

## What changed

- **`useWorkflowStepsEngine`**: a `loadError` state and the `stepsDrawn` ref. The seven load-path `setError` calls became `setLoadError` with the same words. The project and steps reads choose `error` once `stepsDrawn` is set. The line-item read and the lifecycle runner keep `setError`.
- **`src/components/workflow/WorkflowErrorBanner.tsx`**: `role="alert"`, sticky at `top: var(--app-top-chrome)` so a card deep in the list still shows it, theme tokens (`--bg-red-tint`, `--border-red`, `--text-red-700`), and a Dismiss ×. It draws the message it is handed and never composes one. The words come from the write that failed: `projectionWriteError`, the line-item lib's messages, `Failed to update step: …` and the rest.
- **`src/pages/Workflow.tsx`**: `if (loadError) return …` where `if (error) return …` was, and the banner as the page's first child. Dismiss is `setError(null)`. Most writes already clear the error before they run, so the next action clears the banner too.

## Tests

- `components/workflow/WorkflowErrorBanner.render.test.tsx` (2): nothing with no message; the message in an alert, and Dismiss calls back.
- `hooks/useWorkflowStepsEngine.render.test.tsx` (12, 2 new): a failed first steps read and a denied subcontractor land in `loadError` with `error` empty. A lifecycle update that lands and then a failed `refreshSteps()` keep the three steps, with the read's message in `error` and `loadError` empty. A failed lifecycle update stays in `error` with `loadError` null. A line-item read failure stays in `error`.
- `pages/Workflow.render.test.tsx` (13, 2 new): a refused Approve shows *Failed to update step: rls* in the banner while the title and all four cards stay, and Dismiss removes it. An Approve that lands and then fails its re-read shows *Failed to load steps: timeout* in the banner, with the title and the cards still there. The denied subcontractor's case now also checks there is no title and no banner. All three are red against the old page.
