# v2.4323 — Notifications: tapping one opens its page when the app is already open (2026-10-01)

Client only: no migration, no edge function. Found 2026-10-01 reading [`src/sw.ts`](../../src/sw.ts), and reproduced against the real handler before the change.

## Cause

The service worker's `notificationclick` handler, unchanged since the 2026-02-16 PWA upgrade, matched open windows with `client.url.startsWith(new URL(url).origin)`. Every server push sends a path, not a full link: `notify-bid-mark` (`/bids?tab=counts&bidId=…`), `notify-dispatch-request` (`/job-mode/inbox`, `/dashboard`), `notify-team-lead-clock` and `notify-estimator-request` (`/dashboard`), `send-scheduled-reminders` (`/checklist`), `send-checklist-notification` (the caller's path, `/checklist` by default), `notify-help-feedback` (`/help?g=…`), `send-report-notification` (`/jobs?tab=reports`), `paid-job-email`'s ready-to-bill push (`/jobs`) and `mercury-webhook`'s returned-check push (`/jobs?tab=stages&edit=…`). `new URL(path)` with no base throws `TypeError: Invalid URL`. So whenever an app window existed (a desktop tab, or the PWA in the background on a phone) the callback threw inside `event.waitUntil` before `focus()` or `navigate()` ran: the notification closed and nothing else happened. With no window open the loop was skipped and `openWindow(path)` resolved the path itself, which is why it went unnoticed. The workflow pushes (`stepLifecycleNotifications`, `workOrderNotifications`) send a full link built on `window.location.origin` (`/workflows/…`, `/dashboard`), and worked. Settings → Your account → **Test notification** always failed: it sends `/settings` from an open window.

## What changed

- **The kernel** [`src/lib/notificationClick.ts`](../../src/lib/notificationClick.ts): `notificationClickHref(url, origin)` resolves the push's url against the worker's origin; a missing, unparseable or non-http(s) url opens the app's home. `notificationClickWindow(windows, href)` picks the window to reuse: one already on that link, else the first window of the same origin (`clients.matchAll` lists the most recently focused first); none, or a link on another origin, opens a new window. Neither throws. Seven tests.
- **The handler** in [`src/sw.ts`](../../src/sw.ts) resolves the link once, before anything parses it, then focuses the chosen window and navigates it to the absolute link. Both calls start together as before and are now awaited inside `waitUntil` (`Promise.allSettled`, so one failing never stops the other). No window: `openWindow(href)`, as before. One change beyond the fix: a window already on the exact link now wins over a more recently focused one, where the old loop took the first window of the origin.
- **The wiring test** [`src/sw.test.ts`](../../src/sw.test.ts) loads the real `src/sw.ts` with workbox mocked and a fake worker global, then taps: a path with a window open (the bug), a full workflow link, and no window. Against the old handler the first case fails with `TypeError: Invalid URL`. It is the first test of the service worker; the URL rules stay in the kernel's test.

## Rollout

CI deploys it with the client. A device runs the new handler once the new service worker takes over: **Reload** on the "A new version is ready" pill, or every app window closed and opened again. Until then its taps run the old handler.

## Verify

`npx vitest run src/sw.test.ts src/lib/notificationClick.test.ts`. On 2026-10-01 a production build's `dist/sw.js` (real workbox) was loaded under the same fake worker global and tapped: `/settings` and `/bids?…` with a window open focus that window and navigate it, the workflow link likewise, `/checklist` with none opens a window on the full link, and a missing url goes home. Live, after the deploy and a Reload: Settings → Your account → **Test notification** with the app open, tap the notification, and the app comes forward on Settings.
