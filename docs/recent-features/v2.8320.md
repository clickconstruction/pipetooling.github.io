# v2.8320 — In kind: the weekly GC statements email says how much an arrangement pays (punch list #301, the owner's call) (2026-11-22)

The owner's third answer of 2026-11-22: the staff screens leave a bill an in kind deal pays out of late counts, with one line saying how much is scheduled in kind. v2.8309 did that for GC Review, and it made the office's statement week right by its amounts, since the week is built on the same payload. The week still said nothing about what it left out. A total that shrinks with no word reads as money lost. This adds the word.

## What changed

- **The count** (migration `20261123024500_statement_week_in_kind_line.sql`). `get_statement_week_for_office` answers one more key, `in_kind` (`count`, `dollars`): the bills GCs pay that a deal covers, summed from the GC groups of `get_gc_statement_email_payload`. A GC under the $10,000 line is counted too, so the line explains a GC that left the list. A bill no GC pays is never counted. `get_my_statement_week` calls the function and passes the key through.
- **The line** (`supabase/functions/statement-round-email-dispatch/renderOfficeWeek.ts`). `officeWeekInKindLine` words it with the shared `inKindApartWords`: *$1,200 on 2 bills is scheduled in kind, not money owed.* The email prints it once under its summary line, in HTML and in text.
- **The bed.** `supabase/tests/in_kind/40_gc_statement.sql` reads the week's count with two deals open, and again after one ends.

## Decisions taken with the build

- **Counted in SQL, by the payload's own netting.** The week's amounts are netted that way already, so the line and the amounts agree with each other.
- **No line at zero.** An email with no deal reads exactly as before.
- **The renderer's one import.** The file was dependency-free so the client's tests could run it. It still is in that sense: the import is the pure words file every other reader's line comes from.

## Release order

After v2.8309 is on main and its migration is pushed:

1. Merge.
2. `supabase db push`.
3. Deploy `statement-round-email-dispatch`, then `npm run check:edge-drift`.

A function deployed before the push finds no key and prints no line. The function as it runs today ignores the key.

## Verified

Kernel tests in `src/lib/statementWeekEmail.test.ts` (the line once under the summary in both bodies, the rest of the email unchanged, no line at zero or without the key, numbers that came as text). The SQL runs in the in kind bed in CI. It was not run on this machine.
