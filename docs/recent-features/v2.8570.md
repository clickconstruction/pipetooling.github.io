# v2.8570 — The dev seat keeps a job's old number findable, and a sheet reads its job's number (2026-11-25)

Punch list #293. dev-mcp 0.135.0. One edge function, no migration, no client change.

## What was wrong

A set of real jobs was renumbered through the dev seat on 2026-11-25, after a test job's all-digit number had pushed the office's next number far out of its run. Two things were left behind. Both were read on prod through the seat the same day, read only.

- **The old numbers found no job.** `jobs_ledger.prior_numbers` is the list the job search matches and the screens read as *also 550*. Only the combine wrote it. `plan_job_update` changed the number and left the list empty, so a search for a number printed on a bill already sent answered no job.
- **One sub labor sheet still read its job's old number.** `people_labor_jobs.job_number` is display text and the sheet's job is its `job_ledger_id`, so the sheet stayed on its job. The office reads the sheet under that number, though, and `plan_sub_labor` answered *Nothing to change* when asked to put it right.

## What changed

- **`plan_job_update` keeps the outgoing number.** An `hcp_number` or `click_number` that `set` replaces goes on the job's prior numbers in the same PATCH, as `HCP 550` or `C# 543`, the combine's own shape and order (`priorNumbersPlan`, held to `priorNumbersAfter` by test). `keep_old_number: false` leaves it out, for a mistyped number. An entry the job wears again after the change comes off the list.
- **`plan_job_update` takes `prior_numbers: { add?, remove? }`.** It is for a job whose number already changed. An entry already there is dropped. A take-off that is not on the list is refused, and so is an add of the job's own number today. For each number added the plan reads the other jobs wearing it and warns, since a search will find both. The take-off is the way back.
- **The plan says it.** `prior_numbers` shows the list before and after, what is kept, added, taken off or not kept, and what follows. The plan's hash takes the list in, so a list changed since the plan refuses the apply.
- **The read back compares a list as a list** (`landedSame`).
- **`plan_sub_labor` brings a stale sheet number up to date.** A `change` whose `job_id` is the sheet's own job plans one column, `job_number`, when the sheet's text is not its job's number (`staleSheetNumber`). The job, the lines, the payments, the stage and the people are left as they are. With no `reason` it writes no note.
- **It reads where the number leads first.** The table's trigger `people_labor_jobs_link_job_ledger` follows a sheet's number to its job whenever the number changes alone. The plan reads `resolve_job_ledger_id_by_number` for the new number and is refused unless it answers the sheet's own job. The apply reads the link back and says so if it moved.

No Activity line is written for the list: no trigger on `jobs_ledger` watches `prior_numbers`.

## Not changed

The app's Edit Job form has the same two gaps. A number changed there is not kept as a prior number and does not reach the job's sheets. That is the form's, not the seat's.
