# v2.3731 — Stated-need editor: reset only when the row changes (2026-09-22)

Follow-up to [v2.3718](./v2.3718.md). Found by the merge-queue flake that PR #3575 papered over in the test: the component itself had the race.

## The race

`StatedNeedEditor` derives `open`/`text` from its props in `useState`, and *also* re-derived them in a `useEffect([entryId, mode, current])` so that a new code on the same card resets the box. That effect ran on mount too, writing the same values back. Harmless in isolation — but after a data-load commit (the ledger resolving, outside any event) React flushes pending passive effects at the start of the *next* render. A click on *add what it was for…* in that window enqueues `setOpen(true)`, then the mount effect's `setOpen(false)` lands behind it and wins: the box never opens. CI hit it about one run in six; a human at the counter would hit it rarely, and see nothing happen.

## The change

- **[`StatedNeedEditor.tsx`](../../src/components/materials/StatedNeedEditor.tsx)** — the reset effect remembers which `entryId | mode | current` the state was last derived from (a ref, seeded at mount) and returns early when that key has not changed. The mount run is now a no-op; a real row change (Done → mint again, or the parent rewriting `current` after a save) still resets. StrictMode's double-invoke is covered: the ref survives the simulated remount and the key still matches.
- **[`StatedNeedEditor.render.test.tsx`](../../src/components/materials/StatedNeedEditor.render.test.tsx)** — new: link mode opens on click and stays open across a same-props re-render; a new `entryId` resets; ask mode starts open and closes after *Write it down*.

The test hardening from #3575 stays: it is still right for a test to drain effects before clicking.
