# v2.3496 — Accounts Receivable: record a deposit's leftover as a Tip on the job (2026-09-16)

Taunya: *"I need to be able to assign access payments (tips) to the office J000."* ("access" is dictation for *excess*.) The live case: Elaine Giesber's `checkDeposit` of **$1,855.70** posted 2026-09-11 paid three bills on job 960 totalling $1,805.70 and left **$50.00** that nothing in the app would take. Both allocation choices want a bill, and there is no bill for a tip, so the deposit sat in *To match* nagging on the Dashboard banner, the pinned quick row, Quickfill and the `ar-deposits` Needs You card.

**J000 was rejected, twice over by the database and once on the merits.** `apply_mercury_bank_payment_allocations` refuses a `job_id` allocation unless the job is `status = 'billed'` with `revenue - payments_made` headroom; the Office job is `paid` with **$0.00** revenue, so it fails both guards. Making it work would mean holding J000 in Billed forever on invented revenue. J000 is also the configured Office job (`app_settings.overhead_office_job_ledger_id_v1`) carrying **785 clock sessions and 3,195.3 hours** since 2026-03-17, deliberately excluded from Crew P&L and the paid-profit chart, and it sits below the Job Summary number floor (`DEFAULT_MIN_HCP_EXCLUSIVE = 500`) so money parked there would be invisible on that page. And it would have booked nothing: no revenue reader in the app uses `payments_made`, so a tip recorded only as a payment is collected cash that is income nowhere.

**What ships instead** follows the convention the app already has. The HouseCall Pro tips sweep (`src/lib/customers/hcpTipsSweep.ts`, `TIP_LINE_NAME = 'Tip (HCP)'`) records a tip as a **line item on the bill of the job that earned it** plus a matching payment — nine of them are on prod, $10.00 to $163.80, Sep 2025 to Apr 2026. The gap was that only the importer could do it. Now a person can.

## The offer strip

- New kernel [`src/lib/jobs/arTipOffer.ts`](../../src/lib/jobs/arTipOffer.ts) (+15 tests) holds the whole rule: `buildArTipOffer` returns an offer only when the deposit still carries money (`> AR_TIP_OFFER_EPS`, the same 0.0005 the list RPC uses), is **not** flagged returned, and **has already had at least one bill applied**. That last condition is the guard that matters — a deposit nobody has touched is unmatched money, not a tip, and offering there would invite burying real unmatched money on a job.
- The amount is always the whole remainder. A tip is by definition the difference, so there is nothing to type.
- The job list is **closed**: `jobChoicesFromAllocations` returns the distinct jobs this deposit already paid. When they are all one job, as in Elaine's case, there is nothing to pick either and the strip is a single button — *Add a $50.00 Tip line*. When a deposit spans two jobs, a small select of those jobs appears. No job search, because a tip belongs to a job the deposit paid.
- New component [`src/components/jobs/ar/ArTipOffer.tsx`](../../src/components/jobs/ar/ArTipOffer.tsx) draws it above **Allocations** in `BankPaymentsModal`. It carries its own inline confirm rather than reaching for `useConfirmDialog` — a second press inside the strip, no dialog over a dialog, and no new provider dependency in the modal's render smoke. The confirm says plainly that removing the tip later takes two steps in Edit Job.
- [`src/lib/jobs/arApplySentence.ts`](../../src/lib/jobs/arApplySentence.ts) gains one optional `tipOffered` flag: while the strip is on screen the waiting footer reads *"Remaining $50.00 — pick a bill, link a recorded payment, or add it as a tip."*

## The write

New RPC **`record_job_tip_from_deposit(p_mercury_transaction_id, p_job_id, p_amount, p_payment_type, p_note)`** (migration [`20260916060000_record_job_tip_from_deposit.sql`](../../supabase/migrations/20260916060000_record_job_tip_from_deposit.sql)), SECURITY DEFINER, doing three writes in one transaction so a half-failure cannot leave a line with no payment or the reverse:

1. a `jobs_ledger_fixtures` row named **`Tip`**, `count` 1, positive `line_unit_price`, `invoice_id` NULL;
2. **revenue recomputed** from the job's own lines — named rows × price plus un-voided hazmat fees, the same arithmetic `apply_job_discount` uses — never `revenue + amount`;
3. a **job-level** `jobs_ledger_payments` row (`invoice_id` NULL) carrying `mercury_transaction_id` and `reference_number = mercury_id`, `paid_on` forced to the deposit's posted Chicago day.

The body is `apply_job_discount` with the opposite sign; the gates are `apply_mercury_bank_payment_allocations`'s, so **nobody gains a capability they lack in Accounts Receivable today**: roles `dev · master_technician · assistant · primary` (controller is excluded there too), the same six-way job-access check, the deposit row taken `FOR UPDATE` so two people cannot both pass the cap, and the amount capped at `abs(deposit) − Σ payments on it` with the existing 0.0001 tolerance.

**Three deliberate omissions**, each of which would have made the change bigger without making it better:

- **No new `line_kind`.** The column is NOT NULL, defaults to `work`, its CHECK admits only `work`/`discount`, and **36 files branch on it** — a third kind risks tips being dropped from bills, Stripe items or revenue by any reader testing for `work`. The tip is a plain `work` row, exactly as the HCP sweep writes it.
- **No custom activity event.** The existing triggers already record both halves: `jobs_ledger_fixtures_to_activity_ins` writes *"Specific work added: Tip"* (it skips only `line_kind = 'discount'`) and `jobs_ledger_payments_to_activity_ins` writes the payment. `src/lib/jobActivityEvent.ts` is untouched — worth noting because its `eventRenderMeta` looks types up with no fallback, so a new type there would have meant editing a union, a render map and a test.
- **`payments_made` and `status` are left alone.** The B3 trigger owns the first. The second needs no attention: a tip raises revenue and payments by the same amount, so a job's coverage cannot change.

**Expected side effect, stated so nobody is surprised:** inserting the payment fires `enqueue_payment_made_email_ai`, which queues a `paid_job_email_queue` row. Its recipients (`app_settings.paid_job_email_recipients_v1`) are three staff user ids, **not the customer** — a tip sends an internal notice and nothing reaches the payer.

## Deploy

Client and migration shipped in the same PR; `supabase db push` follows the merge, then `npm run gen-types:linked`. The function's type was hand-added to `src/types/database.ts` for the interim (the v2.3405 convention) and is replaced by the regen. During the window between merge and push the strip is on screen and the function is not, so the handler recognises a missing RPC via `isMissingRpcError` and says *"This is not live in the database yet — the change still has to be pushed."*
