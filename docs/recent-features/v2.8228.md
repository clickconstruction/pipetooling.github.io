# v2.8228 — Legal portal: a run claims the firm's emails before it sends (punch list #85, a review residual) (2026-11-21)

Punch list #85 (`to-dos/legal-portal-firm-ready/README.md`), the second of the two residuals the October reviews left for a session: *two overlapping dispatcher runs can send the same email twice (claim rows with `FOR UPDATE SKIP LOCKED`)*. The first, the cap on confirmation emails, is v2.8225. One migration (`20261121235300`), one function to redeploy (`legal-notify-dispatch`). No email's wording, recipient rule or schedule changed.

## The flaw

`legal-notify-dispatch` read a firm's open queue rows, sent each person their email, and only then wrote the ledger (`sent_to`) and the stamp. A second run that began before the first had written read the same rows and sent them again. The digest had the same gap: both runs read `last_digest_at` before either stamped it. The cron fires every five minutes and a run is allowed longer than that; a hand call can land on a tick. No other dispatcher in the repo holds a claim to copy, so this is the card's own suggestion.

## What changed

- **Migration [`20261121235300_legal_notify_claim`](../migrations/20261121235300_legal_notify_claim.md)**: `legal_notification_queue.claimed_until`, `legal_firm_recipients.digest_claimed_until`, and two service-role functions. `legal_notify_claim_events` stamps a lease on the firm's oldest open, free events (`FOR UPDATE SKIP LOCKED`, so a second run waits on nothing and takes other rows) and answers them as they stand now. `legal_notify_claim_digest` stamps one person's digest when it is free and their `last_digest_at` is still the value the run read.
- **The rules** ([`_shared/legalNotifyClaim.ts`](../../supabase/functions/_shared/legalNotifyClaim.ts), pure): the lease (ten minutes, longer than a run can live), when a row is free, how a claim call ended (`claimed`, `missing` before the push, `failed`), and every write that marks a row, each of which clears the claim with it.
- **The dispatcher** claims, sends only what it holds, then marks:
  - An event's ledger write clears `claimed_until`. A person whose send failed is therefore tried by the next tick with the try counted, and the twelve tries of v2.4662 keep their five-minute pace.
  - A digest that went is stamped and let go in one write. One that did not go (the send failed, or its lines could not be read) is only let go.
  - A run that throws part way lets go of what it still holds in a `finally`. If that write fails too, the lease ends by itself.
  - Claimed events are put back in queue order, since an update answers in no promised order.
  - The answer gains `elsewhere`: digests another run held or had already sent.
- **Either deploy order.** Before the push the claim functions answer `PGRST202`; the run then reads and sends exactly as before and writes neither new column. Any other failure to claim sends nothing for those rows that tick and names it in `errors`: no email goes out unclaimed once the claim exists.

## What it does not do

- A run that dies after an email left and before its ledger write still sends that email again, once the lease is past. That gap is as old as the ledger and needs the mail service's own idempotency key to close.
- The other half of the card's line stays open: fifty events stuck retrying can hold back newer ones for up to an hour.

## Verified

- **The SQL**, on a local Postgres 15 with two real sessions (the migration's page lists the eighteen checks): an overlapping run is answered other rows at once, a released row is taken by the next run with its ledger, a past lease is free, the digest's stale-read refusal, and the grants.
- **The function**, run under vitest over an in-memory database (`legalNotifyDispatch.run.test.ts`, 25 tests, 16 new): two runs started together send each person an event once and one digest, and the same two runs with the claim missing send twice, which is the control. A failed send is retried on the next tick and never waits the lease out. A row another run holds is left alone until its lease is past. A run that throws releases every row. Before the push no write names a new column. A claim that cannot be asked sends nothing and says so.
- **The kernel and the pins** (`legalNotifyClaim.test.ts`, 15 tests): the rules above, the migration's text, and the function's source claiming before its first send.
- Not run locally: the whole suite and the type check (CI on the PR). Nothing local type-checks an edge function.
