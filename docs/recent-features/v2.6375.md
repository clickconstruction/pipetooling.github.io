# v2.6375 — A photo keeps the time the camera fired, not the time it reached the app (2026-11-02)

Punch list #247, PR 3 of 3 (the owner's call 4 on 2026-11-02: *Start PR 3 now*). No migration, no function.

- **The read.** `src/lib/photos/photoTakenAt.ts` (pure, tested over hand-built JPEG heads in both byte orders, with a JFIF segment first, torn at every seventh byte): the JPEG's APP1 `Exif\0\0` block → TIFF header → IFD0's pointer to the Exif IFD → `DateTimeOriginal` (0x9003, else `DateTimeDigitized` 0x9004) and `OffsetTimeOriginal` (0x9011). The camera's zone when it wrote one; a wall time with no zone means the company's calendar (`appTzWallTimeMs`, DST-aware, as an email's *4:02 PM* does). Sane means not more than five minutes ahead of the upload and not more than a year behind it; a dead clock's *2000:01:01* or a torn file keeps the upload's time. `readTakenAt(file)` reads the first 256 KB of the file **before the shrink**, since re-encoding on the canvas drops the Exif block (`shrink.ts`), and never throws.
- **Where it is written**: `useReportPhotos.shrinkAndSend` (the report's camera and the desk's file pick, the tile's `takenAt` updated once read), `StageChecklistSheet.onFile` (the checklist's photo, which also names the file by the day) and `PhotoPress.onFile` (the Tally box's shot). Each writes the time into the row's own `taken_at` / `photo_taken_at`, so the `uploaded_photos` view, Documents → Photos, the Development page's Photos look and History lines (v2.6371, v2.6373) and the photo-save sweep's Drive name (`photoDriveName` reads `taken_at`) all follow with no change of their own. A text's picture keeps its message's time, as the card planned.
- **Why no migration.** The card drew one new column per table with the view reading it first. Each of the three tables already keeps the upload moment in `created_at`, so the two stay apart with `taken_at` as the photo's own time; and the `uploaded_photos` view is being replaced the same day by punch list #244's `20261102171500_job_photo_notes.sql` (a fifth branch), so a second `CREATE OR REPLACE` racing it would have dropped whichever landed first. #244's `job_photo_notes` capture can take the same `readTakenAt` once its train lands.
