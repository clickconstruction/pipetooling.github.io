# v2.7248 — A test of the lien § Rules window no longer fails by chance (2026-11-14)

Test only. One case in `src/components/jobs/LienRulesDoor.render.test.tsx` failed once in CI. Nothing in the app changed.

## What happened

On 2026-11-13 the `checks` job of an unrelated PR (the Affidavits print bar, v2.7209) went red on one test of 44,563: *held by the caller (the Lien desk's More sheet on a phone, punch list #352 PR 1)*, added by v2.7200. That PR touches neither `LienRulesDoor.tsx` nor its test. The message was `expected "spy" to be called with arguments: [ false ]`, with no call at all and the window drawn in the page. A rerun of the same commit passed.

## Why, as far as it was run down

The case opened the window, waited for it to be in the page, pressed Escape once and then waited for `onOpenChange(false)`. `LienRulesModal.tsx` listens for Escape on `window` from a `useEffect`. The window is a lazy chunk, so it mounts outside the test's `act`, and an effect can run a moment after the commit that puts the window in the page. A press that lands in that moment is a press nothing hears, and the wait that follows can only time out.

This reading is not proved. In a scratch copy of the case, not kept:

- the old shape passed 450 runs in a row, with every core kept busy for 300 of them, and 120 more with the window's first draw slowed by up to 30 ms;
- with the window's commit into the page slowed by 30 ms it failed once in 420 runs, and that one failure's message was not captured;
- the new shape passed 150 runs with the commit slowed by 8 or 30 ms.

So the old shape can fail by itself on this machine too, rarely, and the cause above fits what CI printed. It has not been shown to be the only one.

## The change

The key is pressed inside the wait, so it is pressed again until the window hears it:

```ts
await waitFor(() => {
  fireEvent.keyDown(window, { key: 'Escape' })
  expect(onOpenChange).toHaveBeenCalledWith(false)
})
```

A second press after the first has landed calls `onOpenChange(false)` again, which the case does not count. The file's other Escape press comes straight after an `act`, where every effect has run, and is left as it was.

If the case fails again with this shape, the listener is not the cause, and the next thing to read is whether the window's `onClose` reached the door at all.
