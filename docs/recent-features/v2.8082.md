# v2.8082 — HR files: the entry composer drops a link pick that is spent or belongs to another file (2026-11-20)

Found by the audit of punch list #315. No migration, no seat change.

## What was wrong

A line's **Correct this entry…** opens the composer with the link picked (`draftTargets` in `PersonFilePanel.tsx`). Add entry writes the entry, then the link.

- **A refused link stayed picked.** `setDraftTargets([])` ran only when the link landed. When the entry saved and the link was refused, the composer closed with the pick still set. The next **+ Add entry**, about anything, opened with *This entry corrects the entry of …* and would link itself to that older entry. Entries never change, so a wrong link on one has to be withdrawn by hand.
- **A pick followed the panel to another person.** The panel is not remounted when the roster opens another file, and nothing cleared the picks. The composer then read *corrects the entry of another day*. The table's guard refuses a link across two people, so nothing wrong could be written, but the refusal was the first sign.

## What changed

- A refused link clears the picks, as a link that lands does. The toast still says the entry is on the line and was not linked, with the reason.
- The picks are cleared when the panel moves to another person.

## Verification

`PersonFilePanel.amendments.render.test.tsx`, two new cases. Both fail on the panel as it stood and pass now.

## Left for the owner

The composer's typed words also stay when another person's file is opened, with the composer open. That is older than punch list #315, and clearing a person's typed words is a choice, so it is in the audit's report and not changed here.
