# v2.6326 — Robot fixtures: fold a second robot source when a bid is adopted (2026-11-02)

Punch list #226 (`to-dos/robot-fixtures-adopt-fold.md`, deleted here), found on 2026-10-31 by the session that built #221 while #6637 (v2.6230, adopt carries plan sets and CountTooling projects) and #6649 met in the merge queue. Fix with a migration (`20261102041932_robot_fixtures_adopt_fold`, `docs/migrations/20261102041932_robot_fixtures_adopt_fold.md`); no client change, no edge function.

## Change

- Since v2.6230 an adopt moves every `bid_count_sources` row of the adopted bid onto the package, the robot's own row too (`source_kind = 'robot'`); it carries no token, so the same-token guard never held it back, and when both bids took robot fixtures the package carried two robot rows. Every robot lookup is `LIMIT 1`, so nothing failed, but Set aside or Undo could strip the wrong share and leave a row shaded by a source that no longer existed, and the From tile drew two Robot chips.
- `robot_fixtures_fold_adopt`, a SECURITY DEFINER helper in the shape of v2.6235's `robot_fixtures_follow_adopt`, runs from `adopt_bid_as_version` right after the count sources move: the package's own robot row (bid-wide first, else the oldest) is kept, the moved rows' `source_shares` are re-keyed to it, and the duplicate is deleted, so one package never carries two robot sources. A folded row is taken off the log line's CountTooling count. The card's recommended defaults were taken: a definer helper (the copy and adopt functions run as the caller), the package's row the keeper, no repair of existing rows (the card's blocker says it could not yet have happened on a real bid).
- The `robot_fixtures` and `bid_copies` SQL beds carry the case: two bids that each took robot fixtures, the adopt, one robot source on the package with every moved share keyed to it, the log line, then Set aside and Undo leaving no row shaded.

Deploy: `supabase db push` after the merge. Nothing waits on it; until it lands an adopt behaves as before.
