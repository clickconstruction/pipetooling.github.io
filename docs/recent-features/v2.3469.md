## Why

Owner, 2026-09-14, reading the GC-on-notice mock-up: "For this rule to work, at least one notice would have had to go out first so that the office knows that all the information is correct." A standing rule of *send without asking* (v2.3405) let the office put a GC's very first notice straight into the run, before anyone had proved the owner of record, the mailing addresses or the GC's copy on real mail. The kernel already knew *first notice we've sent this GC* as a reason to ask the leader — but it checked the rule first, so the reason never fired under "send".

## What shipped

- **Kernel [`lienDesk.ts`](../../src/lib/jobs/lienDesk.ts)** (+1 test): `ruleWaitsOnFirstNotice(policy, gcHasPriorNotice)`; `submitOutcome` checks it before honoring a "send" rule, so the first notice returns `awaiting_approval · first_notice` and the rule applies from the second on. The "send" policy's hint names it. A live promise still wins over everything.
- **Migration**: `job_lien_desk_items_guard()` gains the server-side half — an approval with `approval_mode = 'rule'` on a notice item is refused (`23514`, *the first notice to a GC comes to the leader; a standing rule starts with the second*) while no `job_lien_filings` row of kind `notice_53_056` (not voided) exists on any job with the same `gc_customer_id`. Mirrors the client's `gcsWithPriorNotice` read.
- **[`LienDeskModal`](../../src/components/jobs/LienDeskModal.tsx)** (+1 render case): `ruleLive` (send rule and a prior notice) drives the *Put it in the run ▸* label, the toast, and the footer sentence — a GC on "send" with nothing recorded reads *…has a standing "send" rule, but this is the first notice we've sent them — it goes to the leader; the rule starts with the next one*. The leader's rule picker adds the same sentence while no notice is recorded.
- Guide *send lien notices from the Lien desk*: the standing-rule bullet and the example.

## Live data this changes

None today: on 2026-09-15 no GC carries a *send* rule without a recorded notice (Loberg Contracting, the v2.3405 example, is still on *ask*). The guard matters for the GC-on-notice run, where the rule is ticked in the same decision as the first notices.
