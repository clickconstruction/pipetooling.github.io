# v2.2264 — Sequential stage tasks + ⏳ Coming up (2026-08-25)

Owner decision: tasks inside a roadmap stage run in `sort_index` order (the
existing 4.1/4.2 numbers; ties by id). Per-stage opt-out
(`checklist_tech_tree_groups.sequential`, default true → "In order" /
"Any order" toggle in the stage edit dialog).

## Migration `20260825024351_sequential_stage_tasks.sql`

- `groups.sequential boolean NOT NULL DEFAULT true`.
- `sync_roadmap_to_checklist` rebuilt: materializes only tasks with no open
  earlier sibling (sequential groups), and **de-materializes** not-yet-due
  items already on lists — never deleting an item with a completed/reviewed
  instance or a comment thread. Returns `{created, removed}`.
- New trigger `trg_materialize_next_sequential_task` on
  `checklist_tech_tree_group_tasks.completed_at`: completing a task
  materializes the next sibling immediately (created_by carried over from the
  completed task's item so the reviewer stays the original editor). Cross-stage
  unlocks stay on the normal sync cadence.

## Client

- Kernel `sequentialWaiting` in `checklistTechTreeGraph.ts` (+tests): waiting
  ids + per-task blocker, from the already-sorted `tasksByGroup`.
- `useTechTreeTaskMutations.canActOnTask` gains an `isTaskWaiting` gate for
  non-staff; **staff deliberately bypass it** (unblocking a stuck chain from
  the Map is a two-tap fix).
- Map `GroupNode` + Plan rows: waiting tasks at 50% opacity with an
  "after 3.2" note; task card shows "⏳ Waits its turn — after 3.2" and hides
  the done-toggle for non-staff (via the same gate).
- New self-contained `ChecklistComingUpSection` (Today tab + Dashboard My
  Inbox): the viewer's waiting tasks, dashed/grayed, each naming the blocking
  task, its assignees, and the stage. Reads tech-tree tables via the v2.2261
  assignment-grants-read policies; renders nothing on failure/empty.
- `database.ts`: `sequential` hand-added pending regen.

**Deploy order**: client tolerates the missing column (defaults sequential,
Coming-up hides); push the migration promptly after merge — the first sync
after it prunes not-yet-due tasks off lists (the "35 outstanding" pile
shrinks by design).
