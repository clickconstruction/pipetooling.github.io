# v2.2383 — Edit Bid GC cards + in-place GC creation (2026-08-27)

Owner request, prototyped as a playable artifact first ("GCs on This Bid")
and approved. The complaint: the bid's GC got a big field with contact
chips while "Also sent to" GCs were cramped pills with none, the roles
were explained by two paragraphs, and an unknown GC forced you out of the
modal to create the customer.

- **`GcCard`** (exported from `BidGcRecipientsRow.tsx`): one card shape
  for every GC — name, address, ☎/✉ chips (via
  `extractContactFromCustomer`), and a role chip with a hover title:
  ★ Bid's GC (amber), same letter as {name} (blue), own packet (green,
  `source: 'version'`).
- **`BidFormModal`**: the primary GC renders as a GcCard under a "GCs on
  this bid" heading; the search input mounts only while no GC is chosen or
  after **change ▸** (with a **keep current ↩** escape). The old separate
  contact-chips block is absorbed into the card. Local `changingPrimary`
  state, reset per bid.
- **`BidGcRecipientsRow`**: recipients render as GcCards (was the chip
  row); the tick-list picker keeps its multi-add flow and gains a
  **＋ New GC — create without leaving this modal** row: it opens the
  app's `NewCustomerModal` STACKED over Edit Bid (`openNewCustomerModal`
  with an `onCreated` that reloads customers and inserts the new GC as a
  `bid_gc_recipients` row immediately). Explainer collapses to one line.
- Deliberately out of scope: a "give own packet" action on same-letter
  cards — packet creation lives in the bid-pages Add-GC modal; the chip's
  hover title points there (same as before).

Verified live on the dev server against the ZZ Test bid (customer_id was
genuinely null — the card appears the moment a GC is picked): ★ card with
contacts, change ▸ / keep current round-trip, recipients as cards with
per-source role chips, picker's ＋ New GC stacking the customer form over
a still-live Edit Bid. Closed without saving; no writes.

Help guide `bid-one-project-to-multiple-gcs.md` §"Also sent to" rewritten
for the cards.
