# v2.6436 — The reply box drops a papers read that lands after the box is gone (2026-11-03)

Client only, and nothing the box shows changes: no migration, no function change.

## The incident

PR #6892 (a print restyle touching only `src/lib/peopleDocuments/buildHoursStatementHtml.ts`) went red on 2026-11-03 with every one of its 4023 test files and 36717 tests passing: `Errors 1 error`, `ReferenceError: window is not defined` from `dispatchSetState` via `src/components/gc/messages/reply/usePapers.ts:21`, "This error originated in `ReplyBox.jobStrip.render.test.tsx` … caught after test environment was torn down", and the process exited 1. Main had failed the same way now and then.

## The race

`usePapers` (v2.5641, punch list #127) starts the customer's papers read the moment the strip opens (`io.load(customerId).then(setRead)`) and cancels nothing, by design: a fold must not lose a read already asked. `ReplyBox.jobStrip.render.test.tsx` stubs the quick replies but not the papers, so the box reads through the real client against CI's dummy `https://example.supabase.co`; the test awaits the strip's lines and ends, the cleanup unmounts the box, the environment is torn down (`window` deleted), and the read lands whenever the network answers. React's `setState` on an unmounted fiber still reads `window.event` (`getCurrentEventPriority` under `requestUpdateLane`), so an answer that falls into the gap between the teardown and the worker's exit is a `ReferenceError`, which vitest reports as an unhandled error and the run exits 1. On an M-series Mac the gap is a few milliseconds wide; on a loaded runner it is wider.

## The fix

A `mounted` ref in the hook, set by a mount-only effect, and the landing skips `setRead` when it is false. The read effect is untouched: a fold (`wanted` false) still keeps its read, since the ref follows the box's life, not the effect's. The strip test is unchanged; every `ReplyBox*.render.test.tsx` that renders the box without a `papersIo` is covered the same way.

`usePapers.render.test.tsx` holds three cases: the read once wanted and once per customer; a fold while the read is out keeps it; a read landing after the box is gone, with no `window`, reaches nothing. The third deletes `window` the way the teardown does, lands the read as the network would and listens for the unhandled rejection in vitest's place: against the old hook it caught the incident's exact stack (`getCurrentEventPriority` ← `requestUpdateLane` ← `dispatchSetState` ← `usePapers.ts:21`).

## Verified

The strip test 10/10 in a loop, the reply folder (18 files, 120 tests), the new test green against the fix and red against the old hook, `npm run typecheck`, `npm run lint`, the release-note drift test. The timing itself could not be made to fall in the gap locally: a sweep of landing delays from 5 to 200 ms landed either before the teardown or after the worker's exit, so the regression test reproduces the mechanism instead.
