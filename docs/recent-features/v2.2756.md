# v2.2756 — Row-cap tripwire in the Supabase client (2026-09-04)

Layer 2 of the Takeoffs parts-catalog incident (v2.2755): PostgREST answers every un-limited read with at most `max_rows` (1,000) rows and no error, and five surfaces have now been bitten one at a time as tables grew past the cap (v2.976/978 Crew P&L, team labor, People Review, Settings backups, Takeoffs). Each was fixed at its own call site; nothing could see the next one coming. This PR makes the client notice.

## Client only — no migration, no edge functions

- New kernel [`src/lib/supabaseRowCapTripwire.ts`](../../src/lib/supabaseRowCapTripwire.ts): `restTableFromUrl`, `parseContentRange`, and pure `detectRowCap(probe)` — flags a `/rest/v1/` GET (or set-returning `rpc/` POST) whose request URL carries no `limit` param (postgrest-js writes `.limit()` / `.range()` as `limit=` + `offset=`) and whose response `Content-Range` says exactly `ROW_CAP` rows with an unknown or larger total. `wrapFetchWithRowCapTripwire(fetch, report)` probes every response's headers and returns the response untouched; a reporter throw can't fail a query. `makeConsoleRowCapReporter()` logs one `[row-cap] <table> returned exactly 1000 rows with no limit …` console error per table per session, naming `fetchAllRows` as the fix. 12 tests.
- [`src/lib/supabase.ts`](../../src/lib/supabase.ts) passes the wrapped fetch as `global.fetch` to `createClient`. Dev and prod behave the same (console error); there is no client-side error sink to ship findings to yet — when one exists, swap the reporter.
- Not a static check on purpose: the class is defined by data size, not code shape. A registry-driven lint (`check:row-cap`) can sit beside this if the owner wants CI to block known-large tables too.

## Docs

- `docs/TROUBLESHOOTING.md` → new "`[row-cap]` console error" section: what it means, how to fix (page with `fetchAllRows`, bound with `.limit()`/`.in()`, or add `count: 'exact'` when exactly 1,000 is real).

Verified from a worktree dev server on the pre-v2.2755 client: opening BP396 → Takeoffs logged `[row-cap] material_parts returned exactly 1000 rows with no limit` — the exact bug v2.2755 fixed, caught on first load.
