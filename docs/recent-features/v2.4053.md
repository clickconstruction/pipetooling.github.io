# v2.4053 — Customer portal: Your payments — where each check went (2026-09-28)

Client + **edge function `customer-portal` (redeploy)**; no migration. PR 5 of "Where the checks went" (after [v2.4043](v2.4043.md), [v2.4044](v2.4044.md), [v2.4046](v2.4046.md), [v2.4050](v2.4050.md)). The GC's own bookkeeper gets the lookup the office got in PR 3, on the portal.

## What shipped

- **`supabase/functions/_shared/portalChecks.ts`** (pure, 3 tests from `src/lib/portal/portalChecks.test.ts`) — `buildPortalChecks({ jobs, invoices, payments, events, viewerCustomerId })` pre-scopes what reaches the page: a bill counts when the viewer is its payer (the shared who-pays rule); a linked payment counts with its bill; an unlinked payment counts only on a job whose **every** sent bill is the viewer's, since which bill it paid could otherwise name the other party's money; a move counts when it names a kept payment and carries no actor and no reason. Every kept job is stamped `customer_id: 'viewer'` with no GC and no rule, so the page's kernel counts every line as theirs.
- **`customer-portal`** — reads every sent bill (`billed` | `paid`) and every payment on the viewer's jobs, the `moved` events naming those payments, and returns `checks: { jobs, events } | null`; the job select adds `lien_retainage_held`; the open-bill payment select adds `id, sent_on, reference_number`, and `portalPaymentMethod` puts the number on the label (*check #48211*), so the line under each bill (v2.4044) now names the check. A read failure leaves `checks` null.
- **`parsePortalChecks`** (`src/lib/portal/portalPayload.ts`) — tolerant of the block's absence and of a bad row.
- **`PortalPaymentsSection`** (`src/components/portal/PortalPaymentsSection.tsx`, screen only) — *Your payments*: a search box (number, amount or day), the newest five, **Show all**, each payment as the headline, the applied sentence and its moves, from the same kernel as GC Review's Find a check (`buildGcChecksReport({ gcId: 'viewer', … })`). Nothing on record, no section.
- Guide *share a customer their portal* → **Your payments**; `EDGE_FUNCTIONS.md` → customer-portal; GLOSSARY.

## Deploy

`supabase functions deploy customer-portal` after merge. The client is tolerant of the old payload (the section stays off), so order does not matter.

## Decided here

- **Scope on the server, fold on the client.** The kernel is client code; the edge function sends only rows the viewer may see, stamped as theirs, and the page runs the same fold the office runs — one rule, two readers.
- **A split job's unlinked payment stays off the portal** rather than risk showing the other party's money; the office still sees it in GC Review.
- **The trail shows the day and the amount, never the office's note** — the owner's call on the mock-up.
