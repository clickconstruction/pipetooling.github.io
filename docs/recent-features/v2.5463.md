# v2.5463 — Two changes that each add a server function no longer block each other in the merge queue (2026-10-13)

A mechanical change to one generator, kept alone (GC Mode helper 5, at the lead's word). `scripts/build-dev-mcp-catalog.mjs`
wrote `supabase/functions/dev-mcp/catalog.ts` as one line per list, so every pair of PRs that added an edge function
rewrote the same `EDGE_FUNCTIONS` line and the merge queue dropped whichever came second (#5452 against main, then
#5497 against #5627, on 2026-10-13). The same held for a new table or RPC in a types PR.

- **The layout**: `CATALOG_TABLES` and `CATALOG_RPCS` are written one sorted key per line, and `EDGE_FUNCTIONS` one
  sorted name per line, each line ending in a comma, so an entry added at the end leaves the line before it alone. The
  file grows from 11 lines to about 1,500 (1,510 on 2026-10-13).
- **Nothing else changes**: the three lists are identical to the old file's (527 tables and views, 810 RPCs, 159 edge
  functions, compared by value), `--check` and `devMcpCatalog.test.ts` read the new layout, and `dev-mcp` imports the
  same names. A redeploy of `dev-mcp` is not needed for behaviour; `check:edge-drift` names it until its next deploy.
- **Checked**: two throwaway branches that each added a function and re-ran the generator merged with no conflict.
  Two names that sort next to each other can still touch adjacent lines; re-running the generator on the rebase
  resolves it, as before.
- **Every open PR that carries the old one-line catalog** re-runs `node scripts/build-dev-mcp-catalog.mjs` on its next
  rebase, as CLAUDE.md's rule on generated files already says.
