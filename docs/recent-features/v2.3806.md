# v2.3806 — The Pipeline row says when a check came back (2026-09-24)

Punch list **#40** PR 3 of 3 (PR 1 v2.3795 the Dashboard card + the AR chip; PR 2 v2.3804 the webhook's email + push). Redundant once the card exists — and that was the point: Taunya's eye lives on the Billed Awaiting Payment row, so the row itself says it. Client only; no migration. **The to-do folder `to-dos/returned-check-noticed/` is deleted with this PR** — the three fragments carry the record.

## The change

- **[`bankReturnedDeposits.ts`](../../src/lib/jobs/bankReturnedDeposits.ts)** — `bankReturnedByJob(items)` folds the card's items into a `Map<jobId, { count, total, reason }>`; `bankReturnedBadgeWords` → *check returned · $13,680* (*2 checks returned · $21,680* when two deposits bounced); `bankReturnedBadgeTitle` is the hover. Tested.
- **Pipeline (`JobsStagesTab`)** — one `useBankReturnedPaymentsNudge` read per board (dev / master / assistant-like — the roles that can read `mercury_transactions`; nobody else makes the read), folded per job. The Billed rows' chip slot (`billedExpectedPayChipRenderer`, rendered by both the invoice-kind and job-kind rows and the card list) gains a red badge button **first**, in v2.3784's "Returned by the bank" pill style; it opens Edit Job on ③ Payments received through `tryOpenEditJob(job.id, { paymentsReceivedHighlight: true })` (v2.3795's landing) and re-reads the set after a save. A row with no expected-pay chip and no promise door still renders the badge (the early return respects it).
- **Phone row (`jobNextLine`)** — `JobNextLineInput.bankReturned`; `pickJobNextChip` returns *check returned · $13,680* (red, new action `payments`) ahead of every fact but a missing bid value, since the paid figure is wrong until someone acts; `needsMe` follows. The tab's `onChip` routes `payments` to the same door. Tested.

## Decisions taken

- **After the unlink the badge waits for the next read.** Unlink and remove is not a save, so the row re-reads on the next board load or save rather than the instant the button is pressed; the Edit Job table already reads correctly.
- **One read, not a column.** `jobs_ledger.payments_made` cannot know a deposit bounced; a join per row would be a migration. The card's two small reads, once per board, are enough.
