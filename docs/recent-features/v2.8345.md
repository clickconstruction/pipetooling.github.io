# v2.8345 — Working hours: the database can hold a start and an end for each day (2026-11-23)

The first of five PRs for punch list #429. The owner asked on 2026-11-23 for a way to set specific working hours for a person: a first-time helper works 6:00 AM to 12:00 PM, five days a week. Hours are in 15-minute blocks, and only a dev or the controller sets them for now. He passed the plan and its mock-up the same day and said *build it all*. This is the database half. No screen changes.

## Why

Three things described a person's week, and nothing held them to each other:

- the seven hour numbers on pay (`people_pay_config.salaried_week_hours`), which pay and cost read;
- the workday template (`salary_work_schedule_templates`), which makes a salaried person's clock sessions and always makes 8 hours;
- the week a person says they can work (`person_available_hours`), seven days of start and end minutes from a Sunday on, append-only, which only Utilization and My Time read.

None of them said *6:00 AM to 12:00 PM* in a way pay, the clock and the person all read. The third already has the shape, so the plan promotes it and works the other two out from it.

## What ships

Migration `20261123075925_working_hours_door.sql` ([its page](../migrations/20261123075925_working_hours_door.md)):

- **`person_available_hours.kind`**, `answer` or `set`. Every row today is an answer. A set row is a person's working hours, and it will win over any answer once the readers know it.
- **`working_week_ok(days)`**, the shape of a set week: seven days, Sunday first, each with no range, one range, or two with a break between, every time on a quarter hour, and no more than 16 hours a day. A check on the table holds every set row to it.
- **`set_working_hours(user, days, from, reason, dry_run)`**, the one door. It refuses anyone who is not a dev or the controller. Hours start on this week's Sunday or next week's. For a salaried person it writes the seven hour numbers in the same transaction, each day's hours with the break left out, and one line on the pay log.
- **`working_hours_on(user, day)`**, a day's ranges from the set week in force: the ranges, an empty list for a day off, or nothing when no hours are set.
- The table's insert policy takes an answer only, so nobody signed in writes a set row directly.
- `hours_per_week` widens from tenths to quarter hours.

## Four rules the door holds

1. **Pay carries no date.** A change to a salaried day's length re-prices every week with no pay report, as a change in *Edit pay setup* does today. So the door lets it start this week only, and asks for a reason. A change of times alone moves no pay, may start next week and needs no reason.
2. **A dry run writes nothing.** `dry_run` answers what a save would do, pay included, so the screen and the dev seat can say it before anyone keeps a change.
3. **Hours can be taken off again.** A set row with no week ends working hours from its Sunday. The seven numbers stay where the hours left them.
4. **The newest save in force holds.** Hours saved for next week and then changed for this week stay as changed, next week too. Reading by the latest Sunday would bring the older save back and part a salaried person's hours from their pay.

## What does not change

Nothing reads a set row yet, so no pay figure, session or screen moves. The old client's answers still save as answers. Whoever could answer for a person still can. The lock on the seven numbers and on the workday schedule comes with the screens that replace those doors, so the screen and the database never say different rules.

## The bed

`npm run test:pg:working-hours` (`supabase/tests/working_hours/10_door.sql`, in `scripts/sql-beds.txt`): eighteen shapes a week may and may not take, each role at the door, the helper's week with pay standing still, a change of times from next week, a shorter Friday refused from next week and with no reason and then kept with the numbers and the pay log following, a lunch that is not paid, the Sundays the door takes, an hourly person, hours taken off again, and the table's own door as a signed-in person. Docker on the build Mac belongs to another login, so the bed's first run is the *SQL beds* check on this PR.
