# v2.2586 — Estimate Options cap raised 4 → 6 (2026-09-01)

User request (taunya, 2026-09-01): "I need more than 4 estimate options. Working on a
customer now that is asking for 5 separated". The original `MAX_ESTIMATE_OPTIONS = 4` was an
owner decision from the v2.2457 plan (choice-overload guard); this raises the ceiling to 6 —
covers the ask with one spare while the customer page stays stacked choice cards, not a menu.

- **Both kernels move together** (the parity suite `estimateOptionsSharedParity.test.ts`
  enforces equal caps): [`src/lib/estimates/estimateOptions.ts`](../../src/lib/estimates/estimateOptions.ts)
  and [`supabase/functions/_shared/estimateOptions.ts`](../../supabase/functions/_shared/estimateOptions.ts),
  both `MAX_ESTIMATE_OPTIONS = 6`.
- **Hardcoded literal fixed**: `estimateListOptionsCount` in `src/pages/Estimates.tsx` broke
  at a literal `4` instead of the constant — now uses `MAX_ESTIMATE_OPTIONS`, so the list-row
  "· N options" suffix counts past four.
- **No layout work needed**: the customer-facing `EstimateOptionsPicker` renders stacked
  vertical cards and the draft editor's option strip is `flex-wrap` — both scale to 6 as-is.
- **Help guide** `offer-options-on-an-estimate.md` ceiling wording updated.
- **Deploy note**: the four edge functions importing the shared kernel
  (`get-estimate-for-customer`, `accept-estimate`, `send-estimate-to-customer`,
  `log-estimate-option-view`) must be redeployed **before or with** the client deploy — a
  client that saves 5–6 options against servers still normalizing to 4 would hide the extra
  options from the customer and refuse their acceptance. Server-first is fully backward
  compatible.
