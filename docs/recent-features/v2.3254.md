# v2.3254 — Changing a user's role works again: the users UPDATE policy stops recursing (2026-09-10)

Migration only (`20260910230000_fix_users_update_policy_recursion_controller.sql`); no client change, no edge function.

## Why

Robert, in Active Accounts, changing Kyle from Subcontractor to Helper: a red line under the buttons — *infinite recursion detected in policy for relation "users"* — and the role stayed put.

The Person Desk PR 5 migration (`20260903191916`, v2.2713) widened the `users` UPDATE policy to admit controller, and did it by dropping the policy and re-creating it with the role lookup written inline: `EXISTS (SELECT 1 FROM public.users u WHERE u.id = auth.uid() AND u.role = ANY (…))`. A policy on `users` that selects from `users` re-enters the `users` policies, and Postgres refuses at run time. This is the exact bug `20260704120000` fixed on 2026-07-04 by moving the lookup into the `SECURITY DEFINER` helper `is_user_notes_editor()`; the 09-03 rewrite did not use the helper. Since that push, every authenticated UPDATE of `public.users` — role changes, training-mode toggles (the very widening the migration was for), user notes, profile edits — has failed with this message. Only the service-role edge flows (archive / restore / merge / claim-dev) kept working, because they bypass RLS.

## What shipped

- `is_user_notes_editor()` gains `controller` — the 09-03 intent — and stays `SECURITY DEFINER` with `anon` execute revoked.
- The policy is re-created `TO authenticated`, `USING / WITH CHECK (public.is_user_notes_editor())`. Same four roles the 09-03 policy named; which columns each may touch is still the `users_guard_privileged_columns` trigger's call (role is dev-only; read_only is dev / controller / pay-approved master, never your own; archived_at is edge-flow only).
- Both the function and the policy carry a comment saying why the helper is mandatory, so the next widening reads it before rewriting the predicate.

## Notes for the next session

- **Rule, now stated twice in the ledger:** never put `SELECT … FROM public.users` inside a policy on `public.users`. Route the lookup through a `SECURITY DEFINER` helper (`is_dev()`, `is_user_notes_editor()`, …). `20260714213000` did the SELECT-policy widening correctly by editing the qual in place; `20260903191916` did the UPDATE one wrong.
- The v2.2713 fragment's claim that the controller training-mode write works was never true in prod — the write recursed for everyone. Now it should; a controller toggling training mode on someone else's account is the second thing to verify after the role change.
- A CI guard in `scripts/check-migrations.sh` for this shape (policy on `users` whose body references `from public.users`) would have caught it; not added here to keep the fix migration-only.
