# v2.8070 — Before we start: a long list of bullets is read whole (2026-11-20)

Found by the Fable 5.2 audit of punch list #382. Client only: no migration, no edge function, and none of the four files copied to the edge is touched.

## What was wrong

`readOf` in [`src/lib/startChecks/startChecksIo.ts`](../../src/lib/startChecks/startChecksIo.ts) read each of the six tables behind a list (bullets, yeses, asks, the days they gave, decisions, arrivals) with one `.in('job_id', …)` and no `.range()`. PostgREST cuts a read with no range at 1,000 rows and says nothing. The order is oldest first, so the rows it dropped were the **newest**.

Two screens hand it many jobs at once:

- **The Development page's Schedule look** (`useSiteStartChecks`) reads every desk job of a site in one call. A site with 90 jobs × 3 stages × 4 bullets holds 1,080 bullets. The newest 80 never arrived: their stages read *No list yet* and offered **Use the four** over a list that exists. A yes past the cut showed its bullet still open.
- **The Dashboard's *customers owe us answers* line** (`startAnswersOwedIo`) reads every job in the company with an open bullet on them. Past the same cut it miscounted, and a long enough list of ids overflows the request's address. That read's failure is swallowed, so the line just disappeared.

## The fix

`readOf` now goes through `fetchAllRowsChunkedIn` (`src/lib/supabasePaging.ts`), as the sibling reads in `startAnswersOwedIo.ts` already do:

- each read is paged with `.range(from, to)` under the same total order (`created_at`, then `id`) until a short page arrives;
- the job ids go in pieces of 150, so the address stays short;
- each page still goes through `withSupabaseRetry`, so a lost request is tried again as before and a refusal still throws;
- rows from two pieces interleave, so the whole is sorted by `created_at` then `id` before it is returned. Callers see the order they saw before.

No jobs still reads nothing.

## The test

[`src/lib/startChecks/startChecksIo.paging.test.ts`](../../src/lib/startChecks/startChecksIo.paging.test.ts) stands in a client that answers as PostgREST does, cutting a read with no range at 1,000 rows:

- 1,001 bullets across 90 jobs all come back in order, the newest included, in two pages;
- 160 jobs are asked for in more than one `.in()` list, none over 150, and the rows of the two pieces come back in one order, a tie on the time broken by id;
- a table that cannot be read throws with the read's name;
- no jobs makes no request.

Run both ways: against the file as it stood on `main` the first two fail (*expected … to have a length of 1001 but got 1000*, *expected 1 to be greater than 1*); with the fix all four pass.
