# v2.8432 — The dev seat reads a query plan as the dev (2026-11-24)

Punch list #430. dev-mcp 0.133.0. One migration, one read verb on the dev seat. No client change.

## What was missing

Punch list #430 mended two views that joined a table with row policies through a `COALESCE`, and could not measure either on prod. A plan there was out of reach: PostgREST hands back rows, and the SQL editor and the Supabase MCP plan as the database owner, whom no row policy binds. The walk the card is about only happens under a policy, so only the caller's own plan shows it. Diane said yes to a dev-only, read-only plan reader on 2026-11-24.

## What changed

- **`dev_query_plan`** ([`20261124063000_dev_query_plan.sql`](../../supabase/migrations/20261124063000_dev_query_plan.sql), [its doc](../migrations/20261124063000_dev_query_plan.md)) runs `EXPLAIN` on one of the statements written out in its body, named by key. It starts with the card's two. It takes no SQL and has no dynamic SQL. It is `SECURITY INVOKER`, so the plan is the caller's under their row policies. It refuses anyone but a dev, and it turns its transaction read only before a statement runs.
- **`check_query_plan(statement, analyze?, find?, from?)`** on the dev seat is one GET of it. `analyze: false` asks for the plan alone. The reply opens with a reading of the whole plan: the times, every relation under a `Seq Scan`, the line count.
- **A long plan is fitted in the seat** (`_shared/devMcpQueryPlan.ts`). `agreements_on_file` plans to about 1,290 lines on an empty schema, more than a reply holds. A window of lines goes out with `next_from`, and `find` shows the nodes that hold a piece of text with every node above them, so a scan reads with the joins it sits under. `find` is matched in the function and never reaches the database.
- **A new bed holds it**: `dev-query-plan`, whose assertions are listed in the migration's doc.

## Settled by test before it was written

- Postgres 17.6 refuses `EXPLAIN` inside a `STABLE` function, so the function is `VOLATILE`.
- PostgREST 12.2.12, 13.0.7 and 14.5, the version prod runs, each call a `VOLATILE` function over GET in a read-only transaction, and refuse a write under it with `25006`. The seat's GET door reaches the function, so no write verb was added.
