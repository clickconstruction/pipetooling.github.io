# v2.7134 — The type check has a 12 GB heap: the whole program's check passed 10 GB (2026-11-13)

Infra, no screen. The full TypeScript check of the app outgrew the 10 GB heap it was given, and from 2026-11-13 11:11 UTC it ran out of memory on GitHub's runners in both places it runs.

## What broke

- **The site's deploys.** `deploy.yml`'s Build step runs `tsc -b` before `vite build`. The run for b71cf0c96 (v2.7114) died after 11.5 minutes with *JavaScript heap out of memory* (exit 134), the first out-of-memory build in the sixty failed deploys before it. Every deploy after it would have hit the same wall once the unrelated calls-ahead hold of the same hour cleared.
- **Every pull request's checks.** CI's `checks` job runs `npm run typecheck` (`scripts/typecheck-queued.mjs`, `tsc -p` with the same heap). It died the same way, at about 10,050 MB, on three runs inside an hour: two pull requests and a merge-queue build. Nothing that touches `src` could merge.
- **The size of it.** The full check of main at 9662f1634 peaked at 10.1 GiB resident on a 48 GB Mac. It passed there, just under the line, so the wall is the whole program's growth and not one change. The pull request that tipped it adds files that each take under a second and at most about 120,000 type instantiations.

## The change

`--max-old-space-size=12288` in place of `10240` in three places: the `build` and `analyze` scripts' `tsc -b` in `package.json`, and `scripts/typecheck-queued.mjs`'s `tsc -p`. `src/lib/typecheckLock.test.ts` pins the wrapper's line, so it moves with it. `vite build` keeps its 8 GB.

**Why 12 GB is safe.** A public repository's hosted runner has 16 GB of memory. `tsc` and `vite build` run one after the other in the Build step, and the typecheck is a step of its own in `checks`, so `tsc` never shares the runner with a second big process. On a session's Mac the lock in `scripts/lib/typecheckLock.mjs` already runs one full check at a time. Its header still tells the 2026-11-08 story under the old 10 GB: that is history and stays.

## Is this the best we can do?

No. It buys room, about 2 GB over today's peak, and every merge spends some of it. Three things would do better, and none is small:

- **Drop the deploy's `tsc -b`.** The merge queue's `checks` job already type-checks every merge before it lands, so the build checks the same program a second time, for twelve minutes on each deploy. Taking it out also halves where this wall can be hit.
- **Split the program.** One `tsconfig.json` over all of `src` is one program; project references would check it in parts that each fit.
- **See it coming.** A line in CI that prints the check's peak memory on every run would show the next wall weeks ahead instead of on the day it lands.

Each is the owner's call: they are one row of `to-dos/owner-decisions-pending.md`, not built here.
