## What this surface is

## Shared substrate

**There is no shared selection pointer and no shared client state between the two components.** They never exchange props or context state. Their only coupling is (a) the `clock_sessions` table and (b) parent-owned callbacks — the strip's `onClockSessionsMutated` (Dashboard → `myTeam.loadPending({ silent: true })`) and the button's `onClockInSuccess` (Dashboard → `handleClockInSuccessContractPrompt`, the contract-signing prompt; it does **not** refetch the strip). **Consequence: the two components can be decomposed completely independently, in either order** — but each has its own *internal* substrate that must be seamed before its regions move:

1. **Strip — the approve/status engine**: `optimisticStripApprovedIds` (930) + `stripApproveBusy` (908) + `stripActionsSession` (910) / `stripActionsPayload` memo (968–989) + `stripRejectConfirm` (909), and the handlers `handleStripSessionApprove` / `handleStripPillApprove` / `handleStripSessionRevoke` / `performStripSessionReject` / `requestStripSessionReject`. Fact-sheet coupling: `optimisticStripApprovedIds` is read in 5 units and `stripApproveBusy` in 6, including the Clocked-in-today body (1971) and the Jobs-worked-today per-job detail (2669); both of those write `stripActionsSession`. The *focused-row filter* (`clockedInTodayFocusedRows`, 1197–1200) reads the same optimistic set so an optimistic approve drops the row from the "Needs attention" view. Any table extraction must consume this engine via props/hook — never duplicate it.
2. **Strip — the external data engine is already extracted**: `useDashboardMyTeamSectionState` supplies `clockedInTodayRows: ClockedInTodayStripRow[]`, `jobsWorkedTodayRows: JobsWorkedTodayStripRow[]`, `sessions: DashboardStripSession[]`, `hoursTodayByUserId`, `clockStripWorkDateYmd`, and the report-key maps. The strip's decomposition does not touch it.
3. **Button — the association-picker substrate**: `selectedAssociation` (230; fact sheet: 14 reading units, 13 writing units) + `associationChipFromSearch` (207) + `unifiedSearchText`/`unifiedSearchResults` (228–229) + `serviceTypes`/`enabledBidServiceTypeIds`/`subcontractorServiceTypeIds` (231–233) + `scheduledDispatchJobs`/`workingBoardBidPicks`/`assignedJobsListLoading`/`quickPicksEmpty` + `lastSelectedJobBid` (+ its localStorage persistence) + the refs `assignedJobsShownRef`/`assignedJobsFetchGenRef`/`lastDefaultUnifiedResultsRef`/`unifiedSearchTextRef`/`showToastRef` + four loader effects. All three modals share this one instance (only one modal opens at a time), and the Tally gate's open flag also keeps the loaders running so the review's picks are warm — the tally modal itself renders no picker. This is the button's `useBidPricingEngine` equivalent: build `useClockAssociationPicker` before any modal moves.
4. **Button — the session core**: `openSession`/`todaySessions`/`totalSecondsToday`/`error` + `fetchSessions` + `salaryUiActive` (277; read by 12 units) + the 90 s salary-sync interval. Read by the button row, the quick-time door, all three modals, the Tally gate, `applyUpdateFocusDirectImpl`, and the bridge registrations. Stays in the parent component permanently.

## Preserve-quirks list (odd but load-bearing — do not "fix" during the move)

1. **`showToast` via ref only** in the B2 quick-picks effect — the in-file comment (579) records a render loop when `showToast` was a dep.
