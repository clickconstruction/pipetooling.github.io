## The problem

Identity in the pay/labor domain is keyed by **trimmed name text**: `people_hours`, `people_pay_config`, `people_crew_jobs`/`_bids`, `pay_stubs`(+days), `people_team_members`, `people_hours_display_order`, `person_offsets`, `hours_reviewed` all join on `person_name`; `people_labor_jobs.assigned_to_name` is a `' | '`-delimited multi-name string. Consequences: a name variant ("Behar Kraja (Rough In)") becomes a second identity everywhere; a rename silently zeroes wage joins (see `docs/SALARY_CLOCK_SESSIONS.md`); Crew P&L splits people.

## Where we started (measured — Phase A ran 2026-07-24)

- `person_id → people.id` columns **already existed on all ten name-keyed tables** before Phase B ran — not just the five originally listed here (`people_hours`, `people_pay_config`, `people_crew_jobs`, `pay_stubs`, `people_team_members`); the "remaining" five (`people_crew_bids`, `pay_stub_days`, `people_hours_display_order`, `person_offsets`, `hours_reviewed`) had them too (discovered during B2 — this doc was stale on that point).
- Measured pre-backfill fill rates were low: `people_hours` 103/1,572, `people_pay_config` 3/24, `people_crew_jobs` 109/1,345, `pay_stubs` 14/245, `people_team_members` 0/0. Post-B backfill (rerun 2026-07-30) they are near-100% — see the status log.
- **Key Phase A finding**: pay identity actually keyed on `users.name`, not `people.name` — all 24 pay-config names matched `users` exactly. Phase B resolved names via account-linked users first (`resolve_pay_person_id`), which is why the backfill filled.
- The phase-0 audit script: [`scripts/audit-pay-person-id-phase0.sql`](../scripts/audit-pay-person-id-phase0.sql) (orphan names, fill rates, Phase-D unique-key preflight, junction coverage).
- `clock_sessions` was already `user_id`-keyed (sound).
- Interim tooling: **Combine people** (v2.982, People → Users) folds a duplicate into a keeper — repoints `person_id` AND rewrites names, so it works at every phase.

## Phases (each independently shippable; readers keep name-fallback so a missed backfill degrades to today, never worse)

- **A — Measure** — ✅ DONE 2026-07-24: phase-0 audit run against prod; fill rates + orphan names recorded in the status log.
- **B — Backfill + auto-populate** — ✅ DONE 2026-07-24 (v2.1008 migration `20260722268000` + B2 v2.1009 migration `20260722270000`): resolver + backfill + insert triggers on all ten tables; `people_labor_job_assignees(labor_job_id, person_id)` junction created, trigger-synced from the delimited text, backfilled. Name columns stay as denormalized display. Triggers later widened to `BEFORE INSERT OR UPDATE OF person_name` (v2.1113, migration `20260730164728`).
- **C — Flip readers, one surface per PR** — ✅ DONE 2026-08-16: C-1…C-4 (v2.1010–v2.1012), C1-1…C1-3 (v2.1122–v2.1127), C1-6 costing joins (v2.1577), C1-7 (v2.1266), and the two "deliberately skipped" reads — salary self-probes + My Team name-IN — closed in **v2.1734** (id-first at LOWER query cost). Pattern everywhere: prefer `person_id`, fall back to name.
- **D — Flip writers + access checks** — ✅ SUBSTANTIALLY DONE 2026-08-16 (v2.1729–v2.1735, see log): D0 unique indexes; sub-sheet writers id-link the junction; workflow step pickers, RLS/RPC assignee checks, and lifecycle notifications go id-first; `usePayConfig` exposes `payConfigById` with id-first lookups on the Employment tab. **Deliberate residuals** (recorded per-entry in the log): the pay-table `onConflict` keys stay `person_name` (it is still the PK; `set_person_id_on_write` triggers resolve ids on every write), `usePayConfig`'s map stays name-keyed as the roster join, and a handful of client-side workflow name filters remain (v2.1733 entry lists them).
- **E — Enforce** — 🔲 GATED, scoped 2026-08-16: FKs already exist on all ten tables (D0 discovery) — E is NOT about FK creation. Remaining, in order: (1) NOT NULL on `person_id` where writers guarantee resolution — currently unsafe: inserts with unresolvable names must degrade, not error (fail-soft invariant); (2) re-PK `people_pay_config` (and friends) off `person_name` so `onConflict` can flip; (3) retire `cascadePersonNameInPayTables` — only after NO reader joins by name (fallbacks everywhere today). Do not start E until a full quarter passes with zero name-fallback hits worth keeping.

## Invariants during the migration

1. Never key NEW logic on name text — always `person_id` (fallback reads only).
2. Combine people must keep working at every phase (it already does both id-repoint and name-rewrite).
3. Every phase-C PR includes a before/after check on the surface's totals (Crew P&L totals must not shift from a pure re-keying).

> Phase E and the remaining name-keyed reads are tracked in [`to-dos/person-identity-phase-e.md`](../to-dos/person-identity-phase-e.md) (2026-09-05 sweep).
