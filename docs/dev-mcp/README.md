## The idea

`https://mcp.clicktooling.com/dev` reads the app **as the dev whose key it is**. The function resolves the key to a person, mints that person's own session, and calls the app's own API with it — **GET only**. PostgREST runs GET in a read-only transaction, so the database refuses a write whatever an RPC is named; RLS and every `auth.uid()` role check apply exactly as on the screen. The service role is used for three things: resolving the key, minting the session, writing the call log.

It replaces two habits: read-only REST probes through a signed-in browser pane, and raw SQL through the Supabase MCP.

**Writes are a second path, not a loosening of the first** (v2.3722 / 0.4.0; the narrative v2.4814 / 0.5.0; a matter's planned steps v2.5800 / 0.6.0; a document on its Evidence tab v2.6004 / 0.7.0; a sworn statement drafted onto its Timeline v2.6244 / 0.13.0). Twenty-one verbs POST one of ten hard-coded, dev-gated `SECURITY DEFINER` RPCs as the dev — the same entrypoints the `cost_agent` and `hr_agent` database roles and the Legal desk use — and nothing else: never a generic POST, never a table write, never through `view_as`. The grammar is `plan_` (a dry run, its own call) → `apply_` (the real write, which must quote the plan's hash).

## Connect

Settings → Your account → **Dev MCP keys** → *Issue a key* (deep link `/settings#settings-dev-mcp-keys`) (one per machine; `ptd_…`). Since v2.5899 a key is kept in Vault as well as hashed, so **Copy** on a live row shows it again (your own keys only, behind a confirm, one `dev_mcp_calls` row with `verb reveal_key` per copy; a revoke deletes the secret); a key issued before 2026-10-26 is hash-only and cannot be copied — issue a new one. The card's **Copy setup command** puts `export PT_DEV_MCP_TOKEN='ptd_…'` in your shell profile and the same key under `env` in `~/.claude/settings.json` (v2.6123: the desktop app never reads the profile, so a session it starts had no key and every call answered *Unknown or revoked dev key* while the connector read as connected); `.mcp.json` already registers the `dev-mcp` connector with that variable. MCP servers connect at session start — a session launched without the variable cannot repair the connector mid-flight, and a reconnect in `/mcp` does not either. First call: `whoami`.

## The verbs

|---|---|
| `whoami` | Who the key reads as, and the door's limits. |
| `find_rpc(text)` · `find_table(text)` · `get_table(table)` | The generated catalog (`dev-mcp/catalog.ts`, from `src/types/database.ts`): names, arguments, columns. Never guess a name. |
| `call_read(rpc, args?, limit?)` | Any RPC, as you, over GET. |
| `read_rows(table, select?, filters?, order?, limit?)` | Any table or view, RLS-bound; default 50 rows, at most 200. |
| `find_job(text)` · `find_bid(text)` · `find_customer(text)` · `find_person(text)` | "J1032" / "b482" / a name → ids, with the label the app shows. Jobs and bids use the app's own search RPCs; people are listed as the rosters list them (active, human, not a sample). |
| `get_job(job)` | The Job window: header, **money**, invoices, payments, account strip, stages, hours, recent activity. |
| `get_customer(customer)` | The Customer hub: profile, **money**, contacts, addresses, jobs, bids, estimates. |
| `get_bid(bid)` | A bid's stored facts: the row, count rows, assignments, versions, sends, the submission ledger, the strip. |
| `get_history(development_id, job_id?, bid_id?, since?, limit?)` | A development's History as people wrote it (v2.6044), every body whole, through `dev_history_read` as the reader: the kept lines, the job's and the bid's thread notes, newest first, with who wrote each; the records' own lines (sends, stage moves, bills, payments) stay with `read_rows`. |
| `check_sampler(hours?)` · `check_connections` · `check_locks` · `check_migration_ledger(n?)` | **Is the database healthy?** Each opens with a one-line `reading`, then the rows: sampler gaps over 90 s and the slowest sample (the freeze windows and the early warning of [`DB_FREEZE_RUNBOOK.md`](../DB_FREEZE_RUNBOOK.md) Step 2 — they survive a restart), the newest connection sample against `max_connections`, who waits on a lock **right now** and who blocks them, and the newest ledger rows to hold against `git ls-tree origin/main supabase/migrations/`. Dev-gated definer RPCs (`dev_health_*`, `dev_migration_ledger_tail`) over the same GET door — no service role; they read, they never terminate a backend. |
| `check_edge_boot(after?)` | OPTIONS-probes the edge functions (a generated list, in name order) and names any answering `503 BOOT_ERROR` — deployed but unable to start, which `check:edge-drift` cannot see. **50 per call**: the platform allows a function about 60 calls a minute to other functions, so the reply carries `next_after` — call again with `after`, about a minute later, until it is `null` (three calls today). A probe the rate limit refused is listed as `rate_limited`; it says nothing about that function. |

The `cost_batches` row names you. |
| `plan_hr_entry(entry)` · `apply_hr_entry(entry, plan_hash)` | **File an HR entry** ([`HR_FILES.md`](../HR_FILES.md)) through `dev_hr_entry_write`, a dry-run wrapper over the live `hr_agent_write` (migration `20260922102017`): entries to append, a summary or narrative rewrite; you are named as the author whatever the payload says. Same plan → apply rule. Entries are append-only; a correction is a new entry. |
| `plan_matter_narrative(narrative)` · `apply_matter_narrative(narrative, plan_hash)` | **Write the narrative for the firm** on a legal matter through `dev_legal_narrative_write` (migration `20261007235000`), a dry-run wrapper over the Legal desk's own `legal_set_narrative` ([`EDGE_FUNCTIONS.md` → legal-portal](../EDGE_FUNCTIONS.md#legal-portal)): `{ matter_id, markdown }`, the whole text, at most 40,000 characters; an empty text clears it. The plan names the matter, the length before and after, when it was last saved, and whether the firm reads it now (a matter referred onward and not closed). Apply saves it as you. A save by anyone since the plan changes the hash, so apply refuses: plan again. A whole folder of files still goes on a matter with `scripts/legal-file-documents.ts` (a manifest, dry run unless `--write`); one document at a time is the next row's verb. |
| `plan_matter_plan_item(item)` · `apply_matter_plan_item(item, plan_hash)` | **Plan what happens next on a legal matter** (v2.5800) through `dev_legal_plan_write` (migration `20261023195135`), a dry-run wrapper over the Legal desk's `legal_plan_add` / `legal_plan_update` / `legal_plan_mark_done`: `{ action: 'add', matter_id, on (YYYY-MM-DD), body (what), notes? }` plans a step; `{ action: 'update', entry_id, on?, body?, notes? }` changes one; `{ action: 'mark_done', entry_id, done_on? (today when left out), note? }` says it happened and keeps the day it was planned for. The plan names the matter, the item before and after, and whether the firm reads it now. Apply writes as you with `meta.source = 'mcp'`; the office sees it on the desk's Timeline tab at once. A change to the step since the plan changes the hash, so apply refuses: plan again. Reads need nothing new: `read_rows` on `legal_matter_entries` (filter `kind eq plan`) lists the line. |
| `plan_matter_statement(statement)` · `apply_matter_statement(statement, plan_hash)` | **Draft a sworn statement or an unsworn declaration onto a legal matter's Timeline** (v2.6244 / 0.13.0, punch list #220) through `dev_legal_statement_write` (migration `20261031190000`), a dry-run wrapper over the Legal desk's `legal_statement_add` / `legal_statement_update`: `{ action: 'add', matter_id, on (YYYY-MM-DD, the day it is about), title, body (the paragraphs), affiant { kind: team \| witness, user_id? (notary \| declaration; notary when left out), incident_to?, venue_county? }` drafts one; `{ action: 'update', entry_id, … the fields that change (null clears the span or the county) }` changes a draft it or the office made, refused once the signed copy is filed. The plan names the matter, the statement before, the draft as it would be written with the Said lane's state words (*Draft · not signed.*), how many statements the matter holds and whether the firm reads it now. | `plan_matter_document(document)` · `apply_matter_document(document, plan_hash)` | **File a document on a legal matter's Evidence tab** (v2.6004 / 0.7.0) through `dev_legal_document_write` (migration `20261028010000`), a dry-run wrapper beside the desk's own upload: `{ matter_id, title, shows, original_name, content_base64, dated_on?, state? The Mac runs `python3 scripts/twin/redeem_setup_code.py <code>`, which writes the key to `~/pt-twin-digest/twin.token` and never prints it ([`twins/TWIN_HARNESS.md`](../twins/TWIN_HARNESS.md) → Set up a Mac from the dev seat). Outside the plan → apply grammar; refused through `view_as`. |
| `view_as(role \| user, verb, args?)` | Any verb above as a role's **sample account** or a named person — what *they* see. A dev is never a target (Imitate's rule); both identities are logged (`dev_mcp_calls.as_user_id`). |

**Where the money comes from.** A composite runs the screen's own reads and hands the rows to the screen's own kernels in `_shared/` — `get_job`: `jobMaterialsCostLines` (the four parts buckets) + `jobSubLaborInputs` + `buildJobProfitSummary` (profit) and `profileJobRowMoney` (billed / open); `get_customer`: `customerMoneyStats`, `customerDaysToPay`, `customerEstimateOutcomes`. So a number here is the number on the screen, and a change to the screen's math changes this too. Where that is not possible the reply **says so instead of computing a second opinion**: a bid's priced total lives in the `useBidPricingEngine` hook, so `get_bid.totals` is a sentence, not a figure. A part that cannot be read is reported in place (`{ "error": … }`) and takes only itself down — a failed cost source costs you `money`, not the job.

`job`, `customer` and `bid` take an id, or text that matches exactly one; several matches come back as a short list of ids to choose from.

## What the door refuses

- **Writes** — by the database (`25006`, read-only transaction), not by a list in the function — except the twenty-one `plan_` / `apply_` / `revert_` verbs above, which POST only their ten named RPCs (and `apply_matter_document` the one storage object, as you, removed again if the row is refused; `apply_file_plans` the staged PDF into Drive, v2.6185), and `mint_twin_setup_code`, the one verb outside that grammar, which POSTs `twin-setup` and returns a code, never a key (v2.6187). An `apply_` whose plan no longer matches, or was already applied, writes nothing and says so; a `view_as` of any write verb is refused before the target is even looked up; a training-mode (`read_only`) dev is refused by the database.
- **Names not in the catalog**, and five credential tables that are never read — directly or through an embed (`DENIED_TABLES` in `_shared/devMcpDoor.ts`).
- **Secrets** — any key named `token`, `secret`, `password`, `api_key`, `hash` (whole or as a `_suffix`) is redacted from every reply at any depth, and cannot be filtered on. An agent's transcript is not a place for a portal token.
- **Known limit** — redaction is by key name. A value that *contains* a secret under another name (a portal URL with its token in the path) comes back as the app shows it to you; you are reading as yourself.
- **Oversized asks** — a request over 6,000 characters as a URL; a reply over 80,000 characters is cut, and says so.

## The call log

`dev_mcp_calls`: one row per call — who, verb, the RPC or table named, args (a document's `content_base64` as its length only), outcome, rows, milliseconds — and, since v2.5899, one `reveal_key` row per **Copy** on Settings, written by `dev_mcp_reveal_key` itself. Devs read it. It is also the evidence for which composites are worth building next: a question asked the long way, often, earns a verb.

## Extending it

Kernel first: what a verb may name and how it becomes a GET is pure code in `supabase/functions/_shared/devMcpDoor.ts`; the named verbs are `_shared/devMcpComposites.ts`, written against an injected `Reader` (tests in `src/lib/devMcp/` — their fake reader enforces the generated catalog and the door's rules, so a composite that names a column the table does not have fails in CI, not live). A new composite earns its place from the call log, and its numbers come from a kernel the screen already uses — lift that kernel into `_shared/` first (a move, its own PR). After `npm run gen-types:linked`, run `node scripts/build-dev-mcp-catalog.mjs` (CI fails on a stale catalog) and redeploy `dev-mcp`. The JSON-RPC shell is `_shared/mcpJsonRpc.ts`; the public route is one line in `scripts/cloudflare/mcp-router.worker.js`.
