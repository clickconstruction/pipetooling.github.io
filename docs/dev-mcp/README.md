## The idea

`https://mcp.clicktooling.com/dev` reads the app **as the dev whose key it is**. The function resolves the key to a person, mints that person's own session, and calls the app's own API with it — **GET only**. PostgREST runs GET in a read-only transaction, so the database refuses a write whatever an RPC is named; RLS and every `auth.uid()` role check apply exactly as on the screen. The service role is used for three things: resolving the key, minting the session, writing the call log.

It replaces two habits: read-only REST probes through a signed-in browser pane, and raw SQL through the Supabase MCP.

**Writes are a second path, not a loosening of the first** (v2.3722 / 0.4.0; the narrative v2.4814 / 0.5.0; a matter's planned steps v2.5800 / 0.6.0; a document on its Evidence tab v2.6004 / 0.7.0; a sworn statement drafted onto its Timeline v2.6244 / 0.13.0; a plan set or a paper on a plan part v2.6317 / 0.14.0; Materials on site's presses v2.6367 / 0.16.0; a piece of evidence on a person's HR file v2.6426 / 0.18.0; clock sessions v2.6437 / 0.19.0; a signed hours statement made, sent and filed on a matter v2.6414 / 0.20.0; a waiting field report filed or dismissed v2.6430 / 0.21.0; a teammate's license added or its date changed v2.6475 / 0.24.0; a job as the New Job form makes it v2.6790 / 0.49.0; a teammate's account, login and password reset v2.6792 / 0.50.0; submittal rows and the order log v2.6804 / 0.51.0; a job changed v2.6793 / 0.53.0; a note on a job or a bid v2.6822 / 0.54.0; a bill made and handed over v2.6794 / 0.55.0; the Collections flag and the contract's end v2.6795 / 0.56.0; a whole job's Materials on site moved to another job v2.6808 / 0.57.0; the review of theme marks v2.6844 / 0.59.0). ## Connect

Settings → Your account → **Dev MCP keys** → *Issue a key* (deep link `/settings#settings-dev-mcp-keys`) (one per machine; `ptd_…`). Since v2.5899 a key is kept in Vault as well as hashed, so **Copy** on a live row shows it again (your own keys only, behind a confirm, one `dev_mcp_calls` row with `verb reveal_key` per copy; a revoke deletes the secret); a key issued before 2026-10-26 is hash-only and cannot be copied — issue a new one. The card's **Copy setup command** puts `export PT_DEV_MCP_TOKEN='ptd_…'` in your shell profile and the same key under `env` in `~/.claude/settings.json` (v2.6123: the desktop app never reads the profile, so a session it starts had no key and every call answered *Unknown or revoked dev key* while the connector read as connected); `.mcp.json` already registers the `dev-mcp` connector with that variable. MCP servers connect at session start — a session launched without the variable cannot repair the connector mid-flight, and a reconnect in `/mcp` does not either. First call: `whoami`.

- **Writes** — by the database (`25006`, read-only transaction), not by a list in the function — except the seventy-seven `plan_` / `apply_` / `revert_` verbs above — forty-seven POST only their twenty named RPCs (`dev_theme_review_write` the kept and removed stamps on a theme mark, as the dev, v2.6844; `dev_person_doc_write` the summary or narrative row, as the dev, v2.6608; `dev_on_site_write` as you, under your own RLS; `dev_on_site_move_job` a whole job's on-site rows onto another job, v2.6808; `apply_hours_statement` with `send` also calls `hours-statement-signing` and `send-contract-for-signature` as you, the two the window calls, v2.6414; `apply_person_evidence` then asks `hr-evidence-drive` for the record, as the panel does, v2.6426; `apply_license` sends a license inside 30 days through `notify-dispatch-request`, as the Licenses tab does, v2.6475), the two report verbs (v2.6430) the HR queue's own `file_person_report` / `dismiss_person_report` after the server's read of the report, the two person-matter verbs (v2.6582) the HR file's own `legal_person_matter_open` after the server's read of the person and of any matter standing on them, and the four plan-part verbs (v2.6317) write the rows the job window's Plans section writes (`plan_sets`, `plan_parts`, a lane's request) as you under the same RLS, since no RPC exists for them, as the four submittal verbs (v2.6804) write the rows Bids → Submittals writes (`bid_submittals`, `bid_submittal_items`, `bid_procurement_items`) (and `apply_matter_document` the one storage object, as you, removed again if the row is refused; `apply_person_evidence` its files into `hr-files` the same way, v2.6426; `apply_file_plans` the staged PDF into Drive, v2.6185), and `mint_twin_setup_code`, the one verb outside that grammar, which POSTs `twin-setup` and returns a code, never a key (v2.6187). An `apply_` whose plan no longer matches, or was already applied, writes nothing and says so; a `view_as` of any write verb is refused before the target is even looked up; a training-mode (`read_only`) dev is refused by the database.
- **Names not in the catalog**, and five credential tables that are never read — directly or through an embed (`DENIED_TABLES` in `_shared/devMcpDoor.ts`).
- **Secrets** — any key named `token`, `secret`, `password`, `api_key`, `hash` (whole or as a `_suffix`) is redacted from every reply at any depth, and cannot be filtered on. An agent's transcript is not a place for a portal token.
- **Known limit** — redaction is by key name. A value that *contains* a secret under another name (a portal URL with its token in the path) comes back as the app shows it to you; you are reading as yourself.
- **Oversized asks** — a request over 6,000 characters as a URL; a reply over 80,000 characters is cut, and says so (a file off a mail is never cut: `read_mail_file` hands its bytes over in pieces, and `read_mail_file_text` its words).

## The mail-search skill

A Claude Code session in this repo has `/mail-search` (v2.6568, `.claude/skills/mail-search/SKILL.md`): the verbs above as a working method — the narrowest query first, read a hit only when the snippet does not settle it, say where a file goes before the plan, file once. ## The call log

`dev_mcp_calls`: one row per call — who, verb, the RPC or table named, args (a document's `content_base64` as its length only), outcome, rows, milliseconds — and, since v2.5899, one `reveal_key` row per **Copy** on Settings, written by `dev_mcp_reveal_key` itself. Devs read it. It is also the evidence for which composites are worth building next: a question asked the long way, often, earns a verb.

## Extending it

Kernel first: what a verb may name and how it becomes a GET is pure code in `supabase/functions/_shared/devMcpDoor.ts`; the named verbs are `_shared/devMcpComposites.ts`, written against an injected `Reader` (tests in `src/lib/devMcp/` — their fake reader enforces the generated catalog and the door's rules, so a composite that names a column the table does not have fails in CI, not live). A new composite earns its place from the call log, and its numbers come from a kernel the screen already uses — lift that kernel into `_shared/` first (a move, its own PR). After `npm run gen-types:linked`, run `node scripts/build-dev-mcp-catalog.mjs` (CI fails on a stale catalog) and redeploy `dev-mcp`. The JSON-RPC shell is `_shared/mcpJsonRpc.ts`; the public route is one line in `scripts/cloudflare/mcp-router.worker.js`.
