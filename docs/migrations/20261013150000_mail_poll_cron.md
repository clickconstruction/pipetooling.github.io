# 20261013150000_mail_poll_cron.sql (2026-10-13, v2.5385 — the Docsmit train PR 6a)

The hourly read-back's cron and the switches' home (`docs/DOCSMIT_LIEN_RUN_PLAN.md`, *Delivery drives the desk* and *Managed from Developer settings*).

## What it does

1. **`app_settings`** gains one seeded row, `docsmit_paused = 'false'` (`ON CONFLICT DO NOTHING`). The other `docsmit_*` keys are not seeded: `src/lib/mail/docsmitSettings.ts` fills every default, so the parser stays the one source of truth.
2. **Two policies** on `app_settings`: a dev (`public.is_dev()`) may update and insert any `docsmit_*` row from the app, the shape of `gmail_sync_on_v1`'s policy in `20261013080000`. Reads already fall under the baseline's authenticated read policy. Secrets never live here.
3. **The cron row `mail-poll`**, at seventeen past every hour: `POST /functions/v1/mail-poll` with Vault's `PROJECT_URL` and `CRON_SECRET`, as `gmail-sync`'s cron is scheduled. It fires only once a dev has set the connection up (a `docsmit_env` row exists) and while `docsmit_paused` is not `'true'`, so nothing calls a function that is not deployed, and the pause switch holds the poll as it holds the sends. The row is unscheduled and re-scheduled by name, so re-running is safe.

No table, so no fences. Idempotent. Apply with `supabase db push` after the PR merges; the function itself (`mail-poll`, v2.5381) must be deployed before the switch is set, or each hour logs a 404.
