# 20261101130407_legal_matter_documents_source_message.sql (2026-11-01, v2.6276)

The Legal desk's Evidence door, **From the job's messages…** (punch list #230 PR 5, `to-dos/messages-my-email/README.md`, section 4): the office ticks an email conversation on a collections account's jobs and the app puts each email of it on the matter as an `.eml` through `addLegalMatterDocument`. The desk pulls; a tag in Messages never writes to a matter. This migration gives a document the Messages line it was made from.

- **`legal_matter_documents.source_message_id`** (`uuid`, null on every document the upload, the statement's filing or the dev seat writes) — the `messages` row an `.eml` was made from. The door reads it to hold an email already on the matter, and the Evidence row's ⋯ opens **The line in Messages** (`/messages?thread=<contact>&at=<line>`) through it. Foreign key `legal_matter_documents_source_message_id_fkey` to `messages(id)` `ON DELETE SET NULL`: an untag on My email deletes the person's lines, and the matter keeps its own copy with the link gone.
- **`legal_matter_documents_source_message_idx`**, partial on `source_message_id IS NOT NULL`: the door's read, and the lookup the foreign key's `ON DELETE` makes when a line goes.
- **`legal_matter_documents_one_per_line`**, unique on `(matter_id, source_message_id)` where the line is set and the document is live: two people pressing at once put an email once, and the second press names it as already on the matter (`23505`, worded by the io). A removed document frees its line to go on again.
- No policy and no grant: the office roles already insert and update the table under `legal_office_can_read()` with table-wide grants, which cover a new column. No table is created, so no fence is owed. The firm's portal never sees the column: `MATTER_DOCUMENT_COUNSEL_COLUMNS` does not name it.
- The column and its index go first, on the small table; the foreign key is added `NOT VALID` inside a `duplicate_object` guard and validated last, so the hot `messages` table is held for the shortest stretch before the commit. Every row is null when it is validated.

Tried before the PR on a throwaway local Postgres 15 with stubs for `messages`, `legal_matters` and `legal_matter_documents`: the file applied twice in a row (the second a no-op), the key came out validated, a document's line deleted set it null and kept the document, a line id that is not a line was refused, a second live document of one line on one matter was refused while the same line on another matter and a removed copy's line went on.

Apply with `supabase db push` (`scripts/db-push.sh`) right after the PR merges, from the main checkout. The client reads and writes the new column: until the push, the Evidence list reads as before (`listLegalMatterDocuments` reads again without the column on `42703` or `PGRST200`) and the door's window says it waits for the push instead of listing. `check:calls-ahead` does not see a new column, so the PR carries the *push right after the merge* label by hand. Regenerate `src/types/database.ts` in its own `chore(types)` PR after the push.
