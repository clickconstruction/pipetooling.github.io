# 20261107150000_job_budget_award.sql (2026-11-07, v2.6646)

**What it does**: every project leaves award with one hours baseline, frozen, and its source (punch list #234 PR 1a). Two changes to `job_budgets` (v2.3297) and two functions.

- `job_budgets.kind` now allows `book` beside `bid` and `typed` (`job_budgets_kind_check` dropped and re-added): the labor book's assumed hours (hours per $1k from similar projects × the price) as a row of its own, so the Costs strip, the Pipeline's burning card and the superintendent's line read a number marked a guess instead of nothing. A book row is labor only; materials, subs and other burn against the assumption, and the job's bid link stays on it.
- `job_budgets.awarded_at`, `awarded_by`, `awarded_kind` (`bid` | `book` | `typed`, `job_budgets_awarded_kind_check`), `awarded_labor_hours`, `awarded_labor_usd`, `awarded_materials_usd`, `awarded_total_direct_usd`, `awarded_detail jsonb` — the award snapshot: what the job left award with, who froze it and when. Written once and never updated: *Refresh from bid* moves the live columns and the score (PR 4) reads these.
- `set_book_job_budget(p_job_id, p_labor_hours, p_labor_rate, p_book jsonb)` — the book path, as `set_typed_job_budget` is the typed one. `p_book` is the reading (`hours_per_thousand`, `n`, `price_usd`, `scope`) and lands under `completeness.book`. Refuses zero hours.
- `award_job_baseline(p_job_id, p_source, p_bid_id, p_labor_hours, p_labor_rate, p_book, p_note)` — the one press: writes the live row by its source (`bid` → `snapshot_job_budget_from_bid`, `book` → `set_book_job_budget`, `typed` → `set_typed_job_budget` with no materials, subs or other), then stamps the `awarded_*` columns where `awarded_at IS NULL`. Both `SECURITY INVOKER` over `can_write_job_budget` (dev · assistant · master technician, on a job they can read).

**Tables**: none created, so no fence is owed. **RLS**: unchanged — the columns ride the row's policies. Idempotent: `ADD COLUMN IF NOT EXISTS`, the constraints `DROP IF EXISTS` then `ADD`, `CREATE OR REPLACE` for the functions.

**Why a kind and not a flag**: `resolveJobBudget` already ranks kinds (`bid` · `typed` · the no-row assumption); `book` slots in as a footing with hours and a glyph (≈) so every reader that switches on the kind names it, and a reader built before this (an older client) treats the unknown kind as the assumption, which is what a guess should read as.

**Apply**: `supabase db push` from a clean checkout of `main` right after this merges, before the Pages deploy finishes — the New Job form calls `award_job_baseline` the moment a project is created, and PostgREST answers a missing function with a refusal (the form says the job saved and the baseline did not). Then `npm run gen-types` in a follow-up, so `JobBudgetRow` carries the columns (the client reads them through a cast until then).

**Check**: `select column_name from information_schema.columns where table_name = 'job_budgets' and column_name like 'awarded_%'` reads eight rows; `select pg_get_constraintdef(oid) from pg_constraint where conname = 'job_budgets_kind_check'` names `book`; `select proname from pg_proc where proname in ('set_book_job_budget', 'award_job_baseline')` reads two.
