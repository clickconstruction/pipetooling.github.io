## `bid_changes`

One row per insert, real change or delete of a row on the tables that hold what people type on a bid: `id` (bigint identity — every row of one request shares `changed_at`, so the id is the order), `bid_id`, `bid_version_id`, `table_name`, `record_id`, `count_row_id`, `op` (`insert` · `update` · `delete`), `changed` (the columns this row records), `old_values` / `new_values` (those columns only, jsonb), `label`, `changed_by` (`auth.uid()`; null for the service role, cron and the robots), `changed_at`, and `action` / `by_app`, null until PR 1b reads the `x-bid-action` request tag. One index, `(bid_id, id)`.

**`bid_id` has no foreign key, on purpose.** History outlives the archive's 90-day purge: when a bid is deleted its rows stay, readable by a dev (nobody else can read the bid any more), and a bid put back from *Recently deleted* keeps its id, so its history comes back with it. A key with `ON DELETE CASCADE` would erase the history with the bid; a plain key would refuse the delete. `changed_by` has no key either, like the archive's `deleted_by`: a removed user's changes keep their author.

RLS: **select** `is_dev() OR EXISTS (SELECT 1 FROM bids b WHERE b.id = bid_changes.bid_id)`. The subquery runs under the caller's own policies on `bids` (the office roles, `primary_scope_bids`), so history is never wider than the bid: an estimator reads every bid's, a primary only the bids they are on, a superintendent none. **No write policy**; `INSERT`, `UPDATE`, `DELETE` and `TRUNCATE` are revoked from `authenticated` and everything from `anon`. Not in the realtime publication.

The table's setup sits behind one existence check: once the triggers are live every bid save writes here, and a re-run's `CREATE INDEX IF NOT EXISTS` (SHARE) or `ENABLE ROW LEVEL SECURITY` / `CREATE POLICY` (ACCESS EXCLUSIVE) would hold every save behind it. From now on, build an index on `bid_changes` `CONCURRENTLY` and keep any other DDL on it under a lock timeout.

**Purge**: pg_cron `purge-bid-changes`, daily at 09:20 UTC, deletes rows older than three years. The oldest rows have the lowest ids, so the cutoff is found by walking the primary key from the bottom; the write path carries no index on `changed_at`.

## What `record_bid_change()` writes

`AFTER INSERT OR UPDATE OR DELETE … FOR EACH ROW`, `SECURITY DEFINER`, `SET search_path = public` with every table schema-qualified. The contract-text history's pattern (`20260928050129`): the whole body sits in `BEGIN … EXCEPTION WHEN OTHERS THEN RAISE WARNING`, so a ledger failure never fails the save.

- **Update**: the columns whose value changed (`IS DISTINCT FROM` on the jsonb, so `10300` → `10300.00` is no change). Ids, `created_at`, `updated_at`, `updated_by`, `applied_at`, `applied_by` and the two ordering columns (`sequence_order`, `sort_order`) never count: a reorder or a same-value save writes nothing. **Insert / delete**: every non-empty column, so a removed row can be read back after the archive has purged it.
- **`bids`**: only the columns `bid_changes_bid_columns()` lists (below), on every op. The trigger's `UPDATE OF` is the same list, so robot, follow-up and board writes to `bids` never call the function.
- **bid_id**: the row's own (`bids`: its id). The six `cost_estimate_*_rows` tables reach it through `cost_estimates`.
- **count_row_id**: a count row's own id; prices, custom costs, assignments, part lines and stage splits carry theirs.
- **label** (the row's name at write time): count row → its fixture · price, custom cost (· its house), assignment, stage split → its count row's fixture · part line → its part's name (none for an assembly line) · labor row → its fixture · direct-cost row → its note · SOV line → its label · payment schedule row → its timing · version → its name · `bids`, `cost_estimates` → none (one row can carry several columns; the reader words each).
- **bid_version_id**: count rows and part lines their own; what hangs on a count row, its count row's; a version its own id. Null for what every version shares (labor, direct costs, SOV, schedule, the bid).

**Cascades.** A child's AFTER trigger runs after its parent row is gone (the parent's own AFTER trigger fires first; the cascade's events queue behind it), so it cannot read the parent:

- a price, custom cost, assignment, part line or split removed with its count row (a fixture removed, Clear all, a version deleted) takes its fixture and version from the archive's `BEFORE DELETE` snapshot of the count row (`deleted_records_archive`, indexed on `table_name, record_id`);
- a labor or direct-cost row removed with its cost estimate while the bid lives finds the bid the same way, from the snapshot of the cost estimate. A row is never written without its bid: no bid found, nothing written;
- when the **whole bid** is deleted its rows are not recorded one by one: the bid's own delete row stands for them (its kept columns as they were), and the archive keeps the bundle. Every non-`bids` row checks that its bid still exists.

## The two lists

- `bid_changes_tables()` — the seventeen tables, in trigger-creation order (least written first, `bids` last): `bid_payment_schedule_rows`, `bid_sov_lines`, the five direct-cost row tables, `bid_count_row_custom_costs`, `bid_takeoff_stage_splits`, `bid_versions`, `cost_estimates`, `cost_estimate_labor_rows`, `bid_pricing_assignments`, `bid_count_row_custom_prices`, `bids_takeoff_rough_part_lines`, `bids_count_rows`, `bids`. `bids_takeoff_template_mappings` is not in it: it is By Stage's, and nothing has written it since v2.4396.
- `bid_changes_bid_columns()` — 48 `bids` columns: everything Edit Bid saves (`bidFormPayload.ts`, less `robot_opt_out` and the creation-only `last_contact`), the picks Pricing, Cover Letter and the schedule of values write (the three selected books, the selected version, `alternate_group_tags`, `cover_letter_alt_texts`, the four `sov_*`, the three `include_*`, `bid_to_marked_plans`), and `outcome_at`. Not the stamps (acknowledgements, attestations, reviews, follow-ups, the board, submittals-not-needed), the robot and twin columns, `bid_tab_*`, `materials_model`, `count_tooling_link` or `updated_at`. History cannot be filled in later, so it keeps wide and the reader chooses.

`src/lib/bids/bidChangesCapture.test.ts` reads the newest definition of each and fails CI when a table or a column is not in the generated types. It also pins every column the function reads by name (each table's `id`, `bid_id` or `cost_estimate_id`, `count_row_id`, `fixture`, `bid_version_id`, `part_id`, `house_name`, `label`, `timing`, `name`, `note`, and the parents' and the archive's columns) to the table it reads it from. A rename in a later migration fails CI instead of silently turning capture off. It also checks that every table the function branches on is one of the seventeen. To change either, redefine the function in a new migration; a change to the column list also replaces the `bids` trigger there (`CREATE OR REPLACE TRIGGER`, the statement `20261006191000` builds).

## House rules

Opens with `SET lock_timeout = '3s'`; ends with `apply_read_only_write_blocks()` and `apply_read_only_stmt_blocks()`, which skip tables already covered and so touch `bid_changes` alone. **Not** `apply_digital_twin_write_blocks()`: `bid_changes` has no client write for a twin to be fenced from, and that function drops and recreates three policies on every RLS table in `public` (`CREATE POLICY` takes ACCESS EXCLUSIVE, held to commit). Nothing requires it: no test, script, CI check or entry doc names it.

## What it costs

Measured on a scratch Postgres 15 with stub copies of the seventeen tables, their keys and the archive trigger (a laptop; ratios matter more than the numbers):

| | no ledger | ledger |
|---|---|---|
| 1,000 prices typed, one `UPDATE` each | 30 ms | 110–123 ms |
| 300 count rows imported, one statement each | 8 ms | 30–36 ms |
| a 300-count-row bid copied (`duplicate_bid_to_service_type`'s shape) | 33–36 ms | 228–274 ms, 2,103 ledger rows |
| Clear all (300 count rows + 1,500 cascaded) | 97–113 ms | 292–302 ms, 1,800 ledger rows |
| a whole bid deleted | 93–96 ms | 173–193 ms, 1 ledger row |

About 0.1 ms per row written, more on a cascade (two lookups for a removed parent).

### Row trigger or statement triggers (settled; measured, not argued)

Each ledger row is one subtransaction (the error guard). Past 64 in one transaction, other sessions' snapshots must consult `pg_subtrans`. The alternative kept the row trigger for updates (one row per request, and `bids` needs `UPDATE OF`). It used statement triggers with transition tables for inserts and deletes: one subtransaction per statement, and three triggers per table, since Postgres refuses transition tables on a trigger with more than one event. Same stub, two rounds each:

| | no ledger | row trigger (shipped) | statement triggers |
|---|---|---|---|
| a 300-count-row bid copied | 33 ms · 0 subtransactions | 228–274 ms · 2,103 | 305–458 ms · 308 |
| Clear all (300 + 1,500 cascaded) | ~105 ms · 1,500 (the archive's own) | ~300 ms · 3,300 | 137–168 ms · 1,505 |
| 300 count rows imported, one statement each | 8 ms | 30–36 ms | 223–238 ms |
| 100 fixtures removed one at a time | 30 ms | ~100 ms | 403–437 ms |

- **Cascades.** A foreign-key cascade fires a statement trigger once per table, not once per parent row (tested), which is where statement triggers win.
- **The copy.** It inserts count rows one statement at a time, so statement triggers still pass 64.
- **Single-row saves.** Statement triggers are 3–7 times slower on every single-row statement, the import and each one-at-a-time save, which is most of the traffic.
- **Is the cliff real?** Eight readers read the newest copy while copies looped every 0.4 s, with the same ledger work and the error guard on (about 2,100 subtransactions a copy) or off (none). Read throughput was within noise: 3,461 vs 3,293 and 3,816 vs 3,517 transactions/s; with a long transaction holding the snapshot back, 2,842 vs 3,024 and 3,948 vs 3,833. The measurable cost is transaction ids, about 2,100 per copy.

The row trigger stays.
