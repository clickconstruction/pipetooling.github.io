# 20261013200000_sub_flow.sql (2026-10-12, v2.5420)

The sub's flow (residential R8 · 12, PR 1 of 3, `to-dos/gc-mode/messages/RESIDENTIAL_BUILD_PLAN.md` on `spike/gc-mode`). It follows the residential flow ([20261013170000_residential_flow](20261013170000_residential_flow.md)), which already allows the `sub` kind. A sub's job is one labor job, the sub sheet (`people_labor_jobs`). Every step reads what the work order (`step_commitments`) and the sheet already keep. No table or column is added, and no grant changes. The two columns the sheet lacks, `on_site_at` and `done_at`, come with PR 2's own migration.

## What it does

1. **`flow_fact_ids()`** is re-created with the six sub facts after `review_asked`, as `src/lib/flows/facts.ts` lists them: `sub_asked`, `sub_said_yes`, `sub_declined`, `sub_on_site`, `sub_done`, `sub_paid`. The flow steps' check (`flow_facts_ok`) then lets a step pick them. `flow_paper_ids()` and `flows_kind_known` stay as the residential flow's migration left them.
2. **`flows_seed()`** is re-created with the sub flow, *Sub flow*, and its five steps in one Per job lane: Asked, Said yes, On site, Done, Paid.
   - Said yes is a fork. A yes or a no finishes it, and their no ends the lane.
   - No step carries a reminder.
3. **`SELECT public.flows_seed();`** runs it. On prod, every other kind already has its flow, and the seed adds a step only for a kind with no flow. So it adds the sub flow and its five steps, and changes nothing else. A second run adds nothing.

`src/lib/flows/flowsSql.test.ts` reads each function from the newest migration that defines it, and holds them to the code.
