# 20261112220000_task_places.sql (2026-11-12, v2.7058)

A task can carry a place (punch list #328, PR 1 of 8). A task is words, a day and people. It cannot say where the work is, and on a large property the street address would not help: the task is at the pump house, the north gate, a corner of a field.

## What it does

Six nullable columns on `checklist_items`, the task as written, so a repeating task keeps its place every day:

1. **`place_name text`**: what a person reads and presses, *Pump house*. A place used before is offered again by this name.
2. **`place_lat`, `place_lng double precision`**: the point.
3. **`place_accuracy_m integer`**: the phone's margin in metres when the place was set from where the giver stood. Null when the map was dragged.
4. **`place_set_by uuid`** (`users.id`, set null when the user goes) and **`place_set_at timestamptz`**: who set it and when. The doer reads them, so a place that has gone stale can be judged.

Three checks hold the place whole:

- `checklist_items_place_point_check`: both numbers or neither, latitude within 90 and longitude within 180. It names both numbers `IS NOT NULL`, since a check passes on an unknown answer and a range test on a null is unknown.
- `checklist_items_place_whole_check`: a name, a margin, a setter or a day never stands without a point.
- `checklist_items_place_accuracy_check`: the margin is not negative.

No row is changed. No default is stored, so every task today reads six nulls.

## Who may do what

The row's own policies, unchanged. The office, the task's maker and its assignees read the place with the task. The office or its maker writes it. No new table, so no fence calls.

## Locks

`ADD COLUMN` with no default does not rewrite the table. The foreign key takes a brief lock on `users`, and each check scans `checklist_items` (about 150 rows). `SET lock_timeout = '3s'` makes a busy moment fail fast.
