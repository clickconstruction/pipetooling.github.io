# 20261109160000 — on_site_move_job (v2.6808)

Materials on site (punch list #209): everything a job holds on site moved to another job, every container keeping its id and the code printed on its label. A site's count had been recorded on the phone under the wrong job, and nothing could move it: no screen, RPC or dev-seat verb changed a row's job, the ledger takes no update under RLS, and the only code that carried these rows sat inside the whole-job combine, which deletes the source job. Five functions and two triggers; no table, so no fence call is owed.

1. **`on_site_carry_job(p_from uuid, p_to uuid)` → jsonb**: the on-site block of `migrate_job_ledger_costs_and_delete` ([`20261103054522`](./20261103054522_combine_moves_every_row.md)) lifted out whole, so the rules live once. A place the target already has under the same name takes the source's containers and moves, and the source's place goes; the source's Unsorted row folds into the target's with its movements, box moves and photos; a live cage or box whose label the target already holds keeps its row, since its code is printed on its label, and takes a numbered label (`A1 (2)`); then `job_places`, `job_containers`, `job_material_movements` and `job_box_photos` take the target's `job_id`. `job_container_moves` has no `job_id` and follows its container. It returns what it did: the places, containers (and the retired among them), ledger rows, box moves and photos moved, the places that became one, the Unsorted fold and every label renumbered with its code. Three things differ from the combine's own copy, each on an edge it handled badly or not at all: the loops read in a fixed order, so the report is the same on every run; a numbered label keeps counting past `(8)` and shortens its stem to fit the stencil's 24 characters, where the combine stopped and then failed on the live-label index; and Unsorted folds only into the target's own Unsorted row (the kind, not the word), so a cage someone stencilled UNSORTED stays a cage. `SECURITY INVOKER` with no gate of its own, and `EXECUTE` revoked from `PUBLIC`, `anon` and `authenticated`: its two callers are definers that gate first.
2. **`migrate_job_ledger_costs_and_delete`**: [`20261104130000`](./20261104130000_combine_moves_soft_job_links.md)'s body with that block replaced by `PERFORM public.on_site_carry_job(p_from, p_to);` and the two declarations only the block used (`v_label`, `v_n`) gone. Nothing else changes; the signature and the reply stand.
3. **`on_site_row_takes_container_job()`** with `BEFORE INSERT` triggers on `job_material_movements` and `job_box_photos`: a new row takes the job of the container it names (`to_container_id`, else `from_container_id`; a photo's `container_id`). `SECURITY DEFINER`, so the lookup sees a box the caller cannot; the table's INSERT policy, `on_site_can_touch_job(job_id)`, then judges the row on that job. Before this a row could name one job and a box on another, where no screen read it. It matters after a move, since the source job still stands: a phone that had it open keeps sending presses under the old id, and each now lands with its box, or is refused in the open for someone who is not on the new job's team.
4. **`on_site_job_counts(p_job_id uuid)` → jsonb**: a job's places, containers, retired containers, ledger rows, box moves and photos counted, with `lines_on_hand` and `parts_on_hand` from `on_site_job_summary`. `SECURITY INVOKER`, `STABLE`, granted to `authenticated`: the tables' own RLS decides what the caller counts, so the seat's `call_read` can read it for either job.
5. **`dev_on_site_move_job(p jsonb, p_dry_run boolean DEFAULT true)` → jsonb**: the dev seat's door, `p = { from_job, to_job }`. **`SECURITY DEFINER`**, unlike `dev_on_site_write`: the ledger has no UPDATE policy for anyone, so no caller's own RLS could make this write. Gated `auth.uid()` + `is_dev()`, then a training account (`is_read_only()`) and a digital twin (`is_digital_twin()`) are refused in words. It refuses two ids that are not ids, the same job twice, a job that does not exist, and a source with no place, container, ledger row or photo. Then, inside one block: `on_site_carry_job`, both jobs counted again, and a check that the rows add up (the source empty; the target holding both jobs' ledger rows, box moves and photos, their containers less a folded Unsorted row, their places less the ones that became one), which raises and writes nothing when they do not. A note goes on each job's notes (`jobs_ledger_thread_notes`) in the dev's name, as a combine leaves one. With `p_dry_run` it raises its own state after the reply is built, so every write unwinds and the reply survives.
   - The reply: `{ ok, dry_run, from { id, label, name }, to { … }, by, words, moved { places, containers, retired_containers, movements, container_moves, photos }, places_merged [{ name, containers }], unsorted_folded { code, into_code, movements, container_moves, photos } | null, labels_renamed [{ code, kind, from, to }], photos { rows, in_drive, waiting, words }, on_hand { holds, words }, before { from, to }, after { from, to }, notes { from, to }, next }`. Each job is named as the app names it (`JP972`), by `dev_on_site_write`'s rule. It carries no clock and no made id, so the same plan hashes the same until a row on either job changes.
   - **The parts on hand**: `on_hand.holds` says whether the target's parts after are both jobs' parts before. They can read differently only where a count now resets a line that rows from the other job fed, which is two Unsorted piles that became one. The reply says so in words and nothing is refused for it.
   - **The photos' files**: a row moves with its box. A photo still waiting in the `box-photos` bucket keeps its path, and the sweep files it by the row's job, so it lands in the new job's folder. A file already in Drive stays in the first job's photo folder; `photos.in_drive` counts them and `photos.words` says so. Moving the files is punch list #297.

Additive and idempotent. `CREATE OR REPLACE TRIGGER` takes `SHARE ROW EXCLUSIVE` on `job_material_movements` and `job_box_photos` for a moment, as `20261103143000` did on `job_containers`; the file starts with `SET lock_timeout = '3s'`.
