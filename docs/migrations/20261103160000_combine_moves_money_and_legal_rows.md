# 20261103160000_combine_moves_money_and_legal_rows.sql (2026-11-03, a combine moves the money and legal rows too, punch list #252 PR 2, v2.6458)

20261103054522 (v2.6423) restated `migrate_job_ledger_costs_and_delete` so every row that is not money or legal moves or merges instead of going with the source job's delete, and left fifteen tables on today's cascade until the owner's word. The owner said build on 2026-11-03, with the rules the card `to-dos/combine-rows.md` proposed. Bills and payments keep the billing guard: a source with either is refused unless `p_allow_billed`, where they go with the source by design.

- **`job_pay_applications_stamp()`**: 20261010002000's body with one gate. A write that changes `job_id` and nothing else keeps `updated_by` and `updated_at` (and `deleted_by`), so a combine does not re-stamp the application as the combiner's; every other write stamps as before.
- **`migrate_job_ledger_costs_and_delete`**: 20261103054522's body with two refusals after the work-order one and the money and legal rows after the one-per-job rows, each with its rule in the comment above it. **Refusals**: `agreement_collision` (*Both jobs hold an open agreement. Void one of them, then combine.*) when both jobs hold a `job_contracts` row in `draft` or `sent` (`job_contracts_one_live_per_job_idx`; a sent agreement's link is in the customer's hands); `pay_application_collision` (*Both jobs hold pay applications. Delete one job's applications, then combine.*) when both hold a live `job_pay_applications` row (`job_pay_applications_job_number_live_uniq`; the numbers are on paper the GC holds). **Plain moves**: `jobs_ledger_payment_events` (`from_job_id` and `to_job_id` that name the source), `job_payment_promises`, `job_payment_chase_touches`, `job_lien_filings`, `job_lien_releases` (a bid's waiver names no job and is not touched), `job_demand_letters`, `job_contracts`, `job_pay_applications`. **Merges**: `job_promised_pay_dates` (one per job; the later `marked_at` stands, and the move keeps the date so `job_promised_pay_dates_log_promise` writes no second promise), `job_lien_claim_corrections` (the target's stands, else the source's moves), `legal_matter_jobs` (the matter links to the target once), `job_lien_desk_items` (a live item, not voided and not sent or missed, of a kind the target holds live comes over with `voided_at` set, so the desk still reads it; the rest move). The activity triggers on releases and agreements fire on state changes only, so a move writes no event.

Additive and idempotent; no table is created, so no fence call. No lock beyond `CREATE OR REPLACE FUNCTION`. The generated types do not change: the trigger function is not callable and the combine's signature stands.

Apply order: right after the merge. The client changes nothing but words, so this is harmless on either side of the Pages deploy, but it restates a function the client calls, so `check:calls-ahead` labels the PR *push right after the merge* and the deploy holds until the push.

The bed: `scripts/pgtest-combine-rows.sh` starts from the migrated copy, applies this file a second time (which must change nothing), and plays `supabase/tests/combine_rows/20_scenario.sql`: the first combine now also moves a promised date and a claim correction onto a target with none; the second combine is refused three times in turn (a work order, an agreement, a pay application on both jobs), each time moving nothing, and then moves a payment's trace, a promise, a chase touch, lien paper, desk items (one voided by the rule, one sent, one live), a legal matter's links, an agreement and a pay application whose stamp stands, and keeps the later promised date and the target's claim correction. Beds run only in CI; read the `ok:` lines in the job log.
