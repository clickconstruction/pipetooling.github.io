# 20261121193000_punch_list_ticks.sql (2026-11-21, v2.8196)

`punch_list_ticks`: one person's "I am working on this" tick on one card of the app's `/punch-list` board. Taunya's ask of 2026-11-21. The table ships alone, ahead of the checkbox that reads it, so the merge holds no deploy.

## What it does

- **`punch_list_ticks`**: one row per person and card.
  - `user_id` is whose tick it is. It defaults to `auth.uid()` and goes with the account (`ON DELETE CASCADE`).
  - `card_number` is the card's `number:`, the `#16` on the page. A number is given once and never reused, so a renamed to-do file keeps its tick. The primary key is `(user_id, card_number)`.
  - `section` is the group the card was in when the person ticked it: `ready`, `close`, `gated`, `waiting` or `residual`, as the to-do's `group:` has it. The column takes any word that is not blank, so a new group needs no migration.
  - `board_version` is the newest shipped version the ticking page's build carried, `''` when it had none.
  - `ticked_at` is set by a BEFORE trigger (`punch_list_ticks_stamp`) to `now()` on every insert and update, whatever the client sends.
- **Row security.** Select, insert, update and delete each ask for `user_id = auth.uid()` and `is_master_or_dev()`, the pair `canOpenPunchList` admits to the page. Nobody reads another person's tick, a dev included. `anon` has nothing.
  Since [`20261122000500_punch_list_claims`](./20261122000500_punch_list_claims.md) the select rule is `is_master_or_dev()` alone: everyone who may open the page reads every tick, as a claim, and still writes only their own.
- **The four fences** close the file: training mode writes nothing, a twin writes nothing, an archived caller reads nothing.

## How the page uses it

- A tick is an upsert on `(user_id, card_number)`. An untick deletes the row.
- The page shows a tick only while the card's group is the row's `section`. A card that moved from one section to another shows no tick.
- The page deletes a row whose card moved or left the list, but only when its own build's newest version is past the row's `board_version`. An old copy of the page left open on a phone therefore cannot delete a tick made on a newer one. Until a newer build reads the row it is hidden, not deleted.

## Verified

A stand-in rig on the local Postgres 15, not the app's schema: a stub of what the file leans on (`users`, `auth.uid()`, `is_master_or_dev()`, the roles with the project's default rights, and no-op fences), then the file twice, then a scenario of 17 checks with made-up accounts.

- A dev ticks a card and reads it. The row takes the dev's id by itself.
- A master reads none of the dev's rows, cannot tick under the dev's id, and changes and deletes none of them. The master's own tick on the same card is a second row.
- A helper cannot tick and reads nothing.
- A second tick on one card is one row with the new section and the server's time, not the time the client sent.
- A blank section and a card number of 0 are refused.
- An untick deletes the row and leaves the other person's.
- A signed-out caller is refused the table.
- A deleted account leaves no tick.

The fences are no-ops in the rig. On prod they are read after the push.
