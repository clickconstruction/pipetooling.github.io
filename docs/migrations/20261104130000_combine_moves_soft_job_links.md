# 20261104130000_combine_moves_soft_job_links.sql (2026-11-04, a combine moves every job link the delete would have set to null and every soft pointer, punch list #252 PR 3, v2.6492)

The card `to-dos/combine-rows.md` sorted the tables a combine must carry from `ON DELETE CASCADE` keys alone (v2.6423, v2.6458, v2.6460). The docs pass of 2026-11-04 (#6998) found that the fourteen `ON DELETE SET NULL` links to `jobs_ledger` and the six plain-uuid job pointers were never sorted, so after a combine each kept the source's id and the row stood with no job on it: every text, call, email and team note tied to the source fell to the person (`messages.jobs_ledger_id`), a sub sheet read unlinked (`people_labor_jobs.job_ledger_id`), a mail piece lost its job (`mail_pieces.job_id`), while the guide said everything real moves. The sort with its reasons is in `docs/recent-features/v2.6492.md` (the card was retired on 2026-11-04 once this file was pushed).

- **`gc_projects_owner_terms_guard()`**: 20261009050000's body with one gate. A change of `billing_job_id` alone passes when `current_setting('gc.combine_write', true) = 'on'`, which the combine sets for its one statement and clears after, as `gc_link_crew_job` does with `gc.crew_job_write`; the service role still passes, and every other change of the nine terms by a person outside the money team is refused as before.
- **`migrate_job_ledger_costs_and_delete`**: 20261103170000's body with one block after the money and legal rows, inside the same subtransaction and before the source's delete. A plain move each, since none has a key that asks for a merge. **The `SET NULL` links**: `messages.jobs_ledger_id`, `mail_pieces.job_id`, `people_labor_jobs.job_ledger_id` (with `job_number` re-read from the target as `left(hcp or click number, 10)`, so every rollup that still matches by number finds the sheet; a target with no number keeps the text; a write that sets both at once is one `people_labor_jobs_link_job_ledger` leaves alone), `development_history_entries.job_id`, `file_index.jobs_ledger_id`, `bid_submittals.job_ledger_id`, `lien_owner_record_requests.seed_job_id` (and its `job_ids` array, the source rewritten in place once; the stamp trigger then reads the person combining), `person_offsets.job_id`, `partnerships.farm_job_ledger_id`, `mercury_transaction_ar_income_labels.job_id`, `team_prospect_trial_verdicts.job_ledger_id`, `gc_projects.billing_job_id` (under `gc.combine_write`), `gc_trade_packages.job_ledger_id` (under `gc.crew_job_write`), `gc_project_money.general_conditions_job_id`. **The plain-uuid pointers**: `nudge_offers.jobs_ledger_id`, `ar_stripe_cases.job_id`, `ar_unbanked_check_cases.job_id`, `customer_ratings.job_id`, `job_watcher_notices.job_id`, `schedule_block_events.job_id`. **Two cascade tables made after the card's catalog read** (punch list #254, 2026-11-03): `job_charge_adjustments.job_id`, `job_charge_statements.job_ledger_id`. **Let go on purpose**: `job_status_events.source_job_id` and the four bid tables' `migrated_from_job_id` name the job a move came from, by design, and the move to a bid deletes its job, so a combine never meets a live one. The `estimates`, `clock_sessions`, `dispatch_requests`, `estimator_requests`, `salary_work_schedule_*` and `plan_sets` links were already moved.

Additive and idempotent; no table is created, so no fence call. No lock beyond `CREATE OR REPLACE FUNCTION`. The generated types do not change: the trigger function is not callable and the combine's signature stands.

Apply order: right after the merge. The client changes nothing but words, so this is harmless on either side of the Pages deploy, but it restates a function the client calls, so `check:calls-ahead` labels the PR *push right after the merge* and the deploy holds until the push.

The bed: `scripts/pgtest-combine-rows.sh` re-applies the newest migration that creates the combine (this file) a second time, which must change nothing, and plays `supabase/tests/combine_rows/20_scenario.sql`: the second combine's source now also holds a text and a team note, a prepared text, a mail piece, a sub sheet, a History line, an indexed file, a submittal package, an owner's records request covering the source and the split job, a profit-share posting, a partnership's farm job, a deposit's Income label, a try-out verdict, a GC project's three job links, two AR cases, a rating ask, a watcher email, a schedule change, a charge adjustment and a statement of charges, and each reads on the target after the combine (the sub sheet's number text as the target's, the records request's `job_ids` with the target in the source's place), the held combine before it moving none of them, and both guard flags off at the end. Beds run only in CI; read the `ok:` lines in the job log. Run by hand on a local Postgres 15 on 2026-11-04 before the PR (pgvector stood in by a domain).
