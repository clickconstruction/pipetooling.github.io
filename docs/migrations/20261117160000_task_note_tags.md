# 20261117160000_task_note_tags.sql (2026-11-17, v2.7570)

Tagging a teammate in a task note: the ground. Punch list #375, PR 1 of six. Tagging went live on job notes as #363, and the owner asked on 2026-11-16 for the same in task notes. A task note is a `checklist_instance_events` row of kind `comment`, inserted straight from the client, and it tells nobody. This migration makes the tag a row of its own, the functions that write and read it, and the trigger that answers it. No screen calls any of it yet.

## What it makes

One table, so the four fence calls close the file. Eleven functions and one trigger.

- **`task_note_tags`**: one row a person tagged in a task note. `event_id` is the note, `instance_id` its day row and `item_id` the task, all three cascade. Then `tagged_user_id`, `tagged_name` (the name as it was written), `tagger_user_id`, `created_at`, and how it ended: `cleared_at` with `cleared_how` (`answered` or `done`), `answer_event_id` (set null if that note goes) and `asker_seen_at`. One tag per person per note. Nobody tags themselves. The indexes are the job table's keyed on `item_id`, plus one each on `instance_id` and `item_id` for the cascades, since a day row is deleted in the ordinary run of things.
- **Its read rule**: the two people read their own rows. Anyone else reads a tag when they can read its note, by a sub-select that runs under their own policies on the thread. There is no insert, update or delete policy and no such grant.
- **`task_note_people(instance, with_test)`**, internal: who may be tagged on one day row. Whoever gave the task and whoever has that day row, whatever their role but subcontractor or estimator. Then the office: dev, master technician, assistant, controller. Never an archived person, a digital twin, an account in training mode or a nameless row. Sample and walk-tester accounts only when `with_test`. It returns `on_task` and `gave`, so the box can say who gave the task.
- **`task_note_taggable(instance)`**: the list at the box, the task's own people first, without the caller. It refuses a caller who is not on that same list. Test logins follow `job_note_caller_sees_test()`, which this migration reuses and does not restate.
- **`task_note_post_tagged(instance, body, tagged[])`**: posts a typed note and its tags in one transaction and returns the note's id. `SECURITY INVOKER` on purpose: the note goes in under the caller's own policies, as the box inserts it today. A refused tag posts nothing.
- **`task_note_tags_write(event, tagged[])`**: the definer half. It takes tags only for the note this same transaction has just posted, by a transaction-local marker (`pt.task_note_just_posted`, the rule of `20261116190000` under a name of its own). Ten tags at most. A person the list does not offer is refused by name.
- **`task_note_answers_tags()`** and its trigger, `AFTER INSERT` on `checklist_instance_events` for a `comment` alone: every tag that waits on the note's writer on that task, on any of its day rows, is answered by the note. It never fails the insert.
- **`task_note_tags_mine()`**, **`task_note_tags_count()`**, **`task_note_tag_done(tag)`**, **`task_note_tags_seen()`**: the job functions' twins. The read carries the task's title as written, the day row's date, the note, the answer and `tagged_left`.
- **`note_tags_mine()`** and **`note_tags_count()`**: both kinds in one read and one number. `source` is `job` or `task`. The job rows are `job_note_tags_mine()` unchanged, with `tagged_left` added.

## Rules it settles

- **What answers a tag**: a typed note by the tagged person on that task, or No reply needed. A tick, a stuck line, a moved line, a handed line and every other kind of line answer nothing. One word in the trigger's `WHEN` changes that.
- **Why a trigger here and not on jobs**: a job's notes table cannot tell a typed line from a stamp. A task's thread says what each line is. So History's box, the Roadmap card, Review's Reopen with comment and My Inbox answer a tag from the first day with no client change.
- **The tag stays with the task, not the day**: a note on any day row of the same task answers it.
- **A done task**: tagging still works and nothing reopens.
- **A task handed on**: its tags go with it. The person who gave it away still reads the one note they were tagged in, through `task_note_tags_mine()`, and can still press No reply needed.

## One thing the card planned differently

The card planned `task_note_people(item, with_test)` over the task's giver, the task's assignees and the day row's assignees. This reads the day row instead, and leaves out a person who is only on the task's own list. `task_hand_on` gives away one day of a repeating task and leaves the task's list alone, so that person cannot read that day's thread. Offering them would break the card's first rule, that a tag never reaches someone who cannot open the task. The card named this under *Left to settle*: confirm against `task_hand_on` as it landed.

## The column the card called kind

The card asked for a `kind` column on the read of both kinds. `job_note_tags_mine()` already returns `kind` as `waiting` or `asked`, so the new column is `source`.

## Order and proof

Nothing in the client calls these names, so the push follows the merge and no deploy waits on it. The trigger is live from the push: a typed task note costs one indexed update that finds no row until the first tag is made.

Proved by CI's `task-note-tags` bed (`scripts/pgtest-task-note-tags.sh`, `supabase/tests/task_note_tags/`, a line in `scripts/sql-beds.txt`, `npm run test:pg:task-note-tags`), on the whole schema with the migration applied twice.
