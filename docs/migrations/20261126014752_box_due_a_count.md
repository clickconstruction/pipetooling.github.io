# 20261126014752_box_due_a_count.sql (2026-11-26, v2.8612)

What makes a box due a count, ruled the same in the database as on the phone. It replaces `on_site_door_facts`, first written by [`20261120070000_on_site_door_facts`](./20261120070000_on_site_door_facts.md), and `on_site_job_summary`, first written by [`20261109010000_on_site_job_summary`](./20261109010000_on_site_job_summary.md). Punch list #398.

## Why

Two of the owner's answers of 2026-11-25. Asked *Adding one part marks the whole box as counted today. Is that wanted?*: *"No, the add counts its own line"*. And part A's item 2 of the card: the list's Count chip counted an empty box, which offers no count on its own screen.

The Tally's Add a part writes a `delivered` row with the note *added on site* and, when the box held none of that part, a `counted` row for the line with the note *counted as added* (`ADD_COUNT_NOTE`). A box's last count was the newest `counted` row of any line in it, so one add cleared the amber of an overdue box for the parts nobody counted. Both database functions copied the client's rule on purpose, so a client-only mend would have left the phone's list disagreeing with the Job Mode card's line and the office's chip.

## What changes

`CREATE OR REPLACE` of both functions, with the same arguments, the same answer and the same grants, so the generated types do not change.

- **`on_site_door_facts(uuid) → jsonb`.** `due` leaves out a `counted` row whose note is *counted as added*, and counts only a box that holds a line to count: a line with something on hand, or a Can't find since its last count. The line arithmetic is the summary's own, over the site's boxes.
- **`on_site_job_summary(uuid, timestamptz) → jsonb`.** `last_counts` leaves out the same rows. `lines` keep them: an added part did count that line, and the line's own `last_count_at` reads the add. Every other key is as it was.
- The note's words are one constant on each side. `src/lib/materials/boxDueNote.test.ts` reads this file and fails when the words here and `ADD_COUNT_NOTE` in `src/lib/materials/onSite.ts` part.

## What stays

- A count by hand of any line in a box counts the box, as before.
- A count taken back counts nowhere, as before.
- `boxes`, `stickers`, `rows`, `lines`, `diffs`, `cannot_find` and `credits` answer as they did.
- `SECURITY INVOKER`: every table answers under the caller's own RLS.

## What it does not do

It makes and changes no table, so the four closing calls of a `CREATE TABLE` migration do not apply. It corrects no row: the rule is read at query time.

## Locks

`CREATE OR REPLACE FUNCTION`, `REVOKE`, `GRANT` and `COMMENT` on two functions. No table is locked. `SET lock_timeout = '3s'` opens the file as every migration's does.

## Order

The client reads no new name: the old client reads the new functions and the new client reads the old ones, so the push and the client deploy may land in either order. Between the two, the phone's list and the Job Mode card's line disagree on a box with one added part or on an empty box, which is what they did before this version. `npm run check:calls-ahead` names the two calls as functions the migration replaces, so no deploy waits for the push.

## Test

`npm run test:pg:on-site-guards` applies this migration a second time after every migration, which must change nothing, and plays `supabase/tests/on_site_guards/70_box_due.sql` as the dev through RLS: six boxes, of which an empty one, one with an old count, one counted today, one never counted by hand with an add today, one used down to none and one with a Can't find and none left; then a count by hand, an add into a stocked box, an add into the empty box, and a count taken back. No Postgres runs on the Mac that built this, so the SQL beds job on the PR is the proof of the SQL.
