# 20261102100000 — dev_on_site_write (v2.6367)

The dev MCP's dry-run wrapper for Materials on site (punch list #209): `plan_container` → `apply_container`, `plan_delivery` → `apply_delivery`, `plan_movement` → `apply_movement` and `plan_count` → `apply_count` in `dev-mcp` (server 0.14.0), the verbs the card and the office's Deliveries panel named as coming since v2.6039. Three functions, no table, so no fence is owed.

1. **`on_site_line_on_hand(p_container_id, p_part_id, p_part_name)`**: the ledger's arithmetic in SQL, as `src/lib/materials/onSite.ts` (`containerLines`) reads it — what a container holds of one part is the sum of the line's rows since its last `counted` row, which resets it (a `delivered` or `moved` row into the box adds, a `moved` row out and every other press takes away; rows in `(at, id)` order). A part is a book id, or a typed name folded as the kernel folds it. `SECURITY INVOKER`, `STABLE`. The dry run's before-and-after numbers come from it; `read_on_site` reads the same ledger through the kernel itself, so the two can be held against each other (they were, on the throwaway bed and on the ZZ job).
2. **`dev_on_site_container(p_job_id, p_ref)`** and **`dev_on_site_part(p_line, p_number_key, p_n)`**: the wrapper's two lookups — a live box on the job by its stencil (case and spaces ignored) or its id, refusing a retired one in words; a line's part from `material_parts` by `part_id` (its name and maker come along) or a typed `part_name` (1 to 160), and its whole number (`quantity` or `counted`, up to 100,000).
3. **`dev_on_site_write(p jsonb, p_dry_run boolean DEFAULT true)`**: **`SECURITY INVOKER` on purpose**, unlike the other dev wrappers. Every insert and update runs under the caller's own RLS, so the screens' gate `on_site_can_touch_job`, the tables' CHECKs, training mode's blocks and the digital-twin fence apply exactly as on the phone and the office page — the wrapper can never write what the screens could not. Gated `auth.uid()` + `is_dev()` first, then a training account (`is_read_only()`) and a digital twin (`is_digital_twin()`) are refused in words before the database would refuse them, then the job must exist under the caller's RLS and pass the gate. `p = { action, job_id, agent_label, at?, … }`:
   - `add_container { label, kind (cage | box | loose), where?, place? }` — the stencil upper-cased and trimmed as the screens write it, a live label already on the job refused, the place found by name or made; `move_container { container, place }` — the row's `place_id` and a `job_container_moves` row, as the phone's Move this box writes both; `retire_container { container }` — the plan lists what is still in it (the phone asks the same). Unsorted is never added, moved or retired.
   - `delivery { lines: [{ part_id | part_name, manufacturer?, quantity, unit? }], source?, to? }` — one `delivered` row per line into the job's Unsorted row, made on first use as the office's Deliveries panel makes it, or into a named box; the unit lands in `note` as the panel writes it, the invoice or PO in `source`.
   - `movement { container, part_id | part_name, quantity, reason (moved | used | returned | taken | cannot_find | damaged), to?, note? }` — one press on a line; the quantity is capped at what the box has (the phone's number sheet caps the same), a box with none of the part refuses, `to` is for `moved` only (the Put in… press from Unsorted is a `moved`), `taken` needs a note saying where; the book id and the maker travel with the line as the ledger already has them.
   - `count { container, lines: [{ part_id | part_name, manufacturer?, counted }] }` — one `counted` row per line, the phone's Count this box walk and the office's Correct…; a part not yet in the box may be counted into it; a line left out is not reset.
   - Every row is stamped as the agent's: `by_user_id` is the dev, `by_name` is `<agent_label> · MCP as <dev's name>` (120 characters at most), `created_by` on a place or a box is the dev. `at` is now, or the time given (never ahead); the reply echoes `now` or the time, never the clock, so the plan hashes the same from one second to the next.
   - The dry run returns `{ ok, dry_run, action, job { id, label, name }, after, by, at, container_rows }`: `after` is the row as it would be written with every line's `on_hand_before` / `on_hand_after` (a count's `expected` / `counted` / `diff` with its words — *2 missing*, *3 found*, *counted right*; a movement's press words — *Mark 4 used*, *Move 10 to A1* — and what is left), and `container_rows` is the box's live row count, so a press on the box since the plan changes the plan's hash and apply refuses. The real run adds `ids` (the rows written; a new box's `container_id` and label `code` in `after`).

No table is created, so no read-only fence is owed; the fences on the five Materials tables (`20261029010000`) hold because the wrapper runs as the caller.
