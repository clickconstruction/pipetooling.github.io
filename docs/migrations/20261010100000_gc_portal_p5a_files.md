# 20261010100000_gc_portal_p5a_files.sql (2026-10-10, v2.5170)

GC mode, the real build, the trade partner portal's P5a-m (`to-dos/gc-mode/PORTAL_REAL_BUILD.md` → *The PRs, in order*, item 9; plan `to-dos/gc-mode/mockups/portal-p5a.md`, on branch `spike/gc-mode`). Files from the portal: a trade's file goes into the job's Drive folder and the app keeps the link, never a copy (the owner's call, decision 9). This migration is the ledger of those files and the three verbs that store a file's link. Nothing uploads yet: P5a-1's kind `file` does, through `submit-gc-trade-portal`.

## What it does

1. **`gc_trade_files`**, a new table: one row for each file a trade put in Drive from its portal, and each signed paper the portal makes for it (P5a-2's waiver PDF).
   - `company_id`, `project_id`, `package_id` (null on a quote's file while we bid).
   - `purpose`: `submittal`, `change`, `quote` or `waiver`.
   - `record_id`: the record it went with once the next kind stored its link, null until then.
   - `name`, `mime` (PDF, JPEG, PNG, HEIC or HEIF), `bytes` (10 MB at most), `drive_file_id`, `drive_url` (https).
   - `made_by`: `trade` for an upload, `portal` for a signed paper the function made.
   - `uploaded_at`.
   - RLS: the office team (`gc_office_team()`) reads every row; nobody else reads. The client may never write it; only the service role does. The migration ends with the three block calls, so the training-mode and digital-twin blocks are on it.
2. **`gc_trade_ask_change`** gains `p_file_url text DEFAULT NULL`, stored in `gc_trade_change_requests.file_url` (already a column). A function's arguments cannot change in place, so the old signature is dropped and the new one made in the same transaction. A call without the new argument, as `submit-gc-trade-portal` sends today, reads the same.
3. **`gc_trade_submit_quote`** reads `q->>'file'` into `gc_quotes.quote_file` (already a column, empty before). The rest is P2a's, word for word.
4. **`gc_trade_submittal_send`** takes what it took and refuses what it refused. It now ties an uploaded file to its round.
5. Two helpers, each the service role's alone:
   - `gc_trade_file_link(text)` takes an https link of 2,000 characters at most, or none. Anything else raises `badRequest` with the words "A file's link is an https link."
   - `gc_trade_file_tie(company, purpose, url, record)` sets `record_id` on the company's newest untied file with that link and purpose. Another company's link, or a typed link that is no row of its own, ties nothing.
6. The five functions are granted to `service_role` alone: revoked from `PUBLIC`, `anon` and `authenticated`.

## Checked before the push

**The SQL bed** (`npm run test:pg:gc-portal-p5a`, the `SQL beds` workflow's `gc-portal-p5a` bed, one line in `scripts/sql-beds.txt`): the whole schema on Supabase Postgres 17, this migration a second time, then `supabase/tests/gc_portal_p5a/20_scenario.sql`, all in one transaction that rolls back. It passed locally on Docker on 2026-10-10. It checks:
- the ledger's grants (the client reads, never writes; anon nothing) and the five functions' (the service role's alone);
- `gc_trade_ask_change` has one signature, the new one;
- RLS: a dev reads the rows and cannot write one; a subcontractor reads none;
- the ledger's CHECKs: over 10 MB, an unknown type, an unknown purpose and a link that is not https are each refused with `23514`;
- a change with its photo stores the link and ties Bright Line's file, never Level Line's with the same link; the old call without the link still works; a link that is not https is `badRequest`; the verb's own refusals come first;
- a quote with its PDF stores the link in `quote_file` and ties the file, and one with none keeps `quote_file` empty;
- a submittal round with its uploaded file ties the file to the round; nothing else is tied;
- the restrictive blocks are on the new table.
