# 20261118010000_job_papers_lock.sql (2026-11-17, v2.7659)

Papers before a job opens: the lock in the database. Step 4 of seven. Steps 1 to 3 made the papers a job requires, the office's section and the prompt. This migration makes the database refuse a job to the crew and subs who still owe it a paper, so the prompt is no longer their only lock.

## What it makes

Three functions, eight policies, and six helper functions restated. No table.

- **`job_papers_prompt_only()`**: true for dev, master technician, assistant, controller and primary. The lock leaves them alone.
- **`job_shut_to_me(job)`**: true when the caller owes a paper on the job and is not a prompt-only role. A `CASE` keeps the order: no login, then one look at the live required papers for that job, then the role, then the caller's own papers.
- **`jobs_shut_to_me()`**: the same answer as an array. The policies ask it once a statement.
- **`job_papers_fence`**, restrictive, for every command, `TO authenticated`, on `jobs_ledger` (by `id`) and on `jobs_ledger_thread_notes`, `jobs_tally_parts`, `job_stage_windows`, `painted_maps`, `step_commitments` (by `job_id`) and `file_index`, `messages` (by `jobs_ledger_id`). A row tied to no job passes.
- **Six helpers**, each from its only definition with `AND NOT job_shut_to_me(job)` added last: `helper_on_job` (`20261014220000`), `subcontractor_can_read_jobs_ledger_row` (baseline), `can_report_stage_progress` (`20260909141454`), `on_site_can_touch_job` (`20261029010000`, still `SECURITY INVOKER`), `superintendent_report_job_anchor_allowed` (baseline, its argument still `p_job_ledger_id`), `superintendent_can_touch_job_thread` (`20260902165836`).

## Rules it settles

- **Who is locked**: everyone but the prompt-only roles. The owner settled the office as "Prompt is enough". A primary is with the office because a primary has a Pipeline and money totals too.
- **`job_closed_to_me` says who owes. `job_shut_to_me` says whose rows the database refuses.** The prompt and the Needs you line read the first. Policies and helpers read the second.
- **A locked person keeps their schedule block.** `job_schedule_blocks` and `jobs_ledger_team_members` are not fenced, so the list can show the job's number and a lock.
- **`can_access_project_row` is untouched.** Both overloads take a project, not a job.
- **`TO authenticated`**: `cost_agent` and `hr_agent` hold their own policies on some of these tables and can run only the functions granted to them by name. A fence with no `TO` clause would have broken their reads.
- **A locked person cannot write to the job either.** The policies are `FOR ALL`, so their `USING` is the insert's check too.

## What it leaves for step 5

The functions that list jobs without asking row security (`search_jobs_ledger`, `list_assigned_jobs_for_dashboard`, `list_superintendent_jobs_for_dashboard`, `list_jobs_for_tally`, `list_reports_with_job_info`), the edge functions that read a job with the service key, the push notices and the schedule email.

## Order and proof

No client change rides with it. Each `CREATE POLICY` takes a brief lock on a table in use, so the push waits for a quiet moment, and `lock_timeout` ends it fast if a table is busy.

Proved by CI's `job-papers-lock` bed (`scripts/pgtest-job-papers-lock.sh`, `supabase/tests/job_papers_lock/`, a line in `scripts/sql-beds.txt`, `npm run test:pg:job-papers-lock`), on the whole schema with the migration applied twice.
