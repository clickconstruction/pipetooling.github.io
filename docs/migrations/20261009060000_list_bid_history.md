# 20261009060000_list_bid_history.sql (2026-10-08, v2.4948)

Bid history PR 2 (punch list #73, [`to-dos/bid-history`](../../to-dos/bid-history/README.md)): the reader the History window calls.

`list_bid_history(p_bid_id uuid, p_limit integer DEFAULT 2000)` returns, newest first, one row per change:

- the ledger's rows (`bid_changes`) for the bid **and every bid adopted into it** (`bids.adopted_into_bid_id`, followed recursively). The owner decided on 2026-10-08 that the history follows the adopt and shows both bids, each row with its bid number;
- the delete archive's rows for those bids that the ledger does not hold (`source = 'archive'`): rows removed before the ledger was pushed, kept 90 days. Each comes as op `delete`, with the snapshot as its old values and a label worked out as `record_bid_change()` names a row (a count row by its fixture, what hung on one by that fixture, live or from its own snapshot, and so on). The archive's copy of a removal the ledger already holds is left out;
- each row's bid number and its author's name (`users.name`).

**SECURITY INVOKER**, on purpose: every read runs under the caller's own policies. The ledger is read by whoever can read the bid; the owner decided on 2026-10-08 that every estimator sees every change, which is the ledger's PR 1 rule. The bids decide the adopt scope and the numbers, and the users decide the names. **The archive keeps its dev-only read**, so its rows reach a dev and nobody else. Showing them to everyone who can read the bid would need a read policy on `deleted_records_archive`; that is left to Grace and not made here. The window works without them.

A function only (`CREATE OR REPLACE`), no table touched; `SET lock_timeout = '3s'`. `EXECUTE` revoked from `anon`, granted to `authenticated`.
