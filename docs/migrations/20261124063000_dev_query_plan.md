# 20261124063000_dev_query_plan.sql (2026-11-24, a dev reads the plan of a fixed statement as themself, v2.8432)

Punch list #430. One new function, `public.dev_query_plan(p_key text, p_analyze boolean DEFAULT true, p_max_chars integer DEFAULT 400000) RETURNS jsonb`. No table, no view, no client change. The dev seat's `check_query_plan` reads it.

## Why

A view that joins a table with row policies is as fast as the plan its caller gets. Until this file nothing a session may use could read that plan on prod. PostgREST hands back rows and no plan. The dashboard SQL editor and the Supabase MCP are off limits by `CLAUDE.md`, and they plan as the database owner, whom no policy binds, so their plan is not the one a person waits on. Punch list #430 mended two views on the plan's shape for that reason and left the measure owed.

## What holds it

- **No free SQL.** The caller names a statement by its key. Every statement is written out in the body, whole: `FOR v_line IN EXPLAIN … LOOP`, once analyzed and once not. The body has no `EXECUTE` and no `format(`, so nothing the caller sends is ever part of a statement. A key that names no statement is refused with `22023` and a hint that lists the keys. A new statement is a new migration.
- **The caller's own plan.** `SECURITY INVOKER`: the statement is planned and run as the caller under their own row policies.
- **Devs only, in the database.** `IF NOT public.is_dev()` raises `42501` before the key is read. `EXECUTE` is revoked from `PUBLIC` and `anon` and granted to `authenticated`, as the `dev_health_*` functions are.
- **Read only.** Each statement is a `SELECT`. After the gate the function sets `transaction_read_only` on for the rest of the transaction, so the database refuses a write (`25006`) whichever door the call came through. The seat calls it over GET, which PostgREST already runs read only.
- **The reply is the plan.** `key`, `analyzed`, `line_count`, `cut` and `lines`. Past `p_max_chars` the head that fits and the last twelve lines are kept, with `left_out` and `last_lines`. The cap is a number clamped between 2,000 and 400,000 characters.

## The statements

| Key | Statement |
|---|---|
| `agreements_on_file` | `SELECT * FROM public.agreements_on_file` |
| `people_hours_recorded` | `SELECT * FROM public.people_hours_recorded WHERE work_date >= current_date - 14` |

`p_analyze => true`, the default, is `EXPLAIN (ANALYZE, BUFFERS)`, which runs the statement. `p_analyze => false` is `EXPLAIN` alone and runs nothing, for a statement that might not finish inside the caller's statement timeout.

## Tested before it was written

- **`EXPLAIN` is refused inside a `STABLE` function**, written into the body or run through `EXECUTE`: *EXPLAIN is not allowed in a non-volatile function* (Postgres 17.6, the image prod runs). So the function is `VOLATILE`.
- **PostgREST calls a `VOLATILE` function over GET**, in a read-only transaction: PostgREST 12.2.12, 13.0.7 and 14.5, the version prod runs, against that Postgres each answered a GET of one with its plan, and answered a GET of one that writes with `25006`. `dev_case_search` is volatile and the seat has read it over GET since v2.6620. No write verb was added to reach this one.

## The bed

`dev-query-plan` (`scripts/pgtest-dev-query-plan.sh`, `supabase/tests/dev_query_plan/20_scenario.sql`), new with this file, applies it twice over the whole schema. It asserts the function runs as its caller, is closed to anon, has no dynamic SQL, and that the statements under `EXPLAIN` in its body are the four expected and no other. No session, the assistant and a crew member are refused. A dev with an unknown, empty or null key, a real key with a statement or a clause after it, or a statement for a key is refused, and a row those keys tried to delete is still there. A dev gets each statement's plan, analyzed and not; the plan alone is line for line what the same `EXPLAIN` gives the dev directly, and is not what the tables' owner gets. A reply's parts add up whole and under a smaller cap. A write after a call is refused by the database.

**No table is made**, so the fence calls are not needed. `CREATE OR REPLACE FUNCTION` with the same signature, so the file is safe to run twice.
