# 20260917200000_pay_sources — pay sends carry their source; five functions become the one door (v2.3578)

**What**:

- `pay_stub_payments.source_kind` (`cashapp` · `mercury` · `client_direct` · `other`, nullable) and `source_id` (the Cash App transaction id, the app's `mercury_transactions.id`, or null). A partial unique index on `(source_kind, source_id, pay_stub_id)` — one payment row per send per report, so a send that covered three weeks has three rows and a row backs one send. This inverts the old link (`cashapp_transactions.pay_stub_payment_id` → one payment), which could not express a split.
- `cashapp_transactions.decision_note` — why a send was filed as not pay / expense / ignored.
- Helpers: `pay_rpc_allowed()` (payroll access or the service role), `pay_send_memo(kind, id, note)`, `pay_paid_at_noon(date)` (noon America/Chicago, the instant the app's Record payment writes), `pay_report_net(stub)` and `pay_report_remaining(stub)` (the formula `validate_pay_stub_payments_vs_net` enforces: gross − deductions + additional lines).
- `pay_position(person) → jsonb` — each report's gross · deductions · additional · net · paid · remaining with its payments, `open_total`, pending offsets (no `pay_stub_id`), and the person's Cash App queue (lanes `review` and `advance`). The one read; nobody recomputes net from gross again.
- `record_pay_send(kind, id, person, amount, paid_on, note, dry_run=true) → jsonb` — allocates the send to the person's open reports oldest first, splitting where a report fills; any leftover becomes a `person_offsets` row of type `advance`; a Cash App queue row is set to `recorded` (or `advance` when nothing was open) with `match_rule = 'manual'`. Idempotent on `(kind, id)`: a second call returns `already_recorded` with the rows. Dry run returns the plan and writes nothing.
- `link_pay_send(payment_id, kind, id, amount=null) → jsonb` — attach a source to an existing payment, optionally correcting its amount (the net trigger still refuses more than the report's net). A Cash App id is written into the memo when absent, the old memo becoming the quoted note. Refuses a payment that already carries a different source. The backfill primitive.
- `split_pay_payment(payment_id, parts) → jsonb` — turn one payment into rows summing to the same total (`parts`: `[{amount, source_kind?, source_id?, memo?, paid_at?}]`, ≥ 2, each > 0). The first part updates the row in place; the rest insert on the same report.
- `set_cashapp_lane(id, lane, person=null, note=null) → jsonb` — `review` / `expense` / `before_records` / `not_staff` / `ignored` (`recorded` and `advance` only come from `record_pay_send`); clears the payment/offset links.

**Access**: every function raises `payroll access required` unless `has_payroll_access()` or `auth.role() = 'service_role'`. SECURITY INVOKER — the tables' RLS and the read-only write blocks still apply. Granted to `authenticated` and `service_role`.

**Why**: v2.3578 — the owner (2026-09-17) chose to backfill payments with the Cash App ledger's facts rather than reconcile by hand each time, and to give agents one door instead of the component code's write shapes. See `docs/recent-features/v2.3578.md`.

**Verified**: the migration and a scenario (dry run · apply · idempotent repeat · leftover to advance · nothing open · link with correction · second-source refusal · over-net refusal · split · bad-sum refusal · lanes · the unique index · the access gate) ran green against a throwaway Postgres 15 carrying the baseline's payment triggers.

**Idempotent**: `ADD COLUMN IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS` + add, `CREATE INDEX IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`. Additive; no data touched. No new table, so no read-only block calls.
