# 20261016030000_tech_bio.sql (2026-10-16, v2.5587)

The tech's bio, the ground (punch list #114, `to-dos/tech-about-lines/README.md`): the office's lines about each tech, in the company's words, joined in order into the short resume a customer gets as a second text the first time the tech presses On my way to them (the send is PR 3's). The client reads the new table fail-soft, so it may deploy before the push; push after the feature PR merges and before the types regenerate.

## What it does

1. **`user_bio_lines`**: `user_id` → `users`, `text`, `text_es`, `position`, `added_by` / `added_at`, `removed_at` / `removed_by`, `off_by_user_at` (the tech's veto). One SELECT policy: the row's owner or the office team (`gc_office_team()`). `authenticated` holds SELECT alone; every write goes through the two functions; `service_role` holds all. A partial index on the live lines by user and place. The three fence appliers run at the end (the read-only write blocks, the statement trigger, the digital-twin fence).
2. **`messages.introduces_user_id`** (uuid → `users`, null everywhere today): the thread's memory — PR 3's `quo-send` stamps it on the bio text, and the phone and the server read it to send a bio once per tech per customer. A partial index with `contact_id`.
3. **`bio_opener(p_user_id, p_lang)`**: *A little about Luis: * or *Un poco sobre Luis: * from the first word of the person's name, the same rule as the client's kernel (`src/lib/bio/bio.ts`). SECURITY DEFINER; EXECUTE to `authenticated` and `service_role`.
4. **`edit_bio_line(p_user_id, p_id, p_text, p_text_es, p_position, p_remove)`**: the office adds a line (`p_id` null, the next place), changes its words, Spanish or place, or removes it (`p_remove`). Refused through `quick_reply_caller('change a tech''s bio')` (signed out, a training account, a twin, off the office team), for a person with no real account, an empty line, a line with a line break, a removed line, and a bio that would pass **320 characters** in either language with this line's new words, counted over every live line whichever the tech turned off. Returns the line's id. SECURITY DEFINER; EXECUTE to `authenticated`, revoked from `PUBLIC` and `anon`.
5. **`bio_line_say(p_id, p_say)`**: the tech turns one of their own lines off (stamps `off_by_user_at`, keeping the first stamp) or on (clears it). Refused signed out, for a training account, a twin, a line that is not theirs, and a removed line. SECURITY DEFINER; EXECUTE to `authenticated`, revoked from `PUBLIC` and `anon`.

## Why the shape

- Lines, not one field: Spanish beside each, a veto on each, a count the office sees, and the Edit bio window's ticks (PR 3) are all per line.
- The cap on the whole, not the line: one text of two segments is what the customer gets.
- The opener in SQL and in the kernel: the desk's count and the server's cap must agree to the character.
- No seed and no change to any quick reply: the bio is its own text; the On my way line is untouched.

## Verify

Read-only on prod after the push: `select count(*) from user_bio_lines` reads 0 until the office writes one; `select public.bio_opener(id, 'en') from users where role = 'helpers' limit 1` reads *A little about <first>: *. The SQL bed `npm run test:pg:tech-bio` (CI) walks the office's writes and each refusal, who reads which lines, the tech's veto and each refusal, and who may write.
