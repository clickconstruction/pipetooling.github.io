# 20261010017000_bid_removed_rows.sql (2026-10-09, v2.5079)

Bid history PR 5 (punch list #73, [`to-dos/bid-history`](../../to-dos/bid-history/README.md)): a bid's editors see the bid's own removed rows and put one back. The owner, 2026-10-09: yes, a bid's editors see the bid's OWN removed rows so they can Put them back. The delete archive keeps its dev-only read; these functions read it as their definer, one bid at a time, for someone who can edit that bid.

`can_edit_bid(p_bid_id uuid) RETURNS boolean`, SECURITY DEFINER, STABLE: the bids update policy as one check, each part named after the migration it mirrors:
- the update policy's roles (`20260927210000`): dev, master_technician, assistant, controller, estimator, primary;
- `primary_scope_bids` (`20260823171344`): a primary only on bids they estimate, manage or made;
- training mode (`20260713090000`): not `is_read_only()`;
- the twin fence (`20261005222937`): a digital twin only on bids it made or estimates.

A SECURITY DEFINER function cannot evaluate the caller's policies, so the two below call this instead.

`list_bid_removed_rows(p_bid_id uuid)`, SECURITY DEFINER, STABLE:
1. Refuses anyone `can_edit_bid` says no to: *Only someone who can edit this bid sees what was removed from it.* (42501)
2. Returns the archive's rows still out (`restored_at` null) of the bid's own tables, never the bid itself. These are the rows grouped under the bid, and the direct-cost rows grouped under one of its estimates (live, or removed with the bid's estimate). The bid's own rows only: an adopted bid's are its own editors'.
3. Each row comes with its table, row id, count row, a label named as `list_bid_history` names an archive row, its snapshot as the old values, the columns it held, who removed it and when, and `in_ledger`: whether the bid's own ledger rows hold its removal too (read on `bid_changes_bid_idx`, since every ledger row carries its bid). The window pairs a ledger removal with its archive row by table, row and time: both triggers stamp the deleting transaction's `now()`.

`restore_bid_removed_row(p_archive_id uuid) RETURNS jsonb`, SECURITY DEFINER, VOLATILE:
1. Refuses a row already back or unknown (*That removed row is not waiting to be put back.*), and the bid itself or a table outside the ledger's list (*That row cannot be put back here. A whole bid comes back from Recently deleted.*). It also refuses a row whose bid is gone (*Its bid was removed. …*), and someone `can_edit_bid` says no to (*Only someone who can edit this bid can put back what was removed from it.*).
2. Takes the bundle: the row, then every row of the same delete (the same `deleted_at`, whatever its table) that hangs on a row already in it by a single-column foreign key. So a count row brings back its prices, costs, part lines and submittal ticks.
3. Checks every reference in the bundle against a live row or a row coming back with it, as `restore_deleted_records` does. A gone reference in a nullable column is cleared and named in `warnings`. One in a required column refuses the whole put back: *Its count row was removed too. Put that back first.* (also *Its estimate …*, *Its version …*).
4. Tags the request `x-bid-action: put-back`, so `record_bid_change()` records each insert as the caller's put back (`by_app` false). It inserts parents before children in `restore_deleted_records`' longest-path order over the live keys, and puts the headers back after.
5. Inserts only the columns the snapshot holds, so a column added since takes its default. A unique clash (*That row, or one like it, is already on the bid, so it cannot come back.*) or a key violation refuses all of it.
6. Marks each archive row restored (`restored_at`, `restored_by`) and returns `{ok, bid_id, restored, tables, warnings}`.

A whole bid stays the dev's restore (`restore_deleted_records`, Settings → Recently deleted).

Functions only (`CREATE OR REPLACE`), no table touched; `SET lock_timeout = '3s'`. Each is owned by `postgres`, with `EXECUTE` revoked from `PUBLIC` and `anon` and granted to `authenticated` and `service_role`. Apply order: either. Before it exists, the window lists no removed rows for a non-dev (the read answers *Could not find the function*, which the client reads as none) and Put back on a removed row says *Put back is not ready yet.* Regenerate `src/types/database.ts` and the dev-mcp catalog after the push; until then the client calls both functions untyped.
