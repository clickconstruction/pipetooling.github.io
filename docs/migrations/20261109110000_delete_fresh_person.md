# 20261109110000_delete_fresh_person.sql (2026-11-09, v2.6789)

Delete a person made by mistake. On 2026-11-09 a dev typed a new hire's name wrong, hired without the invite, and found the only way off the roster was Archive; since #260 every person is a users row with a People record linked to it, and since #265 (v2.6530) the key between them is `ON DELETE RESTRICT` and no client may delete the users row, so there was no door.

- `delete_fresh_person(p_user_id uuid, p_dry_run boolean DEFAULT false) → jsonb` `{ deleted, dry_run, name, user_id, person_id, holds: [{ table, column, count }], removed: [text] }`, `SECURITY DEFINER`, `search_path` pinned to `public`, EXECUTE to `authenticated` (revoked from `PUBLIC` and `anon`).
- Gate: the people who may archive — a dev, the controller, or a master in `pay_approved_masters` (archive-user's set, v2.2713) — never in training mode (`users.read_only`, refused with `42501` and plain words; the statement trigger would stop the deletes too), never one's own row. `P0002` for an id with no row; `23514` for a row with a login (`login_attached_at` set, or an `auth.users` row of the same id) or a sample / digital twin, each with its reason.
- Holds: every foreign key into `public.users(id)` or `public.people(id)` is read from `pg_constraint` (any schema, any column, the matching column of a multi-column key) and counted against the person's two ids, so a table added later is held without this function knowing its name. Not holds: the person's own People record (`people.account_user_id`; another record on the same users row is one), and the setup rows the Hire form writes in the same run — `people_pay_config.person_id` (the RESTRICT key that would otherwise block) and `salary_work_schedule_templates.user_id` — which go with the person and are named in `removed`. A salaried hire's template has already made today's clock sessions, which are a hold.
- `p_dry_run` true: the same gate and scan, nothing deleted — the desk reads it to decide between the typed confirm and *Archive instead*.
- The write, in one transaction: the setup rows found by the scan (`EXECUTE` of the collected deletes), the People record (its `BEFORE DELETE` trigger `contacts_keep_thread` runs as for any delete), then the users row.

Idempotent (`CREATE OR REPLACE`); no table is created, so no fence calls. Apply order: the client calls `delete_fresh_person` from the desk's Status row and the Users row's ⋯ menu, so push right after the merge, before the Pages deploy finishes (`check:calls-ahead` labels the PR); until the push, Delete… shows `PGRST202` as its reason and nothing else in v2.6789 waits on it. Bed: `supabase/tests/users_without_login/70_delete_fresh_person.sql` (`scripts/pgtest-users-without-login.sh`, D1–D7: the gate, the dry run, a clock session and an approved-by key as holds, a login and one's own row refused, a pay-approved master and training mode, the pay row going with the person).
