# 20261013160000_mail_config.sql (2026-10-13, v2.5387 — the Docsmit train PR 9)

The Docsmit connection's secrets in Vault (`docs/DOCSMIT_LIEN_RUN_PLAN.md`, *Managed from Developer settings*), written from the app by a dev through `mail-config` and read by `mail-send-docsmit` and `mail-poll` at call time, so the owner rotates them without a terminal.

## What it does

1. **`mail_secret_name_ok(name)`**: the four allowed names — `docsmit_email`, `docsmit_password_sha512`, `docsmit_software_id`, `docsmit_base_url`.
2. **`mail_secret_set(name, value)`**, `SECURITY DEFINER`: makes or replaces the Vault secret of that name (`vault.create_secret` / `vault.update_secret`); a blank value deletes it; any other name raises. Answers whether a value is now kept.
3. **`mail_secret_get(name)`**: the decrypted value, or null.
4. **`mail_secrets_status()`**: `{name: boolean}` for the four, never a value.
5. All three are the service role's only (revoked from `PUBLIC`, `anon`, `authenticated`): a signed-in user never reaches Vault; the dev goes through `mail-config`, which checks the role.

No table, so no fences. Idempotent (`CREATE OR REPLACE`). Apply with `supabase db push` after the PR merges; deploy `mail-config` after it, and redeploy `mail-send-docsmit` and `mail-poll` (they read Vault first from this release).
