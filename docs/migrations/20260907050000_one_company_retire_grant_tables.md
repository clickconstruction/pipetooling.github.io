# 20260907050000_one_company_retire_grant_tables.sql (2026-09-07, v2.2987)

One company, **Phase 5** of [`docs/ONE_COMPANY_PLAN.md`](../ONE_COMPANY_PLAN.md): `master_assistants` and `master_shares` stop being data.

- **Why not drop**: 45 SECURITY DEFINER functions still read the two tables by name (SQL bodies resolve at call time; the census is in the plan doc), 84 policies carry the old adoption branches inside their Phase 2 `is_office_staff() OR (…)` wrapper, and `sync_company_access_grants()` (v2.921) has kept the tables complete so all of it passes. A rename or drop under those readers breaks every gate at once.
- **`sync_company_access_grants()`** now fills only `master_primaries` / `master_superintendents` (walled roles, real tables).
- **Rename** `master_assistants` → `retired_master_assistants`, `master_shares` → `retired_master_shares` (guarded on `relkind = 'r'`, so a rerun renames nothing). Rows and their own RLS policies travel with them; rollback is the reverse rename. Drop after a quiet week (Phase 5c).
- **Views** with the old names and column shapes (`master_id, assistant_id, created_at` / `sharing_master_id, viewing_master_id, created_at`): every live dev/master × every live **assistant, controller or estimator**; every live dev/master × every other. Estimators are included because the live table held two hand-made estimator adoptions (Malachi → Wendi, William); after the Phase 4 backfill "adopted by Malachi" and "adopted by the company owner" are the same thing, so the rule grants nothing new. One hand-made share (a dev → a primary) is dropped — that dev holds no rows. Plain views owned by `postgres` (no `security_invoker`) so policies and functions see the same pairs for every caller; `SELECT` for `authenticated` + `service_role`, revoked from `anon`.
- **84 policies re-bound** (generated by `scripts/one-company-policy-sweep.py --rebind`): DROP + CREATE with byte-identical bodies so their parsed expressions point at the views — a policy expression stores relation OIDs, so without this step they would keep reading the retired tables.

Effect on roles: none. Office roles pass the wrapper outright; primaries, superintendents, estimators, helpers and subs get identical answers from the views. Apply any time; `database.ts` must be regenerated afterwards (the two names move from Tables to Views).
