# 20261023150000_lien_sign_code.sql (2026-10-23, v2.5788)

Lien desk signing by code, PR 1 of 2 (punch list #148). A leader sets a signing code only he knows, four to six digits, under Settings → Your account; on the Lien desk he types it on anyone's screen to put his name on a notice (the desk field is PR 2). The database holds a salted hash and checks the code itself; the office never sees it.

## What it adds

- **`user_sign_codes`** — `user_id` (PK → users, cascade), `code_hash` (hex sha256 of `salt || code`), `code_salt` (a uuid), `set_at`, `failed_tries`, `locked_until`, `last_used_at`. RLS on with **no policies** and every table grant revoked from `anon` and `authenticated`: nothing reads or writes it but the four SECURITY DEFINER functions. The training-mode fences and the twin fence are re-applied at the end, as every new table asks.
- **`set_lien_sign_code(p_code text)`** — the caller's own code: master or dev only, not in training mode, `^[0-9]{4,6}$`, a fresh salt each time, tries and lock reset.
- **`clear_lien_sign_code()`** — deletes the caller's own row.
- **`lien_sign_code_status(p_user_id uuid)`** → `{set, set_at, last_used_at, locked_until}`: the caller himself, or the office set (dev · master · assistant · controller) about any leader. Never the hash.
- **`sign_lien_desk_item_with_code(p_item_id, p_signer_id, p_code, p_fields_hash, p_approve)`** → jsonb. Caller: the office set, not in training mode. Signer: a master or dev, not archived. Answers rather than raises on a code problem, so the counter persists: `{ok:false, reason: format | none | wrong | locked, tries_left, locked_until, message}`; the fifth wrong code sets `locked_until = now() + 15 minutes`. On the right code: tries reset, `last_used_at` stamped, `set_config('lien.code_verified_for', signer, true)` for this transaction, then the item row is updated — mode `code`, `signed_by` the signer, `signed_on_device_of` the caller (NULL when he is the caller), `signer_printed_name` = `users.name`, the hash as passed, the pen columns cleared — and with `p_approve`, `status = 'approved'`, `approval_mode = 'leader'`, `approved_by` = the signer. Returns `{ok:true, signed_at, printed_name}`.
- **The mode CHECK** widens to `type | draw | pen | code`.
- **The guard** (`job_lien_desk_items_guard`), replaced whole as every signing migration does, otherwise as `20261013100000` left it: it reads `lien.code_verified_for` at the top; a newly set signature in mode `code` is refused unless that setting names `NEW.signed_by` (so a direct client UPDATE in mode `code` never passes); a `leader` approval checks the role of the verified signer in place of `auth.uid()` and defaults `approved_by` to him; and the confirm rule takes mode `code` beside `pen`, so his own sign-in may stand behind a code signature or disown it (the pen train's doors, wired to it in PR 2).

## Why a transaction-local setting

A SECURITY DEFINER function runs as the owner, so the row trigger cannot tell a verified code from a client write by `auth.uid()` alone. The function names the signer it verified in `lien.code_verified_for` (third argument `true` = this transaction only) right before its UPDATE and clears it after; the guard accepts mode `code` only while it is set to that signer. No other function sets it.

## Order

1. Merge and deploy the client (v2.5788): the Settings card says *Not switched on yet* until the functions exist (`isMissingRpcError`).
2. `supabase db push` from a main checkout.
3. The follow-up `chore(types)` PR regenerates `src/types/database.ts`; until then the client calls the RPCs with `as never`.

## The lock note

`SET lock_timeout = '3s';` is first. The new table takes no lock anyone waits on. `DROP CONSTRAINT` / `ADD CONSTRAINT` on `job_lien_desk_items` take an ACCESS EXCLUSIVE lock for the CHECK scan; the table holds a few hundred rows. `CREATE OR REPLACE FUNCTION` takes no table lock.

## Verify after the push

1. `select count(*) from pg_proc where proname in ('set_lien_sign_code','clear_lien_sign_code','lien_sign_code_status','sign_lien_desk_item_with_code');` → 4.
2. `select pg_get_constraintdef(oid) from pg_constraint where conname = 'job_lien_desk_items_signer_signature_mode_check';` → carries `'code'`.
3. `select prosrc like '%lien.code_verified_for%' from pg_proc where proname = 'job_lien_desk_items_guard';` → true.
4. `select relrowsecurity from pg_class where relname = 'user_sign_codes';` → true; `select count(*) from pg_policies where tablename = 'user_sign_codes' and policyname not like 'read_only%' and policyname not like '%twin%';` → 0.
5. Nothing written: `select count(*) from user_sign_codes;` → 0.

Then `npm run check:migration-drift`.

## Rollback

A one-off migration drops the four functions and the table, narrows the CHECK back to `type | draw | pen`, and restores the guard from `20261013100000_lien_pen_signature.sql`.
