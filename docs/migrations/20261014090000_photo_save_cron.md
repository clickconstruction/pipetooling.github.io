# 20261014090000_photo_save_cron.sql (2026-10-13, v2.5464)

Messages, cut 10's last item (GC Mode helper 2, directed by the lead session GC MODE). This is the cron for the
`photo-save` sweep (v2.5458, deployed 2026-10-13 13:44 UTC). The sweep copies each photo that came in on a ticked job's
lines to that job's photos in Drive. The ticks are `photo_saves` (v2.5457, `20261014070000`).

## What it does

**The cron row `photo-save`**, every 5 minutes (`*/5 * * * *`), posts to `/functions/v1/photo-save`.
- It uses Vault's `PROJECT_URL` and `CRON_SECRET`, as `gmail-sync`'s and `mail-poll`'s crons are scheduled.
- It fires only while some job's tick is on (`photo_saves.on_since IS NOT NULL`). Every tick starts off, so until the
  office turns one on, nothing calls the function.
- The row is unscheduled and scheduled again by name, so running it again leaves one row.

No table, so no fences. Idempotent. Apply with `supabase db push` after the PR merges. The function is already
deployed.

## Verify after the push

```sql
-- One row, every 5 minutes, posting to photo-save.
SELECT jobname, schedule, active FROM cron.job WHERE jobname = 'photo-save';
-- Once a tick is on, the runs and their answers.
SELECT status, return_message, start_time FROM cron.job_run_details
WHERE jobid = (SELECT jobid FROM cron.job WHERE jobname = 'photo-save') ORDER BY start_time DESC LIMIT 5;
```

Expect one active row on `*/5 * * * *`. The function answers `{ ticks, saved, failed }` in its own logs.

## Rolling back

```sql
SELECT cron.unschedule(jobid) FROM cron.job WHERE jobname = 'photo-save';
```
