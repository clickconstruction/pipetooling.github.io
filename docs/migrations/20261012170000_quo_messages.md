# 20261012170000_quo_messages.sql (2026-10-12, v2.5278)

Messages, cut 5, the Quo link (`to-dos/gc-mode/messages/BUILD_PLAN.md` → Cut 5 on branch `spike/gc-mode`; the kernels are `src/lib/quo/events.ts`, `send.ts` and `webhook.ts`, v2.5261, v2.5266 and v2.5268). Calls and texts from the company number land in a person's thread. The spine (`20261012010000_messages_spine.sql`, v2.5258) made `messages`, and this migration adds what a call or a text from Quo carries, the webhook's one write, and its memory of the deliveries it took. Nothing calls any of it until the `quo-webhook` and `quo-send` edge functions are deployed.

## What it does

1. **`messages` gains six columns.**
   - `quo_id`: Quo's id for the line. That is a message's id, or a call's id for every event of the call. A group text from Quo's app is the id and the number. A plain unique index (`messages_quo_id_key`) backs it, because an upsert's `ON CONFLICT (quo_id)` needs the whole index. The lines with no Quo id are nulls, which never collide.
   - `recording_url`, `transcript`, `summary` and `duration_seconds`: these belong to a call, a voicemail or a missed call only (`messages_call_columns_on_calls`), and a length is never negative (`messages_duration_known`).
   - `delivery`: delivered, undelivered or failed (`messages_delivery_known`), and only on a text we sent (`messages_delivery_on_texts`).
   - `quo_rev`: how many times `quo_write_line` wrote the line. It defaults to 0.
   - A Quo id is never blank (`messages_quo_id_usable`).
   - Each constraint is added `NOT VALID`, then validated.
2. **`quo_write_line(quo_id, rev, row)`** is the webhook's one write. `row` is the line the kernels merged, as `messages` columns by name.
   - With a null `rev` (the webhook found no line), it inserts, or does nothing when a line arrived meanwhile.
   - With a `rev`, it updates only when `quo_rev` still equals it, and adds one.
   - It returns `written`, the line's `id` and its new `rev`. When `written` is false, nothing changed. The webhook reads the line again, merges again and writes again.
   - Two of Quo's events for one call can arrive at once (Quo promises no order), and this way neither writes over what the other added.
3. **`quo_place_number(value, name)`**: the contact a number from Quo lands on, by `contact_for_channel`, with the channel it came on and when that number sent STOP. A number nobody has makes an unknown contact named `name` (the kernel's `unknownContact`) with that one phone, and `made` is true. The number's key is locked for the transaction (`pg_advisory_xact_lock`), so two events for one new number at once make one contact.
4. **`quo_webhook_ids`** (`id` text primary key, `seen_at`) holds the `webhook-id` of each delivery the webhook took in the last 28 hours. Quo retries a failed delivery for about 27 and a half hours.
   - `quo_webhook_claim(id)` takes a delivery. It returns false when the id was taken in the last 28 hours. An older id is taken again. The insert is the lock, so two copies arriving at once are taken once.
   - `quo_webhook_release(id)` gives one back after a failure, before the webhook answers 500.
   - `quo_webhook_ids_forget(keep)` drops what is older than `keep` (28 hours) and says how many went.
   - Indexed by `seen_at`.
5. **Who reaches it.**
   - The office reads the new columns as it reads `messages`: the spine's policy and its `SELECT` grant. It writes none of them, since no column grant was added.
   - `quo_webhook_ids` has RLS with no policy and every privilege revoked from `anon` and `authenticated`. The service role holds `SELECT`, `INSERT` and `DELETE`.
   - The five functions are `SECURITY INVOKER`, and only the service role may execute them.
   - The house fences run at the end (`apply_read_only_write_blocks`, `apply_read_only_stmt_blocks`, `apply_digital_twin_write_blocks`).

## Safety

- `SET lock_timeout = '3s'`. Adding nullable columns and a constant-default `quo_rev` is metadata-only. The unique index and the validations read `messages`, which holds no Quo lines yet.
- Idempotent: `ADD COLUMN IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, constraints behind `pg_constraint` checks, `CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`. The bed applies the file twice.
- Stacked on the spine's migration, which must be pushed first.

## The bed

`npm run test:pg:quo-messages` (`scripts/pgtest-quo-messages.sh`, `supabase/tests/quo_messages/20_scenario.sql`, and a line in `scripts/sql-beds.txt`) checks these things:
- a text Quo sends twice is one line;
- `quo_write_line` writes over the revision it read and refuses a stale one, and after a re-read the summary and the transcript both stand;
- the new columns keep their rules;
- `quo_place_number` makes one unknown contact for a new number, lands the same number on it again, lands a known number on its contact with its STOP, and refuses a word;
- the webhook takes a delivery once, gives one back, takes an id past 28 hours again and forgets the old ones;
- the office reads the new columns and writes none;
- nobody signed in reaches the memory or the functions.

Docker is not reachable on the office Mac, so the bed runs in the SQL beds workflow.
