# 20261111230000_card_sizes.sql (2026-11-11, v2.6956)

The sizes of the business card the company offers, and a person's pick among them (punch list #313; `to-dos/cards-and-footers/README.md` → *A larger card*). A size is another setting of the card's back: a larger photo, or larger words (`src/lib/brandKit/sizes.ts`). The front and the email footer do not change, and any size is drawn in any look.

## What it does

1. **`users.card_size text`**: the size a person picked, by its name in the code (`standard`, `photo`, `text`). Null means the company's default. `users_card_size_short` holds it to 40 characters.
2. **`GRANT UPDATE (card_size)`** to `authenticated`, by name, as the card's other columns were.
3. **One row in `app_settings`, `card_sizes_v1`**: a JSON object in `value_text`, `{"approved": [...], "default": "..."}`. It is seeded with the three sizes on and the standard card as the default, since the owner, asked which sizes to offer, said all three on 2026-11-11. `ON CONFLICT DO NOTHING`: a later push never overwrites what he has switched since.

## Why the shape

- **A row of its own, apart from `card_looks_v1`.** Saving the looks never rewrites the sizes, so a tab left open on an older build cannot drop them. The migration is then a plain insert, with no edit of another row's JSON.
- **The pick is not held to a list in the database.** A pick the owner has since switched off draws as the default (`resolveSize`). So switching a size off needs no write to anyone's row.
- **No new policy.** A person writes their own row and the office anyone's, through the two policies that carry a name and a phone. Any signed-in person reads `app_settings` and only a dev writes it ("Devs can manage app settings"), which is who the owner's card is for.
- **The sizes themselves are code, not rows.** A size is numbers a test holds (`sizes.test.ts`: every size holds a long name, a title and three lines inside the safe margin, in every look). A row could not carry that promise.

**Tables**: none created, so no fence call is owed. **Data**: one settings row is added when absent. **Lock**: a nullable column and one CHECK take a brief `ACCESS EXCLUSIVE` lock on `users`; the CHECK scans a small table whose new column is all null. With `lock_timeout = '3s'` a busy moment fails fast and the push is retried.

**Apply**: `supabase db push` from a clean checkout of `main` after this merges. The client reads the column and the setting fail-soft, so before the push nobody is offered a size and the cards draw as they did. Client first, then the push.

## Verify

Tried before the PR on a local Postgres 15 with stand-ins for `users` and `app_settings`: the file applied twice; with the setting changed between the two runs, the second left it as changed; the column took `text` and refused a 41 letter name; the looks' row was untouched.

**Check** on prod after the push:

```sql
select column_name from information_schema.columns where table_schema = 'public' and table_name = 'users' and column_name = 'card_size';
select value_text from public.app_settings where key = 'card_sizes_v1';
```

One column, and the setting with three sizes and `standard` as the default.
