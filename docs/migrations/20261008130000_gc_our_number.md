# 20261008130000_gc_our_number.sql (2026-10-08, v2.4923)

GC mode, the Board's B5-a. The plan is `to-dos/gc-mode/mockups/board-b5.md` on branch `spike/gc-mode`, approved 2026-10-08, with calls C, D, S and W as recommended and M and H to the owner at their defaults.

It puts **our number** (the general conditions, contingency and fee we add on top of the trades) behind its own door, and makes the tables B5's screens write. It is additive and idempotent. No screen reads it yet: B5-b to B5-d do.

## What it does

1. **`gc_money_team()`**, the money audience named once: dev, the leaders (`master_technician`) and the controller.
   - It is written out as `role IN (…)`, so the one place that says who sees money reads plainly.
   - The client's copy is `GC_MONEY_TEAM` / `canSeeGcMoney` in `src/lib/gc/access.ts`. `access.test.ts` reads the newest migration that defines the function and fails when the lists differ.
2. **`gc_project_money`**: one row per GC project (`project_id` PK → `gc_projects`), holding the three inputs with range checks, `updated_by` and `updated_at`.
   - One `FOR ALL` policy on `gc_money_team()`; `anon` is revoked; the training-mode and twin blocks are applied.
   - **The expand step**: each project's three values are copied from `gc_projects`. Those columns stay, unwritten, until B6-a drops them (the contract step, call S).
   - Since door 1, those columns have been open to `gc_office_team()`, estimators included. On prod they are all 0 and nothing writes them, so nothing has leaked.
3. **Carry**, on `gc_trade_packages`:
   - `carried_invite_id` and `carry_budget`;
   - a composite FK, so the carried ask must be on this trade (`(carried_invite_id, id)` → `gc_invites(id, package_id)`, beside a new `UNIQUE (id, package_id)`), with `ON DELETE SET NULL (carried_invite_id)` (Postgres 15+; prod runs 17.6);
   - a check that the two are never both set.
   - The office team writes it (call C).
4. **Bid tabs**: `gc_bid_tabs` (the day shared, and whether names show) and `gc_bid_tab_views` (who opened it, written by the Portal's P5e). Both are dev only while the Board is built, like B1's tables.
5. **The outcome functions**, all SECURITY INVOKER, so `gc_projects`' team policy is their gate:
   - `gc_mark_bid_sent`;
   - `gc_mark_won` (to `buyout`);
   - `gc_mark_lost`, with why from the five loss reasons, who won and a note;
   - `gc_bring_back`.
   - The plan named one function for both lost and brought back. Two read plainer.
   - Each stamps `public.app_today()`, and each refuses in words a project not in the right state.

Every date default is `public.app_today()`, never `CURRENT_DATE` (#4951).

## Verify after the push

```sql
-- 1. The table, its policy and its blocks.
SELECT polname FROM pg_policy WHERE polrelid = 'public.gc_project_money'::regclass ORDER BY 1;
-- Expected: digital_twin_write_fence_{delete,insert,update}, gc_project_money_team,
--           read_only_users_cannot_{delete,insert,update}.

-- 2. The backfill: every GC project has its row, and the values match.
SELECT count(*) AS projects, count(m.project_id) AS money_rows,
       count(*) FILTER (WHERE m.general_conditions <> g.general_conditions OR m.contingency_pct <> g.contingency_pct OR m.fee_pct <> g.fee_pct) AS differ
FROM gc_projects g LEFT JOIN gc_project_money m USING (project_id);
-- Expected: projects = money_rows, differ = 0.

-- 3. Nobody outside the money team reads it: one rolled-back read per role.
--    Repeat with a user of each role: dev, master_technician, controller (1 row each),
--    assistant, estimator, superintendent (0 rows).
BEGIN;
-- The claim first: its subquery reads public.users, which row security would hide after SET LOCAL ROLE.
SELECT set_config('request.jwt.claims',
  json_build_object('sub', (SELECT id FROM public.users WHERE role = 'estimator' AND NOT read_only LIMIT 1), 'role', 'authenticated')::text, true);
SET LOCAL ROLE authenticated;
SELECT count(*) AS rows_seen FROM public.gc_project_money;
ROLLBACK;
```

dev-mcp's `view_as` gives the same reading through the app: `read_rows gc_project_money` as the assistant's, estimator's and superintendent's sample accounts returns no rows, and as the controller's it returns the row. That works once the types and the catalog are regenerated after the push.

## Rollback

Not expected.
- To undo: drop the four functions, `gc_bid_tab_views`, `gc_bid_tabs` and `gc_project_money`, the two carry columns with their constraints, `gc_invites_id_package`, and `gc_money_team()`.
- The three old columns on `gc_projects` still hold the values, so nothing is lost.
