# 20260912052042_job_baselines.sql (2026-09-12, v2.3367)

Job baselines — what a job actually took, kept for the labor book (PR 2 of the Costs-tab refresh; owner: "collect labor baselines instead of guessing").

- `job_baselines` (one per job): bid, kept_at / kept_by (NULL = the billing trigger) / kept_on (`billed` | `kept`), job status, price, recorded team hours and wages, people, materials (supply-house splits + |card charges|), generated `hours_per_thousand` and `avg_wage_usd`, and a `grade` — `fixture` when the bid had count rows, else `per_thousand`.
- `job_baseline_rows`: the job's recorded hours allocated across the bid's count rows, weighted by the bid's predicted hours where the estimate had any (`weight_source = 'predicted'`), else by count.
- `keep_job_baseline(job, kept_by, kept_on)` — the internal keeper (SECURITY DEFINER, revoked from the API roles); returns false and keeps nothing when the job has no recorded hours. `keep_job_baseline_now(job)` — the Costs tab's **Keep now** door (dev / master / assistant / controller). Trigger `jobs_ledger_keep_baseline_on_billing` keeps one when `status` moves into billed / paid. `job_baseline_rates()` — hours-only rows (no wages) for the Labor tab's per-$1k reading, estimators included.
- RLS: wage roles read `job_baselines`; those plus estimators read `job_baseline_rows`; no direct writes. Back-fill: every billed / paid job with recorded hours.
- CREATE TABLE → ends with both `apply_read_only_write_blocks()` and `apply_read_only_stmt_blocks()`.

Client (v2.3367) reads the row on the Costs tab's baseline strip and the rates on Bids → Labor. Deploy order does not matter (the strip degrades to "not kept yet").
