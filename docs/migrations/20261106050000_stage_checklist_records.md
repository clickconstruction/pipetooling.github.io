# 20261106050000_stage_checklist_records.sql (2026-11-06, the stage checklist filed as a record, punch list #237 PR 3, v2.6571)

The record (`to-dos/stage-checklist-document/`, *A checklist is a record on the job, not a setting*), on top of `20261106040000_stage_checklist_signature.sql`. The rules are `src/lib/jobs/stageChecklist.ts` (when a list is complete) and `stageChecklistRecord.ts` (the record's words and standing); the shape is the signed hours statement's (`20261030030000_hours_statements.sql`).

- **`stage_checklist_records`**, the one new table: one row per job stage and version — `record_no` counted per job, `version` per stage, `record_id` `CL-<job number>-<n>` (the job number as the hours statement names it: the HCP number, else the Click number, else the id's first eight characters), the stage's name and kind, `state` (`filed` · `amended`), `filed_at` (the last answer's stamp) and who answered last, `snapshot` (`{ rows, skipped }` in the sheet's order, each row the question's words, sheet, why and adder, the pick, note, name and time, the signature's mode, printed name, time and PNG path, and the photo's name and Drive id), the counts (answers, signed, No), the amend stamp and reason, and the PDF's name, Drive id, filed time, reason and tries. Read by `can_report_stage_progress(job_id)`; no insert or update policy for anyone, since the two writers run as the owner; a dev deletes.
- **`stage_checklist_kind_of(name)`** (`IMMUTABLE`): the kind a stage line's name reads as, with the app's own stage words (`stageRank`): *rough…* → `rough_in`, *top out* / *stack out* → `top_out`, *trim…* / *finish…* → `trim_set`, else null.
- **`stage_checklist_record_settle(fixture)`** (`SECURITY DEFINER`): the one writer. It reads the stage's list as the sheet draws it (the company's live questions of the kind less the ones skipped on this stage, then the items added for it) and counts each answered when its live row has a pick, the signature where the author asked for one, and the photo where asked unless the pick is Not here — the SQL twin of `questionWaitsOn`. Complete and the latest record not `filed` → a new version with the next record number under the job's advisory lock, the rows as they stand, `filed_at` the latest `answered_at`. Not complete and the latest record `filed` → that record reads `amended` with the reason *A check was added or an answer taken back* (or *Every question was taken off or skipped*); the row stays as it was. Called by triggers on every write of `stage_checklist_answers`, on a job item's insert or retire and on a company question's insert, retire or toggle change (every stage of the kind that holds a record), and on a skip or a put back.
- **`amend_stage_checklist_record(record, why)`** (`SECURITY DEFINER`, EXECUTE `authenticated`): the office's Amend, by whoever `stage_checklist_may_author` says authors on the job, with a reason of three characters or more; a record already amended refuses.
- **The cron** is written again with every clause `20261106030000` carried and a seventh: the sweep runs while a record's PDF waits (`pdf_filed_at IS NULL AND pdf_tries < 5`). The `photo-save` function draws the PDF from the snapshot and files it in the job's photo folder, each version its own file, five tries at most.
- One table is created, so the file ends with the three fence calls, which lock only that table. The four new foreign keys take a short `SHARE ROW EXCLUSIVE` on `jobs_ledger`, `jobs_ledger_fixtures` and `users`; the triggers a short `ACCESS EXCLUSIVE` on three tables of a few rows; `lock_timeout` makes a busy moment fail fast.

Apply order: **push right after the merge** and before the Pages deploy finishes. The client reads the table in every checklist read (the sheet's, the read-out's, the Pipeline door's) and calls the RPC; `check:calls-ahead` sees both and labels the PR. The `photo-save` function is deployed after the push (`supabase functions deploy photo-save`), since it reads the table. After the push, `npm run gen-types:linked` as its own `chore(types)` PR.

A stage already complete when this file lands files on its next write, not at the push: nothing is backfilled, since the filing time is the last answer's stamp and a record no one pressed for should not appear overnight with a stale time. Prod held no complete stage on 2026-11-06.
