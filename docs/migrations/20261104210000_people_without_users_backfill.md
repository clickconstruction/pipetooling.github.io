# 20261104210000_people_without_users_backfill.sql (2026-11-04, v2.6517)

PR 3 of punch list #260: every People record has a users row. PR 1 (`20261104190000`) let a users row stand with no login behind it and PR 2 (`20261104200000`) made every new person one; this file brings the records already on the roster over — on prod 21 of them (17 live, 4 archived) on 2026-11-04.

- `backfill_users_for_people() → { linked, skipped_name_held, skipped_dev, skipped: [{ person_id, reason }] }`, `SECURITY DEFINER`, EXECUTE to `authenticated`; runs as the migration (no caller) and for a dev afterwards (`is_dev()`), refused with `42501` otherwise. For each People record with `account_user_id` NULL: a users row — `name`, the lower-cased address where no other users row holds it (else NULL; the record keeps its address), `phone`, `role` from the kind (`sub → subcontractor`, `helper → helpers`, the rest their own name), `archived_at` and `created_at` carried, `login_attached_at` NULL — and the link. Skipped and named: a record whose trimmed name another users row carries (any case) — the pay tables key on the name and `resolve_pay_person_id` reads `users.name → people.account_user_id` first, so a second users row on one name would re-point someone's pay; the desk's Link account or Combine folds it by hand — a record of kind `dev`, a blank name. Idempotent: a rerun finds nothing unlinked.
- The migration calls it once and prints the answer as a NOTICE in the push's output.
- `people.account_user_id` **stays nullable**: `people_account_user_id_fkey` is `ON DELETE SET NULL` (`invite-user`'s replace of a pending invite deletes its users row) and `combinePeople` nulls a source's account before moving it, so a NOT NULL would refuse both. `roster_people` keeps `account_kind 'external'` as the guard that shows a straggler.

No table is created, so no fence calls. Apply order: push after the merge (no client call lands ahead of it); then regenerate `src/types/database.ts`. After the push, People → Users shows the 17 live records as rows with the *no login* chip under their kind and the 4 archived ones under Archived, and the desk's Merge a duplicate finds no roster-only subs (PR 5 re-points it at no-login users through `merge_user_accounts`).
