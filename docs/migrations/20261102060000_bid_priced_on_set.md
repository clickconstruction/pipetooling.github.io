# 20261102060000_bid_priced_on_set.sql (2026-11-02, v2.6342)

Plan sets by part, the bid (punch list #239, PR 4). The design's third rule, *a bid pins; a job follows*, had no column and no hand-off: a bid carried set rows (`bid_plan_sets`, v2.6168) and the link the robot reads, but nothing said which set the price stood on, and a job opened from the bid started with an empty Plans subfolder stamped on it by the folder maker. This migration gives the bid its pin, gives the bid form a read of what its jobs build from today, and carries the set across when a job is opened from the bid.

## What it does

**`bids.priced_on_set_id`**: the `bid_plan_sets` row the bid was priced on, `ON DELETE SET NULL`. Null means *the set the robot reads* (the row carrying `plans_link`, else `plans_link` itself), so every old bid reads sensibly and nothing is backfilled. **Priced on this set** on the bid form writes it.

**`plan_set_link_key(text)`**: the client's `samePlanLink` in SQL, so two spellings of one Drive link (a `?usp=` tail, a trailing slash, surrounding space) compare equal in the trigger and the client alike.

**`list_bid_jobs_plan_state(uuid[])`**: for each job opened from the bids given, the part it names and the set that part builds from today (name, kind, date, link). `SECURITY DEFINER`, for the office and estimators who may price the bid (`can_access_bid_for_pricing`), since an estimator reads no job row, the same reason `list_bid_jobs_opened` (v2.5659) exists. The bid form reads it for the amber note when a part moved on past the set the bid was priced on.

**`jobs_ledger_seed_part_from_bid`** (`AFTER INSERT ON jobs_ledger`): a job with a `bid_id` and no part takes the bid's set. The set is the pinned row, else the row carrying `plans_link`, else `plans_link` itself as a set named *Plans*. On a development the job **joins a part already building from that same set** (the same building, already in the register, so no second part appears); else a part named after the job is made (or joined, when the site already has one by that name) and, when it builds from nothing yet, seeded with the set as `issued` from `gc`, dated the bid set's date, with the memo *From B398, the set it was priced on · <the row's memo>*. The job then names the part, and the existing `BEFORE UPDATE` mirror (`jobs_ledger_mirror_plan_part`) writes `job_plans_link`. `AFTER INSERT` because a job's own part references the job row. Best effort: a failure is a `WARNING` in the log and the job is saved as it was, the way the client carries the bid's budget. A trigger rather than a client call, so the hand-off works from every door that makes a job (the New Job form, Dispatch's *Open the job*, a robot) and the job form, which another card edits this week, stays untouched.

## What stays

`bid_plan_sets` and `bids.plans_link` are untouched; the robot's link stays the robot's. A job made with no bid, or from a bid with no plans, changes nothing. A job that already names a part (`plan_part_id` set on insert) is left alone.

## Checked before the push

Idempotent (`IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP TRIGGER IF EXISTS`). The trigger body is wrapped in `BEGIN … EXCEPTION WHEN OTHERS` so no job insert can fail on it. No new table, so no fence calls. The client read of `list_bid_jobs_plan_state` is labelled *push right after the merge* by `check:calls-ahead`; the column write refuses in words until the push.
