# 20261110230000_bill_lines_sweep — what the bill lines sweep needs of the database (v2.6882, punch list #298 PR 2)

**File**: `supabase/migrations/20261110230000_bill_lines_sweep.sql`
**Builds on**: [`20261109170000_supply_paper_lines`](./20261109170000_supply_paper_lines.md) (the papers and their lines), [`20261109210000_supply_paper_save`](./20261109210000_supply_paper_save.md) (the office's two presses), `20261030010000_supply_bill_read` (the ledger of reads)

## What it adds

The edge function `bill-lines-sweep` ([`EDGE_FUNCTIONS.md`](../EDGE_FUNCTIONS.md#bill-lines-sweep)) reads the bills on file from the PDF each row links and writes their papers as the service role. This file is the database's half.

- **`supply_bill_holds`**: one row per bill the sweep could not give a paper. `invoice_id` is the key and goes with its bill (`ON DELETE CASCADE`). `why` is one of `reading · link · cannot_open · not_readable · too_big · number_not_in_file · not_a_bill · statement · refused · cut · failed`; `note` is the reason in a sentence (what Drive answered, which numbers the file does hold); `drive_file_id` and `seen_key` are the file and the folded number the hold was made on, so a person who changes the link or the number makes the bill due again; `tried_at` and `tries` pace the retries. A row held as `reading` is a run's claim on a file: a second run's insert on the same key loses, so two runs never read one file. A bill that gets its paper loses its row. Office roles read (`is_office_staff()`), the service role writes, the four fences close it.
- **`supply_papers.text_layer`** (boolean, nullable): `true` when the PDF had a text layer read whole and every part code was checked against it, `false` for a scan or a picture, `null` when it is not known (a paper the form wrote, or a text read that ran out of time). The measure after this PR counts scans against text layers from it.
- **One paper per bill**: the unique index `supply_papers_one_per_invoice` on `invoice_id` where it is set. `supply_paper_save` already kept one paper a bill; the index makes a second writer lose (the sweep reads that as *theirs stands*) instead of doubling a bill's lines. The plain index `supply_papers_invoice_idx` on the same column is dropped, since the unique one serves its reads.
- **`supply_bill_reads.source`** (`form` · `sweep`, default `form`): whose read a row is. `bill-read` counts its own for the office's cap of 150 a day; the sweep counts its own for its cap of 600.
- **The switch** `app_settings.bill_lines_sweep_on_v1`, seeded `'true'`: the card's call 1, a bill reads by itself. The cron runs only while it reads `'true'`.
- **The cron** `bill-lines-sweep`: `6,16,26,36,46,56 * * * *`, a `net.http_post` to `/functions/v1/bill-lines-sweep` with `{ "sweep": {} }` and the cron secret from Vault, scheduled the way the file index sweep is. Unscheduled first, so a second run leaves one row.

## Locks

`SET lock_timeout = '3s'` opens the file. The two `ALTER TABLE … ADD COLUMN` statements are catalog changes (a constant default), and the unique index is built on a table of a few rows; `supply_house_invoices` is touched only by the new table's foreign key.

## Tested

`npm run test:pg:bill-lines-sweep` (`supabase/tests/bill_lines_sweep/20_scenario.sql`), on a copy of the whole schema: the file applies twice; a second claim on a bill being read is refused; a bill takes one paper and papers with no bill are not limited; a read is the form's unless it says the sweep's; the switch is on; the cron is one row; the office reads the holds and writes none, a helper reads none; a deleted bill takes its hold with it.

## Deploy

`supabase db push` after the merge, then `bash scripts/deploy-functions.sh bill-lines-sweep bill-read`. No client calls ahead of it. The cron starts with the push; until the function is deployed its calls answer 404 and read nothing.
