# 20261118040000_trip_numbers.sql (2026-11-17, v2.7703)

A number for each trip. Punch list #379. No screen shows it yet: the client that follows puts it beside a trip's days everywhere a trip is named, and adds a link that opens one trip.

A trip is told by its days, which works on a screen and is hard to say in a text or to cite on a bill. So each trip gets a short number on its site: Trip 1, Trip 2. The owner asked for it on 2026-11-17, before *Put on a bill*, so a bill line has something stable to cite.

## The rules of the number

- **The database hands it out** when the trip is made. Nobody types it.
- **It never changes.** An update that names another number leaves it as it was. Since v2.7884 a trip that moves to another home takes a number there ([`20261118233000`](./20261118233000_combine_carries_job_held_trip.md)).
- **It is never given to another trip.** A deleted Trip 5 does not hand 5 to the next trip, so "Trip 5" on a bill means one trip for good.
- **It runs in the order trips are made**, not the order they went out. A trip filed later from an old ledger takes the next number. It is a handle, not a rank.
- **A deleted trip put back gets its number back.** The undo saves the same trip under its own id and asks for the number it had. The number is kept only when the site handed it out before and no trip holds it now. Any other number asked for is ignored.

## What it adds

| Piece | What it is |
|---|---|
| `trip_number_counters` | The last number each site handed out, or each job that holds its own trips. A table, not `max(trip_number)`, because a deleted trip's number must stay spent. Row security is on with no policy and no grant: the trigger alone touches it. |
| `trips.trip_number` | The number. Unique on a site (`trips_number_on_development`) and on a job that holds its own trips (`trips_number_on_job`). |
| `trips_take_number` | The trigger, a definer. On insert it locks the site's counter row, so two trips made at once take two numbers. On update it holds the number. |
| `trip_save` | Restated from `20261118030000` with `trip_number` in its reply, and `p.trip_number` passed to the insert for a trip made again. A dry run of a new trip names no number: it is handed out when the trip is made. |
| `trip_phone_state` | Restated from `20261118030000` with `trip_number` on the caller's trip and on each open one. |

Trips made before this file are numbered in the order they were made, and each site's counter is set past them.

## The bed

`supabase/tests/trips/40_numbers.sql`, run by `scripts/pgtest-trips.sh` after the first two scenarios, with this file applied a second time. Numbers 1, 2, 3 on a site and 1 on another; a change keeps the number; an update cannot change it; the highest deleted and the next trip takes the number after it; a deleted trip put back with its number; a number never handed out, and one a trip holds, not taken on request; a job's own count; the phone's trip numbered and the phone told; and the counters closed to a signed-in reader.

## Order

Additive and idempotent. One new table, so the four fence calls close the file. It restates two functions from `20261118030000_trips_phone.sql`, so it is pushed with or after that file, never before. The live client does not name `trip_number`, so the push can come any time after the merge. **The client that shows the number must not reach the live app before the push.**
