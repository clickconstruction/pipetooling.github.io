# 20260909200531_bid_review_stamp.sql (2026-09-09, v2.3201)

The Review step of the bid flow gets a record. Three nullable columns on `bids` — `reviewed_at timestamptz`, `reviewed_by uuid → users ON DELETE SET NULL`, `review_note text` — hold the **current** review (the history is the method-less note the button also writes to `bids_submission_entries`, which never moves the chase clock per v2.2413). Plus `twin_no_review_guard`, a BEFORE INSERT OR UPDATE trigger on `bids` that refuses any change to the three columns from an `is_digital_twin()` session — reviewing is a human act, same shape as `twin_no_send_guard` (20260829033440).

- **Additive and idempotent**: `ADD COLUMN IF NOT EXISTS` ×3, `CREATE OR REPLACE FUNCTION`, `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER`. No new table, so no fence appliers; no RLS change (the existing `bids` UPDATE policies cover the columns; primary scoping and superintendent read-only stand); the read-only statement trigger already blocks training-mode users.
- **Apply**: `supabase db push` right after the v2.3201 merge, then `npm run gen-types:linked` (the PR hand-adds the three columns to `database.ts` so the regen is a no-op). Order: the client is fail-soft in either direction — before the push the strip reads Review as *not tracked* and Mark reviewed reports "Save didn't apply"; after the push, and with an old client, the columns simply go unread.
