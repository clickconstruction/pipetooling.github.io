# 20261102160000_plan_set_changes.sql (2026-11-02, v2.6356)

What changed between sets of plans. A `plan_sets` row (punch list #239, PR 1) carried a name, a kind, a source, the date on the sheets, the day it came, a link, a memo and the set it replaces, and nothing for what moved from one set to the next. On the real site the memo ended up holding who sent the set and where the file is, and the one thing a crew wants to know about an updated set, what moved, had no field. The owner, 2026-11-02: *I don't think we do a good job explaining in the notes what changed between plans and this seems like the most important thing to record.*

## What it does

**`plan_sets.changes text NOT NULL DEFAULT ''`**: what changed from the set before it, in the office's words. Empty on a first set, or until someone writes it. The memo keeps its own job: who sent the set, when, and where the file is.

**`plan_part_switch_words(part, set, old)`** (PR 6's History words) now ends with ` · what changed: <changes>` when the set carries them, so the line a part switch writes on every job naming the part reads *Plans · the Lodge now builds from Lodge addendum 2, dated Aug 11, 2026 · replaces Lodge addendum 1 · what changed: the door schedule and the MEP layouts moved; the main stair and the roof deck are new*. A set with no change words writes the line as before. The trigger `plan_parts_history_on_switch` is untouched; it reads the set row whole, so the new column reaches it.

## What stays

No new table, so no fence calls. The mirror onto `job_plans_link`, the papers columns (`20261102010000`) and the part-switch trigger are untouched. The client reads the column through `planSetsIo.ts`'s column list and writes it from the New set form and the *Write what changed* press.

## Checked before the push

Idempotent (`ADD COLUMN IF NOT EXISTS`, `CREATE OR REPLACE`). A constant default on a new column is a catalog change in Postgres 11 and later, so the `ALTER` holds its lock for a moment; `lock_timeout = '3s'` fails fast if a long read holds the table. The `COALESCE` keeps the function safe should the column ever read null.

## After the push

The client's column list names `changes`, so **push right after the merge**, before the Pages deploy finishes: PostgREST answers a missing column with a 400 that breaks the whole Plans read. Regenerate nothing by hand; `src/types/database.ts` and the dev-mcp catalog carry the column in the same PR, and `supabase functions deploy dev-mcp` serves it. The live check: on a ZZ Test development as the dev, add a set with *What changed* filled and *Add the set and build from it*, then read the site's History for the line ending in *what changed: …*; press *Write what changed* on an older set and read it back; delete every ZZ Test row after.
