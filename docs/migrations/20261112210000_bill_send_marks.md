# 20261112210000_bill_send_marks.sql (2026-11-12)

Bills sent, punch list #327, PR 3 (v2.7053). The page at `/bills-sent` draws one line each time a bill leaves, from
`sent_documents`. This is the read under each email line's words about arriving: *Delivered 9:28 AM*, *Opened*,
*Bounced. It did not arrive.*, and under a paid bill's *Paid Nov 9*. One read, no table.

## Why a function

Whether an email arrived lives on `email_send_log`. A dev and the owner read every row of it. The assistant and the
controller read only its RFQ and GC statement rows, so the people who send the bills could not see that one bounced.
`sent_copy_stamps` (20261014140000) answers *opened* and *paid* for the Messages thread and says nothing of delivered
or bounced. Widening the log's policy would open every email the app sends; this read answers only for the copies the
caller can already read.

## What it does

**`bill_send_marks(p_ids uuid[])`** answers one row for each sent copy among `p_ids`: `id`, `last_event`,
`last_event_at`, `email_type`, `paid_on`, `paid_how`.

- `last_event` and `last_event_at` are the log's, joined by the copy's `resend_email_id`, which is unique on the log:
  `sent`, `delivered`, `delivery_delayed`, `bounced`, `complained`, `opened` or `clicked`. Resend's webhook keeps only
  the last event, so `opened` means it was delivered and then opened. Null when the copy was not an email or its log
  row is not written yet: not known, never *did not arrive*.
- `email_type` is the log's type. `gc_statement_scheduled` is a statement the app sent on a schedule, and the line
  then reads *by the app, on …'s schedule*.
- `paid_on` and `paid_how` come only for a copy of a `jobs_ledger_invoices` row whose `status` is `paid`: the newest
  payment's day (its `paid_on`, else the day it was entered, in Chicago) and its `payment_type`.
- A copy with nothing to say still comes back, with nulls.
- Only a reader of `sent_documents` gets rows: `is_office_staff()`, the table's SELECT policy (the dev, the owner, the
  assistants and the controller). Anyone else reads no rows.
- `SECURITY DEFINER` with `SET search_path = public`. `REVOKE ALL … FROM PUBLIC, anon` and `GRANT EXECUTE … TO
  authenticated, service_role`.

No table, so no house calls and no fences. It starts `SET lock_timeout = '3s'`. `CREATE OR REPLACE`, so a second run
changes nothing.

## Checked before the push

The SQL bed `bill-send-marks` (`npm run test:pg:bill-send-marks`) runs every migration on Supabase Postgres 17, then
this one a second time, then the scenario. Docker does not run on the office Mac, so it runs in the SQL beds workflow.

- The controller cannot read a bill's row of the log itself, and reads its mark here.
- A delivered bill that was paid reads delivered, with its paid day and how.
- A bounced send reads bounced. The same bill sent again and opened reads opened, at the time it was opened.
- A statement that went on the schedule reads its type.
- A printed pay sheet, and an email whose log row is not written yet, come back with nulls.
- Only the copies asked for come back. An estimator reads none. anon cannot run it.

*push right after the merge*. The call is best effort: before the push it is refused and the lines draw with no word
