# 20261113000000_task_spot_photos.sql (2026-11-12, v2.7064)

The giver's photo of the spot (punch list #328, PR 6 of 8). A task's place says where. A photo says what it looks like. Until now only the person doing a task could put a photo on it, on a day's card, and never when the task was made.

## Why it is not a task photo

`task_photos` are the doer's: they count toward the finishing photo a task can ask for, they ride the day's card as proof of the work, and the Drive sweep files them. A giver's picture among them would read as proof of work, and would let a task that asks for a finishing photo close on a photo taken before it began. So this photo has its own column and its own bucket, and none of the doer's rules see it.

## What it does

1. **`spot_photo_path text`** on `checklist_items` and on `checklist_tech_tree_group_tasks`, each with a check that a path is 1 to 300 characters or null. A roadmap task's card reads its photo through `roadmap_group_task_id`, as it reads its place.
2. **The bucket `task-spot-photos`**: private, 2 MB a file, JPEG, PNG or WebP. An object is named `item/<checklist_item_id>/<photo_id>.jpg` or `roadmap/<roadmap_task_id>/<photo_id>.jpg`, so the gate reads its task from the name.
3. **`can_write_task_spot_photo(name text)`**, SECURITY DEFINER, open to `authenticated`: the task's own write rule, `can_write_task_criteria`, read from the name. A name of any other shape is refused, never raised on: three parts exactly, a known first part, a task id that matches the uuid pattern before it is cast.
4. **Three policies on `storage.objects`** for this bucket alone:
   - insert and delete: `can_write_task_spot_photo(name)`.
   - select: the task's own table is asked whether the caller can read the task, so the task's row rules decide. A roadmap task's photo is also read by whoever has the list row made from it. The id is compared as text, so a name of another shape matches nothing.

## Who may do what

- **Put or remove a photo:** the office, or the task's maker. For a roadmap task, whoever may edit that roadmap.
- **See it:** whoever may read the task: the office, its maker, its assignees.
- **Nobody else**, and no other bucket's objects are touched by these policies.

No new table, so no fence calls. The Drive sweep does not file these: the picture lives in the bucket for the task's life. Removing a task leaves its picture in the bucket with nothing pointing at it.

## Release order

Merge, then `bash scripts/db-push.sh`. Safe in either order: before the push the client's reads fail by themselves to "no photo", and a photo taken says it did not save.

## Checked

Applied twice to a throwaway local Postgres 15 with stub tables, then exercised as four made-up people: the maker and the office may put the photo, the doer may not, the planner may for a roadmap task, five malformed names are refused without an error, the doer sees the task's photo and a roadmap task's through the list row made from it, a stranger sees none, the doer's delete removes nothing, and another bucket's objects stay closed. The stub is not the app's schema and the app runs Postgres 17 with Supabase's storage schema, so this checks the SQL and its logic, not the fit with the real tables.
