# 20260916150000_ar_applied_deposits_income.sql (2026-09-16, v2.3514)

Deposits applied in Accounts Receivable count as Income (`docs/recent-features/v2.3514.md`). One switch, one small table, four functions, one trigger. **No existing table, column, function or policy changes.** Idempotent and additive.

- **`app_settings.ar_applied_deposits_count_as_income`** seeded `'false'`; policy `master_or_dev_update_ar_applied_income` lets `is_master_or_dev()` UPDATE that one key (mirror of `master_or_dev_update_accounting_label_auto_approve`).
- **`mercury_transaction_ar_income_labels`** (new): `mercury_transaction_id` PK → `mercury_transactions` CASCADE; `job_id` → `jobs_ledger`, `invoice_id` → `jobs_ledger_invoices`, `payment_id` → `jobs_ledger_payments`, all SET NULL; `source` `'trigger' | 'backfill'`; `labelled_at`. RLS on; SELECT for `is_office_staff()` (the AR modal is an assistant surface); **no client write policies** — the SECURITY DEFINER functions own every write. Ends with both `apply_read_only_write_blocks()` and `apply_read_only_stmt_blocks()`.
- **`ar_label_deposit_income(p_mercury_transaction_id, p_job_id, p_invoice_id, p_payment_id, p_source)`** → boolean, SECURITY DEFINER, `service_role` only. Returns false and does nothing when the switch is off, the deposit is not a positive non-duplicate transaction, no `income_part_i` label exists, or **any assignment already exists** (never overwrites a rule's or a person's label). Otherwise inserts the `mercury_transaction_drag_sort_assignments` row for Income and upserts the sidecar.
- **`ar_unlabel_deposit_income(p_mercury_transaction_id)`** → boolean, SECURITY DEFINER, `service_role` only. Only acts when a sidecar row exists. If the current label is no longer Income (someone relabelled it) it deletes just the sidecar. If any `jobs_ledger_payments` row still points at the deposit it does nothing. Otherwise deletes the assignment and the sidecar.
- **`jobs_ledger_payments_ar_income_label_tr()`** + trigger **`jobs_ledger_payments_ar_income_label`** AFTER INSERT OR UPDATE OF `mercury_transaction_id` OR DELETE, FOR EACH ROW. INSERT with a bank link → label; UPDATE that changes the link → unlabel the old, label the new; DELETE → unlabel. The whole body is wrapped in `EXCEPTION WHEN OTHERS THEN RAISE WARNING`, so a labelling failure can never abort the payment write it rides on. Runs after the existing `jobs_ledger_payments_recompute_pm`, `…_to_activity_*` and `enqueue_payment_made_email_ai` triggers; touches none of their tables.
- **`backfill_ar_applied_income_labels(p_dry_run boolean DEFAULT true)`** → jsonb `{ok, dry_run, count, dollars}` or `{error}`, SECURITY DEFINER, EXECUTE for `authenticated` + `service_role`, gated `is_master_or_dev()`. Dry run counts every positive, non-duplicate transaction with at least one payment and no assignment. The real run requires the switch already on and labels each through `ar_label_deposit_income`, `source = 'backfill'`, provenance from the deposit's earliest payment.

Apply order: **client first**, then `supabase db push`, then `npm run gen-types:linked`. Before the push the Banking switch renders disabled with *(not live yet)* (no `app_settings` row) and the AR modal's sidecar read simply errors into "no clause". Dry-run against prod inside `BEGIN … ROLLBACK` through the pooler on 2026-09-16: table, trigger and functions created and rolled back; confirmed absent afterwards.
