# 20261101183219_gmail_mine_untag_and_ties.sql (2026-11-01, v2.6292)

**What it does**: two columns on `email_tag_threads` for Messages → My email (punch list #230, a fix after PR 4's [`20261101154949_gmail_mine_follow_cron.sql`](./20261101154949_gmail_mine_follow_cron.md) and PR 6's [`20261101172319_gmail_mine_follow_window.sql`](./20261101172319_gmail_mine_follow_window.md)), so `gmail-mine`'s untag and its tags' ties stand on the row instead of on guesses.

- `email_tag_threads.untagging_at timestamptz` (with its comment): when an untag began taking the conversation off its job; null otherwise. The untag sets it before it deletes a line. The follow never picks a row that has it, and asks again before each row it reads and before anything lands, so a run that reaches the conversation mid-untag lands nothing back. The row still goes last, so an untag that stops leaves it, marked, for the next untag to find and finish. Tagging the conversation again clears it.
- `email_tag_threads.tied_line_ids uuid[] NOT NULL DEFAULT '{}'` (with its comment): the lines of the boxes (`messages.id`) that this conversation's tag or its follow tied to the job, each recorded before its tie. A tag onto another job moves the person's own lines and these, and an untag unties these and no line someone tied by hand. Until now the two were told apart by `tied_by` alone, which a hand tie by the same person carries too. Every row tagged before this push reads `{}`.

Both columns come in one `ALTER TABLE`, so the table's lock is taken once, and the constant default writes no row (Postgres 11 and later store it in the catalog). No index: the follow reads `untagging_at` only on rows it already picked by person and window, and `tied_line_ids` only by the row's id. The cron's gate (`20261101172319`) is left as it is: a marked row in the window still lets the post go out, and the function passes it by.

**Tables**: none created, so no fence is owed. **RLS**: unchanged. The office team's one SELECT policy and its table-wide grant read the new columns, and nobody signed in writes them (`gmail-mine` writes them as the service role). Idempotent: each column only when missing.

**Tried before the PR** on a throwaway local Postgres 15, over an `email_tag_threads` built as `20261101083844` and `20261101172319` left it, with one row tagged before the push. Applied twice in a row: the second run skipped both columns with a notice. `tied_line_ids` read `uuid[]`, `NOT NULL`, default `'{}'::uuid[]`, and the old row `{}`; `untagging_at` read a nullable `timestamptz`; both carried their comments. With the row marked, the follow's `untagging_at IS NULL` found none; a tag's upsert on `(user_id, gmail_thread_id)` cleared the mark and wrote its record, and the row was found again. A null `tied_line_ids` was refused.

**Apply**: `supabase db push` from a clean checkout of `main` after this merges, with PR 4's and PR 6's migrations first if they are not pushed yet, **then** redeploy `gmail-mine` (`supabase functions deploy gmail-mine --no-verify-jwt`). The new function reads both columns, so deployed before the push it stops every tag and every untag at its first read of the row, before anything is written or taken off, and runs no follow. The push alone is harmless: the function before it never names either column, and a tag it makes in between records no ties.

**Check**: `select column_name, column_default, is_nullable from information_schema.columns where table_name = 'email_tag_threads' and column_name in ('untagging_at', 'tied_line_ids')` reads both. Once a conversation whose mail a box holds is tagged, its row's `tied_line_ids` names the box's line, and an untag leaves the row's `untagging_at` set until the row goes.
