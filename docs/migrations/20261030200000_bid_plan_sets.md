# 20261030200000_bid_plan_sets.sql (2026-10-30, v2.NNNN)

Plan sets on a bid, the ground (the owner's 2026-10-30 ask, item 3 of the Bids tab day: *multiple sets of plans can be uploaded all with their own name, memo, date, and link*). Until now a bid held one plans link, `bids.plans_link`: the Drive folder or file the robots read, the Plans panel searches and the Bid Board's plans icon opens. An addendum, a permit set or a GC's marked copy had nowhere to go but over the one link, or into the notes.

## What it does

**`bid_plan_sets`**: one row per set of plans on a bid — `name` (*Issued set*, *Addendum 2*, *Permit set*), `memo` (a line about it), `plan_date` (the set's own date, a civil date), `link` (a Drive folder or file link, the shape `bids.plans_link` takes), and what `plan-fetch`'s probe last read behind the link: `file_name` (one PDF's name, or *N PDFs* for a folder), `file_size` (the bytes in all), `file_count`, `checked_at`, `check_note` (the probe's reason when it could not read the link). `created_by`, `created_at`, `updated_at` (the house trigger). An index by bid, newest date first. The bid going away takes its sets.

**What stays**: `bids.plans_link` keeps meaning *the set the robot reads* — every reader of it (the robots' dispatch, `plan-fetch`, the Plans panel, the readiness line, the plans-waiting count) is untouched. A bid whose `plans_link` is on none of its rows reads as one set, the link on the bid itself, the way a bid with no `bid_count_sources` row reads as one CountTooling project; so nothing is backfilled and an old bid draws as it did.

RLS: `SELECT` gated by `can_access_bid_for_pricing(bid_id)`, as `bid_versions` and `bid_count_sources` are; `INSERT` / `UPDATE` / `DELETE` by the same gate and the five roles that fill the bid form's Plans section (dev, master, assistant, controller, estimator). `authenticated` reads and writes, `anon` nothing, `service_role` all. Three house calls at the end, since there is a new table.

## Checked before the push

The file is idempotent (`IF NOT EXISTS`, `DROP … IF EXISTS` before each policy and the trigger). No SQL bed: the table has no function of its own, and its policies are the two gates every bid table uses.

## After the push

Nothing to run. The generated types are hand-added for the new table (`src/types/database.ts`); the next gen-types chore regenerates them. The client starts reading and writing sets in the next PR (the bid form's Plan sets field and the Bid Board's picker); until then the table stays empty.
