# 20261121222237_uploaded_photos_bid_branch.sql (2026-11-21, a bid's photos on Documents → Photos and in the job's photo window, punch list #306 PR 9)

A photo added to a bid from the Bid Board's photos icon (`bid_photos`, `20261110195527`) showed in the bid's own window and nowhere else: the `uploaded_photos` view (`20261101084330`, the job branch `20261102171500`, the task branch `20261107093000`) had no branch for it, so Documents → Photos did not list it and a job won from the bid did not show it. Shipped as v2.8215; the rules are `src/lib/photos/uploadedPhotos.ts` and `src/lib/photos/jobPhotosFromBid.ts`.

- **Built on the live definition.** The view was read from prod with `pg_get_viewdef` on 2026-11-21 and held against `20261107093000`: the same six branches, `security_invoker` on. No open PR touched the view that day (#410's write-up photos and #413's photo spots add no branch). The other six branches here are that file's, word for word.
- **`uploaded_photos`** gains a seventh branch, `source = 'bid'`: a bid's photo that stands, which is `added_at` written and `removed_at` empty, the rows the bid's own window and the board's count read. `bid_id` is the bid and `job_id` is null, won or not, the way a text's picture on a bid already reads in the message branch. The photo's `name` is the `caption`; the bid's project name, customer and number ride `job_name`, `customer_name` and `bid_number`; `bucket` is `bid-photos`.
- **A won bid's job is not joined.** Two jobs can name one bid (two bids on prod do today), and a join on `jobs_ledger.bid_id` would hand the same photo back twice. The reader finds the job's bid instead: the Job photos window reads `jobs_ledger.bid_id`, then the view's rows for that bid.
- **One Drive file, one row.** The bid's window takes on any picture in the bid's photo folder as a `bid_photos` row, and a picture saved to Drive from a text lands in that folder, where the message branch already lists it by its line. The bid branch leaves out a row whose Drive file a text's picture carries, asked the way the message branch asks (a file, an image, its line readable). No such pair exists on prod today.

## How the view's security holds for the new branch

- The view is `security_invoker`, restated in this file, so every table under it is read with the caller's own rights and policies. The view grants nothing a table does not.
- **Who reads a `bid` row** is `bid_photos`' own select policy, `bid_photos_select`: `EXISTS (SELECT 1 FROM bids b WHERE b.id = bid_photos.bid_id)` under the caller's RLS on `bids`. That is the bid's own gate: dev, master, assistant, controller and estimator on every bid, a primary only on a bid they estimate, manage or made (`primary_scope_bids`). A superintendent, a helper and a subcontractor read no bid, so they read no `bid` row. The restrictive `archived_fence` on `bid_photos` closes the branch to an archived caller. `anon` has no grant on the view.
- **The joins widen nothing.** `bids` and `customers` are left joins under their own policies: a reader who may see the photo and not the customer keeps the row with an empty customer name.
- **The left-out rows widen nothing either.** The `NOT EXISTS` on `message_attachments` and `messages` runs under the caller's policies (`message_attachments_team`: the office team and the estimator). A reader who cannot read the line finds nothing there, so the row stays in the bid branch, where the reader could already read it from `bid_photos`. A reader who can read the line sees the picture once, in the message branch. Nobody sees a photo through the view that their own read of the table would refuse.
- **No job row is read** by the branch, so it says nothing about a job to a reader with no `jobs_ledger` read (an estimator).
- **The SQL bed** `bid-photos` (`scripts/pgtest-bid-photos.sh`, `supabase/tests/bid_photos/20_scenario.sql`) applies this file twice and asserts it: the view still `security_invoker`, no `anon` select, thirty columns; the office and an estimator read a bid's three standing photos and the text's picture once on its line; a primary reads the photos of the bid they manage (the text's picture as the bid's, since they cannot read the line) and none of another bid's; a primary on no bid, a subcontractor and a superintendent read no `bid` row; a training account reads as an estimator; a removed photo and a shot nobody added are not listed.

**No table is made**, so the fence calls are not needed; nothing here writes. `CREATE OR REPLACE VIEW` with the same thirty columns in the same order, so the file is safe to run twice.

Apply order: the client reads only columns the view already has, so a client ahead of the push lists no bid photos and breaks nothing; push after the merge. No types regen and no dev-mcp catalog rebuild: the view's columns are unchanged.
