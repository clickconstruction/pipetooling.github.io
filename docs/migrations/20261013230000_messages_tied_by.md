# 20261013230000_messages_tied_by.sql (2026-10-12, v2.5425)

Messages, residential R7 (`to-dos/gc-mode/messages/RESIDENTIAL_BUILD_PLAN.md` → R7 on branch `spike/gc-mode`): who tied a line to its job.

A line from someone with a star lands on the starred job as it comes in, because the Quo and email readers write the contact's default job. A person can also tie a line, or untie it, with `tie_message`. Until now the two looked the same in `messages`. So the New lane's **Which job?** could not tell a line the default took from one a person put there on purpose (`src/lib/followUp/newLane.ts`, `tiedByHand`, v2.5394).

## What it does

1. **`messages.tied_by`** (`uuid`, null, `REFERENCES users(id) ON DELETE SET NULL`): the user whose `tie_message` last set the line's job, an untie included.
   - It is null when nobody has: the line came in on the star, or on the person.
   - The readers and `set_default_job` never write it. A star moved later moves no line, as before.
   - A tie the service role makes stamps nobody, since `auth.uid()` is null there.
2. **`tie_message`** is recreated to set `tied_by = auth.uid()` in the same `UPDATE` that sets the job. It is otherwise exactly as the spine wrote it (`20261012010000_messages_spine.sql`). It stays `SECURITY INVOKER`, so the policies and the house fences still refuse training mode and a digital twin. Its `EXECUTE` grants are restated.
3. **`GRANT UPDATE (tied_by) ON messages TO authenticated`**: the office team needs the one column for the invoker's `UPDATE`, as cut 2's `back_by`. It is not in the `INSERT` grant, so a team note never arrives stamped.
4. **No index.** The New lane reads a contact's lines, which `messages_thread (contact_id, at)` already serves.

No new table, so there are no fence calls.

## Safety

- `SET lock_timeout = '3s'`. Adding a nullable column with no default is metadata-only on `messages`. Its foreign key briefly locks `users` and checks no rows, since every value is null.
- Idempotent: `ADD COLUMN IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION` with the same signature, and grants that can be restated.
- **Re-runs**: only the spine's bed runs the spine a second time, and it does so straight after the spine's first run. That second run's `REVOKE` on `messages` comes before this migration, so this column grant stays. No other migration defines `tie_message`.
- **Old clients**: the app does not read `tied_by` yet, and `tie_message`'s signature and answers are unchanged, so the client needs no deploy first.

## The bed

`npm run test:pg:messages-spine` (`supabase/tests/messages_spine/20_scenario.sql`, section 7) now also checks five things:
- the estimator who ties Elena's email is stamped on it;
- untying it stamps the estimator again;
- a line the reader writes on the star as it comes in carries nobody;
- the office team holds `UPDATE` on the one column;
- the line training mode and a twin tried to tie carries nobody.

The bed runs in CI on this PR (SQL beds), since no Docker or Postgres server is reachable from the office Mac.
