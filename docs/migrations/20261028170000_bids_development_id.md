# 20261028170000_bids_development_id.sql (2026-10-28, v2.6019)

Punch list #208, PR 1 — the development on bids. Adds `bids.development_id uuid references public.developments(id) on delete set null`, the same shape as `jobs_ledger.development_id` (v2.1198, `20260801100000_developments_on_jobs.sql`): deleting a development un-groups its bids and never deletes them. A partial index `idx_bids_development_id` (where the column is set) serves the Bid Board's house filter and the Development page PR 2 adds. The backstop `bids_development_master_match` (function `bids_development_master_match_fn`, fired on INSERT and on UPDATE OF `development_id`) mirrors the job's trigger **as it stands**: one company (v2.2984, `20260907010000_one_company_backfill_owner.sql`) made `jobs_ledger_development_master_match_fn` a no-op, and `bids` carries no `master_user_id` to compare against, so the body returns the row unchanged. The function and trigger keep the job's shape so a same-master rule, if multi-company ever returns, has one hook on each side. No table is created, so no fence calls.

Purely additive: the old client never reads or writes the column, so the push can land before or after the client deploys. The client that reads it (the Edit tab's Development picker, the Bid window's house line, the Bid Board's line, search and filter, New Job from a won bid, the suggestion by address) ships in the same PR; the `chore(types)` PR follows the push (`npm run gen-types:linked`). Until the types land, the client reads the column through the embedded `development:development_id(id, name)` join and writes it through the typed-subset payload (`src/lib/bids/bidFormPayload.ts`).
