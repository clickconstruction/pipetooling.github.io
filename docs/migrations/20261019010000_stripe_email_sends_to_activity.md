# 20261019010000_stripe_email_sends_to_activity.sql (2026-10-19, v2.5634)

Every Stripe bill email becomes a line in the job's trail. The invoice trigger (`jobs_ledger_invoices_to_activity`, 20260608010000) logs a bill's first send only, `invoice_sent` when `sent_to_customer_at` is first stamped; `send-stripe-invoice` appends a row to `jobs_ledger_invoice_stripe_email_sends` on every send, and that log had no trigger, so a resend from the row's Stripe **Resend** button made no line (the owner's catch on the Palmer row, job 251, after v2.5633 put the send in the activity box). The migration adds `jobs_ledger_invoice_stripe_email_sends_to_activity()` and its AFTER INSERT trigger: one `invoice_stripe_email_sent` event per send (*Invoice emailed to customer (Stripe)*, `detail.invoice_id` and `detail.source_id` = the send row, financial, the actor `auth.uid()` which is null for the service role), skipped when the invoice already has a sent event within two minutes, so a bill's first send keeps its one `invoice_sent` line. The backfill at the end gives the resends already logged since the 2026-06-08 backfill their line under the same guard, by `source_id`, so a second run changes nothing. No table, so no RLS fences; `SET lock_timeout = '3s'`. Apply with `supabase db push` after the merge; the client needs nothing (the box draws `invoice_stripe_email_sent` since v2.5633 and subscribes to the table's inserts). Proven by the bed `scripts/pgtest-stripe-email-sends-trail.sh`.
