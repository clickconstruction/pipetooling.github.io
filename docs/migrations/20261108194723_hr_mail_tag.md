# 20261108194723_hr_mail_tag.sql (2026-11-08, v2.6715)

A mail conversation onto an HR file (punch list #289): the dev seat's mail tag takes a person as its target, and each mail lands as a dated entry on the person's file.

- `person_file_entries.gmail_message_id` and `gmail_thread_id` (text, nullable): which mail an entry was made from and which conversation it belongs to, in the box `email_tag_threads.user_id` names. The partial unique index `person_file_entries_gmail_once` on `(person_id, gmail_message_id)` is the dedupe key: a thread tagged twice adds only the mails the file has not seen, and a second apply racing the first lands nothing twice. Gmail's ids are per mailbox, so the same mail tagged out of two logins' boxes is two entries.
- `email_tag_threads.person_id` (uuid → `people.id`, cascade): the follow's row for a person-tagged conversation. The check `email_tag_threads_one_job` is dropped and `email_tag_threads_one_target` takes its place: exactly one of `bid_id`, `project_id`, `jobs_ledger_id`, `person_id`. Partial index `email_tag_threads_person`.
- The read policy `email_tag_threads_team_reads` is made again: the office team reads the job rows as before, and only a dev reads a person row, since an HR file's existence is the devs' alone.
- The cron `gmail-mine-follow` is unchanged: it already posts while any row is inside the 60-day window, so a person row is followed by the same schedule.

No table is created, so no fence call is owed. Idempotent.

**Order**: push right after the merge, before `gmail-mine` and `dev-mcp` are deployed — the new gmail-mine reads `person_id` on every tag-row query and refuses a tag whose row it cannot read, and the seat's person target answers *gmail-mine answered without a plan* until gmail-mine follows. The old gmail-mine keeps working against the new columns.
