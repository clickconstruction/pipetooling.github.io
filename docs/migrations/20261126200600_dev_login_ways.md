# 20261126200600_dev_login_ways.sql (2026-11-26, v2.8671)

Two dev-only functions for the person desk's *Ways in* row (punch list #447). No table, so no fence call.

- **`dev_login_ways(p_user_id)`** reads whether the login has a password set and each of its ways in (`auth.identities`: provider, the address it carries, when it was last used, when it was linked). It never returns a hash or a token. A dev only.
- **`dev_unlink_google(p_user_id)`** deletes the login's `google` identity, takes `google` out of `auth.users.raw_app_meta_data.providers`, and deletes the login's `auth.sessions` so a session Google opened does not outlive the link. The password, the `users` row and everything that points at the person stay. It refuses a login whose only way in is Google (*Set a password first*). A dev, or the service role: `change-user-email` calls it when a dev moves a person's address.

These are the first functions in this project that write to the `auth` schema. Both are `SECURITY DEFINER` with an empty search path, owned by `postgres`, with `EXECUTE` revoked from `PUBLIC` and `anon`.

**Apply order**: push right after the merge. The desk's *Ways in* row calls `dev_login_ways`, and until the push the row says the read was refused. `change-user-email` calls `dev_unlink_google` fail-soft, so it works before the push and reports the link as not removed. Redeploy `change-user-email` after the push.
