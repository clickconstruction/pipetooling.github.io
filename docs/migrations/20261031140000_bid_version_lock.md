# 20261031140000_bid_version_lock.sql (2026-10-31, v2.6234)

A bid version can be locked by its owner so only they edit it. The owner: *a user should have the option to lock down that version so only they can edit, if they choose; this should definitely not be enabled by default.*

- `bid_versions.owner_user_id` (the person who made or adopted the version; defaults to the signed-in user on insert, older rows took the bid's estimator, else its maker), `locked_by`, `locked_at`. Nothing is locked by the migration.
- `bid_version_lock_may_override()`: dev or master. `bid_version_lock_refusal(version)`: the words, or NULL when the write may go — the holder, a dev, a master and the service role (the robots' fenced verbs) pass.
- `bid_version_write_guard()` on every table that carries `bid_version_id` (count rows, takeoff mappings, rough-in lines, pricing facets, CountTooling projects, plan sets) and `price_book_version_write_guard()` on the facets' children (`price_book_entries.version_id`, custom prices, assignments): BEFORE INSERT OR UPDATE OR DELETE, a refused write raises the refusal, which `formatErrorMessage` shows as it is.
- `bid_versions_set_owner` (BEFORE INSERT) and `bid_versions_lock_guard` (BEFORE UPDATE): only the owner, the holder, a dev or a master turns the lock; a lock names the one who sets it (a dev or master may set another's); a locked version's own row is the holder's too; each lock or unlock writes a `bids_submission_entries` line naming who.

Reads, sends, adopts and copies are untouched: the guards fire on writes to the version's facets only. Apply order: with v2.6234's merge, `supabase db push`, then `npm run gen:types`. The picker reads `select *`, so it stands before the push and shows the lock after.
