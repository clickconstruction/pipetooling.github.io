# 20261010025000_gc_award_guard.sql (2026-10-09, v2.5100)

GC mode, the Board: only `gc_award` writes a trade's award. The plan is `to-dos/gc-mode/mockups/board-b6.md` → *The award guard* on branch `spike/gc-mode`, read back to the lead and approved 2026-10-09. The gap was found after the 10-09 stop, in a docs audit by the LIEN DESK email preview session, and confirmed by the lead on main (`HANDOFF_2026-10-09.md` → *A security gap to fix first*).

It is idempotent: `CREATE OR REPLACE` for both functions and the trigger. No table is created, and no column, policy or other function changes.

## The gap

B6-a (`20261009140000`) added `awarded_invite_id`, `awarded_by` and `awarded_on` to `gc_trade_packages`, with comments saying "Written by gc_award only". Nothing held that. The table carries door 1's `gc_trade_packages_team` policy (`20261008003000`: every verb for `gc_office_team()`, so dev, master, assistant, controller and estimator), and no trigger or column grant guarded the three columns. Any of the five roles could set or clear an award with a plain UPDATE through REST, past `gc_award`'s dev-only gate, its SQL vetting check (call G) and its statement of work. What Building's daily log and the statement of work treat as awarded would follow. Nothing on prod was written that way: the lanes' live checks never ran.

## What it does

1. **`gc_trade_packages_award_guard()`** (plpgsql, SECURITY INVOKER) and its trigger, `BEFORE INSERT OR UPDATE … FOR EACH ROW` on `gc_trade_packages`. It fires on every row, not `UPDATE OF`, so no other trigger's change slips past it. It refuses, with *A trade's award changes only through Award and draft the statement of work in Compare quotes.* (`42501`), an INSERT that sets any of the three columns or an UPDATE that changes any of them, unless one of these holds:
   - **gc_award's flag** `gc.award_write` is `'on'` for the transaction;
   - **a key letting go**, inside its own trigger (`pg_trigger_depth() > 1`): an ask's `ON DELETE SET NULL (awarded_invite_id)` and a user's `ON DELETE SET NULL` on `awarded_by`. An ask's delete still meets the award's day CHECK and the statement of work's key, as before; a user's delete clears who awarded, which no CHECK ties;
   - **server code with no person** (`auth.uid() IS NULL`): the service role, a migration, a SQL bed's fixtures, as `gc_projects_owner_terms_guard` lets the service role pass.

   No role is named. A dev's plain UPDATE is refused too, since it would skip the gate and draft no statement of work. When award's door opens (call W), only `gc_award`'s own first check changes; this trigger stays as it is.
2. **`gc_award`** is restated byte for byte as B6-a made it, with two lines added: `PERFORM set_config('gc.award_write', 'on', true)` just before its UPDATE of `gc_trade_packages`, and `PERFORM set_config('gc.award_write', '', true)` just after. The flag is local to the transaction, and a refusal's rollback takes it with it. PostgREST sets no custom setting a request can choose, and no public function sets one from its arguments.
3. The comments on `gc_award` and on `awarded_invite_id` name the guard.

## Checked before the push

**The SQL bed** `supabase/tests/gc_award/20_scenario.sql` (`npm run test:pg:gc-award`; GitHub's `SQL beds` workflow runs it, and on a migration PR every bed runs). The runner now re-applies B6-a's migration and then this one, in that order; re-applying B6-a's alone would put back a `gc_award` with no flag. Added to the scenario:
- before any award: an estimator setting an award by hand, naming who awarded alone, and making a trade already awarded, and a dev setting an award by hand, are each refused in the guard's words, and nothing is awarded;
- `gc_award` still awards (the existing step 3), and its flag reads empty once it returns;
- after the award: a dev clearing it, and an estimator clearing it, moving its day or renaming who awarded, are each refused; an estimator's budget edit on the awarded trade saves and leaves the award as it was;
- *An award needs its day* now runs under the flag inside its subtransaction, so the award's day CHECK still refuses (`23514`) behind `gc_award`, and the flag goes with the refusal. *An awarded ask cannot be deleted* is unchanged (`23503` or `23514`): the key's SET NULL passes the guard;
- a person who awarded is deleted with someone signed in: `awarded_by` goes null through its key and the award stays.

Four beds on main write awards in their fixtures as postgres with no one signed in (`gc_back_charges` 20, `gc_building` 40 and 50, `gc_owner_billing` 80). They run unchanged, and so do the open GC branches' fixtures.

**`src/lib/gc/awardSql.test.ts`** reads every `gat.refused` line of the bed, so the guard's eight refusals are held to the plain-words rules.

## Verify after the push

Through the management API, every write rolled back (`to-dos/gc-mode/scripts/verify/` on the spike has the shape).

```sql
-- 1. The trigger is on the table.
SELECT tgname, tgenabled FROM pg_trigger
WHERE tgrelid = 'public.gc_trade_packages'::regclass AND tgname = 'gc_trade_packages_award_guard';
-- Expected: one row, tgenabled O.

-- 2. gc_award turns the flag on and off.
SELECT (length(prosrc) - length(replace(prosrc, 'gc.award_write', ''))) / length('gc.award_write') AS flags
FROM pg_proc WHERE oid = 'public.gc_award(uuid, uuid)'::regprocedure;
-- Expected: 2.

-- 3. A dev's plain write of an award on the test project is refused in words.
BEGIN;
SELECT set_config('request.jwt.claims',
  json_build_object('sub', (SELECT id FROM public.users WHERE role = 'dev' AND NOT read_only LIMIT 1), 'role', 'authenticated')::text, true);
SET LOCAL ROLE authenticated;
UPDATE public.gc_trade_packages SET awarded_by = auth.uid() WHERE project_id = 'ef8905d1-039a-4cbc-9d69-9468cfea50e0';
-- Expected: A trade's award changes only through Award and draft the statement of work in Compare quotes.
ROLLBACK;

-- 4. gc_award still awards, rolled back, as a dev (the building project's test ask carries a $12,500 quote).
BEGIN;
SELECT set_config('request.jwt.claims',
  json_build_object('sub', (SELECT id FROM public.users WHERE role = 'dev' AND NOT read_only LIMIT 1), 'role', 'authenticated')::text, true);
SET LOCAL ROLE authenticated;
SELECT public.gc_award('115b6971-ee16-4459-9340-85fc35d5c1e3') IS NOT NULL AS awarded;
-- Expected: true.
SELECT coalesce(current_setting('gc.award_write', true), '') AS flag_after;
-- Expected: empty.
ROLLBACK;

-- 5. After the rollbacks.
SELECT count(*) AS awarded FROM public.gc_trade_packages WHERE awarded_invite_id IS NOT NULL OR awarded_by IS NOT NULL;
-- Expected: 0, as at the 10-09 stop.
```

## Not done

- **Deleting an awarded trade.** `gc_trade_packages_team` also lets the office team DELETE a trade, and an awarded trade's delete takes its statement of work and lines by cascade, though `gc_sows` is dev only. That is its own piece in the Board lane: a DELETE guard while `awarded_invite_id` is set, after award's door (call W).

## Rollback
