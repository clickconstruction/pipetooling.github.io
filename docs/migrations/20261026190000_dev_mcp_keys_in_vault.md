# 20261026190000_dev_mcp_keys_in_vault.sql (2026-10-26, v2.5899)

Dev MCP keys kept in Vault, so a live key can be copied again from Settings → Your account → Dev MCP keys ([`docs/recent-features/v2.5899.md`](../recent-features/v2.5899.md)). The owner's pick on 2026-10-26 over a one-press reissue: only the key's sha256 was stored, so nothing could be copied.

- `dev_mcp_credentials.secret_id uuid NULL` — the Vault secret holding the key itself. Null on keys issued before this file and on revoked keys.
- `dev_mcp_issue_key(p_token text, p_label text)` → `uuid`, `SECURITY DEFINER`: for the caller (a dev, not a twin, not in training mode, each refused in words); checks the key's shape (`ptd_` + 64 hex, still generated in the browser), stores `encode(digest(key, 'sha256'), 'hex')` as before for the `dev-mcp` lookup and the key in Vault (`vault.create_secret`, name `dev_mcp_key_<row id>`), the row's `user_id` and `created_by` the caller. EXECUTE to `authenticated`, revoked from `PUBLIC` and `anon`.
- `dev_mcp_reveal_key(p_credential_id uuid)` → `text`, `SECURITY DEFINER`: the caller's **own live** key, decrypted from `vault.decrypted_secrets`. Another dev's key and a missing row get the same refusal; a revoked key and a key with no secret are refused in words. Writes one `dev_mcp_calls` row per reveal (`verb reveal_key`, `target dev_mcp_credentials`, `args {credential_id, label, from: settings}`, `status ok`) — the log the card promises. EXECUTE to `authenticated`, revoked from `PUBLIC` and `anon`.
- `dev_mcp_credentials_forget_secret()` (trigger, `SECURITY DEFINER`) on `BEFORE UPDATE OF revoked_at` (when a live row is revoked) and `BEFORE DELETE`: deletes the row's `vault.secrets` entry and clears `secret_id`; a Vault refusal is a NOTICE, never a blocked revoke (the same guard as `legal_portal_link_forget_secrets`, `20261006072618`).
- The table's and the column's comments say where the key sits and who may read it.

Additive and idempotent (`ADD COLUMN IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP TRIGGER IF EXISTS`). No `CREATE TABLE`, so no fence appliers. **Deploy the client first, then push**: the v2.5899 card reads the table without `secret_id` until the column is there (a retry on `42703`) and issues the old hash-only way while the function is missing (`PGRST202`); the old client's insert still works after the push (a row with no secret, no Copy). `dev-mcp` itself does not change. After the push, a `chore(types)` PR regenerates `src/types/database.ts` (and `dev-mcp/catalog.ts`) so the card's narrow casts can go.
