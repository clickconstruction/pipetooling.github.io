# 20261007090000_gc_issue_plan_set

**Version:** v2.4757 · **Date:** 2026-10-06 · **Plan:** `to-dos/gc-mode/NEW_PROJECT_REAL_BUILD.md` on `spike/gc-mode`, step 6.

## What it adds

`public.gc_issue_plan_set(set_in jsonb) RETURNS uuid`, `SECURITY INVOKER`, `search_path = public`. The one press that puts a new set of plans on a GC project, in one transaction:

- the `gc_plan_sets` row at the next `rev`, with its kind, note, issue day, checker (`checked_by_user_id`, required) and the Drive link with the verdict `gc-drive-access` gave before the press;
- its `gc_plan_set_items`: the sheets and sections it adds (`added`, with title, discipline and page), renames (`renamed`, with `was_title`), takes out (`removed`) and otherwise names (`revised`), each number once;
- the trades it brings as `gc_trade_packages` after the job's own, with their scope lines (`added_in_set_id` = this set) and exclusions; nobody is asked yet;
- the scope lines it adds to trades already on the job, after the trade's own lines, `added_in_set_id` = this set;
- the lines it ties to new sheets or sections (`retiedLines`): `gc_scope_items.sheets` / `specs` set to the list given, an empty list meaning the trade as a whole.

It refuses, in plain words, a missing project, a lost bid (`gc_projects.lost_on`), a set with no name and a set with no checker. `EXECUTE` is granted to `authenticated` only; the tables' policies (dev-only while the build goes on) decide who may.

## Input

The `issuePlanSet` action's shape from the prototype, as `src/lib/gc/newProjectDraft.ts`-style JSON: `projectId`, `label`, `kind`, `note`, `issuedOn?`, `checkedByUserId`, `drive?: { url, access, checkedOn }`, `sheets`, `addedSheets`, `removedSheets`, `retitledSheets` (each with `wasTitle?`), `specs`, `addedSpecs`, `removedSpecs`, `retitledSpecs`, `newTrades` (the New project trade draft), `newLines`, `retiedLines`.

## Applied

With `supabase db push` after the PR merged. Idempotent (`CREATE OR REPLACE`), additive, no table change.
