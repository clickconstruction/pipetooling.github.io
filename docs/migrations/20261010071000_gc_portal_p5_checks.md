# 20261010071000_gc_portal_p5_checks.sql (2026-10-10, v2.5150)

GC mode, the real build, the trade partner portal's P5c-m (`to-dos/gc-mode/PORTAL_REAL_BUILD.md` → *The PRs, in order*, item 11; plan `to-dos/gc-mode/mockups/portal-p5.md`, on branch `spike/gc-mode`). It widens two CHECKs for the trade's half of the job, and changes nothing else: no table, column, function, policy or grant. Nothing writes the new values yet. P5c-3 and P5c-4 will.

## What it does

1. **`gc_trade_messages_kind_known`** gains three kinds, beside the twenty it held (`20261008050000_gc_trade_portal_links`):
   - `accepted`: we accepted the trade's work and ask for its final pay application (P5c-4);
   - `finalIn`: its final pay application came in (P5c-4);
   - `punch`: an item added to its punch list or sent back. It waits on the owner's yes (the plan's decision 7), and a kind with no sender costs nothing; the lead asked for it now so a yes needs no second migration.
2. **`esign_consents_record_type_check`** gains two record types, beside the seven it held (newest in `20261009140000_gc_award_and_sow`):
   - `gc_draw`: a pay application, a final pay application or an unconditional waiver the trade signs in its portal, keyed by the draw (`gc_draws.id`);
   - `gc_trade_change`: a change order the trade signs, keyed by the change order.
   P5c-3's four signatures write a ledger row as `sign_sow` does, so the consent's words are kept beside the act the SQL records.
3. Each CHECK is dropped and added again `NOT VALID`, then validated. The scan runs under the validate's lighter lock, and `lock_timeout` (3s) fails the push fast if a table is busy. A second run gives the same CHECKs.

## Rollback

Not expected. To undo, add each CHECK again with the values it held before (the two migrations named above). Nothing writes the new values until P5c-3 and P5c-4 (and `punch` until the owner's yes).
