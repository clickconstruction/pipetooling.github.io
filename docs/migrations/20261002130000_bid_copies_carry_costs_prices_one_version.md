# 20261002130000_bid_copies_carry_costs_prices_one_version.sql (2026-10-02, v2.4413)

Punch list #79: the four gaps the audit for #78 (v2.4388) found in the bid copy functions. The owner said yes to all four defaults on 2026-10-02. `CREATE OR REPLACE` of `clone_count_rows_to_bid_version`, `duplicate_bid_to_service_type` and `adopt_bid_as_version` (each the newest body on main, `20261002100000`, with additions only; same signatures, so owners and grants stay), one new helper, and one foreign key. `create_bid_version` is not re-created: it copies count rows through the clone helper.

| Gap | Before | Now |
|---|---|---|
| 1. Quoted fixture costs (`bid_count_row_custom_costs`) | no copy carried them; an adopt left them under the retired bid; a deleted count row left its cost behind | a new version and a same-trade duplicate copy them; a duplicate into another trade does not (the quote is the other trade's); an adopt moves them; the table has a foreign key to its count row, `ON DELETE CASCADE` |
| 2. A duplicate of a bid with versions | every version's count rows went into one list: a bid with two versions of three rows gave a copy of six | the copy is one plain bid made from the version the bid is on (`selected_bid_version_id`, else the first by `sort_order`, `created_at`: the client's `pickActiveVersion`) |
| 3. A duplicate and the bid's own prices | custom prices, hidden rows, assignments and `selected_price_book_version_id` kept the first bid's `price_book_version_id`; the copy's Pricing tab reads prices by its own bid and found none | each price the copied version owns is cloned for the copy with its entries (name, order and offer flag kept, `source_version_id` = the price it came from); the three child tables and the saved price are re-keyed onto the clones; a shared book (no `bid_id`) stays shared |
| 4. An adopt and `bid_submittal_takeoff_choices` | left with the retired bid | left with the retired bid, decided: a submittal is built after the award, on the bid it was built on |

**Packages.** A package (lot) of quoted costs shares a `lot_group_id`, and the app reverts a package with `DELETE … WHERE lot_group_id = …`. Each copy gets a new id per package (a `MATERIALIZED` CTE mints one per distinct source id), so reverting a package in one version or bid leaves the other alone. A new version keeps `quote_line_id` (the quote is on the same bid); a duplicate sets it NULL (the quote line is the first bid's).

**The saved price of a duplicate** follows the Pricing tab's rule (`deriveActivePricingId`): the copied version's ★ when it was cloned, else the bid's saved price when it was cloned, else the first clone; with no clone, the saved price stays when it is a shared book and is cleared when it is a price of the first bid that did not come along. A custom price, hidden row or assignment on such an uncloned price (another version's) is left behind.

**Who may copy quoted costs.** The table's INSERT policy allows dev, master_technician, assistant, controller and estimator. A primary or a superintendent may make a version or a duplicate, and an INSERT they are not allowed would fail the whole copy. New `can_write_bid_custom_costs()` (`SECURITY DEFINER`, `STABLE`, reads the caller's role; EXECUTE revoked from PUBLIC and anon, granted to authenticated and service_role) guards both INSERTs: for those two roles the copy is made without the costs and nothing fails. The adopt's UPDATE needs no guard: RLS hides the rows from it.

**The foreign key.** `bid_count_row_custom_costs_count_row_id_fkey` → `bids_count_rows(id)`, `ON DELETE CASCADE`, added once (the `DO` block checks `pg_constraint`), after a `DELETE` of costs whose count row is gone. On prod on 2026-10-02 the table held **no row**, so the delete removes nothing and the key validates nothing.

**Prod on 2026-10-02, read-only:** 0 quoted cost rows; 0 bids pointing at another bid's price (saved price, assignments or custom prices), so nothing needs repairing; 23 bids with versions (47 versions); 237 bids owning 291 prices.

**Tested** on a throwaway copy of the whole schema (`npm run test:pg:bid-copies`; it also re-runs #78's stage-box scenario, since both exercise the same functions). The scenario runs as an estimator through RLS in a transaction that rolls back. Against the old functions it fails at the first gap (*new version: quoted costs* reads none). With this migration all 22 steps pass: a new version's costs and its package reverting alone, a deleted count row taking its cost, a duplicate of a split bid (three rows, not six; no versions; that version's prices and costs), a same-trade duplicate (its own price, entry and saved price; the source untouched; the costs), a duplicate into another trade (prices, no costs), a duplicate of a bid on a shared book (still shared), an adopt (costs moved, none left behind), and a primary making a version (made, without costs, no error).

[`bidCopySql.test.ts`](../../src/lib/bids/bidCopySql.test.ts) now holds the quoted costs to all three copies, pins the columns of the cost, price and entry inserts, the version rule, the re-keying of the three child tables and the two role guards. `bid_submittal_takeoff_choices` is its one table left behind, with the decision beside it.

The generated types gain the new relationship and the new function: a `chore(types)` PR follows the push. Apply with `supabase db push` after the PR merges. The client change (the quoted costs read again when the version changes) works with or without the migration.
