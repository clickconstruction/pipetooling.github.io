# 20261008071000_labor_rows_unmatched.sql (2026-10-07, v2.4864)

Bid history PR 0b (punch list #73, [`to-dos/bid-history`](../../to-dos/bid-history/README.md)): the Labor tab's load sync stops deleting typed hours. A labor row no counted fixture claims (a version switch, a renamed or removed fixture) is set aside here instead of deleted, and taken back when its fixture is counted again.

1. **`cost_estimate_labor_rows_unmatched`**: the labor row's own columns (fixture, count, the three hours, `is_fixed`, `kind`, `unit`, `source`, `source_note`, same types), `labor_row_id` (the row it came from, no FK) and `parked_at`; FK to `cost_estimates` `ON DELETE CASCADE`; index `(cost_estimate_id, parked_at DESC)`. A set-aside row cannot stay in `cost_estimate_labor_rows`: pricing history, job budgets, baselines, the estimate breakdown and the copies sum that table, and a fixed (task) row counts its hours at any count.
2. **Who reaches it**: RLS as `cost_estimate_labor_rows` (`celr_*`: whoever can price the bid, `can_access_bid_for_pricing`), four policies `celru_*`; `anon` revoked. The delete archive (`zzz_archive_on_delete`, grouped under the cost estimate like the labor rows). Ends with `apply_read_only_write_blocks()`, `apply_read_only_stmt_blocks()` and `apply_digital_twin_write_blocks()` (the twin fence keys the table through `cost_estimate_id`).
3. **Bid history**: the table fits the ledger's trigger pattern (it reaches its bid through `cost_estimate_id`, as the labor rows do), so it joins `bid_changes_tables()` (eighteen, first in creation order since nothing uses it yet) and gets the same `record_bid_change` trigger. `record_bid_change()` is replaced whole from `20261007050000` with one change: a set-aside row is labelled by its fixture, as a labor row is. `bid_changes_app_actions()` adds the sync's three new tags: `labor-rename`, `labor-park`, `labor-take-back` (the band's `labor-use-parked` is a person's press, so not listed).

Idempotent (`IF NOT EXISTS`, `DROP … IF EXISTS`, `CREATE OR REPLACE`, the trigger guarded by a `pg_trigger` check); `SET lock_timeout = '3s'`. Locks: only the new table (its own triggers and policies) and the fence helpers' catalog work, which create only what is missing.

Apply order: **client first or with the merge** is safe. Before the push the client cannot read the table, so the sync deletes an unclaimed row as it did before (tagged `labor-sync`; the ledger keeps its values) and the band stays empty; `useBidPricingEngine.laborSync.render.test.tsx` holds both fallbacks. After the push, regenerate `src/types/database.ts` and the dev-mcp catalog (the table is hand-added to the types until then).
