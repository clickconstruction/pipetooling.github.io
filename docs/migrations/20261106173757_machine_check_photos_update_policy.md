# 20261106173757_machine_check_photos_update_policy.sql (2026-11-06, v2.6578)

One policy, `"machine_check_photos update"`: the person who took a machine check's photo may update their own `machine_check_photos` row while `filed_at` is null, and the new row must still be theirs and unfiled. The table shipped with `20261106030000_machines.sql` (v2.6555) carrying SELECT, INSERT and DELETE policies and no UPDATE policy, so the `storage_path` the phone writes after each upload was refused silently (zero rows, no error) and the `photo-save` sweep, which files the rows with a `storage_path` and no `filed_at`, never filed a machine photo into Drive. Found on the 2026-11-06 live walk of punch list #271. The sweep writes `drive_file_id`, `filed_at` and `fail_why` as the service role and is not bound by this. Idempotent (`DROP POLICY IF EXISTS` first); no table is made, so the three fence calls are not needed.

The bed `supabase/tests/machine_photos_path/` (`scripts/pgtest-machine-photos-path.sh`, `npm run test:pg:machine-photos-path`) proves it: the taker records the path on their own photo, changes nothing once the sweep has filed it, cannot mark it filed themself, and another signed-in person updates nothing.

Apply order: **push right after the merge** of v2.6578. Its client (`addCheckPhoto`) now reads the update back and, when no row comes, takes the object and the row back and shows *The photo went up, but its record was refused the path to it* on the sheet, so from the deploy until the push every machine photo would fail loudly instead of silently; before the push nothing filed anyway. No types change (no column).
