# 20261102041932_robot_fixtures_adopt_fold.sql (2026-11-02, v2.6326)

Robot fixtures: fold a second robot source when a bid is adopted (punch list #226). Since v2.6230 `adopt_bid_as_version` moves every `bid_count_sources` row of the adopted bid onto the package under the new version, the robot's own row too (`source_kind = 'robot'`, written by `robot_fixture_source` the first time the estimator takes robot fixtures). That row carries no token, so the adopt's same-token guard never held it back, and when both bids took robot fixtures the package ended with two robot rows. Nothing failed — every robot lookup (`robot_fixture_source`, `set_aside_robot_fixtures`, `untake_robot_fixture_rows`, `untake_robot_fixtures`) is `LIMIT 1` — but Set aside or Undo could strip the wrong share and leave a row shaded by a source that no longer existed, and the Counts tab's From tile drew two Robot chips. Found on 2026-10-31 by the session that built #221, while #6637 and #6649 met in the merge queue; it could not happen on prod until a real bid had a robot pull.

- **`robot_fixtures_fold_adopt(p_source_bid_id, p_target_bid_id, p_new_version_id)`**, new, SECURITY DEFINER, in the shape of `robot_fixtures_follow_adopt` (20261031015000) and `adopt_logs_both_bids` (20261031203414). Once the adopt has moved the count sources it finds the package's own robot row — the one not on the new version: the bid-wide row first, else the oldest by `first_imported_at` — and for every other robot row on the package re-keys `bids_count_rows.source_shares` on the rows that name it (the moved rows; a row that already carries the package's share keeps that value) to the package's row, then deletes the duplicate. With no robot row of the package's own the moved row is the package's now and nothing changes. Returns how many rows folded. Refused for a signed-in caller who cannot price both bids (`auth.uid()` NULL — the owner, the service role — is trusted); keeps the digital-twin fence's rule since a definer skips the fence (a twin writes only on bids it made or is the estimator of); writes only once the version is the package's; the `read_only_block_stmt` statement trigger still fires inside it. EXECUTE for `authenticated` and `service_role`, none for `anon`.
- **`adopt_bid_as_version`**: 20261031203414's body verbatim plus the call right after the `bid_count_sources` move and the sweep of what was left, with the folded rows taken off the log line's CountTooling count (`GREATEST(v_cts - v_folded, 0)`: a folded row is not a project that arrived, so a package that already had the robot reads *0 CountTooling projects* when only the robot's row came). `bidCopySql.test.ts` still walks the adopt's body: no closed table is written, and the helper is a definer, so it is not walked.
- **The beds**: `npm run test:pg:robot-fixtures` seeds a package and a second bid that each took robot fixtures (the second one updating a row of hers), adopts the second into the package and asserts one robot source on the package (its own id), every moved share keyed to it, the adopted pull's rows on the new version, the log counting no project, then Set aside on the updated row strips the one share, Undo on the package's own pull leaves the source for the moved row it still shades, and Undo on the adopted pull leaves no row shaded and no source. `npm run test:pg:bid-copies` runs the same adopt through the real doors as the estimator (the pulls written by a definer helper of the bed), asserting the one source, the moved share keyed to it, both pulls on the package, the log line and the Set aside → Undo end state.

No table or column changes; one new function with its grants; no `CREATE TABLE`, so the three fence calls are not made; idempotent (`CREATE OR REPLACE`). Apply order: with v2.6326's merge, `supabase db push`. The client's call is unchanged, so nothing waits on the push; until it lands an adopt behaves as before (a second robot row on the package).
