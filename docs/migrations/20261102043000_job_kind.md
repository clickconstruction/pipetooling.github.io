# 20261102043000_job_kind.sql (2026-11-02, v2.6329)

A job's kind, service call or project, as the office's own answer (punch list #238, PR 1; [v2.6329](../recent-features/v2.6329.md)).

- **`jobs_ledger.kind text`**, nullable, no default: `service` (priced by the work, billed at the end) or `project` (priced before the work, moved by change orders). `ADD COLUMN IF NOT EXISTS`; a nullable column with no default is a catalog write with no rewrite and no scan, so the `ACCESS EXCLUSIVE` lock is brief, and `SET lock_timeout = '3s'` fails the push fast if the table is busy.
- **`jobs_ledger_kind_known`**: `CHECK (kind IS NULL OR kind IN ('service', 'project'))`, added `NOT VALID` inside an `IF NOT EXISTS` guard. It holds every write from here on. It is left unvalidated on purpose: every row is null, so there is nothing to prove, and `db push` sends a file as one transaction, so a `VALIDATE` in this file would scan the table under the `ADD COLUMN`'s lock until the commit. A later migration may validate it under `SHARE UPDATE EXCLUSIVE`, which blocks no read or write, if anything ever needs it validated.
- No backfill: a job with no kind reads from its signals through `src/lib/jobs/jobKind.ts` (a billing-only job, a price before the first day of work, a bid or a GC project behind it, Stage Plan rows, an HCP number), and the explicit kind wins once the office presses one. PR 2's Quickfill deck line lists the jobs the signals cannot settle.
- No new table, so no fence calls. The existing `jobs_ledger` policies and table-wide grants cover the column: the office roles that update a job's row write its kind. `jobs_ledger_fields_to_activity_upd` names its columns, so a press writes no activity line. Idempotent: a second run adds nothing.
- The name is safe beside the tables that already have a `kind`: no function reading `jobs_ledger` by its latest definition in `supabase/migrations/` names `kind` unqualified in a query over both (the hits are insert lists, aliases and a CTE's own column).

## Order

Push right after the merge. `npm run check:calls-ahead` reads function, table and view names, not columns, so it does not label this PR and the deploy does not hold for it; nothing breaks while the push is pending, because the client never names the column in an insert or a select list. Every read goes through `select *`, where a missing column is a missing key. One function writes it, `saveJobKind` (`src/lib/jobs/jobKindWrite.ts`), after the row is in. Until the push the chip and the filter read from the signals, a press on Edit Job says *Could not save the job's kind* with PostgREST's reason, and a New Job with a kind to save is still made and says *Job saved, but its kind could not be saved*. After the push, the types chore (`src/types/database.ts` gains `kind` on `jobs_ledger`).

## How to verify

SQL steps through the Management API's query endpoint, read only:

1. `SELECT is_nullable, column_default, data_type FROM information_schema.columns WHERE table_schema = 'public' AND table_name = 'jobs_ledger' AND column_name = 'kind';` reads `YES`, null, `text`.
2. `SELECT convalidated, pg_get_constraintdef(oid) FROM pg_constraint WHERE conname = 'jobs_ledger_kind_known' AND conrelid = 'public.jobs_ledger'::regclass;` reads false and the check.
3. `SELECT count(*) FROM public.jobs_ledger WHERE kind IS NOT NULL;` reads 0 right after the push.

On a ZZ Test job as the dev: press **Project** on the Edit tab, read the chip beside the name, press **Service call**, read it again, delete the job.
