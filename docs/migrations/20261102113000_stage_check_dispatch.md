# 20261102113000_stage_check_dispatch.sql (2026-11-02, a stage check sent to Dispatch, punch list #245 PR 1)

A crew member on a stage checklist row hits a check they cannot answer and sends it to Dispatch (`to-dos/stage-check-to-dispatch/`, v2.6360). The request is one more structured flavour of `dispatch_requests`, `pending_action = 'stage_check'`, with the job in `job_ledger_id` as every request has it and, new here, the stage and the check in two columns. The rules are `src/lib/jobs/stageCheckDispatch.ts`.

- **Two columns on `dispatch_requests`**: `fixture_id` → `jobs_ledger_fixtures` and `checklist_question_id` → `stage_checklist_templates`, each `ON DELETE SET NULL`, so a stage or a check deleted leaves the request standing as a plain note with the job on it. NULL on every other request.
- **`dispatch_requests_one_open_stage_check_idx`**: a partial unique index over the two columns where `pending_action = 'stage_check' AND status = 'open'`. One open request per check per stage. The phone reads the open requests first and wears *With Dispatch* in place of the press; two phones that send at once meet the index, and the client reads its `23505` as *Already with Dispatch*.
- **The comment on `pending_action`** now lists every known value, `stage_check` among them.
- **No policy changes.** The crew inserts in their own name (`dispatch_requests_insert`), reads their own rows (`dispatch_requests_select`), and the dispatch group and a dev read and close, as every request. `pending_action` has no CHECK (baseline), so the new value needs no widening. The guard trigger `dispatch_requests_guard_update` lists neither new column on purpose: Dispatch may re-point a request at another check from the context window (PR 2), as they may close one.
- **The row's payload carries the same facts.** `pending_payload.stage_check` = `{ fixture_id, question_id, reason, stage_name }`, so the inbox row's two doors (**Open the job**, **Open the check**) read a column the inbox has selected since v2.1615 and never wait for the push. The two id columns are the sheet's read-back and PR 2's trigger and window.
- Additive and idempotent. No table is created, so no fence call. The two foreign keys take a short `SHARE ROW EXCLUSIVE` on `jobs_ledger_fixtures` and `stage_checklist_templates`; the index builds over a table of a few thousand rows; `lock_timeout` makes a busy moment fail fast.

Apply order: push right after the merge and before the Pages deploy finishes. The client writes the two columns in every send and reads them back when the sheet opens, by name, which `check:calls-ahead` cannot see; before the push a send fails with the database's reason and the sheet draws no chip, and the inbox reads as before. After the push, `npm run gen-types:linked` as its own `chore(types)` PR.

PR 2 adds the self-close trigger over the two columns (a request closes itself when its check is answered, skipped or taken off on that stage) and the context window; PR 3 the Pipeline's mark.
