# 20261101172319_gmail_mine_follow_window.sql (2026-11-01, v2.6289)

**What it does**: the follow of Messages → My email (punch list #230, a follow-up to PR 4's [`20261101154949_gmail_mine_follow_cron.sql`](./20261101154949_gmail_mine_follow_cron.md)) now keys its 60-day window on the conversation's newest mail, not on its last read. PR 4 followed a tagged conversation while `coalesce(last_read_at, tagged_at)` was within 60 days. Every good read moved `last_read_at`, so a conversation that still read was followed for good, and the cron posted every five minutes for as long as anything was ever tagged.

- `email_tag_threads.last_mail_at timestamptz` (with its comment): the newest mail in the conversation when `gmail-mine` last tagged it or read it well. That is Gmail's `internalDate`, with a draft, Spam, Trash and a chat left out, or the tag's own time when no mail has one. The tag sets it. A good read of the follow moves it forward and never back. It is null on a row tagged before this push until the follow first reads it.
- The index `email_tag_threads_last_mail` on `(last_mail_at)`.
- `email_tag_threads.last_read_at`'s comment, amended: the function now sets it on a failed read too, beside `last_error`, and reads the least recently read first. So every row takes its turn. PR 4 read a failed row after the rest, so once a run's worth of healthy rows was in the window, a row that failed once was never read again.
- The cron `gmail-mine-follow` is scheduled again, `*/5 * * * *`, with the same post as PR 4's: `{"action":"follow"}` to `/functions/v1/gmail-mine` with the vault's `PROJECT_URL` and `CRON_SECRET` in `X-Cron-Secret`.

**The gate**: the post goes out only `WHERE EXISTS (SELECT 1 FROM public.email_tag_threads WHERE greatest(last_mail_at, tagged_at) > now() - interval '60 days')`. That is the function's own window (`followWindow` in `src/lib/myMail/mineFunction.ts`, held to this file by `followWindowSql.test.ts`): a conversation is followed while its newest mail, or its tag when that is later, is younger than 60 days. A tag holds its conversation for the whole 60 days even when its newest mail is older, since the tag's grey line on the thread says later mail lands by itself. After that it is followed while mail keeps coming. `greatest` passes over a null `last_mail_at`, so a row tagged before the push is held by its tag alone until its first read. Nothing posts once every tagged conversation has gone quiet.

**Tables**: none created, so no fence is owed; `email_tag_threads` gains one column and one index. **RLS**: unchanged. The office team's one SELECT policy and its table-wide grant read the new column, and nobody signed in writes it (`gmail-mine` writes it as the service role). Idempotent: the column and the index are made only when missing, and the cron row is unscheduled by name, then scheduled, so a second run leaves one job.

**Tried before the PR** on a throwaway local Postgres 15 with stubs for `cron.schedule` / `cron.unschedule` / `cron.job`, `net.http_post` and `vault.decrypted_secrets`, and an `email_tag_threads` with the columns the gate reads. PR 4's migration was applied first, and its gate posted for a conversation read yesterday whose newest mail was 61 days old: the bug. Then this file was applied twice in a row. It left one job at `*/5 * * * *`, the column once with its comment, the index once, and `last_read_at`'s new comment. Its gate posted nothing with no rows. It posted nothing for a newest mail 61 days old (tagged 70 days ago, read yesterday), for a newest mail 90 days old on a tag 61 days old, or for a tag 61 days old with no newest mail yet. It posted once each for a newest mail 59 days old, a tag yesterday whose newest mail was 90 days old, and a tag yesterday with no newest mail yet. Each post went to `<PROJECT_URL>/functions/v1/gmail-mine` with the secret, `Content-Type: application/json` and `{"action": "follow"}`.

**Apply**: `supabase db push` from a clean checkout of `main` after this merges, with PR 4's migration if it is not pushed yet, **then** redeploy `gmail-mine` (`supabase functions deploy gmail-mine --no-verify-jwt`). The order matters this time. The new function reads and writes `last_mail_at`, so a function redeployed before the push stops every tag before its row is kept (its lines are written, and a second tag after the push finishes it) and runs no follow. The push alone is harmless: the function before it never reads the column, and the gate falls back to `tagged_at`.

**Check**: `select schedule, command from cron.job where jobname = 'gmail-mine-follow'` reads `*/5 * * * *` and a command naming `greatest(last_mail_at, tagged_at)`. Once a conversation is tagged, its `email_tag_threads.last_mail_at` holds its newest mail's time, and a later mail moves it within five minutes. A conversation whose newest mail and tag are both older than 60 days keeps its `last_read_at` where it was.
