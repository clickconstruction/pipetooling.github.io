# 20261101175329_user_imitations.sql (2026-11-01, v2.6290)

Messages → My email (punch list #230, a privacy fix): a record of every imitation. Imitate and View as (`login-as-user`) hand a dev, a master or an assistant a real magic-link session as another account, and its JWT is the person's own, so My email's gate let it read that person's own mailbox. From this migration on, `login-as-user` writes one row here as the service role before it hands out the link, and opens no imitation it cannot record; `gmail-mine` reads the rows back as the service role and refuses a session whose magic-link sign-in follows an imitation of the same person (`src/lib/myMail/imitation.ts`).

- **`user_imitations`** — one row per imitation: `operator_id` (`users`, `ON DELETE SET NULL`: who imitated, kept as a row once that account is deleted), `target_id` (`users`, `NOT NULL`, `ON DELETE CASCADE`: whose account the session was opened as; the rows go with the person) and `created_at` (`now()`, when the link was made). An index on `(target_id, created_at DESC)` serves `gmail-mine`'s read, a person's rows from 24 hours before a sign-in.
- RLS: SELECT for a dev alone, `USING (public.is_dev())`; no INSERT, UPDATE or DELETE policy. Every privilege the project's defaults hand a new table is revoked first, so `authenticated` holds SELECT alone, `anon` nothing, and the service role writes. The three fence calls close the file.

Tried before the PR on a throwaway local Postgres 15 with stubs for `users`, `auth.uid()`, `is_dev()` and the fence helpers, and Supabase's default privileges: the migration applied twice in a row; the service role wrote two rows; a dev read both, an assistant and the person imitated read none; `authenticated` and `anon` were refused every INSERT, UPDATE and DELETE, and `anon` the SELECT; deleting the operator kept the row with no operator, deleting the person took their rows; the read by person and time used the index. The CI SQL beds apply it against the whole schema on the PR.

Apply with `supabase db push` (`scripts/db-push.sh`) after the PR merges, from the main checkout, **before** `login-as-user` and `gmail-mine` deploy: deployed first, `login-as-user` refuses every imitation (it cannot write the record) and `gmail-mine` refuses every magic-link session (it cannot read it), both on the safe side. No client calls the new table. Regenerate `src/types/database.ts` in its own `chore(types)` PR after the push.
