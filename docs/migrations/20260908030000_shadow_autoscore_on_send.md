# 20260908030000 — shadow scorecards land on Send

v2.3126. Additive and idempotent (`CREATE OR REPLACE FUNCTION`, `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER`). Adds `public.score_locked_shadows(p_reference_bid_id uuid DEFAULT NULL) RETURNS integer` (SECURITY DEFINER, EXECUTE for service_role only) — the database twin of twin-mcp's `score_shadows` loop: every `twin_shadow_runs` row still `locked` whose reference bid now has `bid_date_sent` and a positive `bid_value` gets `delta_pct = round((locked − human) / human × 100, 1)`, the teacher (`estimator_id` → `bid_date_sent_attested_by` → `created_by`, with `users.name` / `calibration_standard`), `status = 'scored'`, and the same `[shadow SCORECARD] …` note on both the shadow and reference ledgers (formatted like `toLocaleString()` via the small `shadow_fmt_money` / `shadow_fmt_pct` helpers; authored as the twin seat). Then `bids_score_shadow_on_send_trg` — `AFTER UPDATE OF bid_date_sent, bid_value ON bids`, row-level, `WHEN` both are non-null — calls it for that bid inside an `EXCEPTION WHEN OTHERS THEN RAISE WARNING` block, so scoring can never fail a bid update. Why: the scorecard used to wait for the next agent run to call `score_shadows`; now it lands the moment the estimator sends. `score_shadows` remains the manual door and only ever touches `locked` rows, so the two paths cannot double-score.
