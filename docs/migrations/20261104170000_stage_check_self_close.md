# 20261104170000_stage_check_self_close.sql (2026-11-04, a stage check closes itself when the check is settled, punch list #245 PR 2a, v2.6494)

A check the crew sent to Dispatch (`to-dos/stage-check-to-dispatch/`, v2.6360) is settled on the sheet three ways: answered, skipped on this job, or taken off. Each now closes every open `stage_check` request on that stage and check, in the settler's name, with a note that says how, so nobody closes by hand what the row already settled and the inbox never holds a row the crew answered. The two columns PR 1 added, `fixture_id` and `checklist_question_id`, are what the triggers match on.

- **`stage_check_close_settled(fixture, question, who, note)`**: the one close the three triggers share, `SECURITY DEFINER`, `search_path` pinned, callable by nobody but the triggers (revoked from `PUBLIC`, `anon` and `authenticated`). It sets `status = 'closed'`, `closed_at`, `closed_by_user_id` and `closed_note` on every open `stage_check` request whose `checklist_question_id` matches, and whose `fixture_id` matches when a stage is given; a NULL stage is a company question taken off, which closes the request on every stage.
- **`stage_check_settler_name(name, user)`**: the stamped name on the row, else the user's name, else *someone*.
- **`stage_checklist_answers_close_stage_check`** (AFTER INSERT OR UPDATE OF `pick`, `answered_at`): fires when a pick is on the row and, on an update, the pick or `answered_at` moved. A note saved or a photo attached before the pick settles nothing; a pick already there and pressed again still counts, since `saveAnswerPick` writes `answered_at` every time. Note: *Answered on the sheet by Luis Ortega · Yes*. Closed in the answerer's name (`answered_by`, else `auth.uid()`).
- **`stage_checklist_skips_close_stage_check`** (AFTER INSERT): a live skip (`put_back_at IS NULL`). Note: *Skipped on this job by Sal Super: the hub is not poured yet*. A put back reopens nothing.
- **`stage_checklist_templates_close_stage_check`** (AFTER UPDATE OF `retired_at`): when `retired_at` goes from NULL to set. A job item (`job_id` set) closes its own stage's request, *Taken off by Sal Super*; a company question (`job_id` NULL) closes the request on every stage, *Taken off the company's list by Dee Dev*, in the Settings editor's name since the row names nobody.
- **`promote_stage_checklist_item`** restated verbatim but for two lines: it sets the transaction-local `stage_check.settle_note` to *Added to the company's list* around its own retire and clears it after, so a request open on a job item the office promotes closes reading *Added to the company's list by Dee Dev*, not as a take off. The check lives on as a company question under a new id; a later send on it makes a new request.
- **Who may**: nothing changes in the policies. The crew still cannot update `dispatch_requests` (`dispatch_requests_update_dispatch_or_dev`); the close runs under the definer. The baseline's guard trigger `dispatch_requests_guard_update` admits it, since it holds the content columns and leaves `status` and the `closed_*` columns alone. A request a dev or Dispatch closed by hand is already closed, so the triggers find nothing.
- Additive and idempotent: `CREATE OR REPLACE` throughout, `DROP TRIGGER IF EXISTS` before each `CREATE TRIGGER`. No table is created, so no fence call. The three `CREATE TRIGGER`s take a short `SHARE ROW EXCLUSIVE` lock on each of the three checklist tables; `lock_timeout` makes a busy moment fail fast.

Apply order: any time after the merge. Nothing in the client reads a new name; until the push a settled check leaves its request open for Dispatch to close by hand, as PR 1 shipped. PR 2b (the context window and the loop back) refreshes the sheet's *With Dispatch* chip after a settle and pushes the sender when Dispatch settled it, reading the note this migration wrote.

The SQL bed `npm run test:pg:stage-check-self-close` (`scripts/pgtest-stage-check-self-close.sh`, `supabase/tests/stage_check_self_close/20_scenario.sql`) applies the migration twice and plays every settle as each user under RLS: a note alone leaves the request open, the crew's answer closes it in their name while their own update of the request reaches no row, a second press after the close changes nothing, a new send on the same check after the close is allowed and the skip closes it, the take off and the company retire each close theirs and nothing else, the promote says so, and a plain request and a request on another check stay open throughout.
