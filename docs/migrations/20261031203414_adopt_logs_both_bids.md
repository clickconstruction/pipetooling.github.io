# 20261031203414_adopt_logs_both_bids.sql (2026-10-31, v2.6250)

The adopt writes a line on both bids' logs. Until now `adopt_bid_as_version` left no trace of its own: `bids_submission_entries` got nothing on either bid, and `bid_changes` attributes every moved row to the target while the source's `adopted_into_bid_id` is not a column it records, so a retired source's own record never said where it went. Found in the ZZ Test dry run of 2026-10-31 for the Gun Dog adopts (punch list #208's bids becoming BP556's versions).

- `adopt_bid_as_version(p_target_bid_id, p_source_bid_id, p_name, p_target_base_name)`: 20261031123000's body verbatim, plus `GET DIAGNOSTICS` after the count-row, price-scenario, plan-set and CountTooling-project moves (the two inserts that turn a bare link into a row count as one each), and, before the source retires, two `bids_submission_entries` lines written as the caller the way a lock or unlock writes its line (`bid_versions_lock_guard`, 20261031140000): on the source, *Robert adopted this bid into B556 "…" as the version "…". Moved there: 3 count rows, 1 price scenario, 1 plan set, 1 CountTooling project. The cost estimate and this log stay here.*; on the target, *Robert adopted B167 "…" as the version "…". Moved here: …. The old bid left the board and stays searchable by its number.* The name is the version's (`p_name`, else the source's project name, else *Adopted bid*); the person is `users.name` for `auth.uid()`, else *Someone*.
- The insert policy on `bids_submission_entries` covers devs, masters, assistants and estimators, the same set `can_access_bid_for_pricing` admits, so no helper runs as the owner. `bidCopySql.test.ts` still walks the body: no closed table is written.
- The robot-fixture pulls still move through `robot_fixtures_follow_adopt` and are not counted in the line (they ride the count rows they landed on).
- The retire step also clears the source's `selected_price_book_version_id`. The scenario it named moved to the new version (and is that version's ★ when it was one of the moved ones), so on the retired row the pointer named a scenario of another bid's version, and the readers that take a version-less bid's pointer as its ★ (`bidPackageMap`, `coverLetterVersionBundle`, `loadPricedTakeoffRows`) drew it. The column is in `bid_changes_bid_columns()`, so the source's own change history gains a *price book* row on the day it was adopted — the ledger's first mark of an adopt on the source.

No table, column or grant changes; idempotent (`CREATE OR REPLACE`). Apply order: with v2.6250's merge, `supabase db push`. The client's call is unchanged, so nothing waits on the push; until it lands the adopt behaves as before (no log line).
