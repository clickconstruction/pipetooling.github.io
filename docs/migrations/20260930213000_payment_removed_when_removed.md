# 20260930213000_payment_removed_when_removed.sql (2026-09-30, v2.4269)

A job's history now shows "Payment removed" at the time the payment was removed. Until now the trigger stamped a removal with the payment's own `created_at`, so every removal sat on the same instant as its add and read as an instant undo.

- **`jobs_ledger_payments_to_activity()`** rewritten from its live body (`pg_get_functiondef`, read 2026-09-30). On DELETE, `occurred_at = now()`, and the `(event_type, source_id)` dedupe is gone: a row is deleted once per life, and the guard hid a second removal after a restore. On INSERT, `occurred_at` stays `created_at` and the insert stays idempotent, but the guard now counts: an add is logged only while adds ≤ removals for that id. A payment restored with the same id (`restore_deleted_records`) after a logged removal therefore logs a fresh "Payment" at `now()`. Summary, detail, actor and the `jobs_ledger` existence check are unchanged. The two triggers (`jobs_ledger_payments_to_activity_ins` / `_del`) are untouched.
- **One-time correction**: every `payment_removed` event still carrying the bug's stamp (its `occurred_at` equals the archived row's `created_at`) moves to `deleted_records_archive.deleted_at`, matched by `record_id = detail->>'source_id'`, where that payment has exactly one archived deletion. That was 43 events on 28 jobs on 2026-09-30. The 11 removals from before the archive existed (2026-07-18) have no deletion time on record and keep their stamp. A re-run changes nothing.
- **No removal events were deleted.** On 2026-09-30 no `payment_removed` event pointed at a payment that still exists, so none was spurious. The case that looked like one (job 878's $6,077.51, payment `241af1ce…`) was a real removal: the check was taken off job 878 at 21:00:57 UTC and applied to job 650 at 21:02:53 as a new payment. `apply_mercury_bank_payment_allocations` never deletes or re-inserts a payment, so it does not produce phantom removals.

Proof: `npm run test:pg:payment-activity`. It builds a throwaway Postgres with the old trigger, reproduces the bug, runs the migration twice, then checks five scenarios: the correction, a removal stamped when removed, a restore then a second removal, a delete and re-insert in one transaction, and an idempotent add.

Apply order: any. Nothing in the client changes; the history screen already sorts by `occurred_at`.
