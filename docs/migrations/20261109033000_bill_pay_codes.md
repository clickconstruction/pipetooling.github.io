# 20261109033000_bill_pay_codes.sql (2026-11-08, v2.6769)

The bill text's link: a ten-letter code on the bill (punch list #290, PR 2 of two; `to-dos/short-bill-link.md`). PR 1 (v2.6768) put the bill's pay page in the text the share row sends: `my.clickplumbing.com/pay/<jobs_ledger_invoices.id>`, 69 characters, a page that asks Stripe for the bill's current payment link each time it is opened, so the link never expires as Stripe's own does (30 days after the due date). This migration gives the bill a code so the link reads `my.clickplumbing.com/pay/<code>`, 43 characters.

## What it does

1. **`jobs_ledger_invoices.pay_code text`**, nullable: one code per bill, minted once, kept in plain. The bill's id is already the capability for `/pay/<id>` and sits in plain on the row, so a code beside it is no weaker; one per bill because a bill has one address for its life (the text, Copy link and a resend show the same); no expiry because a bill is owed until paid, and the paid page stops asking. The estimate's per-send hashed codes (#281) fit a link that retires in 14 days; a bill's does not. `jobs_ledger_invoices_pay_code_shape` (`^[23456789abcdefghjkmnpqrstuvwxyz]{10}$`, added `NOT VALID` since every row is NULL today, so no scan) and the unique partial index `jobs_ledger_invoices_pay_code_key`. NULL on every row until its bill is asked for; no backfill.
2. **`mint_pay_code() → text`**: ten letters from the 31-letter alphabet with no 0, O, 1, l or I, each byte of `gen_random_bytes` used only when it is under 248 (8 × 31), so no letter is likelier than another. Writes nothing; EXECUTE to `authenticated` and `service_role`, since `bill_pay_code` runs as its caller.
3. **`bill_pay_code(p_invoice_id uuid) → text`**: the code on the row, else `UPDATE … SET pay_code = mint_pay_code() WHERE id = $1 AND pay_code IS NULL RETURNING pay_code`, minted again on a unique violation (one chance in 10¹⁴), five tries. **SECURITY INVOKER** on purpose: the table's own policies say who may read and update a bill, the read-only statement trigger refuses a training account, the twin and archived fences refuse theirs, and a caller who can read the row but not update it (the UPDATE touches no row and the row still reads NULL) is refused with *Only the office can make a bill's link.* A bill not there is *That bill is not there.* The service role (`create-stripe-invoice`, right after it writes a new bill) mints the same way. EXECUTE to `authenticated` and `service_role`, revoked from `anon`.

No CREATE TABLE, so the four fence appliers are not run; the fences already on `jobs_ledger_invoices` cover the new column.

## Release order

Merge the PR, `supabase db push`, then `supabase functions deploy pay-link create-stripe-invoice`. Either order is safe on its own: a client ahead of the push asks an RPC that is not there, is refused, and keeps PR 1's `/pay/<id>` link (`billPayCode` never throws); `pay-link` ahead of the push answers a `?code=` lookup with its 500 words, which no text carries until a client has minted a code, and `?id=` as before. `src/types/database.ts` picks up the column and the function in the next `chore(types)` PR; the client calls the RPC untyped until then.
