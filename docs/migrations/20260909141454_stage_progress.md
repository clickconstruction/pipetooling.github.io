# 20260909141454_stage_progress.sql (2026-09-09, v2.3192)

Stage-weighted field reports. Adds crew-reported progress to stage line items and two SECURITY DEFINER doors so field roles (who cannot read `jobs_ledger_fixtures`, and must not see prices) can report by stage.

- `jobs_ledger_fixtures.progress_pct integer` (0–100 check `jobs_ledger_fixtures_progress_pct_range`), `progress_at timestamptz`, `progress_by uuid`, `progress_report_id uuid` — all nullable, no backfill.
- `can_report_stage_progress(p_job_id)` — office roles (dev / master / assistant / controller / primary / superintendent / estimator), or a field user who is a team member on the job, has a clock session on it, or passes `subcontractor_can_read_jobs_ledger_row` (the sub/schedule rule the `jobs_ledger` SELECT policy uses).
- `list_job_stage_progress(p_job_id)` — the job's priced Order / Any rows with `weight_pct` (share of the stage lines' value), `progress_pct`, `progress_at`, `draw_paid`. Returns no amounts.
- `record_stage_progress(p_job_id, p_fixture_id, p_pct, p_report_id)` — stamps one stage; refuses a plain row or a row on another job. The read-only training-mode statement trigger on the table still blocks read-only users.
- Grants: `authenticated` may execute all three; `PUBLIC` / `anon` revoked. No CREATE TABLE, so no read-only apply calls.

**Apply order**: client first, then `supabase db push`. The client tolerates the gap — the report form falls back to the plain slider when the list RPC is missing, and the stamp RPC is best-effort. Regenerate types after the push (`npm run gen-types:linked`); `stagePlanForm.ts` reads `progress_pct` loosely until then.
