# 20261113160000_on_site_prices.sql (2026-11-13, v2.7159)

A price of the site's own (punch list #342, PR 2 of 3). A name a crew typed on site has no page in the parts book, so it had no price on the server: the one price it could carry lived in the browser that read an invoice. A site's pricing window lets a person accept a price for such a row. This table holds each answer.

## What it does

One table, `on_site_prices`, one row per answer:

1. **`development_id`** or **`job_id`**: where the answer belongs, as a tie does. One of the two, never both and never neither (`on_site_prices_scope_check`).
2. **`row_key`**, **`row_name`**: the site screen's row key, `id:<part id>` or `words:<the same-words fold>` (`rollKey` in `src/lib/materials/siteRollup.ts`), and the name as it read.
3. **`kind`**: `price`, or `left_out` for a row a person set aside as not a part to price (scrap, tools, a mixed box).
4. **`unit_price`**: the price for one, as counted on site. Null when `kind` is `left_out`, and never null or negative for a price (`on_site_prices_price_check`).
5. **`source`**: `bill` or `typed`. **`source_line_id`** names the bill line (`supply_paper_lines`, set null if the line goes). **`source_words`** is the supply house as it read.
6. **`priced_on`**: the day the price is from, the bill's day or the day it was typed (the client sends it; the default is `public.app_today()`, never the UTC session's `CURRENT_DATE`). The on-site price rule flags it past 90 days, as it flags a parts-book price.
7. **`by_user_id`** (the caller by default), **`by_name`**, **`at`**.

Two partial indexes serve the one read the rule makes: the newest answer of a key in a scope.

**The newest answer of a row is the one read** (`latestSitePrices` in `src/lib/materials/sitePrices.ts`). A second price for a row is a second row, and deleting it lets the first stand again.

**A price never touches the ledger.** It is a reading, like a tie. No row of `job_material_movements` changes, and the Parts Book is not written.

**A price belongs to its site.** A name can mean another part on the next site.

## Who may do what

A price is money. Unlike the ties, **read** is held to the roles that write.

- **Read**: `on_site_can_tie_parts()`, the roles that read the Materials desk with its money (dev, master_technician, assistant, controller, primary), on a scope `on_site_can_read_ties(development_id, job_id)` lets them read. A superintendent or a crew member on the job reads nothing here.
- **Insert**: the same roles, in the caller's own name.
- **Delete**: the same roles on the same scopes. Undo and Bring back are deletes.
- **Update**: nobody. `authenticated` holds `SELECT`, `INSERT` and `DELETE`; `anon` holds nothing.

Both helpers are the ties migration's (`20261113040000`). The migration ends with the four fence calls, since it creates a table.

## Locks

A new table takes no lock on a live one beyond the brief ones its three foreign keys take on `developments`, `jobs_ledger` and `supply_paper_lines`. `SET lock_timeout = '3s'` makes a busy moment fail fast.

## Release order

The client reads the table beside a job's boxes and treats a refused read as no answers, so every screen draws either way. Merge, then `supabase db push` right after. Until the push the pricing window shows a bill's price to read and draws no price box.

## Checked on a database

Docker was not running, so the repo's SQL beds could not run here. The migration was applied twice to a throwaway local Postgres 15 with stub tables and the gates' real bodies, then exercised as three made-up people. An assistant's four answers took (a bill's price, a typed one, a row left out, a job on no site). Nine wrong shapes were each refused: a left-out row with a price, a price with none, a negative one, both scopes, neither, a `text:` key, an unknown kind, an unknown source, another person's name. Nobody could update. A superintendent read nothing, wrote nothing and deleted nothing. A primary read all four and took one back. A signed-out caller read nothing. Deleting the bill line kept the price with the line set null, and deleting the development took its answers with it. The stub is not the app's schema and Postgres 15 is not the app's 17, so this proves the SQL's logic, not its fit; the dry run at the push still matters.
