# 20261024160000_email_box_count.sql (2026-10-24, v2.5814)

Quickfill's Email station reads Gmail's own labels (punch list #159, PR 1 of 5). Three tables, three
settings, one policy helper and one cron, all for the `gmail-count` edge function that PR 2 adds.

- **`email_box_watch`** — the app's own list of what it reads: a shared box (`user_id` null: bids@,
  work@) or a person's own mailbox (`users.email`), the labels the row names (`Inbox`, `Follow Up`,
  `Next Actions` by default), `is_on`, `added_by`, and the sweep's health for that box (`last_run_at`,
  `last_ok_at`, `last_error`). One row per address, lower-cased. Deleting the person deletes the row
  and everything under it. A `BEFORE UPDATE` trigger (`email_box_watch_guard`) lets a person change
  their own labels and switch and refuses anyone but the owner or a dev changing the address or whose
  box it is.
- **`email_box_threads`** — one row per thread the sweep saw in a counted label: `arrived_at` (the
  first message's date), `last_at`, `from_name`, `from_address`, `subject`, `first_seen_at`,
  `last_seen_at`, `gone_at` (set when a sweep no longer finds it: cleared). Never a body or a file.
  Unique on `(watch_id, label_name, gmail_thread_id)`, a partial index on the open rows.
- **`email_box_days`** — the trend: one row per box, label and app-calendar day with `count`,
  `oldest_days`, `new_count`, `cleared_count`; the last sweep of the day wins.
- **Settings** in `app_settings`: `email_count_on_v1` (`'false'`), `email_count_lead_v1` (the one
  lead's user id, empty), `email_count_limit_days_v1` (`'3'`), changed only by the owner or a dev
  through `master_or_dev_update_email_count`.
- **Who sees what**: `email_box_can_see(watch)` (SECURITY DEFINER, stable): the office team for a
  shared box; the person and the lead for a person's box; nobody else, the owner included unless he
  names himself the lead. The watch table's SELECT adds the owner and a dev (the list itself), its
  INSERT and DELETE are theirs, its UPDATE is theirs or the person's own row. The threads and the
  trend are SELECT through `email_box_can_see` and written by the service role alone.
- **Cron** `gmail-count`, every 15 minutes, posting to `/functions/v1/gmail-count` with the cron secret
  only while `email_count_on_v1` reads `'true'`. The function lands in PR 2; while the switch is off
  nothing posts.
- The three fences cover the new tables.

Apply with `supabase db push` after the PR merges, from the main checkout; then regenerate
`src/types/database.ts` in its own PR. No client reads the tables until PR 3 (the Settings cards) and
PR 4 (the station), so order does not matter against the client. The Google admin step (adding
`https://www.googleapis.com/auth/gmail.metadata` to the service account's domain-wide delegation row)
comes before the switch goes on, with PR 2.
